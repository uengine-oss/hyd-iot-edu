# 교재 전체 점검 (고치지 않는다 · Opus)

> 자리표시: `<저장소>`는 저장소 루트, `<작업 폴더>`는 저장소 밖의 임시 작업 폴더(본문의 「scratchpad」)다. 이 지시문이 쓰이는 단계는 같은 폴더의 `README.md`에 있다.

HYD 제조 AI 교육과정의 이론 교재(PPTX 덱)가 모두 만들어졌다. 사용자가 전체를 한 번 더 점검해 달라고 했다. 사용자의 물음 그대로: **「우리 시스템과 실라버스에 충실한가, 내용이 어색한 데는 없는가, 1일차 · 초반 일차에 비해 뒤로 갈수록 품질이 떨어진 것은 없는가.」** 덱을 고치지 않고, 맡은 덱들을 읽어 찾은 것을 낸다. 서브에이전트를 쓰지 않는다. 트집을 잡으려고 항목을 늘리지 않고, 실제로 고쳐야 할 것만 적는다.

저장소: `<저장소>`. scratchpad: `<작업 폴더>/전체점검/`

## 배경 (알아야 할 것)
- 기준 문서: `production/standards/제작기준.md` — **전체를 먼저 읽는다.** 대상(노베이스 대학생), 실라버스는 틀이면서 방향, 개념은 표준대로 · 예는 HYD 실제 대상으로, 구현 설명 · 단서 · 내부 사정 · 가상 강조를 쓰지 않는다, 한 장 1분 30초(단원 본문 장수 ≈ 이론 분 ÷ 1.5, ±15 %, 모자라면 안 됨), 메시지는 쓸모를 말한다, 같은 문장 틀 반복 금지, 실습은 2장, 문어체, AI가 쓴 티 금지.
- 만들어진 순서와 방식: 통합반 1~4일차는 사용자와 여러 차례 다듬어 컨펌받은 덱이다(그림체와 화법의 기준). 통합반 5~11일차는 그 뒤 하룻밤에 작업자들이 일차마다 따로(여럿은 동시에) 썼다. 실전반 온라인 2~8일차와 오프라인 19개 회차는 통합반 덱에서 장을 가져와 조립한 것이다(`조립.py`, 새로 쓴 장은 `새장_*.md`). 그래서 사용자가 걱정하는 「뒤로 갈수록 품질 저하」는 실제로 있을 수 있다 — 솔직하게 본다.
- 실라버스: `production/standards/피지컬AI_실라버스_최종본.xlsx`(시트 넷. `cd` 저장소 뒤 `uv run --no-project --with openpyxl python`으로 읽는다).
- 시스템의 사실: `production/standards/통합반_01일차_기술사실표.md`, `통합반_02-04일차_기술사실표.md`, `통합반_05-08일차_기술사실표.md`, `통합반_09-11일차_기술사실표.md`(저장소 코드와 실행 기록에서 뽑은 것. 각 문서의 「확인 못 한 것」 「실라버스와 구현이 다른 곳」 절 포함). 사실표로 가려지지 않는 것은 저장소 코드(`services/`, `students/`, `docs/`)를 직접 찾아 확인해도 된다(읽기만. `.env`는 열지 않는다. docker · 실행 중인 시스템은 건드리지 않는다).

## 품질의 기준선 (모든 점검자가 같은 것을 읽는다)
`production/decks/integrated/day01/통합반_01일차.md`의 온톨로지 단원(간지 「…온톨로지…」부터 그 단원 끝까지)과 `production/decks/integrated/day03/통합반_03일차.md`의 첫 단원을 **먼저 정독한다.** 이것이 컨펌받은 품질이다. 맡은 덱을 이 기준선에 견준다: 한 장이 주는 내용의 밀도, 필요 → 개념 → 적용의 이음, 메시지 문장의 질, 실제 값과 예의 구체성, 노트가 강사의 말로 읽히는가, 표현 수단(삽화 · 실제 데이터 · 도식)의 다양함.

## 볼 것
A. **실라버스 충실**: 맡은 덱의 일차(회차)에 해당하는 실라버스 이론 행의 「상세 교육 내용」 항목이 하나하나 다뤄지는가(항목 → 장 번호로 대조). 다뤄지지 않은 항목, 한 줄로만 스친 항목, 실라버스에 없는데 큰 분량을 차지한 것. 단원 본문 장수와 분 ÷ 1.5의 차이. 실습 행마다 간지 + 설명 한 장이 있고 설명이 실라버스의 실습 내용과 맞는가.
B. **시스템 충실**: 화면의 이름 · 수치 · 식별자 · 도구 이름 · 관계 이름 · 절차가 사실표(와 저장소)와 맞는가. 없는 것을 있다고 쓴 곳, 사실표의 「확인 못 한 것」을 사실처럼 쓴 곳, 덱 사이 · 장 사이에 같은 대상의 값이나 이름이 다른 곳(예: 같은 사건의 시각 · 유온 · 식별자, 「추천안 / 조치 카드」, 「거절 / 반려」). 장마다 `### 제작 기준` 칸에 근거가 적혀 있다 — 표본으로 장 열 곳쯤 골라 그 근거를 실제로 사실표에서 찾아 맞는지 확인한다(근거 표기가 헛것인지 가리는 것이 목적이다).
C. **어색함**: 문장이 어색하거나 뜻이 불분명한 곳, 번역투, AI가 쓴 티(같은 문장 틀의 되풀이 · 구호 · 「핵심은」류 · 과장 · 의미 없는 대구), 유치한 표현, 앞뒤 장이 이어지지 않는 곳, 앞에서 정의하지 않은 용어를 쓰는 곳, 노트가 지시문이거나 화면에 없는 새 내용을 담은 곳, 구현 설명 · 단서 · 변명. 단원마다 메시지만 이어 읽어 이야기가 되는지 본다.
D. **기준선 대비 품질**: 위 기준선과 견줘 맡은 덱이 나은지 · 같은지 · 못한지, 못하다면 무엇이 못한지(예: 정의 낭독이 이어진다, 표 · 카드만 이어지고 그림이 없다, 예가 일반론이고 실제 값이 없다, 메시지가 정의 문장이다, 장이 얇다, 노트가 화면을 되읽는다). 덱 안에서도 앞 단원과 뒤 단원(특히 정리 · Wrap-up 단원)의 품질 차이를 본다.
E. **화면**(통합반 덱을 맡은 점검자만): 덱마다 scratchpad로 렌더해(**출력 PPTX는 반드시 scratchpad로**: `uv run --no-project --with python-pptx --with pymupdf python .claude/skills/lecture-deck/scripts/deck2pptx.py <덱.md> <scratchpad/전체점검/이름.pptx> --render <scratchpad/전체점검/이름_r>`, 묶음은 `uv run --no-project --with pillow python production/tools/deck/시트.py <렌더 폴더> <접두어> --cols 3 --per 9`) 전 장을 훑고, 기준선(1일차)의 화면과 견줘 삽화의 질 · 빈 칸 · 작은 글자 · 같은 형태의 연속이 어떤지 본다. 렌더는 다른 작업과 차례로 돈다(기다린다). 조립 덱(실전반 · 오프라인)을 맡은 점검자는 렌더하지 않는다.
조립 덱을 맡은 점검자가 더 볼 것: 장을 골라 온 탓에 생기는 문제 — 정의 없이 쓰이는 용어, 앞에서 보이지 않은 그림 · 장을 가리키는 말, 통합반의 일차 번호나 「지난 시간」이 틀리게 남은 곳, 단원의 흐름이 튀는 자리, 새로 쓴 장(틀 · 실습 설명 · 퀴즈)의 품질이 가져온 장보다 떨어지는가, 퀴즈가 실린 장만으로 풀리는가. 통합반 원문 자체의 결함은 「원문」이라고 표시해 적는다.

## 산출물
scratchpad `전체점검/결과_<프롬프트가 주는 이름>.md`:
1. **덱별 점수표** — 덱마다 한 줄, 다섯 항목을 1~5로(5 = 기준선과 같거나 낫다, 3 = 눈에 띄게 못하다, 1 = 다시 써야 한다): `덱 | 실라버스 충실 | 시스템 충실 | 문장 · 흐름 | 내용의 밀도와 구체성 | 표현 수단 | 한 줄 평`. 점수는 후하게 주지 않는다. 기준선 덱 자체를 맡았으면 5를 기준으로 삼되 흠은 그대로 적는다.
2. **고칠 것 목록** — `심각도(상 · 중 · 하) | 덱 | 장 번호 「제목」 | 문제(원문 인용 한 줄) | 고치는 법(한 줄, 가능하면 바뀔 문구)`. 상 = 사실 오류, 실라버스 항목 누락, 없는 것을 있다고 씀, 뜻이 틀리게 전달됨, 유치함 · 내용 없음. 중 = 어색한 문장, 흐름 끊김, 문장 틀 반복, 정의 없는 용어, 구현 설명 · 단서, 덱 사이 불일치. 하 = 사소한 표현. 덱마다 「상」과 「중」을 빠짐없이, 「하」는 대표적인 것만.
3. **뒤로 갈수록 품질이 떨어졌는가**에 대한 답 — 맡은 범위에서 예 · 아니오와 근거(어느 덱 · 어느 단원이, 무엇이).
4. 확인하지 못한 것.
