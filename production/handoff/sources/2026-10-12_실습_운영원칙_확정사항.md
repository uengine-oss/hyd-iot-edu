## 1. 가장 중요한 결론

1. **Lab은 수업 안에서 직접 무언가를 만들고 시험하는 활동을 가리키는 내부 표현**이다. 실제 실라버스 표의 `구분`에는 오직 **`이론` / `실습`**만 사용한다. `Lab`, `랩`, `체험`, `과제`, `시연`을 제3의 구분으로 만들지 않는다.
2. **온라인에서 강사가 혼자 코드를 작성하거나 포털·bpmn.io를 조작해 보여줘도 `실습`**이다. 화면 조작·작도·파일 생성·도구 연결·실행·결과 확인은 이론이 아니다.
3. **오케스트레이션에는 별도의 VS Code 코딩 Lab이나 BPM 엔진 개발 Lab을 넣지 않는다.** 그러나 **bpmn.io 사용법 익히기, BPMN 직접 그리기, HYD 포털에서 가져오기·매핑·검사·배포·실행**은 기존 범위의 **`실습`**으로 반드시 유지한다. 즉, **“독립 Lab 없음” ≠ “실습 없음”**이다.
4. **Wrap-up = 복습**이다. Lab이 아니며 `구분=이론`. **온톨로지·에이전트·프로세스 등 영역의 마지막에 30분**, 새 실습·과제 없이 학습을 정리한다. 매일 추가 복습을 만들라는 뜻은 아니며, **Wrap-up 뒤에는 새로운 실습을 배치하지 않는다.**
5. **공통 핵심 실습은 통합반과 실전반이 같다.** 실전반은 같은 핵심 산출물을 만든 후 **선택한 일부 실습에만 현실적인 복합 조건·제약·예외 처리를 더한다.** 실전반이 별도의 대형 프로젝트를 새로 만드는 과정은 아니다.
6. **온톨로지·업무 DB·SOP·DMN 등 앞부분에서 만든 자산을 뒤의 에이전트 실습에서 재사용한다.** 응용이 바뀔 때마다 온톨로지/DB를 재구축하거나 단순 데이터 조회 보고서를 반복하지 않는다.
7. **에이전트 응용은 데이터 분석·데이터 패브릭에 편중하지 않는다.** 실제로 수행하는 일과 산출물이 서로 다른 업무를 선정한다. 다양한 응용을 보여주되 **검증되지 않은 구현을 가능한 것처럼 쓰지 않는다.**
8. **실습은 ‘구경’이 아니라 ‘실제 결과물 완성’이 기준**이다. 목적, 입력, 작업 절차, 저장되는 산출물, 성공 판정과 예외를 명확히 한다. 포털 버튼 클릭이나 로그 조회만으로 긴 시간을 채우지 않는다.
9. 신규 편성 활동의 시간은 **한 행당 50분 이하**가 원칙이다. 단, **이미 잠긴 통합반 온라인 1~4일차 승인본의 기존 시간·행은 건드리지 않는다**(그 안의 인제스천 70분 활동 등). 개별 활동 상한과 **과정별 전체 시수**는 별개다.
10. **확정된 편성을 이 문서 작성 때문에 다시 변경하지 않는다.** 이 문서는 *의사결정의 기록*이며 새로운 실습을 추가하거나 시간을 재편성하는 제안서가 아니다.

## 3. 시간·과정별 공통 운영 규칙

### 3.1 시간표의 형식

학생에게 제공하는 실라버스 표는 기본적으로 **`구분 | 제목 | 상세 교육 내용 | 시간(분)`** 네 열이다. `구분`의 값은 **이론 또는 실습**이다. 제목은 **학습자가 얻는 가치·할 수 있게 되는 일 중심**, 도구·프레임워크 명칭과 구체적 작업은 **상세 교육 내용**에 정확히 기재한다.

상세 내용에는 단순히 ‘이해하기’, ‘경험하기’라고 쓰지 않는다. 필요한 만큼 **배경·개념·이전 학습과의 연결·도구·입력 자료·학생/강사의 실제 행동·결과 파일·검증 방법**을 적는다. 단, 한 실습의 연속 작업을 10~15분짜리 유사 행으로 끝없이 분리하거나 ‘3개 프로세스 비교하기’처럼 자체 가치가 약한 별도 행을 추가하지 않는다.

### 3.2 시간 합계

| 과정 | 편성 | 실제 교육 시간 | 휴식 처리 |
|---|---|---:|---|
| 통합반 온라인 | 11일 × 240분 | **44시간** | 표에서 별도 휴식 차감 없음 |
| 실전반 온라인 | 8일 × 240분 | **32시간** | 표에서 별도 휴식 차감 없음 |
| 통합반 오프라인 | 정규 10회 × 240분 | **각 회 실제 수업 200분** | 회차마다 휴식 40분 별도, 총 달력상 40시간 |
| 실전반 오프라인 | 정규 9회 × 240분 | **각 회 실제 수업 200분** | 회차마다 휴식 40분 별도, 총 달력상 36시간 |

오프라인은 `50분 수업 + 10분 휴식` × 4교시다. **수업 200분 + 휴식 40분 = 240분**이며, 한 회차의 200분에 Wrap-up 30분도 포함해야 한다. 개강특강 120분과 기업과제는 **이번 담당 실라버스 범위 밖**이다.

### 3.3 온라인과 오프라인의 역할

| 운영 요소 | 온라인 | 오프라인 |
|---|---|---|
| 실행 주체 | **강사 1인이 이론 설명·구현·실행·결과 확인을 촬영/시연** | **학생이 강사와 함께 직접 수행**. 온라인보다 진행이 느림 |
| 이론 | 초보자가 이해할 수 있도록 WHY·정의·원리·예시·연결 이유를 충분히 설명 | **회차당 보통 20~30분, 최대 30분 정도**. 필수 개념은 남기고 중복 설명·예시를 압축 |
| 실습 | 무엇을 왜 만들고, 어떤 결과가 나오는지 상세한 시연 | 직접 조작·프롬프트 작성·수정·오류 해결에 학습시간 집중 |
| 포털 | 필요한 기능을 직접 만들고 실행. 단순 반복 구경 금지 | 필요한 연결·확인만 간결하게, 포털만 50분씩 보기 금지 |
| 지속성 | 앞서 만든 코드·데이터를 다음 날 재사용 | **쉬는 시간 뒤 같은 실습을 이어서 수행 가능**. 교시마다 파일/프로젝트 강제 초기화 금지 |
| 실습 수준 | 기본 과제 + 다양성을 보여주는 선택 응용 | 핵심 과제 선별, 학생 완주와 일부 조건 검증 중심 |

오프라인 이론 환산의 **예시 지침**: 온라인 50~60분 설명 → 오프라인 약 25~30분, 온라인 40분 → 약 20분, 온라인 30분 → 약 20분, 원래 매우 짧으면 약 절반. 이것이 모든 이론 행에 기계적으로 적용하는 고정 공식은 아니며, **회차당 이론 총량 최대 30분 원칙**이 우선한다.

> **시간 주의:** 모든 신규 활동은 최대 50분을 기준으로 나누되 **한 업무를 의미 없이 잘게 쪼개지 말 것**. 소개→설계→도구 조작→실행→검토가 자연스럽게 연결된 하나의 가치 단위로 편성한다. 시간은 **설계 추정치**이며 녹화/학생 리허설 **실측치**와 다르다.

## 4. 교육 내용의 큰 흐름과 공용 자산

`온톨로지의 필요성 → 클래스·인스턴스·스키마·그래프 DB → SOP·DMN·BSC/KPI → 문서 인제스천(영역 마지막) → 에이전트 원리·제작 → Skill·MCP → HITL → SDD → BDD·응용 → BPM/BPMN·프로세스 오케스트레이션 → 사람·AI·기업 시스템이 연결된 업무 완주`

| 앞에서 준비한 자산 | 뒤에서 어떻게 재사용하는가 | 하면 안 되는 것 |
|---|---|---|
| 온톨로지 스키마, 클래스·인스턴스, 노드·관계, Neo4j | 에이전트의 원인 후보 조회·업무 맥락 이해·근거 추적 | 에이전트 Lab마다 그래프 DB를 처음부터 재설계 |
| SOP·DMN 결정표 | 조치 금지 조건·작업 절차·판단 근거·검증 기준 | 단순 문서 생성만으로 규칙을 실행했다고 주장 |
| BSC·KPI·What-if | 조치의 비용·생산 영향·성과 판단 근거 | 수치가 없는데 비용·효과를 사실처럼 만들어 냄 |
| 검토·적재한 매뉴얼·출처 | 에이전트 답변 근거·학습 퀴즈·작업 제안의 원문 확인 | 검토 전 후보를 확정 지식으로 취급 |
| 기존 업무 DB·설비 시계열·HYD 포털 | 고장 추론·데이터 분석·품질 판단·업무 자동화 등 | 모든 실습을 ‘기존 데이터 조회→보고서 생성’으로 반복 |
| 학생이 만든 에이전트·Skill·MCP 설정 | 후속 HITL·SDD·BDD에서 같은 구현 재사용, BPMN에서 역할 배정 | 매 회차 처음부터 에이전트를 새로 생성 |

**중요한 분리:** 온톨로지 초반의 `schema.json`/Cypher를 사용한 소량 노드·관계 적재는 **그래프 모델링 실습**이다. **문서 인제스천(원문→추출→매핑→검토·승인→지식 반영)**을 앞당긴 것이 아니다. **본격 인제스천은 각 과정 온톨로지 영역 마지막**에 배치한다.

## 5. 온톨로지 영역의 실습 합의

### 5.1 공통 핵심 활동

| 단계 | 실습의 목적·작업 | 반드시 확인할 산출물/조건 |
|---|---|---|
| 초기 준비·관계 확인 | Notion 학습노트 생성, HYD 환경·첫 설비 이상 시연, arrows.app에서 설비·센서·원인·조치 관계 작성 | Notion 페이지·관계도·초기 데이터→경보→판단→조치의 흐름. 포털 전체 시연은 불필요하게 반복하지 않음 |
| 온톨로지 모델링 | 클래스/인스턴스/속성/카디널리티·식별자를 정의하고 `schema.json` 및 샘플 노드·관계를 구성, Cypher로 Neo4j 조회·적재 | 관계 방향·속성·식별자와 실제 그래프 조회 결과; **학생 랩 전용 DB와 HYD 기준 그래프 구분** |
| 조치 판단 | 제공된 SOP의 단계·금지 조건을 구조화하고 DMN 결정표 작성, BSC/KPI·What-if로 허용/제외 및 조치 효과 판단 | 판단 조건·근거·비교 결과. **새 문서 인제스천을 여기서 진행하지 않음** |
| **온톨로지 영역 마지막: 인제스천** | 매뉴얼 등록→정보 추출→원문 대조→검토·승인→적재→지식 지도·출처 확인, 필요시 개정 사항 검토 | 검토 완료 지식, 출처·개정 정보, 적재 결과. **바로 뒤 Wrap-up 30분** |

### 5.2 실전반의 응용 방식

통합반과 **동일한 기본 관계 모델·그래프 구현·판단 기준·인제스천 결과**를 만든다. 일부 실습에만 **공용 부품/복수 센서 관계, 조건 충돌, 복합 SOP·DMN 조건, 매뉴얼 개정 내용과 기존 지식의 불일치** 같은 현실 제약을 추가한다. 모든 실습을 복잡하게 만들 필요는 없다. **인제스천을 에이전트 파트로 옮기거나 생략하지 않는다.**

## 6. AI 에이전트 영역 — Lab을 다양하게 구성하기로 한 이유

### 6.1 의도

처음에는 온톨로지·DB를 조회해 문서로 요약하는 비슷한 Lab이 반복될 위험이 있었다. 최신 결정은 **에이전트가 실제로 다른 일을 하게 만들자**는 것이다. 온톨로지·SOP·DB는 **필요할 때 쓸 수 있는 공용 자산**이며, 독립된 데이터나 파일 기반 예제를 사용하는 별도 응용도 허용한다.

| 응용 유형 | 에이전트가 하는 일 | 결과물·학생이 얻는 가치 | 자료·환경 |
|---|---|---|---|
| 설비 고장 추론·점검 결정 | 센서/온톨로지/SOP 근거로 원인 후보를 좁히고 다음 점검 순서를 추천 | **점검 대상·우선순위·근거**, 단순 그래프 Q&A보다 한 단계 나아감 | HYD 공용 지식·센서 자료 |
| 품질 불량 후속 처리 | 불량 접수를 분류하고 누락 정보를 확인한 뒤 담당 업무·후속 조치를 제안 | **품질 대응 항목/처리 초안** | 별도 불량 접수 자료 가능 |
| 센서 데이터 분석 | 복수 센서의 변화·이상 구간을 분석하고 시각화, 가설 구분 | **차트·이상 구간·가설** | HYD 시계열 또는 CSV |
| 데이터 패브릭 활용 | 설비·정비·부품 등 서로 다른 출처의 정보를 한 업무에 모아 사용 | **근거가 연결된 업무 결정/인수인계** | 연결 가능한 DB 또는 준비된 동일 구조 자료 |
| 회의 후속 업무화 | 회의록에서 결정사항·담당자·기한을 추출하고 항목별 다음 행동 생성 | **구조화된 작업 목록** | 회의록 문서, 파일 기반 별도 Skill |
| 대화형 AI 학습 코치 | 매뉴얼·학습노트에서 퀴즈를 만들고 답변별 피드백·후속 질문 수행 | **근거 있는 대화형 퀴즈/해설** | Notion 내보낸 Markdown/기존 매뉴얼 |
| 사람에게 확인받는 업무 | 정보가 없을 때 멈추고 질문, 답변 후 재개 | **보류→확인→재진행 기록** | 앞에서 만든 업무 에이전트 재사용 |
| 제안·검토 분담 | 한 에이전트가 초안 작성, 다른 에이전트가 오류·근거 누락을 점검 | **제안·검토·수정 기록** | 기존 에이전트 응용 |
| 교대 인수인계 | 완료 조치·남은 작업·주의할 점을 여러 기록에서 모음 | **근거 있는 인수인계서** | 설비 이벤트·작업 기록·DB |

**이 목록은 승인된 수업의 응용 범위/사례를 설명하는 것이지 모든 과정에서 위의 9개를 전부 독립 실습해야 한다는 뜻이 아니다.** 구체적인 세부 배치는 확정 XLSX를 따른다. 특히 실전반 온라인의 시간은 통합반 에이전트 온라인의 절반이므로 선택 응용 수를 줄인다.

### 6.2 에이전트 기본 실습 — 반드시 직접 수행

- **HYD 포털에서 나의 에이전트 생성:** 역할·목표·사용 도구 설정, 질문 실행, 답변의 근거와 호출 결과 확인. 제공된 기준 에이전트를 읽기만 하고 끝내지 않는다.
- **VS Code·Claude Code에서 실제 결과를 만드는 에이전트 제작:** 앞에서 준비한 온톨로지·업무 DB·SOP 등을 필요에 따라 사용하여 점검 결정이나 업무 처리를 수행한다. Text-to-Cypher나 정보 조회만 반복하지 않는다.
- **실습의 차별성:** 에이전트의 호출·추론 과정이 보이고, **파일·작업 목록·점검 결과·대화형 반응 등 기능적 결과물**이 남아야 한다.

### 6.3 Skill 실습 — 사용법 설명에서 끝내지 않음

- `SKILL.md`의 목적·호출 조건·입력·출력·절차·예외 처리를 이해하고 **재사용 가능한 업무 수행 지침을 작성**한다.
- **SOP는 현장 업무 절차**, **Agent Skill은 에이전트에게 수행 방법을 제공하는 지침**이라는 차이를 구분한다.
- 회의록→담당자별 후속 작업, 매뉴얼/학습노트→대화형 퀴즈처럼 **전혀 다른 가치가 있는 응용**을 사용한다.
- 결과가 잘못되었거나 근거가 빠진 경우 수정을 포함한다. 단순히 `.md`를 하나 만들었다고 실행 확인을 대체하지 않는다.

### 6.4 MCP — 서버 하나만 연결하는 실습이 아님

**최신 합의:** MCP를 여러 개 실제로 연결·호출·비교해본다. **HYD 내부 업무 도구**뿐 아니라 **파일시스템·Git·시간** 등 **서로 다른 종류의 MCP 서버 3종 이상**을 **사전 준비된 환경에서 시험하고 조합**하는 구성을 기본으로 한다.

| 위치 | 가능한 공통 활동 | 반드시 구분할 제약 |
|---|---|---|
| HYD 포털 도구(MCP) | 업무 DB·온톨로지·판단 관련 MCP 확인, 서버 등록·연결 검사·읽기 도구 호출, 결과/기록 확인 | HYD 포털의 등록/검사/에이전트 도구 선택 제약을 따른다. 모든 로컬 MCP를 그대로 등록 가능하다고 가정하지 않음 |
| VS Code·Claude Code | 사전 준비된 **Filesystem, Git, Time** 등 여러 MCP 연결, 도구 검색·호출·결과 비교, 파일 읽기→변경 이력 확인→결과 파일 저장 등 조합 | 각 서버 실행 방식(stdio/HTTP), 권한, 경로·계정 제약과 환경별 가용성을 사전 확인 |
| 외부 서비스 확장(조건부) | Fetch, Notion, Google 서비스 등으로 확장 가능성 소개 | 실제 계정·토큰·권한·네트워크가 검증된 경우에만 실습 확정. **필수 완주 조건으로 임의 추가 금지** |

**실전반의 심화:** MCP 설치 개수를 늘리는 것이 아니라 **이미 연결한 여러 도구를 묶어 하나의 업무를 완결**하고, 파일/권한/연결 오류 및 불완전한 입력을 처리한다.

### 6.5 HITL → SDD → BDD는 한 이야기로 이어짐

1. **HITL:** 에이전트가 판단했다는 이유만으로 자동 승인하지 않는다. 사람의 승인·보류·거절과 권한을 설명하고 HYD 작업함에서 상태 변화를 확인한다. 필수 정보가 없으면 **보류→질문→응답 후 재개**. **AI끼리 독립 검토**하는 것은 사람 승인과 다른 기능이다.
2. **SDD(에이전트 영역 후반):** 기존 업무 에이전트가 정상 동작하는 상태에서 **새 요구(예: 긴급 정비 분류)**를 넣는다. 모호한 바이브 코딩 변경으로 기존 출력 계약/승인 규칙이 흔들릴 수 있는 **사전 확인된 반례**를 보여준다. `spec.md`에 **기존에 지킬 것 + 새 기능 + 불변 조건 + 입력·출력 계약 + 수용 기준**을 적고 명세를 기준으로 코드와 기능을 수정한다. **`spec.md`만 고치는 실습은 아님**.
3. **BDD(다음 단계):** **같은 코드·같은 명세**에 `Given / When / Then`으로 **일반 요청, 긴급 요청, 정보 누락, 승인 거절, 도구 오류, 회귀 테스트**를 수행한다. 실제 실패 원인 수정→재실행→기존 기능 보존 확인을 한다. 새로운 프로젝트나 DB를 다시 만들지 않는다.

> ‘바이브 코딩을 하면 반드시 기존 기능이 망가진다’고 주장하지 않는다. **실패 비교를 교육에 쓰려면 입력 데이터·기존 코드·실패 조건을 먼저 재현**해야 한다. 재현되지 않으면 임의의 실패 화면을 만드는 대신 준비된 테스트/반례를 사용한다.

### 6.6 온라인·오프라인, 통합·실전의 사례 선택

| 과정 | 에이전트 편성 | 실제 Lab 구성 원칙 |
|---|---|---|
| **통합반 온라인** | 5~8일차 | 기본 에이전트 → 다양한 응용(추론·품질·데이터 분석) → Skill·다중 MCP·회의록·학습 코치 → HITL·SDD → BDD·교대 인수인계 → 영역 Wrap-up 30분 |

**오프라인은 온라인의 모든 선택 실습을 가져오지 않는다.** 학생 완주 가능성을 우선하여 핵심을 **선별해 깊게 수행**한다. 이미 학생이 이해한 내용은 간결하게 설명하고 바로 직접 구현한다. 하나의 실습을 쉬는 시간 뒤 계속 진행해도 된다.

## 7. BPMN·프로세스 오케스트레이션 — 별도 Lab 없음, 기존 실습은 필수

### 7.1 정확한 뜻

- **금지:** 오케스트레이션 파트에 새 **독립 VS Code Lab**, 자체 BPM 엔진 코딩 프로젝트, 새 인프라 구축 과제, 기존 학습과 무관한 대형 외부 연동 Lab 추가.
- **필수 `실습`:** **bpmn.io 사용법 숙지 → 간단한 승인 흐름 그리기 → 실제 업무 BPMN 작성 → HYD 포털 가져오기·에이전트/역할/시스템 매핑·사전 검사·등록·배포 → 이벤트로 실행·결과 확인**.
- **이론:** 프로세스 정의/필요성, End-to-End, BPM 생명주기, BPMN 2.0 모델링 요소, 프로세스 엔진·정의·인스턴스·변수·상태, Agent/User/Service Task, 승인·분기·타이머·권한·예외·기록·운영. **BPMN을 단순 도형 사용법으로만 가르치지 않는다.**
- 도구 조작은 강사 단독 시연이어도 **이론이 아니라 실습**으로 적는다.

### 7.2 세 가지 실제 업무 흐름 — 모두 직접 그려 실행

| 흐름 | 기초 시나리오 | 수행·확인 내용 | 주의 사항 |
|---|---|---|---|
| **설비 이상 대응** | 쿨러 열화 경보 → 에이전트 진단/제안 → 운전원 승인·거절 → PLC 명령 → 효과 확인 → 결과 | BPMN 역할·승인/거절 경로·승인 지연 알림을 그리고, 실제 경보로 처리 건을 완주 | 거절 시 설비 명령 없음. **승인 지연 알림은 자동 반려가 아님** |
| **정기 점검** | 점검 도래 → 정비 계획 에이전트 → 보전팀장 승인·거절 → CMMS 정비 오더 → 생산팀 공지 → 종료 | 직접 작도, 매핑·검사·배포, 점검 이벤트로 실행해 실제 오더·공지 결과 확인 | **설비 제어 단계가 없는 기업 업무 흐름** |
| **재고 보충** | 재고 부족 → 구매 에이전트 → 구매 담당 승인·거절 → ERP 발주 → 공급사 통지 → 시뮬레이션상 입고·재고 반영 → 종료 | 직접 작도, 매핑·검사·배포, 재고 보충 이벤트로 발주·입고 반영 확인 | 실제 실물 물류 지연을 연기하는 흐름으로 **임의 확장 금지**. 현 구현의 단순 종료 구조 유지 |

**세 업무의 실행 결과를 비교하기만 하는 별도 소규모 실습 행을 만들지 않는다.** 각 업무의 ‘설계하기’와 ‘연결·실행하기’ 속에서 실행 확인을 자연스럽게 포함한다. A/B/C 같은 시나리오 부호는 내부 식별 용도로 사용할 수 있으나, **학생용 큰 제목에는 가치 중심 표현**을 사용한다.

### 7.4 반드시 표시할 구현상의 제약

- HYD 포털의 BPMN 가져오기 화면에는 **일부 시스템 단계의 상세 연결 설정 입력 칸이 부족**하다. `*.mapping.json`과 **검증된 API 절차**로 매핑해야 하는 경우가 있다. **포털 클릭만으로 모든 매핑을 완료할 수 있다고 적지 않는다.**
- 예제 A·B·C의 BPMN 및 매핑 참고 파일이 HYD 레포 `students/flows/`에 있다. 사용할 파일이 실제 환경에서 작동하는지 확인한다.
- 공용 서버에서 **동일 경보에 대해 마지막에 배포된 학생 흐름이 경로를 가져갈 수 있다.** 실습 조별 네임스페이스·배포 순서·기준 흐름 복원 절차를 준비한다.
- 시험이나 시연에서 **실제 프로세스 실행 검증이 된 범위**와, 화면에서 아직 확인되지 않았거나 외부 연동이 필요한 범위를 구분한다.

## 8. Lab을 새로 작성하거나 교재로 전환할 때의 작성 규칙

한 활동마다 다음 항목을 구체적으로 채운다. 이것은 **실습의 준비·검증 체크 항목**이며, 실라버스 표에 열을 늘리라는 뜻은 아니다.

| 검토 항목 | 문서에 적을 내용 |
|---|---|
| 학습 가치 | 학생이 기존에 못 하던 **무엇을 할 수 있게 되는지** — 도구명이 아니라 업무 결과 |
| 선행 조건 | 이전 회차에서 준비된 자산, OS/VS Code/Claude Code/HYD/DB 실행 상태, 로그인·권한·사전 자료 |
| 입력 | 정확한 사건·샘플 문서·CSV·DB 테이블·센서 태그·업무 규칙 등. **없는 데이터를 지어내지 않음** |
| 수행 주체·도구 | 학생 직접/강사 단독, HYD 포털/Neo4j/bpmn.io/VS Code 등 |
| 실제 동작 | 설정→프롬프트·작성/작도→연결→실행→결과 확인. 단순 기능 소개만 하지 않음 |
| 산출물 | `schema.json`, Cypher, `SKILL.md`, 실행 가능한 에이전트, `spec.md`, BDD 테스트 결과, `.bpmn`, 처리 기록 등 **확인 가능한 결과** |
| 완료 판정 | 어떻게 성공인지 확인하는가? 결과값·출처·그래프 질의·도구 호출 결과·실제 프로세스 상태 등 |
| 실패·예외 | 권한 거절, 입력 누락, 도구 오류, 승인 실패 등 **실제 지원/재현 가능한 경우만** |
| 복원 절차 | 공용 데이터 보호, 학생 생성 자산 분리, 학생 배포 흐름 해제/기준 흐름 복원, 비밀값 제거 |
| 시간 근거 | 소개→설계→구현→실행→검토→수정이 **50분 이내** 가능한지 추정; 현장/녹화 실측과 구분 |

**좋은 상세 내용의 예:** “제공된 센서값과 온톨로지의 고장 관계·SOP를 조회해 원인 후보와 점검 우선순위를 만드는 에이전트를 작성하고, 결과에 연결된 근거·미확인 정보를 확인한다.”

**나쁜 상세 내용의 예:** “에이전트 체험하기”, “데이터 분석 실습”, “MCP 이해하기”, “BPMN 실행 결과 비교”, “틀린 것을 찾아 수정하기(어떤 오류가 있는지 확인되지 않음)”.

## 9. 실습 관련 금지·주의 체크리스트

- [ ] 학생 표의 `구분`에 **이론/실습 이외 표현**을 넣지 않았는가?
- [ ] **Wrap-up은 영역 말미 30분 복습**이며 이후 신규 실습이 없는가?
- [ ] 승인한 **통합반 온라인 1~4일차**의 시간·문구를 임의 변경하지 않았는가?
- [ ] **본격 인제스천은 온톨로지 영역 마지막**에 있고, 초기 그래프 적재를 인제스천과 혼동하지 않는가?
- [ ] 에이전트의 공용 온톨로지·DB·SOP **재사용**이 실제 연결 구조에 근거하는가?
- [ ] 고장 추론·품질·분석·회의록·학습 코치·인수인계가 **서로 다른 결과**를 만들며 비슷한 조회 보고서를 반복하지 않는가?
- [ ] MCP는 **여러 서버를 시험**하되 HYD 포털 기능과 로컬 VS Code 연결 제약을 구분했는가?
- [ ] HITL(사람 결정)과 AI 간 독립 검토를 명확히 구별했는가?
- [ ] SDD가 **기존 동작 보존 + 추가 기능 구현**, BDD가 **같은 구현에 대한 행동·회귀 검증**이라는 흐름인가?
- [ ] 실전반이 **같은 핵심 실습을 유지하되 일부 응용만 추가**하는가? 모든 Lab을 통째로 복제하지 않는가?
- [ ] 오프라인 **이론 최대 30분/실수업 200분+휴식 40분** 및 학생 진행 속도를 지켰는가?
- [ ] 신규 활동이 **50분 이하**인가? 기존 잠금 승인본에 소급해 임의 수정하지 않았는가?
- [ ] **BPMN 독립 코딩 Lab 없음**과 **bpmn.io·HYD 직접 실습 있음**을 혼동하지 않았는가?
- [ ] 설비 대응·정기 점검·재고 보충은 **각각 직접 작도·매핑·실행**하는가?
- [ ] 실행 검증 없는 외부 API/계정/도구를 필수 실습으로 단정하지 않았는가?
- [ ] 수업 시간·실행 검증을 **설계 추정 vs 실제 실측**으로 구분했는가?
- [ ] 개강특강·기업과제 등 담당 범위 밖의 활동을 덧붙이지 않았는가?

## 10. 다음 작업자에게 남기는 고정 지시

**지금 확정된 엑셀을 수정하기 전에 먼저 사용자의 새로운 변경 지시가 있어야 한다.** 이 문서는 기존 승인 결정을 상세히 기록하는 것이지 새 수업안을 승인받는 절차를 대신하지 않는다. 새로운 Lab 아이디어가 떠올라도 먼저 **어느 과정/회차의 어떤 학습 목표를 대체하며 시간과 산출물이 어떻게 달라지는지**를 보여주고, 기존 공용 자산과 실제 기능을 확인한 뒤 반영한다.

**가장 중요한 한 문장:**  
> **온톨로지로 신뢰할 지식을 준비하고, 에이전트 실습에서는 그 지식과 도구로 ‘서로 다른 실제 업무’를 완성하며, 프로세스 오케스트레이션에서는 별도 코딩 Lab 없이 BPMN을 직접 그려 사람·AI·시스템의 실행을 연결한다. 모든 과정의 학습 결과는 같은 핵심을 공유하고, 실전반에서 선택적으로 현실 조건을 더한다.**
