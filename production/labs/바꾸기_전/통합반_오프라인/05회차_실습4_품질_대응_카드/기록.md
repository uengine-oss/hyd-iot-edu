## 이 묶음의 상태
- 수업 도구는 VS Code의 GitHub Copilot 채팅(GPT-6 Luna)이다. 이 PC에는 VS Code와 Copilot이 없어서 **Copilot으로는 한 번도 돌려 보지 못했다.** `완성/`과 `기록/`은 2026-10-13에 Claude Code로 대신 돌린 것이다(macOS, Python 3.14). Copilot과 GPT-6 Luna로 다시 돌려 바꿔야 한다.

- Copilot의 답과 VS Code 화면을 보여 주는 자리는 모두 사진 자리로 비워 두었다(`찍어_주실_화면.md`, 10곳). 가이드에 글로 실은 카드와 표는 `완성/결과/`와 `기록/`의 결과 파일(`3_결과_Q01.json`, `4_결과.json`, `6_결과.json`, `7_결과.json`)에서 스크립트가 읽어 옮긴 것이다.

- 6차례 뒤 열두 건의 유형과 추가 확인 항목이 4차례와 같은지, 카드의 칸이 아홉 그대로인지 스크립트로 보았다(같았다). 8차례 뒤 결과 json과 `도구.py`가 7차례와 바이트까지 같았다.
- `완성/`을 다른 곳에 복사해 `python3 에이전트.py`를 다시 실행했을 때 결과 두 파일이 바이트까지 같았다. 없는 접수 번호를 주면 결과를 건드리지 않고 「그런 접수 번호가 없습니다」라며 끝난다.
- `도구.py`와 `에이전트.py`에 유형 코드, 부서 이름, 원인을 말하는 표현, 로트 번호의 모양, 접수 번호가 적혀 있지 않았다(주석의 실행 예 `Q01` 한 곳만 있다).
- 여유 과제 둘은 `완성/`의 사본에서 사람이 돌려 보았다: 기준의 사진 낱말을 `사진 첨부` · `사진 있음`으로 바꾸면 Q06 한 장만 바뀐다(추가 확인 항목에 사진). `python3 에이전트.py Q09`는 카드 한 장만 남긴다.

## 대신 돌리면서 본 것
- 1차례: 차례를 열 줄로 적고 유형 고르기와 원인 정하기를 「정해져 있지 않음」으로 두었다. Q01의 유형을 스스로 고르지 않았다. 허용 목록에 `원인_분석`이 없어 에이전트는 Q01의 종결된 분석을 볼 수 없다는 것, 표의 대장 줄은 읽어 달라고 해서 직접 본 것이라는 것을 짚었다. 물음은 여섯이었다.
- 2차례: **요청하지 않았는데 「3번 결정이 내는 결과」를 따로 적어, 본문만 보고 확정하면 Q02 · Q03 · Q04 · Q05가 시정 조치로 가고 Q01은 조사 요청으로 간다고 접수 번호를 들어 알렸다.** 그러고 「임시 기준으로 이해하고 그대로 만들겠다」고 했다. `원인_분석` 함수도 미리 써 두겠다고 했고(규칙이 도구를 넷이라고 정해서), 빼라고 하자 뺐다. Q06의 사진과 Q08의 48개가 글자 모양만으로 잡힌다는 한계도 이때 알렸다. 다시 물어 온 것은 다섯이다.
- 3차례: Q01이 미확정 · 조사_요청으로 나왔다. 미분류 카드의 `단서` 칸을 스스로 정했다고 밝혔다.
- 4차례: 프로그램을 고치지 않았다. 시키지 않았는데 「대장과 맞는 것은 Q05뿐」이라고 알렸다(에이전트가 아니라 채팅의 AI가 대장을 읽은 것이다).

- 6차례: 일곱 건이 바뀌었다(Q01 미확정→확정, Q03 · Q04 확정→미확정, Q02 · Q05는 원인의 글과 출처, Q07 · Q09는 근거). 분석 번호를 md의 원인 근거 줄에 넣었다고 밝혔다. 대장의 상태가 종결도 진행도 아니면 오류를 내고 멈추게 했다고 알렸다.

## 덱과 어긋나거나 덱에 없는 것
- **실라버스와 덱의 낱말.** 실라버스는 「불량 유형 · 필요한 확인 정보 · 담당 업무 · 대응 초안」, 덱 37장은 「품질 유형 · 추가 확인 항목 · 담당 부서 · 대응 초안」이다. 카드의 칸 이름은 덱을 따랐다.
- **에이전트가 모델을 부르지 않는다.** 실습 2와 같은 판단이다. 접수 본문은 사람이 쓴 글인데 단서 낱말과 정규식으로만 읽는다. 그래서 생기는 한계(「사진은 아직 찍지 못했고」가 사진으로 잡힌다, 로트 수량이 불량 수량으로 잡힌다)를 8단계의 소재로 썼다. 덱 36장의 「작은 에이전트」와 같은 것으로 보아도 되는지는 사용자가 정해야 한다.
- **「수정한다」를 푼 방식.** 실라버스의 「원인이 미확정일 때 단정하지 않도록 수정한다」를 살리려고, 2단계에서 원인을 일부러 「본문에 원인을 말한 문장이 있으면 확정」으로 정해 만들고(4단계에서 접수자의 말이 「확인된 원인」으로 나가는 카드 넷을 본다) 6단계에서 대장의 종결만 확정으로 고치게 했다. 가이드에 「일부러 가운데 칸으로 간다」고 밝혔다.
- **원인 분석 대장.** 덱에는 원인이 확정인지를 무엇으로 아는지가 없다. 품질팀의 조사 기록(종결 · 진행)을 새로 두어 그것을 읽는 도구를 넷째 도구로 삼았다.
- 실라버스의 도구 표기 「VS Code」만 있고 Copilot은 `lab/만드는_법.md`를 따랐다.
- 저장소의 QMS 조회 도구 `qms_lots`는 쓰지 않았다(스택이 떠 있지 않다). 그 자료의 로트 번호와 수량만 접수 본문에 옮겼다.
- 저장소의 출하 대기 로트 넷은 아직 출하되지 않은 것이어서, 고객이 받은 제품의 접수에는 이미 출하된 로트 번호 셋을 같은 꼴로 새로 들었다.

## 확인하지 못한 것
- Copilot에서의 실행 전체: 화면 문구, `.github/copilot-instructions.md`를 자동으로 읽는지, 터미널 명령 실행을 어떻게 묻는지.
- **GPT-6 Luna가 규칙에 어긋나는 요청 앞에서 Claude처럼 멈추는지,** 「정해져 있지 않은 것」을 보고 되묻는지, 2단계에서 3번 결정의 결과를 미리 알려 주는지, 기준의 내용을 코드에 옮겨 적지 않는지.
- 학생 PC의 파이썬 명령(`python` · `py`), 한글 파일 이름과 한글 함수 이름이 Windows의 터미널에서 문제없는지.
- 가이드만 보고 따라 했을 때 50분에 들어가는지. 응답을 기다리는 시간만 8분쯤이어서 빠듯하다. 4단계(7분, 열두 건과 대장)와 7단계(5분, 붙여넣기 · 예상 · 실행)가 가장 불확실하다.
- 2단계 표의 오른쪽 칸(다르게 정하는 선택 다섯)으로는 돌려 보지 않았다. 설명은 기준과 접수를 손으로 대어 본 것이다.
- 7단계에서 학생이 Q13을 틀린 자리에 붙여넣었을 때의 오류 문구.
- 8단계의 「아쉬운 곳」 보기 셋 가운데 둘째 · 셋째는 돌려 보지 않았다.
- 가이드의 렌더: 아홉 화면을 1200px 너비의 헤드리스 Chrome으로 찍었고, 그 가운데 준비 · 4단계 · 6단계의 일부를 확대해 눈으로 보았다. 돌리다 고친 것은 4단계 표의 열 구성(좁아서 「볼 것」이 세로로 쪼개졌다)과 6단계 표의 접수 번호 줄바꿈이다. 나머지 여섯 화면의 눈으로 본 모양, 700px 너비, 접어 둔 요청을 펼친 모습, 복사 · 이동 버튼과 글 칸의 저장 동작은 보지 못했다.
