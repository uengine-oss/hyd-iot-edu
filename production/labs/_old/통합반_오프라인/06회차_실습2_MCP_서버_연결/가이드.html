오늘 잇는 것

VS Code가 호스트다. 서버 하나를 이을 때마다 VS Code 안에 클라이언트가 하나 생기고, 그 서버가 내주는 도구가 Copilot 채팅의 도구 목록에 들어온다. 세 서버는 모두 내 PC에서 도는 stdio 방식이다.

요청은 대부분 이 가이드에 준비되어 있어 복사해 보낸다. 순서는 다른 실습과 같다. 읽게 하고(1단계), 정해 주고 계획을 받고(2단계), 작게 연결해 확인하고(3~5단계), 되돌려 준다(8단계). 그 사이에 호출을 일부러 실패시켜 보고(6단계), 규칙에 어긋나는 요청을 보내 본다(7단계).

VS Code · 탐색기

받은 폴더 시작을 VS Code로 연다

VS Code의 「파일 → 폴더 열기」에서 시작 폴더를 고른다. 이 폴더를 신뢰하느냐고 물으면 신뢰한다고 답한다.

시작/ ├─ .github/ │ └─ copilot-instructions.md ← 이 폴더의 규칙 ├─ .vscode/ │ └─ mcp.json ← 서버의 연결 설정. 지금은 비어 있다 ├─ 서버/ ← 준비된 서버 셋(파이썬 파일). 고치지 않는다 ├─ 도구/ │ ├─ 자료_준비.py ← 업무자료 폴더를 만든다 │ └─ 연결_점검.py ← 서버에 직접 연결해 도구 목록을 본다 ├─ 구매팀_자료/ ← 다른 부서의 폴더. 6단계에서 쓴다 └─ 결과/ ← 지금은 비어 있다

완성 폴더도 함께 받았다. 이 실습을 끝까지 마친 상태가 들어 있다. 막히면 열어서 내 것과 견준다.

돌아온 답에서 세 가지를 찾는다

답이 오는 데 30초쯤 걸린다. 문장은 사람마다 다르게 나오므로 옆 사람과 글자가 같을 필요는 없다. 아래 세 가지가 내 답에도 있는지를 본다.

①

접근 범위를 정하는 자리가 서버마다 다르다파일시스템 서버는 허용할 폴더를 인수로 적고, Git 서버는 --repository로 저장소 하나를 적는다. 시간 서버는 파일도 저장소도 보지 않아 정할 범위가 없다. 준비 단계에서 연 시간_서버.py의 머리말과 같은 말인가.

②

도구의 수파일시스템 서버의 도구가 몇 개라고 했는가. 「읽기 전용이 아닐 때만」이라는 단서가 붙은 도구가 하나 있는지 찾는다.

③

Copilot이 나에게 되묻는 것답의 끝에 「정해 주셔야 하는 것」이 있는가. 대신 돌린 실행에서는 네 가지를 물었다(허용할 폴더, 읽기 전용, 저장소, 기본 시간대). 규칙 파일의 「정해져 있지 않은 것」과 견주어 본다.

되묻는 까닭규칙 파일에 「정해져 있지 않은 것은 스스로 정하지 말고 묻는다」고 적어 두었기 때문이다. 규칙이 없었다면 허용할 폴더는 AI가 알아서 골랐을 것이다. 서버가 어디까지 드나드는지는 편의가 아니라 권한의 문제이고, 권한은 요청하는 사람이 정한다.
설정 파일이 바뀌어 버렸다면편집기에서 .vscode/mcp.json을 열어 servers가 비어 있는지 본다. 무엇인가 들어가 있으면 요청의 마지막 문장이 빠진 것이다. 변경을 되돌리고 요청을 다시 복사해 보낸다.
되묻지 않고 답이 끝났다면「연결하려면 내가 정해 줘야 하는 것이 무엇인지 규칙 파일의 정해져 있지 않은 것에서 찾아 물어 줘」라고 한 번 더 보낸다.

표 아래의 네 줄을 읽는다

표 아래에 세 서버를 견준 네 줄이 있다. 아래는 완성 폴더의 결과에서 옮긴 것이다. 내 결과와 같은 말을 하는지, 다르다면 어느 쪽이 내 표와 맞는지를 본다.

견준 것완성 폴더의 결과에 적힌 것
도구 이름을 짓는 방식filesystem과 time은 서버 이름 없이 동작_대상으로 짓는다(list_directory, read_text_file, get_current_time, convert_time). git은 모든 도구에 git_을 앞에 붙이고 뒤에 git 명령의 이름을 둔다(git_status, git_log).
필수 인수filesystem은 부른 두 도구 모두 path가 필수다. git은 부른 두 도구 모두 필수 인수가 없다(볼 저장소는 서버를 띄울 때 정해진다). time은 인수가 전부 필수이고, 서버에 기본 시간대가 있어도 timezone을 넘겨야 한다.
돌아온 결과의 모양filesystem은 꾸밈없는 글이다(폴더는 한 줄에 하나씩 [FILE] 표시, 파일은 내용 그대로). git도 글이지만 git 명령의 출력 모양이다(상태 부호 M·??, 커밋 번호 | 날짜 | 쓴 사람 | 메시지 줄과 바뀐 파일 줄). time은 JSON 객체다.
다시 불러도 결과가 같은지time의 get_current_time은 부를 때마다 달랐다(앞서 02:19:24, 이번 02:20:05). convert_time은 같은 인수로 두 번 불러 결과가 같았다. 다만 날짜를 오늘로 보므로 날이 바뀌면 datetime의 날짜가 달라진다. filesystem과 git은 이번에 한 번씩만 불러서 다시 부른 결과를 견주지 못했다. 서버 설명으로는 파일과 저장소가 바뀌지 않는 한 같아야 하지만 확인한 것은 아니다.
확인한 것과 확인하지 못한 것넷째 줄을 다시 읽는다. 시간 서버는 두 번 불러 견주었지만, 나머지 둘은 한 번씩만 불러서 「견주지 못했다」고 적었다. 부르지 않은 것을 부른 것처럼 적지 않는다는 규칙의 3번이 이 문장을 만들었다. 기록을 읽는 사람은 어디까지가 확인된 사실인지를 알 수 있다.
표의 칸이 여섯이 아니라면규칙 파일의 「정해져 있는 것」에 칸의 이름 여섯이 적혀 있다. 그 줄을 들어 표를 맞춰 달라고 한다.
도구를 부르지 않고 표를 채웠다면허용 물음이 여섯 번 뜨지 않았다면 의심한다. 「표의 각 줄을 실제로 불렀는지, 부르지 않은 줄이 있으면 어느 줄인지 말해 줘」라고 묻는다.

허용 폴더를 넓혀 6단계를 다시 해 본다. 7단계에서 Copilot이 내놓은 길이다. filesystem의 args 끝에 "${workspaceFolder}/구매팀_자료"를 더하고 서버를 다시 시작한 뒤, 같은 파일을 읽어 달라고 한다. 대신 돌린 실행에서는 연결_점검.py로 같은 호출을 보내 이번에는 내용이 돌아왔다. 실패 기록의 첫째 줄은 지우지 않는다.

필수 인수를 빼고 직접 불러 본다. 채팅에서는 모델이 인수를 채워 주기 때문에 필수 인수가 빠지는 일이 드물다. 터미널에서 python 도구/연결_점검.py --호출 time convert_time source_timezone=Asia/Seoul time=14:00을 실행해 본다. 보낸 요청과 받은 응답이 JSON-RPC 메시지 그대로 보인다. 응답의 isError가 무엇이고, 어느 인수가 없다고 하는가.
