# 작업 하나 — 시작부터 정리까지

아래 순서를 스스로 밟고 단계마다 번호 보고를 한다. push · 지우기는 기본으로 먼저 묻고, 사용자가 "알아서 해"로 맡겼으면 묻지 않고 끝까지 한다(헌법 4절).

## 1. 작업 폴더

- 열린 작업이 있으면(`PYTHONUTF8=1 .venv314/Scripts/python.exe workspace/동기화.py status`) 사용자 범위와 일치하는 폴더의 `스펙.md`·`기록.md`부터 읽고 잇는다. 병행 작업은 범위와 담당 경로를 구분해 다른 세션의 현재 상태를 덮어쓰지 않는다. 남은 일의 정본은 `workspace/강의제작/남은일.md` — 끝낸 줄은 지운다.
- 새 일이면 `PYTHONUTF8=1 .venv314/Scripts/python.exe workspace/동기화.py 시작 "짧은 제목"` → `작업/<오늘>_<제목>/`. `스펙.md`에 의도 · 범위 · 읽을 문서 · 인수 조건을 채운다.
- 녹화 원본 · 시험 출력 · 임시 파일은 그 작업 폴더나 `작업/촬영/<도구>/`에만 둔다. 저장소 다른 자리에 흩지 않는다.

## 2. 착수 전 원문 완독

`workspace/README.md` 색인에서 해당 작업의 지침을 찾는다. 읽을 규칙 문서는 많아야 2개다(산출물 지침 하나, 촬영이면 그 도구의 촬영준비, 덱이면 형식 문서). 사실은 통독하지 않고 작업하면서 필요한 대목만 이 순서로 찾는다(이 수에 세지 않는다):

- 포털 동작: `workspace/개발/문서/UIUX_PLAN.md` 「교재에서 찾는 포털 기능」 → 포털 코드 `it/portal/www` → 떠 있는 포털 화면. 화면을 볼 때 사건 생성 · 승인 · 명령 전송 · 데이터 변경 · AI 호출은 그 작업에 허용된 범위에서만 하고, 확인한 화면 · 판본 · 본 범위를 기록에 남긴다.
- 사례 · 값 · 이름: 그 회차 사실표 `workspace/강의제작/지침/사실표/`(통합 1 · 실전 1은 `01일차`, 통합 2~4 · 실전 2~3은 `02-04`, 통합 5~8 · 실전 4~5는 `05-08`, 통합 9~11 · 실전 6~8은 `09-11`) → 저장소 코드 · 시드 · `it/neo4j/v2/` · 제공 BPMN `it/process/definitions/` · 떠 있는 그래프. 실제 동작 · 값은 코드 · 그래프가 정한다. 사실표와 다르면 코드 · 그래프를 쓰고 그 사실표 행을 같은 작업에서 고친다.
- 모든 교재가 같게 쓰는 말 · 대표 값 · 사건 기록: `통합반_01일차_기술사실표.md` 「같은 말 · 같은 값」.
- 시스템이 바뀐 자리: `workspace/개발/문서/교재_고칠곳.md`에서 맡은 파일 이름으로 찾는다. 줄 번호는 표를 쓴 날 기준이라 실물을 보고, 고친 줄은 표에서 지운다.
- 계층 이름 · 역할 · 설계 원칙: 설계서 v3 `workspace/강의제작/지침/설계서_v3_유압설비_IoT-SCADA_아키텍처.pdf`.

제작자와 감독은 작업을 시작하거나 이어받을 때(새 세션 · 요약 직후 · 실패 직후) 다음 제작 · 검수 전에 담당 작업 폴더의 `스펙.md` · `기록.md`와 현재 산출물의 지침 원문을 처음부터 마지막 인수 조건까지 직접 읽는다. 파일 · 해시가 같아도 다시 읽고, 출력이 잘리면 빠진 범위를 나누어 읽는다. 이 재독은 지침을 읽는 것이고 산출물 재검증이 아니다 — 같은 판본 산출물의 유효한 검증 근거는 재사용한다. 읽은 뒤 git · 실행 상태와 기록의 차이로 최신 판본 · 다음 행동 · 미확인을 복원한다. 오래된 진행 기록은 현재 작업 목록이 아니고, 옛 완료 표시 · 경로는 실물로, 게시 여부는 게시 판본으로 다시 확인하며, 과거 샘플의 지시 · 포트를 현재 값으로 쓰지 않는다. 지난 세션의 도구 부재 · 오류와 다른 PC의 성공은 지금 여기서 다시 확인하고, 작업 폴더와 촬영 원본(`작업/촬영/<도구>/`)이 없는 PC면 그 의존성을 적고 가능한 준비를 계속한다. 요약 · 키워드 검사는 원문을 대체하지 않고, 미확인을 임의 결정으로 메우지 않는다. Claude에서는 `.claude/hooks/guide_gate.py`가 이것을 동작으로 돕는다: 지침을 끝까지 읽기 전에는 Edit · Write로 그 산출물을 고치는 것과 파이썬으로 직접 부른 덱 · 영상 빌드가 막히고, 요약이 일어나면 읽은 기록이 비워져 막히는 이유와 읽을 줄을 알려 준다. 스크립트의 직접 쓰기 · sed는 잡지 못하니 이 절은 그때도 지킨다. 동작 시험은 `guide_gate.py selftest`. Codex는 요약 직후 안내까지다.

## 3. 만들기 · 검사

- 결과물은 그 문서의 인수 조건 표 전 항목으로 판정한다. 근거 있는 통과 또는 해당 없음(이유)만 남고 불통과·미확인·누락이 0이어야 완료다.
- 문서를 고쳤으면 `workspace/강의제작/제작도구/검사/재편검사.py` 오류 0. 링크를 바꿨으면 끊긴 링크 0.
- 실행한 것만 「됐다」고 쓴다. 안 잰 것은 미검증으로 남긴다.

### 강의 산출물(입구 스킬 hyd-syllabus · hyd-course-deck · hyd-script · hyd-video · hyd-coding-lab · hyd-lab-guide 공통)

1. 시작 보고에 2절에서 실제로 읽은 문서와 판본, 이번 산출물에 적용할 기준을 적는다.
2. 한 세션이 한 회차를 처음부터 끝까지 맡는다. 스펙에서 사용자가 요청한 범위와 실라버스 행 순서를 확인하고 기록에 현재 단계와 다음 단계를 표시한다. 같은 회차의 산출물을 서로 다른 세션에 나눠 동시에 제작하지 않는다.
3. 그 세션 안에서 한 번에 한 종류를 작업한다. 먼저 실라버스와 기존 정본으로 수업의 흐름을 잡고 실습에 필요한 입력·실제 행동·성공 조건을 확인한다. 새로 만드는 이론은 덱 → 그 장을 설명하는 대본·노트 → 영상 순으로, 실습은 도구 동선 또는 랩 검증 → 연결 교재와 설명 일치 확인 → 촬영 대본·큐 → 촬영 → 실제 화면을 쓴 가이드·ZIP 순으로 잇는다. 각 산출물에 착수할 때 2절대로 인수조건까지 지침 전체를 먼저 읽는다. 목적·가치는 내용 선택에, 작업 컨텍스트는 입력 자료·대상·앞뒤 연결에, 작업 요령은 실제 제작 과정에 적용한다. 이미 마친 단계는 판본과 인수 근거를 확인해 이어 쓴다. 앞 단계와 어긋나면 원인이 있는 자리와 영향을 받은 연결만 고친 뒤 진행한다. 두 반이 같은 결과물을 쓰면 한 번 만들고 양쪽 연결을 확인한다.
4. 검토는 한 번으로 끝난다: 작업자 작업 → 검토자 1회 → 작업자가 목록만 수정 → 끝. 재검토는 없다.
   - 작업자: 고치는 일을 전부 맡고, 처음 할 때 꼼꼼히 해 두 번 작업하지 않는다. 첫 작업에서 값·이름은 코드·그래프로 맞추고, 실행 결과는 적힌 조건 그대로 돌려 보고, 그림·위치는 렌더로 보고, 연결 산출물까지 함께 맞추고, 그 문서가 정한 실행 검사(도구)를 통과시킨 뒤 넘긴다. 인수조건 항목별 판정은 검토자 한 번이다(전표의 reviewer는 authors가 아니다). 감독은 판정 기준 전부와 이 상한을 첫 지시에 적고, 빠뜨린 관점을 뒤에 단계로 덧붙이지 않는다.
   - 검토자: 만든 사람이 아니고 고치지 않는다. 지침 원문·실제 산출물·본보기를 대조해 한 번 읽고, 맞는 곳은 그 자리에서 확정하고, 틀린 사실과 인수조건 불통과만 근거와 함께 목록으로 낸다. 표현·취향은 올리지 않는다. 결함 수는 행이 아니라 원인으로 센다.
   - 볼 범위: 이미 확정·통과한 것은 다시 보지 않고 근거를 재사용하며, 요청이 정한 곳과 변경부·연결부, 근거가 비거나 어긋난 항목만 본다. 이론 덱에서 볼 장은 `workspace/강의제작/제작도구/검사/장확정.py <과정> <NN> 상태 [--오프라인]`이 뽑고, 검토자가 맞다고 본 장은 같은 도구의 `확정`으로 적는다. 새로 만든 산출물은 전체를 본다. 시스템이 바뀌어 사실 근거가 달라졌으면 전 장을 다시 읽지 않고, 바뀐 이름·값으로 찾아 닿은 장만 본다.
   - 수정: 작업자는 목록을 실물로 확인해 그 목록만 고친다. 확정된 곳은 건드리지 않는다. 지적이 틀렸으면 고치지 않고 까닭을 적는다.
   - 끝: 감독은 목록대로 고쳐졌는지만 실물로 보고 새 지적을 만들지 않는다. 남은 것은 불통과·미확인으로 적어 보고한다. 라운드를 더하거나 전체를 다시 볼 때는 까닭을 사용자에게 먼저 말하고 답을 받는다.
   - 현재 도구의 에이전트를 쓴다(Codex 작업은 Codex). 특정 모델명 때문에 다른 CLI·계정·서비스를 실행하지 않는다. 사용자의 명시적인 도구·모델 선택이 우선이다.
5. 작업 중에는 실제 수행한 내용과 확인 근거를 남긴다. 실습 영상의 재생 범위는 영상.md V요-35를 따른다. 결함이 생기면 마지막 정상 상태와 원본을 보존해 그 범위만 고치고, 영향을 받은 후속 산출물만 다시 판정한다. 통과 근거를 새로 만들기 위해 같은 작업을 되풀이하지 않는다.
   - 확정 산출물의 승인 범위(여기 한 곳이 정한다): 확정 산출물은 사용자가 재생해 확정한 영상과 확정 회차(두 반 1회차, 통합반 2 · 3회차, 실전반 2회차)의 덱 화면 · 대본 발화다. 그 화면 · 발화 · 영상은 결함을 「대상 · 어긋남 · 근거 · 고칠 문장」으로 적어 사용자 승인을 받은 범위만 고친다. 사용자가 그 회차 · 장의 수정을 맡겼으면 그 요청이 승인이고, 적은 것은 변경 기록으로 남긴다. 승인 없이 고치는 것은 발표자 노트, 덱 MD의 화면에 나가지 않는 칸(제작 기준 · 화면 구성), 대본의 비낭독 부분(파일 머리 · 「이 회차의 구성」 표 · 행 제목 줄 · 끝 표시)이다. 4번의 검토자 확정(`장확정.py`)은 이 사용자 확정과 다르다.

보고:

- 항목별 요구 → 결과 → 근거 대조, 인수 조건 N항목 중 통과 · 불통과 · 해당 없음(까닭) 숫자, 불통과 목록(번호 · 근거 위치).
- 각 단계가 끝나면 `기록.md`의 해당 산출물 자리에 판본, 실제로 한 일, 하지 않은 일, 확인하지 못한 결과, 남은 조치와 인수전표 위치를 적는다. 나중에 수행 여부를 물으면 이 기록과 전표로 답한다. 판본이 바뀌거나 근거에 공백이 있는 범위만 다시 확인한다.
- 작업 폴더의 `인수전표.json`에 산출물·근거의 경로와 SHA256, 지침 경로와 인수 조건 행마다의 SHA256(`…/인수검사.py --틀 <지침.md>`이 낸다), 항목별 판정·위치·이유, 작성자·검토자를 연결한다. 형식과 명령은 `workspace/강의제작/제작도구/검사/인수검사.py` 머리말을 따른다. 완료 보고 전 `…/인수검사.py <인수전표.json> --완료` 오류 0을 확인한다. 이 검사는 누락·판본·독립성·상태를 검사하며 내용·윤문·시각 판단을 대신하지 않는다.

## 4. 제자리에 넣기 — 최신 하나만

| 무엇 | 어디 | 규칙 |
|---|---|---|
| 최종본(덱 · 대본 · 랩 · 가이드 · 영상 · 실라버스) | `workspace/강의제작/산출물/…` | 이전 판을 지우고 바꿔 끼운다. 이름에 판 꼬리(v1 · 날짜 · 사본)를 붙이지 않는다. 영상이면 `산출물/영상/README.md` 그 행을 고쳐 쓴다 |
| 다시 만들 재료(원고 · 큐 · 구성 · 음성 캐시 · 도구) | `workspace/강의제작/제작도구/…` | 고칠 때 다시 쓰는 것만. 녹화 원본 · 프레임 · 합성 wav는 재료가 아니다 |
| 규칙이 바뀜 | 그 산출물의 지침 문서 그 자리 | 덧붙이지 않고 그 주제 자리를 다시 써서 합친다 |
| 시스템 코드 | main(`it` · `ot` · `dmz` · `common` …) | 시스템 문서는 `workspace/개발/문서/`의 소수만. 새 설명 문서를 늘리지 않는다 |
| 공개하면 안 되는 개인 자료 | `작업/_로컬/` | 어느 브랜치에도 올리지 않는다 |

## 5. 동기화

`CLAUDE.md` 2절대로 `PYTHONUTF8=1 .venv314/Scripts/python.exe workspace/동기화.py pull` → `… commit "무엇을 왜" [main 경로 …] [--만 workspace 경로 …]` → 바로 `… push`. 다른 작업 폴더가 열려 있으면 `--만`으로 이 작업의 경로만 올린다(`status`가 로컬에만 · 내용 다름을 보여 준다). 이전 판 경고가 나오면 고치고 다시.

## 6. 정리

`스펙.md`의 상태를 「확정」으로 바꾸고 `… workspace/동기화.py 정리 --실행` → 작업 폴더가 지워진다. 끝 보고에는 바뀐 것 · 자리 · 검증 결과 · 남은 일만 적는다.

## 늘

- 착수 전에 세 가지를 가르고 첫 보고에 쓴다: 재사용할 것(이미 있고 맞는 것) · 건드리지 않을 것(이번 일과 닿지 않는 것) · 이것만 볼 것(바뀐 곳과 그 연결). 정확하고, 되풀이 없이, 빠르게 끝나는 길을 고른다.
- 딱 봤을 때 정말 필요한가로 본다 — 지울 것은 「이건 이런 건데 필요합니까」로 묻는다. "알아서 해"로 맡겼으면 분명히 필요 없는 것은 지우고(지운 것은 git 이력) 애매한 것만 묻는다.
- 같은 사실은 한 곳에만 쓰고 나머지는 가리킨다. 사본을 만들지 않는다.
