# 복사해서 실행하고, 결과를 이해하는 HTML 실습가이드

HTML 실습가이드의 제작·수정에 적용한다. 특정 강의의 단계 수·도구·색상은 해당 계약을 따른다.

## 읽을 내용과 보낼 내용을 구분한다

학생이 블록을 읽자마자 어디서 무엇을 해야 하는지 알 수 있게 만든다.

| 종류 | 표시할 내용 | 복사 후 행동 |
|---|---|---|
| 읽는 지침 | 상황, 필요한 이유, 학생이 판단할 조건 | 복사 대상과 시각적으로 구분 |
| Agent 프롬프트 | 요청 본문, 수정 범위, 보호 조건, 완료 기준 | 지정된 코딩 Agent 채팅창에 붙여넣고 전송 |
| 터미널 명령 | 사용할 셸·실행 폴더·명령 | 해당 터미널에 붙여넣고 실행 |
| 코드 수정 위치 | 상대 파일 경로, 함수 또는 주석 표식 | 편집기에서 파일과 수정 위치 찾기 |
| 직접 붙여넣는 코드 | 대상 파일·교체 범위·언어 | 지정 범위에 붙여넣고 저장 |

코딩 Agent가 구현하는 실습이라면 파일 경로를 보여주는 것과 학생에게 코드를 붙여넣게 하는 것을 혼동하지 않는다. 정답 코드 블록을 불필요하게 추가하지 않는다.

종류는 색상과 텍스트로 함께 표시한다. 복사 버튼에는 알아볼 수 있는 아이콘과 이름을 함께 넣고, 아이콘은 장식 처리해 접근성 이름이 중복되지 않게 한다. 복사는 본문만 포함하며 설명·줄 번호·셸 프롬프트 기호를 섞지 않는다.

버튼의 완료 메시지도 목적지를 따른다. 터미널 명령을 복사했는데 Agent 채팅창에 붙여넣으라고 안내하지 않는다. 클립보드 접근이 거부되면 해당 텍스트를 선택하고 수동 복사 방법과 붙여넣을 곳을 알려준다. 빈 학생 입력을 복사 성공으로 표시하지 않는다.

복구 미리보기와 실제 적용처럼 판단이 필요한 명령은 별도 블록과 버튼으로 나눈다. 여러 줄을 한꺼번에 실행하도록 만들기 전에 중간 결과 확인이 필요한지 판단한다.

## 실습은 이야기와 행동을 연결한다

앞 단계에서 얻은 결과 → 아직 해결되지 않은 문제 → 이번 기능이 필요한 이유 → 학생이 정할 요구 → 구현 → 관찰 → 다음 단계로 이어간다. 설치 가이드처럼 절차만 나열하거나 개념 사전처럼 설명만 늘어놓지 않는다.

예: “정비 이력을 찾았습니다. 이제 해당 설비의 매뉴얼과 비교해야 합니다. 다른 설비의 문서를 근거로 쓰지 않도록 질문과 적용 대상을 함께 전달해 봅시다.”

그 뒤 학생이 필요한 입력·결과를 이해하고 Agent에게 실제 코드의 연결과 수정 영향을 조사하게 한다. 조사 답에서 수정 범위·보호 조건·확인 방법을 파악한 후 자신의 구현 요청을 작성한다. 완성 예시는 현재 과제에 필요한 조건만 짧게 담는다.

### 바이브코딩 수업 방식 (다른 강의에서 확정한 것. HYD 과정은 `hyd-lab-guide` 스킬이 먼저다)

배우는 것은 정답 프롬프트가 아니라 Agent와 효율적으로 일하는 방법이다. 기본 화면은 짧은 상황과 지금 할 일, 직접 작성할 자리, 실행과 실제 화면 확인 순서로 흐른다.

- 먼저 학생이 기능의 역할, 입력→처리→결과의 연결, 빈 함수 링크와 수정 영향, 유지할 기능·명세, 검사 명령·실행 위치·화면 결과를 조사하도록 요청한다. 조사는 한 번에 시켜도 되며 이해되지 않는 부분만 추가로 대화한다. 이때 구현부터 하지 않는다.
- 조사 결과를 바탕으로 학생이 목표·수정 범위·지킬 조건·검증을 정해 구현을 요청한다. 범위 밖 변경이 필요하면 Agent가 이유를 먼저 설명하게 한다. 학생이 아직 보지 못한 함수명이나 검사 명령을 모범에 갑자기 넣지 않는다.
- 작업 방법과 질문 순서·핵심 힌트는 기본 화면에 짧게 표시한다. 힌트를 숨기거나 중첩 토글로 만들지 않는다. 복사 가능한 완성 요청만 ‘막히면 정답 확인’ 토글에 넣는다. 힌트에 코드 해석이나 정답 요청문을 그대로 나열하지 않는다. 완성 요청을 읽고 따라 치는 것을 기본 경로로 만들지 않는다.
- 실습은 자연어 대화로 진행한다. 명세 도구(Spec Kit 등)는 강의 계약이 정한 실습에만 쓴다.
- 확인할 화면에는 실제 캡처와 표시를 넣는다. 오류 안내는 바로 아래 오류 토글로 연결하고, 작업한 Agent에게 실행 명령·오류 전문·화면 캡처를 보내도록 한다. 학생 화면에 제작 메모·선택 시나리오 전환·저장복구 메뉴를 추가하지 않는다.

조사 설명과 승인 예시를 길게 늘려 학생의 판단을 대신하지 않는다. 변경 영향이 복잡한 과제만 그림을 사용하고, 단순 연결은 짧은 화살표 흐름으로 충분하다.

## 명령 다음에 결과를 읽는 법을 둔다

명령마다 학생이 확인할 출력·화면과 다음 행동을 적는다. 검사 통과, 미구현 과제에서의 예상 중단, 서비스 오류를 구분한다. 명령이 새 사건을 만들면 어느 식별자로 화면에서 찾는지도 안내한다.

결과가 다음 단계 구현 뒤에 저장되거나 표시되는지 실제 호출 순서로 확인한다. 앞 단계에서 아직 존재할 수 없는 화면을 성공 기준으로 요구하지 않는다. Agent가 도구 순서를 선택하는 실습은 특정 호출 순서만 정답으로 강제하지 않는다.

설명용 예상 출력은 실제 실행 기록과 구분한다. 연결 검사 통과를 실제 모델 호출·전체 수업 완주로 표현하지 않는다.

## 편집과 확인

편집 원본과 생성 산출물을 표시한다. JSON·생성기로 MD/HTML을 만드는 경우 MD를 직접 수정하면 다음 생성 때 덮어쓰는지도 안내한다. 외부 게시나 ZIP 제작을 가이드 수정의 자동 후속 작업으로 추가하지 않는다.

변경한 범위에서 다음을 확인한다.

- 복사한 내용과 실제 붙여넣은 내용의 일치, 목적지별 완료 메시지, 빈 입력·복사 실패 처리.
- 접힌 힌트·모범의 초기 상태, 학생 작성 내용 보존, 키보드 이동과 모바일 가로 넘침.
- 단계 이동 버튼과 직접 링크의 화면 일치. 같은 페이지의 해시만 바뀌는 이동도 확인한다.
- 실행 위치·명령 인수·상태값·화면 확인 조건이 현재 코드와 일치하는지 대조.

구조 검사·브라우저 검사·실제 학생 완주를 구분해 기록한다. 이전 증거는 입력과 구현이 같은 범위에서 재사용하고, 작은 문구 수정마다 전체 모델 실험을 반복하지 않는다.
