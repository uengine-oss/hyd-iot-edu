# 입력 변경 뒤 분기와 시간제한을 다시 검토하기

재작업은 이전 작업의 결과와 승인·이벤트 이력을 보존하고 새 작업 세대를 만든다. 입력 생산 작업이 바뀌면 그 값을 읽는 후행 작업뿐 아니라 시퀀스 조건과 게이트웨이도 영향을 받는다. 별도 흐름에서 이미 판단한 분기라면 그 앞의 실제 검토 작업을 새 세대에 포함한다. 옛 검토 결과로 새 분기를 조용히 선택하지 않는다.

## 운영 흐름

1. 실행 중인 인스턴스에서 다시 수행할 작업을 선택하고 재작업 미리보기를 읽는다. `/api/instances/{id}/rework-preview?workitem_id={uuid}`는 작업·조건 의존성, 무효화할 값, 재사용 근거, 효과 및 보류 사유를 반환한다.
2. `condition_recheck` 사유가 있는 작업은 바뀐 입력을 쓰는 분기 앞의 검토 작업이다. 이 작업의 담당자가 새로 검토해야 한다는 점까지 확인하고 기존 재작업 API로 현재 snapshot_token·새 UUID·역할·사유를 제출한다. 기존 승인이나 실제 서비스 효과가 있으면 별도 효과 검토 계약도 계속 적용한다.
3. 새 생산 작업을 완료한다. 생산자의 정확한 UUID·세대·판본·DONE·출력값이 확인돼야 새 검토 작업이 열린다. 작업의 일반 inputData에 없는 변수도 분기 조건에 쓰이면 이 대기에 포함한다. 누락된 새 값에 시작 입력이나 옛 결과를 대신 넣어 기본 분기를 선택하지 않는다.
4. 열린 작업의 `[ConditionData]`에서 현재 분기 입력을 확인하고 실제 검토 결과를 제출한다. flow_state의 `condition_snapshots`에는 그 값과 생산 출처가 남는다. 새 제출 이후 엔진이 고정 정의의 조건을 평가하고 해당 분기로 진행한다.
5. 검토에 부착된 경계 타이머는 새 검토가 실제로 열리는 순간부터 시작한다. 기존 타이머의 경과시간을 새 작업에 재사용하지 않는다. 새 검토가 먼저 끝나면 새 타이머를 취소하고, 새 타이머가 먼저 울리면 그 세대의 검토를 취소하고 시간초과 경로로 간다. 이전 시간초과 작업의 도달 기록은 새 타이머가 울린 증거가 아니다.

선행 작업이 내야 할 필수 조건 값이 없으면 검토는 TODO에서 기다린다. 검토 작업 자신의 선택 출력이 빠져 조건을 판정할 수 없으면 PENDING과 `CONDITION_INPUT_UNAVAILABLE`로 남긴다. 검토 결과를 보완해 같은 작업에 다시 제출할 수 있다. 명시적인 null 값과 변수가 없는 상태는 구별한다. 조건 언어 자체는 현재 정의 엔진의 제한된 비교식이며 자연어 조건을 AI로 자동 해석하는 기능이 아니다.

## 도달·세대·복구 근거

`flow_state.activity_arrivals`는 작업이 실제 열린 UUID와 세대를 기록한다. 시간초과로 CANCELLED된 과거 검토도 이 근거가 있으면 새 검토의 진입 근거로 사용할 수 있다. 단, 새 생산자 완료를 기다리는 조건과 새 타이머 이후 작업의 제어 도달을 생략하지 않는다. 단순 start_date는 TODO 생성 시각일 수도 있어 도달 증거로 사용하지 않는다.

새 세대를 다시 재작업하면 대기 중인 조건 의존성도 최신 생산자 UUID로 바뀐다. 옛 UUID 제출은 거절한다. 생산 완료, 대기 해제, 새 타이머 생성, 인스턴스 상태는 기존 전이 잠금과 같은 PG 거래에 저장한다. 서비스가 재시작돼도 저장된 대기 상태와 생산자 연결로 이어간다. 같은 요청 UUID의 재전달은 최초 영수증을 반환한다.

조건 검토가 필요한데 게이트웨이에 앞선 실제 작업이 없거나, 과거 CANCELLED 작업의 도달 근거가 없으면 자동으로 가상의 제어 흐름을 만들지 않는다. `condition_replay_requires_arrival` 또는 `dependency_control_arrival_unavailable`로 보류한다. 복수의 모호한 생산자·순환 의존·완료 인스턴스·확인되지 않은 외부 효과도 기존 보류 계약을 유지한다. 시작 이벤트에서 직접 이어지는 조건 분기의 재실행 토큰, 전체 BPMN 병합/반복 의미, 실제 PLC/업무 효과 보상은 후속 개발 범위다.

## 예제와 근거

[condition-recheck-v1.json](examples/condition-recheck-v1.json)은 별도 경로의 `a`가 x를 생산하고 `b`의 사람 검토 뒤 `g`가 x를 읽는 정의다. x=old이면 c, 다른 명시 값이면 기본 d로 간다. b의 시간제한이 먼저 끝나면 late로 간다. hold는 별도 도달 경로가 끝나기 전에 인스턴스가 조기 종결되지 않는지 관찰하기 위한 작업이다. 예제의 5분 타이머는 현재20배속에서15초다. 업무 환경의 권장 시간제한이 아니다.

회의2 19~24행의 이벤트·태스크 실행 구조, 434~436행의 인스턴스 모니터링 및 사용자의 정의/데이터 변경 요구와 연결된다. 고정 C03 process-gpt-completion `b272c9ab458f3ca3e18fe286e4e770d291b99e89`의 `process_engine.py`978~1034행은 시작 작업 IN_PROGRESS/다른 작업 TODO의 새 재작업 행과 보상 생성 호출을 만든다. `polling_service/workitem_processor.py`4431~4535행은 부착된 boundary 이벤트를 시스템 이벤트 후보로 추가한다. 이 코드를 참고하되, HYD의 정확한 생산자 세대·조건 대기·PG 원자성·타이머 도달 검사를 제품에 이미 있는 동일 구현으로 주장하지 않는다. 제품의 보상 생성 호출을 실제 PLC 효과가 취소됐다는 증거로 사용하지 않는다.


A071 검증: 전체982/6warnings와 실제 `scripts/probe_rework_conditions.py <새 폴더>`의24/24가 통과했다(`.evidence/reaudit/a071-live-verified/`). 최초 검사기 KeyError와 실제 이전 timeout 작업의 조기 개방 실패는 각각 a071-live-first/, a071-live-final/에 보존했다. 후자는 단위 반례를 추가한 뒤 수정하고 실제 새 타이머 도달을 다시 확인했다. 프로세스 강제 종료/재시작·두 세대·동시 완료·기록 보존·Execution 투영을 포함한다. 새 Codex 실행·직접 UI 검수·PLC 효과 보상은 이 검사에 포함하지 않는다.

동일배포본의 기존 쿨러 회귀도 `a071-cooler/`에서42/42로 통과했다. 동일20배속/허용치의 legacy bridge에서 사람승인→PLC ACK→재관측→실제CMMS `WO-1004-9047`→ev:closed/Execution을 확인했다. 이는 일반 재작업 검사와 별개이며 효과 보상이나 새Codex 실행 검증은 아니다.
