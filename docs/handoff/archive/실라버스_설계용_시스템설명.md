# 실라버스 설계용 시스템 설명 — 수강생이 보고, 해 보고, 알게 되는 것

2026-10-08 기준. 75시간(3시간 × 25회) 과정을 짤 강사를 위한 문서다.
"무엇을 고쳤나"가 아니라 "수강생이 이 시스템으로 무엇을 하게 되나"만 적었다.
시간은 실제로 재 본 값이면 **실측**, 재 본 적이 없으면 **예상**으로 표시했다. 출처는 맨 끝 "숫자 출처"에 있다.

---

## 이 시스템을 한 문단으로

유압 설비 세 대가 돌아가는 가상 공장이 있다. 설비에 이상이 생기면 감지 프로그램이 센서 값을 보고 경보를 울린다.
경보 하나는 "처리 건" 하나가 되고, 그 안의 일이 나뉜다. AI 에이전트(스스로 자료를 찾아 읽고 답을 내는 AI 일꾼)가
원인을 찾고, 쓸 수 있는 조치를 모으고, 규정을 검사하고, 순위를 매겨 조치 카드를 만든다.
사람은 카드 중 하나를 고른다(승인). 그러면 명령이 관문과 설비 제어기를 거쳐 설비에 들어간다.
시스템은 설비가 정말 나아졌는지 다시 지켜보고, 정비 요청을 회사 정비 시스템에 남긴 뒤 처리 건을 닫는다.

**한 줄 흐름**

> 설비 이상 → 감지 프로그램이 경보 → 처리 건 열림 → AI가 원인 · 후보 · 규정 · 순위 → 사람이 카드 선택 → 관문 · 제어기 검사 → 설비 명령 → 다시 지켜보기 → 정비 요청 → 끝

설비 세 대: **HYD-01**(쿨러 문제 담당), **HYD-02**(펌프 문제 담당), **HYD-03**(팬 문제 담당).
자주 나오는 센서: 유온 TS1(기름 온도) · 압력 PS1 · 유량 FS1 · 진동 VS1 · 냉각 효율 CE.

## 처음 버전과 지금

처음 버전은 2026-10-03에 받은 저장소 상태다. 회의 뒤 구조가 두 군데에서 크게 바뀌었다.
지식은 미리 손으로 넣어 두던 것에서 **매뉴얼을 넣으면 지식이 되는** 방식으로 바뀌었다.
경보마다 정해진 코드가 돌던 것은 **사건 하나를 일 단위로 나눠 맡기는** 방식으로 바뀌었다.

| 무엇 | 처음 버전 | 지금 | 수강생에게 뜻하는 것 |
|---|---|---|---|
| 사건 처리 | 경보가 오면 정해진 코드가 카드 한 장을 만들고 끝. 기록이 남지 않음 | 경보 하나 = 처리 건 하나. AI · 사람 · 시스템이 일을 나눠 맡고 끝까지 기록 | "지금 누구 손에 있나"를 화면으로 따라간다 |
| 지식 | 설비 · 고장 · 조치 지식을 미리 손으로 넣어 둠. 판단에 거의 안 쓰이는 그림 | 매뉴얼 PDF · 회사 DB 구조를 넣으면 지식이 되고, 판단에 실제로 쓰임 | 지식을 만드는 과정 자체를 실습한다 |
| AI | 정해진 틀로 카드를 채움. 데이터 조회 없음 | Claude Code 같은 범용 AI가 일을 집어 가 지식 지도 · 회사 DB · 센서 기록을 직접 조회하고 근거를 붙임 | AI가 어디서 무엇을 읽었는지 기록으로 확인한다 |
| 사람 승인 | 승인 버튼 하나. 거절 · 권한 · 시간 초과 없음 | 권한이 없으면 거절, 오래 안 고르면 상급자에게, 되돌릴 수 없는 명령은 검토 요구 | 책임 있는 승인이 어떻게 생겼는지 본다 |
| 회사 사정 | 고정 가짜 값. 순위에 납기 · 품질 반영 없음 | 실제 DB 표. 납기 · 품질 · 공급사 값이 순위를 바꾸고, 값이 바뀌면 옛 승인은 거절 | "설비만 보면 틀리는 판단"을 직접 만든다 |
| 시나리오 | 쿨러 하나. 펌프 · 팬 가상 설비 없음 | 쿨러 · 펌프 · 팬 세 가지를 끝까지 + 함정 장면 | 같은 흐름에서 다른 판단이 나오는 것을 비교한다 |
| 끝맺음 | 종결 때 정비 요청이 나가지 않음 | 회사 정비 시스템에 정비 요청 한 줄이 실제로 생김 | 처리가 회사 업무로 이어지는 것을 본다 |
| 화면 | 표와 주기 새로고침 | 메뉴 12개, 쉬운 이름, AI 활동이 실시간으로 올라옴 | 화면만 보고도 흐름을 따라간다 |

## 가르칠 수 있는 덩어리 (15개)

화면 이름은 지금 포털 메뉴 그대로다: 홈 · 시스템 구성 · 결함 시뮬레이션 · 이상 확인 · 조치 · 실시간 모니터링 · 지식 지도 · 조치 방법 · 조치 판단 규칙 · 승인과 실행 · 처리 건 · 지식 관리 · 관리.
회차 문서(`docs/sessions/`)는 옛 이름을 쓴다. 대응: 프로세스 인스턴스 → **처리 건**, 온톨로지 지식 지도 → **지식 지도**, 에이전트 스킬 → **조치 방법**, 업무 프로세스 → **승인과 실행**, 고급 › 정의 등록 → **관리**, DDL · 매뉴얼 절 → **지식 관리**.

### 3. 지식 지도 — 설비 · 고장 · 조치 · 회사 목표가 이어진 그림

| | |
|---|---|
| ① 무슨 일 | 온톨로지(설비 · 고장 · 조치가 서로 어떻게 이어지는지 적어 둔 지식 지도)가 그래프 DB에 있다. 표에는 "값"만, 지도에는 "왜"가 있다. |
| ② 화면 | 지식 지도(층 칩, 이상 패턴 경로) · 지식 관리 › 질의 보기 |
| ③ 해 보는 것 | "유온 상승 → 고장 유형 → 원인 → 조치 방법" 길을 직접 걷는다. 조치 하나가 설비 값을 거쳐 생산량 · 납기 같은 회사 지표에 닿는 사슬을 세 개 찾는다. 표의 구조와 지도의 구조를 나란히 비교한다. |
| ④ 시간 | 화면 · 질의는 기다림 없이 바로 나온다(**예상**, 따로 안 잼). |
| ⑤ 알게 되는 것 | "구조"라는 말이 표에서는 칸 이름, 지도에서는 뜻과 연결이라는 것을 구분한다. |
| ⑥ 회차 | 05 · 06 |
| ⑦ 아직 안 되는 것 | 특별히 없음. 지도에는 판단에 쓰는 센서만 있다(설비 태그 19개 중 5개). |
| ⑧ 시나리오 | 쿨러(경로) · 펌프 · 팬(영향 사슬) |

### 4. 매뉴얼과 회사 DB를 넣으면 지식이 된다

| | |
|---|---|
| ① 무슨 일 | 제조사 매뉴얼을 넣으면 AI가 정비 절차를 뽑고, 사람이 검토해 등록하면 지식 지도에 "조치 방법"이 생긴다. 회사 DB의 표 구조를 넣으면 "어느 표의 어느 칸에 값이 있다"는 연결이 지도에 생긴다(값 자체는 안 넣는다). |
| ② 화면 | 지식 관리(매뉴얼 등록 · 업무 데이터 연결 · 이 문서로 답할 수 있는 질문) · 조치 방법 |
| ③ 해 보는 것 | 예시 매뉴얼을 미리보기 → 등록하고 새 조치 방법을 찾는다. 회사 DB 구조 파일을 넣어 연결을 만들고 되돌린다. 등록한 문서로 "답할 수 있는 질문 / 아직 못 하는 질문"을 본다. |
| ④ 시간 | 작은 매뉴얼 AI 추출 약 2분 40초(**실측**). 짧은 시험 매뉴얼 41초(**실측**). 실제 제조사 매뉴얼 80쪽 15분(AI 일꾼 2개, **실측**). 구조 파일 미리보기 · 등록 · 되돌리기(**예상**: 기다림 거의 없음). |
| ⑤ 알게 되는 것 | 지식은 미리 다 넣어 두는 것이 아니라 문서와 DB에서 만들어 들이는 것이다. |
| ⑥ 회차 | 09 |
| ⑦ 아직 안 되는 것 | 받는 문서는 PDF · md · txt뿐(한글 · 워드 파일 없음). AI 추출은 내 PC AI 일꾼이 떠 있어야 한다. 규칙을 DB 질의로 바꾸는 기능은 규칙 이름만으로는 안 되고, 넣은 표의 칸 이름을 직접 지정해야 한다. |
| ⑧ 시나리오 | 쿨러 · 팬(매뉴얼 예시) · 펌프(예비 펌프 준비 상태) |

### 5. 조치 판단 규칙 — 같은 질문에 늘 같은 답

| | |
|---|---|
| ① 무슨 일 | 원인 순위 · 규정 검사처럼 매번 같은 답이 나와야 하는 부분은 AI가 아니라 규칙표가 정한다. 규칙은 "이 조건이면 이 조치를 빼라 / 깎아라 / 경고하라"를 적은 표다. |
| ② 화면 | 조치 판단 규칙(판단 조건 → 판단 실행) · 지식 관리 › 질의 보기(규칙 · 임계값) |
| ③ 해 보는 것 | 실제 값으로 판단을 돌리고 1위 카드를 적는다. "팬 100 % 누적 30시간"을 넣기 전에 어느 규칙이 걸릴지 예상하고 결과와 비교한다. 규칙의 기준값(24시간)을 48로 바꿨다가 되돌린다. |
| ④ 시간 | 판단 실행은 버튼 한 번에 결과(**예상**, 따로 안 잼). |
| ⑤ 알게 되는 것 | AI에게 맡길 것과 규칙으로 고정할 것을 나눈다. |
| ⑥ 회차 | 08 |
| ⑦ 아직 안 되는 것 | 화면에서 규칙 기준값을 직접 고치는 기능은 없다(그래프 DB 화면에서 고친다). |
| ⑧ 시나리오 | 쿨러 |

### 6. 여러 조치가 경쟁해 1등을 고르는 과정

| | |
|---|---|
| ① 무슨 일 | 운동회 선발처럼 다섯 단계로 1등을 뽑는다. **후보 모으기**: 지식 지도에서 이 고장의 조치 후보를 모은다(쿨러 4장, 팬 6장). **안 되는 후보 빼기**: 규정 · 안전 한계 · 예측 온도로 탈락시킨다(예: 펌프의 "압력 올리기"는 씰 손상을 키워 규정상 탈락). **점수 매기기**: 회사 목표 지표(가동률 · 고장 간격 · 생산량 · 매출 · 납기 준수 등 21개, 결과를 보여 주는 후행 지표 11개와 결과를 움직이는 선행 지표 10개)에 주는 득과 실을 계산하고, 예측 온도 · 경고 · 감점 · 과거에 같은 선택을 한 비율, 회사 사정(납기가 급한가, 지연 보상금, 품질 클레임)을 더하고 뺀다. **1등 추천과 이유**: 카드에 점수 · 예상 유온 · 승인 역할 · 과거 같은 선택이 보이고, 점수 계산은 "근거 보기"에 있다. **사람의 최종 선택**: 권한 있는 사람이 고른다. |
| ② 화면 | 조치 판단 규칙(판단 결과, 카드별 점수 항목) · 승인과 실행(판단 결과, 기업 시스템 현황) |
| ③ 해 보는 것 | 카드의 점수표와 근거 값을 읽고 "왜 1등인가"를 말로 설명한다. 23회차처럼 회사 DB 값(납기 · 계약 손실 · 완제품 재고)을 바꾸고 1등이 바뀌는 것을 본다. 예: 납기를 30시간 뒤로 미루면 납기 점수가 0이 되어 1등이 "팬 최대"에서 "팬 최대 + 부하 80 %"로 바뀐다. 계약 손실 · 재고 값만 바꾸자 "계획 정지" 카드가 4위에서 2위로 올랐다(프로그램은 안 고치고 데이터만 바꿈). |
| ④ 시간 | 값 바꾸고 다시 판단(**예상**: 바로). 실제 경보에서 AI 일꾼의 순위 매기기 일 하나 101초(**실측**). |
| ⑤ 알게 되는 것 | 좋은 조치는 설비 하나가 아니라 회사 목표와 사정까지 따져 정해진다. 순위를 정하는 식도 데이터라서 프로그램 수정 없이 바뀐다. |
| ⑥ 회차 | 06 · 08 · 10 · 23 |
| ⑦ 아직 안 되는 것 | "이 값이 바뀌면 순위가 뒤집힌다"를 화면이 미리 알려 주지는 않는다. 수강생이 값을 바꿔 보며 직접 찾는다. 품질 점수는 상한이 있어 클레임 금액을 1,000 넘게 올려도 더 변하지 않는다. |
| ⑧ 시나리오 | 쿨러 · 펌프 · 팬 모두(특히 쿨러 · 23회차) |

### 7. AI 에이전트가 맡는 네 가지 일

| | |
|---|---|
| ① 무슨 일 | 경보가 나면 AI가 차례로 네 일을 한다: 원인 진단 → 조치 후보 → 규정 검토 → 우선순위 · 카드 작성. 일마다 지식 지도 · 센서 기록 · 회사 DB 중 무엇을 읽었는지 기록이 남는다. |
| ② 화면 | 이상 확인 · 조치(사건 상세의 조치 과정) · 처리 건(에이전트 활동) |
| ③ 해 보는 것 | 쿨러 경보 하나의 AI 실행 기록을 단계별로 읽고 "단계 · 도구 · 출처 · 읽은 값" 표를 만든다. 경보가 열려 있을 때 조치 판단 규칙 화면의 순위와 AI 카드의 순위를 비교한다. |
| ④ 시간 | 시스템 안 기본 AI로 네 일 약 15~18초(**실측**). 실제 AI 일꾼(Claude Code)으로 네 일 합 269초, 일 하나 29~101초(**실측**). |
| ⑤ 알게 되는 것 | 에이전트 = AI 모델 + 도구 + 정해진 절차라는 것을 기록으로 확인한다. |
| ⑥ 회차 | 10 |
| ⑦ 아직 안 되는 것 | 기본 설정은 시스템 안 AI다. 실제 AI 일꾼을 쓰려면 설정 한 줄을 바꾸고 일꾼을 켜야 한다(8 · 9번 덩어리). |
| ⑧ 시나리오 | 쿨러 |

### 8. AI에게 도구를 붙여 직접 묻게 하기

| | |
|---|---|
| ① 무슨 일 | MCP(AI가 바깥 데이터에 물어볼 수 있게 붙이는 연결 규격)로 지식 지도 · 회사 DB · 규칙과 센서 기록을 AI에 붙인다. AI는 구조를 먼저 읽고, 질의를 스스로 만들어 실행한다. 서버는 이 AI를 하위 프로그램으로 불러 쓴다. |
| ② 화면 | 관리(프로세스 정의 등록 · 버전 선택 · 실행) · 처리 건(에이전트 활동) |
| ③ 해 보는 것 | 내 PC의 Claude Code에 지식 지도 연결을 붙이고 "펌프 누설의 원인과 조치는?"을 묻는다. 수업용 질문 세 가지(센서 기록 · 회사 DB · 규칙)를 실행하고 어느 도구가 어느 출처를 언제 읽었는지 표로 만든다. 질문을 바꿔 다시 실행한다. |
| ④ 시간 | 질문 하나 답까지 27~52초(**실측**). |
| ⑤ 알게 되는 것 | AI는 아무 데나 쓰지 못하고, 붙여 준 읽기 전용 도구만 쓴다. "데이터 없음"과 "거짓"은 다르다. |
| ⑥ 회차 | 07 · 11 · 12 |
| ⑦ 아직 안 되는 것 | 수강생별 AI 계정 · 사용량 운영 방식은 정해지지 않았다. Codex는 PC 설정에 따라 모델을 따로 지정해야 할 수 있다. |
| ⑧ 시나리오 | 펌프(질문 예) · 팬(진동 질문) · 곁가지(규칙 성립 여부) |

### 9. 내 PC에서 AI 일꾼 돌리기와 사람에게 묻기

| | |
|---|---|
| ① 무슨 일 | 일을 "집어 가는" 일꾼을 내 PC에서 띄운다. 경보가 나면 내 일꾼이 네 일을 차례로 가져가 처리한다. 일꾼이 모르는 것이 있으면 사람에게 묻고 멈췄다가, 답을 받으면 이어 간다. 일꾼이 죽으면 다른 일꾼이 이어받는다. |
| ② 화면 | 처리 건(내 차례 › 에이전트의 질문, 에이전트 활동) |
| ③ 해 보는 것 | 일꾼을 켜고 팬 경보(또는 약한 쿨러 고장)로 네 일이 내 PC에서 처리되는 것을 본다. 앞 일의 결과가 다음 일의 입력으로 넘어가는 표를 만든다. 일꾼이 묻는 질문에 답하고 이어지는 것을 본다. |
| ④ 시간 | 질문이 오기까지 9.6초, 답한 뒤 다시 움직이기까지 16.1초(**실측**). 쿨러 한 바퀴 6분 22초(**실측**). 팬 경보에서 사람 선택이 열리기까지 6분 15초(다른 일이 섞인 상태, **실측**). |
| ⑤ 알게 되는 것 | 범용 AI를 업무 시스템의 "일꾼"으로 쓰는 구조와, AI가 사람에게 묻는 지점을 안다. |
| ⑥ 회차 | 13 · 14 |
| ⑦ 아직 안 되는 것 | 근거 없는 카드를 서버가 막는 장면(코드를 일부러 고쳐 보는 실험)은 재현하지 못했다. Codex는 같은 질문에도 사람에게 묻지 않고 끝냈다. 일꾼의 작업 요약 하나가 영어로 나온 적이 있다. |
| ⑧ 시나리오 | 팬 · 쿨러(약한 고장) · 곁가지(사람에게 묻기) |

### 10. 사건 하나를 일 단위로 나눠 맡기와 그 기록

| | |
|---|---|
| ① 무슨 일 | 경보 하나가 처리 건 하나를 연다. 업무 흐름 그림(BPMN, 일의 순서와 담당을 그린 표준 그림)대로 일이 처음부터 전부 목록으로 생기고, 하나씩 "대기 → 진행 → 제출 → 완료"로 바뀐다. 가지 않은 갈래는 "취소"가 된다. 끝난 처리 건은 지식 지도에도 기록이 그림자처럼 복사된다. |
| ② 화면 | 처리 건(목록 · 상세의 결과 · 흐름 · 기록, 기록 › 지식 반영 표) · 승인과 실행(업무 흐름: AI · 담당자 · 시스템 줄) |
| ③ 해 보는 것 | 쿨러 경보 직후 일 목록 9줄을 세고 담당(AI · 운전원 · 생산관리자 · 설비 제어 · 처리 시스템 · 정비 시스템)을 적는다. 상태가 바뀌는 시각을 표로 만든다. 끝난 처리 건이 지식 지도에 어떻게 남았는지 질의로 찾는다. |
| ④ 시간 | 경보 뒤 처리 건 열림 3.3초(**실측**). 기본 AI의 네 일 약 18초(**실측**). |
| ⑤ 알게 되는 것 | 주인공은 처리 흐름이고 AI는 그 안의 일 하나다. |
| ⑥ 회차 | 15 · 18 |
| ⑦ 아직 안 되는 것 | 새 흐름 그림을 등록해도 경보가 여는 처리 건에는 쓰이지 않는다(경보용 흐름은 고정 파일). |
| ⑧ 시나리오 | 쿨러 |

### 11. 사람의 승인 · 거절 · 시간 초과

| | |
|---|---|
| ① 무슨 일 | 사람이 카드를 고르면 역할을 검사한다. 운전원은 거절, 생산관리자는 통과. 정해진 시간(규칙상 10분) 안에 아무도 안 고르면 상급자 확인 일이 열린다. 고르기 전 "새 예측 검토"를 눌러 지금 값으로 다시 확인한다. |
| ② 화면 | 처리 건(내 차례 › 조치 카드 선택) · 결함 시뮬레이션(최근 제어 요청 결과) · 관리(정의 등록 · 버전 선택 · 실행) |
| ③ 해 보는 것 | 운전원으로 골라 거절을 받고, 생산관리자로 다시 고른다. 다른 경보에서는 일부러 안 고르고 기다려 상급자 호출을 본다. 점수 입력 양식이 있는 간단한 흐름을 버전 1 · 2로 등록해, 같은 점수 7이 버전에 따라 다른 결과로 끝나는 것을 본다. |
| ④ 시간 | 10분 제한이 20배속에서 30초. 안 고르면 32초 뒤 상급자 호출(**실측**). 흐름 버전 실습은 기다림 없음(**예상**). |
| ⑤ 알게 되는 것 | 사람은 버튼만 누르지만 그 버튼에는 권한 · 기한 · 기록이 붙어 있다. |
| ⑥ 회차 | 16 |
| ⑦ 아직 안 되는 것 | 30초는 읽고 고르기에 짧다. 화면에서 기한을 늘리는 방법은 없다(강사가 흐름 파일을 바꾸고 다시 켜야 함). |
| ⑧ 시나리오 | 쿨러 · 곁가지(권한 거절 · 시간 초과) |

### 12. 설비 명령, 세 겹 검사, 다시 지켜보고 정비 요청으로 끝내기

| | |
|---|---|
| ① 무슨 일 | AI는 설비에 직접 쓰지 못한다. 명령은 세 겹을 지난다: 사람 승인 → 관문(승인 기록 · 형식 · 중복 · 운전 모드를 검사하는 프로그램) → PLC(설비를 직접 움직이는 제어기)의 안전장치(위험 값이면 설비를 스스로 멈춤). 명령 뒤 시스템은 정해진 시간 동안 설비가 정말 나았는지 다시 지켜보고, 나았으면 정비 요청을 남기고 끝낸다. |
| ② 화면 | 결함 시뮬레이션(최근 제어 요청 결과, 설비 카드 운전 상태) · 처리 건(명령 · 다시 지켜보기 · 정비 요청 일) · 승인과 실행(시스템 실행 이력) |
| ③ 해 보는 것 | 설비를 원격 수동으로 바꾸고 고장을 넣어, 제어 카드가 규정상 전부 빠지는 것을 본다. 쿨러 · 펌프 · 팬 각각의 "다 나았다" 기준(유온 55 ℃ 아래 · 압력 165 이상 · 진동 1.2 아래)을 기록에서 찾아 표로 만든다. 회사 정비 시스템에 정비 요청 한 줄이 생긴 것을 확인한다. |
| ④ 시간 | 명령 뒤 설비 응답 1.5초(**실측**). 다시 지켜보기 규칙 15분 = 20배속 45초(**예상**, 규칙 환산). 쿨러에서 설비 응답부터 종결까지 약 50초(**실측**). |
| ⑤ 알게 되는 것 | 안전은 한 곳이 아니라 여러 층이 나눠 지킨다. "명령 성공"과 "문제 해결"은 다르다. |
| ⑥ 회차 | 02 · 17 · 19 |
| ⑦ 아직 안 되는 것 | 원격 수동 장면에서는 조치가 없어 설비가 과열로 멈춘 뒤 책임자 확인 일이 남는다(정상 동작이지만 정리가 필요). |
| ⑧ 시나리오 | 쿨러 · 펌프 · 팬 · 곁가지(과열 정지) |

### 13. 회사 시스템이 판단을 바꾸는 장면

| | |
|---|---|
| ① 무슨 일 | 생산 · 판매 · 정비 · 품질 · 구매 시스템의 실제 표가 있다. 납기가 급하면 생산을 유지하는 조치가 올라가고, 승인된 공급사가 아니면 부품 구매가 필요한 조치가 빠진다. 카드를 받은 뒤 값이 바뀌면 옛 카드로 한 승인은 거절된다. |
| ② 화면 | 조치 판단 규칙 · 승인과 실행(기업 시스템 현황 · 시스템 실행 이력의 변경 전 · 후 표) |
| ③ 해 보는 것 | 납기 · 품질 값을 바꾸기 전과 후의 카드 순위를 비교표로 만든다. 공급사 승인을 끄면 "펌프 축 씰 교체"가 빠지고, 다시 켜면 돌아오는 것을 본다. 카드를 받은 뒤 납기를 바꾸고 옛 카드를 골라 거절 사유(바뀐 입력 이름)를 읽는다. 바꾼 값은 모두 되돌린다. |
| ④ 시간 | 값 바꾸고 다시 판단(**예상**: 바로). 승인 거절 장면은 30초 선택 시간 안에 납기 변경과 선택을 이어서 해야 한다. |

## 실라버스 짤 때 알아둘 것

- **20배속이 기본이다.** 가상 공장이라 시간을 빨리 돌린다. 규칙의 10분 선택 기한은 30초, 15분 다시 지켜보기는 45초가 된다. 1~2배속은 쓰지 않는다.
- **실제 AI 일꾼은 일 하나에 29~101초**(쿨러 실측, 네 일 합 269초). 시스템 안 기본 AI는 네 일을 약 15~18초에 끝낸다. AI 일꾼 회차는 기다리는 시간을 수업 안에 넣어야 한다.
- **한 바퀴 완주 시간(자동 실행, 사람 고르는 시간 제외)**: 쿨러 기본 AI 약 2분 반 · 실제 AI 일꾼 6분 22초, 펌프 3분 34초, 팬 2분 5초. 모두 실측이다.
- **선택 시간 30초는 짧다.** "새 예측 검토" 직후 바로 제출해야 한다. 카드를 천천히 읽는 활동은 처리 건이 끝난 뒤 기록 화면으로 하는 편이 맞다.
- **포털로 넣는 쿨러 고장은 센 고장이다.** 조치 없이 두면 경보 뒤 약 1분에 설비가 멈춘다. 실제 AI 일꾼 회차는 팬 고장이나 스크립트의 약한 쿨러 고장으로 한다.
- **PC 사양**: 지금 구성은 Docker에 메모리 4 GB 이상 할당을 권장한다. 16 GB 학생 PC는 보류된 설비층 제품 교체(약 3.5 GB 추가 예상)를 전제로 한 값이다. 전체 켜기는 제작자 PC에서 4분 28초(실측)였고, 학생 PC에서는 아직 재 본 적 없다.
- **수강생 AI 계정 · 사용량 운영 방식은 정해지지 않았다**(운영 측 결정). 제작자 PC의 구독 로그인 Claude Code · Codex로만 검증했다.
- **커리큘럼 초안의 회차별 분 배분(설명/실습/정리)은 전부 예상치다.** 강사가 배포본으로 한 번 완주한 뒤 실측으로 바꾼다.
