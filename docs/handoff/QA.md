## 질문과 답

**Q1. ZIP(R2 인계)이 뭔가?** 이전 AI 가 쓴 "기존 판단을 정답으로 보지 말고 감사부터 하라"는 지시서. 참고일 뿐 지시가 아님. 그 안의 회의 원문 2가 진짜 요구. 1단계 프롬프트가 참조하는 개별 파일은 FINAL ZIP 에 없다(HTML 안에만 있음).

**Q2. 데이터 패브릭을 구현하라는 건가?** 아니다. 회의 L63~67 "패브릭까지 안 가더라도 DB 에서 값을 가져오면 된다", L447 "다종 DB 가 되면 패브릭이 필요하다는 시나리오로 확장". 후반 설명만.

**Q3. 우리가 ProcessGPT 를 만드는 건가? 홍보용?** ProcessGPT 가 하는 일의 축소판을 오픈소스 조각으로 학생과 직접 조립하고, 후반에 "이걸 제품화한 것이 ProcessGPT"로 실제 제품을 보여 준다(L164 지금은 우리 거 안 씀, L172 후반 락인, L436 "이렇게 구현하다 보면 프로세스 GPT 가 되어 버린다"). 미니 버전이 교육의 본체, 제품 시연은 마지막 장.

**Q4. 에이전트는 태스크에 속하고 프로세스 인스턴스 개념인가?** 맞다. 박 이사 스키마(L19~24): 프로세스 안에 이벤트 · 룰태스크 · 서비스태스크 · 휴먼태스크. 에이전트는 그중 한 태스크의 실행자. ProcessGPT 코드도 같다(todolist 한 줄 = 태스크, 에이전트 = agent_orch 가 자기 것인 행을 폴링하는 워커). 레포는 반대 순서(카드 뒤 Incident)였고 이번 B5 로 뒤집었다.

**Q5. 레포 47개를 다 빠삭하게 조사해야 하나?** 아니다. 항목 대응 레포만(HANDOFF.md §4 "참고 레포 조사 결과"). 빌릴 조각을 정한 뒤 그 레포만 깊게.

**Q6. 온톨로지 · 프론트 등 ProcessGPT 전반을 참조해야 하지 않나?** 맞다. 온톨로지 정본은 process-gpt-vue3/ontology(스키마 계약 29노드 · 47엣지) · process-gpt-strategy(BSC · 인제스천 · 영향도) · ontology-studio. HYD v2 는 이미 그 구조를 따르고 있어 Execution 레이어만 추가했다. 그래프 DB 는 Neo4j 유지(회의 전제).

**Q7. 바로 착수하면 되나? 정해진 것만 하지 말고 유연하게?** 착수했다. 고정은 회의가 요구한 목표와 §3 규칙, 유연은 구현 방법(단계마다 실제로 돌려 보고 바꾸되 DECISIONS.md 에 이유). 유료 · push · 삭제는 묻는다.

**Q8. 작업보고 없이 쭉 진행하는 거 아닌가?** 맞다. 기록은 docs/handoff/ 갱신으로 대신한다.

**Q9. pull 했나?** 했다. 로컬을 원격 main(aad500b, 박용주 10-02 온톨로지 v2)으로 fast-forward, 사용자 한 줄 수정 보존.

**Q10. 온톨로지 등은 이미 레포에 다 구현돼 있는 거 알지?** 안다. 재구현 금지, 재사용(HANDOFF.md §4 "레포에 이미 있는 것").

**Q11. 목표를 스스로 잡을까, 함께 작성할까? 핸드오프 폴더로 상태 관리?** Claude 가 GOAL.md 초안을 잡았고 사용자 확인을 기다린다. 상태 관리는 이 폴더(GOAL · HANDOFF · QA · DECISIONS · USER_UTTERANCES).

전체 사건 효과와 승인 소유권을 확인해 무조치 PENDING 명령만 새 판단/동의로 전환한다. 이미 종료된 사건은 권한 있는 검토 후 CANCELLED로 종결한다. 실제 효과를 지우거나 성공으로 바꾸지 않는다. 종료된 실제 실패사건/서비스 재시작은 검증했고 활성사건의 실제 재승인·PLC는 후속이다.

### A046: 승인 뒤 현재조건이 바뀌면?

실제 MES 납기6→36 변경에서 옛 승인 명령을 멈추고, 새 판단과 별도 사람 동의 뒤 PLC ACK/CMMS/재관측을 확인했다. synthetic 경보와 기록 출력을 사용했으므로 새Codex/실제고장 검증은 아니다. 상세 경계는 HANDOFF §9 A046.

### A047: 지식 수정 중 오류나 중복 저장은?

기존 승인 관계가 사라지는 실제 결함을 고쳐 속성·관계·단계·영수증을 함께 저장한다. 오래된 조회 판본은409로 거절하고 응답 유실은 같은 요청으로 재확인한다. 실제Neo4j14/API6·화면·서비스 재시작으로 확인했다. 지식 변경이 기존 판단/실행의 모든 의미 관계에 전파되는 것까지 완료됐다는 뜻은 아니다.

### A048: 지식 노드를 나중에 추가하거나 의미 연결을 제거하면?

투영에 사용하는 지식 식별자·노드·프로세스 멤버십 변경을 감지해 기존 사건/판단/실행의 그래프 조인을 다시 연결한다. 없어진 멤버십은 오래된 MAPS_TO를 지우고 경고한다. 실제저장소10/가동6/재시작4 확인. 저장된 판단·승인·업무 출력 자체를 새 지식으로 다시 실행하지 않는다. 투영만 훼손된 경우의 별도 명시 복구는 아래 A049를 따른다.

### A049: 그래프 쓰기가 거절되거나 복원 원천과 revision이 다르면?

정확한 반영 영수증이 없으면 완료 처리하지 않고 해당 원천을 검토 대기로 보존한다. 운영자가 원천·고정 정의·의존 판단·그래프를 비교해 명시적으로 재등록하며, 실제 전송을 별도로 확인한다. 실제저장소11/가동CLI·사건 전체 복원·서비스 재시작9 확인. 업무 원문을 바꾸거나 완료를 꾸미지 않았다. 여러 업무 DB 전체 백업 복원, 투영 단독 훼손 자동 탐지, 새 Codex 경로까지 검증한 것은 아니다.

### A050: 일반 문서 추출도 실제 에이전트로 검증했나?

아직 아니다. 고정 원문 판본으로 Codex 워커 작업을 요청하고 결과·인용을 검사한 뒤 사람이 적재하는 경로는 배포했다. 전체728·실제 계약13+5·포털 검증은 명시 합성 출력이며 의미 추출 정확성을 증명하지 않는다. 기존 정규식 파서는 빠른 구조화 미리보기로 표시한다. 새 Codex 텍스트/PDF 추출·OCR/표 검증은 남겨 두고 정책 거절 경로를 우회하지 않았다.

### A051: 센서도 현재 스키마를 읽고 생성한 질의로 조회할 수 있나?

TimescaleDB 실제 스키마·최근 관측 태그를 읽고 SELECT를 실행하는 MCP를 배포했다. 실제 임계값 변경·빈 결과·잘못된 열·연결 실패와 읽기 권한을13+9검사로 확인했다. 이 SQL은 검사기가 작성했으며 새Codex 생성이나 PromQL 구현 증거가 아니다. 현재 Prometheus는 플랫폼 지표이고 팬 진동 원천은 TimescaleDB다. 지속 조건은 평균만으로 판정하지 않으며 관측 간격·구간·신선도 계약이 필요하다.

### A052: PromQL도 실제 원천에서 실행되나?

실제 Prometheus2.55.1을 기동하고 metadata/레이블 조회와 단일·구간 PromQL을 MCP로 배포했다. 실제17항목과 서버 중지→UNKNOWN→재시작 복구를 확인했다. 조회한 지표에는 플랫폼 상태 외 detector의 최신 TS1·이상점수도 있다. 팬 진동 VS1은 exporter에 없으며 원천은 TimescaleDB다. scrape가 최근이어도 마지막 센서 이벤트가 최근이라는 뜻은 아니다. 새 Codex의 질의 생성과 지속조건/관측 누락 판단은 아직 미검증이다.

### A053: 조회 실패나 관측 없음이 원인 판단에서 사라지지 않나?

기존 코드에는 그 결함이 있었고7실패로 재현했다. 이제 Evidence의 UNKNOWN/오류가 순위·진단에 보존되며 미확인 후보 또는 전체불일치에서는 후속 추천을 보류한다. 실제22항목과 포털 보류·정상 경로를 확인했다. 이는 구간 전체 관측이나 새 Codex 보류 재개까지 검증한 것은 아니다. 구간 간격/DAQ/CEP 시간계약은 계속 남는다.

### A054: 입력이 끊겼다가 돌아와도 계속 이상이었던 것으로 계산하나?

기존 CEP는600초 공백 뒤 RAISE,599초 공백 뒤 CLEAR를 냈다. 이제 허용 관측 간격을 넘으면 새 구간부터 계산하고, 미확인 입력으로 기존 경보를 해제하지 않는다. 격리된 실제 Kafka 경로11항목을 확인했다. 가동 팬의 VS1 보고 간격은20배속 경사 창보다 길어 현재 UNKNOWN이 발생하며, 보고 주기와 실제 팬 경로 수정이 다음 일이다.

### A055: 팬 수집과 실제 복구까지 확인했나?

시간조건 입력6종을 매초 수집하도록 배포하고 실제DB 주기를 확인했다. 첫 실행은 process 재시작, 두 번째는 정상 진동의 경사 부호가 해제를 막아 각각12/13으로 실패했다. 결정13의 하한 히스테리시스대로 수정 후 전체796/실제 팬14항목, 승인→PLC→재관측→CMMS→종결을 확인했다. 실패2건의 사람 검토는 보존했다. 새 Codex 검증은 아니며 프로세스 재시작 원인과 정의 기반 CEP 일반화는 남는다.

### A057: 정의를 바꾸면 운영 감지와 재시작에도 반영되나? 효율적으로 진행하나?

TESTS/해제/유지시간 정의를 운영 Kafka 경로에 연결했고 실제 원천 변경·오류·강제종료 복구14항목을 확인했다. 전체832, 쿨러42/42, 팬 종결을 확인했지만 펌프·가림 진단 보류 전달/재평가가 실패했다. 같은 실패의 긴 대기를 검사기에서 제거하고 다음 수정은 이 시스템 결함에 집중한다. 근거 임계값을 낮추거나 새 Codex 성공으로 둔갑시키지 않는다. 재개에 필요한 최소 근거를 HANDOFF §9에 남기며 교재/리허설은 하지 않는다.

### A059: 새세션에서 할까요? 너무 오래되었는데

현재 재개점은 HANDOFF §9 A059 인계 시점이며 새 세션에서 그 지점부터 이어간다. 전체 목표는 바뀌지 않는다. 최종871검사, 실제PG7, 실제 펌프17·팬14·가림18과 포털 보류/재평가를 확인했다. 마지막 process 결과접수 backoff 보강은 이미지 빌드만 했고 배포/쿨러 최신 회귀가 남았다. 인계 시점에는 HYD 컨테이너 중지·PowerShell 워커/검사 프로세스0을 확인했다. 기존 F 블록 전환만을 목표로 다시 시작하지 않는다. 전체 요구의 미결과 최신 Codex 검증도 유지한다. 실제 새 호스트 세션 재현 시험은 하지 않았다.
