## 0. 한눈에

**이야기 한 줄**: 같은 공장(유압 파워팩)에서 성격이 다른 사건 세 건이 일어난다 — **A 쿨러 과열**(경보가 울리면 바로 식힌다) · **B 펌프 누설**(당장 멈추지 않고, 근거로 정비 일정을 잡는다) · **C 작동유 열화**(센서가 없어 사람이 입력해 시작한다). 세 사건을 **처음부터 끝까지 함께 끌고 가며**, 막마다 같은 일을 세 번 한다.

**막 순서**: 시작 → 온톨로지(공장이 아는 것) → 에이전트(AI 일꾼) → BPMN(업무 흐름) → 마무리(ProcessGPT 제품 시연 50분).

**막 안의 순서(고정)**: 막마다 똑같이 세 부분이다.

| 부분 | 무엇을 | 무엇으로 | 원칙 |
|---|---|---|---|
| ① 이론 | 그 막의 개념을 **처음부터**(LLM이 뭔지도 모르는 사람 기준). 20~30분 단위 여러 개, 단위마다 비유 → 무엇 → 왜 → (어떻게) + 눈으로 보기 + 가벼운 직접 해보기 | **일상 예시**(카페 · 배달 · 맛집 · 여행)와 **범용 도구**(채팅 AI · arrows.app · demo.bpmn.io · DMN 데모) · 종이 · 역할극 — **포털은 쓰지 않는다** | 막 첫머리에 모두. 세 시나리오 공통 개념 + "이번 막에서 무엇을 왜 하나"(흥미) + 이 막의 랩업들이 쓸 개념까지. 통합반이 더 길다 |
| ② 설비체험 | 이론의 개념을 우리 공장에 적용 — **포털에서 같은 활동을 A → B → C 순서로** | 포털(+ 막에 따라 bpmn.io) | 설명은 한 번, 내용이 달라 결과가 다르다. 두 번째 · 세 번째는 빨라지고 복습이 된다(이벤트 스토밍 수업에서 배민 → 11번가 → 구글드라이브를 차례로 하는 것과 같은 방식) |
| ③ 랩업 | **이 포털의 기능이 어떻게 만들어졌는지** 과정과 결과를 눈으로 보고, 바이브 코딩 · 명세 먼저(SDD) 방식으로 Claude Code에 시켜 직접 만든다 | VS Code 터미널의 Claude Code + 콘솔 로그(도구 호출) | 포털 기능 하나 = 랩업 하나. 막마다 여러 개. 랩업마다 "다시 만드는 포털 기능 · 볼 결과 · 출발본" |

모든 단계는 **강사와 함께** 한다. 혼자 하는 단계는 없다.

## 2. 시나리오 3개 정의

### 2-1. 왜 지금 세 시나리오로는 3번 반복이 안 되나 (저장소 확인)

- 지금의 쿨러 HYD-01 · 펌프 HYD-02 · 팬 HYD-03은 **같은 구조의 파워팩 세 대**(`it/neo4j/v2/instances.cypher:108-111` "설비 3대는 같은 구조")이고, 셋 다 **센서 경보로 시작해 같은 기준 흐름 하나**(`it/process/definitions/anomaly_response_v22.json`, 경보 정책에 세 패턴이 함께 있음)를 탄다: 진단 → 후보 → 규정 검토 → 순위 → 사람 선택 → 설비 명령 → 15분 재관측 → 작업지시.
- 지식은 한 매뉴얼(`ks:manual-hm`)의 절들로 이미 다 들어가 있다. 학생이 새로 넣는 문서는 지금 HM-9(작동유) 한 장뿐이다.
- 그래서 BPMN 막에서 A·B·C를 세 번 그려도 같은 그림이 세 번 나온다. 사용자 지적이 맞다.

### 2-3. 대안 — 쿨러 · 펌프 · 팬을 유지하고 문서만 시나리오마다 다르게

| | 업무 성격으로 나누기(추천) | 쿨러 · 펌프 · 팬 유지 + 문서만 다르게 |
|---|---|---|
| 온톨로지 막 3회 | 문서 · 내용 · 결과가 다름 | 문서를 3장 새로 쓰면 다름(쿨러 · 펌프 문서 새로) |
| 에이전트 막 3회 | 근거 종류가 다름(손익 / 예측 · 업무 DB · 보류 / 사람 입력) | 셋 다 센서 근거 → 순위. 차이가 작음 |
| BPMN 막 3회 | 시작 방식 · 끝나는 방식이 다름(경보·회복 / 경보·일정 / 사람 입력·루프) | **셋 다 같은 기준 흐름** — 반복이 의미 없음. 다르게 하려면 억지로 흐름을 바꿔야 함 |
| 준비량 | 펌프 문서 1장 + B 흐름 견본 1개 + 라이브 확인 | 쿨러 · 펌프 문서 2장 + 다른 흐름을 만들 명분이 없음 |

**추천: 업무 성격으로 나누기.** 이유: ① 반복이 진짜 의미를 가지려면 막 셋 모두에서 결과가 달라야 하는데, 대안은 BPMN 막에서 무너진다. ② C(작동유)는 이미 사람 입력 시작 · 정비형 흐름 · 매뉴얼 적재까지 라이브로 검증됐다(HANDOFF A160, B7 실제 워커 46/46). ③ 새로 준비할 것은 B 하나(문서 1장 + 흐름 견본)이고 코드 수정 없이 된다(6절).

### BPMN — 승인부터 작업지시까지, 사건 한 건을 끝까지 닫는다

**정리한 것**
- L2 · L3은 하나로 합침(틀 세우기 하나).
- **L7(세 설비로 넓히기)은 뺌** — 설비체험 B · C가 같은 틀에 다른 고장을 넣는 일을 대신한다.
- **L18(채점기)은 에이전트 막에 둠** — 개념(흔들림 · 정답표)이 에이전트 이론 A-T8에 있다. 지식 품질 검사는 L6(온톨로지).
- **L24 재정의(확인 필요)**: 원래 "펌프 판단 추가(SDD)"였으나 펌프가 시나리오 B가 되어 랩업 소재로 겹친다. "사전 검사 규칙 하나를 명세 먼저 더하기"로 바꾸면 포털 기능(사전 검사)과 1:1이 되고 SDD(명세 먼저 · 기존 기능을 깨지 않고 추가)가 그대로 마지막 랩업이 된다.
- **L26(Notion 지식 퀴즈)은 선택** — 포털 기능을 다시 만드는 랩업이 아니다(포털에는 Notion MCP 등록만 있다). 시작 0-1 Notion 노트와 이어지므로 남는 시간 후보로 둔다.
- L13의 원래 소재(팬 진동)는 팬이 A로 흡수되므로 A 데이터(유온 · 팬 지시값)로 바꾼다.

**포털 기능인데 랩업이 없는 것(빈칸)**: 손익 · What-if(A7), KPI 목표 · 관점 중요도 바꿔 보기(B5), 흐름 판본 배포 · 되돌리기 · 기준 비교(B4), 사람 입력으로 사건 열기(B7), KPI 실적 · 역추적(A8), 옛 DB 뜻 복원(A9), 출발본 내보내기 · 가져오기(B6). 지금은 설비체험에서만 다룬다. 남는 시간에 넣을 후보는 5절.

**랩업 재료(확인 필요)**: 사용자 메모에는 "랩업은 시나리오 3개와 별개로 미니 제조 관련으로" 쓰여 있다. 두 가지 길: (가) 랩업 데이터를 A 쿨러 하나로 통일 — 포털 기능을 "다시 만드는" 것이 눈에 바로 대조된다. (나) 시나리오와 별개인 작은 제조 예(예: 포장 라인) — 시나리오 반복 피로가 없지만 포털과 대조가 한 번 걸러진다. 이 문서의 행은 (가)로 적었다.

**출발본 상태**: 포털용 출발본(구성 내보내기 · 가져오기, B6)은 있다. 랩업용 출발본(Claude Code로 시작할 작은 폴더 · 데이터 · 첫 지시문)은 저장소에서 찾지 못했다 → **랩업 23개 모두 준비할 것**.
