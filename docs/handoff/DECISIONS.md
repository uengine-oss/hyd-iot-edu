# DECISIONS — 결정 경위와 폐기된 판단

## 15. 전체 재대조·필요한 재구현 승인 (2026-10-04, Codex 세션 발화 C08~C11)

사용자는 F의 워커 전환만이 아니라 회의 원문 + HYD 현재 구현 + uengine-oss 지도의 실제 코드 전체 대응을 요구했다. 잘못된 구조는 큰 교체가 필요해도 교체하고, 관련된 유용한 기능도 강의 관점에서 가져온다. 시간이 들더라도 잘못된 것을 덮지 않으며 맥락 유실을 막도록 단계마다 기록한다. 목표는 GOAL 현재 계약·HANDOFF §9 G·AUDIT.md에 연결한다.

새 권한: 컴퓨터 자원 사용·삭제를 위임했다(C11). 필요 작업에 적용하며 새 결제·원격 push 승인으로 확대하지 않는다.

정정: 종전 DECISIONS 12/REPO_GAP가 원문 313~348행을 '결정론 원칙'의 근거로 든 것은 부정확하다. 해당 발언은 DB/Prometheus 메타데이터를 제공하여 LLM이 질의를 생성하도록 하자는 내용이다. 결정론 엔진 재사용과 LLM 질의 생성은 별도로 요구 적합성을 검증한다. 엔진 상태 관리가 결정론적이라는 이유로 동적 데이터 조회 요구를 생략할 수 없다.

범위 구분: 회의는 최소 스키마·기본 모델을 허용하고(15~22, 438), 자유로운 프로세스/룰 관리 제품 기능은 후반 확장으로 연결한다(448). 사용자 최신 지시는 지원 범위 내 여러 시나리오가 정의·지식·실데이터를 통해 실행되고 관련 기능을 적극 보강하는 방향이다. 모든 제품을 무조건 설치하거나 모든 임의 업무를 지원한다는 뜻으로 확대하지 않는다.

보류된 판정: 이전 '제품에 없음', '교육용 축소', 'D4만 남음'은 현재 전체 범위의 결론으로 재사용하지 않는다. 관련 저장소와 반증 근거를 조사해 항목별로 확정한다.

## 16. 서비스 실행 계약과 실패 의미 교정 (2026-10-04, G2 첫 묶음)

근거: A005/A006/A008 인메모리 반례와 수정 전 테스트 5 실패 재현. completion b272c9a `polling_service.py:45~76`은 정의/버전의 활동 타입으로 디스패치하고 `workitem_processor.py:5026~5258`은 업무별 도구 결과를 처리한다. HYD의 서비스 실행은 특정 activity ID 3개에 묶여 있었다.

- 정의의 `tool` 계약(incident:command, incident:reobserve, enterprise:WO_CREATE)으로 서비스 실행을 선택한다. 선택 폼도 formHandler:select_card로 식별하며 Incident 콜백도 tool로 대기 작업을 찾는다. 이 목록은 지원 도구 계약이며 모든 임의 서비스 지원을 뜻하지 않는다. 미지원 도구는 오류/재시도 경로로 보낸다.
- Execution 투영은 정의 ontologyRef와 인스턴스 tenant_id를 사용한다. ontologyRef가 없으면 거짓 연결을 생성하지 않고 경고한다. 새 정의의 그래프 노드 생성/버전 동기화는 아직 별도 미결이다.
- 기업 도구가 ok=false이면 결과를 error 이벤트에 보존하고 성공 제출을 하지 않는다. 동일 작업/decision ID로 재시도한다.
- 원제품은 retry 3 뒤 DONE을 기록한다. HYD는 **PENDING + 오류 + consumer 해제**, 인스턴스 RUNNING으로 유지한다. 실패를 성공 종결로 보이지 않게 하라는 최신 사용자 지시 및 실제 제어/작업지시 결과 의미를 따른 명시적 편차다. 수동 복구 UI/권한·재시도 API는 G2 후속에서 검증/구현한다.
- 기준 테스트 중 '오류 3회 뒤 DONE' 기대 1개를 위 계약에 따라 PENDING으로 변경했다. 과거 259 passed 증거는 원본으로 보존한다. 기존 145개 테스트의 기대를 임의 수정한 것이 아니다.

정본은 [HANDOFF.md](HANDOFF.md) §2(확정 방향) · §3(규칙)이다. 여기에는 **왜 그렇게 됐는지와 무엇을 버렸는지**만 둔다. 되살리지 않기 위해 지우지 않는다.

## 폐기된 판단 — 되살리지 마라

- R1 추천 기본값(SQLite 유지 · 쿨러 우선 고정 · T2SQL/패브릭 보류 조건)을 "정답"으로 쓰는 것 → R2 가 미결정으로 되돌렸고 사용자가 "AI 판단 믿지 말라"고 함. 쿨러부터 가는 것은 의존 순서상 결정이지 R1 때문이 아님.

## 13. C4 펌프·팬 시나리오 — 온톨로지가 정답, 그 아래층(설비·PLC·탐지·회복 판정)을 맞춘다 (2026-10-04 새벽)

**계기.** 회의 14번(세 시나리오 교재)과 aad500b 알려진 한계 "펌프·팬 결함 시뮬레이터 없음". 온톨로지 v2 에는 두 패턴의 임계값·원인·증거 SQL·스킬·예측·순위 규칙이 모두 있었고, 설비 시뮬레이터·탐지기·회복 판정만 쿨러 전용이어서 그 길을 한 번도 타 본 적이 없었다.

**결정.**
1. 임계값·예측값은 온톨로지 그대로(PS1<165·FS1<8.0·Load≥80, VS1>1.2 상승, fc:pump-switch 182 bar, fc:fan-slow-vs1 1.0, 인터록 PS1<130·VS1≥2.0). 시뮬레이터 상수는 그 값이 나오도록 풀었다(thermal.py 머리 주석).
2. PLC 에 `PumpSelect`·`Stop` 쓰기를 추가한다. 온톨로지 원자 조치 action:select-pump·action:controlled-stop 이 실제로 실행되어야 "예비 펌프 전환"·"계획 정지" 스킬이 종결까지 간다. `PRESSURE_SET` 은 계속 거부: rule:no-pressure-raise 가 금지하는 옛 절차이고 이 PLC 에 압력 설정값이 없다(배우는 요점은 "규정상 제외"이지 실행이 아님).
3. 인터록은 온톨로지 AFFECTS 노트(PS1<130 저압, VS1≥2.0 진동)를 따른다. 결과로 "팬 100 %로 올리면 마모된 베어링이 인터록을 건다"는 교차 효과가 생긴다 — 쿨러 조치(fan-max)를 팬 결함에 쓰면 왜 안 되는지를 설비가 보여 준다.
4. 탐지기 clear 는 raise 아래 히스테리시스(PS1≥168·FS1≥8.0, VS1<1.1). 펌프 패턴은 Load<80 에서도 끝난다(저부하는 압력이 낮은 게 정상). 따라서 derate-70 은 경보를 가리지만 재관측(PS1≥165)은 실패 → 에스컬레이션. 예측 fc:pump-derate70 = 160 bar 와 일치하는 이야기.
5. 재관측 회복 기준은 패턴별(`definition.RECOVERY`). 쿨러 TS1<55 는 그대로.
6. 시나리오 스크립트에 펌프·팬 흐름을 "미리" 쓰지 않는다. 실행 못 하는 스크립트는 검증 없는 주장이 된다(CLAUDE.md §5). 컨테이너를 올릴 수 있을 때 쓰고 돌린다.

**폐기.** "펌프·팬은 쿨러 완료 뒤 결정" 보류(HANDOFF §6). 쿨러 한 바퀴(B11)는 돌았고 D3 이식도 코드로 끝나 보류 사유가 사라졌다.

## 22. 실행 정의는 등록된 버전의 내용으로 고정한다

제품 completion의 명시 버전 조회 계약을 참고하되, 못 찾으면 작업본으로 fallback하는 부분은 HYD에 채택하지 않는다. tenant/id/version별 immutable 저장을 기존 proc_def_version에 HYD tag로 분리하고 현재 proc_def는 조회용 head로 유지한다. 같은 버전의 다른 내용은 실패, 기존 인스턴스/워커는 자신이 시작한 버전으로 처리한다. 제품의 major/minor 자동 steering/feedback publish를 구현했다는 뜻은 아니다. 정의 변경 실습은 새 버전 등록이 필요하다.

## 23. 실행 그래프는 정의별 버전의 흐름 노드를 보존한다

ProcessGPT vue3 SCHEMA.md §4.2/5.2(d88f78c)는 head 요소와 과거 dangling 참조를 명시한다. HYD에서는 변경 전후 실행을 강의에서 비교하기 위해 ProcessVersion과 tenant/definition/version/element별 FlowNode snapshot을 보존하는 확장을 선택한다. 원본과 동일한 구현이라고 설명하지 않는다. SQL의 immutable 정의가 원본이며 Neo4j는 재생성 가능한 투영이다.

업무 온톨로지 Process/Task/Event/Gateway는 유지한다. ProcessInstance USES_VERSION ProcessVersion HAS_NODE 버전별 FlowNode, WorkItem EXECUTES 버전별 Task 또는 Event, 버전별 FlowNode MAPS_TO 업무 FlowNode로 구분한다. 연결할 업무 Process가 없더라도 실행 기록을 버리지 않으며 경고를 노출하고 가짜 업무 노드를 만들지 않는다. 역할 없는 정의도 투영한다. 재투영은 이전 담당자 연결을 제거한다. 스키마2.5.0과 generated 산출물에 이 계약을 선언한다. 동시 상태 전이의 순서 보장/outbox는 별도 후속이며 이 투영만으로 해결됐다고 하지 않는다.


## 24. 정의 등록은 실행 버전과 폼 계약을 함께 고정한다

vue3 ProcessGPTBackend.ts L421~572/615~700/943~1045(d88f78c)의 form_def·proc_def_version·실행 버전 선택을 대조했다. HYD 공개 등록은 forms 필드에 폼의 fields_json을 포함하고 기존 immutable 정의 저장에 같이 넣는다. ## 28. 업무 MCP는 SQL 구문과 실제 DB 권한을 함께 제한한다

neo4j-text2sql25ab12a의 AST 기반 SQLGuard를 참고하되 HYD의 업무 원천은 ent 스키마로 제한한다. CTE 이름과 실제 테이블을 구별하고 함수 호출 허용 목록, 쓰기/잠금 거절, 바깥 LIMIT 최대200을 적용한다. 문자열 내부의 SQL 단어는 데이터로 보존한다. 임의 PostgreSQL 문법 전체 지원을 뜻하지 않는다.

MCP는 hyd_enterprise_reader 전용 역할만 허용하며 postgres DSN은 연결 단계에서 거절한다. 현재 ent 16테이블 SELECT/RLS 조회정책과 7개 읽기 RPC, read-only transaction/5초 제한을 함께 쓴다. PUBLIC에 남아 있던 두 쓰기 RPC 실행 권한을 회수하고 service_role의 실행 권한은 유지한다. 새 테이블/함수는 권한과 계약을 명시적으로 검토해 추가한다. 이 역할은 한 교육공장의 업무 데이터를 읽는 역할이며 여러 고객의 업무 행을 분리하는 제품용 tenant 인증 구현은 아니다. 코드/배포 검증은 AUDIT A022 후속을 따른다.


## 29. 업무 워커의 MCP 목록에서 개인 계정 앱을 제외한다

호출별 `--disable apps`로 개인 계정 앱의 MCP 도구를 노출하지 않는다. 사용자 config.toml이나 execpolicy rules를 수정하지 않는다. 실제 도구 목록 19개/업무 서버3종 읽기 및 변경 후 worker.main의 두 정의 실행으로 검증했다(AUDIT A023). CLI의 내장 도구나 OS/네트워크 접근까지 전부 격리했다는 뜻은 아니다. 서로 다른 작업 디렉터리도 보관 경계이며 접근통제를 대신하지 않는다. 시작한 도구의 종료 기록 누락과 사람질문/재개 경로는 계속 별도로 검증한다.


## 30. 타이머와 서비스 복구는 화면 목록과 분리하고 인스턴스별로 직렬화한다

ProcessGPT의 타이머 RPC/30분 stale consumer 정책을 대조했다. HYD는 SQL due 조회와 대기 서비스 키 순회로 화면 한도가 실행을 누락시키지 않도록 한다. 승인·완료·타이머·callback은 같은 인스턴스/작업 행을 잠그고 최신 상태를 읽어 DB에 원자 저장한다. deadline이 지난 선택은 타이머 poll 이전에도 거절한다. 도착 순서가 늦은 callback보다 현재 Incident 상태를 사용한다.

PLC ACK 뒤 서버가 죽으면 기존 Store.restore 정책대로 PROCESS_RESTART_REVIEW를 유지한다. 대기 서비스는 이를 읽어 recovered=false와 생산관리자 확인 작업으로 연결하며 명령을 재발행하지 않는다. 사람 확인 뒤 ev:escalated로 끝낸다. 실제 강제종료38/38 및 Pg11/11은 AUDIT A021. 이 계약을 DB/외부시스템/그래프 전체 exactly-once 보장으로 확대하지 않는다. 일반 engine claim 복구 지연과 durable outbox는 후속이다.


## 31. 부모 갱신 트리거가 있는 작업표는 부모부터 잠근다

A021 실제 Codex의 PostgreSQL 교착은 부모→자식 엔진과 자식→부모 워커트리거의 순서 역전이었다. claim/result/status/release/legacy RPC/stale정리 모두 부모부터 잠근다. 경쟁중 부모는 claim에서 건너뛰고 다음poll에 재검사한다. 프로세스 없는 adhoc 큐는 HYD process RPC의 범위가 아니다. 직접 SQL 수정 클라이언트는 같은 순서를 지켜야 한다. 기존 반례7/7→수정후7/7과 실제전체 재실행은 AUDIT를 따른다.

## 32. 업무 질문은 권한 승인과 분리하고 DB에 원자적으로 남긴다

CLI의 permission 이벤트만으로 업무 질문을 구현했다고 하지 않는다. 에이전트가 명시적 __human_input__ JSON으로 질문하면 작업은 IN_PROGRESS/HUMAN_ASKED이며 결과폼을 가짜로 채우지 않는다. 질문·job·session·알림을 DB에 함께 저장하고 workspace파일은cache다. 현재 질문의 답변만 받고 중복은409, 저장된 같은세션을 재개한다. 답변은 CLI권한이나 PLC승인을 변경하지 않는다. 실제Codex 두입력/두분기와 새worker·캐시부재 복구를 확인했으며 포털직접클릭은 도구제약으로 미완료다.


## 33. 승인 접수와 외부 전달 결과를 분리한다

사람의선택/승인스냅샷/할일제출/응답타이머취소는같은PG트랜잭션에저장한다. SQLite book이나외부업무를그보다먼저변경하지않는다. 전달자는저장한입력과같은멱등키만사용하며, 전달실패시후속작업은진행하지않고역할이있는사람의재시도를받는다. 기존legacy승인·거부API는프로세스소유Incident/결정에사용할수없다. 일반그래프·감사outbox까지보장하는계약은아니며현재PLC/업무조건재검증은후속이다. 실제강제종료/동시연결/실제설비범위는APPROVAL_RECOVERY를따른다.

## 34. Incident 종결은 실제 CMMS 접수 참조를 따른다

재관측 성공은 RESOLVED이며, 승인한 옵션과 후속 정비 요청을 보존한 뒤 실제 CMMS 성공/ref를 받아야 WORK_ORDER_CREATED/CLOSED로 전이한다. 임의 WO 번호와 다른 대안 SOP를 만들지 않는다. WO-only는 PLC를 거치지 않으며 정비 접수가 실제 정비 완료를 뜻하지 않는다. SQL/SQLite 응답 저장 실패와 재시작은 같은 요청/멱등키로 회수한다. 자동3회 소진 뒤 원승인 역할을 검증한 재시도를 받으며 프로세스 소유 건의 legacy 우회는 막는다. 실제6/6·인스턴스40/40·직접48/48 범위와 새Codex 시작심사거절은 WORK_ORDER_RECOVERY에 구분한다.


## 35. 문서 원문·검토·적재를 분리하고 개정은 소유 그래프를 대조한다

ontology-studio6a229be8의고정target_schema/원문hash·페이지/적재뒤질의루프를참고한다. 노드별부분성공/문자열절단/파일명식별을그대로채택하지않는다. HYD 원문은tenant+논리문서UUID+원본SHA,인용은판본/페이지/문자좌표/정확문자열로검증한다. 사람검토플랜전체를확인하고문서소유그래프/배치before·after/head를한Neo4j거래에저장한다. ManualIngestionDocument/Batch는적재이력제어메타데이터이며새업무온톨로지클래스를문서마다추론해추가하는것이아니다.

## 36. 승인한 내용과 실행 시점의 조건을 함께 검증한다

선택 당시 규칙/역할/소스가유효했다는사실은나중의실행허가가아니다. 선택접수·승인전달·명령발행직전에현재그래프와원천을다시읽는다. 읽기실패/오래된센서/필수미확인값은통과값으로대체하지않는다. 카드actions/steps/approver/forecast와공개경고·감점및중요업무조건이바뀌면새검토가필요하다. 평가감사는승인접수와구분하여남기며승인스냅샷을덮어쓰지않는다.

WARN의미확인은미확인변수와근거를사람에게공개한경고로유지한다. 기존카드에없던미확인경고를승인뒤추가해실행할수없다. EXCLUDE/PENALTY필수값미확인은보류한다. 이정책을적용하니펌프의필수온도예측누락이노출됐다(A030). 해당금지규칙을지우거나임의예측값을넣어정상으로만들지않는다. 실제증거와미완료재작업/예측범위는CURRENT_APPROVAL을따른다.


## 37. 현재 조치 예측은 명시 모델과 원천 입력을 따른다

A030에서는 Asset가 모델ID/판본/범위/시간을 지정한다. 현재카드/MCP/승인검사는 같은 모델 제공자를 사용하며 고정 Forecast 설계점을 실패시 대체값으로 쓰지 않는다. 평형값과 일정시간뒤/구간최대값을 구분하고 예상인터록은 제외한다. 현재모델은 교육용 시뮬레이터용이며 현장검증모델로 설명하지 않는다. 입력/조치/계수/시각/적용범위/관련정책SHA를 저장한다.

시간과TS1의작은변화는명시재검토정책으로취급하지만정책/모델/조치/운전설정/열화변경을무시하지않는다. 검토한카드와다른명령은접수/전달/발행경계에서거부한다. live submit의가정facts덮어쓰기도거부한다. 이결정작성시점에는변경값미리보기와일반재작업이미완료였다. 이후변경값의새검토는38번/A031로연결했으며일반재작업은남아있다. 기본값쿨러/펌프성공을범용파라미터변경완료로세지않는다. 상태생산자는열화진행시작/종료를즉시발행한다. 검증과반례는FORECAST_MODEL에남긴다.

## 38. 변경 조치의 검토본을 보존하고 명시적으로 승인한다

A031은 활성 선택 작업에서 팬·부하를 현재 원천/모델/규칙으로 다시 계산한다. 명시 범위 안의 조치값만 받으며 facts나 원본 SOP를 덮지 않는다. 원래 결정 SHA와 작업/사건/설비/선택지에 묶인 불변 검토본을 먼저 저장하고, 사람은 그 ID를 지정해 승인한다. 원문 기본 절차와 실제 적용할 변경값을 화면과 승인 스냅샷에서 구분한다. 역할·SOP 절차·후보 근거가 빠진 것을 새 검토본으로 정당화하지 않는다.

미리보기는 승인/명령이 아니다. 승인은 기존 PG 거래와 전달 outbox를 사용하며 전달/발행 시 현재 조건과 정확 조치값을 다시 확인한다. 새 검토본을 만든 뒤에도 역할·기한·현장조건 위반은 거부한다. 느린 검사 도중 기한을 넘긴 요청도 접수하지 않는다. 일반 완료 태스크 재작업/효과 보상은 별도다. 실제 실행 범위와 20배속 첫 실패/5배속 비교 조건은 DECISION_REVIEWS에 보존한다.

## 39. 경보 원인을 보존하고 지원 범위 밖 입력은 사람 검토로 보낸다

A032의 anomaly_response 2.1은 지원 패턴·회복 tag/op/limit·CLEAR 요건·미지원 경로 alert_triage 1.0을 명시한다. 사건은 접수 당시 기준을 저장한다. 모르는 경보를 냉각기 진단으로 바꾸거나 TS1<55를 기본 회복 기준으로 만들지 않는다. PLC 사유별 정지 경보와 CLEAR의 원래 ID/패턴을 보존하며 원천 사유가 없으면 만들어 채우지 않는다.

미지원 경보의 검토 폼은 원문을 보여 주고 확인 내용을 기록한다. 서비스/에이전트/명령 선택을 포함할 수 없다. 검토 완료와 경보 CLEAR를 실제 회복·제어 승인으로 해석하지 않는다. 늦은 가이드와 결정도 이를 바꾸지 못한다. 실제 동시 경보의 저장 오류와 뒤따른 그래프 연결 누락을 수정했다. 새 실제49/49, 정상 쿨러5배속42/42, 펌프/팬/mask20배속37/37과 앞선20배속 승인 실패는 ALERT_ROUTING에 조건별로 보존한다. 원천 이벤트의 내구성 있는 접수/재처리는 EVENT_INBOX의 다음 설계이며 아직 구현 완료가 아니다.


## 40. 업무에 필요한 가이드 저장은 태스크 완료의 전제다

A034 실제 Codex 진단은 MCP가 반환한 asset/pattern 중심 가이드였고 경보 ID는 생략돼 있었다. 사건을 이미 식별한 엔진은 생략 필드를 원천 Incident에서 유지한다. 명시된 ID/설비/패턴/사건이 충돌하면 거절한다. 에이전트가 다시 쓴 evidence로 원문을 교체하지 않는다.

승인 입력인 가이드의 저장 실패를 post-commit 로그만 남기고 DONE으로 넘기지 않는다. SQLite 가이드를 먼저 저장한 뒤 PG의 DONE/다음 태스크를 commit한다. PG 실패 때 같은 가이드를 재저장하는 것은 멱등이며 명령을 발행하지 않는다. 이 순서가 두 DB의 원자 거래를 뜻하지는 않는다. 실제 PG/SQLite7/7과 전체549검사를 통과했고 배포 후 새 Codex 완주42/42 exit0를 확인했다. [GUIDE_COMMIT.md](GUIDE_COMMIT.md) 참조.

## 41. 실패한 승인 폐기는 효과 조회와 명시 취소로 남긴다

종료 사건의 실패 승인은 원래 payload/error/history를 보존한 DISCARDED로 기록하고 남은 인스턴스는 CANCELLED로 구분한다. 정상 회복/조치 취소로 설명하지 않는다. 같은 인스턴스 거래에서 역할·상태·서비스·다른 승인과 원래 효과를 확인한다. 결정 ID별 전체 기업 원장을 조회하며 최근300건에 없다는 이유로 효과 부재를 추측하지 않는다. 조회 실패와 기존/불명확 효과는 폐기 성공으로 바꾸지 않는다. 같은 요청 재전달은 같은 결과를 반환하고 다른 요청은 충돌한다. 원본 ProcessGPT의 새 UUID/재작업 이력은 REWORK에서 별도 연결한다. 이번 기능을 일반 재작업·물리 효과 보상으로 확대하지 않는다.

## 42. 시작 입력과 실행 결과의 생산 작업을 구분한다

새 인스턴스의 시작 입력은 initial_variables에 불변으로 보존한다. variables_data의 값이 작업 결과로 바뀌면 variable_sources에 실제 workitem UUID/활동/판본을 기록한다. 별도 서버 전이는 runtime으로 표시하며 작업 출처를 만들어 붙이지 않는다. 이전 인스턴스의 NULL은 원문 미보관이며 누적 값을 복사해 최초 입력이라고 하지 않는다. 재작업의 변수 재사용/무효화는 이 출처와 고정 정의에 근거해야 한다. 이 기록 자체가 새 작업 재실행이나 외부 효과 보상은 아니다. 실제 범위는 REWORK의 A036 후속이다.

## 43. 재작업 영향 계획과 실행 권한·효과 검증을 구분한다

영향 범위는 클라이언트의 활동 목록 대신 고정 정의의 흐름·변수·분기 조건·타이머와 실제 선행 참조에서 서버가 계산한다. 유효한 생산 작업과 불변 시작 입력만 새 변수 후보로 사용한다. 계획의 snapshot_token은 로컬 관측 근거이며 외부 효과를 확인하거나 실행을 승인하지 않는다. 기존 rework_count가 CMMS 동일 요청 재시도에도 쓰이므로 새 세대 식별자를 따로 설계한다. A037 미리보기의 execution_available=false는 새 세대 전이가 아직 연결되지 않았다는 명시 상태이며 전체 재작업 범위를 축소한 결정이 아니다.

## 44. 재작업 세대와 같은 요청의 재전달을 별도로 저장한다

generation은 새 판단/결과를 위한 작업 세대이고, 기존 rework_count는 동일 CMMS 요청 재시도에도 쓰인다. 완료 행은 그대로 보존하고 새 UUID/supersedes_id와 불변 요청 receipt를 같은 인스턴스 거래에 저장한다. 같은 UUID의 같은 내용은 접수 당시 결과를 반환하며 상태변경/다른내용은 다시 검토한다. 중간 작업의 입력은 무조건 최초seed가 아니라 유효한 선행 생산자의 출력으로 재구성한다. 해당 예제가 원래2·측정7·검토9라면 검토 재실행의 입력은7이다. 외부 효과/승인을 확인하지 않은 Incident에는 이 전이를 그대로 적용하지 않는다. A038의 보류 범위는 후속 구현 대상이며 전체 목표의 축소가 아니다.


## 45. 판단 원문은 생산 작업·세대와 실제 claim에 연결한다

## 57. 센서 원천의 메타데이터와 생성 SQL을 같은 조회 계약에 연결한다 — A051

## 58. PromQL은 실제 지표와 레이블을 확인한 뒤 원천에서 실행한다 — A052

## 59. 미확인 진단 근거를 거짓으로 바꾸거나 대안을 탈락시키지 않는다 — A053

## 60. 입력이 없던 시간을 CEP 조건 유지 시간으로 계산하지 않는다 — A054

## 61. 시간조건 입력은 매초 관측하고 팬 해제는 정한 히스테리시스를 따른다 — A055

## 62. 감지 정의는 TESTS이며 활성 경보는 발생 당시 정의와 ID를 유지한다 — A056/A057

## 63. 부족한 진단은 완료하지 않고 내구적으로 보류하며 새 평가를 요청한다 — A058/A059

## 64. 경로 종료와 전체 종결을 분리하고 새 생산 결과와 흐름 도달을 모두 기다린다 — A062/A063
