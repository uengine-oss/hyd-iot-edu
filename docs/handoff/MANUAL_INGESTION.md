# A026 문서 원천·검토·적재 계약

2026-10-04 A050. 원문·사람 검토·원자적 적재·개정·되돌리기에 추출 프로세스 요청/결과·서버 작업 이력을 연결했다. 실제 Codex 일반문서 추출은 아직 미검증이다. 아래 A026 기록은 과거 범위이며 최신 작업 계약은 다음 절을 따른다.

## 추출 작업 요청과 결과 검토 (A050)

보관 원문을 다시 검토하거나 업로드한 뒤 「에이전트 추출 요청」을 누른다. 같은 원문 판본을 고정한 `manual_source_extraction@1.0` 인스턴스의 businessRuleTask를 기존 cliagents Codex 워커가 맡도록 등록한다. 접수만으로 완료를 표시하지 않는다. 워커가 없으면 IN_PROGRESS로 대기한다. 결과는 「이 문서의 추출 작업」에서 선택하고 「추출 진행·결과 확인」으로 읽는다. 이력은 서버 PG에서 페이지 조회하므로 브라우저 저장소를 잃어도 결과가 남는다. 응답 미확인 요청의 UUID는 sessionStorage에 보존하여 접수를 재확인한다. 접수된 뒤 요청 버튼을 다시 누르면 별도의 새 추출 작업을 만든다.

API: `POST /api/kg/manuals/sources/{source_id}/extractions`는 `request_id` UUID를 받는다. 동일 원문/UUID는 같은 인스턴스를 반환한다. `GET .../extractions?limit=50&offset=0`은 해당 원문/tenant의 실행 이력, `GET .../extractions/{instance_id}`는 상태와 완료 제안을 반환한다. 페이지 원문은 시작 변수에 고정한다. 고정 폼의 인용 계약을 엔진이 완료 전에 검증하며, 다른 원문·잘못된 좌표/인용·누락된 페이지 검토 기록은 완료하지 않는다. 페이지별 검토 note가 있다는 사실은 의미 정확성의 증명이 아니다.

추출 결과에 reviewed/by를 넣어도 사람 승인이 되지 않는다. 결과에서 이름·단계·SOP 번호·고장 유형/관계를 사람이 검토한 뒤 기존 commit을 수행한다. 에이전트 제안 적재 시 서버는 생산 인스턴스/작업/세대/세션을 다시 확인하여 원장에 저장한다. 가짜 세션을 만들지 않으며 실제 세션이 없으면 null이다. 단계 원문과 에이전트 제안 원문은 작업 출력에, 최종 검토 내용은 배치 plan에 남는다. 관련 SOP가 없으면 빈 제안을 검토 결과로 반환할 수 있으며 적재는 비활성이다.

검증: 전체728, 실제 계약13 + 포털 생성 작업/PG 이력5, 별도 실제 그래프2단계/원문 관계 조회·되돌림. 모든 A050 proposal은 가짜 CLI 또는 검사기의 명시 합성 출력이다. 포털의 대기/결과 확인·인용/검토 폼은 직접 확인했고 최종 적재/되돌림은 HTTP로 확인했다. 실제 일반문서 Codex 추출·PDF/OCR/표 정확성은 완료로 세지 않는다. 근거는 HANDOFF §9 A050.

## 근거와 현재 결함

회의2 253~285행은 전문가가 정한 스키마에 회사 DDL/SOP를 인스턴스로 넣고 그 과정을 가르치라고 한다. 새 문서마다 온톨로지 클래스를 임의 생성하는 요구가 아니다. ontology-studio 6a229be8의 agent_session/service.py 71~237행은 기존 target_schema, 구조/의미/레코드 추출, 적재 후 실제 질문 검증을 연결한다. document_indexing은 원문 해시·페이지·chunk_ref를 남긴다. batch_ingest의 문자열 절단/노드별 부분 성공까지 HYD의 승인된 적재 계약으로 채택하지 않는다.

이전 HYD는 전역 절 ref를 ID로 쓰며 모든 절을 ks:manual-hm에 연결했다. 잘못된 SOP 검증 전에 절을 저장하고 원문/PDF 페이지/영속 업로드 이력을 보존하지 않았다. 반례는 `manual-ingest-observation.json`이며 순수 함수/가짜 IO 관찰이다. 현재 API는 이 구현을 `manual_api.py`/`manual_review.py`/`manual_graph.py`로 교체했다. 일반 Skill 편집 API의 별도 소유권 충돌은 그래프 비교로 탐지하며 그 API 전체를 원자적으로 재작성한 것은 아니다.

## 원천 계약

- 논리 문서는 UUID, 판본은 원본 바이트 SHA256으로 구분한다. 파일명은 표시 정보이며 식별자가 아니다. 다른 문서의 같은 절 번호를 합치지 않는다. 기존 문서의 개정은 그 문서 ID를 명시해야 한다.
- 원본 바이트와 추출 결과를 같은 SQLite 트랜잭션에 영속 보존한다. 원문 보관 성공과 Neo4j 적재 성공은 별도 상태다. 그래프 적재 실패가 원문 증거를 지우면 안 된다.
- 추출 페이지와 전체 텍스트를 절단하지 않는다. 인용은 판본/페이지/문자 시작·끝/정확한 원문 문자열을 포함하고 저장된 추출 결과와 대조한다. PDF 추출 좌표는 추출 텍스트 좌표이며 화면의 바운딩 박스가 아니다.
- 텍스트 디코딩 실패를 replacement 문자로 감추지 않는다. PDF에서 텍스트가 없는 페이지는 OCR 필요 상태로 표시한다. 일부 페이지가 읽혔다고 문서 전체 추출 완료로 판정하지 않는다. OCR/표 읽기 정확도는 별도 검수 대상이다.
- 같은 판본의 재요청은 기존 원본/추출 결과를 반환한다. 추출기 버전과 해시는 저장하며, 추출기 변경으로 과거 인용 좌표를 몰래 바꾸지 않는다.

## 추출 결과는 작업 폴더의 파일로 받는다 (A119, r14 B1)

ontology-studio는 에이전트가 `/workspace/output/_parsed_*.json`을 쓰고 서버가 `batch_ingest(경로)`로 읽는다. HYD는 결과를 마지막 메시지 JSON으로 받아 출력 토큰 상한(A092 160 KB) 때문에 40,000자 구간 분할(A093)이 필요했고, GPU 모델은 긴 JSON 닫힘을 놓쳤다(A073 2/2). 적대 판정(결과·효율·안정성·범용성)은 studio 방식이 낫다고 보았다.

- **워커(`worker/outcome.py`·`runner.py`·`workspace.py`)**: 실행이 끝나면 작업 폴더의 `output/result.json`이 있는지 본다. 있으면 그 파일이 결과다(크기 상한 `MAX_RESULT_FILE_BYTES` 기본 16 MB → 초과·UTF-8 아님·JSON 아님·객체 아님은 형식 교정 사유로 같은 세션에 돌려보냄, 메시지로 대체하지 않음). 없으면 지금처럼 마지막 메시지의 JSON을 받는다(하위 호환, 네 에이전트 작업은 그대로). 경로는 고정 상대 경로라 작업 폴더 밖을 가리킬 수 없고, 새 실행 시작 때 이전 시도의 파일을 지운다. `task_completed` 이벤트에 `result_source: file|message`. 지시문은 두 방법 중 하나로 제출하라고 적고(`prompt.output_contract`·CONSTITUTION), 형식 교정 프롬프트는 파일을 고쳐 쓰라고 말한다.
- **추출 정의 1.8(`manual_extraction.INSTRUCTION`)**: `{"proposal": …}`를 `output/result.json`에 쓰고 마지막 메시지는 "결과 파일 작성 완료: 절 n, 절차 m" 한 줄. 서버 계약(`validate_proposal`: source_id 일치·앵커·페이지 검토)은 파일 내용에 그대로 적용된다 — 틀린 source_id는 FB_REQUESTED 교정.
- **구간 기준(`manual_segments.DEFAULT_MAX_CHARS`) 40,000 → 80,000자**: 출력 상한이 사라졌으므로 제약은 입력 컨텍스트와 실행 제한 시간이다. 구간 텍스트는 에이전트 컨텍스트에 두 번(입력으로 읽고, 인용 JSON으로 다시 써서) 들어가고 한 실행은 1,800초 안에 끝나야 한다. 실측 상한은 단일 작업 82,795자·1,180초(A092)라 80,000은 그 아래에서 시간 여유 약 35 %를 두고, CJK 비관치 1토큰/자로도 2×80 K + 설명 10 K가 200 K 컨텍스트 안이다. 분할·병합 코드는 그대로이며 EHU40(126,168자)은 4구간 → 2구간, HM-FULL(82,795자)은 1 → 2구간이 된다.
- **검증**: 단위 신규 5(파일 우선·깨진 JSON·배열·필드 누락·크기 초과·파일 없을 때 메시지 폴백 / 러너가 파일을 읽고 이전 시도 파일을 지움 / 깨진 파일 → 교정 왕복 → 제출 / 추출: 파일 제안·틀린 source_id 교정 뒤 DONE / 기본 구간 80,000·EHU40형 80쪽 → 2구간), 전체 **1,198 passed**(`.evidence/a119/pytest-full.log`). 사용자 지시(10-07)로 "수정을 빼면 실패" 되돌림 확인은 생략.
- **라이브 재측정(`.evidence/a119/ehu40-1/`, 2026-10-07 22:37:55~22:48:08, process 1.8 재빌드·호스트 워커 Claude Code opus 1개)**: 실제 다이킨 EHU40 80쪽 PDF(126,168자) → **구간 2(이전 4)·612초(10.2분, 이전 1.6 실측 902초=15.0분)·교정 0(이전 0)·검사 10/10(이전 10/10)**, 절 52(이전 56)·절차 28(이전 37)·단계 113(이전 140)·경고 36, 커버리지 0.125. 두 구간 모두 `output/result.json`(70,733 B·65,656 B)으로 제출했고 `task_completed.result_source = file`, 마지막 메시지는 "결과 파일 작성 완료: 절 n, 절차 m" 한 줄. 절차 수가 준 것은 6~9장(수령 점검·운반 설치·배관·배선)을 이번 실행이 SOP로 삼지 않은 범위 차이이며(아래 재현성 절), 13장 정비 절차는 전부 같다.

### EHU40 두 번 추출의 재현성 — B4(구조는 코드, 절차는 LLM) 결정 (A119, r14 B4)

사용자 지시(10-07)로 새 실행은 1회만 하고, 기존 실측 2회(`a094-ingest-real-ehu40` 정의 1.4/1.5, `-2` 정의 1.6)와 비교했다. 비교 스크립트 `.evidence/a119/compare_runs.py` → `compare.json`·`compare.md`. SOP는 id의 숫자 절 경로(`SOP-EHU40-13-5-1`·`SOP-13-5-1` → 13.5.1)로 맞춘다.

| 쌍 | 절 집합 Jaccard | SOP 집합 Jaccard(공통/각) | 공통 SOP 단계 수 일치 | 단계 텍스트 유사도(정규화 평균) | 단계 인용 위치 동일 | 순서 뒤집힘 |
|---|---|---|---|---|---|---|
| 1.6 ↔ 1.8(이번) | 0.793 (46/53·51) | **0.711 (27/37·28)** | **27/27** | **0.901** | 45/106 (42 %) | 1 (13.3 정기 점검표 13단계, 유사도 0.414) |
| 1.4 ↔ 1.6 | 0.881 | 0.558 (24/30·37) | 19/24 | 0.268 | 49/93 | 0 |

1.4↔1.6은 지시문 변경(번역 금지·소절별 절차)이 섞여 재현성 척도가 아니다(텍스트 유사도 0.268은 한국어 번역 때문). 1.6↔1.8은 출력 경로만 다르므로 재현성 척도로 쓴다. 공통 27개 SOP는 단계 수가 전부 같고 13.5~13.10 정비 절차는 텍스트 유사도 0.79~1.0이다. **흔들리는 지점:** ① 범위 — 1.6은 6~9장(수령 점검 6.1·6.2, 운반·설치 7.x, 배관 8.1, 배선 9·9.5.3)을 SOP 9개로 냈고 이번은 내지 않았다(13.8 안전밸브는 이름만 달라 같은 절차). "설치·배선 지시가 정비 SOP인가"는 계약이 정하지 않은 경계다. ② 인용 범위 — 같은 단계의 인용 문자열 선택이 달라 위치 동일률 42 %(서버가 위치를 찾으므로 전부 유효한 인용이며 내용 손실 아님). ③ 13.3 정기 점검표(표를 13단계로 펼치는 방식)만 텍스트가 갈린다.

**판정: B4는 하지 않는다.** 수업에 쓰는 대상(13장 정비 절차·단계·순서)은 두 번 모두 같은 SOP 집합·같은 단계 수·뒤집힘 없음으로 나왔고, 흔들림은 "어느 장을 SOP로 볼지"와 "인용 문자열을 어디서 끊을지"다. 둘 다 코드 파서가 고칠 성질이 아니고(정규식 파서는 절차 8/37, r14-g4 실험) 지시문 한 줄(범위: 6~9장 설치·배선 지시를 포함할지)과 검토 화면의 문제다. 범위를 고정하고 싶으면 정의에 "SOP로 삼을 장"을 명시하는 것이 다음 행동이다(사용자 결정).

## 추출 제안과 검토

- (A117, r14 B2) 앵커는 page + quote만 필수. 서버(`procsvc/manual_locate.py`)가 정확 일치 → 글자·숫자만 비교 → 낱말 사이 끼어듦 허용 순으로 위치를 찾아 start/end를 채우고, 여러 곳이면 "더 긴 인용" 교정을 요청한다. 에이전트가 보낸 좌표가 맞으면 그대로 둔다. 실물 EHU40 앵커 리플레이 265/267·231/233(`.evidence/a117/replay_locate.json`).

원문 업로드 → 실제 에이전트가 고정 스키마와 원문 좌표를 읽고 추출 제안 → 사람이 이름/단계/고장 유형/관계를 검토 → 전체 검증 → 하나의 Neo4j 트랜잭션으로 적재 → 실제 조회로 연결 확인 순서다. 기존 정규식은 명시된 구조의 빠른 추출 보조로만 남길 수 있다. 일반 문서를 이해하는 에이전트 실행으로 설명하지 않는다.

새 SOP를 FailureMode에 연결하는 것과 실행 후보에 활성화하는 것은 별도 결정이다. 현재 후보는 DMN Rule OUTPUTS 관계를 따른다. 적재 후 후보가 되게 하려고 규칙을 자동으로 고치지 않는다. 화면/교재는 적재와 후보 활성화 상태를 구별해야 한다.

## 적재·개정·되돌리기 (배포한 계약)

문서/판본별 KnowledgeSource·ManualSection, Skill/Step의 원문 인용을 저장한다. 문서 소유 노드/인접 관계 전체를 before/after JSON으로 같은 Neo4j 거래에 기록한다. 개정은 현재 head와 preview.previous_batch가 같아야 한다. 문서의 기존 속성·유형·관계가 기록과 달라지면 수정/되돌리기를 거절한다. 외부 Rule OUTPUTS나 실행 참조를 삭제하지 않는다. 전체 교체는 소유 관계를 명시 삭제한 뒤 노드를 삭제하며 DETACH DELETE를 쓰지 않는다.

SOP 번호는 Skill.sopId 유일 제약으로 한 스킬에만 귀속된다. 다른 원천/기존 시드가 가진 번호는 덮어쓰지 않는다. UI에서 담당자가 등록 번호를 명시 변경할 수 있고 원문 인용은 그대로 남긴다. 과거 legacy 적재를 새 원문의 소유물로 추정해 자동 인수하지 않는다. 참조 중인 SOP를 별도 판본으로 병행 유지하는 제품 수준 이행은 후속이며, 과거 판단 참조를 지우는 것으로 갈등을 해결하지 않는다.

되돌리기는 해당 문서의 최신 배치부터 진행한다(DDL A004의 임의 중간배치 제거와 다름). 이전 그래프와 head를 함께 복원하고 배치를 ROLLED_BACK으로 남긴다. 원본 SQLite와 검토/배치 기록은 보존한다. 이전 판본 이력은 SUPERSEDED, 현재만 ACTIVE로 반환한다. 같은 배치 재전송은 같은 내용/원래 접수 결과이며 개정을 다시 적용하지 않는다. 동시 요청은 공용 적재 잠금과 노드 잠금으로 직렬화한다. 감사 Kafka와의 원자적 outbox는 범위 밖이다.

원문은 process-data의 manuals.sqlite3에 남고 원본/전체페이지/페이지별인용/보관목록/재검토 API로 접근한다. 목록은50건 기본/최대100건, total/next_offset을 반환한다. 파일명이 같아도 별도 문서이며 개정에는 document_id를 명시한다. 검토 담당자와 reviewed=true가 없으면 commit400이다. 서버 tenant 경계의 보관소이며 제품 로그인/다중tenant 그래프 격리 전체 구현으로 설명하지 않는다.
