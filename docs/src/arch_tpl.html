처음 보는 분을 위한 3분 이야기

공장에는 기름을 높은 압력으로 밀어 기계를 움직이는 유압 설비가 세 대 있습니다. 이 시스템의 목적은 하나입니다. 설비가 이상해지면 빨리 알아채고, 원인을 짚고, 사람의 승인을 받아 안전하게 조치하고, 정말 나아졌는지 확인한 뒤 기록을 남기는 것입니다.

  1. 설비가 값을 낸다. 설비 옆의 작은 제어기(PLC)와 수집 장치가 1초마다 온도·압력·진동 값을 꺼내 공장 안 게시판({n:emqx})에 붙입니다. 이 프로젝트에서는 진짜 기계 대신 {nn:sim}이 물리 계산으로 흉내 냅니다.MQTT 토픽 plant/hyd01/tag/TS1 등 · {c:c_sim_pub}
  2. 공장 안에서 먼저 쓴다. 운전실 화면({n:fuxa})이 같은 게시판을 보고 값과 알람을 띄웁니다. 사무실 쪽이 통째로 멈춰도 화면·수동 조작·자동 정지(트립)는 공장 안에서 그대로 돕니다.
  3. 경계를 넘는다. 공장과 사무실은 직접 연결하지 않고 문 두 개로만 오갑니다. 올라가는 문({n:ing})은 값을 읽어 사무실 장부에 옮기기만 하고, 내려가는 문({n:gw})은 검사를 통과한 명령과 경보 표시만 공장에 씁니다.
  4. 장부에 남기고 나눠 쓴다. 사무실 장부({n:rp})는 들어온 순서대로 번호를 붙여 보관합니다. 검사관({n:det})이 이상을 찾고, 심부름꾼({n:sink})이 기록 DB({n:tsdb})에 옮기고, {nn:graf}가 추세를 그립니다.
  5. AI가 조사한다. 이상 경보가 나면 AI({n:agent} 조사관, 또는 instance 모드의 {n:worker} AI 직원)가 지식 지도({n:neo})에서 원인 후보와 조치 방법을 찾고, 기록 DB에서 증거를 확인하고, 회사 업무 데이터({n:ent})까지 따져 조치 카드를 씁니다. AI는 설비에 직접 명령할 수 없습니다.
  6. 사람이 고른다. 담당자가 포털({n:portal})에서 근거를 읽고 카드 하나를 승인합니다. 업무 진행({n:proc})이 승인 내용을 다시 확인한 뒤에야 명령을 만듭니다.
  7. 두 번 검사하고 실행한다. 명령은 내려가는 문에서 한 번(검사 1), 설비 옆 PLC에서 또 한 번(검사 2) 검사를 받고 나서야 팬 속도나 부하를 바꿉니다. 명령에는 120초 만료가 붙어 늦게 도착한 옛 명령은 버려집니다.
  8. 정말 나아졌는지 본다. 명령이 들어갔다고 끝내지 않습니다. 정해진 시간 동안 지켜보며 경보가 풀리고 값이 기준 안으로 돌아왔는지 확인한 뒤, 정비 작업지시를 내고 사건을 닫습니다.

3-1. 한눈에 보기: 무엇이 무엇과 이어지나

먼저 큰 길만 봅니다. 상자에는 번호 · 이름 · 제품만 적었습니다. 위(설비)에서 아래(사람)로 읽고, 가운데 세로줄(척추)을 따라가면 됩니다: 설비 → 공장 게시판 → 두 문 → 장부 → AI → 업무 진행 → 업무 기록부. 파란 값은 아래로, 빨간 명령은 위로, 보라 경보는 공장 화면과 AI 쪽으로 갑니다.

이 그림과 3-2 상세 그림은 같은 번호(부품 ①~㉖)를 씁니다. 연결 번호(C)는 3-2와 본문 {sec:lines}절 기준이고, 이 그림에도 같은 번호로 붙어 있습니다.

3-2. 컨테이너 배치도: 상자 안까지 전부

3-1과 비슷한 배치에 상자를 넓혀, 상자마다 안쪽 구성(토픽 · 검사 조건 · 표 · 처리 순서 · 도구 · 포트 · 계정)을 모두 적었습니다. 좁은 화면에서는 그림을 옆으로 밀어 봅니다. 상자 안 내용을 쉬운 말로 풀어 쓴 설명은 {sec:parts}절 부품 카드에 있습니다.

기술 레이어 구조도: 층마다 구성요소, 화살표마다 프로토콜

설계서 v2의 「그림 1」과 같은 방식으로 그렸습니다. 띠 하나가 층 하나(위 L9 사람 · 업무 → 아래 L1 설비)이고, 띠 왼쪽에 층 이름과 핵심 기능, 오른쪽에 그 층의 구성요소 {{NLC}}개를 카드로 따로 놓았습니다. 카드는 컨테이너가 아니라 하는 일 단위입니다. 예를 들어 plant-sim 컨테이너 하나 안의 열 모델 · soft-PLC · 고장 램프 · DAQ 필터 · 엣지는 각자 카드입니다. 카드 아래 회색 꼬리표가 실제로 그 일을 하는 컨테이너 · 포트입니다. 화살표 {{NLA}}개에는 번호와 프로토콜 · 토픽 · 표 이름을 붙였고, 같은 번호로 {sec:lyrtext}절의 글과 화살표 표에 전부 풀어 썼습니다.

층별 설명: 그림을 위에서 아래로 읽기

앞 그림의 띠 아홉 개를 하나씩 풉니다. 쉬운 말 칸은 그 층이 무슨 일을 하는지 이야기로, 기술 세부 칸은 제품 · 버전 · 포트 · 토픽 · 보관 · 검사 조건입니다. 글 속 동그라미 숫자(4 같은)는 그림의 화살표 번호이고, 누르면 아래 화살표 표의 그 줄로 갑니다. 화살표 {{NLA}}개가 모두 어느 한 문장에 나옵니다.

화살표 {{NLA}}개 전부

「L3 → L2」처럼 층이 바뀌는 화살표는 층 표시를 붙였습니다. 종류 색은 그림과 같습니다.

레이어별 기술 표

층마다 무엇을 맡고 무엇은 맡지 않는지, 실제로 돌아가는 기술과 원래 설계(설계서 v3의 실제 제품)가 어떻게 다른지를 한 줄씩 적었습니다. 「하지 않는 일」 칸은 책임을 다른 층에 넘기는 경계입니다.

레이어 간 시퀀스: 쿨러 열화 한 건의 처음부터 끝까지

세로줄은 층, 가로 화살표 하나가 한 단계입니다(왼쪽 번호 순서대로). 같은 층 안의 일은 그 세로줄 위의 상자로 그렸습니다. 기본 운영 방식(legacy) 기준이고, instance 모드에서 달라지는 점은 {sec:s6}절에 있습니다. 화살표 색은 기술 레이어 구조도와 같습니다.

구역 사이의 규칙과 잠금 현황

원칙
  1. 공장과 사무실을 직접 잇지 않는다. 두 망을 오가는 것은 {n:ing}(올라가는 문)과 {n:gw}(내려가는 문) 둘뿐입니다. compose 망 설정상 다른 컨테이너는 상대 망에 붙지 못합니다.
  2. 올라가는 문은 쓰지 않는다. {n:ing}의 코드에는 공장 게시판에 발행하는 부분이 없습니다({c:c_ing_sub}는 구독만).
  3. 내려가는 문은 두 가지만 쓴다. {n:gw}는 검사를 통과한 자동 명령({c:c_gw_auto})과 경보 표시({c:c_gw_disp})만 씁니다.
  4. AI는 명령 필드를 만들 수 없다. 카드에 명령 번호·토픽·만료 같은 필드가 있으면 가드레일이 거부합니다. 명령은 사람이 승인한 뒤 {n:proc}가 만듭니다.
  5. 설비 옆이 마지막 판단을 한다. PLC는 누가 보냈든 모드·만료·중복·범위·트립을 다시 보고, 인터록(65 ℃ 등)은 네트워크와 상관없이 설비 옆에서 혼자 겁니다.
숨기지 않고 적는 것: 이 원칙을 「무엇으로」 지키나

실제 공장은 위 원칙을 방화벽 장비, 계정별 권한(ACL), 암호화(TLS)로 강제합니다. 이 시스템은 학생 노트북에서 가볍게 돌리려고 상당 부분을 프로그램 규칙으로만 지킵니다. 그래서 아래 표의 「없음」은 그 칸의 원칙이 코드가 지켜 주는 동안에만 지켜진다는 뜻입니다.

두 가지 운영 방식: legacy와 instance

같은 부품으로 두 방식이 돕니다. 차이는 「경보 한 건을 누가 끌고 가나」입니다. 스위치는 .env의 PROCESS_MODE입니다.

legacy (저장소 기본값)

  1. 경보가 {n:agent}를 깨운다({c:c_ag_alert}).
  2. agent가 정해진 순서(신선도 → 원인 → 증거 → 스킬 → 카드 → 가드레일)로 계산해 카드를 {n:proc}에 낸다.
  3. process가 사건으로 받아 사람 승인을 기다리고, 승인되면 명령 → ACK → 재관측 → 작업지시 → 종결.

판단은 LLM 없이 계산. LLM은 요약 문장만. Supabase · cliagents 없이 compose 하나로 돈다.

instance (ProcessGPT 방식, 현재 개발 PC 설정)

  1. 경보 하나가 프로세스 인스턴스 하나를 연다({n:proc}가 정의 anomaly_response_v22.json으로, 기록은 {n:supa}).
  2. 인스턴스 안의 Task가 차례로 생긴다: 진단 → 후보 → 규정 확인 → 순위(AI) → 선택(사람) → 명령 → 재관측 → 작업지시.
  3. AI Task는 {n:worker}가 집어 Claude Code로 수행하고, MCP 창구({n:dmnmcp} {n:entmcp} {n:kgmcp})로만 데이터를 본다. 워커가 없으면 AGENT_BRIDGE=legacy일 때 {n:agent}의 계산으로 대신 채운다({c:c_proc_ag}).
  4. 사람 Task(카드 선택)는 10분 넘게 비면 상향 보고로 간다.

Supabase(supabase start) 필요. 컨테이너 워커는 cliagents 프로필과 ANTHROPIC_API_KEY, 호스트 워커는 로그인한 Claude Code와 scripts/run_worker_host.sh.

이 개발 PC의 현재 설정 (.env, 키 값 제외)

PROCESS_MODE=instance · AGENT_BRIDGE=legacy · PROCESS_REPO=pg · ENTERPRISE_BACKEND=supabase · COMPOSE_PROFILES에 cliagents 없음(워커는 컨테이너가 아닌 방식으로 돌리거나 legacy 다리로 채움) · TIME_SCALE=20 · DAQ_PROFILE=lite. 저장소 기본값(.env.example)은 PROCESS_MODE=legacy, ENTERPRISE_BACKEND 미지정(memory)입니다.

비유와 그 한계

legacy는 「조사관 한 명이 보고서를 써서 결재 서류함에 넣는」 방식, instance는 「사건마다 결재 서류철을 새로 만들고 칸마다 담당(AI 직원 · 운전원 · 시스템)을 정해 차례로 채우는」 방식입니다. 한계: instance에서도 AI 직원은 사람처럼 아무 시스템이나 열 수 없습니다. 허락된 창구(MCP 도구)만 쓰고, 결정 계산 자체는 판단 엔진이 합니다.

일곱 가지 흐름

번호 순서대로 따라가면 됩니다. 각 단계 밑의 작은 글씨가 기술 세부입니다.

흐름 1 · 계측: 기름 온도 한 값이 기록되기까지

  1. {nn:sim}이 1초마다(설비 시간 20초) 열의 저울을 계산합니다. 정상이면 쿨러 입구 온도 TS1이 약 48 ℃입니다.thermal.py · TIME_SCALE=20 · lite 프로필에서 TS1 · CE · PS1 · FS1 · VS1 · LoadSP 매초
  2. 값을 공장 게시판 칸 plant/hyd01/tag/TS1에 붙입니다({c:c_sim_pub}). 받았는지 확인하지 않고 한 번 던집니다.QoS 0 · 페이로드 {t, v, q:"good"}
  3. {nn:fuxa}가 같은 칸을 구독해 화면에 띄웁니다({c:c_fuxa}). 60 ℃면 「높음」, 65 ℃면 「인터록」 알람.
  4. {nn:ing}가 같은 값을 구독해({c:c_ing_sub}) 장부 plant.tag에 설비 열쇠 hyd01로 적습니다({c:c_ing_pub}).대기열 2만 건 · 넘치면 버리고 셈
  5. {nn:det}가 장부에서 읽어 기울기·이상 점수를 계산하고 feat.1s에 적습니다({c:c_det}).
  6. {nn:sink}가 장부를 읽어({c:c_sink_sub}) {nn:tsdb}의 tag_1s · feat_1s 표에 옮깁니다({c:c_sink_db}). 1분 요약 tag_1m이 자동으로 만들어집니다.
  7. {nn:graf}가 기록 DB를 읽어({c:c_graf}) 추세를 그립니다. 포털 「실시간 모니터링」이 이 화면을 끼워 보여 줍니다.

흐름 2 · 경보: 이상을 찾아 화면과 AI에 알리기까지

  1. 쿨러 핀에 먼지가 낍니다(강의에서는 포털 「결함 시뮬레이션」이 {n:sim}의 /api/fault를 불러 냉각 능력을 43 %로 서서히 낮춥니다, {c:c_browser}).
  2. {nn:det}가 Neo4j에서 읽어 둔 정의({c:c_det_neo})대로 「TS1 > 55 ℃ 그리고 냉각 효율 CE < 70 % 그리고 TS1이 오르는 중」이 60 설비초 이어지는지 봅니다.IDLE → CANDIDATE → RAISED · 20배속이면 현실 약 3초
  3. 이어지면 쿨러 열화 경보 RAISE를 장부 alerts에 적습니다. 해제(TS1 < 52 ℃이고 더 오르지 않음 60초)면 CLEAR를 같은 경보 ID로 적습니다.alertId ALT-hyd01-0001-xxxx · evidence에 정의 판본(sha256) · 값 · 관측 나이
  4. {nn:gw}가 경보를 읽어({c:c_gw_alert}) 공장 게시판 plant/hyd01/alert에 붙이고({c:c_gw_disp}), {n:fuxa}의 「IT 경보」 표시등이 켜집니다.
  5. {nn:sink}가 경보 표를 채웁니다. {nn:proc}도 경보를 읽습니다({c:c_proc_rp}): legacy에서는 사건이 경보가 아니라 {n:agent}의 카드로 열리고(흐름 3), process는 경보의 해제(CLEAR)를 재관측 판정에 씁니다. instance에서는 RAISE 하나가 곧바로 인스턴스 하나를 엽니다(흐름 6). legacy면 {nn:agent}가 같은 경보로 깨어납니다({c:c_ag_alert}).
  6. 아무도 조치하지 않으면 기름이 계속 데워져 65 ℃에서 PLC가 펌프를 세웁니다(트립). 검사관은 OVERHEAT_TRIP 경보를 바로 냅니다. 55 ℃ 아래로 식은 뒤에만 리셋할 수 있습니다.

흐름 3 · AI 조사: 원인을 짚고 조치 카드를 쓰기까지 (legacy)

  1. 대응할 경보인가. {n:agent}가 {n:proc}에 경보 정책을 묻습니다({c:c_ag_proc}).
  2. 데이터가 신선한가. 최신 TS1이 60초 넘게 묵었거나 수집 다리가 멈췄으면({c:c_ag_ing}) 판단을 보류합니다. 낡은 값으로 판단하지 않기 위해서입니다.
  3. 원인 후보. 지식 지도에서 「쿨러 열화 → 냉각 손실 → 원인: 쿨러 핀 오염(사전확률 0.6) · 주변 고온(0.2)」을 찾습니다({c:c_ag_neo}).
  4. 증거 확인. 원인마다 지도에 적힌 증거 질문(예: 「CE 30초 평균 < 70」, 「TS4 ≥ 35 ℃」)을 기록 DB에 읽기 전용으로 던집니다({c:c_ag_tsdb}). 결과는 통과 · 실패 · 모름. 근거가 모자라면 보류합니다.
  5. 조치 방법. 1순위 원인의 고장 유형에 연결된 SOP 스킬(예: 팬 최대 SOP-COOL-01)과 단계, 매뉴얼 절을 붙입니다.
  6. 요약과 검사. LLM 키가 있으면 요약 세 문장만 맡기고({c:c_ag_llm}), 가드레일이 명령 필드·근거 누락·범위 밖 값을 검사한 뒤 카드를 제출합니다.
  7. 조치 카드 순위. 승인 대기가 되면 규칙(선택 · 제외 · 감점 · 경고), 예측, BSC 득실, 선례, 업무 데이터({c:c_ag_ent})로 카드 2~3장의 순위를 매겨 제출합니다. 이 계산에는 LLM을 쓰지 않습니다.

흐름 4 · 승인과 실행: 사람의 결정이 설비에 닿고 확인되기까지

  1. 담당자가 {nn:portal}에서 카드와 근거를 읽고 카드 하나를 고릅니다. 팬·부하 값은 카드 범위 안에서만 바꿀 수 있습니다({c:c_browser} → {n:proc} /decide).
  2. {nn:proc}가 고른 카드가 그 사건의 카드인지, 값이 범위 안인지 다시 확인하고 명령을 action.cmd에 적습니다. 120초 만료가 붙습니다({c:c_proc_rp}).
  3. 검사 1 · 게이트웨이. {nn:gw}가 읽어({c:c_gw_cmd}) 스키마 · 허용 목록 · 만료 · 중복 · 모드(REMOTE_AUTO인가)와 초당 2건을 봅니다. 통과면 cmd/auto에 붙이고({c:c_gw_auto}), 통과든 거부든 감사 기록을 남깁니다.
  4. 검사 2 · PLC. {n:sim}이 받아({c:c_sim_sub}) 출처·모드 · 만료 · 중복 · 범위 · 트립을 다시 보고 팬과 부하를 바꿉니다. 결과(DONE/REJECTED와 이유)는 status에 실려 흐름 1의 길로 올라갑니다.
  5. {n:proc}가 ACK를 30초 안에 받아야 합니다. 못 받거나 거부면 사람에게 넘깁니다(ESCALATED). 명령을 다시 보내지 않습니다.
  6. 재관측. 900 설비초(20배속이면 45초) 동안 지켜보며 경보 CLEAR와 회복 기준(쿨러면 TS1 < 55 ℃)을 함께 확인합니다({c:c_proc_tsdb}). 값은 돌아왔는데 CLEAR가 늦으면 최대 3번 연장합니다.
  7. 회복되면 {nn:ent}에 CMMS 작업지시(쿨러 청소)를 실행하고({c:c_proc_ent}) 실제 번호를 받아야 사건을 닫습니다. 사례는 지식 지도에도 기록됩니다({c:c_proc_neo}).
일이 틀어지면
  • 운전원이 손으로 조작 중이면: PLC가 REMOTE_MANUAL이라 게이트웨이가 「MODE」로 거부하고, ACK가 오지 않아 사건이 사람에게 넘어갑니다.
  • 명령이 늦게 도착하면: 120초가 지난 명령은 게이트웨이와 PLC가 모두 버립니다. 옛 조치가 뒤늦게 실행되지 않게 하는 안전장치입니다.
  • 승인 전에 저절로 나으면: 조치 없이 해결(RESOLVED_WITHOUT_ACTION)로 닫습니다.
  • process가 명령 도중 재시작되면: 명령을 자동으로 다시 보내지 않고 확인 대상으로 올립니다.

흐름 5 · 운전원 직접 조작: 화면 버튼이 기계를 움직이기까지

  1. 운전원이 {nn:fuxa}에서 팬 값을 80으로 바꿉니다({c:c_oper}).
  2. FUXA가 plant/hyd01/cmd/manual에 {"FanSpeedSP": 80}을 붙입니다({c:c_fuxa}).
  3. {n:sim}의 PLC가 명령 ID를 붙이고 모드(LOCAL이면 거부)·범위·트립을 본 뒤 실행합니다. REMOTE_AUTO였다면 REMOTE_MANUAL로 바뀌어, 그 뒤로 오는 AI 쪽 자동 명령은 거부됩니다. 사람의 손이 언제나 AI보다 우선합니다.
  4. 결과와 새 값이 흐름 1의 길로 화면에 돌아옵니다. 이 흐름은 사무실 쪽을 전혀 거치지 않습니다.

흐름 6 · instance 모드: 경보 한 건 = 인스턴스 하나, Task 단위로

  1. 경보 RAISE가 Supabase 수신함을 거쳐 {nn:proc}에 들어오고, 정의 anomaly_response_v22의 인스턴스가 열립니다({c:c_proc_supa}).
  2. 진단 · 후보 · 규정 확인 · 순위 Task가 AI 몫(cliagents)으로 todolist에 쌓입니다.
  3. {nn:worker}가 3초마다 일을 찾아 집고(120초 임대, 30초마다 갱신) Claude Code를 실행합니다({c:c_wk_supa} {c:c_wk_llm}). Claude Code는 허락된 창구만 씁니다: 판단 엔진({c:c_wk_dmn}), 기업 DB({c:c_wk_ent}), 지식 지도 읽기({c:c_kgmcp_neo}).
  4. 결과가 Task 양식에 맞는지 검사하고(틀리면 두 번까지 고쳐 달라고 함) 저장합니다. 질문이 필요하면 멈추고 사람의 답을 기다립니다. 워커가 죽으면 임대가 끝난 뒤 다른 워커가 이어받습니다.
  5. 「선택」 Task는 사람 몫입니다. 운전원이 포털 「프로세스 인스턴스」에서 카드를 고릅니다. 10분 넘게 비면 상향 보고 Task로 갑니다.
  6. 이후 명령 · 재관측 · 작업지시는 흐름 4와 같은 길(검사 1 · 2 포함)로 갑니다. 기업 실행은 Supabase ent 스키마에 기록됩니다({c:c_ent_supa}).

  2. 「에이전트 추출 요청」을 누르면 추출 인스턴스(manual_source_extraction)가 열리고, AI 직원(cliagents 워커, {n:worker})이 고정 스키마와 원문 좌표를 읽어 스킬·단계·고장 유형 제안을 만듭니다. 제안의 모든 인용은 판본 · 쪽 · 글자 위치 · 원문 문자열로 검증됩니다.
  3. 사람이 이름 · 단계 · SOP 번호 · 연결할 고장 유형을 검토해 확정해야 적재됩니다. AI가 「검토함」이라고 써도 승인이 되지 않습니다.
  4. 한 번의 Neo4j 트랜잭션으로 적재하고 전후 상태를 기록합니다({c:c_proc_neo}). 최신 배치부터 되돌릴 수 있습니다. 새 SOP를 고장 유형에 잇는 것과 실제 조치 후보로 켜는 것(규칙)은 별개의 결정입니다.

코드에서 확인한 한계와 결함 가능성 (2026-10-07)

결함 가능성 · 실행 미확인

빈 DB에서 탐지 정의가 비는 문제. {n:seed}는 constraints · instances · knowledge_a098 세 파일만 넣고, 검사관이 읽는 detectionMode='held'와 해제 식(clearRule)은 detector-patterns.cypher에만 있습니다(이 파일은 scripts/ontology_v2.py만 넣음). 그래서 Neo4j 볼륨을 지우고 compose만으로 처음 띄우면 {n:det}의 패턴 카탈로그가 0개가 되어 /healthz가 503이 될 것으로 보입니다. 코드를 읽어 추론한 것이며 빈 DB 기동은 실행해 보지 않았습니다. 기존 볼륨에는 이미 들어 있어 지금 돌아가는 환경에는 영향이 없을 수 있습니다.

  • {n:emqx}에 계정·ACL이 없습니다. 게시판에 붙을 수 있으면 cmd/auto에 쓸 수 있습니다(PLC 검사는 여전히 거침).
  • {n:fuxa}의 이미지 태그가 latest입니다. 화면 생성기는 FUXA 1.3을 가정하므로 새 판에서 달라질 수 있습니다. FUXA에는 상태 확인(healthcheck)이 없습니다.
  • FUXA의 IT 경보 문구는 「쿨러 성능 저하」로 고정돼 있어 펌프 누설·팬 진동 경보에도 같은 문구가 보입니다.
  • {n:ing}의 /healthz는 항상 200이고, 버린 건수는 Prometheus 지표로 나가지 않습니다.
  • {n:sim}의 「로컬 패널」 API(/api/manual)는 출처를 FUXA로 처리해 LOCAL 모드에서는 거부됩니다. FUXA는 mode 토픽으로 LOCAL을 원격 해제할 수 있습니다.
  • status는 매초 보내지만 수집 계약 표는 PLC 상태 보고 주기를 10초로 적고 있습니다(신선도 한도 계산에 쓰임).
  • 게이트웨이 통과 기록의 검사 이름은 EXPIRY, 거부 기록은 EXPIRED로 다릅니다.
  • {n:dmnmcp}의 설명 주석은 도구 8개를 적지만 실제 도구는 14개입니다. ALLOWED_TOOLS 기본값이 compose와 워커 설정 파일에서 다릅니다(설정 파일에만 Bash(python *)).
  • {n:det}의 이상 점수는 학습 모델이 아니라 고정 기준의 z-점수 계산입니다. cep.py의 옛 고정 임계값 함수는 호출되지 않는 코드입니다(정본은 그래프의 TESTS).
  • APOC 플러그인은 켜져 있지만 저장소 코드에서 호출하는 곳은 없습니다.
  • {n:agent}의 실행 트레이스는 메모리에만 있어 재시작하면 사라집니다(제출된 카드는 process에 남음).

용어집

유압 설비
기름을 높은 압력으로 밀어 기계를 움직이는 장치. 펌프 · 밸브 · 쿨러 · 탱크로 이루어진다.
PLC
설비 바로 옆의 작은 제어 컴퓨터. 위험하면 네트워크와 상관없이 스스로 멈춘다(인터록 · 트립).
OT / IT
OT는 기계를 움직이는 공장 쪽 기술, IT는 기록 · 분석 · 업무를 하는 사무실 쪽 기술.
DMZ
공장과 사무실 사이의 완충 지대. 다리가 아니라 다리 가운데의 검문소에 가깝다. 이 시스템에서는 두 망에 붙은 서비스 둘로 흉내 낸다.
MQTT · 브로커
장치들이 게시판(브로커)에 쪽지를 붙이고 구독한 쪽이 바로 받는 가벼운 통신 방식. 전달하는 곳이지 보관하는 곳이 아니다.
토픽
게시판(또는 장부)의 칸 이름. 예: plant/hyd01/tag/TS1.
QoS 0 / 1 · retain
QoS 0은 한 번 던지고 확인 안 함, QoS 1은 받았는지 확인함. retain은 칸마다 마지막 한 장을 붙여 두어 나중에 온 쪽도 지금 상태를 바로 알게 함.
Kafka · Redpanda
번호를 붙여 디스크에 쌓는 장부. 여러 쪽이 각자 읽고, 설비별 순서가 지켜지고, 오래 남는다. Redpanda는 Kafka와 같은 방식으로 쓰는 가벼운 제품.
CEP
복합 이벤트 처리. 「온도 높음 + 효율 낮음 + 오르는 중이 60초」처럼 여러 조건이 시간 동안 함께 일어나는지 보는 방식.
시계열 DB
시간 순서로 쌓이는 값을 잘 저장 · 요약하는 DB. 여기서는 TimescaleDB.
온톨로지
무엇이 무엇과 어떤 관계인지 적은 지식 지도. 여기서는 설비 · 고장 · 원인 · 조치 · 규칙 · 업무 지표가 이어져 있다.
SOP · 스킬
표준 작업 절차. 이 시스템에서 「조치 방법 = 스킬 = SOP」는 같은 것을 가리킨다.
BSC · BPMN · DMN
BSC는 성과 지표 체계(관점 · 목표 · 지표), BPMN은 업무 흐름도 표준, DMN은 결정 규칙 표준.
HITL
Human-in-the-loop. 사람이 고리 안에 있어 승인해야 실행된다는 뜻.
가드레일
AI가 낸 결과가 넘으면 안 되는 선(명령 필드 금지 · 근거 필수 · 범위 안 값)을 기계적으로 검사하는 장치.
LLM
글을 읽고 쓰는 대형 언어 모델(예: GPT, Claude).
MCP
AI가 외부 도구 · 데이터를 정해진 방식으로 부르게 하는 연결 규격. 여기서는 AI 직원이 쓰는 「창구」.
프로세스 인스턴스 · Task
업무 정의(서식)로 만든 실제 업무 한 건이 인스턴스, 그 안의 개별 작업이 Task. Task마다 맡는 쪽(AI · 사람 · 시스템)이 정해져 있다.
ACK · 재관측
ACK는 설비가 명령을 받았다는 응답. 재관측은 명령 뒤 실제로 나아졌는지 다시 보는 것.
outbox · 임대(lease)
outbox는 보낼 것을 먼저 적어 두고 보낸 뒤 지우는 방식(잃어버리지 않기 위해). 임대는 일을 집은 쪽이 일정 시간마다 「아직 하는 중」을 갱신하고, 끊기면 다른 쪽이 가져가는 방식.
compose 프로필
여러 컨테이너를 묶어 한꺼번에 켜고 끄는 단위.
