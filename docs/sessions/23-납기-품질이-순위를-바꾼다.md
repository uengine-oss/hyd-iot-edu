# 23. 납기 · 품질이 순위를 바꾼다 (5부, 180분: 설명 50 / 실습 100 / 정리 30)

## 이번에 할 것 / 끝나면 보이는 것
설비만 보면 틀리는 판단을 본다. 업무 DB의 납기(MES) · 보상(ERP) · 고온 로트(QMS) · 공급사(SCM) 값을 바꾸면 같은 경보의 카드 순위가 달라진다. 값이 바뀌면 옛 승인은 거절된다.
끝나면 "값 바꾸기 전/후 카드 순위" 비교표 1장과 승인 거절 1건이 남는다.

## 준비
- 업무 DB는 Supabase `ent` 스키마(`ENTERPRISE_BACKEND=supabase`). Supabase Studio http://127.0.0.1:54323 → 스키마 `ent` → 테이블 `production_orders`(MES 생산오더, 납기 `due_in_h`) · `sales_contracts`(ERP 계약·보상) · `quality_profiles`·`lot_dispositions`(QMS) · `suppliers`(SCM, `avl`) · `fg_inventory`(완제품 재고) — 정의는 `it/supabase/migrations/20261003000002_enterprise.sql`, 납기 시각 기준 열은 `20261007000017_enterprise_time_anchors.sql`.
- 포털 **조치 판단 규칙** 탭(설비 · 이상 패턴 · 사실값 덮어쓰기 · 판단 실행), **업무 프로세스** 탭(기업 시스템 현황 · 시스템 실행 이력).
- 순위 식의 납기·품질 항: `it/agent/agentsvc/cards.py` 280~286행. 공급사 동기화 `POST /api/kg/scm/sync`. 업무 시각 기준 `docs/enterprise-catalog.md`.

## 실행 장면
1. [화면] 조치 판단 규칙 → HYD-01 / COOLER_DEGRADATION → 판단 실행 → [확인] 카드 순위와 각 카드의 순위 식 항(납기 · 품질 포함)을 "전" 열에 적는다.
2. [화면] Studio → `ent.production_orders`에서 HYD-01 주문의 납기를 30시간 뒤로(시각 기준 열 `due_at`이 있으면 그 열, 없으면 `due_in_h`) → 다시 판단 실행 → [관찰] 납기 항(`scoreParts.delivery`)이 0이 된다(순위 식: 남은 시간이 24 h 이상이면 납기 항 0, `GET /api/kg/ranking-policy/rule:rank-value`) → 반대로 납기 2 h · 지연 보상 500만원/h로 바꾸면 생산을 유지하는 카드에 +, 감산 카드에 작은 +, 정지 카드에 −가 붙어 순위가 바뀐다 → [확인] "후" 열. (DB 대신 같은 비교를 터미널로: `POST 127.0.0.1:8091/api/agent/decide`의 `facts`에 `{"order_due_h": 30}` 또는 `{"order_due_h": 2, "order_penalty_per_h": 500}` — 화면의 "사실값 덮어쓰기"와 같은 경로.)
3. [화면] `ent.quality_profiles`에서 해당 설비 행의 고온 로트 값(`auto_qty` 수량 · `auto_claim` 클레임 비용, 일반 로트는 `gen_*`; `lot_dispositions`는 비어 있다)을 바꾼다. 순위 정책의 품질 항은 `-1.5 * min(1, claim / 1000)`이라 claim이 1000 이상이면 -1.5에서 멈춘다 — 지금 HYD-01 claim 3000을 더 올려도 변화가 없으니 1000 미만(예 500)으로 내리거나 수량을 0으로 바꿔 비교한다 → 판단 실행 → [확인] 품질 항이 음수인 카드에 경고가 붙는다(`cards.py` 286행 `risky`). 품질 항은 **그 카드의 예측 유온이 55 ℃ 이상일 때만** 음수가 된다(순위 정책 `quality` 식) — 설비가 정상이면 로트 값을 아무리 바꿔도 0이므로 **쿨러 경보가 열려 있는 동안** 실행한다.
4. [화면] 펌프 경보(HYD-02)로 같은 실험(**실제 누설 근거가 없으면 판단이 "근거 없음 — 보류"로 끝나므로 20회차처럼 누설을 주입한 상태에서**): `ent.suppliers`에서 sup:b의 `avl=false` → `curl -X POST 127.0.0.1:8080/api/kg/scm/sync` → 판단 실행 → [관찰] "펌프 축 씰 교체"(SOP-PMP-04, 핵심 부품 구매가 들어가는 카드)가 `rule:avl`("핵심 부품은 승인 공급사에서만 구매")로 제외 → `avl=true` 복원 → 동기화 → 카드 복귀 → [확인] 제외/복귀 2건.
5. [화면] 실제 승인에서의 효과: 경보 실행 중에 카드를 받은 뒤(내 할일에 선택 작업이 열린 상태) MES 납기를 바꾸고 옛 카드를 선택 → [관찰] 선택이 거절되고(HTTP 400) "현재 조건에서 승인을 보류합니다: 업무 판단 입력 order_due_h가 변경됐거나 확인되지 않습니다; 순위 판단 입력 order_due_h가 변경됐습니다. 새 판단을 검토하세요" → [확인] 거절 1건(사유에 바뀐 입력 이름). 역할은 그 카드의 승인 역할로 고른다(아니면 납기 검사 전에 403). 20배속에서 선택 작업은 30초 안에 끝나므로 납기 변경 → 선택을 바로 이어서 하고, 납기는 곧바로 원래 값으로 돌린다.
6. [정리] 바꾼 DB 값을 전부 원래대로. **커리큘럼의 "전사 판단 세 가지(복구 방식 vs 납기 · 부품 구매 · 로트 처분) 실행"은 v1 온톨로지의 별도 시나리오(sc:…)였고 현재 v2에는 없다 — 패턴별 카드 순위와 공급사 제외로 대체.**

## 막혔을 때
- 값을 바꿔도 순위가 같다: 해당 입력이 순위 정책에 연결돼 있는지(`docs/ranking-policy.md` "현재 정책 조회·변경"), 시각 기준이 `due_at`인지(`probe_time_anchors.py`: 납기 시각은 고정, 남은 시간이 흐름).
- Studio에서 ent 테이블이 안 보임: 스키마 선택을 `public`에서 `ent`로.
- 승인 거절이 아니라 통과: 바뀐 값이 그 카드의 입력이 아니다. `approval-check` 사유 확인(`POST /api/agent/approval-check`).
