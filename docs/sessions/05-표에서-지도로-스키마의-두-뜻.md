# 5. 표에서 지도로, 스키마의 두 뜻 (2부, 180분: 설명 70 / 실습 80 / 정리 30)

## 이번에 할 것 / 끝나면 보이는 것
시계열 표에는 숫자만 있고 "왜"가 없다. 지식 그래프(Neo4j)에서 설비 구조와 "경보 → 증상 → 고장 유형 → 원인" 경로를 걷고, DB 스키마와 온톨로지 스키마가 어떻게 다른지 표로 적는다.
끝나면 원인 후보 4개가 나온 질의 결과와 "두 스키마 차이" 표 1장이 남는다.

## 준비
- Neo4j Browser http://127.0.0.1:7474 (Connect URL `neo4j://127.0.0.1:7687`, neo4j / hydpass123).
- 파일: `it/neo4j/v2/schema.json`(온톨로지 스키마 원본), `it/neo4j/v2/queries.cypher`(정답 질의 예시), `it/timescaledb/init.sql`(DB 스키마).
- 포털 **온톨로지 지식 지도** 탭(설비 HYD-01, "이상 패턴 경로" 선택).

## 실행 장면
1. [화면] Neo4j Browser → `CALL db.schema.visualization()` → [관찰] 클래스(노드 라벨)와 관계가 그림으로 → [확인] 라벨 수를 센다(`schema.json`의 클래스 수와 비교).
2. [화면] `MATCH (a:Asset {id:'HYD-01'})-[:HAS_COMPONENT]->(c)-[r:MONITORED_BY|ACTUATED_BY]->(x) RETURN a,c,x` → [관찰] 부품·센서·구동기 → [확인] `docs/hyd01-status-lookup.md` L7 행의 "부품 5 · 센서 17"과 같은지.
3. [화면] `queries.cypher`의 `q2-diagnosis-path`를 붙여 넣고 `:param symptom => 'sym:ts1-rise'` → [관찰] 고장 유형·원인(prior)·증거·조치 방법(SOP)·매뉴얼이 한 표로 → [확인] 원인 후보 행 수를 세고(쿨러는 4개가 기준, `scenario-walkthrough.md` 2절 카드 설명), prior 순으로 정렬돼 있는지.
4. [명령] `.venv314/Scripts/python.exe scripts/ontology_v2.py queries --only q2-diagnosis-path` → [관찰] 같은 질의를 터미널에서 실행한 결과 → [확인] 3단계와 같은 행.
5. [화면] 포털 **온톨로지 지식 지도** → 이상 패턴 경로 `COOLER_DEGRADATION` → [관찰] 증상 → 고장 유형 → 원인 · 증거 → 조치 방법(SOP) → 규칙 · 성과 지표 경로가 강조 → [확인] 3단계 결과의 id와 화면 노드 id가 같다.
6. [파일] `init.sql`의 `tag_1s`와 `schema.json`의 `Sensor`/`InputData` 정의를 나란히 → [확인] 표 1장: 열 이름/타입(값을 담는 스키마) vs 클래스/관계/속성(뜻과 연결을 담는 스키마), 각각 "값은 어디에"·"뜻은 어디에".

## 막혔을 때
- Browser 접속이 안 된다: `docker ps`에 neo4j (healthy)인지, 포트 7474/7687.
- 질의가 0행: kg-seed가 끝났는지 `docker compose logs kg-seed`(멱등, 다시 돌리려면 `docker compose run --rm --no-deps kg-seed`).
- `ontology_v2.py`가 bolt 연결 실패: `--uri bolt://127.0.0.1:7687`를 명시.
