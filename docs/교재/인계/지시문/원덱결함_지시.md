# 통합반 원 덱의 결함 고치기와 조립 덱 다시 만들기

> 자리표시: `<저장소>`는 저장소 루트, `<작업 폴더>`는 저장소 밖의 임시 작업 폴더(본문의 「scratchpad」)다. 이 지시문이 쓰이는 단계는 같은 폴더의 `README.md`에 있다.

HYD 제조 AI 교육과정의 통합반 덱(`docs/교재/통합반/0N일차/통합반_0N일차.md`)은 다른 덱들의 원천이다: 실전반 온라인 2~8일차(`docs/교재/실전반/0N일차/조립.py`), 통합반 오프라인 1~10회차, 실전반 오프라인 1~9회차(`docs/교재/<과정>_오프라인/NN회차/조립.py`)가 통합반 덱에서 장을 제목으로 찾아 가져오고, 손질 목록(원문 문구 → 바뀔 문구)을 적용한다. 조립 작업자들이 통합반 덱에서 발견해 보고한 결함을 원 덱에서 고치고, 그 장을 쓰는 덱을 다시 조립한다. 모든 작업은 Opus로 한다(서브에이전트를 쓰지 않는다).

저장소: `<저장소>`. 먼저 `docs/교재/기준/제작기준.md`(3 · 8절)와 `.claude/skills/lecture-deck/references/덱MD-PPTX형식.md`를 읽는다.

## 지킬 것 (중요)
- **장 제목을 바꾸지 않는다**(조립 스크립트가 제목으로 장을 찾는다). 그림(SVG)과 삽화 스크립트는 건드리지 않는다. 고치는 것은 덱 MD의 문구와 라벨 좌표뿐이다.
- **고치기 전에** 그 문구가 어느 조립 스크립트의 손질 목록에 원문으로 들어 있는지 찾는다(`조립.py` 27개를 문자열로 검색). 들어 있으면 원 덱을 고친 뒤 그 스크립트의 원문 쪽도 같이 고쳐 손질이 계속 걸리게 한다(바뀔 문구 쪽은 뜻이 같게 유지).
- 확신이 서지 않는 항목은 고치지 않고 보고에 적는다. 내용을 새로 쓰거나 장을 더하지 않는다. 고침은 한 항목에 한두 줄이다.
- 도구(`deck2pptx.py`), 스킬 문서, 제작 기준은 고치지 않는다. 커밋 · push는 하지 않는다.

## 고칠 목록 (장 번호는 보고 시점의 것이니 제목과 문구로 찾는다)
화면에 보이는 것(우선):
1. 4일차 「…」 장의 「(판단 규칙으로는 만들지 않았다)」 — 내부 사정 단서. 그 괄호 구절을 뺀다(보고된 자리는 4일차-43).
2. 6일차 「최소 권한 원칙」 표 — 요소 번호가 2부터 시작한다(1번 줄 없음). 번호를 1부터로 바로잡는다(내용을 지어내 더하지 않는다).
3. 6일차 「에이전트 스킬: 이름을 붙여…」 풀이 장 — 「쿨러 과열 경보」. 스킬 원문의 인용이면 그대로 두고, 덱이 쓴 서술이면 「쿨러 성능 저하 경보」로 맞춘다.
4. 6일차 학습목표 둘째 카드 — 「서 / 버」로 낱말 가운데에서 줄이 바뀐다. 문구를 조금 줄이거나 낱말 순서를 바꿔 낱말이 갈리지 않게 한다.
5. 3일차 「전략 목표와 KPI」 — 카드 제목 「KPI (Key Performance / Indicator)」에서 낱말 하나가 떨어진다. 줄바꿈이 자연스럽게 되도록 문구나 칸을 손본다.
6. 1일차 「판단에 쓰이는 정보가 놓인 곳」 — MES 라벨이 「…Execution / System)」으로 끊긴다. 라벨 폭(요소 셋째 칸의 폭 값)을 조금 넓히거나 풀네임을 설명 줄로 내린다.
7. 9일차 「유온 재확인」(실습 설명 장) → 본문 용어 「재관측」으로. 9일차 실습 간지 · 설명의 「반려 종료」 → 「거절 종결」(본문의 끝 이벤트 이름)로. 「쿨러 경보」 줄임말은 그대로 둔다.
8. 10일차 Quiz 3 — 정답 보기의 「설비를 세우는 정비 오더」에서 화면 근거가 없는 「설비를 세우는」을 뺀다(정답이 달라지지 않는지 확인).
9. 10일차 「지식 한 줄이 끝난 업무가 되기까지」 — 낱말 하나만 떨어진 줄과, 식별자 `CMD-1010-0001-01d1`이 줄을 넘는 것. 문구를 줄이거나 칸을 손봐 맞춘다.
10. 11일차 「HITL을 지키는 검사」 — 카드 본문이 한 문장을 세 줄(불릿)로 끊었다. 뜻 단위로 다시 끊는다.
11. 11일차 「스킬이 정한 순서」 장 — 순서(진단 → 조치 평가 → 업무 값 조회 → 제출)가 6일차의 SKILL.md 원문 절차 순서와 다르다는 보고. 6일차의 원문 장과 사실표(`docs/교재/기준/통합반_05-08일차_기술사실표.md`의 SKILL.md 절과 실행 기록 절)를 대조해, 이 장이 「스킬이 정한 순서」라고 부르는 것이 실제로 무엇인지 가린다. 실행 기록의 호출 순서라면 제목은 두고(바꾸지 않는다) 메시지 · 노트가 「실제 실행에서 불린 순서」로 읽히게 문구를 고친다. 판단이 서지 않으면 고치지 않고 보고한다.
노트 · 정의 순서(가벼운 것):
12. 4일차의 「ADDRESSES로 잇는다면」 — ADDRESSES 관계가 1~4일차 어디에서도 풀리지 않는다. 그 자리 노트나 설명 줄에 뜻을 한 구절 붙인다(2일차 스키마 장이나 사실표에서 뜻을 확인. 확인되지 않으면 관계 이름을 뜻으로 풀어 쓴다).
13. 2일차 「자료형」 · 「제약」 장 — 「kind는 세 값 가운데 하나」의 세 값이 그 장 화면에 없다. 세 값을 그 문장에 괄호로 넣는다(2일차의 다른 장이나 사실표에서 확인).
14. 9일차 「프로세스 변수」 — `chosen_skill`의 풀이가 없다. 설명 줄이나 노트에 한 구절.
15. 10일차 — 라벨 「같은 승인 블록」이 정의 장보다 먼저 나오는 자리: 그 장 노트에 한 구절로 뜻을 붙인다.
고치지 않는 것(보고된 것 가운데): 1일차 노트의 「비유 제안: …」(기준이 허용한 노트 문구다), 9일차 「ISO/IEC 19510」, 「쿨러 열화」(원인을 가리키는 말), 3일차의 단계 그림, 정의 장 없는 「사전 검사」, 9일차 「단계」의 정의 순서, 11일차 「인스턴스 데이터」, 코드의 `T_reobs` 등 요소 id.

## 다시 만들기
1. 고친 통합반 일차의 PPTX를 다시 빌드한다: `cd <저장소> && uv run --no-project --with python-pptx --with pymupdf python .claude/skills/lecture-deck/scripts/deck2pptx.py <md> <pptx> --render <scratchpad/원덱결함/이름>`. 화면이 바뀐 장은 렌더를 눈으로 본다(넘침 · 줄바꿈이 실제로 나아졌는지).
2. **조립 스크립트 27개를 모두 다시 돌린다**(실전반 온라인 2~8일차의 `조립.py`, 실전반 1일차는 `docs/교재/실전반/만들기_01일차.py`, 오프라인 19개). 손질 원문이 맞지 않아 멈추는 스크립트는 원문 쪽을 고쳐 통과시킨다. 돌린 뒤 `git diff --stat`으로 덱 MD가 실제로 바뀐 덱만 가려 그 덱의 PPTX만 다시 빌드한다(바뀌지 않은 덱은 빌드하지 않는다. 렌더 없이 빌드만 하면 빠르다 — `--render`를 빼고). 덱 폴더에 `__pycache__` · 렌더를 남기지 않는다.
3. 바뀐 조립 덱 가운데 화면이 바뀐 장 서너 곳을 골라 렌더로 확인한다.

## 보고 (짧게)
항목별로 고친 것(일차 · 장 제목 · 원문 → 바뀐 문구)과 고치지 않은 것(이유), 함께 고친 조립 스크립트의 손질, 다시 빌드한 덱의 목록, 눈으로 본 범위.
