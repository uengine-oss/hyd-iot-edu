## SLIDE 06 — 정의 없이 넣은 데이터 ②: 관계와 값의 형식이 어긋난다
### 화면 내용
- 유형: 비교
- 아이콘: arrows-exchange, hash
- 메시지: 같은 사실이 이름 셋으로 들어가면 조회가 하나만 찾고, 한계가 글자로 들어가면 크기를 비교하지 못한다.
- 요소:
  1. 같은 관계가 어긋난다 | 설비가 구성 요소를 갖는다는 한 가지 사실 / HYD-01 → 오일 쿨러: HAS_PART / 쿨러 팬 → HYD-01: BELONGS_TO / HYD-01 → 구동 모터: CONTAINS / 이름이 셋이고 하나는 방향이 반대이다 | 하나만 찾는다
  2. **값의 형식이 제각각이다** | 유온의 한계: 65 (수, 비교할 수 있다) / 토출 압력의 한계: 「130 bar」 (글자, 크기를 비교할 수 없다) / 팬 진동의 단위: (없음, 값을 해석할 수 없다) | 판정하지 못한다
- 노트: 앞에서 이름이 흩어진 것에 이어 관계와 값도 어긋납니다. 먼저 왼쪽의 세 연결은 모두 설비가 구성 요소를 갖는다는 같은 사실인데, 이름이 셋이고 하나는 방향도 반대여서 어느 한 이름을 따라 찾으면 하나만 나옵니다. 다음으로 오른쪽에서는 한계를 한 곳에는 수로, 다른 곳에는 단위까지 붙인 글자로 넣었습니다. 글자는 크기를 비교할 수 없으므로 한계를 넘었는지 판정하지 못하고, 단위가 빠진 값은 무엇을 뜻하는지 알 수 없습니다.
### 제작 기준
[일반] 서술. 세 관계 이름(HAS_PART · BELONGS_TO · CONTAINS — 모두 스키마에 없는 이름)은 정해 둔 이름이 없을 때 제각각 붙는 경우를 보이려는 가정이다. 구성 요소 이름: 사실표 2.3. [일반] 서술. 세 경우는 가정이며 속성과 값(65, 130 bar)은 사실표 2.3의 실제 값에서 골랐다.

## SLIDE 07 — 온톨로지 스키마: 클래스, 속성, 관계, 제약의 정의

  2. 스키마가 정하는 것 | 클래스의 이름과 의미, 속성의 이름 · 자료형 · 필수 여부, 식별자의 규칙 / 관계의 이름과 방향, 시작 클래스와 끝 클래스, 카디널리티 | 정의의 범위

## SLIDE 08 — 클래스 정의: 속성 목록과 속성 정의의 세 항목
### 화면 내용
- 유형: 코드
- 메시지: 속성 한 줄은 속성명, 자료형, 필수 여부로 이루어지며, 인스턴스의 값은 이 세 가지에 맞아야 한다.
- 코드: { /   "name": "Sensor", /   "label_ko": "센서", /   "description": "계측 채널. 태그 이름이 /                   실시간 데이터와 연결된다.", /   "properties": [ /     {"name": "id",      "type": "string",  "required": true}, /     {"name": "name",    "type": "string",  "required": true}, /     {"name": "tag",     "type": "string",  "required": true}, /     {"name": "unit",    "type": "string"}, /     {"name": "virtual", "type": "boolean"} /   ] / }
- 요소:
  1. properties | 한 줄이 속성 하나이다. 지난 시간에 그림으로 본 다섯 칸이 여기에 적힌다.
  2. 속성명 | "name": "tag"는 칸의 이름이다.
  3. 자료형 | "type": "string"은 칸에 들어갈 값의 종류이다.
  4. **필수 여부** | "required": true는 값이 반드시 있어야 한다는 표시이다.
- 노트: 스키마에 적힌 센서 클래스의 정의입니다. 영문 이름, 한글 이름, 설명 뒤에 속성 목록이 오고, 지난 시간에 본 센서의 다섯 칸이 한 줄씩 적혀 있습니다. 한 줄은 속성의 이름, 자료형, 필수 여부의 순서입니다. tag 한 줄을 읽으면 이름은 tag, 자료형은 글자, 그리고 반드시 있어야 하는 속성입니다. 값의 형식과 필수 여부가 스키마에는 이렇게 적힙니다.

## SLIDE 09 — 자료형: 칸에 들어갈 값의 종류
### 화면 내용
- 유형: 코드
- 메시지: **자료형**은 칸에 들어갈 값의 종류이며, limit이 number로 정해져 있어 잰 값과 크기를 비교한다.
- 코드: "name": "StateVariable", / "properties": [ /   {"name": "id",      "type": "string",   "required": true}, /   {"name": "name",    "type": "string",   "required": true}, /   {"name": "aliases", "type": "string[]"}, /   {"name": "unit",    "type": "string",   "required": true}, /   {"name": "kind",    "type": "enum",     "required": true}, /   {"name": "normal",  "type": "number"}, /   {"name": "limit",   "type": "number"} / ]
- 요소:
  1. string | 글자이다. id, name, unit이 이 자료형이다.
  2. number | 수이다. limit과 normal은 수여서 잰 값과 크기를 비교한다.
  3. string[] | 글자의 목록이다. aliases처럼 값이 여럿일 때 쓴다.
  4. **enum** | 미리 정한 값 가운데 하나만 받는다. kind가 이 자료형이다.
- 노트: 상태 변수 클래스의 속성 목록입니다. 한계와 정상값이 number, 곧 수로 정해져 있습니다. 앞에서 한계를 글자로 넣어 비교하지 못한 문제가 이 한 줄로 막힙니다.

## SLIDE 21 — MATCH와 RETURN: 찾을 모양과 돌려받을 것
### 화면 내용
- 유형: 코드
- 메시지: MATCH에는 찾을 모양을, RETURN에는 돌려받을 것을 적으며, 모양에 맞는 것마다 한 행이 나온다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / "오일 쿨러"   "TS1" / "오일 쿨러"   "CE"
- 요소:
  1. **MATCH** | 찾을 모양을 적는 자리이다. 이름이 오일 쿨러인 구성 요소에서 MONITORED_BY로 이어진 센서를 찾는다.
  2. **RETURN** | 돌려받을 것을 적는 자리이다. c.name, s.tag는 찾은 구성 요소의 이름과 센서의 태그이다.
  3. 결과 | 모양에 맞는 것이 둘이므로 두 행이 나온다.
- 노트: 조회의 첫 낱말은 MATCH입니다. 이 질의는 오일 쿨러를 재는 센서는 무엇인가라는 질문이고, 센서가 몇 개인지는 적지 않았습니다. 모양에 맞는 것을 모두 찾는 것이 MATCH의 동작입니다. MATCH만으로는 아무것도 보이지 않으므로 RETURN에 구성 요소의 이름과 센서의 태그를 달라고 적었습니다. 오일 쿨러는 TS1과 CE 두 채널로 계측되므로 두 행이 나옵니다.
### 제작 기준
확정 실라버스의 「MATCH · WHERE · RETURN을 통한 조회」. 질의는 사실표 2.3의 [실측] 질의에서 구성 요소 → 센서 구간만 남기고 출발점을 오일 쿨러로 바꾼 **줄인 것**이다. [실측] 2026-10-11 읽기 전용(`cypher-shell --access-mode read`)으로 `MATCH (c:Component {name:'오일 쿨러'})-[:MONITORED_BY]->(s:Sensor) RETURN c.name, s.tag`를 실행한 결과 두 행.

## SLIDE 22 — WHERE: 조건으로 결과를 거른다
### 화면 내용
- 유형: 코드
- 메시지: WHERE에 조건을 적으면 MATCH가 찾은 것 가운데 그 조건에 맞는 것만 남는다.
- 코드: MATCH (s:Sensor)-[:OBSERVES]->(v:StateVariable) / WHERE v.limit IS NOT NULL / RETURN s.tag, v.name, v.limit /  / ── 결과 ── / "PS1"  "토출 압력"   130 / "TS1"  "유온"        65 / "VS1"  "팬 진동"     2.0

  2. IS NOT NULL | 값이 있는 것만 남긴다. 한계가 정해진 상태 변수 셋이 남는다.

- 노트: 찾은 것 가운데 일부만 보고 싶을 때 WHERE를 씁니다. 한계가 정해진 상태 변수만 남겼더니 세 행이 나옵니다.

## SLIDE 23 — CREATE와 MERGE: 새로 만들기와 찾아서 만들기
### 화면 내용
- 유형: 코드
- 메시지: MERGE는 식별자로 먼저 찾아 없을 때만 만들므로 CREATE와 달리 같은 노드를 중복해 만들지 않는다.
- 코드: CREATE (s:Sensor {id: 'sen:ts1', /                   name: '유온 센서', /                   tag: 'TS1'}) /  / MERGE (s:Sensor {id: 'sen:ts1'}) / SET s.name = '유온 센서', /     s.tag  = 'TS1'
- 요소:
  1. **CREATE** | 적은 대로 새로 만든다. 이미 있는지는 보지 않는다. Sensor 레이블이 붙고 속성 셋을 가진 노드 하나가 만들어진다.
  2. **MERGE** | id가 sen:ts1인 센서가 있으면 그 노드를 쓰고, 없으면 만든다.
  3. SET | 찾았거나 만든 노드의 속성에 값을 넣는다.
  4. 식별자로 찾는다 | MERGE의 괄호 안에는 식별자만 적고 나머지 속성은 SET에 적는다.
- 노트: 조회 다음은 만들기이고 표기는 조회와 같습니다. 먼저 위의 CREATE는 괄호 안에 적은 레이블과 속성대로 노드를 만듭니다. 다음으로 아래의 MERGE는 먼저 찾아봅니다. 무엇을 같다고 볼지는 괄호 안에 적은 것으로 정해지므로 그 자리에는 식별자를 적습니다. 이름까지 넣으면 이름을 고쳐 다시 실행했을 때 같은 노드를 찾지 못합니다.
### 제작 기준
확정 실라버스의 「CREATE를 통한 생성」. [일반] CREATE의 동작. [저장소] 속성값은 `sen:ts1`의 실제 값. 저장소에서 CREATE를 쓰는 곳(`manual_graph.py:346`, `skill_graph.py:101`)의 꼴에 실제 값을 넣은 **줄인 것**이며 이 문장은 실행하지 않았다. 확정 실라버스의 「MERGE를 통한 기존 대상 조회 또는 생성」. [저장소] `MERGE (n:Sensor {id: r[0]}) SET n.name = r[1], n.tag = r[2], …`(`instances.cypher:135`)에 실제 값을 넣고 unit · virtual을 뺀 **줄인 것**(「℃」를 코드 칸에 쓸 수 없다). 새 용어: SET.
