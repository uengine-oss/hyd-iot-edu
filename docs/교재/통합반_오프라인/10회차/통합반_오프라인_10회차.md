- 노트: 정기 점검의 시작 조건입니다. 정기 점검은 고장이 난 뒤에 고치는 것이 아니라 운전시간을 기준으로 미리 하는 예방 정비, 영어로 Preventive Maintenance입니다. HYD-02의 점검 주기는 2,000시간이고, 준비할 시간을 두려고 50시간 앞인 1,950시간에 도래 경보가 납니다. 경보 패턴 PM_DUE의 PM이 예방 정비의 약어입니다.
### 화면 구성

### 제작 기준
[저장소 · 실측] 업무 규칙 「마지막 정기 정비 뒤 운전시간 ≥ 주기 - 사전 알림(2,000 - 50 = 1,950 h)」, 시작 값(운전 1,950 h · 주기 2,000 h · 도래까지 50 h): 사실표 5.1.1 표. [일반] 예방 정비(Preventive Maintenance). 한계까지의 여유(250 h)는 싣지 않았다. 새 용어: 예방 정비(PM).

  1. 승인이 빠진 경로 | 설비 명령 앞의 경로에 사람의 승인이 없으면 등록하지 않는다 | 등록 전의 검사
  2. 거절 갈래의 실행 | 승인 조건의 선을 지나지 않고 실행에 닿는 경로가 있으면 등록하지 않는다 | 등록 전의 검사

- 노트: 7회차에 배운 사람의 승인, HITL은 프로세스 그림에서 사용자 작업 하나로 그려집니다. 이 자리가 그림에 있어야 한다는 것은 검사로 지켜집니다. 설비 명령 앞의 경로에 사람의 승인이 없는 프로세스는 등록하기 전의 검사에서 거절됩니다. 거절의 갈래에서 실행에 닿는 경로가 있어도 마찬가지입니다. 실행 중에는 승인하려는 쪽이 그 조치의 승인 역할인지를 검사해, 아니면 거부하고 기록으로 남깁니다.

### 제작 기준

- 문장: 이 처리 건이 닫힌 뒤의 상황으로 옳은 것은?
- 요소:
  1. 처리 건이 끝났으므로 씰 키트의 재고 부족도 해결되었다
  2. 발주는 만들어지지 않았고 재고 보충이 필요한 상태는 그대로 남아 있다
  3. 발주는 나갔지만 입고만 이루어지지 않았다
  4. 승인 지연 타이머가 처리 건을 자동으로 닫았다
- 노트: 처리 건의 기록으로 업무의 상황을 읽는 문항입니다. 처리 건이 닫혔다는 것과 그 업무의 원인이 해결되었다는 것이 같은지를 생각해 보시기 바랍니다.
### 제작 기준
재고 보충의 거절 경우: `E_rejected` · 반려 「발주하지 않았습니다」, 재고 보충 필요 표시는 켜진 채: 사실표 5.1.3 표. 본문의 「거절 경로의 설계」 · 「대기와 완료」 장으로 풀린다.

## SLIDE 51 — Quiz 2. 승인을 생략하자는 의견
### 화면 내용
- 유형: 문답
- 메시지: 정비 계획 에이전트의 제안이 대부분 적절했으므로 승인 작업을 빼고 정비 오더를 바로 등록하자는 의견이 나왔다.
- 문장: 이 의견에 대한 판단으로 옳은 것은?
- 요소:
  1. 제안이 정확하다면 승인 작업을 빼고 에이전트의 제안을 바로 등록한다
  2. 승인 작업을 서비스 작업으로 바꾸어 시스템이 대신 승인하게 한다
  3. 정비 오더는 효과를 내는 작업이므로 설비보전팀장의 승인 뒤에 둔다
  4. 승인 지연 타이머를 중단형으로 바꾸어 기한이 지나면 자동으로 등록한다
- 노트: 누가 무엇을 맡는지, 책임의 경계를 묻는 문항입니다. 에이전트가 맡은 일과 사람이 맡은 일이 무엇이었는지, 그리고 효과를 내는 작업을 어디에 두었는지를 떠올려 보시기 바랍니다.
### 제작 기준
효과를 내는 작업은 승인의 갈림 뒤에 둔다, 에이전트는 제안까지 한다: 사실표 2.2 표 · 5.1.5 표. 본문의 「역할 배분」 · 「타이머의 설계」 · 「AI가 맡은 일과 사람이 맡은 일」 장으로 풀린다.

## SLIDE 52 — Quiz 3. 발주를 직접 내는 도구를 연결하자는 의견
### 화면 내용
- 유형: 문답
- 메시지: 재고 보충을 빨리 끝내려고, 구매 에이전트에게 발주를 직접 등록하는 쓰기 도구를 연결하자는 의견이 나왔다.
- 문장: 이 의견에 대한 판단으로 가장 알맞은 것은?
- 요소:
  1. 발주의 등록은 승인 뒤의 프로세스 작업에 두고 에이전트는 읽기만 한다
  2. 스킬에 「승인 뒤에만 발주한다」고 적어 두면 쓰기 도구를 연결해도 된다
  3. 발주한 뒤에 감사 기록이 남으므로 쓰기 도구를 연결해도 문제가 없다
  4. 발주 수량을 규칙으로 계산하게 하면 사람의 승인은 필요하지 않다
- 노트: 책임의 경계를 묻는 문항입니다. 에이전트의 읽기와 프로세스의 쓰기가 어디에서 나뉘었는지, 스킬에 적은 순서와 엔진이 지키는 순서가 어떻게 달랐는지를 떠올려 보시기 바랍니다.
### 제작 기준
에이전트 도구는 읽기, 업무 시스템에 쓰는 일은 승인 뒤의 시스템 단계: 사실표 2.2 · 5.1.1 표(C: 구매 담당 승인 뒤 ERP 발주). 본문의 「MCP의 읽기와 프로세스의 쓰기」 · 「스킬이 정한 순서와 프로세스 정의가 정한 순서」 장으로 풀린다.
