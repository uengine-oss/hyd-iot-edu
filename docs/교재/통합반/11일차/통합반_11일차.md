## SLIDE 09 — 경보의 패턴에서 원인 후보까지: 그래프로 들어가는 입구
### 화면 내용
- 유형: 관계도
- 메시지: 경보의 pattern 값 COOLER_DEGRADATION이 이상 패턴 노드의 code 속성과 같아서, 경보가 그래프의 출발점이 된다.
- 요소:
  1. **이상 패턴** | 쿨러 성능 저하 | 0,50
  2. 증상 | 유온 상승 | 34,50
  3. 고장 유형 | 쿨러 냉각 / 성능 상실 | 67,50
  4. 원인 | 후보 셋 | 100,50
- 연결: 이상 패턴 > 증상 : DETECTS ; 증상 > 고장 유형 : INDICATES ; 원인 > 고장 유형 : CAUSES
- 노트: 경보 메시지와 지식 그래프는 따로 만들어졌지만 한 곳에서 만납니다. 경보의 pattern 값인 COOLER_DEGRADATION이 그래프의 이상 패턴 노드가 code 속성으로 가진 값과 같습니다. 그래서 diagnose는 이 값으로 출발 노드를 찾고, DETECTS와 INDICATES를 따라 고장 유형에 이른 뒤 CAUSES를 거슬러 원인 후보를 얻습니다. 2일차에 식별자를 여러 저장소가 함께 쓰도록 정한 까닭이 이 자리에 있습니다.
### 화면 구성
노드 넷을 한 줄로. 이상 패턴을 강조한다. CAUSES는 원인에서 고장 유형으로 향한다.
### 제작 기준
[저장소] 이상 패턴 노드 `pattern:cooler-degradation`의 `code: COOLER_DEGRADATION`, 조회문 `MATCH (p:AnomalyPattern {code: $pattern})-[:DETECTS]->(s:Symptom)-[:INDICATES]->(fm:FailureMode)<-[:CAUSES]-(c:Cause)`: 2~4일차 사실표 2.2 인스턴스 표 · 2.7 ②. 관계 이름과 방향은 1 · 2일차 덱과 같다. 대상 이름은 1일차 덱의 표기.

## SLIDE 10 — 스키마가 정한 관계가 조회의 길이 된다
### 화면 내용
- 유형: 코드
- 메시지: 2일차에 정의한 클래스와 관계의 이름이 그대로 조회문에 쓰이며, 스키마에 없는 관계는 에이전트가 따라갈 수 없다.
- 코드: MATCH (p:AnomalyPattern {code: $pattern}) /       -[:DETECTS]->(s:Symptom) /       -[:INDICATES]->(fm:FailureMode) /       <-[:CAUSES]-(c:Cause)
- 요소:
  1. $pattern | 경보의 pattern 값이 / 이 자리에 들어간다.
  2. 클래스와 관계 | 노드의 종류와 관계의 이름, / 방향은 스키마가 정했다.
  3. **돌아오는 것** | 쿨러 핀 오염 같은 / 인스턴스이다.
- 노트: diagnose가 원인 후보를 찾을 때 보내는 조회문입니다. 첫 줄의 $pattern 자리에 경보의 pattern 값이 들어갑니다. AnomalyPattern, Symptom, FailureMode, Cause는 2일차에 정의한 클래스이고, DETECTS, INDICATES, CAUSES는 그때 이름과 방향을 정한 관계입니다. 스키마가 길을 정했고, 그 길을 따라가 돌아오는 것은 쿨러 핀 오염 같은 인스턴스입니다.
### 화면 구성
왼쪽 조회문, 오른쪽 짚을 점 셋.

## SLIDE 80 — Quiz 3. 발주를 직접 내는 도구를 연결하자는 의견

- 메시지: 재고 보충을 빨리 끝내려고, 구매 에이전트에게 발주를 직접 등록하는 쓰기 도구를 연결하자는 의견이 나왔다.
