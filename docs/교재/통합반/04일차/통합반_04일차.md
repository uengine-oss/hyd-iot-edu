## SLIDE 12 — 3단계 지식 후보 추출과 LLM
### 화면 내용
- 유형: 풀이
- 메시지: 정리되지 않은 문장에서 원인과 조건을 가리려면 뜻을 읽어야 하므로 지식 후보의 추출은 LLM이 맡는다.
- 요소:
  1. 지식 후보 | 구조를 가려 둔 원문을 모델이 읽고 원인, 조치, 조건을 정해진 형식으로 뽑은 제안이다. / 검토와 승인을 거치기 전이므로 아직 지식이 아니다. | 3단계의 결과

## SLIDE 14 — 추출 결과 읽기: 식별자, 값, 연결, 근거 절
### 화면 내용
- 유형: 코드
- 메시지: 문장 하나에 섞여 있던 이름, 값, 연결, 근거가 항목으로 나뉘어야 그대로 노드와 속성과 관계가 될 수 있다.
- 코드: # 매뉴얼 HM-8.4의 문장 / 쿨러 핀 오염(먼지 · 유막으로 핀이 막힘)이 가장 흔하다 / (사전 확률 0.6). 관련 부품은 쿨러 코어다. /  / # 구조화 출력: 원인 한 건 / { /   "id": "cause:cooler-fin-fouling", /   "name": "쿨러 핀 오염", /   "aliases": ["핀 오염", "핀 막힘"], /   "prior": 0.6, /   "failure_mode": "fm:cooler-performance-loss", /   "parts": ["part:cooler-core"], /   "section": "HM-8.4" / }
- 요소:
  1. JSON | 이름과 값의 쌍으로 데이터를 적는 형식이다. 중괄호 안이 원인 한 건이다.
  2. **id · name · aliases** | 식별자, 사람이 읽는 이름, 별칭이다. 접두사 cause가 클래스를 드러낸다.

- 노트: 위가 원문이고 아래가 모델이 낸 원인 한 건이며, 이름과 값의 쌍을 중괄호로 묶은 이 형식이 JSON입니다. 먼저 위의 세 줄을 봅니다. 식별자와 이름과 별칭은 2일차에 배운 그대로입니다. 다음으로 prior는 문장에 있던 사전 확률, 곧 매뉴얼이 이 원인을 얼마나 흔하다고 보는지를 적은 값이고 맨 아래의 section은 근거가 된 절입니다. 그 사이의 failure_mode와 parts는 이 원인이 이어질 대상을 식별자로 가리킵니다.
