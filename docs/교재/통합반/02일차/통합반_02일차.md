- 메시지: 온톨로지 스키마의 정의는 Neo4j에서 레이블, 관계 유형, 속성, DB 제약으로 옮겨진다.
- 머리: 온톨로지 스키마 | Neo4j | 예
- 요소:
  1. 클래스 | 노드의 레이블 | :Sensor
  2. 인스턴스 | 노드 | 유온 센서
  3. 속성 | 노드와 관계의 속성 | tag: 'TS1'
  4. 관계 유형 | 관계 유형 | :OBSERVES
  5. 상위 · 하위 클래스 | 한 노드에 레이블 둘 | :Task:FlowNode
  6. 식별자의 고유성 | DB 제약 | id의 유일 제약
- 노트: 두 쪽의 말을 한 줄씩 맞추었습니다. 상속은 한 노드에 레이블을 둘 붙여 나타냅니다. 온톨로지 스키마는 지식이 어떤 모양이어야 하는가를 정한 정의이고, Neo4j의 레이블과 제약은 그 정의를 도구 안에 옮겨 놓은 것입니다.
### 제작 기준
확정 실라버스의 「온톨로지 스키마와 Neo4j의 레이블 · 관계 유형 · DB 제약 조건을 구분」. [저장소] 클래스 이름 = 레이블, `(:Task:FlowNode)`, id 유일 제약: 사실표 2.2 · 2.6. Neo4j가 필수 속성이나 자료형을 검사한다고 쓰지 않았다. 구현 설명(어떤 제약만 걸려 있는가)은 싣지 않는다.

## SLIDE 104 — DB 제약: 저장할 때 데이터베이스가 검사하는 조건
### 화면 내용
- 유형: 풀이
- 메시지: **DB 제약**은 데이터를 저장하는 순간에 데이터베이스가 직접 검사하는 조건이다.
- 요소:
  1. **DB 제약** | 스키마의 제약 가운데 데이터베이스에 걸어 둔 것이다. / 조건에 어긋나는 데이터는 저장되지 않는다. | Constraint
  2. 유일 제약 | 같은 레이블의 노드끼리 어떤 속성의 값이 겹치지 않게 한다. / 예: 센서 노드의 id에 걸면 id가 sen:ts1인 센서를 하나 더 만들 수 없다. | 식별자의 고유성
  3. 스키마와 DB 제약 | 스키마는 무엇이 옳은 데이터인지를 정한다. / DB 제약은 그 조건을 저장하는 순간에 지키게 한다. | 정의와 검사
- 노트: 스키마에서 식별자는 겹치지 않는다고 정했습니다. 이 제약을 Neo4j에 유일 제약으로 걸어 두면, 같은 id의 노드를 또 만들려고 할 때 Neo4j가 저장을 거절합니다. 스키마가 먼저이고 DB는 그것을 담는 그릇입니다.
### 제작 기준
[일반] DB 제약의 정의. [저장소] `CREATE CONSTRAINT … FOR (n:Sensor) REQUIRE n.id IS UNIQUE`: 사실표 2.6 · 2.7 ⑧. 제약을 만드는 문장은 싣지 않는다. 새 용어: DB 제약, 유일 제약.

## SLIDE 105 — Cypher와 Neo4j Browser
### 화면 내용
- 유형: 풀이
- 메시지: Neo4j의 그래프는 **Cypher**라는 질의 언어로 조회하고 만들며, Neo4j Browser가 그 질의를 실행하는 화면이다.
- 요소:
  1. 질의(Query) | 데이터베이스에 보내는 요청 한 건이다. 무엇을 찾을지 또는 무엇을 만들지를 적는다. | 요청
  2. **Cypher** | Neo4j의 질의 언어이다. 찾으려는 노드와 관계의 모양을 글자로 그려서 적는다. | 질의 언어
  3. Neo4j Browser | Neo4j에 딸린 웹 화면이다. Cypher를 입력해 실행하고 결과를 그래프와 표로 본다. | 질의 실행 화면

### 제작 기준
확정 실라버스의 「Neo4j Browser의 역할을 소개」. [일반] 정의. [저장소] Browser는 Neo4j에 딸린 웹 화면이며 포털과 별개: 사실표 2.9. 에이전트의 원인 후보 조회가 Cypher 질의: 사실표 2.7 ②. 접속 주소 · 계정과 화면의 모양은 싣지 않는다. 새 용어: Cypher, 질의, Neo4j Browser.

## SLIDE 110 — MATCH: 찾을 모양을 적는다
### 화면 내용

  2. 이 모양 | 이름이 오일 쿨러인 구성 요소에서 MONITORED_BY로 이어진 센서이다.

## SLIDE 111 — RETURN: 돌려받을 것을 적는다
### 화면 내용

- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / "오일 쿨러"   "TS1" / "오일 쿨러"   "CE"

  3. 결과 | 모양에 맞는 것이 둘이므로 두 행이 나온다.
- 노트: MATCH만으로는 아무것도 보이지 않습니다. RETURN에 구성 요소의 이름과 센서의 태그를 달라고 적었습니다. 오일 쿨러는 TS1과 CE 두 채널로 계측되므로 두 행이 나옵니다.

## SLIDE 120 — MERGE: 있으면 찾고 없으면 만든다
### 화면 내용
- 유형: 코드
- 메시지: MERGE는 같은 것이 이미 있으면 그것을 찾고, 없을 때만 새로 만든다.
- 코드: MERGE (s:Sensor {id: 'sen:ts1'}) / SET s.name = '유온 센서', /     s.tag  = 'TS1'
- 요소:
  1. **MERGE** | id가 sen:ts1인 센서가 있으면 그 노드를 쓰고, 없으면 만든다.
  2. SET | 찾았거나 만든 노드의 속성에 값을 넣는다.
  3. 식별자로 찾는다 | MERGE의 괄호 안에는 식별자만 적고 나머지 속성은 SET에 적는다.
- 노트: MERGE는 먼저 찾아봅니다. 무엇을 같다고 볼지는 괄호 안에 적은 것으로 정해지므로 그 자리에는 식별자를 적습니다. 이름까지 넣으면 이름을 고쳐 다시 실행했을 때 같은 노드를 찾지 못합니다.
### 제작 기준
확정 실라버스의 「MERGE를 통한 기존 대상 조회 또는 생성」. [저장소] `MERGE (n:Sensor {id: r[0]}) SET n.name = r[1], n.tag = r[2], …`(`instances.cypher:135`)에 실제 값을 넣고 unit · virtual을 뺀 **줄인 것**(「℃」를 코드 칸에 쓸 수 없다). 새 용어: SET.

## SLIDE 121 — 같은 문장을 두 번 실행했을 때
### 화면 내용
- 유형: 비교
- 아이콘: copy, circle-check
- 메시지: 같은 문장을 다시 실행하면 CREATE는 같은 노드를 또 만들려 하고, MERGE는 결과가 달라지지 않는다.
- 요소:
  1. CREATE를 두 번 | 같은 센서를 한 번 더 만들려고 한다 / 유일 제약이 있으면 Neo4j가 거절한다 / 없으면 같은 센서가 둘이 된다 | 실행할 때마다 새 기록이 필요한 데이터에
  2. **MERGE를 두 번** | 두 번째에는 이미 있는 노드를 찾는다 / 노드는 하나 그대로이다 / 몇 번을 실행해도 결과가 같다 | 한 번만 있어야 하는 지식에
- 노트: 설비나 센서처럼 한 번만 있어야 하는 지식은 MERGE로 넣습니다. 넣다가 멈추어 처음부터 다시 실행해도 중복이 생기지 않습니다. CREATE는 작업 기록처럼 실행할 때마다 한 건이 새로 생겨야 하는 데이터에 씁니다.
### 제작 기준
[일반] 두 절의 차이. [저장소] 인스턴스 적재는 MERGE로 하며 여러 번 실행해도 같다(`instances.cypher:1-4`), CREATE는 실행마다 새 기록이 필요한 곳에 쓴다: 사실표 2.7 ⑥ · ⑦. 유일 제약: 사실표 2.6.
