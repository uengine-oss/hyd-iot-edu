유압 설비 세 대가 도는 가상 공장에서, 쿨러 · 펌프 · 팬 고장이 났을 때 AI와 사람이 함께 원인을 찾고 조치를 골라 설비를 되살리기까지를 직접 해 보는 과정이다. 먼저 끝난 쿨러 사건 하나를 처음부터 끝까지 보고 직접 한 번 돌려 본 뒤, 그 사건의 일생을 7막으로 나눠 다시 따라간다. 1~2막에서는 공장 · 메시지 통로 · 지식 지도 · 규칙 같은 부품을 하나씩 직접 만져 보며 기본 모델을 이해한다. 3막에서 읽은 처리 건의 흐름도를 지도 삼아 4막부터 칸을 하나씩 파고들고, 뒤에서는 같은 흐름을 다른 고장과 다른 회사 사정으로 다시 돌고 흐름 자체를 새 버전으로 바꿔 본다. 마지막에는 기본 모델에서 부딪힌 한계에서 출발해 데이터 패브릭과 ProcessGPT가 왜 필요한지 설명으로 확장한다. 기술(메시지 통로, 지식 그래프, AI 도구 연결, 업무 흐름 그림 등)은 그 일을 하다 필요해지는 순간에 짧게 다룬다.

**과정 흐름 한 줄**

> 한 바퀴 통째로 보기 → 1막 공장과 길 → 2막 지식 준비 → 3막 사건 발생(흐름 지도 읽기) → 4막 처리(칸별로 파고들기) → 5막 되돌아보기 → 6막 일이 꼬일 때(다른 고장 · 회사 사정 · 내 PC 일꾼) → 7막 흐름 바꾸기 · 펌프로 반복 · 확장

끝나면 수강생은 이렇게 할 수 있다.

1. 설비 경보 하나가 원인 찾기 → 조치 고르기 → 설비 명령 → 회복 확인 → 정비 요청으로 이어지는 한 바퀴를 흐름도의 칸으로 나눠 따라가며, 지금 누구(AI · 사람 · 시스템) 손에 있는지 말하고, 흐름을 새 버전으로 바꾸면 다음 실행부터 바뀐 흐름이 쓰이는 것을 보일 수 있다.
2. 매뉴얼과 회사 데이터 구조를 넣어 우리 공장 지식으로 만들고(인제스천), 그 지식에서 "왜 이 조치인가"의 길을 직접 걸어 설명할 수 있다.
3. AI가 도구 연결로 지식 지도의 구조를 먼저 받고 질의를 만들어 묻는 과정을 직접 해 보고, 내 PC의 AI 일꾼에게 공장 일을 맡겨 AI가 무엇을 읽고 판단했는지 기록으로 확인하며, AI가 묻는 질문에 사람으로서 답할 수 있다.
4. 원인과 1등 조치를 돌리기 전에 예측하고, 납기 · 품질 · 공급사 같은 회사 사정이 판단을 어떻게 뒤집는지 값을 바꿔 보여 줄 수 있다.
5. 틀린 선택(위험한 조작, 경보만 끄는 조치, 권한 없는 승인)이 어느 겹에서 막히는지 보이고, "경보가 꺼진 것"과 "설비가 나은 것"을 데이터로 구별하며, 이미 나간 조치를 다시 할 때 무엇을 확인해야 하는지 말할 수 있다.

  1. 시스템 구성 화면에서 설비 → 메시지 통로 → 기록 DB → 화면으로 이어지는 부품을 손가락으로 따라간다. 부품마다 어떤 오픈소스가 그 일을 하는지 이름표를 붙인다.

### 단원 3. 지식 지도에서 "기름이 뜨겁다 → 왜 → 무엇을 할까 → 회사에 어떤 영향"의 길을 직접 걸어 보기

- 막 · 흐름도의 칸: 2막 · 흐름도 바깥 — "원인 진단" · "조치 후보 조회" 칸이 읽게 될 지식
- 갈래: 지식
- 활동 유형: 돌려 보기 / 만들기 후보: Claude Code로 지도의 구조를 읽고 새 고장 · 원인 · 조치 연결을 넣는 Cypher를 만들어 길 걷기로 확인
- 해 보는 것
  1. 지식 지도에서 "유온 상승 → 고장 유형 → 원인 → 조치 방법" 길을 직접 걷고, 단원 1의 AI 카드에 나온 원인 · 조치와 같은지 비교한다("AI는 원인을 어떻게 알았지?"의 첫 답).
  2. 길 끝의 조치 방법을 조치 방법 화면에서 열어 단계 목록을 읽는다.
  3. 조치 하나가 설비 값을 거쳐 생산량 · 납기 같은 회사 목표 지표에 닿는 사슬을 세 개 찾는다(팬 속도 → 진동, 압력 저하 → 사이클 지연 등).
  4. 센서 기록 표의 구조와 지식 지도의 구조를 나란히 놓고 차이를 적는다. 지도의 구조(어떤 종류의 점과 연결이 있는지)는 8단원에서 AI가 먼저 받아 가는 그것이다.
- 알게 되는 것: 표에는 "값"이, 지도에는 "왜"가 있다. "구조"라는 말이 표에서는 칸 이름, 지도에서는 뜻과 연결이다.
- 쓰는 시나리오: 쿨러(경로), 펌프 · 팬(영향 사슬)
- 이 안에서 자연스럽게 다루는 것: (온톨로지와 DB 스키마의 차이) (그래프 DB와 질의 언어 Cypher) (다섯 층: 설비 · 고장 · 조치 · 지표 · 회사 목표)

### 단원 4. 매뉴얼과 회사 데이터 구조를 넣어 우리 공장 지식으로 만드는 과정을 처음부터 끝까지 해 보기

- 막 · 흐름도의 칸: 2막 · 흐름도 바깥 — 3단원에서 걸은 지식의 출처("이 지식은 누가 넣었지?")
- 갈래: 지식
- 활동 유형: **[직접 만들기]** 확정 — 매뉴얼 · 회사 DB 구조로 지식을 만든다(AI 추출은 Claude Code 일꾼, 4단원은 강사 화면 · 11단원에서 직접)
- 해 보는 것
  1. 지식 관리에서 예시 매뉴얼(쿨러 · 팬 매뉴얼)을 미리보기 → 검토자 입력 → 등록하고, 조치 방법 화면에 새 조치 방법이 생긴 것을 찾는다. 이 순서(넣기 → 미리보기 → 사람 검토 → 등록 → 되돌릴 수 있는 묶음으로 남기기)를 인제스천 과정 그림으로 적는다.
  2. 회사 DB 구조 파일을 넣어 "어느 표의 어느 칸에 값이 있다"는 연결(업무 데이터 연결)을 지도에 만들고, 값 자체는 들어가지 않았음을 질의로 확인한 뒤 되돌린다. 예비 펌프 준비 상태 칸을 골라 15단원의 펌프 판단과 이어 둔다.
  3. 등록한 문서로 "이 문서로 답할 수 있는 질문 / 아직 못 하는 질문" 보고를 본다.
  4. AI 추출(매뉴얼에서 정비 절차를 AI가 뽑기)은 추출 작업이 일로 올라가 내 PC AI 일꾼이 집어 가야 하므로 이 단원에서는 강사 화면으로 본다. 통합반은 11단원에서 일꾼을 켠 뒤 직접 다시 해 본다.
- 알게 되는 것: 지식은 미리 다 넣어 두는 것이 아니라 문서와 회사 DB에서 만들어 들인다. 사람이 검토해야 지식이 된다.
- 쓰는 시나리오: 쿨러 · 팬(매뉴얼 예시), 펌프(예비 펌프 준비 상태 연결)
- 이 안에서 자연스럽게 다루는 것: (인제스천) (DDL과 표 구조) (값 대신 위치만 넣는 이유) (검토 · 되돌리기 배치)
- 대표 화면: [지식 관리](../.evidence/a141/knowledge-1440.png) · [조치 방법](../.evidence/a141/skills-1440.png)(a151 세트에 이 장면이 없어 기존 캡처)
- 필요 시간 근거: 작은 매뉴얼 AI 추출 약 2분 40초, 짧은 시험 매뉴얼 41초, 실제 제조사 매뉴얼 80쪽 15분(AI 일꾼 2개)(**실측**). 구조 파일 미리보기 · 등록 · 되돌리기는 기다림 거의 없음(**예상**).
- 기존 회차 문서: 09

### 단원 5. 매번 같은 답이 나와야 하는 판단은 규칙으로, 일의 순서는 흐름 정의로 정해 둔 곳을 찾아 결과를 미리 맞혀 보기

- 막 · 흐름도의 칸: 2막 · "규정 검토" · "조치 후보 정리" 칸이 쓸 규칙과 순위 식, 그리고 흐름도 자체가 등록된 정의라는 것
- 갈래: 지식
- 활동 유형: 돌려 보기 / 만들기 후보: Claude Code로 규칙 하나(빼라 · 깎아라)를 결정표에 더하고, 그 규칙 조건을 회사 DB 질의로 바꾸기(규칙 → 쿼리)
- 해 보는 것
  1. 조치 판단 규칙 화면에서 지금 값으로 판단을 돌리고 1위 카드와 걸린 규칙, 카드별 점수 항목을 적는다.
  2. "팬 100 % 누적 30시간"을 넣기 전에 어느 규칙이 걸려 어느 카드가 빠지거나 깎일지 예상하고, 실행해 비교한다.
  3. 같은 화면에서 HYD-02 펌프 패턴과 예비 펌프 "가용 / 정비 중"을 바꿔, 어느 조치가 규정상 빠지는지 미리 본다(15단원 예측의 재료).
  4. 관리 메뉴에서 등록된 흐름 정의와 버전 목록을 열어 "일의 순서도 정의로 저장된다"는 것만 확인한다. 직접 등록은 11 · 14단원에서 한다.
  5. (통합반) 규칙 기준값(24시간)을 48로 바꿨다가 되돌린다 — 화면에서 고치는 기능은 없어 그래프 DB 화면에서 한다(15단원에서 "기본 모델의 한계"로 다시 쓴다).
- 알게 되는 것: AI에게 맡길 것과 규칙으로 고정할 것을 나눈다. 규칙은 "빼라 / 깎아라 / 경고하라"를 적은 표이고, 순위를 정하는 식도 데이터다.
- 쓰는 시나리오: 쿨러, 펌프(규정 제외 미리 보기)
- 이 안에서 자연스럽게 다루는 것: (결정표 DMN) (결정론과 확률적 판단의 차이) (질의 템플릿) (흐름 정의와 버전)

### 단원 6. 고장을 넣어 경보가 처리 건을 여는 순간을 잡고, 그 처리 건이 아홉 칸으로 나뉘어 누구 손을 거치는지 흐름도로 읽어 과정의 지도로 삼기

- 막 · 흐름도의 칸: 3막 · 첫 칸 "설비 경보"(시작)에서 흐름도 전체로 — 아홉 칸과 갈림 · 기한(이후 단원의 목차)
- 갈래: 설비·데이터 통로(앞 절반) · 처리 흐름·사람(뒤 절반)
- 활동 유형: 돌려 보기 / 만들기 후보: Claude Code로 감지 조건(켜짐 · 꺼짐 기준) 하나를 더해 새 경보가 처리 건을 여는지 확인
- 해 보는 것
  1. 결함 시뮬레이션에서 세 고장을 차례로 넣고 탐지 단계가 "정상 → 후보 → 경보"로 바뀌는 것과 걸린 시간을 적는다(펌프 · 팬은 경보까지만 보고 결함을 복구한다).
  2. 실시간 모니터링에서 기름 온도 · 이상 점수 · 경보 그래프가 같은 순간에 어떻게 움직이는지 본다.
  3. 펌프 누설 경보 중 부하를 낮춰 경보가 꺼지는데 압력은 그대로인 것을 확인한다(9단원의 "회복됐나?" 칸이 경보가 아니라 값을 보는 이유).
  4. 쿨러 경보를 하나 더 넣고, 이상 확인 · 조치 화면의 경보 한 건이 몇 초 뒤 처리 건 목록의 새 처리 건이 되는 것을 찾는다.
  5. 그 처리 건의 흐름도와 승인과 실행 화면의 업무 흐름(AI · 담당자 · 시스템 줄)을 나란히 열고, 일 목록 9줄을 세어 줄마다 담당(AI · 운전원 · 생산관리자 · 설비 제어 · 처리 시스템 · 정비 시스템)을 적는다. 일 목록이 처음부터 전부 만들어져 있다는 것을 본다.
  6. 아래 "흐름도 칸 ↔ 단원" 표를 받아, 단원 1의 시각표와 네 궁금증을 칸 위에 붙인다. 이 표가 이후 단원의 목차다.
- 알게 되는 것: 경보 조건과 회복 조건이 다르다. 경보 하나가 처리 건 하나를 연다. 주인공은 업무 흐름이고 AI는 그 안의 일 하나다.
- 쓰는 시나리오: 쿨러 · 펌프 · 팬(경보까지만), 가림 맛보기, 쿨러(처리 건)
- 이 안에서 자연스럽게 다루는 것: (켜지는 조건과 꺼지는 조건을 다르게 두는 깜빡임 방지) (업무 흐름 그림 BPMN) (시작 이벤트 → 프로세스 인스턴스 → 일(task)) (할 일 목록 표)

### 단원 8. 내 PC의 Claude Code에 지식 지도를 붙여, 지도의 구조를 먼저 받고 질의를 만들어 묻는 과정을 직접 따라가 보기

- 막 · 흐름도의 칸: 4막 · ① 원인 진단 칸 안 — AI가 지식 지도에 묻는 방식(도구 연결)
- 갈래: 에이전트
- 활동 유형: **[직접 연결해 관찰]** 확정 — 내 Claude Code에 지식 지도 MCP를 붙여 스키마 → Cypher → 진단 · 조치를 관찰
- 해 보는 것
  1. 빈 폴더에 지식 지도 연결 설정 파일(읽기 전용)을 두고 Claude Code를 연다. 연결된 도구 2개(구조 받기 · 읽기 질의)가 보이는지 확인한다.
  2. "펌프 누설(압력 저하)의 원인 후보와 조치 방법은? 먼저 구조를 읽고 질의로 답해."를 묻는다. AI가 지도의 구조를 먼저 받고 → 그 구조에 맞춰 Cypher를 만들어 실행하는 순서와, 만든 Cypher를 복사해 둔다.
  3. 만든 Cypher를 정답 질의와 그래프 DB 화면에서 나란히 돌려 원인 · 조치가 겹치는지, 다르면 무엇이 빠졌는지 적는다. 3단원에서 손으로 걸은 길과도 비교한다.
  4. 지도를 고치는 질의(CREATE)를 시켜 거절되는 것과, 쓰기 도구가 아예 목록에 없는 것을 확인한다. 7단원 기록의 지식 지도 도구 줄이 같은 방식으로 돌았다는 것을 연결한다.
  5. 지식 지도 연결만으로는 "지금 값"을 모른다는 것을 확인하고, 기간계(센서 기록 · 업무 DB) 연결까지 붙여 진단에서 조치까지 이어 묻는 모습은 11단원에서 서버가 일꾼에게 세 연결을 붙여 준 상태로 관찰한다. 수강생 Claude Code에 기간계 연결을 직접 붙이는 절차는 제작자가 돌려 보지 않았다(⑤ 7).
- 알게 되는 것: AI는 지식 지도의 구조(어떤 종류의 점과 연결이 있는지)를 먼저 받고 그에 맞춰 질문을 만든다. 붙여 준 읽기 전용 도구만 쓰고, 답이 맞는지는 호출한 도구와 만든 질의로 판정한다.
- 쓰는 시나리오: 펌프(질문 — 15단원 예측의 재료가 된다)
- 이 안에서 자연스럽게 다루는 것: (MCP — AI에 바깥 데이터를 붙이는 연결 규격) (온톨로지 스키마를 먼저 돌려주는 도구) (질의 언어 Cypher) (읽기 전용 권한)
- 대표 화면: [지식 지도 — 이상 패턴 경로](../.evidence/sessions/05/screen-portal-pattern-path.png)(비교용) — Claude Code 연결 · 도구 호출 장면은 어느 세트에도 없어 별도 촬영 필요

### 단원 11. 내 PC의 AI 일꾼에게 팬 사건을 맡기고, 일꾼이 모르는 것을 사람에게 묻게 해 보기

- 막 · 흐름도의 칸: 6막 · ①~④ AI 네 칸을 내 PC 일꾼이 맡는다 + 칸 안에서 AI가 사람에게 묻기
- 갈래: 에이전트
- 활동 유형: 돌려 보기 / 만들기 후보: Claude Code를 서버가 하위 프로그램으로 불러 일을 집어 가게 하는 연결(일꾼)을 직접 구성하기(회의 L176~188의 "서버 통합")
- 해 보는 것
  1. 내 PC에서 일꾼(Claude Code)을 켜고, 팬 베어링 마모 경보를 넣어 네 칸이 내 PC에서 처리되는 것을 본다. 8단원에서 손으로 붙인 지식 지도 연결을 이번에는 서버가 일꾼에게 붙여 준다.
  2. 앞 칸의 결과가 다음 칸의 입력으로 넘어가는 표를 만든다.
  3. 일꾼이 사람에게 묻는 질문 카드에 답하고, 같은 일이 이어서 끝나는 것을 본다.
  4. 생산관리자로 팬 카드("팬 40 % + 부하 80 %")를 골라 진동이 내려가고 종결되는 것을 보고, 회복 기준표에 팬 줄(진동 1.2 아래)을 채운다.
  5. (통합반) 관리 메뉴에서 수업용 질문 흐름 세 가지(센서 기록 · 회사 DB · 규칙)를 등록 · 실행하고, 어느 도구가 어느 출처를 언제 읽었는지 표로 만든다. 질문 문구를 바꿔 다시 실행한다. 예: 12단원의 함정 전에 "HYD-03 최근 진동 최대값은?", 13단원 전에 "HYD-02 생산오더는 납기까지 몇 시간?". 규칙 질문에서 "데이터 없음"과 "거짓"이 다르게 답해지는지 확인한다.
  6. (통합반) 4단원에서 강사 화면으로 본 매뉴얼 AI 추출을 내 일꾼으로 직접 돌린다.
- 알게 되는 것: 범용 AI를 업무 시스템의 "일꾼"으로 쓰는 구조와 AI가 사람에게 묻는 지점.

### 단원 13. 납기 · 품질 · 공급사 사정이 바뀌면 1등이 뒤집히고, 이미 한 조치는 어떻게 다시 하는지 찾아보기

- 막 · 흐름도의 칸: 6막 · ④ 조치 후보 정리에 들어가는 회사 값 · ⑤ 조치 선택 직전의 재확인 · 끝난 칸의 "다시 수행"과 "이전 조치의 영향"
- 갈래: 시나리오(회사 사정 — 쿨러 · 펌프 다시 보기)
- 활동 유형: 돌려 보기 / 만들기 후보: Claude Code로 점수 식에 회사 지표 항 하나를 더해(순위 정책 데이터) 1등이 바뀌는지 확인
- 해 보는 것
  1. 쿨러 패턴으로 판단을 돌려 카드 순위 "전" 열을 적는다. 회사 DB에서 납기를 30시간 뒤로 미루고 다시 판단해 납기 점수가 0이 되며 순위가 바뀌는 것을 "후" 열에 적는다.
  2. 쿨러 경보가 열려 있는 동안 품질(고온 로트 · 클레임) 값을 바꿔 경고가 붙는 카드를 찾는다.
  3. 펌프 누설 중 공급사 승인을 끄면 "펌프 축 씰 교체"가 빠지고, 다시 켜면 돌아오는 것을 본다.
  4. 카드를 받은 뒤 납기를 바꾸고 옛 카드를 골라 거절 사유(바뀐 입력 이름)를 읽는다. 승인과 실행 화면의 기업 시스템 현황에서 바꾼 값을 확인하고, 바꾼 값은 모두 되돌린다.
  5. (통합반) 계약 손실 · 재고 값만 바꿔 "계획 정지" 카드의 순위가 오르는지 직접 찾아본다(제작자 실측 예: 4위 → 2위).
  6. (통합반) 이미 한 조치를 다시 하기: 쿨러 경보에서 1등이 아닌 카드(예: 팬만 올리는 카드)를 골라 설비 명령이 나간 뒤, 처리 건 상세의 "이전 조치의 영향"(영향 보기)에서 나간 설비 명령이 "자동으로 되돌리지 않음 · 사람 확인 대상"으로 표시되는 것을 본다. 확인 전에는 "다시 수행"이 보류되는 것을 보고, 설비 상태를 확인해 확인 기록을 남긴 뒤 다시 수행한다. 사건이 승인 대기로 다시 열리고 옛 명령은 "다시 수행으로 대체됨" 이력으로 남고, 새 판단 · 새 승인을 거쳐 끝나는 것을 본다. 정비 요청 · 구매요청 같은 회사 거래를 역거래로 되돌리는 것은 설명으로 다룬다.
- 알게 되는 것: 설비 값만 보면 틀리는 판단이 있다. 순위를 정하는 식도 데이터라서 프로그램 수정 없이 바뀐다. 승인은 "그때의 사실"에 묶여 있다. 이미 바깥 세상을 바꾼 조치는 조용히 덮어쓰지 않고, 되돌리거나 사람이 확인한 뒤에 다시 한다.
- 쓰는 시나리오: 쿨러(납기 · 품질 · 다시 수행), 펌프(공급사)
- 이 안에서 자연스럽게 다루는 것: (MES · ERP · QMS · SCM 회사 시스템) (점수 식의 납기 · 품질 항과 상한) (승인 직전 재검사) (재작업 — 새 작업 세대) (효과 보상과 사람 확인 영수증)
- 대표 화면: [승인과 실행 — 기업 시스템 현황](../.evidence/a141/process-1440.png)(기존 캡처) · [조치 판단 카드 — 점수와 순위](../.evidence/a151-capture/05-조치판단카드-추천1등.png) — 다시 수행 · 이전 조치의 영향 장면은 어느 세트에도 없어 별도 촬영 필요
- 필요 시간 근거: 값 바꾸고 다시 판단은 바로(**예상**). 옛 승인 거절 장면은 30초 선택 기한 안에 납기 변경과 선택을 이어서 해야 한다. "이 값이 바뀌면 순위가 뒤집힌다"를 화면이 미리 알려 주지 않으므로 값을 바꿔 보며 찾는 시간이 필요하다. 다시 수행은 제작자가 실제 서비스에서 API 검사로 끝까지 확인했지만(쿨러 → 팬만 카드 → 설비 응답 → 확인 기록 → 사건 재개 → 새 승인 → 두 번째 설비 응답 → 정비 요청 종결, 22/22) 포털 화면으로 수강생이 끝까지 해 본 기록은 없다(⑤ 15).
- 기존 회차 문서: 23 (다시 수행은 회차 문서 없음 — `docs/effect-compensation.md` · `docs/rework-conditions.md`)

  4. 예측표와 실제를 한 줄씩 대조하고, 틀린 곳은 지도 · 규칙 중 어디를 못 봤는지 적는다.
  5. 세 바퀴 비교표(④ 마무리)를 채운다.
  6. 기본 모델의 한계 목록을 만든다: 회사 DB가 한 종류뿐이다(현장은 여러 종류의 DB · ERP를 쓴다), 경보 흐름은 고정 파일이라 바꾸려면 다시 켜야 한다(14단원), 규칙 기준값을 그래프 DB 화면에서 직접 고친다(5단원). 이어서 확장 설명을 듣고 그림 1장을 그린다: 여러 DB를 하나처럼 묻게 하는 데이터 패브릭, 흐름을 자유롭게 바꾸고 규칙을 관리하는 우리 플랫폼 ProcessGPT(수업에서 쓴 처리 건 · 일꾼 · 도구 연결 · 규칙 · 지식 지도 · 화면이 제품의 어느 부품에 해당하는지 대응표 포함), 설비 · 데이터 층을 실제 공장 제품(소프트 PLC · 경보 처리 · 스트림 탐지 · 구역 분리 등)으로 바꾸는 방향. 데이터 패브릭과 설비층 교체는 이번 시스템에는 없고 방향만 정해 보류된 것이다.
  7. 세 바퀴 중 하나를 골라 비교표와 바퀴별 기록지로 5분 발표하고 자가 평가를 한다.
- 알게 되는 것: 지식 지도와 규칙을 읽으면 시스템의 판단을 미리 설명할 수 있다. 판단이 멈추는 것도 설계된 동작이다. 기본 모델의 한계가 데이터 패브릭과 ProcessGPT로 어떻게 이어지는지 말로 설명한다.
- 쓰는 시나리오: 펌프 내부 누설(HYD-02), 발표는 쿨러 · 팬 · 펌프 · 회사 사정 중 하나
- 이 안에서 자연스럽게 다루는 것: (규정 제외 규칙) (증거 창: 최근 2분 평균) (다시 평가 요청과 승인의 차이) (예비 펌프 전환 명령) (데이터 패브릭) (ProcessGPT) (IoT · 설비층 제품 교체의 방향과 보안 구역) (제품과 같은 일 목록 모양)
- 대표 화면: [조치 판단 규칙 — 설비 · 패턴 · 예비 펌프 선택](../.evidence/a141/decision-1440.png) · [결함 시뮬레이션 — HYD-02 카드](../.evidence/a141/scenario-1440.png) · [처리 건 — 흐름 전 단계 완료](../.evidence/a151-capture/13-처리건-흐름도전단계완료_표시-영문목록.png)(펌프 전용 장면은 어느 세트에도 없어 별도 촬영 필요)

## ④ 시나리오별 진행 틀

모든 바퀴는 같은 흐름도(6단원 표의 아홉 칸)를 탄다. 다른 것은 **이번 바퀴에서 얻는 가치**와 수강생이 흐름도 위에 기록하는 것이다. 바퀴는 과정에서 쿨러 → 팬 → 회사 사정 → 펌프 순으로 돈다.

### 쿨러 바퀴 — 흐름도의 칸을 하나씩 열어 "누가, 무엇을 보고, 무엇을 남기나"를 안다

- 목표 가치: 처음 보는 공장에서 경보 하나가 정비 요청으로 끝나기까지 흐름도의 칸마다 무엇이 일어나고 누구 손에 있는지 말할 수 있게 된다.
- 진행 순서: 단원 1(통째로 한 바퀴 · 궁금증) → 2(경보 앞의 길) → 3 · 4 · 5(칸이 읽을 지식 · 규칙 준비) → 6(설비 경보 칸 · 흐름도 = 지도) → 7(①~④ AI 칸) → 8(① 칸 안에서 AI가 지도에 묻는 방식) → 9(⑤~⑨ 사람 · 설비 · 확인 · 정비 칸) → 10(흐름 전체 되짚기). 단원 1의 궁금증 네 개를 6단원에서 칸 위에 붙이고, 칸을 지날 때마다 답을 적는다.
- 수강생이 기록할 것
  - 흐름도 칸별 시각표: 주입 → 설비 경보 → 처리 건 열림 → ①~④ → 카드 → ⑤ 선택 → ⑦ 설비 응답 → 경보 해제 → ⑧ 효과 확인 → ⑨ 정비 요청 → 종결
  - 칸마다 담당(AI · 운전원 · 생산관리자 · 설비 제어 · 처리 시스템 · 정비 시스템)과 읽은 출처
  - "왜 1등인가" 두세 문장, 회복 기준표 쿨러 줄(유온 55 ℃ 아래)
- 대표 화면: [홈](../.evidence/a151-capture/01-홈-설비3기정상.png) · [조치 판단 카드](../.evidence/a151-capture/05-조치판단카드-추천1등.png) · [종결 결과](../.evidence/a151-capture/12-처리건-종결결과_표시-영문목록.png) — a151 세트 14장 전체가 이 바퀴의 장면이다(`README.md` 장별 설명)

### 팬 바퀴 — AI 칸을 내 PC 일꾼에게 맡겨 본 뒤, 일부러 틀린 선택으로 여러 겹의 안전을 확인한다

- 목표 가치: ①~④ 칸을 내 PC AI 일꾼에게 맡기고 사람은 칸 안의 질문에 답하는 역할을 해 본 뒤, 사람이 틀렸을 때 흐름도의 어디서(어느 칸 · 어느 겹) 막히는지 안다.
- 진행 순서: 단원 11(내 일꾼이 팬 경보의 네 칸 처리 · 질문에 답 · 정상 종결, 통합반은 질문 흐름으로 진동 · 납기 · 규칙을 물어 근거 확인) → 12(팬 100 % 함정, 펌프 가림, 원격 수동 과열 정지). 단원 12는 시스템 기본 AI 상태로 한다(일꾼과 함정을 같이 돌린 제작자 검증은 없음).
- 수강생이 기록할 것
  - 칸 → 다음 칸으로 넘어간 입력 표, AI 질문과 내 답, 일꾼이 쓴 도구 · 출처
  - 함정마다 예상 → 실제 → 막은 칸 · 겹(설비 제어기 안전장치 / ⑧ 효과 확인 · "회복됐나?" / ③ 규정 · 운전 모드 검사 / ⑤ 권한 · 기한)
  - 회복 기준표 팬 줄(진동 1.2 아래), 예측 압력 · 실측 압력 · 기준 165 비교
- 대표 화면: [에이전트의 질문 카드](../.evidence/a148/52/screen-question-card-1440.png) · [결함 시뮬레이션 — 수동 조작 · 보호 정지 해제](../.evidence/a141/scenario-1440.png) — 팬 함정 · 가림 장면은 별도 촬영 필요

### 회사 사정 바퀴 — 같은 고장에서 회사 값만 바꿔 ④ 칸의 1등이 뒤집히는 순간과, 이미 한 조치를 다시 하는 길을 찾는다

- 목표 가치: 설비 값이 같아도 회사 사정이 바뀌면 판단이 바뀌고, 승인은 그때의 사실에 묶여 있으며, 이미 나간 조치는 확인 · 되돌리기를 거쳐야 다시 할 수 있다는 것을 안다.
- 진행 순서: 단원 13(납기 · 품질 → 쿨러 순위 전후, 공급사 → 펌프 카드 제외, 옛 승인 거절, (통합반) 다시 수행).
- 수강생이 기록할 것
  - 카드 순위 전 · 후 비교표와 바꾼 값 · 되돌린 값
  - 옛 승인 거절 사유(바뀐 입력 이름)
  - (통합반) 이전 조치의 영향 목록과 처리 방법(보상 / 사람 확인), 다시 수행 전후 처리 건 상태
- 대표 화면: [승인과 실행 — 기업 시스템 현황](../.evidence/a141/process-1440.png) · [조치 판단 카드 — 점수와 순위](../.evidence/a151-capture/05-조치판단카드-추천1등.png)

### 펌프 바퀴 — 돌리기 전에 흐름도 칸 순서로 예측하고, 지식 지도와 규칙으로 근거를 대며 맞춰 본다

- 목표 가치: 시스템이 각 칸에서 무엇을 할지 미리 말하고 맞히는 경험으로, 지식 지도 · 규칙을 "읽을 줄 아는" 단계에서 "써서 설명하는" 단계로 넘어간다.
- 진행 순서: 단원 15(예측표 → 펌프 누설 주입 → 보류와 다시 평가 → 예비 펌프 전환 → 대조). 재료는 앞에서 이미 만들어 둔다: 4단원(예비 펌프 준비 상태 연결) · 5단원(규정 제외 미리 보기) · 8단원(AI에게 물은 펌프 질의) · 12단원(가림 결과).
- 수강생이 기록할 것
  - 예측표(흐름도 칸 순서): 원인 / 빠질 조치와 이유 / 1등 조치 / 승인 역할 / 회복 기준 / 첫 판단이 멈출지
  - 실제 결과와 한 줄씩 대조, 틀린 곳마다 "지도 · 규칙 중 어디를 못 봤나"
  - 회복 기준표 펌프 줄(압력 165 이상), 쿨러와 달랐던 곳(패턴 · 카드 · 명령 · 회복 기준) 4행

### 마무리 — 세 바퀴 비교표

단원 15에서 펌프 바퀴를 마친 뒤 채운다. 줄은 흐름도 칸(설비 경보의 감지 조건 · 원인 진단 · 규정 검토에서 빠진 조치와 이유 · 조치 후보 정리의 1등 · 조치 선택의 승인자 · 설비에 명령 · "회복됐나?"의 회복 기준 · 실패하면 어디로)과 "이번 바퀴의 목표" 한 줄이고, 열은 쿨러(기준 열, 따라가기) · 팬(맡기기 · 함정) · 펌프(예측), 그리고 회사 사정(1등 뒤집기)은 "무엇이 달라졌나" 열로 붙인다. 발표는 이 표와 바퀴별 기록지를 쓴다.
