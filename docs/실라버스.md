# 실라버스 — 시작 → 온톨로지 → 에이전트 → BPMN → 마무리, 막마다 이론 → 포털(사건 A · B · C) → 랩업

작성 2026-10-09. **사용자 확인 전 안**이다. 시나리오 설계 `scenario-research.md`의 세 사건(A 긴급 대응 · B 정비 계획 · C 예비품 구매)과 그 문서의 기능이 **모두 구현되어 있다고 가정**했다.
코드 · DECISIONS · HANDOFF · TODO는 고치지 않았고, 커밋하지 않았다. 표 파일은 `docs/실라버스.xlsx`(같은 행 데이터).

**시간 읽는 법**: 모든 분은 **예상 소요**다(리허설 실측 아님). 행마다 부품(설명 몇 분 + 따라 하기 몇 분 + AI 대기 몇 분 + 여유 몇 분)을 더해 만들었다(3절). AI 대기는 저장소의 실제 실행 기록에서 가져왔다. 쉬는 시간은 넣지 않았다(5-6).

**시간은 내용이 정한다(사용자 결정 2026-10-09, 엄격)**: 한 행 = 가르칠 내용 하나. 그 내용에 드는 만큼만 시간을 준다(5분 · 20분 · 45분 모두 된다). 50분 · 25~30분 같은 길이에 맞추려고 부품을 덧붙이거나, 여러 내용을 한 행에 묶거나, 행을 쪼개거나 합치지 않는다. 그래서 행 길이가 고르지 않고, 합계가 고정 합계와 맞지 않는다(차이와 조정 선택지는 5절).

**반영한 사용자 결정(2026-10-09)**
- 수강생은 코딩도 "LLM"이라는 말도 처음이다. 모든 단계는 강사와 함께 한다(혼자 하는 단계 없음). AI는 API 키로 실제로 쓴다.
- 제목은 가치 문장. 재료(바이브 코딩 · 명세 먼저 · Claude Code · MCP …)는 제목 · 주제가 되지 않는다.
- **온톨로지가 중심**: 문서에서 지식 그래프를 만들고, AI 일꾼은 그 지도에 물어 판단한다. 문서를 찾아 붙이는 방식(RAG)은 금지가 아니라 **비교 · 보조**로만 둔다(OT2의 "찾아서 답하기와 그 한계", OL7b의 "문서만 찾은 답 vs 지도 길 + 원문 구절 답").
- **피드백 순환 · 점진 학습(지난 판단에서 배워 나아지기)은 이 과정에 없다** — ProcessGPT 제품의 몫이고, 마무리(E1)에서 한 줄로만 말한다.
- 막 안의 순서는 늘 같다: **이론 → 포털 → 랩업**.
  - **이론 = 준비**: 포털 · 랩업 전에 알아야 할 개념과 "무엇을 왜 하나"를 비유로 아주 쉽게. **설명만으로도 된다.** 외부 도구는 **arrows.app(온톨로지 그리기)과 demo.bpmn.io(BPMN · DMN)만**, 그 밖의 해보기는 종이 · 포스트잇 · 역할극. 개념 설명과 도구 첫 사용(그리기)은 서로 다른 내용이라 다른 행이다(OT4 / OT4b, OT7 / OT7b, BT1 / BT1b). AI 체험(언어 모델 · 에이전트 · 도구)은 이론에 넣지 않고 랩업에서 Claude Code를 쓰며 자연스럽게 한다. 이론에서는 포털을 쓰지 않는다. 포털 들어가기 전 "지금까지 배운 것" 10분.
  - **포털 = 강사를 따라 한 단계씩, 강사는 단계마다 설명을 이어 간다.** 사건 A는 천천히(활동마다 한 행), B · C는 빠르게(1행씩), 막 끝에 세 사건 나란히(짧은 한 행).
  - **랩업 = 같은 기능을 바이브 코딩으로 한 번 더 만든다.** 막마다 끊기지 않는 한 줄 트랙. 강사는 만드는 동안 계속 설명하고, 학생이 틀리고 되돌리는 시간을 넣었다. 랩업마다 필요한 단계만 쓴다(3-1). 막 끝 "트랙 되짚기"에서 과정 노트를 한 번 쓴다.
- 마무리는 ProcessGPT 소개와 강사 시연 한 행(학생 실습 없음). 내용대로 매겨 50분 고정은 풀었다. 그 앞에서는 ProcessGPT를 도구로 쓰지 않는다(모두 수업 포털).
- 막 비율 목표 온톨로지 40 · 에이전트 35 · BPMN 25. 고정 합계 통합 영상 2640 · 통합 오프 2520 · 실전 영상 1920 · 실전 오프 2280분 — **이번 안은 이 합계에 억지로 맞추지 않았다**(5절). 통합반과 실전반은 행이 같고 시간 · 깊이만 다르다.

### 5-6. 쉬는 시간

### 5-7. 추정이 가장 흔들리는 곳과 열린 결정

**흔들리는 곳**

1. **Claude Code 생성 대기(랩업 24행, 행마다 3~6분)** — 작은 코드 생성의 실측이 없다. 5분이 걸리면 랩업마다 +2분, 통합 오프 약 +48분. 출발본을 만들며 한 번씩 재면 바로 고칠 수 있다.
2. **B · C 대기(정비창 · 입고)** — 20배속에서도 정비창 6분 · 리드타임 2.4시간이라 수업 압축(3분 가정)이 정해지지 않으면 BP3 · BP4가 깨진다(결정 4).
3. **AI 일꾼 4단계 3~4분** — A 실측. B · C 일꾼은 아직 돌지 않았다(가정: 기능 구현됨).
4. **오프 학생 막힘(여유 · 실수 · 복구)** — 20~30명 기준 추정. 첫 사용 도구(arrows.app · bpmn.io · VS Code)에서 편차가 가장 크다.
5. **에이전트 시험 실행이 실제 일꾼을 부르는가** — 지금 코드는 내장 판단 경로다(`scenario-research.md` §9). 실제 일꾼이면 AP2~AP4가 행마다 3~4분 대기, 내장 경로면 수 초로 줄어 행이 3분씩 짧아진다.

3. **나눈 행의 경계**: OT8 / OT8b(전략맵 / 상충), AT4 / AT4b(지금 값 / 읽기만), BT4 / BT4b(시작 / 예외), BT5 / BT5b(닫힘 / 지표)는 한 개념의 두 면으로 볼 수도 있다. 하나로 보면 다시 합친다(분은 두 행의 합 그대로).
