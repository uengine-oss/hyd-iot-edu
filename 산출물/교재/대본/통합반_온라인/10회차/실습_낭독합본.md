# 통합반 10회차 실습 1 — 정기점검작도


## 다운로드와 앞 흐름 열기

앞 승인 구조를 정기 점검 업무에 적용하겠습니다. 설비 명령 대신 정비 오더와 생산팀 공지로 이어지는 차이를 반영합니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 승인 블록을 새 업무에 맞추기

담당자·에이전트·시스템 레인을 유지하고 메시지 시작 이벤트를 정기 점검 도래로, 제안 작업을 정비 계획 제안으로, 사용자 작업을 설비보전팀장 승인으로 바꾸겠습니다. 냉각 명령과 재관측·유온 갈림은 정비 오더 등록·생산팀 공지와 결과 보고 흐름으로 바꿉니다. 이번 참조는 오더 등록과 공지를 한 서비스 작업으로 묶습니다.

승인 작업 뒤에는 승인 여부 게이트웨이를 두겠습니다. 승인은 정비 오더와 공지, 정상 보고와 종료로 잇고, 거절은 반려 보고와 별도 종료로 연결합니다. 승인 작업의 경계 타이머는 비중단형으로 두고 지연 알림과 알림 종료로 연결하겠습니다. 알림이 끝나도 사람의 승인 작업은 남아 있어야 합니다. 기한과 조건 값은 다음 연결 단계에서 설정합니다.

## 그림과 저장 파일 확인

작업6개, 승인 게이트웨이1개, 정상·거절·알림 끝 이벤트3개를 참조 그림과 대조합니다. 요소 수만 맞추지 않고 각 선의 방향과 끝, 타이머가 붙은 작업도 읽겠습니다. 거절 경로에서 오더로 가는 선이 없는지 확인합니다. 단순 표시 이름을 바꿔도 ID가 자동으로 바뀐다고 가정하지 않고, element-map.md에 직접 만든 요소 ID를 적겠습니다.

어긋난 연결이나 종류가 있으면 해당 항목을 고친 뒤 승인·거절·지연 경로를 다시 따라가겠습니다. output/pm-planning.bpmn으로 저장하고 편집기에서 다시 열어 레인·종류·선이 유지되는지 보겠습니다. 없는 속성 패널을 찾느라 진행을 멈추지 않고, 편집기가 제공하는 기능과 XML의 종류·참조를 함께 확인합니다. 다음 실습은 이 파일을 실행 기능과 연결하는 단계입니다.


# 통합반 10회차 실습 2 — 정기점검실행


## 다운로드와 연결 대상 준비

앞 정기 점검 흐름을 연결하고, 정비 시점 제안과 승인 뒤 오더·공지 결과를 각각 확인하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 가져오기와 매핑

흐름 메뉴에서 작성한 파일을 가져오고 시작 조건을 PM_DUE로 지정하겠습니다. 제안에는 판단·제안 부품과 정비 계획 에이전트, 승인에는 승인·거절 부품과 설비보전팀장 역할을 연결합니다. 정비 오더 등록·공지 작업은 정비 작업지시 부품으로 연결합니다. source/pm-planning.mapping.json을 보면서 정비 예정 시간이 담긴 값 alert.evidence.night_window_id와 공지 받는 사람·제목·내용을 입력하겠습니다. 이 경로의 값이 실제 입력에 있는지도 확인합니다.

정상·반려·지연 보고를 각각 해당 작업에 연결합니다. 승인은 approval이 승인인 조건, 거절은 그 밖의 경우로 두고 비중단형 타이머 기한은10분으로 설정하겠습니다. 제공 파일의 ID를 무조건 복사하지 않고 내 요소 대응표와 맞춥니다. 내 그림에 맞춘 연결 값은 output/pm-planning.mapping.json에도 기록하고 포털 설정과 대조하겠습니다. 현재 포털의 설정 폼을 우선 사용하며 다른 배포본에서 지원 항목이 없으면 임의 요청을 만들지 않고 미연결 항목을 기록합니다.

## 검사·등록·배포

검사에서 나타난 요소와 사유를 읽고 연결 누락이나 조건을 고친 뒤 다시 검사하겠습니다. 판본 등록 후 업무 프로세스에서 정의와 판본을 골라 배포합니다. 등록과 배포를 구별하고 배포한 ID·판본·시각을 기록합니다. 공용 환경에서는 가장 최근 배포가 경보 경로를 바꾸므로 수업에서 정한 환경과 순서를 확인하겠습니다.

## 승인과 반려의 결과 비교

정기 점검 이벤트를 한 번 발생시키고 경보 번호로 처리 건을 찾아 내 정의·판본인지 확인합니다. 승인을 기다리는 상태에서 추천 정비 시점과 근거를 읽고, 현재 근거와 권한·정비 조건이 충족될 때 권한 있는 역할로 승인하겠습니다. 부족하면 보류 사유를 남기고 승인한 경우에만 다음을 확인합니다. 승인 기록, CMMS 오더와 생산팀 공지, 결과 보고를 각각 확인합니다. 오더 등록은 현장 정비 완료가 아니며 공지만 실패한 경우 오더부터 다시 만들지 않고 남은 기록을 확인합니다.

거절 경로를 확인할 별도 교육용 건은 앞 건의 오더와 자원 예약 변화가 섞이지 않도록 시작 상태와 대상을 먼저 확인합니다. 업무상 거절 사유가 있는 건에서 그 근거를 적어 거절하겠습니다. 조건을 마련하지 못하면 이 경로는 미확인으로 남기며 정상 설정을 훼손하지 않습니다. 반려 종료와 오더·공지 미생성을 해당 처리 건의 기록으로 확인합니다. 앞 건에서 생긴 오더를 새 건의 결과로 읽지 않도록 ID를 대조합니다. 지연 알림을 확인하는 경우에도 승인 대기가 남는지 보며, 현재 수업 배속과 업무 기한을 구분합니다.

## 기록 저장

설정과 기록이 다르면 실제 문제의 위치와 사유를 찾아 필요한 항목만 수정하고 저장·재검사하겠습니다. 이미 배포한 정의는 이전 결과를 보존하고 새 판본과 별도 사건으로 재확인합니다. 오더가 이미 만들어졌으면 중복 생성하지 않도록 남은 공지·보고부터 확인합니다.

BPMN·매핑·요소 대응표를 저장하고 다시 열어 포털의 정의·판본과 맞추겠습니다. 정의·판본·경보·처리 건과 승인/거절, 오더·공지·미확인을 result-review.md에 저장하겠습니다. 파일을 다시 열어 상태와 실제 업무 결과가 구별되는지 보겠습니다. 같은 승인 구조를 다음 구매 흐름에도 이어 쓰겠습니다.


# 통합반 10회차 실습 3 — 재고보충작도


## 다운로드와 정비 그림 이어 쓰기

정기 점검에서 사용한 승인 구조를 재고 보충에 적용하겠습니다. 발주와 입고는 서로 다른 작업으로 남깁니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 구매 업무의 앞뒤 작업 구성

시작을 재고 부족 메시지 이벤트로, 제안을 발주안 제안으로, 사용자 작업을 구매 담당 승인으로 바꾸겠습니다. 승인 블록과 비중단형 지연 알림은 유지하되 이 업무에도 같은 승인 정책이 맞는지 확인합니다.

승인 뒤에는 ERP 발주·공급사 통지, 입고·재고 반영, 입고 완료 보고를 차례로 놓겠습니다. 거절은 발주로 이어지지 않고 반려 보고와 거절 종료로 보냅니다. 발주 등록과 실제 입고는 별개이므로 작업도 나누겠습니다. 이 수업 시스템은 즉시 입고 기능을 쓰지만 실제 공급사 거래나 배송을 수행하는 것은 아닙니다.

## 조건·역할·저장 확인

참조의 작업7개, 승인 게이트웨이1개, 정상·거절·알림 끝 이벤트3개와 대조합니다. 승인 대기가 알림으로 취소되지 않는지, 거절에서 발주로 가는 길이 없는지, 발주 다음 입고와 보고까지 연결됐는지 선을 따라 보겠습니다. 구매 담당자 레인과 에이전트·시스템 레인의 책임도 읽습니다.

실제 누락이나 잘못된 선이 있으면 고치고 승인·거절·지연의 세 경로를 다시 확인합니다. element-map.md에 내 요소 ID를 적고 output/spare-purchase.bpmn으로 저장하겠습니다. 다시 열어 연결과 종류를 확인합니다. 다음에는 이 그림에 구매 에이전트와 ERP·입고 기능을 연결합니다.


# 통합반 10회차 실습 4 — 재고보충실행


## 다운로드와 시작 상태 기록

구매 흐름을 연결하고, 승인 수량과 발주·입고·재고 변화를 같은 처리 건에서 대조하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 구매·입고 기능 연결

작성한 흐름을 가져와 시작 조건을 SPARE_BELOW_MIN으로 정하겠습니다. 제안에는 기존 예비품 구매 에이전트, 승인에는 구매 담당 역할을 연결합니다. source/spare-purchase.mapping.json을 대조하면서 ERP 발주 부품의 공급사 통지 설정과 입고 확인 부품의 바로 입고 처리를 입력하겠습니다. 승인된 부품·수량·공급사가 발주에 전달되는지 설정을 읽습니다.

승인은 approval이 승인인 조건, 거절은 기본 경로로 연결하고 타이머는 비중단형10분으로 둡니다. 정상 보고는 입고 완료, 반려 보고는 발주하지 않음, 지연 보고는 승인 대기로 구분합니다. 내 요소 ID에 맞춘 설정을 output/spare-purchase.mapping.json과 포털에 저장하고 검사 사유를 고친 뒤 정상 정의를 판본 등록·배포하겠습니다.

## 발주와 입고를 따로 확인

재고 보충 이벤트로 열린 건이 내 정의·판본인지 확인하고 추천 수량·공급사·경고와 현재 재고를 읽겠습니다. 공급사 승인 여부와 금액별 전결 범위, 품질 경고까지 확인하겠습니다. 현재 역할의 권한과 업무 조건이 충족될 때 승인하고, 전결 범위를 넘거나 근거가 부족하면 필요한 승인 절차 또는 보류를 기록합니다. 승인한 경우에는 발주 번호와 수량, 공급사 통지, 입고 번호·수량·검수 기록, 재고 반영과 결과 보고를 각각 확인합니다.

처음의 현재고3개·예약2개·발주 중0개에6개가 입고됐다면 현재고9개, 예약2개, 발주 중0개이므로 보충 판단 수량은7개입니다. 이 숫자를 무조건 기대 결과로 쓰지 않고 실제 시작 값과 승인 수량으로 계산하겠습니다. 발주 중 수량이 먼저 반영되어 보충 필요 표시가 꺼졌더라도 입고가 끝난 것으로 읽지 않습니다. 발주 뒤 입고가 실패했다면 기록을 확인하고 전체를 무조건 다시 실행해 중복 발주하지 않겠습니다.

## 거절 건과 결과 저장

거절 경로를 확인할 별도 교육용 건은 앞 건의 발주·입고로 바뀐 재고와 섞이지 않도록 시작 상태와 대상을 먼저 확인합니다. 업무상 거절 사유가 있는 건에서 그 근거를 남기겠습니다. 조건을 마련하지 못하면 해당 경로는 미확인으로 두겠습니다. 해당 건에서 발주·통지·입고가 생성되지 않았는지, 반려 종료와 미해결 업무가 기록에 남는지 확인합니다. 다른 건의 재고 변화가 섞였다면 이번 거절의 효과로 단정하지 않고 구분합니다.

기대와 다른 기록은 실제 입력·매핑·승인 내용과 연결해 원인을 찾겠습니다. 고칠 항목이 있으면 이전 결과를 보존하고 설정 수정·저장·재검사를 거쳐 새 판본과 별도 사건으로 재확인합니다. 이미 생성된 발주를 다시 만드는 방식으로 입고 실패를 고치지 않겠습니다.

BPMN·매핑·요소 대응표를 저장한 뒤 다시 열어 포털 설정과 맞추겠습니다. 시작 값, 승인 내용, 발주·입고·처리 건 ID와 판본, 실제 결과와 미확인을 result-review.md에 저장하겠습니다. 파일을 다시 열어 완료 상태와 실제 입고 근거가 연결되는지 봅니다. 공용 환경의 배포 복구는 정해진 범위와 시점에 따르고 임의로 전체 흐름을 내리지 않겠습니다. 이 기록과 교재의 기존 예시를 구별해 전체 업무 흐름 복습으로 돌아갑니다.
