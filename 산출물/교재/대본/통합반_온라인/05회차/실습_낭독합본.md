# 통합반 5회차 실습 1 — 업무에이전트구성


## 자료 다운로드와 작업 공간 열기

포털에서 본 냉각 대응을 바탕으로, 원인 근거와 추가 확인 사항을 제시하는 에이전트를 구성하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


기본 제공 에이전트에서 목표·역할·업무 지침·연결 서버를 먼저 읽겠습니다. 기본 항목을 직접 바꾸지 않고 새 수업용 에이전트를 만들겠습니다. 이름을 정하고 목표에는 ‘냉각 경보의 원인 후보와 필요한 추가 확인을 근거와 함께 정리한다’, 역할에는 ‘설비보전 판단 보조’를 적겠습니다. 설비 조작은 목표에 넣지 않습니다.

## 지침과 도구 선택하기

수행 지침에는 원인 후보를 찾고, 확인한 값과 문서 근거를 읽고, 확인하지 못한 항목을 분리해 결과를 내도록 적겠습니다. 목표는 도달할 결과이고 지침은 그 결과에 이르는 방법입니다. 서버 선택 화면에서는 현재 교육 환경에 등록된 지식·시계열·업무 조회 서버와 허용 도구를 확인하겠습니다. 필요 없는 서버는 연결하지 않습니다. 화면의 서버 선택과 개별 도구 권한은 같은 것이 아니므로 실제 호출 가능 목록도 확인하겠습니다.


## 같은 질문으로 비교하고 기록 읽기

기준 사건의 식별자와 시각, 설비를 review.md에 적겠습니다. 기본 제공 에이전트와 새 에이전트에 ‘이 냉각 경보에서 확인된 원인 근거와 아직 확인해야 할 항목을 정리해 주세요’라는 같은 요청을 넣겠습니다. 실행 중 값이 갱신되면 그 차이를 기록해, 결과 차이를 지침 변경 때문이라고 단정하지 않겠습니다.

최종 문장만 비교하지 않고 호출 기록을 열겠습니다. 어떤 도구에 어떤 입력을 넘겼고, 돌아온 결과의 어느 값이 다음 호출에 쓰였는지 따라갑니다. 원인 후보와 확인된 원인, 조회 실패와 조회 0행을 구별하는지도 보겠습니다. 근거가 없는 결론이 나오면 지침의 어느 요구가 빠졌는지 고치고 같은 조건으로 다시 확인하겠습니다. 도구나 권한 문제는 지침 문장을 길게 쓰는 것으로 해결되지 않으므로 설정 상태도 따로 봅니다.

## 저장과 재확인

design.md에 변경 전후의 목표·역할·지침·서버를 저장하고, review.md에는 기준 사건·호출 입력·결과 출처·남은 미확인을 적겠습니다. 포털의 설정을 다시 열어 저장된 내용과 비교합니다. 더 긴 답변을 좋은 결과로 보지 않고, 확인한 사실과 보류한 판단이 구분되고 원문과 도구로 되짚을 수 있는지 보겠습니다. 다음에는 이 흐름의 일부를 로컬 기능으로 직접 만들겠습니다.


# 통합반 5회차 실습 2 — 원인추론과점검계획


## 다운로드와 입력 확인

여러 원인 후보의 증거를 대조하고, 부족한 정보에 맞춰 점검 순서를 제안하는 기능을 만들겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


이번 프로젝트의 내부 구성은 아직 모르므로, 원인 근거를 찾는 데 어떤 자료와 기능이 준비됐는지부터 확인하겠습니다.


expected.md에 첫 사례에서 확인할 근거를 먼저 적겠습니다. 원인 후보에 연결된 증거 조건, 필요한 태그, 집계와 시간 창을 찾습니다. 평균과 최댓값·최솟값 차이는 다른 집계입니다. 입력의 신선도와 표본 누락을 확인하지 않고 숫자 하나만 비교하지 않겠습니다.

## 근거를 읽는 기능과 출력 약속 만들기

코딩 도우미에게 이렇게 요청하겠습니다. source의 스키마·그래프·사례를 읽어 원인 후보를 찾고 증거를 평가하는 agent.py를 만들어 주세요. 입력의 실제 필드와 관계 이름을 먼저 확인하세요. 기준은 그래프에서 읽고 코드에 임의 수치를 넣지 마세요. 확인됨·확인 못함·지지 근거 없음의 상태를 구별하고, 근거마다 태그·집계·시간 창·실제 값·기준·출처를 남겨 주세요. 누락·묵은 값·불충분한 표본은 0이나 정상으로 바꾸지 마세요. 여러 후보가 남으면 함께 제시하고 확정 원인이라고 쓰지 마세요.

출력은 output/result.json과 output/inspection.md로 정하겠습니다. 점검 계획에는 원인 후보, 확인할 근거, 확인 순서와 이유, 필요한 사람의 확인을 적게 합니다. 순서는 제공 SOP의 선행 조건과 안전 조건을 먼저 따르고, 자료가 순서를 정하지 않으면 ‘제안’이라고 표시하도록 하겠습니다. 실제 제어나 작업지시는 호출하지 않습니다.


## 실행 고리와 결과 대조

기능이 원인 후보 조회, 필요한 증거 읽기, 관찰, 다음 확인의 순서를 기록하도록 요청하겠습니다. 모델을 쓰는 부분과 수치·조건을 계산하는 부분을 나누고, 최대 반복 횟수와 확인 불가 시 종료 조건도 설정합니다. 수업에서는 생성된 실제 인자에 맞춰 사례 하나를 실행하고 expected.md의 근거와 대조하겠습니다. 결과가 다르면 그래프 해석, 센서 집계, 신선도, 문장화 중 어디에서 달라졌는지 확인합니다.

제공 사례 중 태그가 부족하거나 관측 시각이 오래된 경우, 여러 원인에 맞는 증거가 있는 경우를 찾아 비교하겠습니다. 추가 입력이 필요하면 원문과 구별한 검증용 사례로 정의하고 그 입력이 확인하려는 조건을 적습니다. 정상 기능을 고장 내거나 과거 관측을 실제 장애로 바꾸지는 않습니다. 빠진 태그가 보류와 추가 점검으로 이어지는지, 복수 근거에서 하나를 임의로 확정하지 않는지 확인합니다. 점검 순서를 고칠 때도 원문에 없는 조작 단계를 덧붙이지 않겠습니다.

## 저장과 다시 열기

작성한 기능과 입력 사본, 예상 근거, 실제 결과와 수정 기록을 저장하고 다시 열겠습니다. 어느 근거로 후보가 남았고 무엇을 추가로 확인해야 하는지 설명할 수 있는지 보겠습니다. 지금 만든 기능이 실제 고장 원인을 확정하거나 현장 작업을 승인한 것은 아닙니다. 다음에는 품질 접수를 후속 업무로 연결하겠습니다.


# 통합반 5회차 실습 3 — 품질대응카드


## 자료 다운로드와 작업 공간 열기

품질 접수의 사실과 추정을 나누고, 담당 부서가 다음 확인을 이어갈 수 있는 대응 카드를 만들겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


처리 방법은 앞에서 익혔으니 이번에는 품질 접수에서 달라지는 기준부터 확인하겠습니다.


먼저 Q01의 측정값과 공차, Q03의 빠진 로트와 수량, Q04의 유온 원인 추정을 읽겠습니다. 원문에 사진을 첨부했다고 쓰여 있어도 실제 파일이 제공되지 않았다면 사진 내용을 확인한 것으로 적지 않습니다. review.md에 접수 번호와 원문 구절, 확인한 사실과 추가로 필요한 정보를 나누겠습니다.

## 카드 형식과 처리 기능 만들기

코딩 도우미에게 이렇게 요청하겠습니다. 제공 접수와 분류 기준을 읽어 품질 대응 카드를 만드는 quality.py를 작성해 주세요. 접수 번호, 원문 근거, 유형 후보, 확인된 정보, 추가 확인, 담당 부서와 근거, 후속 업무 초안을 JSON과 Markdown으로 내 주세요. 원인 미확정은 조사 요청으로 남기고 추정을 사실로 바꾸지 마세요. 기준에 없는 담당 부서는 임의로 정하지 마세요. 실제 통보나 업무 등록은 하지 마세요.

결과는 output/cards.json과 output/cards.md에 저장하도록 하겠습니다. 분류가 겹치면 후보와 근거를 남기고 무조건 하나로 줄이지 않습니다. Q08처럼 라벨과 수량 문제가 함께 있으면 각각의 확인 사항이 살아 있어야 합니다. 품질 문제가 아닌 일정 문의도 억지로 불량 유형에 넣지 않도록 지시하겠습니다.

## 원문과 카드 대조하고 수정하기

작성된 코드가 source를 덮어쓰지 않는지, 누락 값을 추정으로 채우지 않는지 읽고 수업 환경에서 실행하겠습니다. 먼저 Q01의 수치와 Q03의 미확인 사항을 원문과 대조합니다. Q04에서는 유온과 불량의 시간 관계가 원인 확정으로 바뀌지 않았는지 보겠습니다. Q05의 원인 확인도 접수자가 그렇게 보고했다는 출처를 남겨야 합니다.

나머지 접수도 같은 기준으로 확인하겠습니다. Q09의 추가 검사와 Q04의 표본을 합칠 때 중복 여부가 확인되지 않았다면 임의의 전체 불량률을 만들지 않습니다. Q10은 일정 문의로 분리하고, Q11은 앞 접수와 같은 로트라는 정보와 원인 미확정을 함께 남깁니다. 기대와 다르면 해당 조건을 고친 뒤 같은 입력을 다시 처리하겠습니다.

## 저장과 재확인

원문 판본, 카드, 분류 근거, 차이와 수정 내역을 저장하겠습니다. cards.json과 cards.md를 다시 열어 같은 접수 번호의 내용이 맞는지 보고, 조사 요청이 확정 조치로 바뀌지 않았는지 확인합니다. 사람이 확인하고 업무로 넘길 수 있는 초안이 이번 결과입니다. 다음에는 시간에 따른 센서 변화를 도표와 요약으로 읽겠습니다.


# 통합반 5회차 실습 4 — 센서이상시각화


## 다운로드와 자료 범위 확인

센서의 시간별 변화를 도표로 확인하겠습니다. 단위와 누락 구간을 보존하면서 설명이 원자료와 맞는지 검토할 겁니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


이번에는 센서 자료의 시간·단위·누락 처리가 핵심입니다. 도우미와 입력의 실제 범위부터 확인하겠습니다.


실제 교육 환경의 조회 자료를 사용할 때는 제공 CSV 대신 조회한 값을 input에 별도 저장하겠습니다. 먼저 현재 서버의 메타데이터에서 설비·태그·단위·조회 가능 구간을 확인하고, 시작·종료 시각과 시간대를 고정합니다. 조회가 실패하거나 결과가 없으면 가상 입력으로 진행한다는 사실을 기록하겠습니다. 과거 사례의 평균값을 연속 측정값으로 바꾸지는 않습니다.

## 시각화와 요약 기능 만들기

코딩 도우미에게 이렇게 요청하겠습니다. source의 CSV를 읽어 시간순으로 정렬하고 태그별 도표를 만드는 visualize.py를 작성해 주세요. 단위가 다른 온도와 압력은 별도 축 또는 별도 그림으로 구별하세요. 입력에 없는 값이나 누락 구간을 임의로 보간하지 마세요. 중복 시각, 숫자 변환 오류, 빈 값을 보고하고, 사용한 시간 범위와 태그를 결과에 적으세요. 결과는 output/chart.png와 output/summary.md로 저장해 주세요.

상승 구간은 각 태그에서 직전 유효 관측값보다 높은 인접 관측을 이어 표시하는 방식으로 먼저 정하겠습니다. 누락을 사이에 둔 두 값을 연속 상승으로 묶지 않습니다. 이 표시가 설비의 이상 판정 기준은 아닙니다. 실제 경보 기준을 적용하려면 그 기준의 출처와 집계·시간 창을 추가로 확인해야 합니다.

## 도표와 원자료 맞춰 보기

도우미의 변경 설명으로 입력·처리 기준·저장 위치를 확인한 뒤 수업 환경에서 실행하겠습니다. 도표의 첫 시각과 마지막 시각, 태그별 값과 단위를 CSV의 행과 맞춥니다. 빈 온도 값이 0으로 찍히거나 누락 구간이 매끈한 선으로 이어졌다면 처리 방식을 고칩니다. 표시된 상승 구간의 시작과 끝을 실제 행에서 다시 확인하겠습니다.

요약에는 자료가 가상 입력이라는 점, 사용한 기간·설비·태그, 관찰한 변화와 미확인 사항을 적겠습니다. 온도와 압력이 함께 움직였다고 한쪽이 다른 쪽의 원인이라고 쓰지 않습니다. 값이 오른 구간과 경보 기준을 넘은 구간도 구별합니다. 요약에 나온 모든 숫자가 원자료나 명시한 계산에서 나오는지 확인하겠습니다.

## 저장하고 다시 열기

사용한 입력과 처리 기준, 코드, 그림과 요약, review.md를 저장하겠습니다. 그림과 요약을 다시 열어 기간과 태그가 일치하는지 확인하고 자료를 바꿨을 때도 같은 검사 기준을 적용할 수 있도록 남깁니다. 이제 네 활동에서 확인한 근거와 남은 미확인을 바탕으로 에이전트의 역할을 정리하겠습니다.
