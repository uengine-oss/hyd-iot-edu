# 통합반 7회차 실습 1 — 승인과거절


## 자료 다운로드와 승인 대상 확인

추천 내용이 같아 보여도 현재 조건과 담당 권한에 따라 결정은 달라집니다. 승인과 거절의 근거와 후속 기록을 비교하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 승인과 거절을 각각 확인하기

먼저 승인 역할이 배정된 계정과 그 역할을 확인합니다. 승인할 수 없는 역할에서는 결정 기능이 제한되는지 보고, 권한을 임의로 바꾸지 않겠습니다. 승인 가능한 연습 건에서는 추천안과 현재 조건을 확인한 뒤 승인합니다. 누가 어떤 역할로 무엇을 결정했는지 기록을 열고, 승인 뒤의 상태와 후속 작업을 확인하겠습니다. 승인 기록과 실제 후속 실행 결과는 구별해서 적습니다.

이번에는 현재 조건이나 근거가 승인 기준을 충족하지 않는 별도 연습 건을 검토하겠습니다. 거절할 사유를 확인했을 때 그 근거를 남기고 거절하겠습니다. 거절 사유와 종료 상태를 확인하고 이후 작업이나 명령이 생성됐는지 기록으로 봅니다. 이미 처리한 건을 되돌려 재사용하지 않습니다. 검토 의견이나 가드레일 통과만으로 사람의 결정이 생긴 것으로 읽지 않겠습니다.

## 기록 저장과 재확인

두 건의 입력, 역할, 결정과 처리 결과를 review.md에 남기고 다시 열어 비교합니다. 기대와 다르면 권한·현재 조건·결정 기록·후속 처리 순으로 확인하고 미확인은 그대로 적겠습니다. 이 기록을 다음 질문 실습에서 정보 답변과 승인 결정의 차이를 확인하는 기준으로 쓰겠습니다.


# 통합반 7회차 실습 2 — 확인질문과재처리


## 다운로드와 기존 프로젝트 열기

앞 에이전트에 정보가 부족한 정비 요청이 들어왔습니다. 이미 확인할 수 있는 값은 활용하고 필요한 질문만 하도록 확장하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


source/입력/점검_요청.json의 요청 번호와 설비, 경보 패턴, 사례 필드를 읽습니다. source/사람/답변.json은 교육용 답변 입력이고 실제 승인 기록이 아닙니다. 기존 에이전트가 받는 cases.json 구조와 새 요청 구조는 다를 수 있으므로, 요청에서 사례 ID를 찾은 뒤 기존 입력으로 연결하는 부분을 먼저 확인하겠습니다. 원본 필드 이름을 몰래 바꾸지 않습니다.

## 부족한 정보를 묻는 단계 만들기

코딩 도우미에게 이렇게 요청하겠습니다. 기존 원인 추론 기능을 유지하고 요청 처리 단계를 더해 주세요. 요청 번호로 상태를 보관하고, 설비·경보·사례 중 판단에 필요한 정보를 입력과 참조 자료에서 확인하세요. 참조로 확인할 수 없는 값만 질문하고 보류하세요. 답이 오면 같은 요청에 연결해 다시 확인하고 기존 분석으로 넘기세요. 답변으로 승인이나 권한을 만들지 마세요. 확인하지 못한 값은 추정하지 마세요.

output/requests.json에는 상태, 확인 질문, 받은 답과 근거, 다음 처리 여부를 남기게 하겠습니다. 누락 값이 기본 설비나 0으로 바뀌지 않는지를 결과에서 확인하겠습니다. 요청 번호가 다른 답을 섞지 않도록 하고, 답이 부족하거나 맞지 않으면 추가 확인 상태를 유지하도록 하겠습니다.

## 질문 전후를 같은 요청으로 비교하기

R04처럼 정보가 빠진 요청을 먼저 넣어 필요한 확인 질문과 보류 상태를 보겠습니다. 제공 답변을 읽고 해당 요청에 대응하는 값만 입력한 뒤 재처리하겠습니다. 답변 파일에 대응 값이 없으면 임의로 채우지 않고 질문 상태를 기록합니다. 답을 받은 뒤 원인 후보와 근거가 기존 분석으로 이어지는지도 확인합니다.

R02처럼 사례 ID로 확인 가능한 값이 있는 경우에는 참조한 원문을 남기고 불필요한 재질문이 없는지 보겠습니다. R04처럼 단서가 부족한 경우에는 진행을 보류해야 합니다. ‘급하니 승인한 것으로 처리’라는 답변을 별도 연습 입력으로 넣어도 정보만 받고 승인은 별도 단계로 남는지 확인하겠습니다. 로컬의 연습 상태는 HYD의 실제 승인 권한이 아닙니다.

## 수량·긴급 사유·승인권자 확인으로 확장하기

source/업무요청_추가.json은 이번 활동의 교육용 입력입니다. 기존 사례 입력과 다른 요청 형식이므로 원인 분석 입력에 그대로 넣지 않고, 그 앞의 요청 접수 단계에서 처리하겠습니다. 부품 수량, 긴급 사유, 승인권자 정보 중 비어 있고 참조로도 확인할 수 없는 항목을 각각 질문하도록 요청합니다. 수량을 0으로 채우거나 요청자의 역할을 승인 권한으로 복사하지 않습니다.

각 요청 번호에 연결된 source/업무답변_추가.json을 입력하고 전후 상태를 비교하겠습니다. 정보가 갖춰져도 사람의 실제 승인 상태는 별도 승인 대기로 남깁니다. 답변에 ‘승인한 것으로 처리’가 있어도 수량 등 업무 정보만 반영하는지 확인하고 결과를 저장하겠습니다.

## 저장과 이어 쓰기

질문 전후 입력, 요청별 상태와 실제 결과, 수정과 재확인을 저장하겠습니다. 파일을 다시 열어 다른 요청의 답이 섞이지 않았는지 봅니다. 이 프로젝트의 판본을 남기고 다음 제안·검토 실습에서 이어 쓰겠습니다.


# 통합반 7회차 실습 3 — 제안과검토


## 다운로드와 같은 프로젝트 준비

앞 요청 처리에 작성과 검토 역할을 나누어 붙이겠습니다. 검토 의견도 원문에 근거해야 합니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 작성 역할과 검토 역할 만들기

먼저 writer.md에 업무 요청 초안을 작성하는 역할을 적겠습니다. 요청 번호, 대상과 부품, 수량, 긴급 사유, 승인권자 정보와 근거 위치를 남기고 모르는 값은 미정으로 둡니다. 코딩 도우미에게 기존 요청 처리와 원인 분석을 유지하면서 이 지침으로 초안을 생성하는 단계를 추가하도록 요청하겠습니다.

reviewer.md에는 원문과 참조 자료를 직접 읽고 근거·수량·승인 정보의 누락과 모순을 찾는 역할을 적겠습니다. 작성자의 자기 평가를 그대로 받지 않고 별도 호출에서 원문과 초안을 대조하도록 연결합니다. 검토 의견마다 대상 항목, 문제와 원문 위치, 필요한 수정 또는 추가 확인을 남깁니다. 같은 모델을 두 역할로 쓴다고 오류까지 독립적인 것은 아니므로 제 판단으로도 근거를 대조하겠습니다.

## 초안·검토·수정본 비교

정보가 빠진 요청을 작성 역할에 넣고 실제 초안을 저장합니다. 같은 원문과 초안을 검토 역할에 넘겨 의견을 받고, 확인된 의견을 작성 역할에 반영하게 하겠습니다. 자료에 없는 담당자나 기한을 검토자가 만들어 내면 그 의견을 채택하지 않고 미확인으로 남깁니다. 누락이 없다고 나와도 억지로 오류를 만들지 않습니다.

검토 상태와 사람의 최종 승인 상태는 서로 다른 필드로 저장하겠습니다. 검토 통과가 사람 승인이나 업무 실행 허가로 바뀌지 않는지 코드와 결과를 확인합니다. 추가 확인이 필요한 건은 질문 단계로 돌리고 답을 받은 뒤 같은 번호로 다시 작성·검토합니다.

## 저장과 이어 쓰기

writer.md와 reviewer.md, 초안·검토 의견·수정본, 반영 여부와 근거를 저장하겠습니다. 파일을 다시 열어 어떤 의견이 실제로 반영됐는지 대조합니다. 이 프로젝트를 보존한 채 다음 이론에서 요구 변경과 명세를 살펴보겠습니다.


# 통합반 7회차 실습 4 — 모호한변경비교


## 다운로드와 변경 전 상태 보존

기존 정비 요청에 긴급 처리를 추가할 때, 요구를 명확히 하지 않으면 무엇이 달라질 수 있는지 비교하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 같은 조건에서 모호한 변경 적용

변경 전 사본에서 일반 요청을 실행해 입력·조회 자료·설정과 실제 출력을 저장합니다. 이제 다른 사본의 코딩 도우미에게 ‘긴급 정비 요청도 구분해서 빨리 처리할 수 있게 추가해 주세요’라고 요청하겠습니다. 이 단계에서는 세부 명세를 나중에 쓰는 방식의 차이를 살펴봅니다. 변경된 파일을 먼저 읽고 실제 외부 명령이나 승인 우회 경로를 실행하지 않는 교육용 범위에서 비교하겠습니다.

두 사본에 같은 일반 요청과 긴급 요청을 넣습니다. 기존 출력 이름·자료형·뜻, 정보 누락 처리, 승인 대기 조건을 항목별로 비교합니다. 실행 번호나 시각처럼 매번 달라지는 값은 연결 관계를 확인하고, 문장의 표현 차이와 계약 위반을 구별합니다. 긴급의 해석이 달랐다면 무엇을 기준으로 삼았는지도 기록하겠습니다.

## 차이와 미확인 남기기

제공 기록의 실패가 이번 환경에서 재현되지 않으면 실패를 일부러 만들지 않고 실제 차이만 남깁니다. 결과가 같아도 확인한 입력 범위를 넘어 모든 변경이 안전하다고 결론 내리지 않겠습니다. 관련 없는 수정은 보존한 원본과 대조하고 비교 대상에서 구분합니다.

두 사본, 변경 요청, 입력과 실제 출력, 변경 파일 목록과 비교표를 저장하겠습니다. 다시 열어 같은 입력을 비교했는지 확인하고, 이 기록을 다음 명세 작성의 근거로 이어 쓰겠습니다.


# 통합반 7회차 실습 5 — 명세에따른변경


## 다운로드와 비교 기록 이어 받기

앞 비교에서 확인한 변경 범위를 명세로 정하고, 기존 동작을 유지하면서 긴급 판단을 추가하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


## 명세를 먼저 작성하기

현재 프로젝트의 입력과 출력 구조를 읽고 spec.md를 작성하겠습니다. 목표, 입력, 출력, 금지 조건과 수용 기준을 나눕니다. 기존 일반 요청의 결과 항목과 뜻, 정보 누락 시 보류, 승인 없이 업무를 확정하지 않는 조건을 먼저 적겠습니다.

추가 요구는 교육용 기준으로 판단할 때의 유온이 섭씨 60도 이상이면 긴급 여부를 참으로 표시하는 것입니다. 다른 자료의 임계값이나 실제 설비 안전 기준을 바꾸는 것은 아닙니다. 어떤 태그·집계·시간 창의 값을 쓸지 입력 자료에 맞춰 명시하겠습니다. 값이 없거나 유효하지 않으면 긴급 여부를 추정하지 않고 보류합니다. 긴급 표시가 생겨도 승인 절차와 일반 요청의 출력 계약은 유지합니다.

수용 기준에는 같은 입력과 자료에서 일반 요청의 기존 결과가 유지되는지, 긴급 입력에 표시가 추가되는지, 누락이면 보류하는지, 거절이면 후속 업무가 없는지를 적겠습니다. 실행 번호와 시각은 값 자체의 동일성 대신 형식·연결 관계를 검사하도록 정합니다. 출력에 필드를 더할 때 기존 소비자가 이를 받아들일 수 있는지도 확인하겠습니다.

## 명세에 맞춰 구현하고 비교하기

코딩 도우미에게 spec.md를 읽고 필요한 부분만 고치도록 요청하겠습니다. 기존 일반 요청 처리와 질문 단계, 승인 조건을 보존하고 긴급 여부와 그 근거를 추가해 주세요. 임계값과 입력 검사를 명세와 맞추고, 기존 출력 이름과 뜻은 유지해 주세요.

수정된 파일을 비교해 관련 없는 변경이 없는지 읽고, 수업 환경에서 일반·긴급·누락 입력을 같은 조건으로 확인하겠습니다. 새 기능만 보지 않고 변경 전 일반 요청의 결과와 대조합니다. 기대와 다르면 차이를 먼저 기록한 뒤 코드와 명세 중 실제 원인이 있는 곳을 확인합니다. 검사에 맞추려고 기존 기대값을 바꾸지 않겠습니다.

## 다음 검증의 재료 저장

spec.md와 구현 판본, 입력, 조회 자료, expected.json에 직접 적은 기대 결과, 실제 결과를 저장하겠습니다. 가상 경계 입력은 복사본에만 만들고 원본과 구별합니다. 다시 열어 각 수용 기준에 대응하는 입력과 기대가 있는지 확인하겠습니다. 이번에는 저장한 결과로 복습하고, 다음 회차에서 같은 프로젝트를 시나리오와 반복 검증으로 이어가겠습니다.
