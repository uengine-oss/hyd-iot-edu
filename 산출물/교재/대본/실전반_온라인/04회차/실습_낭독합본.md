# 실전반 4회차 실습 1 — 업무에이전트구성


## 자료 다운로드와 작업 공간 열기

포털에서 본 냉각 대응을 바탕으로, 원인 근거와 추가 확인 사항을 제시하는 에이전트를 구성하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


기본 제공 에이전트에서 목표·역할·업무 지침·연결 서버를 먼저 읽겠습니다. 기본 항목을 직접 바꾸지 않고 새 수업용 에이전트를 만들겠습니다. 이름을 정하고 목표에는 ‘냉각 경보의 원인 후보와 필요한 추가 확인을 근거와 함께 정리한다’, 역할에는 ‘설비보전 판단 보조’를 적겠습니다. 설비 조작은 목표에 넣지 않습니다.

## 지침과 도구 선택하기

수행 지침에는 원인 후보를 찾고, 확인한 값과 문서 근거를 읽고, 확인하지 못한 항목을 분리해 결과를 내도록 적겠습니다. 목표는 도달할 결과이고 지침은 그 결과에 이르는 방법입니다. 서버 선택 화면에서는 현재 교육 환경에 등록된 지식·시계열·업무 조회 서버와 허용 도구를 확인하겠습니다. 필요 없는 서버는 연결하지 않습니다. 화면의 서버 선택과 개별 도구 권한은 같은 것이 아니므로 실제 호출 가능 목록도 확인하겠습니다.


## 같은 질문으로 비교하고 기록 읽기

기준 사건의 식별자와 시각, 설비를 review.md에 적겠습니다. 기본 제공 에이전트와 새 에이전트에 ‘이 냉각 경보에서 확인된 원인 근거와 아직 확인해야 할 항목을 정리해 주세요’라는 같은 요청을 넣겠습니다. 실행 중 값이 갱신되면 그 차이를 기록해, 결과 차이를 지침 변경 때문이라고 단정하지 않겠습니다.

최종 문장만 비교하지 않고 호출 기록을 열겠습니다. 어떤 도구에 어떤 입력을 넘겼고, 돌아온 결과의 어느 값이 다음 호출에 쓰였는지 따라갑니다. 원인 후보와 확인된 원인, 조회 실패와 조회 0행을 구별하는지도 보겠습니다. 근거가 없는 결론이 나오면 지침의 어느 요구가 빠졌는지 고치고 같은 조건으로 다시 확인하겠습니다. 도구나 권한 문제는 지침 문장을 길게 쓰는 것으로 해결되지 않으므로 설정 상태도 따로 봅니다.

## 저장과 재확인

design.md에 변경 전후의 목표·역할·지침·서버를 저장하고, review.md에는 기준 사건·호출 입력·결과 출처·남은 미확인을 적겠습니다. 포털의 설정을 다시 열어 저장된 내용과 비교합니다. 더 긴 답변을 좋은 결과로 보지 않고, 확인한 사실과 보류한 판단이 구분되고 원문과 도구로 되짚을 수 있는지 보겠습니다. 다음에는 이 흐름의 일부를 로컬 기능으로 직접 만들겠습니다.


# 실전반 4회차 실습 2 — 원인추론과점검계획


## 다운로드와 입력 확인

여러 원인 후보의 증거를 대조하고, 부족한 정보에 맞춰 점검 순서를 제안하는 기능을 만들겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


이번 프로젝트의 내부 구성은 아직 모르므로, 원인 근거를 찾는 데 어떤 자료와 기능이 준비됐는지부터 확인하겠습니다.


expected.md에 첫 사례에서 확인할 근거를 먼저 적겠습니다. 원인 후보에 연결된 증거 조건, 필요한 태그, 집계와 시간 창을 찾습니다. 평균과 최댓값·최솟값 차이는 다른 집계입니다. 입력의 신선도와 표본 누락을 확인하지 않고 숫자 하나만 비교하지 않겠습니다.

## 근거를 읽는 기능과 출력 약속 만들기

코딩 도우미에게 이렇게 요청하겠습니다. source의 스키마·그래프·사례를 읽어 원인 후보를 찾고 증거를 평가하는 agent.py를 만들어 주세요. 입력의 실제 필드와 관계 이름을 먼저 확인하세요. 기준은 그래프에서 읽고 코드에 임의 수치를 넣지 마세요. 확인됨·확인 못함·지지 근거 없음의 상태를 구별하고, 근거마다 태그·집계·시간 창·실제 값·기준·출처를 남겨 주세요. 누락·묵은 값·불충분한 표본은 0이나 정상으로 바꾸지 마세요. 여러 후보가 남으면 함께 제시하고 확정 원인이라고 쓰지 마세요.

출력은 output/result.json과 output/inspection.md로 정하겠습니다. 점검 계획에는 원인 후보, 확인할 근거, 확인 순서와 이유, 필요한 사람의 확인을 적게 합니다. 순서는 제공 SOP의 선행 조건과 안전 조건을 먼저 따르고, 자료가 순서를 정하지 않으면 ‘제안’이라고 표시하도록 하겠습니다. 실제 제어나 작업지시는 호출하지 않습니다.


## 실행 고리와 결과 대조

기능이 원인 후보 조회, 필요한 증거 읽기, 관찰, 다음 확인의 순서를 기록하도록 요청하겠습니다. 모델을 쓰는 부분과 수치·조건을 계산하는 부분을 나누고, 최대 반복 횟수와 확인 불가 시 종료 조건도 설정합니다. 수업에서는 생성된 실제 인자에 맞춰 사례 하나를 실행하고 expected.md의 근거와 대조하겠습니다. 결과가 다르면 그래프 해석, 센서 집계, 신선도, 문장화 중 어디에서 달라졌는지 확인합니다.

제공 사례 중 태그가 부족하거나 관측 시각이 오래된 경우, 여러 원인에 맞는 증거가 있는 경우를 찾아 비교하겠습니다. 추가 입력이 필요하면 원문과 구별한 검증용 사례로 정의하고 그 입력이 확인하려는 조건을 적습니다. 정상 기능을 고장 내거나 과거 관측을 실제 장애로 바꾸지는 않습니다. 빠진 태그가 보류와 추가 점검으로 이어지는지, 복수 근거에서 하나를 임의로 확정하지 않는지 확인합니다. 점검 순서를 고칠 때도 원문에 없는 조작 단계를 덧붙이지 않겠습니다.

## 저장과 다시 열기

작성한 기능과 입력 사본, 예상 근거, 실제 결과와 수정 기록을 저장하고 다시 열겠습니다. 어느 근거로 후보가 남았고 무엇을 추가로 확인해야 하는지 설명할 수 있는지 보겠습니다. 지금 만든 기능이 실제 고장 원인을 확정하거나 현장 작업을 승인한 것은 아닙니다. 이처럼 반복할 수행 방법을 다음에는 스킬 파일로 정리하겠습니다.


# 실전반 4회차 실습 3 — 회의록스킬작성


## 다운로드와 스킬 폴더 만들기

설비보전 회의에서 결정한 일과 아직 남은 일을 구분하는 스킬을 만들겠습니다. 다음 회의에도 같은 기준이 적용돼야 합니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


이번에는 프로그램 내부보다 반복해서 사용할 업무 지침이 대상입니다. 두 회의록에 어떤 결정과 미결 사항이 담겼는지 먼저 확인하겠습니다.


코드 폴더를 작업 공간으로 열고 .github/skills/meeting-actions 폴더에 SKILL.md를 새로 만들겠습니다. 머리말의 name은 meeting-actions, description은 ‘회의록에서 결정사항과 후속 작업·담당자·기한을 근거와 함께 정리할 때 사용한다’로 적겠습니다. 폴더 이름과 name을 맞추고, 도우미가 실제로 이 스킬을 인식하는지 확인합니다. 파일이 있다는 사실만으로 적용됐다고 말하지 않겠습니다.

## 절차와 예외 직접 작성하기

본문에는 입력, 수행 순서, 예외, 출력을 적겠습니다. 입력은 회의록 원문이고, 순서는 원문 구간을 읽고 결정과 제안·미결정을 구별한 뒤 후속 작업을 정리하는 것입니다. 작업마다 내용·담당자·기한·상태·근거 문장을 남기게 하겠습니다. 담당자나 기한이 없으면 미정으로 표시하고, 여러 사람이 적혀 있으면 한 명을 임의로 책임자로 고르지 않도록 적습니다.

‘원인이 금형 쪽이면 점검한다’는 조건부 작업이지 이미 확정된 작업이 아닙니다. ‘정하지 않고 넘어갔다’는 제안을 결정으로 바꾸지 않도록 예외를 적겠습니다. ‘내일까지’는 회의 날짜가 분명할 때만 날짜로 풀고 원문 표현과 해석 기준을 함께 남기겠습니다. ‘이번 주 안’처럼 기준이 여럿일 수 있는 말은 임의 마감 시각을 만들지 않겠습니다.

출력은 output/actions.md와 output/actions.json으로 정하겠습니다. 같은 항목 ID를 써서 두 형식이 일치하도록 하고, 원문 위치와 확인이 필요한 항목을 포함하겠습니다. 이 파일은 일하는 방법을 적은 지침입니다. 일정 등록이나 알림 발송 권한이 생기는 것은 아닙니다.

## 두 회의록으로 적용과 원문 대조

도우미에 meeting-actions 스킬로 첫 회의록을 정리해 달라고 요청하겠습니다. 적용 기록을 확인한 뒤 결과와 원문을 나란히 엽니다. 결정과 제안이 섞이지 않았는지, 담당자와 기한을 지어내지 않았는지, 이미 끝난 일을 새 할 일로 만들지 않았는지 확인하겠습니다. 틀린 항목은 결과만 고치는 데서 멈추지 않고 SKILL.md의 해당 규칙을 고쳐 다시 적용합니다.

이번에는 두 번째 회의록을 같은 스킬로 처리하겠습니다. 이 자료에는 담당자가 없는 확인 사항, 두 사람이 맡는 현장 안내, 조건부 점검과 보류된 양식 변경이 있습니다. 이 차이가 결과에 그대로 남는지 보겠습니다. 첫 회의록의 이름과 날짜가 새 결과에 섞이면 입력과 재사용 지침을 분리해 고치겠습니다.

## 회의 사이에서 이어진 조치 확인

두 결과를 요청별로 다시 대조하겠습니다. 정기 회의의 구매팀 전달과 주간 협의의 전달 완료·견적 확인은 이어지는 기록입니다. 문장이 비슷하다고 하나를 지우거나, 같은 일을 새 작업으로 두 번 만들지 않겠습니다. 이전 결정, 후속 확인, 아직 남은 일을 각각 남기도록 스킬을 보완합니다.


이번 수정이 새 회의록에만 맞춘 예외가 아닌지 보겠습니다. 이름이나 특정 날짜를 지침에 고정하지 않고, 출처와 상태 변경을 확인하는 규칙으로 남기겠습니다.

## 저장과 재확인

SKILL.md와 두 회의록별 출력, 수정 이유를 저장하겠습니다. 새 입력에 같은 방법을 썼는지, 한 번의 결과를 복사한 것은 아닌지 다시 확인합니다. Markdown과 JSON의 작업 수·ID·담당자·기한도 대조합니다. 이어지는 MCP에서는 이 지침이 필요로 하는 외부 도구를 어떻게 연결하는지 살펴보겠습니다.


# 실전반 4회차 실습 4 — MCP도구연결


## 다운로드와 포털 조회 도구 확인

앞 에이전트의 조회 도구를 확인한 뒤, 점검 자료·변경 이력·시각을 서로 다른 서버에서 연결하겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.


먼저 교육용 포털에서 업무 DB와 판단 엔진 서버의 등록 상태, 연결 검사 결과, 실제 도구 목록을 확인하겠습니다. 읽기 도구 하나의 이름·설명·필수 입력·읽기 표시를 기록하고, 대상과 권한을 확인한 뒤 조회합니다. 호출 기록의 서버·도구·입력·결과와 자료의 기준 시각을 review.md에 적겠습니다. 읽기 표시만 믿지 않고 허용 목록과 실제 기능을 함께 확인합니다. 실습1의 에이전트에서도 같은 조회를 사용할 수 있는지 설정과 호출 기록을 대조하겠습니다.

## 로컬 작업 자료와 세 서버 설정

코드/도구의 자료_준비.py를 열어 어떤 폴더와 Git 이력을 만드는지 읽겠습니다. 수업에서 코드 폴더의 터미널에 python 도구/자료_준비.py를 실행하면 이 실습 폴더 안에 업무자료가 준비됩니다. 이미 업무자료가 있으면 그대로 두는 기본 실행만 사용하겠습니다. 다시 만들기 옵션은 쓰지 않습니다. 업무자료와 제공된 구매팀_자료는 연습용 자료이며 실제 업무 저장소가 아닙니다.


VS Code 작업 공간의 .vscode/mcp.json을 만들겠습니다. 최상위 servers 아래 filesystem, git, time을 각각 둡니다. 각 항목의 type은 stdio, command는 교육 환경의 Python 실행 파일로 정하고 args에 해당 서버 스크립트의 절대경로를 넣습니다. 파일 서버에는 --read-only와 업무자료 절대경로, Git 서버에는 --repository와 같은 업무자료 경로를 추가합니다. 시간 서버에는 서버/시간_서버.py 경로를 넣습니다. 제공 설정_작성.md의 형식과 실제 경로를 대조하며 적겠습니다.

이 로컬 설정은 이론의 HYD mcpServers 설정을 그대로 붙여 넣는 것이 아닙니다. VS Code는 이 파일의 servers를 읽습니다. HYD가 서버에서 실행된다면 강사 PC의 로컬 경로가 그 서버에서도 보이는 것은 아니므로 포털에 로컬 경로를 등록하지 않겠습니다.

## 연결하고 한 요청으로 조합하기

세 서버를 각각 시작하고 도구 목록을 확인하겠습니다. 파일 서버의 허용 폴더와 읽기 전용 모드, Git 서버의 대상 저장소, 시간 서버의 시간대 입력을 기록합니다. 실패하면 실행 파일·스크립트 경로·대상 폴더·서버 오류를 순서대로 확인합니다. 한 서버가 실패했다고 다른 두 서버까지 성공으로 묶지 않겠습니다.

이제 ‘업무자료에서 쿨러 점검 메모를 읽고, Git에서 최근 변경과 아직 커밋하지 않은 변경을 확인한 뒤, 시간 도구의 Asia/Seoul 현재 시각을 기준으로 남은 확인 사항을 정리해 주세요. 파일 경로·커밋·조회 시각을 각 근거에 남기고, 과거 회의록의 상대 날짜는 회의 날짜를 기준으로 해석해 주세요’라고 요청하겠습니다. 세 도구가 실제로 호출됐는지 기록을 펼쳐 보고 output/combined.md의 각 문장을 원문과 이력으로 대조합니다. 현재 시간과 문서 작성 날짜를 섞어 옛 기한을 새 기한으로 바꾸지 않겠습니다.

## 실패와 권한 경계 확인

연습용 구매팀_자료는 파일 서버 허용 범위 밖에 두었습니다. 그 파일을 요청했을 때 접근이 거부되고 미확인으로 남는지 보겠습니다. 범위를 몰래 넓히는 대신 이 요청에서 필요하지 않은 자료라고 기록합니다. 결과가 일부만 보이면 읽은 범위를 적고 필요한 구간을 다시 확인합니다. 조회 실패나 시간 초과는 값 없음이나 업무 완료로 바꾸지 않겠습니다.

## 저장하고 재확인

설정 파일, 서버별 목록과 호출 기록, 결합 결과, 오류와 수정 내역을 저장하겠습니다. 다시 열어 결과의 파일 근거와 Git 변경, 조회 시각이 서로 맞는지 봅니다. 서버 연결 성공과 답변의 정확성은 별개입니다. 네 실습에서 남긴 근거를 기준으로 이제 에이전트·스킬·MCP의 역할을 함께 정리하겠습니다.
