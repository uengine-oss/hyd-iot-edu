## 1. 판본과 시작 상태 기록

> [화면 02-01] 판본, 폴더 구조, 기대 상태 표. 비밀 설정값은 제외한다.
> [조작] 제공된 HYD 저장소의 판본·실행 구성을 기록하고 ot·dmz·it 폴더와 compose.yaml의 역할을 연결한다. 이미 켜진 환경이면 현재 상태부터 관찰한다.

이번에는 서비스를 실행하고 각 역할이 동작할 준비가 됐는지 확인하겠습니다. 같은 프로젝트라도 어떤 기능을 켜는지에 따라 필요한 서비스가 달라질 수 있습니다. 그래서 먼저 이번 환경의 판본과 실행 구성을 기록하겠습니다.

폴더에서 OT, DMZ, IT에 해당하는 부분을 찾겠습니다. 앞 이론에서 본 역할들이 어느 코드와 구성에 연결되는지 확인하는 겁니다. Compose 파일에는 함께 실행할 서비스의 구성이 있습니다. 그 밖에서 준비해야 하는 작업자나 연결도 있는지 제공 절차와 대조하겠습니다.

이름만 보고 모두 같은 상태여야 한다고 적어도 될까요? 우선 서비스 하나를 골라 시작 명령과 의존 대상을 읽겠습니다. 계속 요청을 받는 역할인지, 자료를 준비하고 끝나는 역할인지부터 확인하겠습니다. 그 뒤 기대 상태를 표에 적겠습니다. 포털이 열리는 것만으로 판단부터 조치까지 전체 과정이 준비됐다고 볼 수는 없습니다.

> [선택 분기 · 비낭독] 구성과 절차를 읽어도 역할을 설명하기 어려운 항목이 있을 때만 아래 질문을 사용한다. 설명할 수 있으면 기대 상태를 적고 도구 확인으로 진행한다.
> [입력 · 비낭독] 구조 탐색 요청: `첨부한 구성의 서비스 한 항목이 무슨 일을 하는지 파악하려 합니다. 아직 정상 여부를 판정하거나 설정을 수정하지 마세요. 명령·의존성·상태 검사 중 무엇부터 읽어야 할지 질문 하나로 안내해 주세요. 제가 해당 부분을 읽고 역할을 설명하겠습니다.`
> [응답 분기 · 비낭독] 강사가 선택한 항목의 실제 구성으로 답한다. 명령을 먼저 읽으라는 질문이면 구성에 적힌 명령과 역할을 확인하고, 다른 질문이면 그 위치를 찾는다. 자료가 없으면 서비스 역할을 추측하지 않는다. 이후 상시 서비스·일회성 준비·외부 의존성 중 해당 범위를 정리한다.

## 2. 도구와 엔진 구분

> [화면 02-02] 도구 버전과 엔진 상태를 구분한 화면.
> [조작] docker --version, docker compose version, python --version으로 각 도구의 응답을 확인한다. Docker 엔진 상태는 별도로 확인한다. Copilot 사용 여부는 필수 환경 판정과 구분한다.

VS Code는 파일을 읽고 터미널에서 명령을 실행할 작업 공간입니다. Docker Desktop은 컨테이너 실행 환경을 제공하고, Compose는 정의된 여러 서비스를 함께 다룹니다. Python은 다음 기록 추적 랩의 코드를 실행할 때 사용합니다.

버전 확인 명령부터 읽어 보겠습니다. 버전이 나오면 그 명령을 실행할 수 있다는 근거가 됩니다. 하지만 Docker 명령의 버전이 나왔다는 것만으로 엔진이 실행 중이거나 HYD 서비스가 준비됐다고 말할 수는 없습니다. 도구, 엔진, 서비스가 각각 어떤 상태인지 따로 확인하겠습니다.

AI의 도움을 사용하는 경우에도 관측을 먼저 남기겠습니다. 버전은 나오는데 다음 단계가 안 된다면, 무엇까지 확인했는지와 어디서부터 안 됐는지를 질문에 넣습니다. 제공된 절차와 코드를 따라가는 데 모델 키는 배포하지 않습니다. 선택적인 대화 사용 여부와 서비스의 정상 여부도 별개로 기록하겠습니다.

## 3. 실행 순서 읽고 적용 범위 정하기

> [화면 02-03] 해당 판본의 실행 절차와 단계별 준비 확인. 토큰·키는 제외한다.
> [조작] 문서/시스템/4_켜고_돌리는_법.md와 수업의 실행 구성을 대조한다. 업무 데이터베이스·서비스·외부 작업자의 선행 조건을 확인하고 해당 프로필의 기동 절차를 적용한다. 이미 실행 중이면 재기동 장면을 만들려고 내리지 않는다.

이제 제공 절차에서 이번 구성의 시작 순서를 찾겠습니다. 어떤 서비스가 다른 서비스의 준비를 기다리는지 살펴보겠습니다. 선행 조건이 빠지면 뒤의 서비스만 다시 켜도 문제가 풀리지 않을 수 있습니다.

환경 변수는 어떤 설정을 정하는지, 실행 프로필은 어떤 구성을 선택하는지 확인하겠습니다. 비밀값 자체를 기록하거나 보여 줄 필요는 없습니다. 사용한 설정의 이름과 구성, 문제가 생겼을 때 볼 로그 위치를 남기면 됩니다.

단계를 하나 진행할 때마다 무엇이 끝났는지 확인하겠습니다. 주소 목록이 출력된 것과 그 주소에서 필요한 응답을 받은 것은 다릅니다. 절차에 적힌 준비 조건을 확인한 뒤 다음 단계로 넘어가겠습니다. 이미지 내려받기나 설치, 권한 복구가 필요한 시간은 별도로 기록합니다.

## 4. 상태를 종류별로 판정

> [화면 02-04] 장기 실행 서비스 상태, 일회성 작업의 종료 코드·로그, 기대와 관측의 비교.
> [조작] 해당 구성에서 docker compose ps -a 등으로 상태를 확인한다. 로그는 서비스와 관측 시각이 맞는 필요한 구간을 사용한다. 실제 실패가 없다면 실패 사례를 연출하지 않는다.

상태 목록을 볼 때는 먼저 그 항목이 어떤 일을 하는지 확인하겠습니다. 계속 실행되는 서비스라면 실행 상태와 해당 서비스가 제공하는 상태 검사 결과를 봅니다. 자료를 준비하고 끝나는 일회성 작업이라면 종료 코드와 완료 기록을 봐야 합니다.

종료됐다는 표시만으로 실패라고 하면 정상적으로 일을 마친 준비 작업도 실패로 읽게 됩니다. 반대로 실행 중이라는 표시만으로 모든 기능이 정상이라고 하면 연결 문제를 놓칠 수 있겠죠. 기대 상태 옆에 실제 관측과 그 근거를 적어 보겠습니다.

확인표에서 기대와 관측이 다른 항목이 있는지 보겠습니다. 차이가 있다면 그 행과 관련 로그를 놓고 원인을 좁히겠습니다. 모두 기대와 맞으면 확인한 범위를 남기고 포털 접속으로 넘어가겠습니다. 분명한 결과를 다시 묻기 위해 대화를 만들 필요는 없습니다.

> [선택 분기 · 비낭독] 아래 대화는 기대와 다른 관측이나 판단할 수 없는 항목이 있을 때만 진행한다. 정상 경로에서는 건너뛰고 §5로 이동한다.
> [조작 · 비낭독] `환경_확인표.md`에 실제 기대·관측·근거를 적고 채팅 컨텍스트로 선택한다. 관련 문서의 해당 판본 절차와 필요한 로그만 추가한다. 비밀 설정값은 첨부하지 않는다.
> [입력 · 비낭독] `이 확인표에서 도구 설치, 엔진 실행, 서비스 준비를 구분하려 합니다. 제가 확인했다고 쓴 항목 하나의 근거를 먼저 질문해 주세요. 답한 뒤 아직 입증하지 못한 범위와 다음 확인 한 가지만 제안해 주세요. 관측하지 않은 장애를 추정하거나 전체 재설치·초기화를 제안하지 마세요.`
> [응답 분기 · 비낭독] 실제 질문을 읽는다. 강사는 해당 관측과 그 한계를 답한다. 버전 출력에 대한 질문이면 “버전 출력으로 확인한 것은 명령을 사용할 수 있다는 점이고, 엔진과 서비스는 별도 확인이 필요합니다.”라고 답한다. 다른 질문이면 실제 확인표의 해당 근거로 답한다.

제 답변을 보낸 뒤 제안된 다음 확인이 원래 절차와 맞는지 보겠습니다. 질문에 대한 답이 그럴듯해도 이번 판본에 없는 명령이나 서비스를 가져오면 그대로 적용할 수 없습니다. 필요한 항목 하나만 골라 확인하겠습니다.

> [조작·분기 · 비낭독] 실제 응답을 원문 절차와 대조한다. 기대·관측을 혼동한 표의 문장이 있다면 그 행만 수정한다. 시스템 변경은 해당 판본 절차에서 필요한 것으로 확인된 경우만 적용하며 초기화하지 않는다. 필요한 상태 조회나 접속을 한 가지 수행하고 관측을 갱신한다. 기대와 다르면 해당 출력으로 다음 확인을 좁히고, 같으면 그 범위만 확인으로 남긴다. 실제 장애가 없으면 정상 서비스와 일회성 작업의 판정 차이를 설명한다.

확인표를 고친 것과 환경 문제가 해결된 것은 다릅니다. 방금 확인한 결과를 근거로 판정을 남기고, 아직 확인하지 않은 기능까지 정상이라고 넓혀 적지는 않겠습니다.

원인 후보를 얻은 것과 해결한 것은 다릅니다. 고쳤다면 같은 기준으로 다시 확인한 결과가 있어야 합니다. 실제 실패 로그가 없다면 이번 실행에서 실패를 겪었다고 작성하지 않습니다.

## 5. 접속 결과와 미확인 구분

> [화면 02-05] 포털 접속 결과와 환경 확인표. 미확인 항목도 남긴다.
> [조작] 제공 주소의 포털과 주요 서비스를 각각 확인하고, 다음 전체 과정에 필요한 외부 작업자의 준비 상태를 구분한다. 접속하지 않은 것은 미수행, 시도했지만 필요한 증거를 얻지 못한 것은 미확인으로 적는다.

마지막으로 포털과 주요 서비스의 접속을 확인하겠습니다. 접속하지 못했다면 서버 장애라고 바로 결론 내리지는 않겠습니다. 주소가 맞는지, 권한이 있는지, 연결이 닿는지, 서비스가 어떤 응답을 줬는지를 나누어 보겠습니다.

확인표에는 기대 상태, 관측 상태, 근거 위치, 판정을 남깁니다. 목록에서 서비스가 몇 개 보였다는 것보다 이번 구성에 필요한 항목을 각각 확인했는지가 중요합니다. 외부 작업자를 아직 확인하지 못했다면 포털 접속 성공과 별도로 표시하겠습니다.

이 표를 바탕으로 다음 실습을 준비하겠습니다. 다음에는 저장된 사건의 처리 과정을 읽으면서 추천과 승인, 실행과 결과를 구별하고, 작업지시에서 판단의 근거를 거슬러 찾아보겠습니다.

> [연결 · 비낭독] 전체 과정 관찰·기록 추적 실습으로 이어 간다. 실제 화면·관측 결과는 후속 삽입하며, 이번 문서 완성을 환경 실행 성공으로 보고하지 않는다.
