> [운영 · 비낭독] 강사가 혼자 자료를 읽고 판단·요청·검토·수정·실행을 시범 보이는 발화다. 학생 응답이나 조작을 기다리지 않는다. 이번 문서 작성에서는 실행·화면 조작·캡처를 하지 않았다. 화면은 후속 삽입한다. 실제 Copilot 응답과 실행 출력은 아래 분기에 따라 읽으며 예시 답변을 실제 응답으로 대신하지 않는다. 운영 시간은 미확정이다. 이전 고정 견적은 철회했다. 기존 완성본의 검증 결과는 시작본의 구현 성공을 보증하지 않는다.

> [진행 원칙 · 비낭독] 조작하면서 해당 판단을 설명한다. 힌트와 AI 요청 예시는 필요한 경우에만 사용하며 모두 순서대로 소진하지 않는다. 이미 확인한 결론을 모르는 척하거나 질문 횟수를 채우지 않는다. 오류 분기는 실제 오류가 있을 때만 사용한다.

## 시작. 자료를 받아 작업 폴더 열기

기록 추적 실습 자료를 내려받겠습니다. 파일 이름이 세 번째 실습인지 확인하고 작업할 위치에 압축을 풀겠습니다. 이제 VS Code에서 파일, 폴더 열기를 선택합니다. 압축을 푼 폴더 안에 시작코드가 있습니다. 이 폴더를 열겠습니다.

탐색기에 자료와 파이썬 파일이 함께 보입니다. 먼저 설명 파일을 읽겠습니다. 오늘 만들 부분은 기록 사이의 참조를 비교하는 함수 하나입니다. 파일을 읽고 결과를 저장하는 부분과 테스트는 이미 제공되어 있습니다. 목표와 입력, 고칠 범위, 확인 방법이 정해져 있으므로 비교 규칙을 이해하고 함수 하나로 옮기는 데 집중하겠습니다.

저장 기록은 recorded 폴더에 있고, 제가 고칠 것은 trace_records 파일 안의 검사 함수입니다. 결과는 result 폴더에 저장됩니다. 별도로 들어 있는 코드 폴더는 비교용 완성본이므로 지금은 열지 않겠습니다.

검사 함수에는 아직 구현하지 않았다는 오류가 들어 있습니다. 이 상태로 실행하면 그 자리에서 멈추도록 만들어 둔 겁니다. 실제 설비 장애를 넣어 둔 것이 아닙니다. 먼저 무엇을 비교할지 정한 다음 이 빈 부분을 채우겠습니다.

## 먼저: 경보에서 작업지시까지 전체 과정 읽기

> [화면 03-00] 동일 사건 기록 중 확보된 구간, 식별자·시각, 미확인 구간.
> [조작] 전체 과정의 기록 종류를 짚되 제공 발췌가 모든 단계를 담고 있다고 전제하지 않는다. 원문 없는 구간을 다른 사건으로 채우지 않는다. 승인 전 명령 없음은 해당 구간의 기록 범위가 충분할 때만 판정한다.

참조를 비교하기 전에 전체 흐름에서 각 기록이 무엇을 말하는지 보겠습니다. 경보는 이상 조건이 성립했다는 기록이고, 추천은 어떤 조치를 제안했는지 보여 줍니다. 담당자의 승인, 설비에 보낸 명령, 처리 응답은 다시 구분해야 합니다.

팬 속도가 그대로였으면 승인 전 명령이 없었다고 말해도 될까요? 그것만으로는 부족합니다. 명령 기록과 그 기록이 포괄하는 시각을 확인해야 합니다. 응답을 받은 것, 유온이 완화된 것, 핀 세척이 끝난 것도 각각 다른 결과입니다.

제가 가진 자료에서 확인되는 구간을 먼저 적고, 없는 구간은 미확인으로 남기겠습니다. 오늘 만드는 도구는 이 흐름 전체의 성공을 판정하지 않습니다. 마지막 작업지시에서 판단을 거슬러 찾을 때, 직접 참조가 맞는지를 비교합니다.

## 1. 입력을 읽고 첫 질문 보내기

> [화면 03-01] 원본 발췌의 직접 참조·도착 식별자, Copilot Chat에 선택한 입력과 첫 요청.
> [조작] `recorded/case_a.json`에서 `work_order.decision_id`, `decision.id`, `source_paths`, `provenance`, `context`를 구분한다. VS Code에서 Copilot Chat을 열고 입력 JSON을 컨텍스트로 선택·첨부한다. 화면에 표시된 첨부 파일명을 확인한다. 해당 기능이 없으면 필요한 발췌를 붙여 넣고 원본 경로를 적는다. 개인 정보·비밀값을 포함하지 않는다.

이 자료는 이천이십육 년 시월 십사 일의 실제 실행에서 필요한 항목을 발췌한 것입니다. 교재의 예시 사건과는 별도 실행이므로 온도나 식별자를 서로 옮겨 채우지 않겠습니다.

파일을 위에서부터 읽어 보겠습니다. 원본을 설명하는 부분이 있고, 작업지시와 판단에 해당하는 묶음도 있습니다. 이름에 아이디가 붙은 항목이 여럿 보이는데, 이것들을 아무렇게나 이어도 되는 걸까요? 우선 각 항목이 자기 기록의 이름인지, 다른 기록을 가리키는 값인지 나누어 메모하겠습니다.

같은 설비라는 이유만으로 묶는 방법도 떠오릅니다. 그런데 같은 설비에 다음 날 다른 사건이 생기면 구분할 수 없겠네요. 제가 필요한 것은 비슷한 기록을 모으는 방법이 아니라, 이 작업지시가 어느 판단에서 나왔는지 찾는 방법입니다. 여기까지 파악한 내용을 질문에 넣겠습니다.

Copilot 채팅을 열고 지금 읽은 입력 파일을 붙이겠습니다. 제가 보고 있는 파일이 자동으로 모두 전달됐다고 생각하지 않고, 첨부된 파일 이름까지 확인합니다. 아직 비교할 항목을 확정하지 않았으므로 코드부터 요청하지 않겠습니다.

> [입력 · 비낭독] 첫 요청: `첨부한 자료에서 작업지시가 어느 판단에서 나왔는지 찾고 싶습니다. 식별자가 여러 개라 각각 자기 기록의 이름인지 다른 기록의 참조인지 아직 구별 중입니다. 코드는 작성하지 말고, 제가 자료에서 먼저 찾아볼 항목을 질문 하나로 좁혀 주세요. 처음부터 비교할 필드와 정답을 모두 알려 주지는 마세요.`
> [응답 분기 · 비낭독] 실제 응답의 질문을 읽는다. 비교 대상 질문이면 아래 자기 답변을 사용한다. 다른 질문이면 입력에서 확인한 사실로 해당 질문에 답한다. 질문 없이 구현을 내놓으면 “코드는 아직 적용하지 않고 비교 대상부터 설명하겠습니다.”라고 말하고 요청 범위를 다시 좁힌다. 질문·답변을 미리 받은 것처럼 꾸미지 않는다.

질문을 받은 부분으로 돌아가 보겠습니다. 작업지시에는 자기 식별자 외에 판단을 가리키는 항목이 있습니다. 그 값을 판단 묶음의 식별자와 나란히 놓겠습니다. 두 값이 같은지, 원본 위치도 맞는지 보겠습니다. 제가 찾은 비교 대상은 이 두 항목입니다.

제가 이렇게 찾은 이유를 채팅에 적겠습니다. 작업지시에 적힌 판단 참조가 도착한 판단의 식별자와 맞아야 같은 연결이라고 볼 수 있습니다. 단순히 같은 화면이나 같은 묶음에 있다는 이유만으로 연결하지 않겠습니다.

> [입력 · 비낭독] 실제 질문에 대한 강사 답변과 위 판단을 채팅에 입력한다. `source_paths`의 원본 위치도 확인해 연결표에 기록한다.

## 2. 검사 함수 하나 구현하고 변경 검토하기

> [화면 03-02] 시작 함수, 두 번째 요청, 실제 제안의 변경 비교, 저장.
> [조작] `trace_records.py`를 컨텍스트에 추가한다. 자기 기준을 정리한 뒤 `test_trace_records.py`를 열어 검증 범위와 대조한다. 빈 `check_link`와 이를 호출하는 `inspect_records`, 출력에서 사용하는 반환 항목을 확인한다. 수정 대상은 시작코드의 함수 한 개다.

이제 함수를 열겠습니다. 비교 결과와 이유를 돌려주도록 자리는 마련되어 있지만, 어떤 조건으로 나눌지는 비어 있습니다. 가장 먼저 떠오르는 방법은 두 값이 같으면 확인, 다르면 실패로 나누는 겁니다. 그런데 자료가 부족할 때도 실패라고 해도 될까요? 기록이 잘못 연결된 것과 비교할 근거가 없는 것은 다른 상황 같습니다.

여기서 두 번째 입력을 잠깐 열겠습니다. 교육용으로 일부를 가린 자료입니다. 원본과 달라진 항목을 찾아 두 파일 옆에 적겠습니다. 없는 값을 다른 곳에서 가져와 채우지 않고, 지금 자료로 무엇까지 말할 수 있는지 정해야겠습니다.

> [조작 · 비낭독] 두 JSON의 구조를 비교해 누락 항목을 직접 찾는다. 발견 전에는 해당 필드에 바로 커서를 놓아 답부터 보여 주지 않는다. 구조 비교가 막히면 “두 파일의 같은 위치를 나란히 보면 무엇이 달라졌나요?”라고 묻는다. 정답 필드에 커서를 놓거나 판정 규칙을 힌트로 읽지 않는다.
> [입력 · 비낭독] 기준 탐색 요청: `두 값의 같음과 다름으로만 판정하려 했는데, 일부 항목이 없는 입력에서는 결론을 내릴 근거가 부족해 보입니다. 지금 제 기준이 놓치는 경우를 하나씩 질문해 주세요. 먼저 제가 경우를 나누어 설명한 뒤에 구현하겠습니다. 입력 자료는 바꾸지 마세요.`
> [응답 분기 · 비낭독] 실제 질문에 맞춰 강사가 입력의 값과 존재 여부를 확인한다. 답을 먼저 받은 경우에도 제안된 경우를 원본·가림 자료와 대조한 뒤 자기 말로 다시 정리한다. 실제 질문 없이 문답을 주고받은 것처럼 이어 읽지 않는다.

이제 세 경우를 나누겠습니다. 비교할 값이 없으면 미확인, 둘 다 있는데 다르면 실패, 둘 다 있고 같으면 확인으로 두겠습니다. 빈 문자열 두 개는 같다는 계산 결과가 나와도 연결을 입증하지 못합니다. 그래서 일치 여부보다 값이 있는지를 먼저 보겠습니다. 이 기준은 제가 자료를 읽고 정한 판단이고, 코드는 그 판단을 옮기는 역할입니다.

함수 아래를 보면 검사 결과를 모으고 화면에 출력하는 부분이 있습니다. 이 부분이 사용할 항목도 반환해야 합니다. 판정만 돌려주면 나머지 부분이 읽을 정보가 사라집니다. 호출 방식과 반환 형식을 유지하면서 함수 안만 구현해 달라고 요청하겠습니다.

> [입력 · 비낭독] 구현 요청: `제 규칙은 참조 값 또는 도착 식별자가 없거나 빈 문자열이면 미확인, 둘 다 있고 다르면 실패, 둘 다 있고 같으면 확인입니다. 첨부한 시작본 trace_records.py의 check_link 함수만 구현해 주세요. 함수 인자와 나머지 입출력·테스트는 유지하세요. link, state, reference, identity, reason을 반환해야 합니다. recorded 파일과 context는 수정하거나 누락 참조를 추정하는 데 사용하지 마세요. 적용 전 변경 내용과 조건 순서를 설명해 주세요.`
> [응답 분기 · 비낭독] 실제 제안에서 값 추출·누락 검사·불일치 검사·반환 항목을 차례로 읽는다. 변경 비교에서 함수 밖 수정, 입력 변조, context 추정이 있으면 수락하지 않는다. 텍스트 제안이면 함수 부분만 원본과 나란히 비교한다. 필요한 지적만 후속 요청하고 다시 검토한다.

변경된 줄을 보겠습니다. 먼저 두 값을 어디에서 가져오는지, 그다음 누락을 먼저 확인하는지 보겠습니다. 마지막으로 판정과 이유, 비교한 두 값을 함께 돌려주는지 확인합니다. 입력 자료를 바꾸거나 다른 함수까지 고친 부분은 이번 요청 범위에 들어가지 않습니다. 테스트도 제 코드가 맞는지 확인하는 기준이므로 결과에 맞춰 고치지 않겠습니다.

> [범위 이탈 분기 · 비낭독] 전체 구현을 바꾸거나 입력·테스트를 수정한 제안이면 적용을 멈추고 “요청보다 수정 범위가 넓어졌습니다. 입출력과 검사 기준은 그대로 두고, 빈 함수 하나로 범위를 돌리겠습니다.”라고 말한다. 채팅에 `입력·테스트·다른 함수 변경은 제외하고 check_link만 다시 제안해 주세요.`를 보내고 변경 비교를 다시 확인한다.

> [부분 수정 분기 · 비낭독] 실제 오류가 있으면 해당 줄과 이유를 말한 뒤 `이 조건에서 빈 문자열 두 개가 확인으로 통과합니다. 값의 존재를 먼저 확인하도록 check_link 안의 해당 조건만 고쳐 주세요.`처럼 실제 문제에 맞는 요청을 한다. 오류가 없으면 “정한 조건과 맞으므로 이 함수 변경을 적용하겠습니다.”라고 말한다. 일부러 잘못된 응답을 연출하지 않는다. 검토한 변경만 적용하고 파일을 저장한다.

이 검사 코드는 로컬 파일만 읽으며 서버나 모델을 호출하지 않습니다. 지금 코드를 검토하는 Copilot 대화와 검사 프로그램의 실행은 별개입니다.

코드를 저장하겠습니다. 제안이 그럴듯한 것과 실제 입력에서 기대한 결과를 내는 것은 다릅니다. 이제 터미널에서 실행해 확인하겠습니다.

## 3. 첫 입력 실행하고 결과 해석하기

> [화면 03-03] 시작코드에서 구현한 함수의 실행 출력과 새 결과 JSON.
> [조작] VS Code 터미널을 연다. 현재 위치가 `시작코드`이고 `trace_records.py`, `recorded`가 그 아래 있는지 확인한다. `python trace_records.py`를 실행한다. `result/trace_result.json`을 연다. 폴더가 다르면 파일 탐색기 경로와 대조해 시작코드로 이동한다. 기존 완성본 result와 혼동하지 않는다.

터미널을 열고 현재 위치부터 확인하겠습니다. 지금 수정한 파일과 입력 폴더가 있는 시작코드 위치에서 실행해야 합니다. 첫 명령은 기본 입력을 읽어 결과를 저장합니다.

실행 전에 예상부터 적겠습니다. 원본 발췌에서는 작업지시의 판단 참조가 판단 식별자와 같습니다. 첫 연결은 확인이어야 합니다. 나머지 두 연결은 필요한 직접 참조나 독립된 사건 원문이 부족하므로 미확인으로 예상합니다.

> [실행 결과 분기 · 비낭독] 실제 출력을 읽는다. 예상대로 확인 1개·미확인 2개이면 아래 해석을 이어 간다. `NotImplementedError`면 저장한 파일과 실행 경로, 빈 함수가 남았는지 확인한다. 파일 없음이면 작업 폴더와 입력 경로를 확인한다. 판정이 다르면 해당 연결의 입력값과 함수 조건을 대조하고, 실제 출력·예상·관련 함수만 채팅에 붙여 한 조건의 원인을 질문한다. 수정 후 같은 명령으로 다시 확인한다. 오류가 난 상태에서 아래 정상 결과 발화를 읽지 않는다.

첫 연결은 확인이고, 나머지 두 연결은 미확인입니다. 결과 파일의 두 값을 입력과 다시 대조하겠습니다. 전체가 미확인인 것은 프로그램이 멈췄다는 뜻이 아닙니다. 현재 자료만으로 모든 연결을 입증하지 못했다는 판정입니다.

context에 사건과 경보의 식별자가 함께 있더라도 없는 직접 참조를 대신 만들 수는 없습니다. 다음에 필요한 것은 판단이 사건을 가리키는 항목, 그리고 사건이 경보를 가리키는 항목을 확인할 수 있는 원문입니다. 제공 자료에서 못 찾은 것과 실제 시스템에 연결이 없다는 결론은 구분하겠습니다.

## 4. 두 번째 입력과 경계 조건으로 응용하기

> [화면 03-04] 교육용 가림 입력의 예상, 두 번째 결과, 네 테스트, 필요한 부분 수정.
> [조작] `recorded/case_a_redacted.json`을 열어 첫 입력과 비교한다. 이어 터미널에서 `python trace_records.py recorded/case_a_redacted.json --output result/redacted_result.json`, `python -m unittest -v`를 순서대로 실행한다. 두 번째 입력을 첫 결과 경로에 덮어쓰지 않는다.

두 번째 입력에서는 작업지시의 판단 참조 하나를 가렸습니다. 교육용으로 만든 파생 자료이지 실제 시스템에서 참조가 누락된 사례는 아닙니다. 이번에는 첫 연결도 미확인으로 바뀌어 세 연결 모두 미확인이어야 합니다. 예상이 정해졌으니 다른 파일 이름으로 결과를 저장하겠습니다.

> [결과 분기 · 비낭독] 실제 가림 결과를 읽고 원본 결과와 비교한다. 첫 연결이 확인이라면 누락을 우회하거나 context에서 채우는 코드가 있는지 점검한다. 실제 차이를 첨부해 `원본은 첫 연결 확인, 가림 입력은 미확인을 예상했습니다. 실제 차이를 보고 제 조건 중 어느 부분을 확인할지 질문해 주세요. 입력 자료는 고치지 마세요.`라고 요청하고 필요한 함수 부분만 수정·저장·재실행한다. 예상과 맞으면 그대로 비교를 정리한다.

다음은 네 가지 입력을 자동으로 확인하는 테스트입니다. 원본에서 한 연결만 입증되는지, 다른 판단 식별자는 거부하는지, 참조가 없을 때 주변 정보로 추정하지 않는지, 빈 문자열 두 개를 연결로 인정하지 않는지 확인합니다.

다른 식별자를 넣은 경우에는 연결 판정이 실패여야 합니다. 그 실패를 예상대로 찾아내면 테스트는 통과합니다. 연결이 실패한 것과 테스트 자체가 실패한 것은 서로 다릅니다.

> [테스트 분기 · 비낭독] 네 테스트의 실제 통과·실패를 읽는다. 실패가 있으면 그 테스트 하나의 기대값·실제값과 함수만 첨부하고 원인 설명을 요청한다. 강사가 설명을 검토한 뒤 필요한 조건만 수정·저장하고 두 실행 명령과 테스트를 다시 확인한다. 모두 통과하면 “정해 둔 네 입력에서 기대한 판정이 나왔습니다.”라고 말한다. 통과 개수·응답 내용은 실제 결과를 따른다.

이 검사는 정해 둔 입력에서 코드가 어떤 판정을 내리는지 확인합니다. 테스트가 통과해도 자료에 없는 사건 연결까지 입증된 것은 아닙니다. 코드의 동작과 사건의 근거를 별도로 적겠습니다.

## 5. 판단의 한계까지 정리하기

> [화면 03-05] 연결표, 직접 구현한 코드, 두 결과, 테스트 관측, 추가로 필요한 원문.
> [조작] 실습 폴더의 `연결표.md`를 열어 비교 필드·값·판정·원본 위치를 정리한다. 구현한 시작코드와 그 result를 연결한다. 실제 관측한 결과만 적고 미해결 항목을 남긴다.

마지막으로 연결표를 정리하겠습니다. 비교한 필드와 값, 판정, 원본 위치를 함께 남깁니다. 두 입력에서 어떤 참조가 달라졌고 결과가 어떻게 바뀌었는지도 적겠습니다.

제공된 작업지시는 배정됨 상태이고 완료 시각은 없습니다. 이 도구가 확인하는 것은 참조의 연결입니다. 명령 응답이나 유온 완화, 실제 정비 완료를 대신 판정하지 않습니다.

근거가 부족한 곳을 찾아 미확인이라고 설명한 것도 이번 검토의 결과입니다. 전체 추적을 완료했다고 바꾸기보다 어디까지 확인했고 어떤 원문이 더 필요한지 남기겠습니다. 이제 그 판단에 쓰이는 지식과 원인별 조치의 관계를 살펴보겠습니다.
