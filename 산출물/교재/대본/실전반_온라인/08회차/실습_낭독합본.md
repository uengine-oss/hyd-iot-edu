# 실전반 8회차 — 업무명세


## 제조 업무의 요청과 프로젝트 확인

앞에서 근거를 확인한 제안과 사람의 결정을 구별했습니다. 이번에는 생산관리와 설비보전이 정기 점검 시점을 정하려고 합니다. 생산 일정과 정비 준비 상태를 대조해, 회의에서 결정할 안건과 시간 후보를 제시하는 에이전트를 만들겠습니다. 실습 코드를 받아 압축을 풀고 VS Code에서 열겠습니다.

제가 받은 것은 업무 요청입니다. 이 프로젝트의 내부 구성은 아직 모르니 현재 자료와 준비된 기능부터 확인하겠습니다.


도우미가 찾은 자료를 열어 보겠습니다. 회의에서 야간을 검토하자는 의견은 있었지만 확정은 아니었습니다. 생산 시간과 정비 자원은 다른 기록에 있으므로 회의록만 요약해서는 후보를 결정할 수 없습니다.

## 판단할 조건을 명세로 만들기

먼저 정비 소요 시간, 끝내야 할 기한, 생산에 사용하는 시간, 부품과 작동유·인력의 준비를 구별하겠습니다. 시간은 날짜와 시간대를 포함해서 비교합니다. 재고가 두 개여도 다른 작업에 예약된 수량을 빼야 이번 작업에 쓸 수 있는지 알 수 있습니다.

spec.md에 입력과 출처, 판단 조건, 산출물과 사람 검토 범위를 적겠습니다. 후보마다 적합·제외·보류와 이유를 남기고, 적합한 후보가 있을 때만 추천합니다. 확정된 제외 사유가 있어도 아직 확인하지 못한 조건은 함께 남기겠습니다.


‘잘 정리한다’는 표현 대신 원문으로 확인할 조건을 남기겠습니다. 안건에는 결정할 질문과 그 이유가 있어야 합니다. 이미 끝난 점검표 배포를 새 작업으로 만들거나, 제안만 된 대체 생산을 승인된 것으로 취급하면 요구를 충족하지 못합니다.

## 최초 요청과 후속 요청 구분

최초 요청에서는 준비 상태가 확인되지 않은 자원이 있습니다. 나중에 그 확인 자료를 받았을 때 같은 요청을 다시 검토해야 합니다. 앞 보고서는 보존하고 무엇이 어떤 근거로 바뀌었는지 비교하도록 명세에 넣겠습니다. 날짜가 새롭다는 이유만으로 모든 조건을 덮어쓰지 않습니다.


명세와 요청, 출처 목록을 저장하고 다시 열겠습니다. 다음 단계에서는 이 질문에 답할 지식 구조를 만들고, 바뀌는 상태는 별도의 입력으로 이어 쓰겠습니다.


# 실전반 8회차 — 지식구조


## 앞 명세를 지식으로 연결하기

앞에서 정한 점검 조율 명세를 이어 쓰겠습니다. 이번 자료를 열고 앞 요청·명세·출처 목록을 input에 가져오겠습니다. 빈 양식으로 앞 결과를 덮어쓰지 않습니다.

## 질문과 지식·현재 정보 나누기

어떤 기준으로 시간 후보를 비교하는지, 미결 안건이 어느 회의 기록에서 나왔는지, 담당 역할이 무엇을 확인해야 하는지 질문을 적겠습니다. 회의와 안건·근거 문서, 규칙의 관계를 만들되 창고 수량이나 특정 날짜의 인력 상태를 영구적인 기준으로 넣지는 않겠습니다.


도우미가 제안한 구조에서 ‘회의에서 나온 의견’과 ‘생산 담당이 확인한 상태’가 같은 사실로 합쳐졌는지 보겠습니다. 정비 기한을 설명한 규칙과 후보가 실제 그 기한을 지키는지 계산한 결과도 구별합니다.

## 직접 작성한 구조를 조회로 검증

질문별 조회문을 작성하고 원문에서 적은 답과 비교하겠습니다. 어떤 안건의 근거를 물었는데 관계 이름만 나오거나 출처 없는 설명이 나오면 필요한 연결을 보완해야 합니다. 클래스와 관계의 형식이 맞더라도 서로 다른 대상이 연결될 수 있으므로 개별 식별자도 확인하겠습니다.


조회한 안건에서 원문 절까지 돌아가 보겠습니다. 답이 없으면 입력 누락, 식별자, 관계, 조회 범위 가운데 원인을 찾고 수정 후 같은 질문으로 확인합니다. 지식 파일·조회문·대조 기록을 저장하고 다시 열겠습니다. 다음 에이전트는 이 기준 지식과 시점이 있는 생산·자원 자료를 함께 읽습니다.


# 실전반 8회차 — 제안에이전트


## 기준 지식과 요청 이어 쓰기

앞에서 만든 명세와 지식 구조를 이번 작업 공간의 input에 연결하겠습니다. 이제 정비 시간 후보를 비교하고, 담당자가 결정해야 할 안건을 정리하는 에이전트를 구성합니다.

## 목표·스킬·입출력 계약 작성

목표에는 근거 있는 후보와 추가 확인을 제시한다고 적겠습니다. 스킬에는 기준 지식 읽기, 생산·자원 자료 대조, 조건별 판정, 안건과 보고서 작성 순서를 둡니다. 주간 생산을 옮기자는 제안은 실제 생산 해제의 근거가 아니며, 과거 세척 이력도 이번 점검의 완료 기록이 아닙니다.


포털에 등록된 읽기 서버와 허용 도구를 확인하고 실제 이름과 입력을 연결하겠습니다. 로컬 파일이 포털 서버에서도 자동으로 보이는 것은 아니므로 준비된 읽기 경로를 확인합니다. 승인 카드가 요구하는 후보 식별자와 이유를 맞추고, 안건과 미확인은 보고서에서 잃지 않게 연결하겠습니다. 임의 점수로 후보를 그럴듯하게 순위 매기지 않고 명세의 적합 조건과 종료 시각 순서를 사용합니다.

## 최초 자료의 판단과 근거 대조

먼저 최초 요청을 넣겠습니다. 세 시간 후보가 각각 어떤 조건에서 제외되거나 보류되는지 원문과 대조합니다. 부품 실물에서 예약을 뺀 수량, 자정이 넘어가는 작업의 길이, 완료 기한을 결과에서 다시 계산해 보겠습니다. 도구 호출 성공만으로 판단까지 맞다고 보지는 않습니다.


## 후속 확인을 반영하고 차이 검증

이번에는 같은 요청에 후속 확인 자료를 추가하겠습니다. 작동유와 야간 인력의 확인이 어떤 후보에 적용되는지 봅니다. 생산 계획이나 정비 기한은 바뀌지 않았으므로 그 이유로 제외됐던 후보까지 살아나면 잘못된 처리입니다.

새 보고서와 이전 보고서를 나란히 보겠습니다. 바뀐 판단에는 새 근거가 붙고, 유지된 판단은 기존 근거를 보존해야 합니다. 조건을 충족한 추천도 사람의 계획 검토를 거쳐야 하며 일정 등록이나 설비 정지를 실행한 것은 아닙니다.

목표·스킬·에이전트 ID·도구 계약과 두 판본의 결과를 저장하겠습니다. 다시 열어 원문에서 결론까지 이어지는지 확인한 뒤 이 출력 계약을 업무 흐름에 넘깁니다.


# 실전반 8회차 — 흐름실행


## 앞 에이전트를 업무 흐름으로 연결하기

앞 명세와 에이전트 정의·ID·출력 계약을 이번 작업 공간에 가져오겠습니다. 요청을 받아 자료를 비교하고 담당자가 검토한 뒤 결과를 남기는 흐름을 만들겠습니다. 회의 준비의 결과와 실제 정비 실행은 구별합니다.

## 추천 가능 여부와 사람 검토 나누기

bpmn.io에서 요청 시작, 자료 검토 에이전트, 추천 가능 여부 확인, 담당자 검토, 결과 보고를 연결하겠습니다. 필요한 정보가 없으면 추가 확인을 보고하고, 적합 후보가 있을 때 사람의 계획 검토로 보냅니다. 사람의 거절은 거절 이유를 보고하는 경로로 닫겠습니다. 보류 보고가 끝나도 정비 계획이 확정됐다는 뜻은 아닙니다.


그림을 저장하고 다시 열어 보류·검토·거절의 길을 확인하겠습니다. 다음으로 포털에서 앞 에이전트와 담당 역할, 보고 부품을 실제 요소 ID에 연결합니다. 기존 냉각 대응 흐름을 그대로 덮어쓰지 않고 별도 정의로 관리하겠습니다.

## 검사와 두 입력 판본의 처리 확인

사전 검사에서 나온 위치와 사유를 읽고 현재 그림과 매핑을 고치겠습니다. 검사한 판본을 등록하고 수업 환경에서 요청을 시작합니다. 첫 자료와 후속 자료의 처리 기록은 같은 업무 요청에 속하더라도 별도 실행 기록으로 보존하겠습니다.

최초 자료에서 확인이 남는다면 보고에 그 이유가 있어야 합니다. 후속 자료로 추천이 가능해졌다면 실제 후보와 근거를 확인한 뒤 담당자가 검토합니다. 승인·거절 뒤 보고에 전달된 값이 앞 에이전트의 어떤 판본인지 확인하겠습니다. 요청 번호만 같고 서로 다른 자료를 섞지 않아야 합니다.


마지막으로 보고에서 일정 등록·메일 발송·정비 오더·현장 작업이 실행된 것처럼 표현되지 않았는지 확인하겠습니다. BPMN과 매핑, 명세·에이전트 정의, 두 자료 판본의 기록을 저장하고 다시 열겠습니다. 다음 제품 비교에서도 이름보다 이 역할과 기록의 연결을 보겠습니다.

## 시연에서 확인할 기준 작성하기

관찰표에 지식, 에이전트, 프로세스 정의, 실행 인스턴스, 사람 작업, 결과 제출을 먼저 적겠습니다. HYD에서 이 역할이 어디에 있었는지 앞 기록의 번호를 연결합니다. 이어서 수업에 준비된 제품의 주소와 판본, 계정에서 접근 가능한 범위를 확인합니다. 접속이나 권한이 준비되지 않았다면 실제 시연은 미확인으로 두고 제공 설명을 실제 화면을 본 것처럼 읽지 않겠습니다.

## 정의와 실행 한 건을 따라 보기

준비된 제품 화면에서 사용할 정의를 열고 작업 담당과 입력·결과 계약을 확인하겠습니다. 실행되는 인스턴스 한 건을 골라 현재 누구 차례인지, 에이전트가 결과를 내면 누가 다음 작업을 여는지, 사람에게 맡긴 작업은 어디에 모이는지 따라갑니다. 직접 새 실행을 하는 경우에는 수업용 읽기·제안 범위와 사람 확인 조건을 먼저 확인합니다.

화면에서 확인한 이름과 상태, 근거 위치를 관찰표에 직접 적습니다. 자연어로 만든 정의나 여러 에이전트 기능이 보이더라도 생성된 설계가 명세와 승인 조건을 지키는지 별도로 봅니다. 소개 문구와 실제 확인한 기능을 같은 칸에 적지 않겠습니다.

## 차이와 미확인을 고쳐 기록하기

HYD와 이름이 다르면 역할과 입출력을 대조해 대응을 수정합니다. 완료 표시가 보여도 한 일과 하지 못한 일은 결과 기록에서 확인합니다. 권한, 감사 추적, 실패 처리 가운데 이번 화면에서 확인하지 못한 것은 미확인으로 남깁니다. 특정 메뉴가 없다는 이유만으로 제품 전체에 그 기능이 없다고 단정하지 않습니다.

관찰표와 비교한 정의·인스턴스 식별자, 자료 출처를 저장하겠습니다. 다시 열어 설명만 읽은 항목과 실제 화면에서 확인한 항목이 구분되는지 봅니다. 이 기록을 마지막 학습 노트에 연결하겠습니다.

## 내 문장으로 지식 노트 쓰기

knowledge-note.md에 지식·제안·승인·실행·완료의 구분을 제 문장으로 적겠습니다. 각 개념에는 참고 문서의 절과 이번에 만든 파일을 연결하고, 그 파일의 확인 결과와 미확인 범위를 붙입니다. ‘작동했다’는 말만 남기지 않고 어떤 입력과 판본을 어떤 기록으로 확인했는지 적겠습니다.

코딩 도우미에는 실제 산출물 목록과 확인 기록만 제공해 연결 초안을 정리하도록 요청합니다. 없는 실행을 만들어 넣거나 참조 예제의 결과를 내 작업 성과로 섞지 않았는지 제가 대조합니다. 잘못된 링크나 판본은 고치고 다시 열어 확인하겠습니다.

## Notion에 기록하고 되짚기

수업 계정에서 Notion MCP 연결과 쓰기 대상의 권한을 사전에 확인한 경우에는 그 대상에만 기록하는 시연을 하겠습니다. 연결이 준비되지 않았으면 준비한 Markdown을 Notion에 직접 붙여 정리합니다. 로컬 파일 링크가 다른 기기에서도 자동으로 열리는 것은 아니므로, 필요한 산출물을 해당 학습 공간에 첨부하고 링크를 실제 첨부 자료로 바꿉니다.

저장한 페이지를 다시 열어 개념에서 출처로, 산출물에서 검증 근거로 찾아갑니다. 첨부가 빠졌거나 접근할 수 없으면 파일과 권한을 바로잡고 다시 확인합니다. 쓰기나 다시 열기를 못 했다면 로컬 초안 작성과 Notion 반영 완료를 구분해 남기겠습니다.

## 과정 마무리

로컬 노트와 자료 목록, 실제 저장한 페이지 위치, 남은 확인 항목을 보존하겠습니다. 이번에 할 수 있게 된 범위와 아직 연결이 필요한 부분을 구분한 뒤 복습과 퀴즈로 돌아갑니다. 다음에 같은 업무를 다시 맡을 때 이 자료에서 기준과 근거를 찾아 시작할 수 있게 남기겠습니다.
