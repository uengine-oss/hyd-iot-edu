# 실전반 5회차 실습 1 — 승인과거절


## 자료 다운로드와 승인 대상 확인

승인과거절 ZIP을 내려받아 압축을 풀고 VS Code에서 코드 폴더를 열겠습니다. review.md에 교육 환경, 준비된 작업 번호와 승인 역할을 적을 자리가 있습니다. 수업용 HYD 포털을 열고 준비된 연습 작업의 추천안, 근거와 현재 상태를 읽겠습니다. 실제 설비 명령이 연결되지 않은 교육용 대상인지 확인합니다.

## 승인과 거절을 각각 확인하기

먼저 승인 역할이 배정된 계정과 그 역할을 확인합니다. 승인할 수 없는 역할에서는 결정 기능이 제한되는지 보고, 권한을 임의로 바꾸지 않겠습니다. 승인 가능한 연습 건에서는 추천안과 현재 조건을 확인한 뒤 승인합니다. 누가 어떤 역할로 무엇을 결정했는지 기록을 열고, 승인 뒤의 상태와 후속 작업을 확인하겠습니다. 승인 기록과 실제 후속 실행 결과는 구별해서 적습니다.

이번에는 별도로 준비된 동등한 연습 건에서 거절하겠습니다. 거절 사유와 종료 상태를 확인하고 이후 작업이나 명령이 생성됐는지 기록으로 봅니다. 이미 처리한 건을 되돌려 재사용하지 않습니다. 검토 의견이나 가드레일 통과만으로 사람의 결정이 생긴 것으로 읽지 않겠습니다.

## 기록 저장과 재확인

두 건의 입력, 역할, 결정과 처리 결과를 review.md에 남기고 다시 열어 비교합니다. 기대와 다르면 권한·현재 조건·결정 기록·후속 처리 순으로 확인하고 미확인은 그대로 적겠습니다. 이 기록을 다음 질문 실습에서 정보 답변과 승인 결정의 차이를 확인하는 기준으로 쓰겠습니다.


# 실전반 5회차 실습 2 — 확인질문과재처리


## 다운로드와 기존 프로젝트 열기

확인질문과재처리 ZIP을 내려받아 압축을 풀겠습니다. 지난 회차에 직접 만든 원인 추론 에이전트 프로젝트를 별도 사본으로 보존하고 VS Code에서 그 사본을 열겠습니다. 이번 자료의 source를 추가하고 새 output 폴더를 마련합니다. 제공된 완성 에이전트를 새로 실행하는 것이 아니라 앞서 만든 기능에 요청 확인 단계를 붙입니다.

source/입력/점검_요청.json의 요청 번호와 설비, 경보 패턴, 사례 필드를 읽습니다. source/사람/답변.json은 교육용 답변 입력이고 실제 승인 기록이 아닙니다. 기존 에이전트가 받는 cases.json 구조와 새 요청 구조는 다를 수 있으므로, 요청에서 사례 ID를 찾은 뒤 기존 입력으로 연결하는 부분을 먼저 확인하겠습니다. 원본 필드 이름을 몰래 바꾸지 않습니다.

## 부족한 정보를 묻는 단계 만들기

코딩 도우미에게 이렇게 요청하겠습니다. 기존 원인 추론 기능을 유지하고 요청 처리 단계를 더해 주세요. 요청 번호로 상태를 보관하고, 설비·경보·사례 중 판단에 필요한 정보를 입력과 참조 자료에서 확인하세요. 참조로 확인할 수 없는 값만 질문하고 보류하세요. 답이 오면 같은 요청에 연결해 다시 확인하고 기존 분석으로 넘기세요. 답변으로 승인이나 권한을 만들지 마세요. 확인하지 못한 값은 추정하지 마세요.

output/requests.json에는 상태, 확인 질문, 받은 답과 근거, 다음 처리 여부를 남기게 하겠습니다. 코드에서 누락 값이 기본 설비나 0으로 바뀌지 않는지 읽습니다. 요청 번호가 다른 답을 섞지 않도록 하고, 답이 부족하거나 맞지 않으면 추가 확인 상태를 유지하도록 하겠습니다.

## 질문 전후를 같은 요청으로 비교하기

R01처럼 정보가 빠진 요청을 먼저 넣어 필요한 확인 질문과 보류 상태를 보겠습니다. 제공 답변을 읽고 해당 요청에 대응하는 값만 입력한 뒤 재처리하겠습니다. 답변 파일에 대응 값이 없으면 임의로 채우지 않고 질문 상태를 기록합니다. 답을 받은 뒤 원인 후보와 근거가 기존 분석으로 이어지는지도 확인합니다.

R02처럼 사례 ID로 확인 가능한 값이 있는 경우에는 참조한 원문을 남기고 불필요한 재질문이 없는지 보겠습니다. R04처럼 단서가 부족한 경우에는 진행을 보류해야 합니다. ‘급하니 승인한 것으로 처리’라는 답변을 별도 연습 입력으로 넣어도 정보만 받고 승인은 별도 단계로 남는지 확인하겠습니다. 로컬의 연습 상태는 HYD의 실제 승인 권한이 아닙니다.

## 저장과 이어 쓰기

질문 전후 입력, 요청별 상태와 실제 결과, 수정과 재확인을 저장하겠습니다. 파일을 다시 열어 다른 요청의 답이 섞이지 않았는지 봅니다. 이 프로젝트의 판본을 남기고 다음 명세 실습에서 그대로 확장하겠습니다.


# 실전반 5회차 실습 3 — 명세에따른요구사항추가


## 다운로드와 변경 전 상태 보존

명세에따른요구사항추가 ZIP을 내려받아 압축을 풀고 앞 실습의 프로젝트를 VS Code에서 열겠습니다. 변경 전 파일과 입력, 실제 확인 기록을 별도 보존하겠습니다. 이번 자료의 source/기존_비교기록은 모호한 요청을 세 사본에 보냈던 제공 기록입니다. 이번에 실행한 결과와 구별해서 읽습니다.

요청.txt와 변경 전 요청_처리.json, 각 사본의 출력과 바뀐 파일 목록을 비교하겠습니다. 출력 항목, 일반 요청의 상태, 승인 조건이 달라진 부분을 review.md에 적습니다. 일부만 바뀐 파일이므로 없는 파일을 삭제된 것으로 읽지 않습니다. 모호한 요청이 항상 실패한다거나 세 결과가 모든 경우를 대표한다고 결론 내리지 않겠습니다.

## 명세를 먼저 작성하기

현재 프로젝트의 입력과 출력 구조를 읽고 spec.md를 작성하겠습니다. 목표, 입력, 출력, 금지 조건과 수용 기준을 나눕니다. 기존 일반 요청의 결과 항목과 뜻, 정보 누락 시 보류, 승인 없이 업무를 확정하지 않는 조건을 먼저 적겠습니다.

추가 요구는 교육용 기준으로 판단할 때의 유온이 섭씨 60도 이상이면 긴급 여부를 참으로 표시하는 것입니다. 다른 자료의 임계값이나 실제 설비 안전 기준을 바꾸는 것은 아닙니다. 어떤 태그·집계·시간 창의 값을 쓸지 입력 자료에 맞춰 명시하겠습니다. 값이 없거나 유효하지 않으면 긴급 여부를 추정하지 않고 보류합니다. 긴급 표시가 생겨도 승인 절차와 일반 요청의 출력 계약은 유지합니다.

수용 기준에는 같은 입력과 자료에서 일반 요청의 기존 결과가 유지되는지, 긴급 입력에 표시가 추가되는지, 누락이면 보류하는지, 거절이면 후속 업무가 없는지를 적겠습니다. 실행 번호와 시각은 값 자체의 동일성 대신 형식·연결 관계를 검사하도록 정합니다. 출력에 필드를 더할 때 기존 소비자가 이를 받아들일 수 있는지도 확인하겠습니다.

## 명세에 맞춰 구현하고 비교하기

코딩 도우미에게 spec.md를 읽고 필요한 부분만 고치도록 요청하겠습니다. 기존 일반 요청 처리와 질문 단계, 승인 조건을 보존하고 긴급 여부와 그 근거를 추가해 주세요. 임계값과 입력 검사를 명세와 맞추고, 기존 출력 이름과 뜻은 유지해 주세요.

수정된 파일을 비교해 관련 없는 변경이 없는지 읽고, 수업 환경에서 일반·긴급·누락 입력을 같은 조건으로 확인하겠습니다. 새 기능만 보지 않고 변경 전 일반 요청의 결과와 대조합니다. 기대와 다르면 차이를 먼저 기록한 뒤 코드와 명세 중 실제 원인이 있는 곳을 확인합니다. 검사에 맞추려고 기존 기대값을 바꾸지 않겠습니다.

## 다음 검증의 재료 저장

spec.md와 구현 판본, 입력, 조회 자료, expected.json에 직접 적은 기대 결과, 실제 결과를 저장하겠습니다. 가상 경계 입력은 복사본에만 만들고 원본과 구별합니다. 다시 열어 각 수용 기준에 대응하는 입력과 기대가 있는지 확인하겠습니다. 이어서 이 프로젝트를 시나리오와 반복 검증으로 확인하겠습니다.


# 실전반 5회차 실습 4 — 기존기능과추가기능검증


## 다운로드와 같은 프로젝트 확인

기존기능과추가기능검증 ZIP을 내려받아 압축을 풀고 앞 실습의 프로젝트를 VS Code에서 열겠습니다. spec.md와 입력, 기대 결과, 구현 판본이 서로 같은 버전인지 확인하겠습니다. 이번 자료의 scenarios.md와 review.md는 빈 작성 양식입니다. 이미 통과한 결과가 아닙니다.

## Given·When·Then 작성하기

일반 요청, 긴급 요청, 필수 정보 누락, 승인 거절을 각각 적겠습니다. Given에는 입력과 조회 자료, 권한과 상태를, When에는 요청 처리나 결정 동작을, Then에는 출력 항목과 상태, 후속 작업의 유무를 적습니다. ‘잘 처리된다’ 대신 실제로 가를 조건을 쓰겠습니다.

긴급 기준 바로 아래와 정확히 60도인 입력도 복사본으로 준비하겠습니다. 명세의 태그와 집계·시간 창이 같은지 먼저 확인합니다. 없는 값을 0으로 해석하지 않는지, 질문에 답해도 승인까지 생기지 않는지도 넣겠습니다. 기대 결과는 실행하기 전에 명세와 맞춰 적고 파일로 저장합니다.

## 실행 가능한 검사와 반복 비교

코딩 도우미에게 시나리오를 검증 코드로 연결하도록 요청하겠습니다. 각 검사에 입력과 기대를 연결하고, 실패하면 사례 이름과 실제 차이를 표시해 주세요. 실제 외부 명령은 보내지 않는 교육용 경계를 사용하고 그 경계가 확인하지 못하는 범위도 남겨 주세요. 기존 출력 계약과 승인 거절 조건은 새 긴급 기능과 함께 검사해 주세요.

검사 코드를 먼저 읽고 수업 환경에서 실행하겠습니다. 같은 입력·자료·설정으로 반복해 확인하고 실행별 결과를 남깁니다. 설명 문장이 달라도 의미와 근거가 맞으면 그 차이만으로 실패로 세지 않습니다. 필수 항목 누락, 근거 없는 단정, 승인 조건 위반은 구별해 실패로 기록하겠습니다. 단순한 반복 통과를 모든 상황의 정확성으로 바꾸지 않겠습니다.

## 실제 실패를 고치고 회귀 확인하기

실패가 있으면 입력 연결, 조회 값, 판단 규칙, 출력 생성 순서로 기록을 대조하겠습니다. 확인한 원인을 수정하고 해당 시나리오를 다시 검사한 뒤 일반 요청과 거절을 포함한 기존 검사도 모두 실행합니다. 실패가 없으면 일부러 실패를 만들지 않고 확인한 조건과 범위를 기록합니다.

로컬에서 승인 상태를 흉내 낸 검사는 실제 HYD 권한 검증을 대신하지 않습니다. 포털에서 확인한 승인 기록과 로컬 검사 결과를 구별하고, 외부 연동 미검증은 그대로 남기겠습니다.

## 결과 저장과 전체 정리로 연결

시나리오, 기대값, 실제 결과와 실패 기록, 수정 내역, 재검사 결과와 남은 미확인을 저장하겠습니다. 파일을 다시 열어 같은 판본의 결과인지 확인합니다. 이제 목표·도구·스킬·사람의 결정·명세·검증이 어떻게 이어지는지, 이번 기록을 바탕으로 전체 흐름을 정리하겠습니다.
