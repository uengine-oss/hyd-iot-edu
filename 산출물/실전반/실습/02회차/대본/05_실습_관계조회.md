# 실전반 2회차 실습 1 — 그래프의 관계 조회

> 강사 단독 진행. 조작·입력·확인 분기는 낭독하지 않는다. 아래 결과 표현은 직접 확인한 경우에만 사용한다. 제공 예제 적재·조회는 실행 검증했다. 브라우저 조작·촬영은 별도 확인한다.

## 자료를 내려받고 작업 공간 열기

앞 이론에서는 그래프의 연결을 사이퍼로 조회하는 방법을 배웠습니다. 이번에는 쿨러 점검에 필요한 센서와 기준값, 교체 부품을 찾아보겠습니다. 필요한 정보에 맞춰 경로와 조건을 정하고, 나온 결과가 원자료와 맞는지 확인하겠습니다.

실습 시작 도구에서 실전반, 온라인 2회차, 관계 조회를 선택해 새로 시작하겠습니다. 열린 폴더의 START.md에서 준비 절차를 확인하고, 이 폴더의 터미널에서 예제 준비 명령을 실행하겠습니다.

> [조작] 해당 항목 선택 → 새로 시작 → 작업 폴더·START.md 확인 → Docker 실행 상태에서 `python prepare_example.py` 실행. VS Code 기본 UI 소개는 하지 않는다. 실제 준비 결과를 기다린다.

> [결과가 표시된 뒤 발화] 노드 20개와 관계 19개가 준비됐습니다. 브라우저를 여는 명령을 실행하고, 출력된 주소로 접속하겠습니다.

> [조작] `python lab_db.py` 실행 → 출력의 Browser 주소와 Bolt 값을 보여 줌 → Browser로 전환. 학생별 포트는 실행 결과를 사용한다.

## Neo4j Browser에서 연결하고 화면 살펴보기

실습 안내의 링크를 열면 이렇게 접속 정보를 확인하는 창이 나옵니다. 지금 열린 도구가 Neo4j Browser입니다. 먼저 실습 데이터베이스에 연결하겠습니다.

> [조작] `랩_연결.json`의 browser 링크를 그대로 열고 자동 표시된 연결 창에서 시작한다. 주소는 현재 연결 파일의 connectURL이 포함된 값을 사용한다. 포트 번호를 이전 촬영값으로 고정하지 않는다. 기존 결과가 남은 화면을 첫 접속으로 사용하지 않는다. 연결 창을 닫았다가 다시 여는 조작을 추가하지 않는다. 아래 발화는 실제 미리 채워진 값과 터미널 출력을 대조한 뒤 사용한다.

접속 정보가 이미 들어 있네요. 프로토콜은 볼트이고, 그 옆이 연결할 주소입니다. 터미널에 나온 실습 DB 주소와 맞는지 확인하겠습니다. 사용자 이름은 네오포제이입니다. 이번 실습 DB는 비밀번호 없이 연결하도록 준비했으니 이 칸은 비워 두고, 아래 Connect를 누르겠습니다.

> [조작] 자동 입력된 Protocol `bolt://` → Connection URL → Database user `neo4j` → Password 빈칸을 차례로 가리켜 확인 → Connect 클릭. 맞는 값을 다시 입력하지 않는다. 실제 연결 성공 전 다음 발화를 하지 않는다. 처음 안내창은 아래 화면 정리 구간에서 설명하며 닫는다.

> [연결 후 발화] 왼쪽 위에 접속 주소와 데이터베이스 이름이 나타났습니다. 방금 준비한 실습 DB에 연결된 상태입니다. 포털의 지식 지도와는 별도이므로 여기에서 하는 조회가 포털 화면을 바꾸지는 않습니다.

> [촬영 준비] 새 실습을 시작하기 전에 이전 시연의 쿼리·결과·오류 카드와 입력을 비우고 메뉴를 닫는다. 학생 링크의 자동 연결 창에서 시작한다. 연결 뒤 새로 나타나는 소개 카드는 아래 안내와 함께 다루며, 이전 시연 결과와 혼동하지 않는다. 이어 찍는 장면은 직전 학습 결과와 패널 상태를 유지한다.

새 탭 기능을 알려 주는 안내가 나왔네요. 이번에는 스트림에서 쿼리를 실행할 거라, 디스미스를 눌러 닫겠습니다.

> [조작] 처음 안내가 나타난 경우에만 Dismiss를 누른다. 이미 닫힌 이어 찍기에서는 이 문장과 조작을 반복하지 않는다.

아래에는 소개 카드와 연결 결과가 있습니다. 쿼리 결과를 보기 편하도록 화면만 정리할게요. 위쪽 입력칸에 콜론 클리어를 적고 엔터를 누르겠습니다. 데이터는 그대로 두고 화면의 카드만 비우는 명령입니다.

> [조작] 위쪽 입력칸 클릭 → `:clear` 입력 → Enter. 명령이 남으면 입력칸을 비운다. 새 실습을 시작하기 전의 이전 시연 정리와 구분한다.

왼쪽 맨 위의 원통 모양 버튼이 데이터베이스 오버뷰입니다. 여기를 눌러 준비된 데이터의 종류를 확인하겠습니다.

> [조작] 왼쪽 패널이 접힌 경우 Open Sidebar를 안내하며 연 뒤 Database overview 클릭. 노드20·관계19 확인.

> [데이터 정보가 나온 뒤 발화] 여기에 보이는 레이블은 노드의 종류이고, 관계 유형은 노드를 잇는 연결의 종류입니다. 이론에서 본 구성 요소와 센서를 실제 예제에서도 구분해 둔 거예요. 이 목록의 이름을 쿼리에 사용하게 됩니다.

위쪽의 달러 표시 옆이 쿼리 입력칸입니다. 문장을 적고 오른쪽 Run을 누르면 아래에 결과가 생깁니다. 결과가 표라면 열 제목은 요청한 항목이고, 한 행은 조건에 맞게 찾은 조합입니다. 노드와 관계 자체를 요청하면 그래프로 연결을 볼 수도 있어요. 먼저 표로 센서 식별자와 태그를 확인한 뒤 그래프로 바꿔 보겠습니다.

> [조작] 입력칸 → Run → 결과가 나타날 아래 영역을 차례로 가리킨다. 첫 조회까지 왼쪽 패널을 유지한다. 실제 폭이 부족해 접어야 할 때만 “쿼리를 넓게 보려고 왼쪽 패널을 접겠습니다. 이 버튼으로 다시 펼칠 수 있어요”라고 말하며 접는다. 화면 밖에서 미리 접지 않는다.

이제 쿨러에 연결된 센서를 찾아볼게요. 위쪽 입력칸을 누르겠습니다.

## 쿨러 점검에 필요한 센서 확인하기

쿨러의 상태를 확인하려면 어떤 센서를 봐야 하는지부터 찾겠습니다. 매치에 쿨러에서 센서로 이어지는 패턴을 넣고, 리턴에는 점검할 센서의 식별자와 태그를 받겠습니다. 같은 이름의 다른 장치가 섞이지 않도록 고유 식별자를 쓰겠습니다.

> [조작] 위쪽 입력칸에 아래 문장을 작성한다. 줄바꿈은 Shift+Enter. 입력 중 커서는 글자를 가리지 않는 아래 여백에 둔다.

```cypher
MATCH (c:Component {id:'comp:cooler'})-[:MONITORED_BY]->(s:Sensor)
RETURN c.name AS component, s.id AS sensor_id, s.tag AS tag
ORDER BY s.tag;
```

오른쪽 런을 눌러 실행하겠습니다.

> [조작] Run 클릭 → 실제 결과 2행 확인 뒤 해석한다.

> [결과 확인 뒤] 씨이와 티에스원, 두 센서가 나왔습니다. 쿨러 이름이 두 번 나오지만 같은 쿨러에 연결된 두 센서입니다. 연결 방향도 그림에서 확인해 볼게요.

## 표의 연결을 그래프로 확인하기

같은 패턴의 관계에 알이라는 이름을 붙이고, 리턴에는 씨, 알, 에스를 넣겠습니다. 속성값 대신 노드와 관계 자체를 돌려받는 문장입니다.

> [조작] 위쪽 입력칸에 아래 문장을 작성한다. 줄바꿈은 Shift+Enter. 입력 중 커서는 글자를 가리지 않는 아래 여백에 둔다.

```cypher
MATCH (c:Component {id:'comp:cooler'})-[r:MONITORED_BY]->(s:Sensor)
RETURN c,r,s;
```

런을 눌러 그래프를 보겠습니다.

> [조작] Run 클릭 → 그래프 렌더와 Nodes (3), Relationships (2) 확인 뒤 해석한다.

> [결과 확인 뒤] 쿨러에서 센서 두 개로 연결돼 있습니다. 방금 표에서 확인한 두 행을 이 연결로 읽을 수 있네요. 이제 확인할 물리량까지 따라가겠습니다.

## 확인할 물리량과 기준값 좁히기

앞 결과 카드는 비우고 다음 조회를 보겠습니다. 센서 이름만으로는 어떤 값을 확인해야 할지 알 수 없습니다. 설비에서 구성 요소와 센서를 거쳐 물리량까지 연결하고, 태그와 물리량, 단위, 한계를 함께 받겠습니다.

> [조작] `:clear`로 앞 결과 카드를 비운 뒤 위쪽 입력칸에 아래 문장을 작성한다. 줄바꿈은 Shift+Enter. 입력 중 커서는 글자를 가리지 않는 아래 여백에 둔다.

```cypher
MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)-[:OBSERVES]->(v:StateVariable)
RETURN s.tag AS tag, v.name AS quantity, v.unit AS unit, v.limit AS limit
ORDER BY tag;
```

런을 눌러 실행하겠습니다.

> [조작] Run 클릭 → 실제 결과 5행 확인 뒤 해석한다.

> [결과 확인 뒤] 다섯 센서의 물리량을 찾았습니다. 한계가 비어 있는 행도 있네요. 연결을 못 찾은 것은 아닙니다. 물리량까지 찾았지만 그 속성값이 없는 거예요. 이 값은 영으로 바꾸지 않겠습니다.

## 한계가 있는 항목만 남기기

이번에 필요한 것은 한계가 등록된 항목입니다. 같은 경로에 웨어를 넣어 한계가 있는 행만 남기겠습니다. 어떤 행이 빠지는지도 함께 보겠습니다.

> [조작] 위쪽 입력칸에 아래 문장을 작성한다. 줄바꿈은 Shift+Enter. 입력 중 커서는 글자를 가리지 않는 아래 여백에 둔다.

```cypher
MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)-[:OBSERVES]->(v:StateVariable)
WHERE v.limit IS NOT NULL
RETURN s.tag AS tag, v.name AS quantity, v.unit AS unit, v.limit AS limit
ORDER BY tag;
```

런을 눌러 조건을 적용하겠습니다.

> [조작] Run 클릭 → 실제 결과 3행 확인 뒤 해석한다.

> [결과 확인 뒤] 압력, 온도, 진동에 해당하는 세 행이 남았습니다. 단위가 서로 다르므로 한계 숫자의 크기로 위험 순위를 정할 수는 없습니다. 여기서는 등록된 기준을 찾았고, 실제 측정값에 대한 판단은 하지 않았습니다.

## 교체 부품의 품번 확인하기

앞 카드를 비우고 교체 부품을 확인하겠습니다. 같은 구성 요소에서 부품을 사용하는 관계로 이동할게요. 장치 이름과 교체 부품 이름을 함께 받고, 품번까지 확인하겠습니다.

> [조작] `:clear`로 앞 결과 카드를 비운 뒤 위쪽 입력칸에 아래 문장을 작성한다. 줄바꿈은 Shift+Enter. 입력 중 커서는 글자를 가리지 않는 아래 여백에 둔다.

```cypher
MATCH (:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:USES_PART]->(p:Part)
RETURN c.name AS component, p.name AS part, p.partNo AS part_no
ORDER BY c.id;
```

런을 눌러 품번을 확인하겠습니다.

> [조작] Run 클릭 → 실제 결과 3행 확인 뒤 해석한다.

> [결과 확인 뒤] 장치와 그 장치에 쓰이는 부품이 구분돼 나왔습니다. 쿨러 코어, 팬 베어링, 펌프 축 씰 키트의 품번을 원자료와 대조하겠습니다. 뒤의 모델 설계에서는 이 부품에 공급 조건을 연결합니다. 지금 예제에 없는 공급처를 여기서 추정하지는 않겠습니다.

## 센서 목록으로 집계 검증하기

앞 결과를 정리하고 마지막으로 구성 요소별 센서 수를 보겠습니다. 카운트에 디스팅트를 넣어 서로 다른 센서를 셀게요. 숫자만 받지 않고 센서 태그 목록도 함께 받아 집계의 근거를 보겠습니다.

> [조작] `:clear`로 앞 결과 카드를 비운 뒤 위쪽 입력칸에 아래 문장을 작성한다. 줄바꿈은 Shift+Enter. 입력 중 커서는 글자를 가리지 않는 아래 여백에 둔다.

```cypher
MATCH (:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)
RETURN c.id AS component_id, c.name AS component,
       collect(DISTINCT s.tag) AS tags, count(DISTINCT s) AS channels
ORDER BY channels DESC, component_id;
```

런을 눌러 목록과 집계를 함께 보겠습니다.

> [조작] Run 클릭 → 실제 결과 3행 확인 뒤 해석한다.

> [결과 확인 뒤] 쿨러와 주 펌프는 둘씩, 팬은 하나입니다. 목록의 태그 수와 집계가 맞습니다. 여기서 센서가 없는 구성 요소는 영으로 나온 것이 아니라 결과에서 빠졌습니다. 센서까지 연결되는 패턴을 찾았기 때문입니다.

## 질의와 결과 저장하기

실행한 쿼리와 확인한 결과를 저장하겠습니다. 센서 목록, 한계가 있는 항목, 교체 부품과 품번을 질문별로 남기고, 집계에는 원래 태그 목록도 함께 적겠습니다. 나중에 이 결과를 다시 확인할 수 있도록 접속한 실습 DB와 확인 시점도 기록하겠습니다.

> [조작] VS Code에서 조회_작성.cypher와 조회_기록.md 저장 → 다시 열어 보존 확인 → 재부팅 전 개인 보관 경로로 복사. VS Code UI 기본 설명은 생략한다.

앞 이론의 조회 문법으로 실제 질문에 답해 봤습니다. 다음에는 포털의 기준 지식 지도로 이동해서 같은 종류의 연결을 직접 탐색하겠습니다. 오늘 사용한 예제 DB와는 별도입니다. 데이터를 만드는 크리에이트와 머지는 뒤의 그래프 구현 실습에서 적재 결과와 중복 여부를 보며 사용하겠습니다.
