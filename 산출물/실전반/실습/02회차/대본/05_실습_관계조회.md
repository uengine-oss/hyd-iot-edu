# 실전반 2회차 실습 1 — 그래프의 관계 조회

> 강사 단독 진행. 조작·입력·확인 분기는 낭독하지 않는다. 아래 결과 표현은 직접 확인한 경우에만 사용한다. 제공 예제 적재·조회는 실행 검증했다. 브라우저 조작·촬영은 별도 확인한다.

## 자료를 내려받고 작업 공간 열기

이번에는 설비에서 센서와 교체 부품을 찾아볼게요. 결과가 몇 행 나왔는지만 보지 않고, 어떤 대상이 연결돼서 나온 행인지 확인하겠습니다. 실습 시작 도구에서 관계 조회를 선택하고 새로 시작을 누릅니다.

> [조작] 현재 과정·온라인 02회차·관계 조회 선택 → 새로 시작. VS Code에서 열린 폴더와 START.md를 확인한다. 수동으로 시작할 때는 해당 ZIP만 풀고 그 폴더를 연다.

먼저 조회할 예제를 준비할게요. Docker가 실행된 상태에서 VS Code 터미널에 파이썬 준비 명령을 넣겠습니다. 이 폴더에서 쓸 DB와 예제만 준비하는 명령입니다.

> [조작] `python prepare_example.py` 실행. 노드 20개·관계 19개 준비 완료 표시를 확인한 뒤 이어 간다.

이제 브라우저를 열겠습니다. 터미널에 나온 접속 주소를 사용할 거예요. 앞에서 쓰던 포털의 DB 주소를 넣으면 다른 데이터를 보게 됩니다.

> [조작] `python lab_db.py` 실행 → 열린 Neo4j Browser의 Connect URL에 출력된 bolt 주소 입력. Username은 neo4j, Password는 비움. 연결 완료 후 조회_작성.cypher와 조회_기록.md를 연다.

이 예제에는 설비 한 대의 구성과 계측 채널이 들어 있습니다. 먼저 쿨러에서 센서로 가는 연결 하나부터 조회해 볼게요.

## 한 단계 연결을 조회하기

질의 파일을 열고, 오일 쿨러에서 센서로 가는 패턴을 적겠습니다. 구성 요소와 센서의 종류를 쓰고, 사이에는 계측 관계를 둡니다. 이름만 같은 다른 대상을 섞지 않도록 쿨러 식별자를 조건으로 쓰겠습니다.

> [조작] 조회_작성.cypher에 MATCH (c:Component {id:'comp:cooler'})-[:MONITORED_BY]->(s:Sensor) RETURN c.id, c.name, s.id, s.tag;를 작성하고 한 문장씩 실행한다. 결과 행을 조회_기록.md에 옮긴다.

결과에서는 쿨러가 몇 번 나왔는지와 서로 다른 센서가 몇 개인지를 나누어 봅니다. 쿨러 이름이 반복됐다고 쿨러 노드가 여러 개라는 뜻은 아닙니다. 센서 식별자와 태그를 함께 확인하겠습니다.

> [확인] 제공 예제의 쿨러는 TS1·CE에 연결된다. 다르게 나오면 대상 DB·식별자·관계 방향과 예제 적재 여부를 확인한다. 맞지 않는 결과를 지우거나 성공으로 읽지 않는다.

## 표와 그래프, 여러 단계 경로 비교하기

이번에는 같은 패턴에서 관계에도 변수를 붙이고, 속성값 대신 노드와 관계를 반환하겠습니다. 표에서 읽은 연결이 그래프에서도 같은 대상인지 보겠습니다. 다음으로 출발점을 HYD-01로 바꾸고, 구성 요소와 센서를 거쳐 상태 변수까지 길을 이어 적습니다.

> [조작] 기존 질의를 복사해 -[r:MONITORED_BY]->와 RETURN c,r,s로 바꾼다. 이어 Asset→HAS_COMPONENT→Component→MONITORED_BY→Sensor→OBSERVES→StateVariable 경로를 작성한다. 설비 조건은 code:'HYD-01'. RETURN에 센서 태그·물리량 이름·단위·한계를 둔다. 원자료의 목록과 비교한다.

한계가 없는 물리량은 빈 값으로 나올 수 있습니다. 대상까지 못 찾은 것과 속성값이 없는 것은 다릅니다. WHERE에 한계 값이 있는 조건을 붙여 보고, 어떤 행이 빠졌는지 기록하겠습니다. 빈 값을 영으로 바꾸지는 않겠습니다.

## 구성 요소에서 교체 부품 찾기

같은 설비에서 이번에는 교체할 부품을 찾아보겠습니다. 센서를 찾던 길과 달리 구성 요소에서 부품을 쓰는 관계로 건너갑니다. 쿨러라는 장치와 그 안의 교체 부품인 쿨러 코어를 구별하고, 주문할 때 확인할 품번까지 함께 받겠습니다.

> [조작] MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)-[r:USES_PART]->(p:Part) RETURN c.id,c.name,p.id,p.name,p.partNo ORDER BY c.id;를 작성한다. 속성 반환 결과를 c,r,p의 그래프 반환과 비교하고 준비 안내의 세 부품 경로에 대조한다. 결과와 근거는 조회_기록.md에 남긴다.

## 집계한 값과 원래 행을 맞추기

이제 구성 요소별로 센서가 몇 개 연결되는지 보겠습니다. 먼저 원래 행에서 장치별 센서 식별자를 모아 세고, 그다음 질의의 집계와 비교합니다. 장치 이름과 식별자를 묶는 기준으로 두고 서로 다른 센서를 세겠습니다.

> [조작] Asset→Component→Sensor 질의에서 RETURN c.id,c.name,count(DISTINCT s) AS channels ORDER BY channels DESC,c.id를 작성한다. 집계 대조표에 원래 센서 목록·손으로 센 수·질의 결과를 기록한다. 센서가 없는 구성 요소는 이 MATCH 결과에 없음을 함께 적는다.

수만 맞는지 보지 않고 같은 센서를 셌는지도 확인합니다. 질의와 결과, 사용한 DB와 확인 시점을 저장하고 파일을 다시 열겠습니다. 이렇게 하면 나중에 숫자의 근거가 된 행까지 돌아갈 수 있습니다.
