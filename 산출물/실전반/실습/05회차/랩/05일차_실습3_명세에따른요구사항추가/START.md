# 점검 요청에 긴급 확인 표시를 명세로 먼저 정하고 더하기

앞 실습에서 완성한 점검 요청 기능에 **긴급 확인 표시**를 더하는 요구를, 먼저 `spec.md`로 명세한 뒤 구현합니다. 점검 담당자가 요청 초안에서 긴급 표시와 그 이유, 확인할 항목을 함께 읽을 수 있어야 하고, 기존 요청의 출력과 질문 · 승인 조건은 그대로여야 합니다.

## 출발점

- `코드/input/점검요청/`: 앞 실습(확인 질문과 재처리)의 완성 판본입니다. 하는 일과 결과의 칸은 [코드/input/점검요청/README.md](코드/input/점검요청/README.md)에 있습니다. 같은 폴더의 `결과/`는 이 판본을 그대로 실행한 **변경 전 결과**입니다.
- 원자료 `코드/source/`(읽기만 합니다): `입력/`(요청 R01~R10 · 센서 사례 S01~S11과 설명), `사람/`(답변 · 승인 · 쓰는 법), `온톨로지/`, `매뉴얼/`. 앞 실습과 같은 자료입니다.
- 이번 요구(교육용 조건):
  - 쿨러 성능 저하 경보(`COOLER_DEGRADATION`)의 요청에 긴급 확인 표시를 붙입니다.
  - 판정 값은 판단 시각의 유효한 TS1 120초 평균(`센서_입력.json`의 `readings`에서 `TS1` · `avg` · `120`)이고, 60 ℃ 이상이면 긴급으로 표시합니다.
  - 유효성은 신선도(`freshness.ok`)와 표본(`coverage.covered`)으로 봅니다. 값 누락 · 신선도 실패 · 표본 부족은 미판정(`null`)으로 남깁니다.
  - 실제 설비 기준(운전 화면의 60 ℃ 초과 경고, 65 ℃ 인터록)과 승인 권한은 바꾸지 않습니다.
- `코드/output/spec.md`: 여섯 칸(목표 · 입력 · 출력 계약 · 금지 조건 · 긴급 조건과 유효성 · 수용 기준)의 빈 틀입니다.
- `코드/output/변경_확인_기록.md`: 비어 있는 기록 틀입니다.

## 직접 구현할 것

1. `코드/output/spec.md`의 여섯 칸을 채웁니다. 일반 요청에서 지킬 것과 긴급 확인 표시에서 달라질 것을 나눠 적고, 수용 기준은 실행 결과로 참 · 거짓을 가를 수 있는 문장으로 씁니다.
2. `코드/input/점검요청/`을 `코드/output/점검요청/`으로 복사하고, 명세대로 그 사본을 고칩니다. 실행하면 요청 결과마다 아래가 생깁니다.

| 항목 | 내용 |
|---|---|
| 긴급 확인 표시 | `true` · `false` · `null` 가운데 하나. `null`은 「긴급 아님」이 아닙니다 |
| 표시의 이유 | 판정 값 · 기준 · 신선도 · 표본, 또는 판정하지 못한 까닭 |
| 요청 초안 | 초안만 읽어도 긴급 표시 · 이유와 확인할 항목이 함께 읽힘 |
| 지킬 것 | 기존 결과 칸의 이름 · 형식 · 뜻, 질문 · 승인 조건 |

## 작업 순서

1. **복사**: VS Code 탐색기에서 `코드/input/점검요청` 폴더를 복사해 `코드/output/`에 붙여 넣습니다.
2. **탐색만 요청**: AI에게 파일을 바꾸지 말고 지금 결과의 칸, 요청 상태가 정해지는 곳, 사례에서 TS1 120초 평균 · 신선도 · 표본이 들어 있는 곳을 설명하게 합니다. 설명을 실제 파일과 대조합니다.
3. **명세 먼저**: `spec.md`의 여섯 칸을 직접 씁니다. 빈 칸이 있으면 그 칸이 정할 해석을 구현하는 쪽이 대신 채우게 됩니다. 이어서 기록 틀의 「먼저 적은 기대」에 아래 사례 종류마다 원자료 행이나 연습 사본으로 기대 표시 · 기대 상태와 그 근거가 된 spec.md 줄을 적고, 「기대 칸을 쓴 시각」을 적습니다.
4. **명세와 함께 맡기기**: AI에게 `spec.md`를 읽고 필요한 부분만 고치는 계획을 먼저 받습니다. 기존 칸 · 질문 · 승인에 손대는 계획, 명세에 없는 동작(처리 순서 바꾸기 등)을 더하는 계획은 고칩니다.
5. **작은 단위로 구현**: 판정 값 읽기 → 유효성 → 표시와 이유 → 초안에 보이기 순서로 하나씩 만들고 그때마다 실행합니다.
6. **바뀐 파일 읽기**: 바뀐 파일과 그 까닭을 기록하고, 명세와 관계없는 변경이 섞이지 않았는지 봅니다.
7. **변경 전후 대조**: 변경 전 결과(`코드/input/점검요청/결과/`)와 변경 뒤 결과를 요청 열 건 모두 견줍니다. 매번 달라질 수 있는 값이 있으면 값이 아니라 형식 · 연결 관계를 견줍니다.
8. **원자료에 없는 사례**: 신선도 실패 · 값 없음 · 표본 부족 · 경계값처럼 원자료 요청에 없는 경우는 `코드/output/연습_입력/`(점검_요청.json · 센서_입력.json 사본)이나 `코드/output/연습_사람/`에 사본을 만들어 값만 바꿔 실행합니다. 원본은 고치지 않습니다.
9. **초안 대조**: `점검_요청.md`에서 긴급 표시의 이유와 확인할 항목이 함께 읽히는지 요청마다 봅니다.
10. **어긋나면 가리기**: 구현이 틀렸으면 구현을, 명세가 빠뜨렸으면 명세를 고칩니다. 결과에 맞추려고 기대를 낮추지 않습니다.

## 진행할 때

- 채팅에 파일 이름을 쓸 때는 백틱(`)으로 감쌉니다. 예: `코드/output/spec.md`. 채팅 입력이 밑줄(_)을 서식으로 바꿔 이름이 달라질 수 있습니다.
- AI가 완료를 알리면 실행한 명령과 그 출력 원문(요약이 아니라 나온 글자 그대로)과 바뀐 파일 목록을 붙여 달라고 요청합니다.
- AI가 질문 카드(선택지와 「(권장)」 표시)로 물으면, 「(권장)」은 AI의 추천일 뿐입니다. 근거가 되는 명세 · 원자료 줄을 열어 확인한 뒤 고르거나 직접 입력 칸에 결정과 근거를 적습니다.
- 파일 편집 승인 창(「Allow ChatGPT to edit …」)이 뜨면 바뀔 파일이 `코드/output/` 아래인지 보고 「Allow once」, 아니면 「Deny」를 누릅니다.
- 고친 뒤에는 새 기능을 확인한 요청만이 아니라 열 건 모두를 다시 실행해 변경 전 결과와 견주어 달라고 합니다.

## 실행

랩 폴더(이 START.md가 있는 폴더)에서 실행합니다. `--입력` 폴더에는 `점검_요청.json`과 `센서_입력.json`이 함께 있어야 합니다.

```
python 코드/output/점검요청/점검_요청.py
python 코드/output/점검요청/점검_요청.py --입력 코드/output/연습_입력 --결과 코드/output/연습_결과
python 코드/output/점검요청/점검_요청.py --사람 코드/output/연습_사람 --결과 코드/output/연습_결과
```

## 기대 결과를 먼저 적을 사례 종류

- 쿨러 경보가 아닌 요청: 기존 결과가 그대로이고 긴급 조건을 적용하지 않은 것이 어떻게 보이는지
- 쿨러 경보 · 유효한 값이 60 ℃ 이상인 요청과 미만인 요청
- 판정 값이 기준과 같은 요청(경계값)
- 쿨러 경보 · 신선도 실패, 값 없음, 표본 부족인 요청
- TS1이 아닌 다른 값의 표본이 부족한 쿨러 경보 요청
- 질문 대기라 사례가 정해지지 않은 쿨러 경보 요청
- 긴급 표시가 붙은 요청의 승인 · 거절: 승인 조건과 후속 업무가 그대로인지

## 학생이 정할 것

원문 · 요구만으로 하나로 정해지지 않아 학생이 근거를 찾아 정하는 지점입니다. 정한 내용과 근거를 `spec.md`와 기록 틀의 「정한 것」 표에 적습니다. AI는 이 지점을 정하기 전에 학생에게 묻습니다.

- 쿨러 경보가 아닌 요청의 긴급 확인 표시를 어떻게 남길지(칸을 두지 않음 · `false` · `null` 가운데)와 그렇게 읽힐 뜻
- 미판정(`null`)일 때 요청의 상태를 그대로 둘지, 보류로 바꿀지(기존 승인 조건과의 관계)
- 사례가 정해지지 않은 쿨러 경보 요청의 표시와 이유

> 판단 지점: `false`는 「조건에 대어 보았더니 긴급이 아니다」이고 `null`은 「대어 볼 수 없었다」입니다. 받는 사람이 기다릴 일과 지금 할 일을 가르는 칸이므로, 두 값이 섞이지 않게 명세에 적습니다.
