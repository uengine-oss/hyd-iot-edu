# 실전반 4회차 실습 2 — 원인추론과점검계획

> [제작 안내 — 낭독하지 않음] 강사 단독 시연 대본이다. 조작·AI 응답·접속·실행·캡처는 이번 제작에서 수행하지 않았다. 실제 결과가 나온 뒤 그 값과 근거를 읽고, 다르면 원인을 고쳐 다시 확인한다. 성공을 미리 낭독하지 않는다.

## 다운로드와 입력 확인

포털에서 본 조회와 판단을 독립 에이전트로 만들어, 원인 후보의 증거를 대조하고 점검 요청 초안으로 바꾸겠습니다. 실습 자료를 받아 압축을 풀고 VS Code에서 작업 공간을 열겠습니다.

> [준비 · 비낭독] 원인추론과점검계획 ZIP을 내려받아 압축을 풀고 VS Code에서 폴더를 열겠습니다. START.md에서 과제와 완료 조건을 먼저 읽습니다. 코드/source에는 공통 온톨로지와 사례 입력, 매뉴얼이 있고, 코드에는 모델 접속용 llm_client.py와 .env, 결과 형식을 정한 입출력_계약.md가 있습니다. 완성 에이전트를 실행하는 대신 이 입력을 읽는 도구와 실행 고리를 만들겠습니다. README의 입력 구조를 읽고 graph.json에서 원인·고장 유형·증상·증거의 ID와 관계 방향을 확인합니다. cases.json의 센서 값은 제공된 과거 입력이며 현재 설비 값이 아닙니다.

이번 프로젝트의 내부 구성은 아직 모르므로, 원인 근거를 찾는 데 어떤 자료와 기능이 준비됐는지부터 확인하겠습니다.

> [탐색 요청 · 응답 확인 뒤 다음 단계] 설비 경보의 원인 후보와 추가 확인을 근거와 함께 점검 요청 초안으로 내려 합니다. 현재 프로젝트에서 사용할 자료, 이미 있는 기능, 구현할 부분과 확인할 조건을 찾아 설명해 주세요. 파일을 수정하거나 실행하지 마세요.
> [확인] 답변의 자료 위치와 현재 기능을 실제 파일에 대조한다. 아래 경로·필드 설명은 그 확인 후 진행하며 응답을 미리 받은 것처럼 읽지 않는다.

코드/output/expected.md에 첫 사례에서 확인할 근거와 초안의 칸을 먼저 적겠습니다. 원인 후보에 연결된 증거 조건, 필요한 태그, 집계와 시간 창을 찾습니다. 평균과 최댓값·최솟값 차이는 다른 집계입니다. 입력의 신선도와 표본 누락을 확인하지 않고 숫자 하나만 비교하지 않겠습니다.

제공 그래프와 매뉴얼이 모두 같은 범위를 담은 것은 아닙니다. 펌프 증거의 집계 구간은 그래프에서 2분, PM-2.10에서 1분으로 다릅니다. 이를 같은 조건으로 취급하지 않고 검토 필요로 남기겠습니다. HM-3·5·7·9처럼 제공되지 않은 절을 가리키는 조치도 원문을 확인한 것으로 쓰지 않겠습니다. 냉각 사례부터 근거를 대조하고, 출처나 기준이 맞지 않는 후보는 추가 확인 대상으로 남깁니다.

## 근거를 읽는 기능과 출력 약속 만들기

코딩 도우미에게 이렇게 요청하겠습니다. source의 스키마·그래프·사례를 읽는 도구를 만들고, 모델이 그 도구를 골라 불러 원인 후보와 증거를 평가하는 코드/output/agent.py를 만들어 주세요. 모델이 부른 도구와 입력·결과는 순서대로 호출 기록에 남겨 주세요. 입력의 실제 필드와 관계 이름을 먼저 확인하세요. 기준은 그래프에서 읽고 코드에 임의 수치를 넣지 마세요. 확인됨·확인 못함·지지 근거 없음의 상태를 구별하고, 근거마다 태그·집계·시간 창·실제 값·기준·출처를 남겨 주세요. 누락·묵은 값·불충분한 표본은 0이나 정상으로 바꾸지 마세요. 여러 후보가 남으면 함께 제시하고 확정 원인이라고 쓰지 마세요.

출력은 입출력_계약.md대로 코드/output/점검요청_초안.json과 점검요청_초안.md로 정하겠습니다. 초안에는 대상 설비·구성 요소, 부품, 관측 시각과 값, 확인 항목, 이유와 원문 절, 다른 후보를 적고, 적은 값마다 그 값을 돌려준 호출 번호를 붙이게 합니다. 근거가 모자라면 초안 대신 보류와 그 이유를 냅니다. 초안은 확정 원인도 작업지시도 아니라고 표시하고, 실제 제어나 작업지시는 호출하지 않습니다.

> [조작] 학생 기능은 수업에서 작성한다. 생성 코드의 파일 경로·출력 구조·누락 처리·종료 조건을 읽은 뒤에만 수업 환경에서 실행한다. 모델 접속은 .env와 llm_client.py로만 하고 키는 산출물·채팅에 남기지 않는다.

## 실행 고리와 결과 대조

기능이 원인 후보 조회, 필요한 증거 읽기, 관찰, 다음 확인의 순서를 기록하도록 요청하겠습니다. 모델을 쓰는 부분과 수치·조건을 계산하는 부분을 나누고, 최대 반복 횟수와 확인 불가 시 종료 조건도 설정합니다. 수업에서는 사례 하나를 먼저 실행해 호출 기록에서 모델이 고른 도구·입력·결과를 review.md에 적고, expected.md의 근거와 대조하겠습니다. 결과가 다르면 그래프 해석, 센서 집계, 신선도, 문장화 중 어디에서 달라졌는지 확인합니다.

제공 사례 중 태그가 부족하거나 관측 시각이 오래된 경우, 여러 원인에 맞는 증거가 있는 경우를 찾아 비교하겠습니다. 추가 입력이 필요하면 원문과 구별한 검증용 사례로 정의하고 그 입력이 확인하려는 조건을 적습니다. 정상 기능을 고장 내거나 과거 관측을 실제 장애로 바꾸지는 않습니다. 빠진 태그가 보류와 추가 점검으로 이어지는지, 복수 근거에서 하나를 임의로 확정하지 않는지 확인합니다. 확인 항목을 고칠 때도 원문에 없는 조작 단계를 덧붙이지 않겠습니다. 다른 설비와 다른 경보 사례에도 같은 프로그램을 돌려 첫 사례에만 맞춘 곳이 없는지 보고, 끝으로 check.py로 결과의 구조와 호출 번호를 검사하겠습니다.

## 저장과 다시 열기

작성한 기능과 입력 사본, 예상 근거, 실제 결과와 수정 기록을 저장하고 다시 열겠습니다. 어느 근거로 후보가 남았고 점검 담당자가 무엇을 왜 확인해야 하는지 초안만으로 설명할 수 있는지 보겠습니다. 지금 만든 초안이 실제 고장 원인을 확정하거나 작업지시를 낸 것은 아닙니다. 이처럼 반복할 수행 방법을 다음에는 스킬 파일로 정리하겠습니다.
