# 준비된 정기 정비 흐름은 어떻게 연결돼 있는가 — 읽는 자료

수업 시스템에는 정기 점검 시나리오 B를 처리하는 흐름 「정기 정비」가 이미 등록·배포되어 있습니다. 이 문서와 `pm-planning.mapping.json`은 그 흐름의 그림(`pm-planning.bpmn`)의 각 요소가 실제로 어떤 실행 기능·역할·조건에 연결돼 있는지 읽기 위한 자료입니다. 이 값을 포털에 입력하는 실습은 없습니다. 내 그림과 견줄 때, 그리고 처리 건 기록을 읽을 때 「이 작업이 무엇을 실행했는가」를 찾는 데 씁니다.

## 그림과 연결 값은 다른 파일이다

- 그림(`pm-planning.bpmn`)에는 요소의 종류·이름·레인·선만 있습니다.
- 연결 값(`pm-planning.mapping.json`)에는 어떤 경보로 시작하는지, 각 작업이 어떤 기능(부품)·에이전트·역할을 쓰는지, 갈림의 조건, 타이머의 기한이 있습니다. 두 파일은 요소 ID(`T_agent`, `T_approve` …)로 이어집니다.
- 실행 정의는 수업 시스템이 이 둘을 합쳐 등록한 것이고, 처리 건(인스턴스)은 경보 하나가 그 정의로 연 실행 한 건입니다.

## 시작

| 항목 | 값 | 뜻 |
|---|---|---|
| 시작 방식 | 경보로 시작(`start.kind: alert`) | 메시지 시작 이벤트 |
| 경보 패턴 | `PM_DUE` | 정기 점검 도래. 포털 결함 시뮬레이션의 [정기 점검] 버튼이 업무 감시와 같은 형식의 경보를 보냅니다 |
| 대상 설비 | HYD-02 | 마지막 정기 정비 뒤 운전시간이 주기에 가까워진 설비 |

## 승인 구조 — 세 시나리오 공통

| 그림의 요소 | 연결 값 | 뜻 |
|---|---|---|
| `T_approve` 설비보전팀장 승인 | 부품 `task:select-or-reject`, 역할 설비보전팀장 | 사람이 에이전트의 제안 카드를 승인하거나 사유와 함께 거절 |
| `B_overdue` 승인 지연(점선 타이머) | 기한 `PT10M`(10분) | 멈추지 않는 경계 타이머. 승인 작업을 취소하지 않습니다 |
| `T_notice` 승인 지연 알림 | 부품 `svc:report`, 결과 「승인 지연」 | 알림만 보내고 `E_notice`에서 끝납니다. 승인 작업은 계속 기다립니다 |
| `G_approved` 승인? → 승인 | 조건 `approval == '승인'` | |
| `G_approved` 승인? → 거절 | 그 밖의 경우(기본 경로) | |
| `R_rejected` 결과 보고: 거절 | 부품 `svc:report`, 결과 「반려」 | 보고 문구: 정비 오더를 내지 않았고 정기 점검 도래 표시는 그대로 |

## 정기 정비 쪽 작업

| 그림의 요소 | 연결 값 | 뜻 |
|---|---|---|
| `T_agent` 정비 계획 제안 | 부품 `task:decide`, 에이전트 `agent:pm-plan`(정기 정비 계획 에이전트) | 지시문: 운전시간·허용 오차·생산 오더·정비 인원·부품을 저울질해 언제 정비할지 카드를 냅니다 |
| `T_wo` 정비 오더 등록 · 공지 메일 | 부품 `task:work-order`(CMMS 정비 작업지시), 정비 예정 시간 값 `alert.evidence.night_window_id`, 공지 메일 받는 곳 `production@hyd.local` | 승인한 카드의 정비 오더를 CMMS에 등록하고, 같은 작업 끝에 생산팀 공지 메일을 보냅니다. 수업 흐름은 오더와 공지를 한 작업으로 묶었습니다 |
| `R_ok` 결과 보고 | 부품 `svc:report`, 결과 「정상」 | 보고 문구에 정비 오더 번호와 정비 시점이 들어갑니다 |

연결 값의 `{asset}`, `{work_order.ref}` 같은 표시는 실행할 때 그 처리 건의 값으로 채워집니다.

## 읽을 때 주의할 것

- 정비 오더 등록은 「해야 할 정비를 CMMS에 올려 둔 것」입니다. 현장 정비가 끝났다는 뜻이 아닙니다.
- 메일 주소는 수업 환경용 가상 주소입니다. 메일은 외부로 나가지 않고 수업 메일함에만 남습니다.
- 수업 시스템의 경보는 그 패턴을 받는 배포된 정의 가운데 가장 최근 것이 엽니다. 처리 건을 읽을 때는 어느 정의의 몇 번 판본이 열었는지부터 적습니다.
