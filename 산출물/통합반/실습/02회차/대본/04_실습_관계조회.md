## 노드 하나와 조건 바꾸기

위쪽 입력칸을 누르고 쿨러를 찾는 두 줄을 넣겠습니다. 첫 줄의 매치는 찾을 대상을 나타냅니다. 괄호 안의 씨는 찾은 노드를 뒤에서 부를 이름이고, 컴포넌트는 대상의 종류입니다. 중괄호에는 쿨러의 식별자를 넣었습니다.

```cypher
MATCH (c:Component {id:'comp:cooler'})
RETURN c.id AS id, c.name AS name;
```

## 센서 관계와 표·그래프 비교

앞 결과 카드를 정리하고 이번에는 쿨러에서 센서로 연결을 늘려 보겠습니다. 입력칸에 콜론 클리어를 넣고 실행하겠습니다.

> [full015 · 조작] 입력칸 선택 → :clear → Enter → 카드 정리 완료 확인 → 입력 비움. DB 데이터는 보존한다.

입력칸에 쿨러에서 센서로 이어지는 문장을 넣겠습니다. 왼쪽 괄호는 출발할 쿨러, 오른쪽 괄호는 도착할 센서입니다. 가운데 대괄호와 화살표가 두 노드 사이의 관계예요. 모니터드 바이라는 관계를 따라 센서를 찾습니다.

```cypher
MATCH (c:Component {id:'comp:cooler'})-[:MONITORED_BY]->(s:Sensor)
RETURN c.name AS component, s.id AS sensor_id, s.tag AS tag
ORDER BY s.tag;
```


## 여러 단계 경로와 WHERE

이제 화면을 정리하고 설비 한 대에서 물리량까지 따라가겠습니다. 앞에서는 관계 하나였지만 이번에는 구성 요소, 센서, 물리량으로 이어집니다. 먼저 콜론 클리어로 앞 카드를 비우겠습니다.

> [full023 · 조작] 입력칸 선택 → :clear → Enter → 카드 정리 완료 확인 → 입력 비움. DB 데이터는 보존한다.

입력칸에 여러 단계 경로를 넣겠습니다. 첫 줄은 에이치와이디 영일 설비에서 구성 요소를 찾는 부분입니다. 다음 줄은 그 구성 요소의 센서로 이동하고, 센서가 관측하는 물리량까지 이어집니다. 앞에서 쓴 관계 패턴을 연달아 붙인 모습입니다.

```cypher
MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)-[:OBSERVES]->(v:StateVariable)
RETURN s.tag AS tag, v.name AS quantity, v.unit AS unit, v.limit AS limit
ORDER BY tag;
```

> [full024 · 조작] 입력할 위치와 작업이 전달된 뒤 문장을 넣는다. 한 글자씩 느리게 입력하지 않는다.

리턴에는 태그, 물리량 이름, 단위와 한계를 넣었습니다. 단위까지 받는 이유는 같은 숫자라도 무엇을 측정했는지에 따라 의미가 다르기 때문입니다. 마지막에는 태그 순서로 정렬하겠습니다.

> [full025 · 조작] 설명 중 해당 문장의 위치를 가리킨다.

런을 눌러 설비의 센서와 물리량을 함께 보겠습니다.

> [full026 · 조작] Run 클릭 → 새 결과 렌더 확인. 다음 발화는 결과 확인 후 시작.

다섯 센서의 물리량이 나왔습니다. 압력은 바, 온도는 섭씨처럼 단위를 함께 읽습니다. 한계가 널로 표시된 행도 보이네요. 관계를 찾지 못한 것이 아닙니다. 물리량까지는 찾았지만 그 노드에 한계 속성값이 없는 경우입니다. 널을 영이라고 읽거나 임의의 숫자로 바꾸지 않겠습니다.

> [full027 · 조작] 새 결과가 실제로 나타난 뒤 표를 짚어 해석한다.

이번에는 한계가 등록된 항목만 남겨 보겠습니다. 같은 경로에서 리턴 앞에 웨어 조건을 넣을게요. 한계가 이즈 낫 널이라는 조건입니다. 값이 없는 행을 제외하라는 뜻이에요. 원래 다섯 행 중 한계가 있는 항목이 무엇인지 보면서 비교하겠습니다.

```cypher
MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)-[:OBSERVES]->(v:StateVariable)
WHERE v.limit IS NOT NULL
RETURN s.tag AS tag, v.name AS quantity, v.unit AS unit, v.limit AS limit
ORDER BY tag;
```

런을 눌러 조건을 적용하겠습니다.

## 교체 부품 조회

앞 카드를 비우고 이번에는 교체 부품을 찾아보겠습니다. 같은 설비에서 출발하지만 센서를 찾던 관계 대신 부품을 사용하는 관계를 따라갑니다. 콜론 클리어로 화면을 정리하겠습니다.

> [full034 · 조작] 입력칸 선택 → :clear → Enter → 카드 정리 완료 확인 → 입력 비움. DB 데이터는 보존한다.

입력칸에 부품을 찾는 문장을 넣겠습니다. 설비에서 구성 요소까지는 앞과 같습니다. 그다음 유즈즈 파트 관계로 부품을 찾습니다. 리턴에는 장치 이름, 부품 이름, 품번을 함께 받겠습니다. 어떤 장치에 쓰이는 어떤 부품인지 구별하기 위해서입니다.

```cypher
MATCH (:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:USES_PART]->(p:Part)
RETURN c.name AS component, p.name AS part, p.partNo AS part_no
ORDER BY c.id;
```

> [full035 · 조작] 입력할 위치와 작업이 전달된 뒤 문장을 넣는다. 한 글자씩 느리게 입력하지 않는다.

런을 눌러 장치와 교체 부품을 보겠습니다.

> [full036 · 조작] Run 클릭 → 새 결과 렌더 확인. 다음 발화는 결과 확인 후 시작.

오일 쿨러에는 쿨러 코어, 쿨러 팬에는 팬 베어링, 주 펌프에는 펌프 축 씰 키트가 연결돼 있습니다. 쿨러라는 장치와 쿨러 코어라는 부품은 다른 대상입니다. 품번까지 함께 확인해야 이름이 비슷한 부품과 혼동하지 않을 수 있어요.

> [full037 · 조작] 새 결과가 실제로 나타난 뒤 표를 짚어 해석한다.

## 센서 목록으로 집계 확인

마지막으로 센서 수를 세어 보겠습니다. 앞 카드는 정리하고 구성 요소에서 센서까지 연결하는 패턴으로 돌아갈게요. 이번에는 센서 목록과 집계한 수를 함께 받아 서로 맞는지 확인하겠습니다.

> [full038 · 조작] 입력칸 선택 → :clear → Enter → 카드 정리 완료 확인 → 입력 비움. DB 데이터는 보존한다.

위쪽 입력칸에 집계 문장을 넣겠습니다. 리턴의 장치 식별자와 이름을 기준으로 결과를 묶습니다. 컬렉트는 센서 태그를 목록으로 모으고, 카운트는 센서를 셉니다. 디스팅트는 같은 센서가 중복해서 세어지지 않게 하는 부분입니다.

```cypher
MATCH (:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)
RETURN c.id AS component_id, c.name AS component,
       collect(DISTINCT s.tag) AS tags, count(DISTINCT s) AS channels
ORDER BY channels DESC, component_id;
```

> [full039 · 조작] 입력할 위치와 작업이 전달된 뒤 문장을 넣는다. 한 글자씩 느리게 입력하지 않는다.

런을 눌러 목록과 수를 함께 보겠습니다.

> [full040 · 조작] Run 클릭 → 새 결과 렌더 확인. 다음 발화는 결과 확인 후 시작.

쿨러는 씨이와 티에스원, 두 개입니다. 주 펌프는 에프에스원과 피에스원, 두 개이고 팬은 브이에스원 하나입니다. 목록을 직접 세어 오른쪽 집계와 비교하면 둘, 둘, 하나가 맞습니다. 숫자만 보지 않고 무엇을 셌는지도 함께 확인한 것입니다.

> [full041 · 조작] 새 결과가 실제로 나타난 뒤 표를 짚어 해석한다.

여기에 센서가 없는 구성 요소가 영으로 표시되지는 않았습니다. 센서까지 연결되는 매치 패턴을 찾았기 때문에 그 경로가 없는 구성 요소는 결과에서 빠집니다. 조회 결과에 없다는 것과 데이터베이스에 대상이 없다는 것을 같은 뜻으로 읽지 않겠습니다.

## 저장·재열기·다음 실습

이제 오늘 쓴 문장과 확인한 결과를 저장하겠습니다. 왼쪽의 쿼리즈를 누르고 위쪽 더하기로 새 쿼리 탭을 열게요. 스트림은 실행 결과를 쌓아 보는 곳이고, 이 탭은 다시 사용할 문장을 보관하는 곳입니다.

> [full043 · 조작] Queries → Add new tab.

새 탭의 입력칸에 오늘 실행한 문장들을 넣겠습니다. 맨 위에는 첫 사이퍼 실습이라는 제목을 주석으로 적고, 각 문장 앞에는 실제 확인한 행 수와 센서 수를 남길게요. 두 개의 빗금으로 시작하는 줄은 설명용 주석이라 실행되는 질의와 구분됩니다.

> [full044 · 조작] 실제로 실행한 문장과 확인 기록을 주석과 함께 입력한다. 첫 주석 제목을 확인한다.

왼쪽 목록에 첫 사이퍼 실습이 저장됐습니다. 탭을 한 번 닫고 목록에서 다시 열어 보겠습니다. 방금 넣은 문장과 확인 기록이 그대로 남는지 확인하겠습니다.

> [full045 · 조작] 자동 저장 목록 확인 → 탭 닫기 → 목록에서 다시 열기 → 문장·기록 보존 확인.

문장과 확인 기록이 다시 열렸습니다. 다만 이 목록은 지금 브라우저에 저장된 상태입니다. 학교 컴퓨터는 초기화되므로 파일도 따로 받아야 합니다. 쿼리즈 제목 오른쪽의 내려받기 버튼을 눌러 저장된 문장을 파일로 받겠습니다.

> [full046 · 조작] Download all → 실제 CSV 내려받기 완료 확인.

내려받은 파일은 브라우저의 쿼리 목록을 담은 씨에스브이 파일입니다. 오늘 작성한 문장과 주석이 함께 들어 있습니다. 수업이 끝나면 받은 파일을 개인 저장 공간이나 유에스비로 옮겨 보관합니다. 다음날 이 컴퓨터에 그대로 남아 있다고 생각하면 안 되겠죠.

> [full047 · 조작] CSV의 실제 문장·주석과 원본 일치를 확인. 학교 초기화 후 로컬 보존을 약속하지 않는다.

오늘은 노드 하나를 찾는 문장에서 시작해 센서 관계를 붙였고, 여러 단계 경로에서 조건을 바꿔 봤습니다. 표와 그래프를 비교하고, 센서 목록으로 집계의 근거도 확인했습니다. 다음 실습에서는 포털의 지식 지도를 직접 눌러 연결을 탐색합니다. 오늘 작성한 파일이 없어도 다음 실습은 제공된 시작 자료로 진행할 수 있습니다.
