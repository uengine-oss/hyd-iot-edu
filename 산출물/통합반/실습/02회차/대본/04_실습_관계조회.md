# 통합반 2회차 실습 1 — 그래프의 관계 조회

> 강사 단독 진행. 조작·입력·확인 분기는 낭독하지 않는다. 아래 결과 표현은 직접 확인한 경우에만 사용한다. 제공 예제 적재·조회는 실행 검증했다. 브라우저 조작·촬영은 별도 확인한다.

## 자료를 내려받고 작업 공간 열기

앞 이론에서는 그래프의 노드와 관계를 사이퍼 문장으로 표현하는 방법을 배웠습니다. 매치로 연결을 찾고, 웨어로 조건을 좁히고, 리턴으로 볼 항목을 정했죠. 이번에는 준비된 설비 예제에 직접 써 보겠습니다. 쿨러에 연결된 센서부터 찾고, 물리량과 교체 부품까지 따라가며 결과가 원자료와 맞는지 확인할 거예요.

실습 시작 도구에서 통합반, 온라인 2회차, 관계 조회를 차례로 선택하겠습니다. 새로 시작을 누르면 이번 실습 자료를 받은 폴더가 VS Code에서 열립니다.

> [조작] 해당 항목 선택 → 새로 시작 → 실제 열린 폴더와 START.md 확인. 새 폴더가 열리기 전 다음 발화를 하지 않는다. 다운로드 실패 시 실제 오류에 맞춰 재시도 또는 안내된 수동 ZIP 경로를 사용한다.

VS Code는 이번 실습 파일을 열고 명령을 실행할 작업 공간입니다. 왼쪽의 파일 목록을 탐색기라고 해요. 여기에 이번 실습 폴더가 열렸는지 먼저 보겠습니다. START.md를 누르면 가운데에 시작 안내가 나옵니다. 파일 이름을 눌러 내용을 여는 방식이에요.

> [조작] 실제 탐색기 위치를 가리킨 뒤 START.md 클릭. 탐색기가 접혔다면 탐색기 버튼을 설명하며 열고, 신뢰 확인이 나오면 받은 실습 폴더의 경로·출처를 확인한 뒤 해당 폴더의 신뢰를 선택한다. 신뢰 창을 미리 처리한 것처럼 건너뛰지 않는다.

조회할 데이터부터 준비하겠습니다. 위쪽 터미널 메뉴에서 새 터미널을 열게요. 아래에 나타나는 입력칸은 컴퓨터에 실행할 명령을 적는 곳입니다. 지금 위치가 이번 실습 폴더인지 확인하고, 화면의 준비 명령을 입력한 뒤 엔터를 누르겠습니다.

> [조작] 실제 메뉴 이름·위치를 확인해 가리킴 → 터미널 열기 → 현재 폴더 확인 → `python prepare_example.py` 입력 → Enter. 실행 중에는 완료라고 말하지 않는다.

> [결과가 표시된 뒤 발화] 노드 20개와 관계 19개가 준비됐다는 표시가 나왔습니다. 조회할 설비와 연결이 들어간 거예요. 이제 브라우저를 여는 명령을 실행하겠습니다. 이 명령이 출력한 주소로 이번 실습 DB에 접속합니다.

> [조작] `python lab_db.py` 입력 → Enter → 실제 출력의 Browser 주소와 Bolt 접속값을 보여 주고 열린 Browser로 전환. 주소·포트 번호는 실행 결과를 사용한다.

## Neo4j Browser에서 연결하고 화면 살펴보기

실습 안내의 링크를 열면 이렇게 접속 정보를 확인하는 창이 나옵니다. 지금 열린 도구가 Neo4j Browser입니다. 먼저 실습 데이터베이스에 연결하겠습니다.

> [조작] `랩_연결.json`의 browser 링크를 그대로 열고 자동 표시된 연결 창에서 시작한다. 이번 실제 확인 주소는 `http://127.0.0.1:7628/browser/`이며 `localhost`의 이전 작업 화면으로 바꾸지 않는다. 기존 결과가 남은 화면을 첫 접속으로 사용하지 않는다. 연결 창을 닫았다가 다시 여는 조작을 추가하지 않는다. 아래 발화는 실제 미리 채워진 값과 터미널 출력을 대조한 뒤 사용한다.

접속 정보가 이미 들어 있네요. 프로토콜은 볼트이고, 그 옆이 연결할 주소입니다. 터미널에 나온 실습 DB 주소와 맞는지 확인하겠습니다. 사용자 이름은 네오포제이입니다. 이번 실습 DB는 비밀번호 없이 연결하도록 준비했으니 이 칸은 비워 두고, 아래 Connect를 누르겠습니다.

> [조작] 자동 입력된 Protocol `bolt://` → Connection URL → Database user `neo4j` → Password 빈칸을 차례로 가리켜 확인 → Connect 클릭. 맞는 값을 다시 입력하지 않는다. 실제 연결 성공 전 다음 발화를 하지 않는다. 처음 안내창이 뜨면 “새 탭 소개가 나왔네요. 지금은 Stream에서 진행할 거라 Dismiss를 눌러 닫겠습니다”라고 말하며 닫는다.

> [연결 후 발화] 왼쪽 위에 접속 주소와 데이터베이스 이름이 나타났습니다. 방금 준비한 실습 DB에 연결된 상태입니다. 포털의 지식 지도와는 별도이므로 여기에서 하는 조회가 포털 화면을 바꾸지는 않습니다.

> [실제 화면 분기] 왼쪽 패널이 접힌 경우 “왼쪽 패널부터 펼치겠습니다. Stream 왼쪽의 Open Sidebar 버튼을 누를게요”라고 말하며 연다. 소개 카드가 보이면 “가운데는 처음 접속했을 때 나오는 소개입니다. 지금은 준비된 실습 데이터를 사용하겠습니다”라고 짚고, 첫 쿼리 결과를 이 아래에 이어 보여 준다. 소개 카드나 기존 결과를 화면 밖에서 지워 백지로 만들지 않는다.

가운데 카드는 브라우저 사용 안내입니다. 지금은 준비된 실습 데이터를 살펴볼게요. 왼쪽 패널이 접혀 있으니, 스트림 왼쪽의 패널 열기 버튼을 누르겠습니다.

> [조작] 실제로 접힌 상태에서 Open Sidebar 버튼을 가리키고 누른다. 펼쳐지는 화면을 확인한 다음 설명한다.

왼쪽에는 데이터 정보와 저장한 쿼리를 보는 메뉴가 있습니다. 맨 위 원통 모양의 데이터베이스 오버뷰를 눌러, 어떤 데이터가 들어 있는지 확인하겠습니다.

> [조작] Database overview 클릭 → 노드20개·관계19개 및 실제 레이블·관계 유형 확인.

> [데이터 정보가 나온 뒤 발화] 여기에 보이는 레이블은 노드의 종류이고, 관계 유형은 노드를 잇는 연결의 종류입니다. 이론에서 본 구성 요소와 센서를 실제 예제에서도 구분해 둔 거예요. 이 목록의 이름을 쿼리에 사용하게 됩니다.

위쪽의 달러 표시 옆이 쿼리 입력칸입니다. 문장을 적고 오른쪽 Run을 누르면 아래에 결과가 생깁니다. 결과가 표라면 열 제목은 요청한 항목이고, 한 행은 조건에 맞게 찾은 조합입니다. 노드와 관계 자체를 요청하면 그래프로 연결을 볼 수도 있어요. 먼저 표로 센서 식별자와 태그를 확인한 뒤 그래프로 바꿔 보겠습니다.

> [조작] 입력칸 → Run → 결과가 나타날 아래 영역을 차례로 가리킨다. 첫 조회까지 왼쪽 패널을 유지한다. 실제 폭이 부족해 접어야 할 때만 “쿼리를 넓게 보려고 왼쪽 패널을 접겠습니다. 이 버튼으로 다시 펼칠 수 있어요”라고 말하며 접는다. 화면 밖에서 미리 접지 않는다.

이제 쿨러에 연결된 센서를 찾아볼게요. 위쪽 입력칸을 누르겠습니다.

## 한 단계 연결을 조회하기

먼저 매치에 쿨러에서 센서로 이어지는 패턴을 적겠습니다. 괄호 안은 노드이고, 가운데 화살표는 계측 관계입니다. 다음 줄은 시프트와 엔터를 함께 눌러 내려갈게요. 리턴에는 결과로 볼 쿨러 이름, 센서 식별자, 태그를 적겠습니다. 쿨러 식별자를 조건으로 넣었으니 같은 이름의 다른 장치와 섞이지 않습니다.

> [조작] Browser 입력칸에 MATCH (c:Component {id:'comp:cooler'})-[:MONITORED_BY]->(s:Sensor) RETURN c.name AS component, s.id AS sensor_id, s.tag AS tag;를 작성한다. Run을 말하며 클릭하고 결과를 확인한다. 입력 중 커서는 글자 아래 여백에 둔다.

두 행이 나왔습니다. 쿨러 이름은 같지만 센서 식별자는 서로 다르네요. 오일 쿨러 하나에 센서 두 개가 연결된 결과입니다. 태그는 씨이와 티에스원입니다. 쿨러가 두 개 생긴 것이 아니라, 연결된 센서마다 한 행씩 나온 거예요.

> [확인] 제공 예제의 쿨러는 TS1·CE에 연결된다. 다르게 나오면 대상 DB·식별자·관계 방향과 예제 적재 여부를 확인한다. 맞지 않는 결과를 지우거나 성공으로 읽지 않는다.

## 표와 그래프, 여러 단계 경로 비교하기

이번에는 같은 연결을 그림으로 보겠습니다. 위쪽 입력칸에 같은 패턴을 적되, 관계에 알이라는 변수를 붙일게요. 리턴에는 이름과 태그 대신 씨, 알, 에스를 넣습니다. 쿨러 노드와 관계, 센서 노드 자체를 돌려받는 문장입니다.

> [조작] 위쪽 입력칸 클릭 → MATCH (c:Component {id:'comp:cooler'})-[r:MONITORED_BY]->(s:Sensor) RETURN c,r,s; 작성.

오른쪽 런을 눌러 실행하겠습니다.

> [조작] Run 클릭. Graph 렌더와 Nodes (3), Relationships (2)를 실제 확인한 뒤 아래 결과를 설명한다.

이번에는 그래프가 나왔습니다. 쿨러 하나에서 센서 두 개로 연결돼 있네요. 앞의 표에서는 이 연결이 두 행으로 나왔고, 지금은 노드 세 개와 관계 두 개로 보입니다. 같은 데이터를 무엇으로 돌려받느냐에 따라 결과를 읽는 방식이 달라집니다.

다음에는 설비 한 대에서 출발해 보겠습니다. HYD-01의 구성 요소를 찾고, 센서를 거쳐 그 센서가 관측하는 물리량까지 따라가겠습니다.

> [조작] Asset→HAS_COMPONENT→Component→MONITORED_BY→Sensor→OBSERVES→StateVariable 경로. 설비 조건 code:'HYD-01', RETURN은 센서 태그·물리량 이름·단위·한계. 실행하고 원자료와 대조한다. 이 뒤 구간은 아직 촬영 전이다.

한계가 없는 물리량은 빈 값으로 나올 수 있습니다. 대상까지 못 찾은 것과 속성값이 없는 것은 다릅니다. WHERE에 한계 값이 있는 조건을 붙여 보고, 어떤 행이 빠졌는지 기록하겠습니다. 빈 값을 영으로 바꾸지는 않겠습니다.

## 구성 요소에서 교체 부품 찾기

같은 설비에서 이번에는 교체할 부품을 찾아보겠습니다. 센서를 찾던 길과 달리 구성 요소에서 부품을 쓰는 관계로 건너갑니다. 쿨러라는 장치와 그 안의 교체 부품인 쿨러 코어를 구별하고, 주문할 때 확인할 품번까지 함께 받겠습니다.

> [조작] MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)-[r:USES_PART]->(p:Part) RETURN c.id,c.name,p.id,p.name,p.partNo ORDER BY c.id;를 작성한다. 속성 반환 결과를 c,r,p의 그래프 반환과 비교하고 준비 안내의 세 부품 경로에 대조한다. 결과와 근거는 조회_기록.md에 남긴다.

## 집계한 값과 원래 행을 맞추기

이제 구성 요소별로 센서가 몇 개 연결되는지 보겠습니다. 먼저 원래 행에서 장치별 센서 식별자를 모아 세고, 그다음 질의의 집계와 비교합니다. 장치 이름과 식별자를 묶는 기준으로 두고 서로 다른 센서를 세겠습니다.

> [조작] Asset→Component→Sensor 질의에서 RETURN c.id,c.name,count(DISTINCT s) AS channels ORDER BY channels DESC,c.id를 작성한다. 집계 대조표에 원래 센서 목록·손으로 센 수·질의 결과를 기록한다. 센서가 없는 구성 요소는 이 MATCH 결과에 없음을 함께 적는다.

수만 맞는지 보지 않고 같은 센서를 셌는지도 확인합니다. 질의와 결과, 사용한 DB와 확인 시점을 저장하고 파일을 다시 열겠습니다. 이렇게 하면 나중에 숫자의 근거가 된 행까지 돌아갈 수 있습니다.

## 질의와 결과 저장하기

오늘 쓴 문장과 확인한 결과를 파일로 남기겠습니다. VS Code로 돌아가 조회_작성.cypher를 열고 실행했던 문장을 옮길게요. 조회_기록.md에는 어떤 질문이었는지, 실제로 나온 식별자와 원자료에서 확인한 근거를 함께 적겠습니다.

> [조작] Browser에서 실행한 문장을 선택·복사하는 과정을 설명하며 수행 → VS Code로 전환 → 조회_작성.cypher 열기·붙여넣기 → 조회_기록.md에 실제 결과 기록. 기록은 관찰한 내용만 사용한다.

파일을 수정한 뒤에는 컨트롤과 S를 함께 눌러 저장합니다. 두 파일을 각각 저장하고, 위쪽 탭을 닫았다가 왼쪽 목록에서 다시 열겠습니다. 방금 적은 문장과 결과가 남아 있는지 보겠습니다.

> [조작] 두 파일 저장 → 탭을 닫았다 다시 열어 문장·기록 보존 확인. 학생 결과의 외부 보관은 해당 가이드의 내보내기 경로를 사용하며, 학교 재부팅 뒤 로컬 보존을 약속하지 않는다.
