앞 이론에서는 그래프의 노드와 관계를 사이퍼 문장으로 표현하는 방법을 배웠습니다. 매치로 연결을 찾고, 웨어로 조건을 좁히고, 리턴으로 볼 항목을 정했죠. 이번에는 준비된 설비 예제에 직접 써 보겠습니다. 쿨러에 연결된 센서부터 찾고, 물리량과 교체 부품까지 따라가며 결과가 원자료와 맞는지 확인할 거예요.

VS Code는 이번 실습 파일을 열고 명령을 실행할 작업 공간입니다. 왼쪽의 파일 목록을 탐색기라고 해요. 여기에 이번 실습 폴더가 열렸는지 먼저 보겠습니다. START.md를 누르면 가운데에 시작 안내가 나옵니다. 파일 이름을 눌러 내용을 여는 방식이에요.

## Neo4j Browser에서 연결하고 화면 살펴보기

실습 안내의 링크를 열면 이렇게 접속 정보를 확인하는 창이 나옵니다. 지금 열린 도구가 Neo4j Browser입니다. 먼저 실습 데이터베이스에 연결하겠습니다.

> [조작] `랩_연결.json`의 browser 링크를 그대로 열고 자동 표시된 연결 창에서 시작한다. 주소는 현재 연결 파일의 connectURL이 포함된 값을 사용한다. 포트 번호를 이전 촬영값으로 고정하지 않는다. 기존 결과가 남은 화면을 첫 접속으로 사용하지 않는다. 연결 창을 닫았다가 다시 여는 조작을 추가하지 않는다. 아래 발화는 실제 미리 채워진 값과 터미널 출력을 대조한 뒤 사용한다.

접속 정보가 이미 들어 있네요. 프로토콜은 볼트이고, 그 옆이 연결할 주소입니다. 터미널에 나온 실습 DB 주소와 맞는지 확인하겠습니다. 사용자 이름은 네오포제이입니다. 이번 실습 DB는 비밀번호 없이 연결하도록 준비했으니 이 칸은 비워 두고, 아래 Connect를 누르겠습니다.

> [조작] 자동 입력된 Protocol `bolt://` → Connection URL → Database user `neo4j` → Password 빈칸을 차례로 가리켜 확인 → Connect 클릭. 맞는 값을 다시 입력하지 않는다. 실제 연결 성공 전 다음 발화를 하지 않는다. 처음 안내창은 아래 화면 정리 구간에서 설명하며 닫는다.

> [연결 후 발화] 왼쪽 위에 접속 주소와 데이터베이스 이름이 나타났습니다. 방금 준비한 실습 DB에 연결된 상태입니다. 포털의 지식 지도와는 별도이므로 여기에서 하는 조회가 포털 화면을 바꾸지는 않습니다.

> [촬영 준비] 새 실습을 시작하기 전에 이전 시연의 쿼리·결과·오류 카드와 입력을 비우고 메뉴를 닫는다. 학생 링크의 자동 연결 창에서 시작한다. 연결 뒤 새로 나타나는 소개 카드는 아래 안내와 함께 다루며, 이전 시연 결과와 혼동하지 않는다. 이어 찍는 장면은 직전 학습 결과와 패널 상태를 유지한다.

새 탭 기능을 알려 주는 안내가 나왔네요. 이번에는 스트림에서 쿼리를 실행할 거라, 디스미스를 눌러 닫겠습니다.

> [조작] 처음 안내가 나타난 경우에만 Dismiss를 누른다. 이미 닫힌 이어 찍기에서는 이 문장과 조작을 반복하지 않는다.

아래에는 소개 카드와 연결 결과가 있습니다. 쿼리 결과를 보기 편하도록 화면만 정리할게요. 위쪽 입력칸에 콜론 클리어를 적고 엔터를 누르겠습니다. 데이터는 그대로 두고 화면의 카드만 비우는 명령입니다.

> [조작] 위쪽 입력칸 클릭 → `:clear` 입력 → Enter. 명령이 남으면 입력칸을 비운다. 새 실습을 시작하기 전의 이전 시연 정리와 구분한다.

왼쪽 맨 위의 원통 모양 버튼이 데이터베이스 오버뷰입니다. 여기를 눌러 준비된 데이터의 종류를 확인하겠습니다.

> [조작] 왼쪽 패널이 접힌 경우 Open Sidebar를 안내하며 연 뒤 Database overview 클릭. 노드20·관계19 확인.

> [데이터 정보가 나온 뒤 발화] 노드 아래에는 설비, 구성 요소, 부품, 센서처럼 데이터의 종류가 나옵니다. 이론에서 배운 레이블입니다. 그 아래에는 구성, 계측, 관측처럼 연결을 구분하는 관계 유형이 있어요. 쿼리를 적을 때 이 이름과 방향을 사용합니다.

오른쪽 위 달러 표시 옆이 쿼리 입력칸입니다. 여기에 문장을 적고 오른쪽 런을 누르면 아래에 결과가 생깁니다. 먼저 노드 하나를 찾는 짧은 문장부터 실행해 볼게요.

> [조작] 입력칸 → Run → 결과가 나타날 아래 영역을 차례로 가리킨다. 첫 조회까지 왼쪽 패널을 유지한다. 실제 폭이 부족해 접어야 할 때만 “쿼리를 넓게 보려고 왼쪽 패널을 접겠습니다. 이 버튼으로 다시 펼칠 수 있어요”라고 말하며 접는다. 화면 밖에서 미리 접지 않는다.

이제 쿨러 노드 하나부터 찾아보겠습니다.

## 노드 하나부터 조회하기

위쪽 입력칸을 누르고 매치에 쿨러 노드를 적겠습니다. 괄호 안의 씨는 찾은 대상을 뒤에서 부를 이름이고, 콜론 뒤의 컴포넌트는 대상의 종류입니다. 중괄호에는 찾을 식별자를 넣겠습니다.

시프트와 엔터를 함께 눌러 다음 줄로 내려가겠습니다. 리턴에는 쿨러의 식별자와 이름을 적을게요. 에이에스 뒤에 붙인 이름은 결과 표의 열 제목입니다.

```cypher
MATCH (c:Component {id:'comp:cooler'})
RETURN c.id AS id, c.name AS name;
```

> [조작] 입력칸 클릭 → 첫 줄 입력 → Shift+Enter로 다음 줄 → RETURN 작성. “오른쪽 Run을 눌러 실행하겠습니다”라고 말하며 클릭. 결과가 나타난 뒤 설명한다.

> [결과 확인 뒤] 쿨러 식별자와 이름이 한 행으로 나왔습니다. 매치가 대상을 찾고, 리턴이 화면에서 볼 항목을 정한 결과입니다. 이제 이 노드에서 센서까지 관계를 하나 붙여 보겠습니다.

## 한 단계 연결을 조회하기

먼저 매치에 쿨러에서 센서로 이어지는 패턴을 적겠습니다. 괄호 안은 노드이고, 가운데 화살표는 계측 관계입니다. 다음 줄은 시프트와 엔터를 함께 눌러 내려갈게요. 리턴에는 결과로 볼 쿨러 이름, 센서 식별자, 태그를 적겠습니다. 쿨러 식별자를 조건으로 넣었으니 같은 이름의 다른 장치와 섞이지 않습니다.

> [조작] Browser 입력칸에 MATCH (c:Component {id:'comp:cooler'})-[:MONITORED_BY]->(s:Sensor) RETURN c.name AS component, s.id AS sensor_id, s.tag AS tag;를 작성한다. Run을 말하며 클릭하고 결과를 확인한다. 입력 중 커서는 글자 아래 여백에 둔다.

두 행이 나왔습니다. 쿨러 이름은 같지만 센서 식별자는 서로 다르네요. 오일 쿨러 하나에 센서 두 개가 연결된 결과입니다. 태그는 씨이와 티에스원입니다. 쿨러가 두 개 생긴 것이 아니라, 연결된 센서마다 한 행씩 나온 거예요.

> [확인] 제공 예제의 쿨러는 TS1·CE에 연결된다. 다르게 나오면 대상 DB·식별자·관계 방향과 예제 적재 여부를 확인한다. 맞지 않는 결과를 지우거나 성공으로 읽지 않는다.

## 표와 그래프, 여러 단계 경로 비교하기

이번에는 같은 연결을 그림으로 보겠습니다. 위쪽 입력칸에 같은 패턴을 적되, 관계에 알이라는 변수를 붙일게요. 리턴에는 이름과 태그 대신 씨, 알, 에스를 넣습니다. 쿨러 노드와 관계, 센서 노드 자체를 돌려받는 문장입니다.

> [조작] 위쪽 입력칸 클릭 → MATCH (c:Component {id:'comp:cooler'})-[r:MONITORED_BY]->(s:Sensor) RETURN c,r,s; 작성.

오른쪽 런을 눌러 실행하겠습니다.

> [조작] Run 클릭. Graph 렌더와 Nodes (3), Relationships (2)를 실제 확인한 뒤 아래 결과를 설명한다.

이번에는 그래프가 나왔습니다. 쿨러 하나에서 센서 두 개로 연결돼 있네요. 앞의 표에서는 이 연결이 두 행으로 나왔고, 지금은 노드 세 개와 관계 두 개로 보입니다. 같은 데이터를 무엇으로 돌려받느냐에 따라 결과를 읽는 방식이 달라집니다.

## 설비에서 물리량까지 따라가기

앞에서는 쿨러에서 센서까지 관계 하나를 따라갔습니다. 이제 결과 카드를 비우고 설비에서 출발해 보겠습니다. 첫 줄은 설비와 구성 요소, 다음 줄은 센서와 물리량으로 이어집니다. 앞에서 배운 관계 패턴을 연결한 문장입니다. 리턴에는 센서 태그, 물리량 이름, 단위와 한계를 적겠습니다.

```cypher
MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)-[:OBSERVES]->(v:StateVariable)
RETURN s.tag AS tag, v.name AS quantity, v.unit AS unit, v.limit AS limit
ORDER BY tag;
```

오른쪽 런을 눌러 실행하겠습니다.

> [조작] Run 클릭 → 실제 5행이 나타난 뒤 다음 설명.

다섯 행이 나왔습니다. 센서마다 관측하는 물리량과 단위를 함께 읽을 수 있습니다. 한계 칸이 빈 행도 있네요. 매치가 연결을 찾지 못한 것이 아니라, 찾은 물리량에 한계 속성값이 없는 경우입니다. 빈 값을 영이라고 읽으면 안 되겠죠.

## WHERE로 필요한 행 고르기

이론에서 배운 웨어로 결과를 좁혀 보겠습니다. 입력칸에 같은 경로를 적고, 리턴 앞에 한계가 널이 아니라는 조건을 넣겠습니다. 이즈 낫 널은 값이 있는지를 확인하는 조건입니다. 실행하기 전에 다섯 행 중 몇 행이 남을지 표에서 먼저 세어 보세요.

```cypher
MATCH (a:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)-[:OBSERVES]->(v:StateVariable)
WHERE v.limit IS NOT NULL
RETURN s.tag AS tag, v.name AS quantity, v.unit AS unit, v.limit AS limit
ORDER BY tag;
```

런을 눌러 조건을 적용하겠습니다.

> [조작] Run 클릭 → 실제 3행이 나타난 뒤 다음 설명.

세 행이 남았습니다. 압력, 온도, 진동 항목입니다. 조건을 넣기 전의 다섯 행과 비교하면 한계 값이 없던 두 행이 빠졌습니다. 매치로 연결을 찾고, 웨어로 필요한 행을 고른 뒤, 리턴으로 볼 항목을 정한 순서입니다.

## 구성 요소에서 교체 부품 찾기

앞 카드는 정리하고 다른 관계를 따라가 보겠습니다. 설비에서 구성 요소까지는 같지만, 이번에는 센서 대신 부품을 찾습니다. 유즈즈 파트라는 관계가 달라졌네요. 리턴에 장치 이름과 부품 이름, 품번을 적겠습니다. 마지막 오더 바이는 결과를 장치 식별자 순서로 정렬합니다.

```cypher
MATCH (:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:USES_PART]->(p:Part)
RETURN c.name AS component, p.name AS part, p.partNo AS part_no
ORDER BY c.id;
```

런을 눌러 부품 목록을 보겠습니다.

> [조작] Run 클릭 → 실제 3행이 나타난 뒤 다음 설명.

세 장치에 연결된 부품과 품번이 나왔습니다. 오일 쿨러는 장치 이름이고, 쿨러 코어는 그 장치에 쓰이는 부품입니다. 이름이 비슷해도 서로 다른 대상이네요. 같은 출발점에서 관계를 바꾸면 답할 수 있는 질문도 달라집니다.

## 집계한 값과 원래 행을 맞추기

이제 앞 카드를 비우고 구성 요소별 센서 수를 세겠습니다. 센서까지 찾는 패턴을 다시 쓰고, 리턴에 장치 식별자와 이름을 넣겠습니다. 컬렉트는 센서 태그를 목록으로 모으고, 카운트는 센서 수를 셉니다. 디스팅트를 넣어 같은 센서를 중복으로 세지 않겠습니다.

```cypher
MATCH (:Asset {code:'HYD-01'})-[:HAS_COMPONENT]->(c:Component)
      -[:MONITORED_BY]->(s:Sensor)
RETURN c.id AS component_id, c.name AS component,
       collect(DISTINCT s.tag) AS tags, count(DISTINCT s) AS channels
ORDER BY channels DESC, component_id;
```

런을 눌러 센서 목록과 수를 함께 보겠습니다.

> [조작] Run 클릭 → 실제 3행이 나타난 뒤 다음 설명.

쿨러와 주 펌프는 센서가 둘씩이고, 팬은 하나입니다. 태그 목록을 직접 세어 오른쪽 숫자와 비교해 보세요. 여기서 센서가 없는 구성 요소는 영으로 표시되지 않습니다. 센서까지 연결되는 패턴을 찾았으므로 결과에 나오지 않는 것입니다. 이 차이까지 조회 기록에 남기겠습니다.

## 질의와 결과 저장하기

오늘 쓴 문장과 확인한 결과를 파일로 남기겠습니다. VS Code로 돌아가 조회_작성.cypher를 열고 실행했던 문장을 옮길게요. 조회_기록.md에는 어떤 질문이었는지, 실제로 나온 식별자와 원자료에서 확인한 근거를 함께 적겠습니다.

> [조작] Browser에서 실행한 문장을 선택·복사하는 과정을 설명하며 수행 → VS Code로 전환 → 조회_작성.cypher 열기·붙여넣기 → 조회_기록.md에 실제 결과 기록. 기록은 관찰한 내용만 사용한다.

파일을 수정한 뒤에는 컨트롤과 S를 함께 눌러 저장합니다. 두 파일을 각각 저장하고, 위쪽 탭을 닫았다가 왼쪽 목록에서 다시 열겠습니다. 방금 적은 문장과 결과가 남아 있는지 보겠습니다.

> [조작] 두 파일 저장 → 탭을 닫았다 다시 열어 문장·기록 보존 확인. 학생 결과의 외부 보관은 해당 가이드의 내보내기 경로를 사용하며, 학교 재부팅 뒤 로컬 보존을 약속하지 않는다.
