# 7-3 · 필요한 운전 조건을 사람에게 묻고 판단 이어 가기

## 만들 것

모자란 정보가 있으면 질문을 남기고 멈췄다가, 사람이 답하면 멈춘 자리에서 이어 추천안을 완성하는 프로그램 `work/hitl.py`.

## 왜 만드나

에이전트가 스스로 확인할 수 없는 정보가 있습니다. "오늘 장치를 얼마나 멈출 수 있는가"는 현장 사람만 압니다. 이때 그럴듯한 값을 가정하고 진행하면 틀린 추천이 나옵니다. 대신 멈추고, 묻고, 답을 받은 뒤 이어 갑니다. 멈춘 동안에도 "무엇을 기다리는지"가 남아 있어야 나중에 이어 갈 수 있습니다. 사람이 판단에 참여하는 이 방식을 HITL이라고 부릅니다.

## 주어지는 자료

- `day7/inputs/case_no_window.json` — 앞 랩과 같은 사례인데 작업 가능 시간(`available_minutes`)이 비어 있다
- `day7/inputs/case_base.json` — 정보가 모두 있는 사례
- 첫 랩의 `work/recommend.py`

## Claude Code에 전달할 요구사항의 뼈대

- **목표**: 추천에 필요한 정보가 비어 있으면 묻고 기다리고, 답을 받으면 이어서 끝낸다.
- **명령 두 개**
  - `python work/hitl.py start --case <사례 파일>`: 판단을 시작한다. 모자란 정보가 있으면 질문을 남기고 멈춘다. 없으면 바로 끝낸다.
  - `python work/hitl.py resume --answer <답>`: 멈춘 판단에 사람의 답을 넣고 이어서 끝낸다.
- **멈춘 상태**는 `work/day7/hitl_state.json`에 저장한다. 프로그램이 끝났다가 다시 실행돼도 이어 갈 수 있어야 한다.
- **출력 모양**(두 명령 모두 화면에 JSON)

```json
{"status": "질문 대기", "case_id": "…", "missing": ["available_minutes"], "question": "…", "answers": [], "proposal": null}
```

```json
{"status": "완료", "case_id": "…", "missing": [], "question": null, "answers": [{"field": "available_minutes", "value": 30, "by": "사람"}], "proposal": {}}
```

- **꼭 지킬 것**
  - 비어 있는 값을 가정으로 채우지 않는다.
  - 추천안은 첫 랩의 순위 규칙으로 만든다(`recommend.py`를 다시 쓴다).
  - 숫자가 아닌 답은 받지 않고 계속 기다린다(종료 코드가 0이 아니다).
  - 기다리는 질문이 없는데 `resume`을 하면 오류로 알린다.
  - 사람이 준 답을 기록에 남긴다.
- **완료 기준**: 시간이 빈 사례로 시작하면 멈추고, 30분이라고 답하면 팬 속도 올리기가, 120분이라고 답하면 정지 후 핀 세척이 추천된다.

직접 해 봅니다. `start`를 실행하고, 터미널을 닫았다가 다시 열어 `resume`을 실행해도 이어지는지 봅니다. 이 질문은 "정보를 묻는 것"입니다. 조치를 실행해도 되는지 승인받는 것과는 다릅니다.

## 무엇이 나오면 성공

```
python -m labcheck 7-3
```

- 작업 가능 시간이 비면 추천하지 않고 멈추고, 무엇이 없는지와 질문이 나온다
- 멈춘 상태가 파일에 남는다
- 숫자가 아닌 답은 받지 않고 계속 기다린다
- 답을 받으면 이어서 끝내고, 답에 따라 추천이 달라진다
- 사람이 준 답이 기록에 남는다
- 기다리는 질문이 없을 때 이어 가라고 하면 오류로 알린다
- 모자란 정보가 없으면 묻지 않고 바로 끝낸다
