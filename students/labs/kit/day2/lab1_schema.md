# 2-1 · 연습용 설비의 클래스·관계 스키마 만들기

## 만들 것

소형 냉각장치를 그래프에 담기 위한 약속(스키마) 파일 `work/schema.json`, 그리고 그 약속 가운데 "같은 번호는 하나만"을 연습용 그래프에 실제로 거는 프로그램 `work/apply_schema.py`.

## 왜 만드나

자료를 넣기 전에 "무엇을 어떤 이름표로, 무엇과 무엇을 어느 방향으로 잇는가"를 먼저 정해야 나중에 찾을 수 있습니다. 관계 하나가 빠지거나 방향이 뒤집히면 그 길로는 아무것도 찾지 못합니다. 오늘은 코드를 치는 대신, Claude Code에게 요구를 전하고 만들어진 관계와 식별자가 요구대로인지 확인하는 연습을 합니다.

## 주어지는 자료

- `cooler/cooler.md` — 설비, 부품, 센서 소개
- `cooler/schema_guide.md` — 클래스 · 관계 이름과 스키마 파일의 모양

## Claude Code에 전달할 요구사항의 뼈대

- **목표**: 소형 냉각장치의 설비 · 부품 · 센서를 담을 스키마 파일을 만들고, 중복 금지 조건을 연습용 그래프에 적용한다.
- **입력 자료**: 위 두 문서. 연결 정보는 `.env`에 있고 `labkit.graph`로 그래프에 붙는다.
- **꼭 들어갈 것**
  - 클래스 Asset · Component · Sensor와 각 클래스의 필수 속성(스키마 설명의 표)
  - 관계 세 가지와 방향: 설비 → 부품, 설비 → 센서, 부품 → 센서
  - 클래스마다 `id`가 겹치지 않는다는 조건(`unique`)
- **완료 기준**: `work/schema.json`이 스키마 설명의 모양을 따르고, `python work/apply_schema.py`를 실행하면 스키마 파일의 중복 금지 조건이 그래프의 고유 제약으로 만들어진다. 여러 번 실행해도 오류가 없다.

요구를 전할 때 "어떤 클래스가 필요한가"를 Claude Code가 정하게 두지 말고, 스키마 설명에서 내가 골라 말해 줍니다. 결과를 받으면 빠진 관계가 없는지 먼저 봅니다. 빠졌으면 "이 관계를 더해 달라"고 고쳐 달라고 합니다.

## 무엇이 나오면 성공

```
python -m labcheck 2-1
```

- 스키마 파일에 세 클래스와 필수 속성, 중복 금지 조건이 있다
- 관계 세 가지가 있고 방향이 맞다
- 그래프에 Asset · Component · Sensor의 `id` 고유 제약이 있다

Neo4j Browser(`http://127.0.0.1:17474`)에서 `SHOW CONSTRAINTS`를 실행해 제약 세 개가 보이는지도 눈으로 확인합니다.
