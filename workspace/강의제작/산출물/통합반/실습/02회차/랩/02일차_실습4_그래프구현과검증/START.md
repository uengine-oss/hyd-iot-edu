# 설계한 온톨로지를 그래프 DB에 구현하고 검증하기

## 목표

「현장 정보를 체계화하는 온톨로지 직접 설계하기」에서는 설비 · 센서 · 부품을 종류(이론의 클래스 — 공통 특성을 가진 대상의 유형) · 속성 · 관계로 정의해 모델을 만들었습니다. 이번에는 제공된 설비 · 센서 · 부품 모델(또는 내가 만든 모델)을 이 폴더 전용 랩 DB(그래프 DB)에 적재하고, 질문마다 조회문을 만들어 원자료와 대조합니다. 스키마의 ID와 관계 방향이 그래프의 노드 · 관계로 어떻게 옮겨지는지 직접 봅니다.

그래프에 넣은 자료는 한 번으로 끝나지 않습니다. 수정본이 들어오면 전체를 지우고 다시 넣지 않고 필요한 대상만 고쳐야 다른 곳에서 쓰던 ID와 연결이 그대로 남고, 같은 적재를 다시 실행해도 대상이 늘지 않아야 믿고 다시 돌릴 수 있습니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 첫 단계인 온톨로지의 구현과 검증 — 설계한 모델을 그래프 DB에 옮기고, 질문에 실제로 답하는지 원자료와 대조하는 일 — 를 맡습니다.

만들 것: 모델을 랩 DB에 넣는 적재문(또는 적재 코드), 질문별 조회문, 수정본을 반영하는 수정문, `결과/검증_기록.md`.

## 출발점

- `입력/schema.json` · `입력/graph.json` — 제공된 설비 · 센서 · 부품 모델. 설비 7대 · 구성 요소 · 센서 · 물리량 · 부품과 그 연결이 들어 있습니다.
- `입력/자료/` — 그 모델의 원자료(기준일 2026-10-15). `입력/자료_변경분/2026-10-20_수정본/` — 기준일 뒤 담당자들이 고친 줄만 모은 수정본.
- `입력/요구사항.md` · `입력/자료_검토.md` — 제공된 모델이 답하는 질문과 자료 처리 근거.
- `lab_db.py` — 이 폴더 전용 랩 DB를 켜는 도구. `결과/` — 이번에 만든 것을 두는 자리(「제공 빈 틀」 `검증_기록.md`).
- `AGENTS.md` · `.github/copilot-instructions.md` · `CLAUDE.md` — Codex와 GitHub Copilot이 지키는 작업 규칙(세 파일이 같은 내용). 학생도 함께 읽습니다.
- 내 모델을 쓸 때: 제공 입력은 그대로 두고 내 `schema.json` · `graph.json`을 `결과/내_모델/`에 복사해 씁니다. 만든 날짜 · 질문 · 파일 형식 · ID가 이번 입력과 맞는지 먼저 보고, 관계 이름이나 방향이 다르면 내 모델의 정의로 조회합니다. 내 모델이 없어도 제공된 모델로 끝까지 할 수 있습니다.

## 처음 쓰는 도구

- **랩 DB**: 이 폴더 전용으로 켜는 그래프 DB(이 실습에서는 Neo4j)입니다. 포털 DB와 분리돼 있어 지우거나 다시 적재해도 포털에 영향이 없습니다. `python lab_db.py`가 Docker로 켜고 Neo4j Browser를 엽니다.
- **Neo4j Browser**: 위쪽 입력 칸에 Cypher를 붙여 넣고 실행(▶)합니다. 결과는 그래프 또는 표(Table)로 볼 수 있고, 표가 원자료와 대조하기 쉽습니다.
- 수백 개의 대상을 손으로 적재문에 옮기지 않습니다. AI에게 모델 파일을 읽어 적재문이나 적재 코드를 만들게 하고, 실행 결과의 개수로 확인합니다.
- **명령 실행 승인 창**: AI가 Docker나 랩 DB 주소에 접속하는 명령을 실행하려 하면 이 폴더 밖 실행을 허락할지 묻는 창이 뜹니다. 명령이 `python lab_db.py` · 이 폴더의 적재 · 조회 명령이고 주소가 `127.0.0.1`의 랩 DB인지 보고 「Allow once」, 아니면 「Deny」를 누릅니다.

## 해결할 질문

아래 질문의 답은 보전팀이 지금 가동하는 설비의 예비품 준비를 정할 때 씁니다.

1. 설비별로 어떤 구성 요소에 어떤 센서 · 계산값 · 설정값이 붙어 있고, 각 센서의 물리량 · 단위 · 한계는 무엇인가?
2. 설비별로 구성 요소마다 어떤 교체 부품이 들어가고, 여러 설비가 함께 쓰는 부품은 어느 설비 · 구성 요소에서 쓰는가? 다른 표기로 적힌 품번이나 원자료에 없는 품번으로 물으면 결과가 어떻게 구별되는가?
3. 수정본을 반영한 뒤에도 같은 ID가 유지되고, 같은 적재를 다시 실행해도 대상과 관계가 늘지 않는가?
4. 포털 실습에서 본 기준 지도와 견주면 내 그래프의 식별자 · 관계 방향이 어디서 같고 어디서 다른가?

## 학생이 정할 것

원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 `결과/검증_기록.md` 「정한 것」 표에 적습니다.

- **시점과 상태** — 설비 대장의 상태와 수정본에서 바뀐 상태를 그래프에 어떻게 반영하고, 「지금 가동하는 설비」를 묻는 부품의 사용 설비 조회에 어떻게 드러낼지(답에서 빠지는지, 상태와 함께 보이는지)

AI에게 이 지점을 대신 정하게 하지 않습니다. AI가 고를 것을 내놓거나 「권장」을 붙여도 그대로 따르지 말고, 원문 줄을 열어 내 선택과 근거를 말합니다. 못 정한 지점은 미결로 남깁니다.

## 이번 범위 밖

- 공급 조건 · 입고 이력의 적재와 조회
- 모델의 종류 · 속성 · 관계 정의를 새로 바꾸는 일(이상한 곳은 `결과/검증_기록.md`에 적습니다)
- 포털 DB에 접속하거나 포털 자료를 랩 DB에 넣는 일

자료에 있어도 이번 결과에 만들지 않습니다.

## 결과 형식

`결과/`에 아래 파일을 둡니다. 파일 안에서 무엇을 어떤 문장으로 쓸지는 직접 정합니다.

- `결과/load.cypher`(또는 적재 코드): 모델 파일의 대상과 관계를 랩 DB에 넣습니다. 같은 파일을 다시 실행해도 됩니다.
- `결과/update.cypher`(또는 수정 코드): 수정본의 줄을 이미 넣은 그래프에 반영합니다.
- `결과/query.cypher`: 질문마다 조회문 하나. 조회문 위에 어느 질문의 조회인지 주석(`// 질문 1`)으로 적습니다.
- `결과/검증_기록.md`: 「제공 빈 틀」의 칸대로 채웁니다.

## 진행 단계

한 번에 한 단계씩 갑니다. 단계마다 결과를 확인한 뒤 다음 단계로 갑니다. 단계마다 정하거나 물을 것, 요청에 담을 것, 판단할 증거는 `guide.html`의 같은 번호에 있습니다.

1. **폴더와 출발점 확인** — VS Code 탐색기에서 `입력/`(제공된 모델 · 원자료 · 수정본) · `결과/` · `lab_db.py` · START.md를 열어 각 자리의 역할과 이번 질문을 확인합니다.
2. **랩 DB 켜기** — 터미널에서 `python lab_db.py`를 실행해 이 폴더 전용 랩 DB를 켜고, 열린 Neo4j Browser에 연결합니다.
3. **파일을 바꾸지 않고 자료 파악** — AI에게 파일을 바꾸지 말고, `입력/graph.json`에 어떤 종류의 대상과 관계가 몇 개 있는지와 수정본의 줄마다 그래프의 어느 대상을 가리키는지 파일 · 줄로 짚어 달라고 합니다. 짚은 줄을 직접 엽니다.
4. **요구와 기대 답 정하기** — 질문 · 이 답을 쓰는 사람 · 지킬 조건과, 설비 하나의 구성 요소별 센서 · 교체 부품과 공용 부품 하나의 사용 설비, 수정본 반영 뒤 달라져야 할 것을 원자료에서 직접 찾아 기대 답으로 `결과/검증_기록.md`에 편집기에서 적습니다. 「학생이 정할 것」의 지점마다 고른 것과 근거 줄을 적습니다. 다 적으면 AI에게는 파일을 바꾸지 말고 내가 적은 것을 되짚게만 합니다.
5. **적재 계획 검토** — 대상과 관계를 어떤 문장으로 어떤 순서로 넣을지 AI의 계획을 받아 검토합니다. 스키마의 ID와 관계 방향이 그래프의 노드 · 관계로 어떻게 옮겨지는지 짚습니다. 아직 파일을 만들지 않습니다.
6. **구현 ① 적재하기** — 모델 파일의 대상과 관계를 랩 DB에 넣는 적재문(또는 적재 코드)을 `결과/`에 만들고 실행합니다.
7. **같은 적재 다시 실행** — 같은 적재를 한 번 더 실행하고 종류별 개수를 첫 실행과 비교합니다.
8. **구현 ② 설비별 센서 조회** — 설비 하나를 받아 구성 요소별 센서와 그 물리량 · 단위 · 한계를 돌려주는 조회를 `결과/query.cypher`에 만들고 실행합니다.
9. **구현 ③ 설비별 교체 부품 조회** — 설비 하나를 받아 구성 요소마다 들어가는 교체 부품(사내 품번 · 품명)을 돌려주는 조회를 더하고 실행합니다.
10. **구현 ④ 부품의 사용 설비 조회** — 품번이나 표기 하나를 받아 그 부품을 쓰는 설비 · 구성 요소를 돌려주는 조회를 더하고 실행합니다. 설비의 상태(설비 대장의 「상태」 칸)는 「정한 것」 표의 결정대로 결과에 반영합니다.
11. **구현 ⑤ 수정본 반영하기** — 수정본의 줄마다 필요한 대상 · 관계만 고치는 수정문(또는 수정 코드)을 `결과/`에 만들고 실행합니다. 적재문이 모델 파일의 값을 덮어쓰게 짜여 있으면 적재를 다시 실행할 때 고친 값이 되돌아가므로, 다시 넣을 때는 늘 적재 → 수정 순서로 실행합니다.
12. **포털 기준 지도와 비교** — 포털 실습 「설비 지식의 구조와 연결 관계 탐색하기」에서 펼쳐 본 기준 지도의 설비 → 쿨러 → 센서와, 랩 DB에서 같은 역할을 하는 대상의 식별자와 관계의 시작 · 끝을 `결과/검증_기록.md`에 나란히 적습니다. 포털은 다시 열지 않고 가이드(`guide.html`) 이 단계에 실린 포털 기준 지도 표로 봅니다.
13. **저장하고 다시 열기** — 적재 · 수정 · 조회 파일과 검증 기록을 저장하고, VS Code에서 폴더를 닫았다 다시 연 뒤 랩 DB를 다시 켜고 10단계 조회를 다시 실행합니다. 기록 끝에 기준일 · 수정본 날짜 · 저장 시점 · 확인하지 못한 점을 적습니다.

이 순서는 바이브 코딩 일곱 단계 — 파일을 바꾸지 않고 파악 → 요구와 기대 답을 내 말로 → 계획 검토 → 작게 구현 → 원자료와 대조 → 고침 → 저장하고 다시 열기 — 를 따릅니다.

요청에 파일 이름을 쓸 때는 `결과/schema.json`처럼 백틱(`)으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다.

## 확인

확인할 사례의 종류(어느 행이 해당하는지는 원자료에서 직접 찾습니다):

- 설비별 구성 요소 · 센서 개수
- 한계 방향과 한계 없음
- 설비에 바로 붙은 센서
- 설비별 교체 부품과 교체 부품이 없는 구성 요소
- 공용 부품과 전용 부품
- 상태가 가동이 아닌 설비도 쓰는 공용 부품
- 다른 표기 · 없는 품번
- 수정본의 이름 변경 · 상태 변경 · 값 보완 · 줄 삭제가 바꾸는 그래프의 대상 · 관계
- 반영 뒤 원자료와 다시 센 개수 · 값(「삭제」 줄이 걸린 설비 포함)
- 같은 적재 두 번 · 같은 수정 두 번

실행 명령:

```
python lab_db.py
(적재 · 수정 · 조회문은 열린 Neo4j Browser에서 실행하거나, 만든 코드로 실행합니다)
```

바뀐 파일 확인: AI가 단계를 마칠 때마다 바뀐 파일 목록을 봅니다. `입력/`(원자료 · 수정본 포함)이 바뀌지 않았는지, 요청하지 않은 파일이 생기지 않았는지 확인합니다. 편집 승인 창에서는 경로가 `결과/` 아래일 때만 허용합니다.

## 완료 판정

형식 검사나 실행 성공만으로 완료하지 않습니다. 질문마다 원자료에서 먼저 적은 기대 답과 실제 조회 결과가 맞고, 같은 적재 · 같은 수정을 다시 해도 개수가 같으며, 「정한 것」마다 근거 줄과 그 선택으로 바뀌는 답을 설명할 수 있으면 완료입니다. 고친 점과 확인하지 못한 점은 `결과/검증_기록.md`에 짧게 남깁니다.

## 저장과 다음 실습

적재 · 수정 · 조회 파일과 `검증_기록.md`를 함께 보관합니다. 기록에는 반영한 자료의 기준일과 수정본 날짜를 적습니다. 다음 실습 「작업 절차와 판단 조건을 연결해 조치 기준 만들기」는 이 설비 모델의 ID에 작업 절차와 판단 조건을 잇습니다. 그 실습도 제공된 모델로 시작할 수 있으므로 이 결과는 골라서 가져갑니다. 재부팅 전에 이 실습 폴더를 USB 또는 개인 클라우드에 복사합니다. 자동으로 되살려 주지 않습니다.
