설계한 온톨로지를 그래프 DB에 구현하고 검증하기

설비 · 센서 · 부품 모델을 이 폴더 전용 그래프 DB에 적재하고, 질문마다 조회문을 만들어 원자료와 대조합니다. 다시 적재하고 수정본을 반영해도 ID와 개수가 맞는지 확인하고, 끝으로 포털 실습에서 본 기준 지도와 견줍니다. 진행은 파일을 바꾸지 않고 자료 파악 → 요구와 기대 답 정하기 → 계획 검토 → 기능 하나씩 구현하며 원자료와 대조 → 저장하고 다시 열기 순서입니다.

01 폴더와 출발점 확인

「현장 정보를 체계화하는 온톨로지 직접 설계하기」에서는 설비 · 센서 · 부품을 종류 · 속성 · 관계로 정의해 모델을 만들었습니다. 이번에는 제공된 설비 · 센서 · 부품 모델(또는 내가 만든 모델)을 이 폴더 전용 랩 DB(그래프 DB)에 적재하고, 질문마다 조회문을 만들어 원자료와 대조합니다. 스키마의 ID와 관계 방향이 그래프의 노드 · 관계로 어떻게 옮겨지는지 직접 봅니다.

그래프에 넣은 자료는 한 번으로 끝나지 않습니다. 수정본이 들어오면 전체를 지우고 다시 넣지 않고 필요한 대상만 고쳐야 다른 곳에서 쓰던 ID와 연결이 그대로 남고, 같은 적재를 다시 실행해도 대상이 늘지 않아야 믿고 다시 돌릴 수 있습니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 첫 단계인 온톨로지의 구현과 검증 — 설계한 모델을 그래프 DB에 옮기고, 질문에 실제로 답하는지 원자료와 대조하는 일 — 를 맡습니다.

받기 이 폴더는 「실습 시작」 도구로 받습니다. 도구에서 과정 → 회차 → 실습을 고르고 새로 시작을 누르면 이 판본만 새 폴더에 받아 풀고, VS Code에 이 폴더와 START.md를, 브라우저에 이 가이드를 엽니다. 이어서 할 때는 이전 작업 열기를 누릅니다 — 새로 시작은 늘 새 폴더에 받으므로 고친 파일을 덮지 않습니다. 받기에 실패하면 한 번 더 시도하고, 그래도 안 되면 수동 ZIP으로 받은 ZIP을 풀어 VS Code의 파일 → 폴더 열기(File → Open Folder)로 그 폴더를 엽니다.

필요한 것 VS Code와 Python, 로그인해 둔 Codex 또는 GitHub Copilot, 랩 DB를 켤 Docker Desktop.

AI 계정이 없으면 실습 폴더와 따로 받는 학생용 완성본 묶음(계정이 없는 학생이 결과를 확인하는 용도)으로 결과를 확인하세요.

해결할 질문 아래 질문의 답은 보전팀이 지금 가동하는 설비의 예비품 준비를 정할 때 씁니다.

  1. 설비별로 어떤 구성 요소에 어떤 센서 · 계산값 · 설정값이 붙어 있고, 각 센서의 물리량 · 단위 · 한계는 무엇인가?
  2. 설비별로 구성 요소마다 어떤 교체 부품이 들어가고, 여러 설비가 함께 쓰는 부품은 어느 설비 · 구성 요소에서 쓰는가? 다른 표기로 적힌 품번이나 원자료에 없는 품번으로 물으면 결과가 어떻게 구별되는가?
  3. 수정본을 반영한 뒤에도 같은 ID가 유지되고, 같은 적재를 다시 실행해도 대상과 관계가 늘지 않는가?
  4. 포털 실습에서 본 기준 지도와 견주면 내 그래프의 식별자 · 관계 방향이 어디서 같고 어디서 다른가?

말 풀이 계산값은 계기 없이 다른 값으로 계산해 내는 값이고, 설정값은 사람이 정해 넣는 목표 값입니다. 적재는 모델 파일의 대상과 관계를 그래프 DB에 넣는 일이고, 수정본은 기준일 뒤 담당자들이 고친 줄만 모은 자료입니다.

내 모델을 쓸 때: 제공 입력은 그대로 두고 내 schema.json · graph.json을 결과/내_모델/에 복사해 씁니다. 만든 날짜 · 질문 · 파일 형식 · ID가 이번 입력과 맞는지 먼저 보고, 관계 이름이나 방향이 다르면 내 모델의 정의로 조회합니다. 내 모델이 없어도 제공된 모델로 끝까지 할 수 있습니다.

왜 하는가 만들기 전에 무엇이 주어졌고 무엇을 만들어야 하는지 알아야 AI에게도 같은 출발점을 말할 수 있습니다. 이 답을 누가 어디에 쓰는지에 따라 무엇을 하나로 보고 무엇을 따로 둘지가 달라지므로, 쓰는 사람도 여기서 확인합니다. 제공된 모델과 내가 만든 모델 가운데 무엇을 쓸지 여기서 정해야 뒤에서 개수를 견줄 기준이 하나로 정해집니다.

02 랩 DB 켜기

왜 하는가 이 실습의 적재 · 조회는 이 폴더에만 딸린 그래프 DB에서 합니다. 포털 DB와 떨어져 있어 여러 번 넣고 지워도 포털에 영향이 없고, 처음에 비어 있는 것을 확인해 두어야 뒤에서 센 개수가 모두 이번에 넣은 것임을 믿을 수 있습니다.

할 일 터미널에서 python lab_db.py를 실행해 이 폴더 전용 랩 DB를 켜고, 열린 Neo4j Browser에 연결합니다.

메뉴에서 터미널 → 새 터미널(Terminal → New Terminal)을 누릅니다. 아래쪽에 열린 터미널의 맨 앞 경로가 이 실습 폴더인지 봅니다. 명령은 직접 치지 말고 블록의 복사를 눌러 붙여 넣은 뒤 Enter를 누릅니다 — 손으로 옮기면 오타가 나기 쉽습니다. 명령이 오류로 멈추면 실행한 명령과 출력 전문을 복사해 AI 채팅에 보내고, 무엇이 왜 멈췄는지 먼저 설명해 달라고 합니다.

랩 DB는 Docker로 켜므로 명령 전에 Docker Desktop을 켜 둡니다. 처음 한 번은 DB 이미지를 내려받아 시간이 더 걸립니다.

정하거나 물을 것 출력된 주소가 127.0.0.1의 이 폴더 전용 주소인지 확인합니다.

명령

터미널 명령 · PowerShell · 이 실습 폴더에서

python lab_db.py

「랩 DB 준비 완료」가 나오면 브라우저에 Neo4j Browser 연결 창이 열립니다. Protocol이 bolt://이고 Connection URL이 터미널 출력의 「Connect URL」과 같은 127.0.0.1:포트인지 보고(비어 있으면 그 127.0.0.1:포트를 넣습니다), Database user는 neo4j, Password는 비워 둔 채 Connect를 누릅니다 — 이 랩 DB는 이 PC 안에서만 열리고 비밀번호 없이 켜지기 때문입니다. 연결 정보는 랩_연결.json에도 저장됩니다. Neo4j Browser는 위쪽 입력 칸에 Cypher를 붙여 넣고 실행(▶)하는 화면이고, 결과는 그래프나 표(Table)로 볼 수 있습니다. 원자료와 줄마다 견줄 때는 표가 편합니다.

개수 조회 종류별 노드 수와 관계 수를 세는 두 질의입니다. 뒤에서 적재 · 수정 뒤 개수를 견줄 때도 이 둘을 씁니다.

Neo4j Browser 질의 · 위쪽 입력 칸에서

MATCH (n) RETURN labels(n)[0] AS 종류, count(*) AS 개수 ORDER BY 종류

Neo4j Browser 질의 · 위쪽 입력 칸에서

MATCH ()-[r]->() RETURN type(r) AS 관계, count(*) AS 개수 ORDER BY 관계

막히면 「랩 DB 준비 확인 필요:」로 시작하는 줄이 나오면 랩 DB를 켜지 못한 것입니다. 그 뒤에 Docker에 연결하지 못했다는 글이 있으면 Docker Desktop이 켜져 있는지 보고 같은 명령을 다시 실행합니다. 「이 실습에서 만든 DB가 아닙니다」가 나오면 다른 실습 폴더의 랩_연결.json이 이 폴더에 들어온 것이니, 그 파일을 이 폴더에서 만든 것인지 확인합니다. 「이 PC의 Docker에 없습니다」로 시작하는 줄 뒤에 「랩 DB 준비 완료」가 나오면 멈춘 것이 아닙니다 — 폴더를 USB 등으로 다른 PC에서 옮겨 왔거나 전에 쓰던 DB가 지워져서 이 폴더 전용 랩 DB를 새로 만든 것이고, 새 DB는 비어 있습니다.

판단할 증거 「랩 DB 준비 완료」와 주소가 나왔고, 처음 켰을 때 Browser의 두 개수 조회가 빈 결과(이 폴더 전용 DB가 아직 비어 있음)를 보입니다.
다를 때 처음 켰는데 개수 조회에 대상이 보이면 연결한 주소가 터미널 출력의 주소와 같은지 봅니다. 이전 작업을 연 경우에는 전에 이 폴더에서 넣은 대상의 개수가 보이는 것이 맞습니다.
증거를 확인한 뒤 다음 단계로 갑니다.

03 파일을 바꾸지 않고 자료 파악

왜 하는가 적재가 맞았는지는 모델 파일에 무엇이 몇 개 있는지를 먼저 알아야 셀 수 있습니다. 수정본은 줄마다 그래프의 어느 대상에 닿는지 알아야 필요한 곳만 고칠 수 있습니다.

할 일 AI에게 파일을 바꾸지 말고, 입력/graph.json에 어떤 종류의 대상과 관계가 몇 개 있는지와 수정본의 줄마다 그래프의 어느 대상을 가리키는지 파일 · 줄로 짚어 달라고 합니다. 짚은 줄을 직접 엽니다.

Codex는 왼쪽 활동 표시줄의 Codex 아이콘을 누르면 채팅 창이 열립니다. 입력하기 전에 창 위쪽 탭이 Codex인지 확인합니다. GitHub Copilot을 쓰면 같은 창의 Chat 탭을 엽니다(처음 열면 GitHub 로그인 창이 뜹니다). 창 아래 입력 칸에 요청을 내 말로 적어 보내고, 답에 나온 파일을 왼쪽 탐색기에서 열어 가운데 편집기의 실제 줄을 읽습니다. AI가 「완료」라고 해도 실제 파일과 실행 출력으로 확인합니다.

AI가 파일을 만들거나 고치려 하면 편집 승인 창(Allow ChatGPT to edit the following file?)이 뜹니다. 창에 적힌 경로가 결과/ 아래이고 내가 요청한 변경이면 Allow once(이번 한 번 허용)를 누르고, 입력/ · 자료/의 파일이거나 요청하지 않은 파일이면 Deny(거부)를 누른 뒤 까닭을 채팅으로 알립니다. GitHub Copilot을 쓰면 바뀐 파일의 경로를 같은 기준으로 보고, 요청하지 않은 변경은 되돌립니다.

정하거나 물을 것 수정본에서 무엇이 바뀌는지(이름 · 상태 · 값 · 줄 삭제), 제공된 모델의 ID가 무엇으로 지어졌는지 묻습니다.

요청에 담을 것 — AI에게 그대로 보내는 글이 아니라 내 요청을 짤 때 채울 다섯 가지

아래 다섯 가지를 내 말로 채워 요청을 짭니다. 값은 원자료에서 내가 찾습니다.

목적적재할 모델과 수정본을 파악한다. 아직 아무것도 만들지 않는다.
입력입력/schema.json · 입력/graph.json · 입력/자료_검토.md, 입력/자료_변경분/2026-10-20_수정본/
지킬 것파일을 바꾸지 않는다. 해석보다 파일 · 줄 번호와 개수를 먼저 받는다.
결과의 꼴종류별 대상 수 · 관계 수 표, 수정본 줄마다 「가리키는 대상 · 바뀌는 것」 목록

04 요구와 기대 답 정하기

왜 하는가 기대 답을 내가 원자료에서 먼저 찾아 적어 두어야, 뒤에서 AI가 만든 결과가 맞는지 견줄 기준이 생깁니다. AI가 낸 답을 기대 답으로 옮기면 틀린 결과도 맞아 보입니다. 원자료만으로 하나로 정해지지 않는 지점은 이 답을 쓰는 사람의 일을 보고 내가 정해야 같은 질문에 늘 같은 답이 나옵니다.

할 일 질문 · 이 답을 쓰는 사람 · 지킬 조건과, 설비 하나의 구성 요소별 센서 · 교체 부품과 공용 부품 하나의 사용 설비, 수정본 반영 뒤 달라져야 할 것을 원자료에서 직접 찾아 기대 답으로 결과/검증_기록.md에 적습니다. 「학생이 정할 것」의 지점마다 고른 것과 근거 줄을 적습니다.

가운데 편집기에서 파일을 열어 고친 뒤 Ctrl+S로 저장합니다. 탭 이름 옆 점(●)이 사라지면 저장된 것입니다.

학생이 정할 것 — 지점의 종류 원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 결과/검증_기록.md 「정한 것」 표에 적습니다.

  • 시점과 상태 — 설비 대장의 상태와 수정본에서 바뀐 상태를 그래프에 어떻게 반영하고, 「지금 가동하는 설비」를 묻는 부품의 사용 설비 조회에 어떻게 드러낼지(답에서 빠지는지, 상태와 함께 보이는지)

AI가 이 지점을 물을 때 채팅에 선택지와 직접 입력 칸이 있는 질문 카드가 뜰 수 있습니다. 선택지에 「(권장)」이 붙어 있어도 AI의 추천일 뿐이므로, 원자료의 근거 줄을 열어 본 뒤 직접 입력 칸에 내 결정과 근거 줄을 적어 보냅니다. 선택지를 고르더라도 근거 줄을 함께 적습니다.

정하거나 물을 것 지점마다 내 선택과 근거를 말합니다. AI가 고를 것을 내놓거나 「권장」을 붙이면 따르지 말고 원문 줄을 다시 열어 내 말로 정합니다. 못 정한 지점은 미결로 적습니다.

정하거나 물을 것 교체 부품이 없는 구성 요소를 결과에서 어떻게 보일지(빠지는지, 빈 칸으로 남는지), 여러 설비가 함께 쓰는 부품인지 알 수 있게 무엇을 함께 돌려줄지 정합니다.

10 구현 ④ 부품의 사용 설비 조회

왜 하는가 부품은 여러 구성 요소가 함께 가리키는 대상이라, 부품에서 거꾸로 따라가면 그 부품을 쓰는 설비가 모입니다. 설비의 상태는 설비 대상의 속성이라, 조회에서 그 값을 조건(WHERE)으로 쓰거나 결과에 함께 돌려줄 수 있습니다 — 무엇을 할지는 이 답을 쓰는 사람의 일을 보고 정한 「시점과 상태」를 따릅니다. MATCH가 찾지 못하면 결과 줄이 0개로 나오므로, 「없는 품번」과 「조회가 틀림」을 어떻게 구별해 보일지 함께 정해야 합니다.

할 일 품번이나 표기 하나를 받아 그 부품을 쓰는 설비 · 구성 요소를 돌려주는 조회를 더하고 실행합니다. 설비의 상태(설비 대장의 「상태」 칸)는 「정한 것」 표의 결정대로 결과에 반영합니다.

정하거나 물을 것 다른 표기 · 원자료에 없는 품번으로 물었을 때 무엇을 돌려줄지(빈 결과와 미확인을 어떻게 구별할지) 정합니다. 이 답을 쓰는 보전팀은 지금 가동하는 설비의 예비품을 준비하므로, 가동이 아닌 설비가 결과에 어떻게 보이는지가 「정한 것」 표의 「시점과 상태」 결정대로인지 묻습니다. AI가 결정을 대신 정하려 하면 돌려보내고 내 선택과 근거를 다시 말합니다.
