HYD · 실습 가이드

설계한 온톨로지를 그래프 DB에 구현하고 검증하기

설계 실습에서 다룬 클래스 · 식별자 · 관계를 Neo4j 실습에서 써 본 MERGE로 이 폴더 전용 그래프 DB(랩 DB)에 옮깁니다. 과정의 첫 단계인 온톨로지를 그래프 DB에서 실제로 묻고 고쳐 보며, 역량 질문마다 쿼리를 돌린 결과와 수정본을 반영한 결과를 원자료와 대조합니다. 결과는 사람마다 조금씩 달라도 되고, 내가 먼저 정한 기대 답과 맞으면 됩니다.

04 역량 질문과 기대 답 정하기

왜 쿼리 결과를 견줄 기대 답을 결과보다 먼저 정해야, 틀린 결과가 맞아 보이지 않습니다.

할 일 이번 역량 질문 셋을 Codex에게 알리고 기대 답 후보를 받습니다. ① 설비의 구성 요소마다 어떤 센서가 붙는가? ② 설비의 구성 요소마다 어떤 교체 부품이 들어가는가? ③ 부품을 어느 설비가 쓰고 그 설비의 상태는 무엇인가? 예전 품번이나 원자료에 없는 품번으로 물으면 어떻게 구별되는가? 부탁에는 목적 · 볼 자료 · 지킬 조건 · 확인할 답을 담습니다. 빠진 것은 AI가 짐작으로 채우기 때문입니다. 받아들인 줄을 expected.csv에 적게 하고 열어 봅니다. 「됐습니다」는 AI가 한 일을 스스로 요약한 말이라, 실제로 바뀐 파일이나 실행 결과와 다를 수 있습니다. 볼_열은 쿼리가 돌려줄 열 이름(tag · part · asset · status · note)이고, 질문 ③의 부품은 수정본에서 상태가 바뀌는 HYD-07도 쓰는 부품으로 고릅니다. 파일 수정 승인 창이 뜨면 app/features/ 안이면 Allow once, 밖이면 Deny를 누릅니다. 요청 속 파일 이름은 백틱(`)으로 감쌉니다.

06 스키마를 그래프로 옮기기: 적재와 다시 적재

수정본을 반영한 뒤 설비마다 있어야 할 구성 요소 수와 센서 수를 원자료 줄로 세어 줘. 파일은 바꾸지 마.

Codex 채팅에 붙여 넣는 글

수정본의 줄과 `decisions.csv`의 내 선택(불용 결정 설비)을 `update.cypher`에 반영해 줘. 이름이 바뀐 설비는 식별자를 그대로 두고 이름만 고치고, 전체를 지우지 마. 지우는 범위가 분명하지 않으면 작성하기 전에 물어봐.

터미널(PowerShell · 이 실습 폴더)

python run.py update

확인 바뀐 대상과 개수를 수정본으로 설명할 수 있고, 화면의 두 번째 실행에서 더 바뀐 것이 없으면 됩니다. update.cypher의 MATCH · SET 줄을 봅니다.

터미널(PowerShell · 이 실습 폴더)

랩 DB의 종류별 개수가 Codex가 센 수와 같으면 됩니다.

11 포털 기준 지도와 견주기

왜 무엇을 인스턴스 하나로 셀지는 답할 질문이 정하므로, 포털 지식 지도(여기서는 기준 지도)와 달라도 모델을 바꾸지 않고 까닭을 압니다.

할 일 아래 명령으로 「내 그래프」 표를 띄워 그 아래 기준 지도 표와 쿨러를 어떻게 셌는지부터 견줍니다. 기준 지도의 상태 변수 줄은 내 모델의 물리량 자리이고, CE 센서는 이 원자료 밖입니다.

터미널(PowerShell · 이 실습 폴더)

python run.py compare

결과 화면에 「내 그래프」 표가 보이면 아래 기준 지도 표와 견줍니다.

포털 기준 지도 포털 실습에서 HYD-01의 오일 쿨러를 펼쳐 본 지식 지도 가운데 설비 → 쿨러 → 센서 → 상태 변수 길의 식별자 · 관계입니다. 「 」는 화면의 관계 이름, 괄호는 저장된 이름, →는 방향(시작 → 끝)입니다.

종류식별자(id)알아볼 값관계와 방향
설비asset:hyd-01code HYD-01나가는 「구성 요소」(HAS_COMPONENT): 이것 → comp:cooler
구성 요소comp:coolername 오일 쿨러들어오는 「구성 요소」(HAS_COMPONENT): asset:hyd-01 → 이것
나가는 「관측 센서」(MONITORED_BY): 이것 → sen:ce · 이것 → sen:ts1
센서sen:ts1tag TS1들어오는 「관측 센서」(MONITORED_BY): comp:cooler → 이것
나가는 「읽는 상태 변수」(OBSERVES): 이것 → sv:ts1
센서sen:cetag CE들어오는 「관측 센서」(MONITORED_BY): comp:cooler → 이것
나가는 「읽는 상태 변수」(OBSERVES): 이것 → sv:ce
상태 변수sv:ts1name 유온들어오는 「읽는 상태 변수」(OBSERVES): sen:ts1 → 이것
상태 변수sv:cename 냉각 효율들어오는 「읽는 상태 변수」(OBSERVES): sen:ce → 이것

포털 실습에서 본 것처럼 설비 칸을 HYD-02로 바꾸면 asset:hyd-02에서 같은 comp:cooler로 「구성 요소」 관계가 이어지고, 그 아래 센서 · 상태 변수도 이 표와 같은 노드입니다.

확인 두 표의 차이와 그 까닭을 실제 줄로 말할 수 있으면 됩니다.
