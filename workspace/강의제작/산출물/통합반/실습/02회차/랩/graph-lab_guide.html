설계한 온톨로지를 그래프 DB에 구현하고 검증하기

설비·센서·부품의 온톨로지를 이 폴더 전용 그래프 DB(랩 DB)에 구현합니다. 조회와 부분 수정 결과를 원자료와 대조합니다.

01 폴더 열고 자료 확인하기

클래스룸의 2회차 실습 자료에서 ZIP을 받아 압축 풀기를 선택합니다. VS Code의 파일 → 폴더 열기에서 graph-lab 폴더를 엽니다. 함께 풀린 가이드는 브라우저로 엽니다.

신뢰 여부를 물으면 예, 작성자를 신뢰합니다(Yes, I trust the authors)를 선택합니다. 제한 모드에서는 Codex를 사용할 수 없습니다.

README.md에서 폴더 역할을 봅니다. AGENTS.md는 Codex의 공통 작업 원칙입니다. data/model/에는 바로 쓸 수 있는 모델이 있어 자기 모델이 없어도 시작할 수 있습니다.

터미널 → 새 터미널을 엽니다. 오타를 줄이도록 명령 블록의 복사를 눌러 붙여 넣고 Enter를 누릅니다.

터미널(PowerShell · 이 실습 폴더)

python run.py

원자료 파일마다 행 수가 보이는지 봅니다. 결과는 output/result.html에 저장됩니다. 브라우저가 열리지 않으면 Windows 파일 탐색기로 이 실습 폴더의 output 폴더를 열고 result.html을 두 번 누릅니다(VS Code 탐색기에서 누르면 화면이 아니라 HTML 글이 열립니다). 이후에는 명령을 실행한 뒤 열린 화면에서 F5를 누릅니다.

03 Codex와 모델 파악하기

무엇을 넣을지 알아야 적재한 결과를 검증할 수 있습니다. Codex 채팅을 열어 로그인하고, 파일을 바꾸지 말고 data/model/schema.json과 graph.json의 종류·식별자·관계 방향을 설명해 달라고 요청합니다. 계정이 없거나 막히면 클래스룸에서 별도로 받는 graph-lab-completed.zip을 실행해 볼 수 있습니다.

설비 하나를 골라 센서와 부품까지 가는 길을 원자료 행과 함께 짚어 봅니다. data/model/provenance.md에서 모델에 적용된 기준도 확인합니다. 이 모델은 구성 요소 자리와 일련번호가 붙은 실물을 따로 둡니다.

schema.json의 관계마다 적힌 카디널리티(시작 쪽 수:끝 쪽 수, 1은 많아야 하나)도 봅니다. 적재한 그래프가 이 수를 넘지 않아야 하고, 구조 검사가 그것을 셉니다.

자기 온톨로지 모델을 쓰는 것은 선택입니다. 사용할 때만 기준일·종류·식별자·관계와 카디널리티의 형식을 확인하고, 두 JSON 파일을 app/features/model/에 함께 복사합니다. 실물을 따로 두지 않았거나 확인 필요 후보를 둔 모델이면 뒤의 조회와 수정본 반영도 그 모델의 종류와 관계에 맞춥니다. 제공 모델은 보존합니다.

터미널(PowerShell · 이 실습 폴더)

python run.py

현재 사용하는 모델 경로와 개수를 확인합니다. 자기 모델을 골랐다면 이후 질문과 쿼리도 그 모델에 맞춥니다.

04 질문과 기대 답 정하기

보전팀이 예비품을 준비할 때 쓸 답을 만듭니다. app/features/review.md에 질문·사용할 자료·기준일·지킬 조건을 자기 말로 적습니다. 공급 조건·입고 판단과 모델 정의 변경은 이번 범위에서 제외합니다.

설비별 센서, 설비별 교체 부품, 부품의 사용 설비를 조회할 것입니다. expected.csv에 원자료에서 찾은 답과 근거를 먼저 적습니다. 설비 하나의 센서와 부품, 공용 부품, 다른 표기, 없는 품번을 확인할 값을 고릅니다. 볼 열은 조회 결과에서 비교할 열 이름입니다.

가동하지 않는 설비를 사용 설비 조회에서 어떻게 보일지 정합니다. data/changes/2026-10-20/의 수정본도 읽고 불용으로 바뀐 설비를 상태로 남길지, 그 설비에만 속한 대상과 함께 지울지 선택합니다. decisions.csv에 미리 있는 두 지점 줄(시점과 상태 · 불용 결정 설비)에 고른 것과 근거 줄을 직접 적습니다. 비어 있으면 부품의 사용 설비 조회와 수정본 반영이 그 줄을 짚고 멈춥니다. AI의 추천은 근거가 되지 않습니다.

파일을 손으로 고친 뒤에는 Ctrl+S로 저장합니다(탭 이름 옆 ●가 사라지면 저장됨). 저장하지 않으면 명령이 고치기 전 내용을 읽어 0행으로 보입니다.

지금 내가 대조한 두 지도에서 식별자와 관계 방향이 다른 곳을 짚었어. 내 설명이 내 그래프의 실제 대상·관계와 맞는지 확인해 줘. 파일과 모델은 바꾸지 마.

포털 기준 지도 포털 실습에서 HYD-01의 오일 쿨러를 펼쳐 본 지식 지도 가운데 설비 → 쿨러 → 센서 → 상태 변수 길의 식별자 · 관계입니다. 「 」는 화면의 관계 이름, 괄호는 저장된 이름, →는 방향(시작 → 끝)입니다.

종류식별자(id)알아볼 값관계와 방향
설비asset:hyd-01code HYD-01나가는 「구성 요소」(HAS_COMPONENT): 이것 → comp:cooler
구성 요소comp:coolername 오일 쿨러들어오는 「구성 요소」(HAS_COMPONENT): asset:hyd-01 → 이것
나가는 「관측 센서」(MONITORED_BY): 이것 → sen:ce · 이것 → sen:ts1
센서sen:ts1tag TS1들어오는 「관측 센서」(MONITORED_BY): comp:cooler → 이것
나가는 「읽는 상태 변수」(OBSERVES): 이것 → sv:ts1
센서sen:cetag CE들어오는 「관측 센서」(MONITORED_BY): comp:cooler → 이것
나가는 「읽는 상태 변수」(OBSERVES): 이것 → sv:ce
상태 변수sv:ts1name 유온들어오는 「읽는 상태 변수」(OBSERVES): sen:ts1 → 이것
상태 변수sv:cename 냉각 효율들어오는 「읽는 상태 변수」(OBSERVES): sen:ce → 이것

포털 실습에서 본 것처럼 설비 칸을 HYD-02로 바꾸면 asset:hyd-02에서 같은 comp:cooler로 「구성 요소」 관계가 이어지고, 그 아래 센서 · 상태 변수도 이 표와 같은 노드입니다.

터미널(PowerShell · 이 실습 폴더)

python run.py compare

설비·쿨러·센서의 식별자와 방향을 두 표의 실제 줄로 설명할 수 있으면 저장합니다.
