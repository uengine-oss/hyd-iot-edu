# 현장 정보를 체계화하는 온톨로지 직접 설계하기

## 목표

포털 지식 지도에서 오일 쿨러와 거기 붙은 센서가 어떻게 이어지는지 따라가 봤습니다. 이번에는 그 연결을 직접 만듭니다. 창원1공장 유압 설비 7대의 대장 · 구성 요소 · SCADA 태그 · 예비품 자료를 하나의 설비 지식 모델(종류 · 속성 · 관계)로 정리해, 설비별 센서와 여러 설비가 함께 쓰는 부품을 답하게 합니다.

자료는 시스템마다 따로 내보낸 것이라 같은 센서 이름이 여러 설비에 쓰이고, 같은 장치를 사람마다 다르게 부르며, 줄이 겹치거나 칸이 비어 있습니다. 손으로 다 맞춰 볼 수 없는 양이므로 AI와 코드로 처리하고 결과는 원자료와 대조합니다. 대상마다 겹치지 않는 ID를 주고 단위와 관계 방향을 정해 두어야, 누가 같은 질문을 해도 같은 답이 나옵니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 첫 단계인 온톨로지의 설계 — 질문으로 범위를 정하고, 종류 · 속성 · 관계를 정의해 원자료로 모델을 만드는 일 — 를 맡습니다.

만들 것: 설비 지식 모델의 스키마(종류 · 속성 · 관계의 정의)와 인스턴스(실제 대상과 관계), 원자료에서 그것을 만드는 코드와 모델에 물어보는 확인 코드, `결과/요구사항.md` · `결과/자료_검토.md`.

## 출발점

- `자료/` — 원자료. CSV 8개(설비 대장 · 구성 요소 · 센서 · 예비품 · 품번 교차표 · 공급 조건 · 승인 공급사 · 입고 이력), 현장 메모. 기준일은 2026-10-15입니다. 이번 질문에 쓰는 것은 설비 · 구성 요소 · 센서 · 예비품 · 품번 자료이고, 공급 · 입고 자료는 이번 질문 밖입니다.
- `입력/관계그림.json` — 1회차에 ARROWS로 그린 관계 그림(설비 · 구성 요소 · 센서와 증상 · 원인 · 조치). 이번에는 그 가운데 설비 · 센서 · 부품 쪽을 원자료 전체로 구체화합니다.
- `결과/` — 이번에 만든 것을 두는 자리. 「제공 빈 틀」 `요구사항.md` · `자료_검토.md`가 있고, 모델(스키마 · 인스턴스)은 아직 없습니다.
- `AGENTS.md` · `.github/copilot-instructions.md` · `CLAUDE.md` — Codex와 GitHub Copilot이 지키는 작업 규칙(세 파일이 같은 내용). 학생도 함께 읽습니다.

## 처음 쓰는 도구

- **VS Code**: 왼쪽 탐색기에서 이 폴더의 파일을 엽니다. 처음 열 때 「이 폴더의 작성자를 신뢰합니까」가 나오면 신뢰를 누릅니다. CSV를 누르면 표 글자 그대로 보이고, 고친 파일은 `Ctrl+S`로 저장합니다.
- **터미널**: 메뉴 「터미널 → 새 터미널」로 아래쪽에 엽니다. 이 폴더에서 열리는지 맨 앞 경로를 확인하고 `python check.py`처럼 명령을 입력합니다.
- **Codex(AI)**: 왼쪽 막대의 Codex 아이콘을 눌러 채팅 창을 엽니다. 입력하기 전에 채팅 창 위쪽 탭이 Codex인지 확인합니다(옆의 Chat 탭은 GitHub Copilot이라 로그인 창이 뜹니다). 요청을 입력하면 이 폴더의 파일을 읽고, 허락하면 파일을 만들거나 명령을 실행합니다. AI가 「완료」라고 해도 실제 파일과 실행 출력으로 확인합니다.
- **편집 승인 창**: AI가 파일을 고치려 하면 「Allow ChatGPT to edit the following file?」 창이 뜹니다. 창에 적힌 파일 경로가 `결과/` 아래인지 보고 「Allow once」(이번 한 번 허용)를 누릅니다. `입력/`·`자료/`의 파일이거나 요청하지 않은 파일이면 「Deny」(거부)를 누르고 이유를 채팅으로 알립니다.
- **질문 카드**: AI가 정하기 전에 물어야 할 지점에서는 채팅에 질문 카드(선택지와 직접 입력 칸)가 뜰 수 있습니다. 선택지에 「(권장)」이 붙어 있어도 AI의 추천일 뿐입니다. 원자료의 근거 줄을 열어 확인한 뒤 고르거나, 직접 입력 칸에 내 결정과 근거를 적고 보냅니다.

## 해결할 질문

이 답은 보전팀이 설비별 센서를 찾고, 교체할 부품을 어느 설비와 함께 준비할지 정할 때 씁니다. 같은 부품을 구매팀은 호환 후보를 찾을 때, 창고는 품목별 재고를 셀 때 조회합니다.

1. 설비별로 어떤 구성 요소에 어떤 센서 · 계산값 · 설정값이 붙어 있는가?
2. 각 센서가 재는 물리량과 단위 · 정상값 · 한계(위로 넘는지, 아래로 떨어지는지)는 무엇인가? 설비마다 태그 이름이 달라도 같은 물리량을 재는 센서를 함께 찾을 수 있는가?
3. 교체 부품별로 그 부품을 쓰는 설비와 구성 요소는 무엇인가? 다른 표기로 적힌 품번, 제조사 규격 번호, 원자료에 없는 품번으로 물으면 결과가 어떻게 구별되는가?

## 학생이 정할 것

원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 `결과/요구사항.md` 「정한 것」 표에 적습니다.

- **쓰는 사람에 따라 갈리는 답** — 같은 규격(제조사 품번)으로 등록된 서로 다른 사내 품번을 한 물품으로 볼지 — 그 규격이나 한쪽 품번으로 물었을 때 나와야 할 답이 호환 후보를 찾는 사람과 품목별 재고를 세는 사람에게 같은지

AI에게 이 지점을 대신 정하게 하지 않습니다. AI가 고를 것을 내놓거나 「권장」을 붙여도 그대로 따르지 말고, 원문 줄을 열어 내 선택과 근거를 말합니다. 못 정한 지점은 미결로 남깁니다.

## 이번 범위 밖

- 공급 조건 · 입고 이력을 모델에 넣는 일
- 그래프 DB에 적재하고 조회하는 일(다음 실습)
- 부품 재고 수량을 세거나 발주를 정하는 일

자료에 있어도 이번 결과에 만들지 않습니다.

## 결과 형식

`check.py`와 다음 실습이 읽는 모양입니다. 무엇을 종류·속성·관계로 둘지는 직접 정합니다.

- `결과/schema.json`: `{"classes": {종류: {"meaning": 뜻, "required": {속성: 자료형}, "optional": {속성: 자료형}}}, "relations": {관계: {"from": 종류 또는 [종류…], "to": 종류, "cardinality": "1:N" 등, "properties": {속성: 자료형}}}}`
- 자료형은 `string`·`number`·`integer`·`boolean`·`list` 중 하나이거나, 허용 값 목록(예: `["upper", "lower"]`)입니다.
- `결과/graph.json`: `{"nodes": [{"labels": [종류], "props": {"id": 고유 ID, …}}], "rels": [{"type": 관계, "a": 시작 id, "b": 끝 id, "props": {…}}]}`
- 같은 두 대상 사이에 같은 관계를 여러 개 두려면 그 관계의 props에 `id`를 붙입니다.

## 진행 단계

한 번에 한 단계씩 갑니다. 단계마다 결과를 확인한 뒤 다음 단계로 갑니다. 단계마다 정하거나 물을 것, 요청에 담을 것, 판단할 증거는 `guide.html`의 같은 번호에 있습니다.

1. **폴더와 출발점 확인** — VS Code 탐색기에서 이 폴더의 `입력/` · `자료/` · `결과/` · START.md를 열어 각 자리의 역할과 이번 질문을 확인합니다.
2. **파일을 바꾸지 않고 자료 파악** — AI에게 파일을 바꾸지 말고, 내가 고른 설비 하나의 구성 요소 · 센서 · 교체 부품에 관한 줄을 자료마다 찾아 파일 · 줄로 짚어 달라고 합니다. 짚은 줄을 직접 엽니다.
3. **요구와 기대 답 정하기** — 질문 · 이 답을 쓰는 사람 · 기준일 · 지킬 조건과, 고른 설비의 구성 요소별 센서와 여러 설비가 함께 쓰는 부품 하나의 사용 설비를 원자료에서 직접 찾아 기대 답으로 `결과/요구사항.md`에 내 말로 적습니다. 「학생이 정할 것」의 지점마다 고른 것과 근거 줄을 적습니다.
4. **설계 계획 검토** — 설비 · 구성 요소 · 센서 · 물리량 · 부품을 어떤 종류 · 속성 · 관계로 둘지, ID를 무엇으로 지을지 AI의 계획을 받아 검토하고, 5 ~ 9단계의 구현 순서에 동의합니다. 아직 파일을 만들지 않습니다.
5. **구현 ① 설비와 구성 요소 만들기** — 설비 대장과 구성 요소 목록에서 설비 · 구성 요소 대상과 그 사이 관계를 만드는 코드를 `결과/`에 만들고 실행합니다.
6. **구현 ② 센서와 물리량 잇기** — 센서 목록의 줄마다 센서 대상을 만들어 붙은 곳(구성 요소 또는 설비)과 재는 물리량에 잇는 기능을 더하고 실행합니다.
7. **구현 ③ 단위와 한계 맞추기** — 센서마다 단위 · 정상값 · 한계 · 한계 방향을 물리량의 기준 단위로 맞춰 넣고, 바꾼 값은 원래 표기를 남기는 기능을 더하고 실행합니다.
8. **구현 ④ 교체 부품 잇기** — 구성 요소마다 교체 부품을 사내 품번 하나에 잇고, 예전 품번 · 다른 표기를 부품에 남기는 기능을 더하고 실행합니다.
9. **구현 ⑤ 질문으로 물어보기** — 설비 코드나 품번 · 표기 하나를 받아 `결과/graph.json`에서 구성 요소별 센서, 또는 그 부품을 쓰는 설비 · 구성 요소를 보여 주는 확인 코드를 만들고 실행합니다.
10. **구조 검사와 고치기** — 터미널에서 구조 검사를 실행하고, 나온 문제를 고친 뒤 9단계 확인을 다시 합니다.
11. **저장하고 다시 열기** — 결과 파일을 모두 저장하고 VS Code에서 폴더를 닫았다 다시 연 뒤 9단계 명령을 다시 실행합니다. `요구사항.md` 끝에 기준일 · 저장 시점 · 확인하지 못한 점을 적습니다.

이 순서는 바이브 코딩 일곱 단계 — 파일을 바꾸지 않고 파악 → 요구와 기대 답을 내 말로 → 계획 검토 → 작게 구현 → 원자료와 대조 → 고침 → 저장하고 다시 열기 — 를 따릅니다.

요청에 파일 이름을 쓸 때는 `결과/schema.json`처럼 백틱(`)으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다.

## 확인

확인할 사례의 종류(어느 행이 해당하는지는 원자료에서 직접 찾습니다):

- 같은 태그 이름이 여러 설비에 있는 경우
- 이름이 다른데 같은 것을 재는 태그
- 같은 장치를 다르게 부른 이름
- 같은 대상이 두 번 나온 행
- 기준일(2026-10-15)에 살아 있지 않은 기록(옛 코드 · 철거된 실물)
- 비어 있는 칸(단위 · 교체부품 · 정상값)
- 단위 표기가 다른 값
- 계기 없는 계산값과 설정값
- 여러 설비가 함께 쓰는 부품과 한 설비만 쓰는 부품
- 품번 대신 품명 · 다른 표기로 적힌 칸
- 같은 규격(제조사 품번)으로 등록된 다른 사내 품번
- 원자료에 없는 품번
- 같은 코드를 다시 실행한 결과

실행 명령:

```
python check.py
python 결과/<만든 코드 이름>.py
python 결과/<확인 코드 이름>.py <설비 코드 또는 품번>
```

바뀐 파일 확인: AI가 단계를 마칠 때마다 바뀐 파일 목록을 봅니다. `입력/` · `자료/`가 바뀌지 않았는지, 요청하지 않은 파일이 생기지 않았는지 확인합니다. 편집 승인 창에서는 경로가 `결과/` 아래일 때만 허용합니다.

## 완료 판정

형식 검사나 실행 성공만으로 완료하지 않습니다. 질문마다 원자료에서 먼저 적은 기대 답과 실제 결과가 맞고, 「정한 것」마다 근거 줄과 그 선택으로 바뀌는 답을 설명할 수 있으면 완료입니다. 고친 점과 확인하지 못한 점은 `결과/요구사항.md`에 짧게 남깁니다.

## 저장과 다음 실습

`결과/schema.json` · `결과/graph.json`을 한 쌍으로, 만든 코드 · 확인 코드 · `요구사항.md` · `자료_검토.md`와 함께 보관합니다. 다음 실습 「설계한 온톨로지를 그래프 DB에 구현하고 검증하기」에서는 이 판본을 쓰거나 제공된 설비 · 센서 · 부품 모델로 시작할 수 있습니다. 재부팅 전에 이 실습 폴더를 USB 또는 개인 클라우드에 복사합니다. 자동으로 되살려 주지 않습니다.
