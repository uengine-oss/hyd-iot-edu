01 폴더와 출발점 확인

포털에서 검토를 마친 후보를 적재하고 지식 지도에서 조치 · 원인 · 근거 문서의 연결을 찾았습니다. 이번에는 검토한 문서 지식을 별도 랩 DB의 설비 모델과 조치 기준에 직접 잇고, 처음 정한 질문에 그 지식이 원문대로 답하는지 확인합니다. 사건은 포털에서 본 경보와 같은 종류의 다른 경보 한 건인 10월 27일 01:59 HYD-02 쿨러 성능 저하 경보이고, 그 판정 뒤에 남은 근본 조치가 핀 세척입니다.

검토 결과에는 여러 문서 · 판의 후보와 결정이 섞여 있고, 문서 속 대상은 모델과 다른 이름으로 적혀 있습니다. 승인한 것만 기존 ID에 이어야 다음 실습이 근거 있는 지식만 씁니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 온톨로지 단계의 마지막 — 검토한 문서 지식을 그래프에 잇고 질문으로 확인하는 일 — 을 맡습니다.

받기 이 폴더는 「실습 시작」 도구로 받습니다. 도구에서 과정 → 회차 → 실습을 고르고 새로 시작을 누르면 이 판본만 새 폴더에 받아 풀고, VS Code에 이 폴더와 START.md를, 브라우저에 이 가이드를 엽니다. 이어서 할 때는 이전 작업 열기를 누릅니다 — 새로 시작은 늘 새 폴더에 받으므로 고친 파일을 덮지 않습니다. 받기에 실패하면 한 번 더 시도하고, 그래도 안 되면 수동 ZIP으로 받은 ZIP을 풀어 VS Code의 파일 → 폴더 열기(File → Open Folder)로 그 폴더를 엽니다.

필요한 것 VS Code와 Python, 로그인해 둔 Codex 또는 GitHub Copilot, 랩 DB를 켤 Docker Desktop.

VS Code가 이 폴더를 처음 열 때 폴더를 신뢰할지 묻는 창(Do you trust the authors of the files in this folder?)이 뜨면 신뢰하는 쪽(Yes, I trust the authors)을 누릅니다. 신뢰하지 않으면 제한 모드(Restricted Mode)로 열려 AI 채팅이 동작하지 않습니다. 아래쪽 상태 표시줄에 제한 모드가 보이면 그 표시를 눌러 이 폴더를 신뢰합니다.

AI 계정이 없으면 실습 폴더와 따로 받는 학생용 완성본 묶음(계정이 없는 학생이 결과를 확인하는 용도)으로 결과를 확인하세요.

해결할 질문 이 답은 설비보전팀장과 다음 실습의 에이전트가 핀 세척과 냉각 조치의 조건 · 근거를 그래프로 찾을 때 씁니다.

  1. HYD-02 냉각 성능 상실에서 쓸 수 있는 조치(즉시 완화 · 근본 조치)마다 수행 단계 · 준비 · 금지 · 완료 기준 · 승인은 무엇이고, 근거 문서 · 판 · 절 · 인용은?
  2. 판정에 쓴 규칙마다 근거 원문이 있는가 — 있으면 어디이고, 조건과 무엇이 다른가?
  3. 핀 세척 전에 확인할 현재 값은 무엇이고 어디서 읽는가(그래프로 답하지 않는 것)?
  4. 다른 문서를 더 반영하면 그 문서의 작업은 어느 설비 · 구성 요소 · 부품에 걸리고, 앞서 넣은 연결은 그대로인가?
  5. 제공되지 않은 작업이나 절을 물으면 그래프는 무엇을 돌려주는가?

말 풀이 적재는 대상 · 관계를 그래프 DB에 넣는 일이고, 스키마 확장은 문서 근거를 담으려고 설비 모델에 더하는 새 종류 · 관계와 그 뜻입니다. 승인 후보는 검토 결과에서 결정이 채택 · 수정(상태 approved)인 후보이고, 보류 · 제외 후보는 적재하지 않습니다. 현재 값은 재고 · 작업지시 상태 · 센서 값처럼 계속 바뀌어 그 값이 기록되는 시스템(원천)에서 읽어야 하는 값입니다 — 센서 값은 시계열 DB, 정비 작업지시는 CMMS(설비 보전 관리 시스템), 재고는 ERP(전사 자원 관리 시스템), 생산 실행은 MES(생산 실행 시스템)에 기록됩니다. 내보내기는 그래프의 대상 · 관계를 다음 실습이 읽는 파일 하나로 쓰는 일입니다. 계약은 결과 파일의 모양(열 · 키와 그 뜻)을 정해 둔 입출력_계약.md입니다 — 다음 실습의 기능이 이 모양 그대로 읽습니다.

내 앞 결과를 쓸 때: 제공 입력은 그대로 두고 내 검토 결과 · 모델 등을 결과/내_입력/에 입력/과 같은 이름 · 같은 자리로 복사해, 형식이 입출력_계약.md 「입력」과 같은지 먼저 견준 뒤 씁니다. lab_cypher.py model과 check.py는 결과/내_입력/에 있는 파일을 씁니다. 내 결과가 없어도 제공된 입력으로 끝까지 할 수 있습니다.

왜 하는가 만들기 전에 무엇이 주어졌고 무엇을 만들어야 하는지 알아야 AI에게도 같은 출발점을 말할 수 있습니다. 이 답을 누가 어디에 쓰는지에 따라 무엇을 하나로 보고 무엇을 따로 둘지가 달라지므로, 쓰는 사람도 여기서 확인합니다. 조치에서 근거 문서까지 관계를 따라가려면, 무엇이 이미 검토되었고 무엇이 보류되었는지부터 알아야 합니다.

할 일 탐색기에서 입력/ · 자료/ · 결과/ · lab_db.py · lab_cypher.py · START.md를 찾고 이 답을 쓰는 사람과 해결할 질문을 읽습니다. 입력/검토결과/의 파일 하나를 열어 결정(채택 · 수정 · 제외 · 보류)이 섞여 있는 것을 확인합니다.

02 파일을 바꾸지 않고 자료 파악

왜 하는가 문서 속 대상은 모델의 ID와 다른 이름 · 번호로 적혀 있을 수 있습니다. 어느 기존 ID를 가리키는지 먼저 짝지어 두어야 적재할 때 새 대상을 지어내지 않고 기존 ID에 잇습니다.

할 일 AI에게 파일을 바꾸지 말고 입력/과 자료/문서_목록.csv를 읽어 달라고 해, 검토 결과마다 결정(채택 · 수정 · 제외 · 보류) 수와 후보가 가리키는 대상이 설비 모델 · SOP 구조 · 조건표의 어느 ID인지 표로 받습니다. 짚은 ID를 모델 파일에서 직접 엽니다.

Codex는 왼쪽 활동 표시줄의 Codex 아이콘을 누르면 채팅 창이 열립니다. 입력하기 전에 창 위쪽 탭이 Codex인지 확인합니다. GitHub Copilot을 쓰면 같은 창의 Chat 탭을 엽니다(처음 열면 GitHub 로그인 창이 뜹니다). 창 아래 입력 칸에 요청을 내 말로 적어 보내고, 답에 나온 파일을 왼쪽 탐색기에서 열어 가운데 편집기의 실제 줄을 읽습니다. AI가 「완료」라고 해도 실제 파일과 실행 출력으로 확인합니다.

AI가 파일을 만들거나 고치려 하면 편집 승인 창(Allow ChatGPT to edit the following file?)이 뜹니다. 창에 적힌 경로가 결과/ 아래이고 내가 요청한 변경이면 Allow once(이번 한 번 허용)를 누르고, 입력/ · 자료/의 파일이거나 요청하지 않은 파일이면 Deny(거부)를 누른 뒤 까닭을 채팅으로 알립니다. GitHub Copilot을 쓰면 바뀐 파일의 경로를 같은 기준으로 보고, 요청하지 않은 변경은 되돌립니다.

정하거나 물을 것 검토 결과의 결정 분포와, 후보가 가리키는 대상(설비 · 구성 요소 · 부품 · SOP · 단계 · 규칙)이 어느 기존 ID인지 묻습니다.

03 질문과 기대 답 먼저

왜 하는가 질문이 모델의 범위를 정합니다. 조회 결과를 본 뒤에 기대를 적으면 빠진 연결이 기대에 맞춰 사라지므로, 원문과 검토 결과로 먼저 적어 둡니다.

할 일 결과/구축_기록.md에 목표 · 쓰는 사람을 내 말로 적고, 질문 다섯의 기대 답을 원문 · 검토 결과 줄과 후보 id로 적습니다. 「학생이 정할 것」의 선택 · 근거 · 바뀌는 답(못 정하면 미결)과 기대 칸을 쓴 시각도 적습니다. 다 적으면 AI에게는 파일을 바꾸지 말고 내가 적은 것을 되짚게만 합니다.

가운데 편집기에서 파일을 열어 고친 뒤 Ctrl+S로 저장합니다. 탭 이름 옆 점(●)이 사라지면 저장된 것입니다.

학생이 정할 것 — 지점의 종류 원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 결과/구축_기록.md 「정한 것」 표에 적습니다.

  • 다른 문서의 조건 — 다른 문서가 정한 조건 · 시간 · 승인을 이 작업에 이을지 — 어느 문서의 어느 문장인지는 탐색에서 찾습니다

AI가 이 지점을 물을 때 채팅에 선택지와 직접 입력 칸이 있는 질문 카드가 뜰 수 있습니다. 선택지에 「(권장)」이 붙어 있어도 AI의 추천일 뿐이므로, 원자료의 근거 줄을 열어 본 뒤 직접 입력 칸에 내 결정과 근거 줄을 적어 보냅니다. 선택지를 고르더라도 근거 줄을 함께 적습니다.

정하거나 물을 것 지점마다 내 선택과 근거를 말합니다. AI가 고를 것을 내놓거나 「권장」을 붙이면 따르지 말고 원문 줄을 다시 열어 내 말로 정합니다. 못 정한 지점은 미결로 적습니다.

ID는 그래프 전체에서 하나여야 합니다. 같은 판의 같은 절이라도 문서가 다르면 다른 대상이고, 같은 문서라도 판이 다르면 다른 대상입니다 — 무엇으로 같은 대상을 알아볼지 정해 두어야 다시 적재해도 늘지 않고 다른 문서를 더해도 겹치지 않습니다.

할 일 AI에게 파일을 바꾸지 말고 문서 · 판 · 절 · 인용 · 검토 결정을 담을 새 종류 · 관계와 적재 순서를 제안하게 합니다. 처음 정한 질문 하나를 계획에 대어 어느 노드 · 관계를 따라 답이 나오는지 짚게 하고, 내가 동의하면 결과/schema_ext.json 초안을 만들게 합니다.

정하거나 물을 것 문서 · 판 · 절 · 인용 · 검토 결정을 어떤 종류 · 관계로 담고, 기존 이름(종류 · 관계)은 어떻게 다시 쓸지 정합니다. 무엇으로 같은 대상을 알아볼지(새 대상의 ID)도 정합니다.

05 랩 DB 준비와 설비 모델 · 조치 기준 적재

왜 하는가 이 실습의 적재 · 조회는 이 폴더에만 딸린 그래프 DB(별도 랩 DB)에서 합니다. 포털 DB와 떨어져 있어 여러 번 넣어도 포털에 영향이 없고, 설비 모델과 조치 기준의 수를 먼저 적어 두어야 뒤에서 늘어난 수가 이번에 넣은 것임을 셀 수 있습니다.

할 일 터미널에서 python lab_db.py로 이 폴더 전용 랩 DB를 켜고, python lab_cypher.py model로 설비 모델과 조치 기준(SOP 구조 · 조건표)을 올린 뒤 python lab_cypher.py count로 셉니다.

메뉴에서 터미널 → 새 터미널(Terminal → New Terminal)을 누릅니다. 아래쪽에 열린 터미널의 맨 앞 경로가 이 실습 폴더인지 봅니다. 명령은 직접 치지 말고 블록의 복사를 눌러 붙여 넣은 뒤 Enter를 누릅니다 — 손으로 옮기면 오타가 나기 쉽습니다. 명령이 오류로 멈추면 실행한 명령과 출력 전문을 복사해 AI 채팅에 보내고, 무엇이 왜 멈췄는지 먼저 설명해 달라고 합니다.

랩 DB는 Docker로 켜므로 명령 전에 Docker Desktop을 켜 둡니다. 처음 한 번은 DB 이미지를 내려받아 시간이 더 걸립니다.

정하거나 물을 것 출력된 주소가 127.0.0.1의 이 폴더 전용 주소인지 확인합니다.

명령

터미널 명령 · PowerShell · 이 실습 폴더에서

python lab_db.py
python lab_cypher.py model
python lab_cypher.py count

「랩 DB 준비 완료」가 나오면 브라우저에 Neo4j Browser 연결 창이 열립니다. Protocol이 bolt://이고 Connection URL이 터미널 출력의 「Connect URL」과 같은 127.0.0.1:포트인지 보고(비어 있으면 그 127.0.0.1:포트를 넣습니다), Database user는 neo4j, Password는 비워 둔 채 Connect를 누릅니다 — 이 랩 DB는 이 PC 안에서만 열리고 비밀번호 없이 켜지기 때문입니다. 연결 정보는 랩_연결.json에도 저장됩니다. Neo4j Browser는 위쪽 입력 칸에 Cypher를 붙여 넣고 실행(▶)하는 화면이고, 결과는 그래프나 표(Table)로 볼 수 있습니다. 원자료와 줄마다 견줄 때는 표가 편합니다.

막히면 「can't open file」 · 「No such file or directory」가 나오면 터미널이 이 실습 폴더가 아닌 곳에서 열렸거나 명령의 파일 이름이 실제 파일과 다른 것입니다. 터미널 맨 앞 경로가 이 실습 폴더인지, 명령의 파일 이름이 탐색기에 보이는 이름과 같은지 확인한 뒤 다시 실행합니다.

막히면 「실행 확인 필요: 랩_연결.json이 없습니다. 먼저 python lab_db.py 를 실행하세요.」가 나오면 python lab_db.py가 「랩 DB 준비 완료」까지 가지 않은 것이니, 그 명령의 출력부터 다시 봅니다.

막히면 「랩 DB 준비 확인 필요:」로 시작하는 줄이 나오면 랩 DB를 켜지 못한 것입니다. 그 뒤에 Docker에 연결하지 못했다는 글이 있으면 Docker Desktop이 켜져 있는지 보고 같은 명령을 다시 실행합니다. 「이 실습에서 만든 DB가 아닙니다」가 나오면 다른 실습 폴더의 랩_연결.json이 이 폴더에 들어온 것이니, 그 파일을 이 폴더에서 만든 것인지 확인합니다. 「이 PC의 Docker에 없습니다」로 시작하는 줄 뒤에 「랩 DB 준비 완료」가 나오면 멈춘 것이 아닙니다 — 폴더를 USB 등으로 다른 PC에서 옮겨 왔거나 전에 쓰던 DB가 지워져서 이 폴더 전용 랩 DB를 새로 만든 것이고, 새 DB는 비어 있습니다.

판단할 증거 「랩 DB 준비 완료」와 주소가 나왔고, count의 종류별 수가 입력/ 파일에서 센 수(설비 모델의 노드 · 관계, SOP · 단계 · 규칙)와 같습니다. 그 수를 결과/구축_기록.md 「적재 수」 첫 줄에 적었습니다.
다를 때 수가 다르면 입출력_계약.md 2절의 종류 · 관계별로 다시 세어 어디서 다른지 찾습니다. 「랩 DB 준비 확인 필요」가 나오면 Docker Desktop이 켜져 있는지 봅니다.
