# 작업 절차와 판단 조건을 연결해 조치 기준 만들기

## 목표

포털의 조치 방법 화면에서 쿨러 조치의 단계 · 담당 · 승인을, 판단 규칙 화면에서 어떤 규칙이 조치를 허용 · 제외하는지 봤습니다. 이번에는 그 근거를 매뉴얼 원문에서 직접 찾아 작업 절차(SOP 구조)와 판단 조건(조건표)으로 나누고, 2회차에 만든 설비 모델의 ID에 잇습니다. 사건은 포털에서 본 경보와 같은 종류의 다른 경보 한 건, 10월 27일 01:59(한국 시각) HYD-02 쿨러 성능 저하 경보 `ALT-hyd02-0172-54a5`입니다(경보 ID로 자료 · 결과 화면에서 찾습니다).

SOP(표준 작업 절차, Standard Operating Procedure)는 사람이 따라 하는 절차(적용 조건 · 금지 조건 · 수행 단계 · 완료 기준 · 승인)를 담고, 조건표는 어떤 입력이 어떤 값일 때 조치를 경고 · 감점 · 제외하는지를 담습니다. 조건표는 DMN(판단을 표준 모양으로 적는 방식)의 결정표 — 입력 조건과 판단 결과를 한 행씩 적은 표 — 를 이 실습에서 부르는 이름입니다.

어느 문장을 어느 칸 · 규칙으로 옮길지, 무엇을 잇고 어느 설비에 걸지는 내가 판단 표에 정하고, 원문 인용 · JSON 꼴 쓰기 · 모델 ID 찾기 · 조건표 적용은 제공 코드가 합니다.

줄기(온톨로지 → 에이전트 → 프로세스)에서 이 실습은 첫 단계 온톨로지의 판단 지식 — 절차와 판단 조건을 원문에서 구조화해 설비 모델에 잇는 일 — 를 맡습니다.

만들 것: 판단 표 셋 · `결과/조건표.csv` · `결과/정한_것.csv` · `결과/기대_판정.csv` · `결과/요구사항.md`(내가 AI와 채움), `결과/sop.json`(제공 코드가 판단 표로 씀).

## 출발점

- `입력/schema.json` · `입력/graph.json` — 설비 7대의 설비 · 구성 요소 · 센서 · 부품 모델. 2회차에 만든 설비 모델과 같은 꼴로 제공된 판입니다. `입력/자료/설비_대장.csv` — 그 모델의 설비 대장(기준일 2026-10-15).
- 내 모델을 쓸 때: 제공 입력은 그대로 두고 내 `schema.json` · `graph.json`을 `결과/내_입력/`에 복사해, 형식과 ID 짓는 법이 제공 모델과 같은지 먼저 견준 뒤 씁니다. 제공 코드와 구조 검사는 `결과/내_입력/graph.json`이 있으면 그 모델의 ID로 봅니다. 내 모델이 없어도 제공된 모델로 끝까지 할 수 있습니다.
- `자료/HM-8_매뉴얼.md` — 현행 HM-8 1.1판(2026-09-01 시행) 냉각 계통 조치 원문. `자료/HM-8_1.0판_매뉴얼.md` — 1.1판으로 대체된 옛 판(2025-03-10 시행). `자료/HI-01_보충매뉴얼.md` — 점검 · 이상 확인 보충 기준.
- `자료/판단시스템_결정표_내보내기.txt` — 판단 시스템에 등록된 결정표 · 스킬을 내보낸 것(2025년 도입 판, 2026-10-27 내보냄). `자료/작업지시_이력.csv` — CMMS 작업지시 1년치 내보내기(2026-10-28).
- `자료/작업기준.md` — 회사 작업 기준. `자료/targets.csv` — 냉각 계통 SOP 목록. `자료/failuremodes.csv` — 회사 고장 유형 목록. `자료/사건_기록_HYD-02_1027.md` — 야간 운전원이 HMI에서 옮겨 적은 사건 메모. `자료/확인_사례.csv` — 지난 30일 경보 가운데 고른 확인 사례의 판단 입력(입력마다 원천과 그 시각).
- `입출력_계약.md` — 결과 · 판단 표의 형식. `check.py` — 구조 검사. `sop_tools.py` · `condition_tools.py` — 제공 코드(고치지 않습니다).
- `show_result.py` · `lab_steps.py` — 결과 화면(`python show_result.py`가 채운 단계까지 제공 흐름을 돌려 `결과/보기.html`을 다시 씀). 고치지 않습니다.
- `결과/` — 정할 자리(「제공 빈 틀」)와 README.
- `AGENTS.md` · `.github/copilot-instructions.md` · `CLAUDE.md` — Codex와 GitHub Copilot이 지키는 작업 규칙(세 파일이 같은 내용). 학생도 함께 읽습니다.

## 해결할 질문

이 답은 설비보전팀장이 판단 시스템에 조치 기준을 올릴 때, 야간 운전원이 사건에서 할 수 있는 조치를 볼 때 씁니다.

1. 냉각 계통 조치 일곱 개마다 적용 조건 · 금지 조건 · 수행 단계 · 완료 기준 · 승인은 무엇이고, 어느 고장 유형 · 원인과 어느 설비 · 구성 요소 · 센서에 걸리는가?
2. 판단 규칙으로 옮길 조건의 입력 · 단위 · 연산자 · 경계 · 결과 · 출처는 무엇이고, 판단 시스템에 등록된 결정표의 규칙 가운데 원문에 근거가 없는 것은 어떻게 두는가?
3. 사건 한 건의 판단 요청 때 값을 조건표에 대면 네 후보가 각각 어떻게 되는가?

## 학생이 정할 것

원자료만으로 하나로 정해지지 않아 내가 근거를 찾아 정할 지점입니다. 해당하는 행 · 절은 직접 찾고, 지점마다 고른 것 · 근거(파일:줄) · 바뀌는 답을 `결과/정한_것.csv`에 한 줄씩 적습니다.

- **적용 범위** — 원문에 적용 범위 문장이 없을 때 이 조치 기준을 설비 모델의 어느 설비에 걸지
- **출처가 확인되지 않는 기준** — 판단 시스템 결정표에 있는데 지금 매뉴얼에서 근거 문장을 찾을 수 없는 규칙을 어떻게 둘지 — 그런 규칙이 여럿이면 규칙마다 정하고 근거를 적습니다

AI에게 이 지점을 정하게 하지 않습니다. AI가 고르거나 「권장」을 붙여도 따르지 말고 원문 줄을 열어 내 선택과 근거를 말하며, 못 정하면 미결로 둡니다.

## 이번 범위 밖

- 원문에서 조건을 자동으로 뽑아내는 일(인제스천 — 뒤에서 직접 다룹니다)
- 조건표로 원천 기록을 판정하고 견주는 기능(다음 실습)
- 설비 모델(schema · graph)을 고치거나 그래프 DB에 적재하는 일
- 실제 설비 · 포털 · 업무 시스템을 부르는 일

자료에 있어도 이번 결과에 만들지 않습니다.

## 결과 형식

파일의 모양은 `입출력_계약.md`에 있습니다. 무엇을 어느 칸 · 행에 둘지는 원문을 읽고 직접 정합니다.

- 정할 자리(「제공 빈 틀」): `결과/조건_분류.csv` · `결과/관계.csv` · `결과/설비_연결_기준.csv`(판단 표 셋), `결과/조건표.csv`, `결과/정한_것.csv`, `결과/기대_판정.csv`, `결과/요구사항.md`.
- `결과/sop.json` — 제공 코드 `sop_tools.py`가 판단 표 셋으로 씁니다(`python show_result.py`).

## 지킬 조건

- 모델에 없는 대상에는 새 ID를 만들지 않습니다.
- 조치 기준의 항목마다 원문 출처를 답니다.
- 제공 코드(`show_result.py` · `lab_steps.py` · `sop_tools.py` · `condition_tools.py` · `check.py`)는 고치지 않습니다.

## 진행 단계

한 번에 한 단계씩 갑니다. 단계마다 결과를 확인한 뒤 다음 단계로 갑니다. 단계마다 정하거나 물을 것, 요청에 담을 것, 판단할 증거는 가이드(「실습 시작」 도구가 이 폴더 옆에 내려 둔 파일, 노션 「가이드문서」)의 같은 번호에 있습니다.

1. **폴더와 출발점 확인 · 결과 화면 열기** — VS Code 탐색기에서 `입력/` · `자료/` · `결과/` · START.md를 열어 각 자리의 역할과 이번 질문을 확인하고, 터미널에서 `python show_result.py`를 실행해 결과 화면을 엽니다.
2. **파일을 바꾸지 않고 자료 파악** — AI에게 파일을 바꾸지 말고, 냉각 계통 조치마다 그 조치를 말하는 줄을 자료마다 찾아 파일:줄로 짚어 달라고 합니다. 짚은 줄을 직접 열고, 결과 화면의 「매뉴얼 원문 문장」 · 「판단 시스템 결정표 규칙」 표와 견줍니다.
3. **요구와 기대 판정 정하기** — `결과/요구사항.md`에 목표 · 쓰는 사람 · 쓸 판본 · 지킬 조건을 적고, 사건 네 후보가 조건표에서 유지 · 제외 · 보류 가운데 무엇이 될지 원문과 사건 메모에서 먼저 찾아 `결과/기대_판정.csv`에 근거 줄과 함께 적습니다. 다 적으면 AI에게 파일을 바꾸지 말고 되짚게만 합니다.
4. **계획 검토** — SOP 구조(판단 표 셋)와 조건표에 무엇을 나눠 담을지, 5 ~ 9단계에서 어느 정할 자리를 어떤 순서로 채울지 AI의 계획으로 받아 검토하고 동의합니다. 아직 파일을 만들지 않습니다.
5. **조건 문장 나누기 — SOP 구조** — 절차마다 적용 · 금지 · 제한 · 완료 · 승인 칸에 들어갈 원문 문장과, 고장 유형 · 종류·코드를 `결과/조건_분류.csv`에 원문 자리로 적습니다. 실행해 결과 화면의 「SOP 구조」를 원문과 견줍니다. 실행은 내가 터미널에서 하고, AI가 답에 옮겨 적은 출력이 아니라 터미널에 나온 출력과 결과 화면으로 확인합니다 — 옮겨 적은 글은 실제 출력과 다를 수 있습니다.
6. **고장 유형 · 원인 · 조치 잇기** — 고장 유형에서 즉시 완화 조치 · 근본 조치로, 조치에서 그 조치가 맞는 원인으로 가는 관계를 `결과/관계.csv`에 원문 자리와 함께 적고 결과 화면의 「관계」 표를 봅니다.
7. **적용 범위와 설비 모델 ID 잇기** — 절차마다 걸 설비와 구성 요소 · 센서 이름, 걸지 않은 대상과 까닭을 `결과/설비_연결_기준.csv`에 적고, 「적용 범위」 지점의 고른 것 · 근거를 `결과/정한_것.csv`에 한 줄 적습니다. 결과 화면의 「설비마다 걸린 SOP」를 설비 대장 · 모델과 견줍니다.
8. **조건표 규칙 — 복합 조건과 경계** — 원문의 경고 · 감점 · 제외 조건을 `결과/조건표.csv`에 계약 모양으로 옮기고, 조건 문장의 규칙 칸(`결과/조건_분류.csv`)에 그 rule_id를 적습니다. 결과 화면에서 규칙마다 출처의 원문과 사건 네 후보의 판정을 3단계 기대와 견줍니다.
9. **출처가 확인되지 않는 규칙** — 판단 시스템 결정표에 있는데 받은 원문에서 근거 문장을 찾을 수 없는 규칙마다 조건표에 어떻게 둘지 정해 `결과/조건표.csv` · `결과/조건_분류.csv`에 반영하고, 규칙마다 `결과/정한_것.csv`에 한 줄씩 적습니다. 결과 화면에서 확인 사례의 판정이 직전 실행과 어떻게 바뀌었는지 봅니다.
10. **검사 · 저장하고 다시 열기** — 터미널에서 구조 검사를 실행해 짚은 문제를 고치고, 결과 파일을 모두 저장한 뒤 VS Code에서 폴더를 닫았다 다시 열어 `python show_result.py`와 구조 검사를 다시 실행합니다. `결과/요구사항.md` 끝에 기준일 · 저장 시점 · 확인하지 못한 점을 적습니다.

이 순서는 바이브 코딩 일곱 단계 — 파일을 바꾸지 않고 파악 → 요구와 기대 답을 내 말로 → 계획 검토 → 작게 구현 → 원자료와 대조 → 고침 → 저장하고 다시 열기 — 를 따릅니다.

요청에 파일 이름을 쓸 때는 `결과/조건표.csv`처럼 백틱(`)으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다.

## 확인

확인할 사례의 종류(어느 행이 해당하는지는 원자료에서 직접 찾습니다):

- 같은 조치를 판마다 다른 번호 · 절 · 낱말로 적은 곳(현행 원문 · 옛 판 · 판단 시스템 · 작업 이력)
- 경계 낱말(「이상 · 초과 · 미만」)이 원문끼리 다른 조건
- 여러 조건이 함께 맞아야 하는 조건과 다른 절 · 다른 SOP를 가리키는 단계
- 조치에 필요한 구성 요소 · 센서가 모델에 없는 설비
- 판단 시스템 결정표에서 냉각 계통 밖을 다루는 행
- 사건 기록에서 값이 비어 있는 후보
- 「정할 것」의 결정에 따라 결과가 바뀌는 확인 사례
- 같은 명령을 다시 실행한 결과

실행 명령:

```
python show_result.py
python check.py
```

바뀐 파일 확인: AI가 단계를 마칠 때마다 바뀐 파일 목록을 봅니다. `입력/` · `자료/` · 제공 코드가 바뀌지 않았는지, 요청하지 않은 파일이 생기지 않았는지 확인합니다. 편집 승인 창에서는 경로가 `결과/` 아래일 때만 허용합니다.

## 완료 판정
