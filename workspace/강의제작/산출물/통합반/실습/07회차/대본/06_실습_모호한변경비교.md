# 통합반 7회차 실습 4 — 모호한 기능 변경이 기존 계약에 미치는 영향 확인하기

> [촬영 전 확인 · 비낭독] 온라인 76행 50분. 앞서 만든 점검 요청 프로젝트와 원자료가 필요하다. 학생 코드로 두 버전을 실제 실행해 입력·출력·변경 파일과 진행 시간을 확인한다. 보관 자료의 비교기 재실행과 학생 프로그램 리허설은 서로 다른 확인이다.

## 변경 전의 동작 남기기

작성자와 검토자의 결과를 남긴 프로젝트를 열겠습니다. 추천을 받았지만 아직 사람이 결정하지 않은 요청, 정보가 모자라 답을 기다리는 요청도 골라 보세요. 이 상태에서 무엇이 나왔는지 남겨야 고친 뒤에도 같은 기능이 유지됐는지 비교할 수 있습니다.

> [비낭독] 실습3에서 보존한 프로젝트의 사본 둘을 만든다. 한 사본을 변경 전 기준으로 보관한다. 입력 파일, 관측 자료, 판단 시각, 설정을 기록하고 일반·정보 누락·승인 대기 요청의 실제 결과를 저장한다.

## 짧은 변경 요청으로 구현하기

다른 사본에는 세부 기준을 적지 않고 이렇게 요청해 보겠습니다. “점검 요청에 긴급 표시를 추가해 주세요.” 이제 코딩 도우미가 어느 파일을 고쳤는지 봅시다. 표시를 어디에 붙였는지, 어떤 입력을 기준으로 삼았는지, 목록 순서까지 바꿨는지 바뀐 줄에서 찾아보세요.

> [비낭독] 표시 추가만 요청하고 대상 경보·수치·누락 처리·출력 형식은 지정하지 않는다. 이전 세 사본의 요청.txt는 보관 기록의 출처다. 학생이 사용한 설정과 실행 명령을 기록한다. 제공된 source/기존_비교기록은 별도 디렉터리에서 읽는다. 빠진 파일을 삭제됐다고 해석하지 않는다.

## 같은 입력으로 비교하기

이제 두 버전에 같은 요청과 같은 관측 기록을 넣겠습니다. 먼저 평소 보던 출력 항목이 같은 이름과 뜻으로 남았는지 보세요. 다음에는 자료가 없는 요청이 기다리는 상태를 유지하는지 확인합니다. 마지막으로 사람이 결정하기 전에 실행으로 이어지는 변화가 생겼는지도 확인하겠습니다.

> [비낭독] 요청 식별자로 변경 전후 결과를 연결한다. 학생이 작성한 로컬 프로그램의 출력·모의 실행 기록을 대조한다. 외부 설비나 실제 승인에 쓰지 않는다. 새 실행 번호와 처리가 일어난 시각은 발급 형식·연결 관계를 보며, 원래 고정한 입력·판단 시각은 동일해야 한다. 비교한 항목마다 원문 위치와 실제 전후 값을 기록한다.

## 다음 명세에 넘길 차이

내가 실행한 결과에서 유지된 항목 하나를 고르고, 그렇게 판단한 두 기록을 나란히 열어 보세요. 바뀐 항목이 있다면 어느 요구로 설명할 수 있는지도 적어 봅시다. 차이가 없다면 같은 결과가 나온 입력을 기록합니다. 다음 명세에는 어떤 입력을 읽을지, 어떤 조건으로 긴급을 판정할지, 그 결과를 어디에 표시할지 나눠 적겠습니다.

> [인계 · 비낭독] 기준판·변경 사본, 같은 입력·자료·시각, 실제 출력, 변경 파일 목록과 비교표를 보존한다. 29장 세 사본의 보관 결과를 이번 실행의 결과로 채우지 않는다.
