# 통합반 7회차 실습 5 — 새로운 요구사항을 추가해도 기존 기능 유지하기

> [촬영 전 확인 · 비낭독] 온라인 77행 25분. 실습4의 기준판과 변경 사본·비교표가 필요하다. 제공 입력에서 계산한 기대와 학생 구현의 실제 출력을 구분한다. 학생 프로젝트 실행·수업 시간·촬영은 리허설에서 확인한다.

## 비교한 기록으로 명세 작성하기

기준판의 결과와 긴급 표시를 요청한 사본의 결과를 열겠습니다. 해석이 갈릴 수 있는 조건을 찾아, 어느 입력으로 무엇을 판정할지 먼저 적죠. 쿨러 성능 저하 경보가 대상이고, 판단 시각 직전 이 분의 유온 평균을 섭씨로 읽습니다. 유효한 평균이 육십 도 이상이면 긴급, 그보다 낮으면 긴급하지 않은 것으로 정하겠습니다.

> [비낭독] 실습5 코드/spec.md에는 목표, 입력과 유효성, 출력 계약, 금지 조건, 긴급 조건과 시점, 수용 기준과 비교할 항목의 여섯 빈 절이 있다. 변경 전 프로젝트에서 읽던 기존 항목의 이름·형식·뜻을 먼저 기록한다. 다른 경보는 종전 경로를 보존한다.

최근 관측이 너무 오래됐거나 구간에 표본이 충분하지 않으면 숫자가 보이더라도 미판정입니다. 이때는 왜 보류했는지 남깁니다. 긴급 표시가 생겨도 사람이 결정하기 전에는 설비 조치를 확정하거나 실행할 수 없다는 조건도 적겠습니다.

> [비낭독] TS1, avg, windowSeconds=120, 판단 시점, 단위 ℃와 포함 경계 >=60을 적는다. freshness.ok와 해당 집계의 coverage.covered를 모두 확인한다. 유효할 때 true/false, 자료가 없거나 유효하지 않으면 null과 보류 사유. 필수 업무 정보가 빠진 요청은 질문·보류 동작을 유지한다. 실습 자료에 정확히 60.0 ℃인 실제 사례는 없다.

## 기대 결과를 먼저 적고 구현하기

코드를 고치기 전에 평소 요청, 긴급 표시가 붙을 요청, 필요한 정보가 빠진 요청의 기대 결과를 적겠습니다. 실제 코드를 보고 정답을 옮기는 대신 방금 쓴 조건에서 기대를 끌어냅니다. 이제 코딩 도우미에게 명세를 보여 주고 이 범위만 구현해 달라고 하죠.

> [비낭독] 실습4 사본을 보존한 상태에서 구현할 프로젝트와 명세 위치를 확인한다. 출력에 새 항목을 더하면 기존 소비자가 이를 받아들이는지 점검한다. 원본 센서 자료에서 S01 60.7 / S02 57.8 ℃는 유효, S09 60.1 ℃는 최신성 미충족이다. 실제 프로그램이 결과를 내기 전에 기대값·근거를 별도 파일에 저장한다.

## 같은 자료로 재실행하기

같은 입력과 같은 관측 시각을 넣어 보겠습니다. 일반 요청의 종전 결과와 새 표시, 정보가 빠졌을 때 멈추는 상태를 각각 확인합니다. 평균은 기준보다 높지만 오래된 자료도 넣어 보세요. 미판정인 이유가 결과에 남나요? 승인 대기와 설비 명령 기록도 따로 대조해 보겠습니다.

> [비낭독] 일반·긴급·누락 요청과 유효하지 않은 관측을 실행한다. 필요하면 원본을 보존한 입력 사본에 필수 값을 비우고 변형한 조건을 기록한다. 새 실행 번호·시각은 값의 완전 동일성 대신 형식과 연결 관계를 본다. 예상과 다르면 입력·명세·구현을 대조하고 실제로 다른 항목만 고쳐 재실행한다.
