# 통합반 7회차 포털 실습 — 사람의 확인이 실제 업무 결과를 바꾸는 과정 확인하기

> 촬영 전 확인. 통합반 온라인 72행, 배정 25분. 아래는 포털 소스에 맞춘 실습 원고다. 화면에는 강사가 선택한 사람과 실제 건의 기록을 사용한다. 모의 설비에서의 리허설, 소요 시간, 역할 복원 및 두 처리 건의 결과는 미확인이다. 시작 전 쿨러 경보에 ‘냉각 긴급 대응’이 배포되어 있는지 확인하고 1회차에 승인한 별도 건을 찾는다. 경보가 뜨면 새 처리 건의 흐름 이름과 승인 단계의 거절 버튼을 확인한다. 다른 흐름으로 열린 건은 이 비교에 쓸 수 없다. 제작자가 미리 실습 건을 승인하지 않는다.

## 쿨러 사건의 승인 대기와 분석 근거

| 발화 | 조작·결과 확인 — 비낭독 |
|---|---|
| 쿨러의 냉각 성능이 떨어졌을 때 에이전트가 어떤 조치를 권하는지 보겠습니다. 결함 시뮬레이션에서 쿨러 열화 주입을 누릅니다. | 첫 설비의 ‘쿨러 열화 주입’을 한 번 누른다. 주입 시각을 메모하고 그 시각 이후 열린 쿨러 경보를 찾는다. |
| 이상 확인 · 조치에서 방금 생긴 사건을 엽니다. 설비 상태를 읽어 보고, 추천안을 뒷받침하는 근거를 찾아볼게요. | 사건의 설비와 시각을 맞춘다. 표시된 측정값·조건 한 가지와 추천안을 짚어 실제 값으로 설명한다. |
| 같은 사건의 처리 기록을 열겠습니다. 여기서 에이전트가 어떤 자료를 읽었는지 찾아봅니다. 지금 어느 단계에서 누구의 결정을 기다리는지도 보세요. | 처리 건에 표시된 흐름 이름 ‘냉각 긴급 대응’, 분석 기록과 승인 대기 단계를 확인한다. 근거와 연결된 추천안, 필요한 승인 역할, 임시로 구별할 수 있는 건의 식별 정보를 적어 둔다. |

## 역할 구성과 작업 표시

| 발화 | 조작·결과 확인 — 비낭독 |
|---|---|
| 에이전트 화면의 담당 배정으로 가겠습니다. 업무분장의 운전원 줄에서 원래 이 역할을 맡은 사람을 먼저 살펴보죠. 여기에 사람 한 명을 더합니다. | ‘역할 → 사람 (업무분장)’에서 원래 목록을 확인한다. 현재 운전원 역할에 없는 사람을 선택하고 ‘넣기’를 누른다. 추가된 이름과 원래 이름을 구분한다. |
| 방금 넣은 사람 이름 옆의 빼기를 누릅니다. 운전원 줄을 처음과 견주어 원래 구성으로 돌아왔는지 확인하겠습니다. | 추가한 사람만 빼고 이전 목록과 일치하는지 확인한다. 기본 배정은 그대로 둔다. |
| 이제 내 작업함에서 이 사건의 담당자를 고릅니다. 승인 대기 중인 작업이 보이는지 확인한 뒤, 이 작업과 관계없는 사람으로 ‘나’를 바꿔서 같은 건을 찾아보겠습니다. | 담당자의 개인 또는 역할 공용 작업에서 사건을 구별한다. 관계없는 담당자에게서는 같은 번호의 작업 표시 여부를 다시 본다. 실제로 표시된 결과만 읽는다. |
| 작업함에 보이는지와 조치를 승인할 수 있는지는 따로 살펴야 합니다. 이 안을 승인할 역할이 없는 사람으로 같은 처리 건의 승인 단계를 열겠습니다. 승인 버튼 옆에는 어떤 안내가 있나요? | 승인 권한이 없는 역할임을 먼저 확인한 사람으로 처리 건을 직접 연다. 해당 안의 승인 버튼을 사용할 수 없는지와 역할 제한 문구를 확인한다. 권한 없는 사용자의 버튼이 비활성이라면 서버 응답을 받은 장면이라고 설명하지 않는다. |

## 이번 건의 거절과 결과 보고

| 발화 | 조작·결과 확인 — 비낭독 |
|---|---|
| 이 조치를 결정할 수 있는 담당자로 돌아왔습니다. 추천 이유와 승인 역할을 다시 보고, 이번 건을 진행하지 않기로 한 사유를 적겠습니다. | 담당자를 바꾸고 같은 건인지 확인한다. 현재 추천 근거를 짚고 그 상황에서 검토한 거절 사유를 입력한다. |
| 거절을 누르겠습니다. 처리 기록을 열어 내가 적은 사유가 어디에 남았는지 찾아보죠. | 거절을 한 번만 제출한다. 처리가 끝난 뒤 사람의 결정과 사유, 후속 단계, 결과 보고를 순서대로 확인한다. 실제 화면 글자를 읽는다. |
| 사람이 결정을 기다리던 때와 지금의 처리 상태를 견줘 봅시다. 거절한 뒤 설비에 명령을 보낸 기록이 있는지, 마지막 결과 보고에는 무엇이 남았는지 차례로 살피겠습니다. | 결정 전 대기와 결정 후의 실제 상태를 대조한다. 시스템 처리에 설비 명령이 있는지와 결과 보고 내용을 확인한다. 불러오지 못한 기록을 명령이 없다는 근거로 사용하지 않는다. |

## 앞서 승인한 쿨러 사건과 대조

| 발화 | 조작·결과 확인 — 비낭독 |
|---|---|
| 앞서 운전원이 조치를 승인한 쿨러 사건의 처리 기록을 열겠습니다. 먼저 누가 무엇을 승인했는지 찾고, 그다음에 실제로 실행된 명령과 결과 보고를 따라갑니다. | 1회차에 승인한 처리 건을 읽기 전용으로 연다. 다른 건임을 확인하고 당시 선택한 안, 명령과 후속 확인에 표시된 결과를 실제 기록에 맞춰 짚는다. |
| 두 기록에서 사람의 결정이 적힌 곳을 기준으로 그 뒤를 보세요. 각각 어떤 조치를 결정했고, 어떤 명령과 보고가 남았는지 자기 말로 설명해 보겠습니다. | 이번 거절 건과 기존 승인 건에서 확인한 차이로 마친다. 이전 승인 건을 찾을 수 없으면 비교를 미확인으로 남긴다. 다른 새 건을 승인해 비교를 대체하지 않는다. |

## 제작 확인용 — 낭독하지 않음

- 기준은 실라버스 ‘통합반 온라인 44H’ 72행이다. 포털에서 모의 쿨러 사건 하나를 만들고 그 건은 거절한다. 비교할 승인 건은 1회차에서 남긴 기록이다.
- 학생 코드 main 2d534cb9. it/portal/www/app.js 292·341행(쿨러 열화 주입), 483행부터(사건별 기록). agents.js 309~325행(역할 구성원 추가와 복원). inbox.js 204~215행(사람과 역할 선택). instances.js 348~384행(안별 권한과 버튼), 477~485행(거절 사유 제출). it/process/procsvc/inbox.py 169·201행(역할 검사와 작업함). instances.py 1028행부터(거절과 명령 값 정리). it/portal/www/caseRecord.js 420~429·684~701행(거절 기록과 보고).
- 거절 경로 확인. it/process/procsvc/course_flows.json의 c3_cooling에 있는 거절 분기는 결과 보고를 거쳐 종결된다. course_bootstrap.py의 install이 이 흐름을 배포하며 flow_deploy.py의 경보 매핑은 건을 열 때 고정된다. instances.js의 canReject는 승인 활동의 outputData에 approval이 있어야 거절 버튼을 표시한다.
