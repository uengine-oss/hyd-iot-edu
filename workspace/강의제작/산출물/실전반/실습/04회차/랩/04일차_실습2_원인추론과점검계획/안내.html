원인 분석을 점검 요청 초안으로 연결하기

VS Code에서 이 폴더(이 안내 파일이 있는 폴더)를 열고 START.md를 함께 읽으세요. 이 안내는 START.md와 같은 내용입니다.

출발점직접 구현할 것작업 순서진행할 때실행기대 결과를 먼저 적을 사례 종류학생이 정할 것이번 범위 밖완료 조건저장과 다음 실습

포털에서 본 조회와 판단을 VS Code에서 독립 에이전트로 직접 만듭니다. 에이전트는 설비 그래프와 경보 사례를 읽는 도구를 스스로 골라 부르고, 원인 후보·근거·추가 확인을 점검 요청 초안(대상 설비·부품·관측 시각·확인 항목·이유)으로 바꿉니다. 점검 담당자가 이 초안만 읽고 무엇을 왜 현장에서 확인할지 정할 수 있어야 합니다. 초안은 원인을 확정한 것도, 작업지시를 낸 것도 아닙니다.

출발점

  • 코드/source/ontology/: 설비 그래프(graph.json 노드 83개 · 관계 136개, schema.json). 경보에서 원인·증거·조치까지 가는 길과 증거 한 건을 읽는 법은 source/ontology/README.md에 있습니다.
  • 코드/source/cases/cases.json: 경보 사례 S01~S11(HYD-01~03, 이상 패턴 네 종류). 신선도(freshness)와 관측 충분성(coverage)의 뜻은 source/cases/README.md에 있습니다. 제공된 과거 입력이며 지금 설비의 값이 아닙니다.
  • 코드/source/manuals/: HM-8(쿨러 · 팬), PM-02(정기 점검), PR-07(예비품) 원문과 문서_목록.csv.
  • 코드/llm_client.py, 코드/.env: 모델 접속입니다. .env의 등호 뒤에 수업에서 받은 주소·키를 적고 LLM_MODEL에는 coding을 적습니다. chat(messages, tools)에 도구 목록을 주면 모델이 그 가운데서 골라 부릅니다.
  • 코드/입출력_계약.md: 결과 형식. 코드/check.py: 결과의 구조 검사.
  • 빈 틀: 코드/output/expected.md(기대와 실제), 코드/output/review.md(호출 기록과 어긋남 대조).

에이전트 코드는 아직 없습니다. 도구·실행 고리·결과 작성은 모두 직접 만듭니다.

직접 구현할 것

코드/output/agent.py(필요하면 도구를 둔 파일을 따로)를 만들어 실행하면 코드/output/점검요청_초안.json과 사람이 읽을 코드/output/점검요청_초안.md가 생기게 합니다.

부분내용
도구설비 그래프와 사례 입력을 읽어 물음에 맞는 것을 돌려주는 함수. 무엇을 받아 무엇을 돌려주는지 설명을 붙여 모델에게 알려 줍니다
실행 고리모델이 고른 도구를 대신 실행해 결과를 돌려주고, 부른 순서대로 호출 기록(calls)에 남깁니다
멈춤 조건답을 냈을 때, 반복 한도에 닿았을 때, 같은 호출을 되풀이할 때, 오류가 났을 때 멈추고 그 까닭을 남깁니다
점검 요청 초안대상 설비 · 구성 요소, 부품, 관측 시각 · 값, 확인 항목, 이유(증거 · 원문 절), 다른 후보, 「확정 원인도 작업지시도 아니다」는 표시
보류근거가 모자라 초안을 낼 수 없으면 이유와 빠진 것을 적고 초안 칸은 비웁니다

결과에 적은 값마다 그 값을 돌려준 호출 번호를 붙여, 결과에서 호출로 거슬러 확인할 수 있게 합니다.

작업 순서

  1. 탐색만 요청: AI에게 파일을 바꾸지 말고 코드/source/와 입출력_계약.md를 읽어 원인 후보가 그래프의 어느 관계로 이어지는지, 증거가 사례의 어느 값과 대응하는지, 부품·확인 항목의 근거가 어디 있는지 설명하게 합니다. 설명을 실제 파일과 대조합니다.
  2. 요구와 기대 정리: 점검 담당자가 초안에서 무엇을 보아야 하는지 자기 말로 정리합니다. 코드/output/expected.md에 아래 사례 종류마다 하나 이상 사례를 골라 기대 상태·원인 후보의 근거 상태·초안의 칸을 먼저 적습니다. 다 쓰면 「기대 칸을 쓴 시각」을 적고 저장합니다.
  3. 모델 연결 확인: python 코드/llm_client.py로 모델에 닿는지 확인합니다. 실패하면 화면의 까닭대로 .env를 고치고, 키를 채팅에 붙여 넣지 않습니다.
  4. 계획 검토: 도구 목록(이름 · 입력 · 돌려주는 것)과 실행 고리, 멈춤 조건의 계획만 먼저 받아, 계약의 칸이 모두 어느 도구의 결과에서 채워지는지 확인합니다.
  5. 작은 단위로 구현: 도구 하나씩 → 사례 하나(S01)로 실행 고리 → 점검 요청 초안 작성 순서로 만들고 그때마다 실행합니다.
  6. 호출 기록 대조: 사례 하나의 calls를 열어 모델이 고른 도구·입력·결과와, 그 결과가 다음 호출이나 초안의 어디에 쓰였는지 review.md에 적습니다. 결과의 문장이 아니라 호출이 근거입니다.
  7. 어긋남과 다른 대상: 오래된 값·표본 부족·복수 원인·문서 기준과 다른 곳이 결과에 어떻게 나왔는지 review.md에 대조합니다. 다른 설비·다른 경보 사례에도 같은 프로그램을 돌려 처음 사례에만 맞춘 곳이 없는지 봅니다.
  8. 수정 요청: 다르면 입력(사례 · 원문 줄), 기대(근거), 실제(출력)를 함께 주고 그 부분만 고치게 합니다. 결과에 맞추려고 기대를 바꾸지 않습니다. 고친 뒤 전체 사례를 다시 돌리고 python 코드/check.py를 실행합니다.
  9. 저장 · 재열기: 저장한 파일을 다시 열어 확인합니다.

진행할 때

  • 채팅에 파일 이름을 쓸 때는 백틱()으로 감쌉니다. 예: source/cases/cases.json`. 채팅 입력이 밑줄(_)을 서식으로 바꿔 이름이 달라질 수 있습니다.
  • AI가 완료를 알리면 실행한 명령과 그 출력 원문(요약이 아니라 나온 글자 그대로)을 붙여 달라고 요청합니다.
  • AI가 질문 카드(선택지와 「(권장)」 표시)로 물으면, 「(권장)」은 AI의 추천일 뿐입니다. 근거가 되는 원문·사례 줄을 열어 확인한 뒤 고르거나 직접 입력 칸에 결정과 근거를 적습니다.
  • 파일 편집 승인 창이 뜨면 바뀔 파일이 코드/output/ 아래인지 보고 허용하고, 아니면 거절합니다.
  • 실행이 모델 호출 때문에 느리면 사례 하나(S01)로 먼저 확인한 뒤 전체를 돌립니다. 같은 조건으로 같은 실패를 되풀이해 돌리지 않습니다.

기대 결과를 먼저 적을 사례 종류

  • 증거 기준에 맞는 원인이 하나 있고 값이 신선하며 표본이 충분한 사례
  • 신선도가 한도를 넘은 사례(오래된 값)
  • 관측 충분성이 모자라거나 값이 없는 증거가 있는 사례(표본 부족 · 값 없음)
  • 둘 이상의 원인 후보가 남는 사례(복수 원인)
  • 증거가 등록되지 않은 원인만 있는 사례, 또는 그래프와 원문의 기준이 다른 사례(문서 기준과 다른 곳)
  • 앞 사례와 다른 설비 · 다른 경보의 사례(다른 대상 적용)

학생이 정할 것

원자료만으로 하나로 정해지지 않아 학생이 근거를 찾아 정하는 지점입니다. 정한 내용·근거·바뀌는 사례를 expected.md 「정한 것」 표에 적습니다. AI는 이 지점을 정하기 전에 학생에게 묻습니다.

오래된 값이나 표본 부족 때문에 증거를 확인하지 못한 사례에서, 초안을 보류할지, 확인하지 못한 값을 확인 항목으로 넣어 점검 요청 초안으로 낼지 정합니다.

증거의 기준값 비교를 도구(프로그램)가 할지 모델이 할지 정합니다. 어느 쪽을 골랐는지에 따라 호출 기록에 남는 것과 틀릴 수 있는 곳이 달라집니다.

이번 범위 밖

원자료·그래프·원문 수정, 원인 확정, 작업지시 발행과 설비 제어, 조치 후보 비교·승인 요청(이전 회차와 다음 회차), 포털 호출. 반복할 방법을 스킬 파일로 정리하는 일은 다음 실습에서 합니다.

완료 조건

  • python 코드/output/agent.py가 사례 열한 건을 모두 처리하고 python 코드/check.py에서 확인 필요 0건입니다.
  • 점검요청_초안.md만 읽고도 사례마다 대상 설비·부품·관측 시각·확인 항목·이유를, 보류한 사례는 그 이유를 설명할 수 있습니다.
  • 결과에 적은 값마다 호출 번호가 있고, 그 호출의 입력·결과가 원자료와 같습니다.
  • expected.md에 위 사례 종류마다 실행 전에 적은 기대와 실행 후 실제가 있고, review.md에 어긋남 대조와 다른 대상 적용 결과가 있습니다.
  • 가설을 확정 원인으로, 초안을 작업지시로 쓴 곳이 없고, 결과를 맞추려고 원자료·기대를 바꾸지 않았습니다.

저장과 다음 실습

코드와 결과를 저장하고 다시 열어 확인하세요. .env의 키는 보관용 복사본에 넣지 않습니다. 보관할 결과는 재부팅 전에 USB 또는 개인 클라우드에 복사하세요. 다음 실습에서는 반복할 업무 방법을 스킬 파일(SKILL.md)로 만듭니다.
