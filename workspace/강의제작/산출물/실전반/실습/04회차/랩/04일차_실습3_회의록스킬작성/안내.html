회의 결정과 후속 업무를 추출하는 스킬 만들기

VS Code에서 이 폴더(이 안내 파일이 있는 폴더)를 열고 START.md를 함께 읽으세요. 이 안내는 START.md와 같은 내용입니다.

출발점직접 구현할 것작업 순서진행할 때기대 결과를 먼저 적을 사례 종류학생이 정할 것이번 범위 밖완료 조건저장과 다음 실습

설비보전 회의록 두 건에서 결정·제안·조건부 작업·담당 미정을 가르고, 앞 회의의 결정이 뒤 회의에서 어떻게 이어졌는지 연결하는 회의 후속 스킬(SKILL.md)을 직접 씁니다. 남은 일마다 다음 협의에서 확인할 질문과 원문 근거가 붙어 있어야, 다음 회의를 준비하는 사람이 무엇을 정해야 하는지 바로 알 수 있습니다. 스킬은 이번 두 회의에만 맞춘 답이 아니라 다른 회의록에도 다시 쓰는 일하는 방법입니다.

출발점

  • 코드/source/회의록_1.txt: 10월 설비보전 정기 회의록(2026-10-06). 지난 회의 조치 점검과 안건 여덟 개.
  • 코드/source/회의록_2.txt: 주간 생산·보전 협의 메모(2026-10-08). 정기 회의에서 넘어온 건이 들어 있습니다.
  • 빈 틀: 코드/output/expected.md(적용 전에 적는 기대), 코드/output/review.md(적용 기록과 재적용 대조).
  • 스킬 자리: GitHub Copilot은 이 폴더의 .github/skills/<스킬 이름>/SKILL.md를 읽습니다. 머리말의 name은 폴더 이름과 같게, description은 이 스킬을 언제 쓰는지(호출 조건)를 적습니다. Codex를 쓰면 그 도구가 스킬을 읽는 위치를 먼저 확인합니다.

스킬 파일과 결과는 아직 없습니다.

직접 구현할 것

.github/skills/meeting-actions/SKILL.md를 쓰고, 그 스킬을 두 회의록에 적용해 회의록마다 코드/output/에 사람이 읽을 Markdown과 같은 내용의 JSON 작업 목록을 냅니다(예: 회의록_1_후속.md·회의록_1_후속.json). 두 형식은 같은 항목 ID를 씁니다.

항목마다 다음을 담습니다.

칸내용
ID와 원문 근거항목 번호, 회의록 파일과 절 · 줄, 근거가 된 원문 문장
구분결정 · 제안 · 조건부 작업 · 확인 필요 같은 성격. 담당이나 기한이 없으면 「미정」으로 따로 표시
내용 · 담당 · 기한원문에 적힌 그대로. 상대 날짜는 원문 표현과 해석 기준을 함께
상태끝남 · 진행 중 · 전달함 · 미결 등. 전달한 것과 끝난 것을 다른 상태로, 설비가 여럿이면 설비별로
이어진 기록앞 회의의 어느 항목이 뒤 회의의 어느 문장으로 이어졌는지
다음 협의 질문미결 항목마다, 다음 협의에서 무엇을 정하거나 확인해야 하는지 묻는 질문 한 줄

스킬 본문에는 이 칸을 채우는 방법(입력 · 순서 · 예외 · 출력)을 적고, 특정 사람 이름 · 날짜 · 설비 번호를 적지 않습니다.

작업 순서

  1. 탐색만 요청: AI에게 스킬이나 결과를 만들지 말고 두 회의록에서 결정 · 제안 · 조건부 작업 · 담당 미정 · 이미 끝난 일이 어디 있는지, 두 회의록 사이에 이어지는 내용이 무엇인지 원문 위치와 함께 설명하게 합니다. 설명을 원문과 대조합니다.
  2. 요구와 기대 정리: 다음 회의를 준비하는 사람이 무엇을 보아야 하는지 자기 말로 정리합니다. 코드/output/expected.md에 아래 사례 종류마다 원문 문장 하나 이상을 골라 기대 구분 · 상태 · 다음 협의 질문을 먼저 적고 「기대 칸을 쓴 시각」을 적습니다.
  3. 스킬 계획 검토: SKILL.md의 머리말(name · description)과 본문 구성 계획만 먼저 받아, 위 칸이 모두 어떤 방법으로 채워지는지, 이름 · 날짜가 지침에 들어가지 않는지 확인합니다.
  4. 스킬 작성과 인식 확인: SKILL.md를 쓰고, 도우미가 이 스킬을 실제로 읽어 적용했는지 확인합니다. 파일이 있다는 것만으로 적용됐다고 보지 않습니다.
  5. 첫 회의록 적용: 회의록_1에 적용해 결과와 원문을 나란히 놓고 expected.md와 대조합니다. 틀린 항목은 결과만 고치지 않고 SKILL.md의 해당 지침을 고쳐 다시 적용합니다.
  6. 둘째 회의록과 연결: 회의록_2에 같은 스킬을 적용하고, 앞 회의의 결정과 뒤 회의의 후속 확인을 연결합니다. 전달 완료와 발주 완료, 설비별 점검 상태가 구분되는지 봅니다.
  7. 지침 보완: 미결 항목마다 다음 협의 질문과 원문 근거가 남도록 지침을 보완합니다.
  8. 두 원문에 다시 적용: 고친 스킬로 두 회의록을 처음부터 다시 처리해, 앞에서 맞던 구분 · 담당 · 기한이 그대로인지, 특정 이름 · 날짜에만 맞춘 지침이 없는지 review.md에 적습니다.
  9. 저장 · 재열기: Markdown과 JSON의 항목 수 · ID · 담당 · 기한이 같은지 대조하고 저장합니다.

진행할 때

  • 채팅에 파일 이름을 쓸 때는 백틱()으로 감쌉니다. 예: source/회의록_1.txt`. 채팅 입력이 밑줄(_)을 서식으로 바꿔 이름이 달라질 수 있습니다.
  • AI가 완료를 알리면 적용한 스킬 이름과 실제로 만든 파일 목록, 출력 원문을 붙여 달라고 요청합니다.
  • AI가 질문 카드(선택지와 「(권장)」 표시)로 물으면, 「(권장)」은 AI의 추천일 뿐입니다. 근거가 되는 원문 줄을 열어 확인한 뒤 고르거나 직접 입력 칸에 결정과 근거를 적습니다.
  • 파일 편집 승인 창이 뜨면 바뀔 파일이 .github/skills/ 또는 코드/output/ 아래인지 보고 허용하고, 아니면 거절합니다.
  • 결과를 고칠 때는 입력(원문 줄), 기대(근거), 실제(결과)를 함께 주고, 고친 뒤 같은 종류의 다른 문장에도 통하는지 다시 확인합니다.

기대 결과를 먼저 적을 사례 종류

  • 담당과 기한이 모두 있는 결정
  • 담당이나 기한이 없는 결정(담당 미정)
  • 결론 없이 끝난 논의, 정하지 않고 넘어간 제안
  • 「~이면 ~한다」처럼 조건이 붙은 작업
  • 두 사람이 함께 맡거나, 맡은 사람이 불참해 확인하지 못한 일
  • 앞 회의의 결정이 뒤 회의에서 전달 · 진행으로 이어진 일(전달 완료와 발주 완료)
  • 같은 결정이 설비 여러 대에 걸쳐 설비마다 상태가 다른 일
  • 「내일」「이번 주 안」「다음 주 금요일」처럼 상대 날짜로 적힌 기한

학생이 정할 것

원문만으로 하나로 정해지지 않아 학생이 근거를 찾아 정하는 지점입니다. 정한 내용 · 근거 · 바뀌는 항목을 expected.md 「정한 것」 표에 적고, 같은 결정을 SKILL.md 지침에 반영합니다. AI는 이 지점을 정하기 전에 학생에게 묻습니다.

앞 회의의 결정과 뒤 회의의 후속 기록을 한 항목의 상태 변화로 합칠지, 별도 항목으로 두고 서로 연결할지 정합니다. 어느 쪽이든 결정이 사라지거나 같은 일이 두 번 생기지 않아야 합니다.

상대 날짜를 날짜로 풀지, 원문 표현대로 두고 해석 기준만 적을지 정합니다. 기준이 여럿으로 읽히는 표현을 어떻게 다룰지도 함께 정합니다.

이번 범위 밖

일정 등록 · 알림 발송 · 담당자에게 메시지 보내기, 회의록 원문 수정, 회의록에 없는 담당 · 기한 정하기, 외부 자료(Notion · 파일 서버 · Git) 연결. 외부 자료를 엮은 다음 협의 안건은 다음 실습에서 이 스킬을 다시 써서 만듭니다.

완료 조건

  • .github/skills/meeting-actions/SKILL.md에 name · description과 입력 · 순서 · 예외 · 출력이 있고, 특정 사람 이름 · 날짜 · 설비 번호가 지침에 없습니다.
  • 두 회의록 각각의 Markdown · JSON 결과가 있고, 항목 수와 ID가 같습니다.
  • 결정 · 제안 · 조건부 작업 · 담당 미정이 구분되고, 전달 완료와 발주 완료, 설비별 점검 상태가 다른 상태로 남아 있습니다.
  • 미결 항목마다 다음 협의 질문과 원문 근거가 있습니다.
  • expected.md에 적용 전에 적은 기대와 실제가 있고, review.md에 고친 스킬로 두 원문을 다시 적용한 결과가 있습니다.

저장과 다음 실습
