01 폴더와 출발점 확인

포털 데이터 연결에서 현재 값을 문서의 기준값과 나란히 놓고 구분했습니다. 이번에는 검토한 지식을 별도 랩 DB의 설비 모델과 조치 기준에 잇고, 핀 세척을 하기 전 작업자가 원문과 기록으로 되짚을 수 있는 작업 확인 카드를 만듭니다. 사건은 포털에서 본 경보와 같은 종류의 다른 경보 한 건인 10월 27일 01:59 HYD-02 쿨러 성능 저하 경보이고, 그 판정 뒤에 남은 근본 조치가 핀 세척입니다.

검토 결과에는 여러 문서 · 판의 후보와 결정이 섞여 있고, 문서 속 대상은 모델과 다른 이름으로 적혀 있습니다. 승인한 것만 기존 ID에 이어야 다음 실습이 근거 있는 지식만 씁니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 온톨로지 단계의 마지막 — 검토한 문서 지식을 그래프에 잇고 질문으로 확인하는 일 — 을 맡습니다.

받기 「실습 시작」 도구에서 과정 → 회차 → 실습을 고르고 새로 시작(이어서 할 때는 이전 작업 열기)을 누르면 이 폴더와 가이드가 열립니다. 받기에 실패하면 다시 시도하고, 안 되면 수동 ZIP을 풀어 VS Code의 파일 → 폴더 열기(File → Open Folder)로 엽니다.

필요한 것 VS Code와 Python, 로그인해 둔 Codex 또는 GitHub Copilot, 랩 DB를 켤 Docker Desktop.

받은 폴더 VS Code 왼쪽 탐색기에 이렇게 보입니다.

해결할 질문 이 답은 보전 야간조가 핀 세척 전에 카드로 준비 · 금지 · 완료와 지난 시행 · 부품을 되짚고, 설비보전팀장이 승인할 때 씁니다.

  1. HYD-02 핀 세척 작업 확인 카드 — 준비 · 금지 · 순서 · 완료 · 작업 직전 확인할 현재 값 · 부품 준비 · 지난 시행 · 승인 · 남은 질문은 무엇이고, 원문 절 · 인용과 원천 기록 번호는 무엇인가?
  2. 같은 방법으로 다른 작업의 카드도 만들어지는가? 원문이 없는 작업 · 절은 「결과 없음」으로 구별되는가?
  3. 같은 적재를 다시 해도 수가 같은가? 공급 정보와 작업 조건을 어디까지 답하고, 현재 값 · 승인 없이 정할 수 없는 것은 무엇인가?

말 풀이 적재는 대상 · 관계를 그래프 DB에 넣는 일이고, 스키마 확장은 문서 근거를 담으려고 설비 모델에 더하는 새 종류 · 관계와 그 뜻입니다. 승인 후보는 검토 결과에서 결정이 채택 · 수정(상태 approved)인 후보이고, 보류 · 제외 후보는 적재하지 않습니다. 현재 값은 재고 · 작업지시 상태 · 센서 값처럼 계속 바뀌어 그 값이 기록되는 시스템(원천)에서 읽어야 하는 값입니다 — 센서 값은 시계열 DB, 정비 작업지시는 CMMS(설비 보전 관리 시스템), 재고는 ERP(전사 자원 관리 시스템), 생산 실행은 MES(생산 실행 시스템)에 기록됩니다. 내보내기는 그래프의 대상 · 관계를 다음 실습이 읽는 파일 하나로 쓰는 일입니다. 작업 확인 카드는 작업자가 작업 전에 준비 · 금지 · 순서 · 완료와 지난 기록을 되짚는 표이고, 승인을 대신하지 않습니다. 계약은 결과 파일의 모양(열 · 키와 그 뜻)을 정해 둔 입출력_계약.md입니다 — 다음 실습의 기능이 이 모양 그대로 읽습니다.

내 앞 결과를 쓸 때: 제공 입력은 그대로 두고 내 검토 결과 · 모델 등을 결과/내_입력/에 입력/과 같은 이름 · 같은 자리로 복사해, 형식이 입출력_계약.md 「입력」과 같은지 먼저 견준 뒤 씁니다. lab_cypher.py model과 check.py는 결과/내_입력/에 있는 파일을 씁니다. 내 결과가 없어도 제공된 입력으로 끝까지 할 수 있습니다.

왜 하는가 만들기 전에 무엇이 주어졌고 무엇을 만들어야 하는지 알아야 AI에게도 같은 출발점을 말할 수 있습니다. 이 답을 누가 어디에 쓰는지에 따라 무엇을 하나로 보고 무엇을 따로 둘지가 달라지므로, 쓰는 사람도 여기서 확인합니다. 조치에서 근거 문서까지 관계를 따라가려면, 무엇이 이미 검토되었고 무엇이 보류되었는지부터 알아야 합니다.

할 일 탐색기에서 입력/ · 자료/ · 결과/ · lab_db.py · lab_cypher.py · START.md를 찾고 이 답을 쓰는 사람과 해결할 질문을 읽습니다. 입력/조치검토결과.json에서 사건 경보의 검토 의견을 보고, 고른 작업과 다른 작업 카드의 대상을 확인합니다. 입력/검토결과/의 파일 하나를 열어 결정(채택 · 수정 · 제외 · 보류)이 섞여 있는 것을 확인합니다.

정하거나 물을 것 이 답을 쓰는 사람과 질문을 확인합니다. 다른 작업 카드의 대상이 어느 파일의 어느 값에서 왔는지 말합니다.

02 파일을 바꾸지 않고 자료 파악

왜 하는가 문서 속 대상은 모델의 ID와 다른 이름 · 번호로 적혀 있을 수 있습니다. 어느 기존 ID를 가리키는지 먼저 짝지어 두어야 적재할 때 새 대상을 지어내지 않고 기존 ID에 잇습니다.

할 일 AI에게 파일을 바꾸지 말고 입력/과 자료/문서_목록.csv를 읽어 달라고 해, 검토 결과마다 결정(채택 · 수정 · 제외 · 보류) 수와 후보가 가리키는 대상이 설비 모델 · SOP 구조 · 조건표의 어느 ID인지 표로 받습니다. 짚은 ID를 모델 파일에서 직접 엽니다.

Codex는 왼쪽 활동 표시줄의 Codex 아이콘으로, GitHub Copilot은 같은 채팅 창의 Chat 탭으로 엽니다. 답에 나온 줄은 편집기에서 직접 열어 읽고, 「완료」라는 말 대신 실제 파일과 출력으로 확인합니다.

편집 승인 창(Allow ChatGPT to edit the following file?)에서는 경로가 결과/ 아래인 요청한 변경만 Allow once, 그 밖은 Deny를 누릅니다.

정하거나 물을 것 검토 결과의 결정 분포와, 후보가 가리키는 대상(설비 · 구성 요소 · 부품 · SOP · 단계 · 규칙)이 어느 기존 ID인지 묻습니다.

03 기대 카드 먼저

왜 하는가 작업 확인 카드는 작업자가 작업 전에 되짚는 표이지 승인이 아닙니다. 카드를 조회 결과로 만들기 전에 항목마다 무엇이 들어가야 하는지 원문과 기록에서 먼저 적어 두어야, 빠진 조건과 지어낸 항목이 보입니다.

할 일 결과/구축_기록.md에 목표 · 쓰는 사람을 내 말로 적고, 핀 세척 카드의 항목(준비 · 금지 · 순서 · 완료 · 현재 값 · 부품 · 지난 시행 · 승인 · 남은 질문)마다 기대를 원문 · 검토 결과 · 기록 줄로 적습니다. 「학생이 정할 것」의 선택 · 근거 · 바뀌는 답(못 정하면 미결)과 기대 칸을 쓴 시각도 적습니다. 다 적으면 AI에게는 파일을 바꾸지 말고 내가 적은 것을 되짚게만 합니다.

고친 파일은 Ctrl+S로 저장합니다(탭 이름 옆 ●가 사라지면 저장됨).

학생이 정할 것 — 지점의 종류 원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 결과/구축_기록.md 「정한 것」 표에 적습니다.

  • 다른 문서의 조건 — 다른 문서가 정한 조건 · 시간 · 승인을 이 작업에 이을지 — 어느 문서의 어느 문장인지는 탐색에서 찾습니다

질문 카드의 「(권장)」은 AI의 추천일 뿐이니, 직접 입력 칸에 내 결정과 근거 줄을 적어 보냅니다.

정하거나 물을 것 지점마다 내 선택과 근거를 말합니다. AI가 고를 것을 내놓거나 「권장」을 붙이면 따르지 말고 원문 줄을 다시 열어 내 말로 정합니다. 못 정한 지점은 미결로 적습니다.

할 일 AI에게 파일을 바꾸지 말고 문서 · 판 · 절 · 인용 · 검토 결정을 담을 새 종류 · 관계와 적재 순서를 제안하게 합니다. 처음 정한 질문 하나를 계획에 대어 어느 노드 · 관계를 따라 답이 나오는지 짚게 하고, 내가 동의하면 결과/schema_ext.json 초안을 만들게 합니다.
