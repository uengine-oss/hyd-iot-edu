# 검토 지식으로 작업 확인 카드 만들기

## 목표

포털 데이터 연결에서 현재 값을 문서의 기준값과 나란히 놓고 구분했습니다. 이번에는 검토한 지식을 별도 랩 DB의 설비 모델과 조치 기준에 잇고, 핀 세척을 하기 전 작업자가 원문과 기록으로 되짚을 수 있는 작업 확인 카드를 만듭니다. 사건은 포털에서 본 경보와 같은 종류의 다른 경보 한 건인 10월 27일 01:59 HYD-02 쿨러 성능 저하 경보이고, 그 판정 뒤에 남은 근본 조치가 핀 세척입니다.

검토 결과에는 여러 문서 · 판의 후보와 결정이 섞여 있고, 문서 속 대상은 모델과 다른 이름으로 적혀 있습니다. 승인한 것만 기존 ID에 이어야 다음 실습이 근거 있는 지식만 씁니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 온톨로지 단계의 마지막 — 검토한 문서 지식을 그래프에 잇고 질문으로 확인하는 일 — 을 맡습니다.

만들 것: 스키마 확장 `결과/schema_ext.json`, 문서 · 판 · 절과 승인 지식을 기존 ID에 잇는 적재 파일, 조회문 `결과/query.cypher`, 지난 시행 · 부품 준비를 원천에서 읽는 코드, 작업 확인 카드 둘(`결과/작업확인카드_<SOP ID>.md`), 남은 질문 `결과/남은_질문.json`, 내보내기 `결과/지식_내보내기.json`, `결과/구축_기록.md`.

## 출발점

- `입력/모델/` — 설비 모델(schema.json · graph.json). `입력/조건표.csv` · `입력/sop.json` — 냉각 계통 조치의 조건표와 SOP 구조. `입력/조치검토결과.json` — 그 조건표로 지난 30일 경보를 판정 · 비교한 조치 검토 결과.
- `입력/검토결과/` — 문서마다 후보와 결정(채택 · 수정 · 제외 · 보류) · 근거를 적은 검토 결과 · 고른 작업의 조건(`선택작업_조건.json`). 문서에서 지식을 추출 · 검토하는 실습의 결과와 같은 꼴로 검증해 제공하는 판입니다.
- 내 앞 결과를 쓸 때: 제공 입력은 그대로 두고 내 검토 결과 · 모델 등을 `결과/내_입력/`에 `입력/`과 같은 이름 · 같은 자리로 복사해, 형식이 `입출력_계약.md` 「입력」과 같은지 먼저 견준 뒤 씁니다. `lab_cypher.py model`과 `check.py`는 `결과/내_입력/`에 있는 파일을 씁니다. 내 결과가 없어도 제공된 입력으로 끝까지 할 수 있습니다.
- `자료/` — 검토한 문서의 원문과 `자료/문서_목록.csv`(문서마다 판 · 상태 · 시행일 · 파일 · SHA-256), `자료/작업지시_이력.csv`(CMMS 작업지시 내보내기) · `자료/재고_현황.csv`(ERP 재고 내보내기).
- `lab_db.py` — 이 폴더 전용 랩 DB(그래프 DB)를 켜는 도구. `lab_cypher.py` — 설비 모델 · 조치 기준 적재 · 적재 파일 실행 · 세기 · 내보내기 도구. `입출력_계약.md` — 입력과 결과 파일의 형식. `check.py` — 결과의 구조 검사.
- `결과/` — 이번에 만든 것을 두는 자리. 「제공 빈 틀」 `구축_기록.md`가 있습니다.
- `AGENTS.md` · `.github/copilot-instructions.md` · `CLAUDE.md` — Codex와 GitHub Copilot이 지키는 작업 규칙(세 파일이 같은 내용). 학생도 함께 읽습니다.

## 처음 쓰는 도구

- `python lab_cypher.py model` — 설비 모델과 조치 기준(SOP 구조 · 조건표)을 랩 DB에 올립니다. 무엇이 어떤 이름으로 올라가는지는 `입출력_계약.md` 2절에 있습니다.
- `python lab_cypher.py run 결과/<파일>.cypher` — 적재 파일의 문장을 차례로 실행합니다. `count` — 종류 · 관계별 수. `export 결과/지식_내보내기.json` — 내보내기.

## 해결할 질문

이 답은 보전 야간조가 핀 세척 전에 카드로 준비 · 금지 · 완료와 지난 시행 · 부품을 되짚고, 설비보전팀장이 승인할 때 씁니다.

1. HYD-02 핀 세척 작업 확인 카드 — 준비 · 금지 · 순서 · 완료 · 작업 직전 확인할 현재 값 · 부품 준비 · 지난 시행 · 승인 · 남은 질문은 무엇이고, 원문 절 · 인용과 원천 기록 번호는 무엇인가?
2. 같은 방법으로 다른 작업의 카드도 만들어지는가? 원문이 없는 작업 · 절은 「결과 없음」으로 구별되는가?
3. 같은 적재를 다시 해도 수가 같은가? 공급 정보와 작업 조건을 어디까지 답하고, 현재 값 · 승인 없이 정할 수 없는 것은 무엇인가?

## 학생이 정할 것

원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 `결과/구축_기록.md` 「정한 것」 표에 적습니다.

- **다른 문서의 조건** — 다른 문서가 정한 조건 · 시간 · 승인을 이 작업에 이을지 — 어느 문서의 어느 문장인지는 탐색에서 찾습니다

AI에게 이 지점을 대신 정하게 하지 않습니다. AI가 고를 것을 내놓거나 「권장」을 붙여도 그대로 따르지 말고, 원문 줄을 열어 내 선택과 근거를 말합니다. 못 정한 지점은 미결로 남깁니다.

## 이번 범위 밖

- 문서에서 후보를 다시 뽑거나 검토 결정을 바꾸는 일 — 바꿀 것은 남은 질문으로 남깁니다
- 포털 DB에 접속하거나 포털 자료를 랩 DB에 넣는 일
- 현재 값(재고 · 작업지시 상태 · 센서 값)을 그래프에 넣는 일
- 설비 모델의 기존 ID · 기존 종류 · 관계의 뜻을 바꾸는 일

자료에 있어도 이번 결과에 만들지 않습니다.

## 결과 형식

파일의 모양은 `입출력_계약.md`에 있습니다. 무엇을 어떤 종류 · 관계로 담을지, 새 대상의 ID를 어떻게 지을지는 직접 정합니다.

- `결과/schema_ext.json` — 문서 근거를 담으려고 더한 종류 · 관계.
- `결과/` 아래 적재 파일(`.cypher` 또는 적재 문장을 만드는 코드) — 다시 실행해도 수가 늘지 않게.
- `결과/query.cypher` — 질문마다의 조회문.
- `결과/작업확인카드_<SOP ID>.md` — 작업 확인 카드(계약 「작업 확인 카드」). 고른 작업과 다른 작업 하나 이상.
- `결과/남은_질문.json` · `결과/지식_내보내기.json` — 그래프에 넣지 않은 남은 질문과 내보내기(다음 실습의 입력).
- `결과/구축_기록.md` — 「제공 빈 틀」의 칸대로 채웁니다.
- 만든 코드는 `결과/` 아래에 두고, 이름은 하는 일로 짓습니다.

## 지킬 조건

- `입력/` · `자료/`는 읽기만 합니다.
- 승인(`approved`) 후보만 적재합니다.
- 기존 ID를 바꾸지 않고, 모델에 없는 기존 ID를 지어내지 않습니다.
- 현재 값(재고 · 작업지시 상태 · 센서 값)은 그래프에 넣지 않고 읽을 원천을 가리킵니다.
- 전체를 지우는 문장을 쓰지 않습니다.

## 진행 단계

한 번에 한 단계씩 갑니다. 단계마다 결과를 확인한 뒤 다음 단계로 갑니다. 단계마다 정하거나 물을 것, 요청에 담을 것, 판단할 증거는 `guide.html`의 같은 번호에 있습니다.

1. **폴더와 출발점 확인** — 탐색기에서 `입력/` · `자료/` · `결과/` · `lab_db.py` · `lab_cypher.py` · `START.md`를 찾고 이 답을 쓰는 사람과 해결할 질문을 읽습니다. `입력/조치검토결과.json`에서 사건 경보의 검토 의견을 보고, 고른 작업과 다른 작업 카드의 대상을 확인합니다. `입력/검토결과/`의 파일 하나를 열어 결정(채택 · 수정 · 제외 · 보류)이 섞여 있는 것을 확인합니다.
2. **파일을 바꾸지 않고 자료 파악** — AI에게 파일을 바꾸지 말고 `입력/`과 `자료/문서_목록.csv`를 읽어 달라고 해, 검토 결과마다 결정(채택 · 수정 · 제외 · 보류) 수와 후보가 가리키는 대상이 설비 모델 · SOP 구조 · 조건표의 어느 ID인지 표로 받습니다. 짚은 ID를 모델 파일에서 직접 엽니다.
3. **기대 카드 먼저** — `결과/구축_기록.md`에 목표 · 쓰는 사람을 내 말로 적고, 핀 세척 카드의 항목(준비 · 금지 · 순서 · 완료 · 현재 값 · 부품 · 지난 시행 · 승인 · 남은 질문)마다 기대를 원문 · 검토 결과 · 기록 줄로 적습니다. 「학생이 정할 것」의 선택 · 근거 · 바뀌는 답(못 정하면 미결)과 기대 칸을 쓴 시각도 적습니다. 다 적으면 AI에게는 파일을 바꾸지 말고 내가 적은 것을 되짚게만 합니다.
4. **스키마 확장과 계획 검토** — AI에게 파일을 바꾸지 말고 문서 · 판 · 절 · 인용 · 검토 결정을 담을 새 종류 · 관계와 적재 순서를 제안하게 합니다. 처음 정한 질문 하나를 계획에 대어 어느 노드 · 관계를 따라 답이 나오는지 짚게 하고, 내가 동의하면 `결과/schema_ext.json` 초안을 만들게 합니다.
5. **랩 DB 준비와 설비 모델 · 조치 기준 적재** — 터미널에서 `python lab_db.py`로 이 폴더 전용 랩 DB를 켜고, `python lab_cypher.py model`로 설비 모델과 조치 기준(SOP 구조 · 조건표)을 올린 뒤 `python lab_cypher.py count`로 셉니다.
6. **구현 ① 문서 · 판 · 절 적재** — 문서 목록과 검토 결과에서 문서 · 판 · 절을 노드로 만드는 적재 파일을 `결과/`에 만들고 실행합니다.
7. **구현 ② 승인 후보를 기존 ID에 이어 적재** — 검토 결과의 승인(`approved`) 후보를 노드로 만들고, 출처 절과 기존 ID(설비 · 구성 요소 · 센서 · 부품 · SOP · 단계 · 규칙)에 잇는 적재를 더해 실행합니다.
8. **반복 적재 확인** — 지금까지의 적재 파일을 같은 순서로 한 번 더 실행하고 `count`를 앞의 수와 견줍니다.
9. **구현 ③ 작업 조건 조회** — SOP ID 하나를 받아 그 작업의 준비 · 금지 · 순서 · 완료 · 승인과 원문 출처(문서 · 판 · 절 · 인용)를 돌려주는 조회문을 `결과/query.cypher`에 만들고 실행합니다. 절차 밖 절 · 다른 문서의 조건도 따라오는지 봅니다.
10. **구현 ④ 지난 시행 찾기** — `자료/작업지시_이력.csv`에서 이 작업의 지난 시행을 찾아 작업지시 번호 · 설비 · 상태 · 완료일 · 기록을 출력하는 코드를 `결과/`에 만들고 실행합니다.
11. **구현 ⑤ 부품 준비 읽기** — 이 작업에 쓸 부품의 재고 행을 `자료/재고_현황.csv`에서 읽어 품번 · 현재고 · 예약 · 입고 예정과 원천 행을 출력하는 기능을 더하고 실행합니다.
12. **구현 ⑥ 카드 쓰기** — 조회 결과와 지난 시행 · 부품 준비 출력으로 `결과/작업확인카드_SOP-COOL-14.md`를 쓰는 기능을 더하고 실행합니다(제목 · 규칙은 `입출력_계약.md` 「작업 확인 카드」).
13. **다른 작업 · 제공되지 않은 작업 · 절** — 같은 조회 · 카드 기능으로 다른 작업의 카드를 하나 더 만들고, 제공되지 않은 작업 · 절을 물었을 때 「결과 없음」으로 구별되는지 조회합니다.
14. **답할 수 있는 것과 현재 값 · 승인 · 공급 정보** — 질문마다 그래프로 답하는지, 현재 값 · 승인이 있어야 하는지, 공급 조건(모델)과 오늘 재고(원천)를 어디까지 답하는지 `결과/구축_기록.md` 「답할 수 있는 것과 없는 것」에 적습니다.
15. **구조 검사와 고치기** — 터미널에서 `python check.py`를 실행해 단계별 상태를 보고, 짚은 문제를 고친 뒤 다시 실행합니다.
16. **저장 · 내보내기 · 다시 열기** — `결과/남은_질문.json`을 쓰고 `python lab_cypher.py export 결과/지식_내보내기.json`으로 내보냅니다. 결과 파일을 모두 저장하고 VS Code에서 폴더를 닫았다 다시 연 뒤, `python lab_db.py`로 랩 DB를 다시 켜고 `count`와 질문 조회를 다시 실행합니다. `결과/구축_기록.md` 끝에 기준일 · 저장 시점 · 확인하지 못한 점을 적습니다.

이 순서는 바이브 코딩 일곱 단계 — 파일을 바꾸지 않고 파악 → 요구와 기대 답을 내 말로 → 계획 검토 → 작게 구현 → 원자료와 대조 → 고침 → 저장하고 다시 열기 — 를 따릅니다.

요청에 파일 이름을 쓸 때는 `결과/schema_ext.json`처럼 백틱(`)으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다.

## 확인

확인할 사례의 종류(어느 행이 해당하는지는 원자료에서 직접 찾습니다):

- 보류 · 제외 후보가 그래프와 카드에 들어가지 않았는지
- 같은 적재를 두 번 했을 때의 수
- 절차 밖 절 · 다른 절차 · 다른 문서에 있는 작업 조건
- 설비 별칭 · 제조사 품번으로 적힌 대상
- 완료라고 적혀 있어도 기록이 빠진 시행
- 현재고 · 예약 · 입고 예정이 다른 칸
- 다른 작업의 카드
- 제공되지 않은 작업 · 절을 묻는 질문
- 공급 조건(모델)과 오늘 재고(원천) · 승인의 경계

실행 명령:

```
python lab_db.py
python lab_cypher.py model
python lab_cypher.py run 결과/<적재 파일>.cypher
python lab_cypher.py count
python 결과/<만든 코드 이름>.py
python lab_cypher.py export 결과/지식_내보내기.json
python check.py
```

바뀐 파일 확인: AI가 단계를 마칠 때마다 바뀐 파일 목록을 봅니다. `입력/` · `자료/`가 바뀌지 않았는지, 요청하지 않은 파일이 생기지 않았는지 확인합니다. 편집 승인 창에서는 경로가 `결과/` 아래일 때만 허용합니다.

## 완료 판정

형식 검사나 실행 성공만으로 완료하지 않습니다. 카드 항목마다 먼저 적은 기대와 실제 카드가 원문 · 기록 줄로 맞고, 다른 작업 카드와 「결과 없음」이 구별되며, 같은 적재를 다시 해도 수가 같고, 「정한 것」의 근거와 그 선택으로 바뀌는 답을 설명할 수 있으면 완료입니다. 답하지 못한 것은 남은 질문으로 남깁니다.

`결과/`의 구축 기록 · 스키마 확장 · 적재 · 조회 · 카드 · 내보내기를 함께 보관합니다. 다음 실습 「원인 분석을 점검 요청 초안으로 연결하기」는 이 지식과 카드로 점검 요청을 만듭니다. 그 실습도 제공된 지식으로 시작할 수 있습니다. 재부팅 전에 이 실습 폴더를 USB 또는 개인 클라우드에 복사합니다. 자동으로 되살려 주지 않습니다.
