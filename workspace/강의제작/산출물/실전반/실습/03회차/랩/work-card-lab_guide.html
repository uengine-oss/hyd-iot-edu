01 폴더 열고 랩 DB 준비하기

클래스룸의 3회차 실습 자료에서 ZIP을 받아 압축 풀기를 선택합니다. VS Code의 파일 → 폴더 열기에서 work-card-lab 폴더를 엽니다. 함께 풀린 가이드는 브라우저로 엽니다.

신뢰 여부를 물으면 예, 작성자를 신뢰합니다(Yes, I trust the authors)를 선택합니다. 제한 모드에서는 Codex를 사용할 수 없습니다.

README.md에서 폴더 역할을 봅니다. data/reviews/는 문서에서 뽑은 지식 후보를 원문과 견줘 결정을 적은 검토 결과로, 문서 지식을 추출 · 검토하는 실습의 결과와 같은 꼴입니다. data/model/은 설비 모델, data/sop.json · data/conditions.csv는 조치 기준, data/documents/는 원문입니다. 적재 · 조회 · 내보내기는 제공 코드가 하고, app/features/에는 무엇을 어디에 이을지 내가 정할 자리가 있습니다. AGENTS.md는 Codex의 공통 작업 원칙입니다. Docker Desktop을 켜고 실행 중인지 본 뒤 아래 명령을 실행합니다. 이 폴더 전용 랩 DB가 만들어지고, 설비 모델과 조치 기준(SOP 구조 · 조건표)이 올라갑니다. 포털 DB와 떨어져 있어 여러 번 넣어도 포털에 영향이 없습니다.

사건은 10월 27일 01:59(한국 시각) HYD-02 쿨러 성능 저하 경보(경보 ALT-hyd02-0172-54a5)이고, 그 판정 뒤에 남은 근본 조치가 쿨러 핀 세척(SOP-COOL-14)입니다. 결과 화면의 판정 요청 시각 17:01(UTC)은 한국 시각 02:01입니다. 이 카드는 보전 야간조가 핀 세척 전에 준비 · 금지 · 완료를 원문으로 되짚고, 설비보전팀장이 승인할 때 씁니다.

내 앞 결과를 쓰는 것은 선택입니다. 쓸 때는 형식이 data/contract.md 「입력」과 같은지 먼저 견주고, app/features/my_inputs/에 data/와 같은 이름 · 같은 자리로 복사합니다(검토 결과는 my_inputs/reviews/, 이 사건의 작업 조건은 추출 실습의 output/selected_task.json을 my_inputs/reviews/selected_task.json으로). 넣은 검토 결과는 제공 검토 결과를 통째로 대신하므로, 내 결과에 없는 문서의 행은 연결 규칙에서 뺍니다. 제공 입력은 그대로 둡니다.

터미널을 엽니다. 오타를 줄이도록 명령은 직접 치지 말고 블록의 복사로 붙여 넣습니다.

터미널(PowerShell · 이 실습 폴더)

「랩 DB 준비 완료」와 127.0.0.1 주소, 검토 결과마다 승인 · 보류 · 제외 수와 기존 ID 수가 보입니다. 노드 · 관계 수를 app/features/build_record.md 「적재 수」 첫 줄에 적습니다. 「랩 DB 꺼짐」이 나오면 Docker Desktop이 켜져 있는지 보고 같은 명령을 다시 실행합니다. 결과는 output/result.html에 저장됩니다. 브라우저가 열리지 않으면 Windows 파일 탐색기로 이 실습 폴더의 output 폴더를 열고 result.html을 두 번 누릅니다(VS Code 탐색기에서 누르면 화면이 아니라 HTML 글이 열립니다). 이후에는 명령을 실행한 뒤 열린 화면에서 F5를 누릅니다.

02 Codex와 핀 세척 근거와 기존 ID 찾기

문서 속 대상은 모델의 ID와 다른 이름 · 번호로 적혀 있을 수 있어, 어느 기존 ID를 가리키는지 먼저 봅니다. Codex 확장 아이콘을 눌러 채팅을 열고 로그인합니다. 계정이 없거나 막히면 클래스룸에서 따로 받는 work-card-lab-completed.zip을 실행해 볼 수 있습니다.

파일을 바꾸지 말고, 승인 후보가 가리키는 대상(설비 · 구성 요소 · 부품 · SOP · 단계 · 규칙)이 설비 모델 · SOP 구조 · 조건표의 어느 ID인지 물어봅니다 핀 세척의 준비 · 금지 · 완료가 검토 결과와 data/reviews/selected_task.json의 어느 줄에 있는지, 다른 문서가 이 작업에 거는 조건이 있는지도 함께 묻습니다. 짚은 ID와 줄은 data/model/graph.json · data/sop.json · 원문에서 직접 엽니다.

후보 대상과 기존 ID의 짝 몇 개를 말할 수 있으면 이어 갑니다. 짚은 ID나 줄이 파일에 없으면 근거로 쓰지 않습니다.

03 기대 카드 먼저 적기

조회 결과를 본 뒤에 기대를 적으면 빠진 연결이 기대에 맞춰 사라집니다. app/features/expected.csv에 카드 항목(준비 조건 · 금지 · 제한 · 작업 순서 · 완료 기준 · 작업 직전 확인할 현재값 · 승인 · 추가 자료가 필요한 질문)마다 기대를 원문 · 검토 결과의 파일:줄로 적고, app/features/build_record.md에 목표 · 쓰는 사람 · 기대 칸을 쓴 시각을 적습니다. 절차 밖 절 · 다른 절차 · 다른 문서에 있는 작업 조건, 설비 별칭 · 제조사 품번으로 적힌 대상도 찾아 둡니다. 원문 글자가 깨져 보이면 VS Code 오른쪽 아래 UTF-8을 눌러 Reopen with Encoding → Korean (EUC-KR)으로 다시 엽니다.

파일을 손으로 고친 뒤에는 Ctrl+S로 저장합니다(탭 이름 옆 ●가 사라지면 저장됨). 저장하지 않으면 명령이 고치기 전 내용을 읽어 0행으로 보입니다.

Codex가 파일을 바꾸려 하면 편집 승인 창이 뜹니다. app/features/ 아래 요청한 파일이면 Allow once, 그 밖의 경로면 Deny를 누릅니다. 요청에 파일 이름을 쓸 때는 백틱()으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다. python run.py` 명령은 내 터미널에서 실행하고, 터미널 출력과 결과 화면으로 확인합니다.

08 다른 작업과 답할 수 있는 범위 확인하기

같은 방법이 다른 작업에도 통하고, 없는 것에 「결과 없음」을 돌려줘야 쓸 수 있는 기능입니다. 공급 조건은 설비 모델의 공급사(Supplier)와 공급 관계(SUPPLIES)에서 오고, 그날의 재고와 승인은 그래프 밖입니다.

결과를 보고 app/features/build_record.md 「다른 작업 · 제공되지 않은 것」과 「답할 수 있는 것과 없는 것」(그래프로 답함 · 현재값 필요 · 승인 필요 · 공급 정보 · 원문에 없음)에 근거와 함께 적습니다.

결과 화면의 다른 작업 카드와 「찾은 수 0」 조회가 data/action_review.json과 문서 목록의 어느 값에서 왔는지 짚어 줘. 내가 질문마다 분류를 정하면 build_record.md의 두 표에 그 행을 적어 줘. 다른 파일은 바꾸지 마.

두 번째 카드, 「찾은 수 0」 조회, 추가 자료가 필요한 질문 수가 보이고, 기록 두 표에 근거가 있습니다.

09 내보내고 저장해 다시 열기

내보내기는 지금 랩 DB의 그래프와 추가 자료가 필요한 질문을 한 파일로 남깁니다. 짚은 문제를 고친 뒤 아래 차례로 실행합니다: 내보내기 → 구조 검사 → 파일 → 모두 저장 → 폴더를 닫았다 다시 열기 → 랩 DB 다시 켜기 → 결과 다시 보기.

app/features/build_record.md 끝에 기준일 · 저장 시점 · 확인하지 못한 점을 적고 실습 폴더 전체를 USB나 개인 클라우드에 보관합니다.

구조 검사 출력이 가리키는 파일 · 노드 · 관계를 찾아 어느 정할 자리에서 생긴 문제인지 설명해 줘. 원자료와 검사 기준은 바꾸지 마. 내가 원인을 확인하면 필요한 부분만 고쳐 줘.

내보내기의 노드 · 관계 · 추가 자료가 필요한 질문 수가 랩 DB 수와 같고, 이어지는 구조 검사 출력이 보입니다.
