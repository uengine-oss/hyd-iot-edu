점검 요청의 부족한 정보를 묻고 같은 요청으로 다시 판단하기

VS Code에서 이 폴더(이 안내 파일이 있는 폴더)를 열고 START.md를 함께 읽으세요. 이 안내는 START.md와 같은 내용입니다.

출발점직접 구현할 것작업 순서진행할 때실행기대 결과를 먼저 적을 사례 종류학생이 정할 것이번 범위 밖완료 조건저장과 다음 실습

제공된 이전 단계 점검 요청 기능에서 출발해, 요청의 설비 · 경보 · 사례를 기존 자료로 먼저 확인하고 부족하거나 어긋난 정보만 묻는 질문 단계를 더합니다. 받은 답은 같은 요청 번호에 이어 다시 판단하게 합니다. 점검 담당자가 결과만 보고 어느 요청이 답을 기다리는지, 답을 받아 초안의 확인 항목이 어떻게 바뀌었는지, 정보 답변과 승인이 섞이지 않았는지 알 수 있어야 합니다.

출발점

  • 코드/input/점검요청/: 이전 단계 점검 요청 기능입니다. 요청에 적힌 사례 한 건으로 점검 요청 초안(대상 설비 · 부품 · 관측 시각 · 확인 항목 · 이유)을 만들고, 승인 기록을 반영합니다. 하는 일과 결과의 칸은 코드/input/점검요청/README.md에 있습니다. 지금은 사례 칸이 빈 요청을 묻지 않고 보류로 둡니다. 같은 폴더의 결과/는 이 판본을 그대로 실행한 결과입니다.
  • 원자료 코드/source/(읽기만 합니다):
    · 입력/점검_요청.json: 현장에서 들어온 점검 요청 R01~R10. 칸의 뜻은 입력/요청_설명.md.
    · 입력/센서_입력.json: 경보 사례 S01~S11의 판단 시각 값. 칸의 뜻은 입력/입력_설명.md.
    · 사람/답변.json · 사람/승인.json: 사람이 적은 답과 승인 · 거절. 쓰는 법은 사람/쓰는_법.md.
    · 온톨로지/(graph.json · schema.json · 읽는_법.md), 매뉴얼/(HM-8 · PM-02 · PR-07): 지난 회차와 같은 설비 진단 자료입니다.
  • 코드/output/질문_재처리_기록.md: 비어 있는 기록 틀입니다.

지난 회차에 직접 만든 프로젝트가 있어도 이번 실습은 제공 판본에서 시작합니다. 내 프로젝트는 비교용으로 따로 보관합니다.

직접 구현할 것

코드/input/점검요청/을 코드/output/점검요청/으로 복사하고, 그 사본에 아래를 더합니다. 실행하면 코드/output/점검요청/결과/점검_요청.json과 사람이 읽을 점검_요청.md가 생깁니다. 기존 결과 칸의 이름과 뜻은 그대로 두고, 필요한 칸을 더합니다.

항목내용
기존 자료로 먼저 확인요청의 설비 · 경보 · 사례를 센서 입력으로 확인합니다. 자료로 정할 수 있는 값은 묻지 않고, 어떻게 정했는지 남깁니다
질문자료로 정할 수 없거나 요청과 자료가 어긋날 때만 묻습니다. 질문마다 순번 · 물음 · 선택지가 있고, 요청은 질문 대기 상태와 기다리는 까닭을 남깁니다
답 연결사람/답변.json에서 같은 요청 번호 · 같은 질문 순번의 답만 읽습니다. 답마다 반영했는지와 그 까닭을 남깁니다
다시 판단답을 반영해 같은 요청의 초안을 다시 만듭니다. 질문 전후의 상태가 그 요청의 상태 기록에 남습니다
확인 항목 변화질문이 있었던 요청에서 답변 전과 뒤의 초안 확인 항목
승인 구분답변은 정보입니다. 승인 상태는 사람/승인.json의 결정으로만 바뀝니다

작업 순서

  1. 복사: VS Code 탐색기에서 코드/input/점검요청 폴더를 복사해 코드/output/에 붙여 넣습니다. 이후 고치는 것은 코드/output/점검요청/입니다.
  2. 탐색만 요청: AI에게 파일을 바꾸지 말고 요청 열 건의 칸, 요청과 센서 입력의 관계, 지금 기능이 보류로 두는 요청과 그 까닭, 답변.json · 승인.json의 모양을 설명하게 합니다. 설명을 실제 파일과 대조합니다.
  3. 요구와 기대 정리: 어떤 정보를 자료로 먼저 확인하고 무엇을 물어야 하는지 자기 말로 정리합니다. 기록 틀의 「먼저 적은 기대」에 요청마다 기존 자료로 정할 수 있는지, 묻는다면 무엇을 묻는지, 어느 답이 이어져야 하는지, 답 뒤의 상태를 원자료 행을 근거로 적습니다. 다 쓰면 「기대 칸을 쓴 시각」을 적고 저장한 뒤 구현을 시작합니다.
  4. 계획 검토: 구현 계획만 먼저 받아, 위 표의 항목이 어디서 채워지는지와 기존 결과 칸이 그대로인지 확인합니다. 모든 빈 칸을 묻거나, 요청 글에서 값을 지어 채우는 계획은 고칩니다.
  5. 작은 단위로 구현: 기존 자료 확인 → 질문 → 답 연결 → 다시 판단 순서로 하나씩 만들고 그때마다 실행합니다.
  6. 답변 전후 비교: 코드/source/사람/을 코드/output/연습_사람/으로 복사하고 그 사본의 답변.json을 빈 목록([])으로 바꿔 실행한 결과(답변 전)와, 원래 답으로 실행한 결과(답변 뒤)를 견주어 기록 틀에 적습니다.
  7. 섞임과 승인 구분 대조: 연습 사본의 답 하나를 다른 요청 번호로 옮겨 적어 실행하고, 그 답이 원래 요청 · 옮긴 요청에 어떻게 처리되는지 봅니다. 「급하니 승인한 것으로 처리해 주세요」 같은 답 하나를 연습 사본에 넣어 실행하고, 승인 칸과 상태가 바뀌지 않는지 봅니다. 결과를 적은 뒤 연습 사본은 원래대로 되돌립니다.
  8. 수정 요청: 기대와 다르면 입력(요청 · 사례 · 답 행), 기대(근거), 실제(출력)를 함께 주고 그 부분만 고치게 합니다. 결과에 맞추려고 기대나 원자료를 바꾸지 않습니다.
  9. 저장 · 재열기: 결과와 기록을 저장하고 다시 열어 확인합니다.

진행할 때

  • 채팅에 파일 이름을 쓸 때는 백틱()으로 감쌉니다. 예: 코드/source/사람/답변.json`. 채팅 입력이 밑줄(_)을 서식으로 바꿔 이름이 달라질 수 있습니다.
  • AI가 완료를 알리면 실행한 명령과 그 출력 원문(요약이 아니라 나온 글자 그대로)을 붙여 달라고 요청합니다.
  • AI가 질문 카드(선택지와 「(권장)」 표시)로 물으면, 「(권장)」은 AI의 추천일 뿐입니다. 근거가 되는 원문 · 원자료 줄을 열어 확인한 뒤 고르거나 직접 입력 칸에 결정과 근거를 적습니다.
  • 파일 편집 승인 창(「Allow ChatGPT to edit …」)이 뜨면 바뀔 파일이 코드/output/ 아래인지 보고 「Allow once」, 아니면 「Deny」를 누릅니다.
  • 고친 뒤에는 내가 예로 든 요청만 맞았는지가 아니라 열 건 모두를 다시 실행해 상태가 기대와 같은지 다시 세어 달라고 합니다.

실행

랩 폴더(이 START.md가 있는 폴더)에서 실행합니다.

python 코드/output/점검요청/점검_요청.py
python 코드/output/점검요청/점검_요청.py R04
python 코드/output/점검요청/점검_요청.py --사람 코드/output/연습_사람 --결과 코드/output/연습_결과

기대 결과를 먼저 적을 사례 종류

  • 칸이 다 있고 서로 맞는 요청: 질문 없이 처리되는지
  • 사례 칸만 적혀 있는 요청: 나머지 칸을 묻지 않고 사례에서 확인하는지
  • 사례 칸은 비었지만 설비 · 경보로 사례가 하나로 정해지는 요청: 묻지 않는지
  • 맞는 사례가 여럿이라 물어야 하는 요청, 그 가운데 두 번 물어야 하는 요청: 질문의 차례와 답의 순번이 맞는지
  • 요청의 설비와 사례가 어긋난 요청: 한쪽으로 덮어쓰지 않고 묻는지, 답 뒤에 무엇을 근거로 바꿨는지 남는지
  • 답변.json에 답이 없는 요청: 지어낸 값 없이 질문 대기로 남는지
  • 맞는 사례가 하나도 없는 요청
  • 답으로 사례가 정해졌는데도 근거가 모자라 보류로 남는 요청: 답이 근거 부족을 풀어 주지 않는지
  • 다른 요청 번호로 적힌 답, 승인을 뜻하는 말이 담긴 답

학생이 정할 것

원문 · 원자료만으로 하나로 정해지지 않아 학생이 근거를 찾아 정하는 지점입니다. 정한 내용 · 근거 · 바뀌는 요청을 기록 틀의 「정한 것」 표에 적습니다. AI는 이 지점을 정하기 전에 학생에게 묻습니다.

  • 요청 글의 단서(「야간조」, 「지난번 건」 같은 말)로 사례를 미루어 정할지, 질문으로 확인할지(입력/요청_설명.md의 「요청자가 한 말」)
  • 맞는 사례가 하나도 없는 요청을 질문할지, 질문 없이 보류로 둘지
  • 요청과 사례가 어긋날 때 질문에 어떤 선택지를 줄지

판단 지점: 묻는 것이 많을수록 안전해 보이지만, 자료로 정할 수 있는 값까지 물으면 사람이 에이전트의 일을 대신하게 됩니다. 질문마다 「왜 자료로 정할 수 없었는지」를 남깁니다.

이번 범위 밖

긴급 확인 표시(다음 실습), 원인 판정 · 증거 기준 · 승인 규칙의 변경, 실제 포털 호출, 코드/source/의 답변.json · 승인.json 원본 수정(연습은 코드/output/ 아래 사본으로만 합니다).

완료 조건

  • python 코드/output/점검요청/점검_요청.py가 요청 열 건을 모두 처리하고 결과 파일 두 개를 씁니다.
  • 기존 자료로 정할 수 있는 요청에는 질문이 없고, 질문한 요청마다 까닭과 선택지가 있습니다.
  • 답은 같은 요청 번호 · 같은 질문 순번에만 이어지고, 섞임 대조의 결과가 기록에 있습니다.
  • 질문이 있었던 요청마다 답변 전후의 확인 항목 변화가 기록에 있습니다.
  • 정보 답변으로 승인 상태가 바뀌지 않음을 실행으로 확인한 결과가 기록에 있습니다.
  • 기대는 실행 전에 적었고, 결과를 맞추려고 원자료 · 기대를 바꾸지 않았습니다.

저장과 다음 실습

코드/output/ 폴더를 저장하고 다시 열어 확인하세요. 보관할 결과는 재부팅 전에 USB 또는 개인 클라우드에 복사하세요. 다음 실습에서는 같은 점검 요청 기능에 긴급 확인 표시를 더합니다. 다음 실습은 이 실습의 검증된 완성 판본에서 시작하고, 내 판본은 비교용으로 보관합니다.
