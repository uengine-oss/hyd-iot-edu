직접 정한 기대 결과로 점검 요청 기능 검증하기

VS Code에서 이 폴더(이 안내 파일이 있는 폴더)를 열고 START.md를 함께 읽으세요. 이 안내는 START.md와 같은 내용입니다.

출발점직접 구현할 것작업 순서진행할 때실행기대 결과를 먼저 적을 사례 종류학생이 정할 것이번 범위 밖완료 조건저장과 다음 실습

긴급 확인 표시까지 더한 점검 요청 기능을, 실행하기 전에 명세와 원자료에서 정한 기대 결과로 검증합니다. 일반 · 긴급 · 경계값 · 정보 누락 · 거절 · 도구 오류 사례를 시나리오로 적고, 제공된 테스트 골격에 판정 코드를 구현해 긴급 표시 · 근거 · 미확인 · 기존 출력 계약을 함께 검사합니다. 실제 오류가 나오면 원인을 고치고 기존 사례까지 다시 실행한 뒤, 검증한 기능을 새로 들어온 요청 묶음에 적용합니다. 다음 담당자가 이 기록만으로 무엇을 어떤 기준으로 확인했고 무엇이 아직 확인되지 않았는지 알 수 있어야 합니다.

출발점

  • 코드/input/점검요청/: 앞 실습(명세에 따른 요구사항 추가)의 완성 판본입니다. 하는 일과 결과의 칸은 코드/input/점검요청/README.md에 있습니다. 같은 폴더의 결과/는 이 판본을 그대로 실행한 결과입니다.
  • 코드/input/spec.md: 앞 실습에서 확정한 명세입니다. 기대 결과의 근거로 씁니다.
  • 원자료 코드/source/(읽기만 합니다): 입력/(요청 R01~R10 · 사례 S01~S11), 사람/(답변 · 승인), 온톨로지/, 매뉴얼/.
  • 코드/source/새_대상/: 이번 주에 새로 들어온 요청 R11~R16과 사례 S12~S17, 그 답변 · 승인(교육용 가상 자료). 설명은 코드/source/새_대상/README.md.
  • 코드/output/tests/test_점검요청.py: 테스트 골격입니다. 입력을 만드는 도우미(원자료_요청, 쿨러_경보_요청, 도구_오류_자료, 변경_전_결과, 시험_자료)와 사례 종류별 빈 시험이 있고, 판정 코드는 비어 있어 지금 실행하면 시험마다 「미구현」으로 실패합니다.
  • 코드/output/scenarios.md(사례 | Given | When | Then | 명세 근거), 코드/output/검증_기록.md: 비어 있는 기록 틀입니다.

직접 구현할 것

항목내용
시나리오scenarios.md에 사례 종류마다 Given · When · Then과 명세 근거. 실행하기 전에 적습니다
판정 코드테스트 골격의 빈 시험마다 Then을 단언(assert)으로 옮깁니다. 처리한다(요청, 자료)가 돌려준 결과의 상태 · 보류_사유 · 긴급 표시 · 근거 · 승인 · 후속 업무 같은 계약 칸을 검사합니다
수정과 회귀실패하면 원인을 가려 코드/output/점검요청/(또는 명세 · 시험)을 고치고, 시험 전체를 다시 실행합니다
새 대상 적용검증한 판본을 코드/source/새_대상/에 실행하고, 그 결과를 시나리오의 기대와 대조합니다
기록실행 명령 · 실패 · 원인 · 재실행 · 새 대상 결과 · 다시 쓸 명세와 검증 기록

작업 순서

  1. 복사: VS Code 탐색기에서 코드/input/점검요청 폴더를 복사해 코드/output/에 붙여 넣습니다. 시험은 이 사본을 검사합니다.
  2. 골격 실행: 아래 「실행」의 첫 명령으로 골격을 그대로 실행해, 시험마다 「미구현」으로 실패하는 것을 확인합니다.
  3. 탐색만 요청: AI에게 파일을 바꾸지 말고 명세의 수용 기준, 결과의 계약 칸, 골격의 도우미가 만드는 입력을 설명하게 합니다. 설명을 실제 파일과 대조합니다.
  4. 기대 먼저: scenarios.md에 아래 사례 종류마다 Given(입력 · 자료 · 권한과 상태) · When(처리한다) · Then(결과의 칸과 값, 후속 업무가 있는지)을 적고 「명세 근거」에 spec.md의 줄이나 원자료 행을 적습니다. 경계값은 기준 바로 아래 · 같은 값 · 바로 위를 따로 적습니다. 다 쓰면 「기대 칸을 쓴 시각」을 적고 저장합니다. 구현을 실행해 나온 값을 기대로 옮겨 적지 않습니다.
  5. 판정 코드 구현: 시나리오 한 줄씩 골격의 시험에 단언으로 옮기고 그때마다 실행합니다. null은 is None으로 따로 검사합니다. 계획이나 코드에서 문장 전체를 글자로 맞추는 단언이 보이면, 계약 칸을 보는 단언인지 다시 봅니다.
  6. 실패 가리기: 실패마다 입력 연결 → 조회 값 → 판단 규칙 → 출력 생성 순서로 기록을 대조해 원인을 가립니다. 구현이 틀렸으면 구현을, 명세가 빠뜨렸으면 코드/input/spec.md를 코드/output/spec.md로 복사해 고치고, 시험이 틀렸으면 시험을 고칩니다. 기대를 낮춰 통과시키지 않습니다. 실패가 없으면 일부러 실패를 만들지 않고 확인한 조건과 범위를 적습니다.
  7. 회귀: 고친 뒤에는 고친 시험만이 아니라 시험 전체를 다시 실행합니다.
  8. 표현 차이와 계약 위반: 실습 3에서 직접 만든 판본이 있으면 같은 시험을 그 판본에도 실행해 보고(아래 「실행」의 마지막 명령), 실패를 문장 · 순서 같은 표현 차이와 계약 위반으로 나눠 기록합니다.
  9. 새 대상 적용: 검증한 판본을 새 대상 묶음에 실행해 결과를 코드/output/새_대상_결과/에 쓰고, 시나리오의 「새 대상」 줄과 대조합니다.
  10. 저장: 다시 쓸 명세(고쳤다면 코드/output/spec.md)와 시나리오 · 시험 코드 · 검증 기록을 저장하고 다시 열어 확인합니다.

진행할 때

  • 채팅에 파일 이름을 쓸 때는 백틱()으로 감쌉니다. 예: 코드/output/tests/test_점검요청.py`. 채팅 입력이 밑줄(_)을 서식으로 바꿔 이름이 달라질 수 있습니다.
  • AI가 완료를 알리면 실행한 명령과 그 출력 원문(요약이 아니라 나온 글자 그대로)과 바뀐 파일 목록을 붙여 달라고 요청합니다. 「통과했다」는 말만으로 완료로 보지 않습니다.
  • AI가 질문 카드(선택지와 「(권장)」 표시)로 물으면, 「(권장)」은 AI의 추천일 뿐입니다. 근거가 되는 명세 · 원자료 줄을 열어 확인한 뒤 고르거나 직접 입력 칸에 결정과 근거를 적습니다.
  • 파일 편집 승인 창(「Allow ChatGPT to edit …」)이 뜨면 바뀔 파일이 코드/output/ 아래인지 보고 「Allow once」, 아니면 「Deny」를 누릅니다.
  • 시험이 실패했을 때 AI가 기대값이나 단언을 바꾸자고 하면, 그 기대가 명세의 어느 줄에서 왔는지 먼저 다시 봅니다.

실행

랩 폴더(이 START.md가 있는 폴더)에서 실행합니다. pytest가 없어도 됩니다.

python 코드/output/tests/test_점검요청.py
python -m unittest discover -s 코드/output/tests -v
python 코드/output/점검요청/점검_요청.py
python 코드/output/점검요청/점검_요청.py --입력 코드/source/새_대상 --사람 코드/source/새_대상 --결과 코드/output/새_대상_결과

내가 실습 3에서 만든 판본을 같은 시험으로 검사할 때(PowerShell):

$env:CHECK_PROJECT = "내 판본의 점검요청 폴더 경로"; python 코드/output/tests/test_점검요청.py; Remove-Item Env:CHECK_PROJECT

기대 결과를 먼저 적을 사례 종류

  • 일반: 쿨러 경보가 아닌 요청이 기존 결과 그대로인지
  • 긴급: 유효한 판정 값이 기준 이상인 쿨러 경보 요청
  • 경계값: 기준 바로 아래 · 같은 값 · 바로 위
  • 정보 누락: 사례를 정할 수 없는 요청, 판정 값 누락 · 신선도 실패 · 표본 부족, 승인을 뜻하는 말이 담긴 답
  • 거절: 사유가 있는 거절과 사유가 없는 거절에서 후속 업무가 있는지
  • 도구 오류: 센서 조회가 실패했을 때 그 요청의 결과와 다른 요청의 처리
  • 회귀: 고친 뒤 원자료 요청 R01~R10이 변경 전 결과와 계약 칸에서 같은지
  • 새 대상: 새 대상 묶음의 요청마다 상태와 긴급 표시

학생이 정할 것

명세 · 원자료만으로 하나로 정해지지 않아 학생이 근거를 찾아 정하는 지점입니다. 정한 내용 · 근거 · 바뀌는 시험을 검증_기록.md의 「정한 것」 표에 적습니다. AI는 이 지점을 정하기 전에 학생에게 묻습니다.

  • 도구 오류가 났을 때 기대할 행동: 그 요청만 멈추고 다른 요청은 계속 처리할지, 실행 전체를 멈출지. 명세에 없으면 명세에 무엇을 더할지
  • 어느 칸을 계약으로 정확히 단언하고, 어느 칸(이유 문장 · 물음 문장 등)을 표현 차이로 허용할지
  • 경계값 시험에 쓸 바로 아래 · 바로 위의 값

판단 지점: 시험이 통과했다는 것은 내가 적은 기대와 같다는 뜻일 뿐입니다. 기대를 구현의 출력에서 베끼면 틀린 구현도 통과합니다. 기대가 명세의 어느 줄에서 왔는지가 비어 있는 줄은 아직 검증이 아닙니다.

이번 범위 밖

새 기능 추가(긴급 조건 · 질문 · 승인 규칙 변경), 처리 순서 바꾸기, 실제 포털 · 설비 호출과 그 권한 검증, 코드/source/ · 코드/input/ 원본 수정.

완료 조건

  • scenarios.md의 사례 종류마다 실행 전에 적은 Given · When · Then과 명세 근거가 있습니다.
  • 테스트 골격의 시험마다 판정 코드가 있고, 「미구현」으로 실패하는 시험이 없습니다.
  • 실패가 있었다면 원인 · 고친 곳 · 분류가 기록에 있고, 고친 뒤 시험 전체를 다시 실행한 결과가 있습니다.
  • 새 대상 묶음에 적용한 결과가 코드/output/새_대상_결과/에 있고 시나리오의 기대와 대조돼 있습니다.
  • 다시 쓸 명세와 검증 기록이 저장돼 있고, 로컬 시험이 확인하지 못한 범위(실제 포털 권한 · 외부 연동)가 미확인으로 남아 있습니다.

저장과 다음 실습

코드/output/ 폴더를 저장하고 다시 열어 확인하세요. 보관할 결과는 재부팅 전에 USB 또는 개인 클라우드에 복사하세요. 이 실습으로 점검 요청 기능의 사람의 결정 · 질문 · 명세 · 검증이 한 프로젝트에 쌓였습니다. 이어지는 정리에서 이 기록을 바탕으로 전체 흐름을 되짚습니다.
