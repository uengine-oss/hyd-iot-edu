# 작업 기준의 복합 조건과 예외를 조치 조건표로 표현하기

## 목표

포털 판단 규칙 화면에서 허용 · 제외된 후보를 SOP의 금지 조건과 대조했습니다. 이번에는 그 근거를 제공 SOP(HM-8 매뉴얼)에서 직접 뽑아 조치 조건표로 만들고, 판단 시스템에 등록된 결정표와 행마다 출처를 견줍니다. 사건은 포털에서 본 경보와 같은 종류의 다른 경보 한 건, 10월 27일 01:59(한국 시각) HYD-02 쿨러 성능 저하 경보 `ALT-hyd02-0172-54a5`입니다(경보 ID로 자료 · 결과 화면에서 찾습니다).

조건표는 어떤 입력이 어떤 값일 때 조치를 경고 · 감점 · 제외하는지를 한 행씩 적은 판단 규칙이고, DMN(판단을 표준 모양으로 적는 방식)의 결정표 — 입력 조건과 판단 결과를 한 행씩 적은 표 — 를 이 실습에서 부르는 이름입니다. 무엇을 규칙으로 옮기고 근거 없는 옛 규칙을 어떻게 둘지는 내가 정하고, 조건표를 사례에 대는 일은 제공 코드가 합니다.

줄기(온톨로지 → 에이전트 → 프로세스)에서 이 실습은 첫 단계 온톨로지의 판단 지식 — 작업 기준의 조건을 판단 규칙으로 옮기는 일 — 를 맡습니다.

만들 것: `결과/조건표.csv` · `결과/승인.csv` · `결과/정한_것.csv` · `결과/기대_판정.csv` · `결과/판단기록.md`(내가 AI와 채움). 사례 판정과 남은 후보 표는 결과 화면에 보입니다.

## 출발점

- `자료/HM-8_매뉴얼.md` — 제공 SOP: 현행 HM-8 1.1판(2026-09-01 시행) 냉각 계통 조치 원문. `자료/HI-01_보충매뉴얼.md` — 점검 · 이상 확인 보충 기준. `자료/작업기준.md` — 회사 작업 기준.
- `자료/판단시스템_결정표_내보내기.txt` — 판단 시스템에 등록된 결정표 · 스킬을 내보낸 것(2025년 도입 판, 2026-10-27 내보냄).
- `자료/targets.csv` — 이번 경보에서 검토하는 조치 후보 넷. `자료/사건_기록_HYD-02_1027.md` — 야간 운전원이 HMI에서 옮겨 적은 사건 메모. `자료/확인_사례.csv` — 지난 30일 경보 가운데 고른 확인 사례의 판단 입력.
- `입출력_계약.md` — 조건표 · 승인 표의 형식. `check.py` — 구조 검사. `condition_tools.py` — 제공 코드(고치지 않습니다).
- `show_result.py` · `lab_steps.py` — 결과 화면(`python show_result.py`가 채운 단계까지 제공 흐름을 돌려 `결과/보기.html`을 다시 씀). 고치지 않습니다.
- `결과/` — 정할 자리(「제공 빈 틀」)와 README.
- `AGENTS.md` · `.github/copilot-instructions.md` · `CLAUDE.md` — Codex와 GitHub Copilot이 지키는 작업 규칙(세 파일이 같은 내용). 학생도 함께 읽습니다.

## 해결할 질문

이 답은 야간 운전원이 경보가 났을 때 어느 조치가 남고 어느 조치가 빠지는지, 남은 조치를 누가 승인하는지 볼 때 씁니다.

1. 네 조치의 경고 · 감점 · 제외 조건(입력 · 단위 · 연산자 · 경계 · 결과 · 출처)은 무엇인가?
2. 사건과 확인 사례에서 각 후보는 남는가, 빠지는가, 무엇이 아직 모르는 값인가?
3. 남은 후보와 실행 승인은 어떻게 다른가 — 남은 후보마다 누가 승인하는가?

## 학생이 정할 것

원자료만으로 하나로 정해지지 않아 내가 근거를 찾아 정할 지점입니다. 해당하는 행 · 절은 직접 찾고, 지점마다 고른 것 · 근거(파일:줄) · 바뀌는 답을 `결과/정한_것.csv`에 한 줄씩 적습니다.

- **출처가 확인되지 않는 기준** — 판단 시스템 결정표에 있는데 제공 SOP에서 근거 문장을 찾을 수 없는 규칙을 조건표에 어떻게 둘지 — 그런 규칙이 여럿이면 규칙마다 정하고 근거를 적습니다
- **승인 역할** — 원문의 승인 줄이 하나로 읽히지 않는 후보의 승인을 무엇으로 적을지

AI에게 이 지점을 정하게 하지 않습니다. AI가 고르거나 「권장」을 붙여도 따르지 말고 원문 줄을 열어 내 선택과 근거를 말하며, 못 정하면 미결로 둡니다.

## 이번 범위 밖

- 원천 기록에서 판단 입력을 만드는 일과, 후보를 견주고 검토 결과로 내는 기능(다음 실습)
- SOP 구조(적용 · 금지 · 단계 · 완료 · 승인 전체)를 만드는 일
- 실제 설비 · 포털 · 업무 시스템을 부르는 일

자료에 있어도 이번 결과에 만들지 않습니다.

## 결과 형식

파일의 모양은 `입출력_계약.md`에 있습니다. 어떤 조건을 몇 행으로 옮길지는 원문을 읽고 직접 정합니다.

- 정할 자리(「제공 빈 틀」): `결과/조건표.csv`, `결과/승인.csv`, `결과/정한_것.csv`, `결과/기대_판정.csv`, `결과/판단기록.md`.
- 사례에 대는 일 · 원문 인용 · 남은 후보 표는 제공 코드가 결과 화면에 보입니다(`python show_result.py`).

## 지킬 조건

- 조건표의 행마다 원문 출처를 답니다.
- 남은 후보를 실행 승인처럼 적지 않습니다.
- 제공 코드(`show_result.py` · `lab_steps.py` · `condition_tools.py` · `check.py`)는 고치지 않습니다.

## 진행 단계

한 번에 한 단계씩 갑니다. 단계마다 결과를 확인한 뒤 다음 단계로 갑니다. 단계마다 정하거나 물을 것, 요청에 담을 것, 판단할 증거는 가이드(「실습 시작」 도구가 이 폴더 옆에 내려 둔 파일, 노션 「가이드문서」)의 같은 번호에 있습니다.

1. **폴더와 출발점 확인 · 결과 화면 열기** — VS Code 탐색기에서 `자료/` · `결과/` · START.md를 열어 각 자리의 역할과 이번 질문을 확인하고, 터미널에서 `python show_result.py`를 실행해 결과 화면을 엽니다.
2. **파일을 바꾸지 않고 자료 파악** — AI에게 파일을 바꾸지 말고, 원문의 조건 문장 · 판단 시스템 결정표의 행 · 사건 기록 · 확인 사례가 각각 무엇을 담고 있는지 파일:줄로 짚어 달라고 합니다. 짚은 줄을 직접 열고 결과 화면 2단계 표와 견줍니다.
3. **요구와 기대 판정 정하기** — `결과/판단기록.md`에 목표 · 쓰는 사람 · 지킬 조건을 적고, 사건과 확인 사례 두세 개의 네 후보가 유지 · 제외 · 보류 가운데 무엇이 될지 원문에서 먼저 찾아 `결과/기대_판정.csv`에 근거 줄과 함께 적습니다. 다 적으면 AI에게 파일을 바꾸지 말고 되짚게만 합니다.
4. **계획 검토** — 조건표에 넣을 규칙과 옮길 순서, 승인 표를 채울 때를 AI의 계획으로 받아 검토하고 동의합니다. 아직 파일을 만들지 않습니다.
5. **조건표 규칙 — 복합 조건과 경계** — 원문의 경고 · 감점 · 제외 조건을 `결과/조건표.csv`에 계약 모양으로 한 묶음씩 옮기며 결과 화면에서 출처의 원문과 사건 · 확인 사례의 판정을 3단계 기대와 견줍니다. 실행은 내가 터미널에서 하고, AI가 답에 옮겨 적은 출력이 아니라 터미널에 나온 출력과 결과 화면으로 확인합니다 — 옮겨 적은 글은 실제 출력과 다를 수 있습니다.
6. **출처가 확인되지 않는 규칙** — 판단 시스템 결정표에 있는데 제공 SOP에서 근거 문장을 찾을 수 없는 규칙마다 조건표에 어떻게 둘지 정해 `결과/조건표.csv`에 반영하고, 규칙마다 `결과/정한_것.csv`에 한 줄씩 적습니다. 결과 화면에서 사례 판정이 직전 실행과 어떻게 바뀌었는지 봅니다.
7. **남은 후보와 실행 승인** — 후보마다 실행을 누가 승인하는지와 그 원문 승인 줄을 `결과/승인.csv`에 적습니다. 원문의 승인 줄이 하나로 읽히지 않는 후보는 고른 것 · 근거를 `결과/정한_것.csv`에 적습니다. 결과 화면의 「남은 후보와 실행 승인」 표를 봅니다.
8. **검사 · 저장하고 다시 열기** — 터미널에서 구조 검사를 실행해 짚은 문제를 고치고, 결과 파일을 모두 저장한 뒤 VS Code에서 폴더를 닫았다 다시 열어 `python show_result.py`와 구조 검사를 다시 실행합니다. `결과/판단기록.md` 끝에 기준일 · 저장 시점 · 확인하지 못한 점을 적습니다.

이 순서는 바이브 코딩 일곱 단계 — 파일을 바꾸지 않고 파악 → 요구와 기대 답을 내 말로 → 계획 검토 → 작게 구현 → 원자료와 대조 → 고침 → 저장하고 다시 열기 — 를 따릅니다.

요청에 파일 이름을 쓸 때는 `결과/조건표.csv`처럼 백틱(`)으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다.

## 확인

확인할 사례의 종류(어느 행이 해당하는지는 원자료에서 직접 찾습니다):

- 조건표의 숫자 기준값마다 그 값과 같거나 가장 가까운 값, 그 값의 바로 위 · 아래에서 가장 가까운 값(경계 — 같은 값이 없으면 없다고 적고 가장 가까운 사례로 경계를 본다)
- 경고 · 감점 · 제외가 한 후보에 함께 맞는 경우(복수 사유)
- 입력이 빠졌는데 이미 확인된 제외 사유가 있는 경우
- 값이 비어 있어도 그 후보에는 해당 규칙이 걸리지 않는 경우(적용 대상 밖)
- 「정할 것」의 결정에 따라 결과가 바뀌는 사례
- 사건 한 건
- 같은 명령을 다시 실행한 결과

실행 명령:

```
python show_result.py
python check.py
```

바뀐 파일 확인: AI가 단계를 마칠 때마다 바뀐 파일 목록을 봅니다. `자료/` · 제공 코드가 바뀌지 않았는지, 요청하지 않은 파일이 생기지 않았는지 확인합니다. 편집 승인 창에서는 경로가 `결과/` 아래일 때만 허용합니다.

## 완료 판정

형식 검사 통과만으로 완료하지 않습니다. 조건표의 행마다 원문 문장으로 돌아갈 수 있고, 원문에서 먼저 적은 기대 판정과 조건표를 댄 판정이 맞고, 「정한 것」의 근거와 그 선택으로 바뀌는 사례를 설명할 수 있으며, 남은 후보와 실행 승인을 따로 말할 수 있으면 완료입니다.
