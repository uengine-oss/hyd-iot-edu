설비 · 부품 · 공급 모델을 이 폴더 전용 그래프 DB에 적재하고 부품의 사용 설비와 공급 조건을 돌려주는 조회문을 원자료와 대조합니다. 단계마다 「요청에 담을 것」 다섯 칸을 내 말로 채워 AI에게 요청하고(그대로 보내는 글이 아니며, 값은 원자료에서 찾습니다), 「증거」를 확인한 뒤 다음 단계로 갑니다. 막히면 「정답 보기」를 펼칩니다.

01 폴더와 출발점 · 랩 DB 켜기

「설비·부품·공급 정보를 연결하는 온톨로지 설계하기」에서는 부품마다 쓰는 설비와 공급사별 조건을 모델에 넣었습니다. 이번에는 제공된 설비 · 부품 · 공급 모델(또는 내 모델)을 이 폴더 전용 랩 DB(그래프 DB)에 적재하고, 질문마다 조회문을 만들어 원자료와 대조합니다. 파일 읽기 · 실행 · 개수 세기 · 전후 비교는 제공 코드가 하고, 나는 같은 대상을 알아보는 열쇠와 조회가 돌려줄 것을 정해 문장으로 씁니다.

줄기(온톨로지 → 에이전트 → 프로세스)에서 이 실습은 첫 단계 온톨로지의 구현과 검증를 맡습니다.

받기 · 도구 「실습 시작」 도구에서 이 실습을 고릅니다. 폴더 신뢰 · 탐색기 · 터미널 · 결과 화면 · AI 채팅 · 편집 승인 창은 「설비·부품·공급 정보를 연결하는 온톨로지 설계하기」 가이드와 같습니다. 명령은 직접 치지 말고 블록의 복사로 붙여 넣습니다. 필요한 것 VS Code와 Python, 로그인해 둔 Codex 또는 GitHub Copilot, 랩 DB를 켤 Docker Desktop.

해결할 질문 아래 질문의 답은 보전 · 구매 담당이 예비품을 쓰는 설비와 공급사별 조건을 함께 볼 때 씁니다. 고르는 것은 구매 담당입니다.

  1. 세 설비가 함께 쓰는 펌프 축 씰 키트를 어느 설비 · 구성 요소에서 쓰고, 기준일의 세 공급 조건(승인 여부 · 단가 · 불량률 · 납기)은 무엇이며 각 값은 어느 파일 · 어느 줄에서 왔는가?
  2. 이름이 비슷한 다른 품번, 예전 품번이나 다른 표기, 원자료에 없는 품번으로 물으면 결과가 서로 구별되는가? 비승인 공급사는 승인 상태와 함께 구별되는가?
  3. 같은 적재를 다시 실행해도 대상과 관계가 늘지 않는가?

말 풀이 적재는 모델 파일의 대상과 관계를 그래프 DB에 넣는 일, 정할 자리는 결과/에서 첫 줄에 「제공 빈 틀」이 있는 파일입니다.

내 모델은 고를 때만 결과/내_모델/에 복사해 씁니다(형식 · ID가 맞는지 먼저 보고, 다르면 내 정의로 조회). 없어도 제공 모델로 끝까지 합니다.

정할 것 주소가 127.0.0.1의 이 폴더 전용인지 보고, 내 모델과 제공 모델 가운데 무엇을 쓸지 정합니다.

증거 「랩 DB 준비 완료」가 나오고, 1단계 칸에 모델 파일 개수와 랩 DB 개수(처음 0)가 나란히 보입니다.
다를 때 「랩 DB 꺼짐」이면 python lab_db.py를 다시 실행합니다(이전 작업이면 전에 넣은 개수가 맞음).

02 파일을 바꾸지 않고 자료 파악

왜 적재가 맞았는지는 모델 파일에 무엇이 몇 개 있는지 먼저 알아야 셀 수 있습니다.

할 일 AI에게 파일을 바꾸지 말고 입력/graph.json의 종류별 대상 · 관계 수와 펌프 축 씰 키트에 닿는 관계와 그 값의 원자료 줄을 파일 · 줄로 짚게 하고, 그 줄을 직접 엽니다.

AI가 Docker · 랩 DB 명령을 실행하려 하면 폴더 밖 실행 승인 창이 뜹니다. Deny를 누르고 그 명령을 내 터미널에서 실행합니다.

정할 것 제공 모델의 ID와 공급 조건 관계에 붙은 속성(값과 출처)을 묻습니다.

요청에 담을 것

목적적재할 모델을 파악한다
입력입력/schema.json · graph.json · 자료_검토.md, 입력/자료/
지킬 것파일을 바꾸지 않는다. 파일 · 줄과 개수를 먼저.
결과의 꼴종류별 개수 표, 관계와 값의 원자료 줄 목록
확인 방법개수를 1단계 표와 견주고 출처 줄 몇 개를 연다

명령 없음

증거 짚은 줄을 열면 그 내용이 있고, AI가 바꾼 파일이 없습니다. 펌프 축 씰 키트에 닿는 관계를 내 말로 댈 수 있습니다.
다를 때 짚은 줄이 없거나 다르면 근거로 쓰지 않고 다시 찾게 합니다. 편집 승인 창이 뜨면 Deny를 누릅니다.

03 요구와 기대 답 정하기

왜 기대 답을 원자료에서 먼저 적어야 결과를 견줄 기준이 생깁니다. AI의 답을 옮기면 틀린 결과도 맞아 보입니다.

할 일 결과/검증_기록.md에 질문 · 쓰는 사람 · 지킬 조건을, 결과/기대_답.csv에 질문마다 물을 값 · 볼 열 · 원자료에서 찾은 기대 답(펌프 축 씰 키트의 사용 설비와 세 공급 조건, 다른 표기 · 없는 품번)을 적고, 결정 지점을 결과/정한_것.csv에 적습니다. 다 적으면 AI에게 파일을 바꾸지 말고 되짚게만 합니다.

고친 파일은 Ctrl+S로 저장합니다(탭 이름 옆 ●가 사라지면 저장됨).

학생이 정할 것 — 지점의 종류 원자료만으로 하나로 정해지지 않아 내가 근거를 찾아 정할 지점입니다. 해당하는 행 · 절은 직접 찾고, 지점마다 고른 것 · 근거(파일:줄) · 바뀌는 답을 결과/정한_것.csv에 한 줄씩 적습니다.

  • 쓰는 사람에 따라 갈리는 답 — 구매 담당이 공급사를 비교할 때 승인 여부 · 단가 · 불량률 · 납기 말고도 함께 봐야 할 것이 모델에 있으면, 그것을 조회 결과에 함께 돌려줄지와 어떻게 보일지

질문 카드의 「(권장)」은 AI의 추천일 뿐이니, 직접 입력 칸에 내 결정과 근거 줄을 적어 보냅니다.

정할 것 지점마다 내 선택과 근거를 정합니다. AI의 「권장」은 따르지 않고 원문 줄로 정하며, 못 정하면 미결로 적습니다.

목적질문의 기대 답을 원자료에서 먼저 찾아 적는다(결과 화면이 이 표와 실제 답을 견준다)
입력자료/ 원문 줄, START.md 질문, 2단계 근거 줄

04 판단① 적재문 쓰기

왜 스키마의 종류(이론의 클래스) 이름은 그래프의 레이블이 되고, 대상 하나(이론의 인스턴스)를 저장한 것이 노드입니다. ID는 노드의 속성, 관계 정의의 시작 · 끝은 관계의 방향이 됩니다. CREATE는 실행할 때마다 새로 만들고, MERGE는 같은 것이 있으면 찾고 없으면 만듭니다. 그래서 다시 실행해도 늘지 않으려면 무엇으로 「같은 것」을 알아볼지 먼저 정해야 합니다. 다시 넣을 때 값을 덮어쓰면 수정본으로 고친 값이 되돌아가고, 처음 만들 때만 넣으면 그대로 남습니다.

할 일 결과/load.cypher에 종류 · 관계마다 문장 하나(위에 // 넣을 것: <종류 또는 관계>, 행은 $rows)를 AI와 쓰고 python show_result.py를 실행합니다. 행을 넘겨 실행하고 개수를 세는 것은 제공 코드가 합니다. 같은 적재를 한 번 더 해 늘지 않는지도 봅니다.

정할 것 같은 대상을 무엇으로 알아볼지(MERGE의 열쇠)를 정합니다. ID와 관계의 시작 · 끝이 그래프의 무엇이 되는지도 내 말로 설명합니다.

요청에 담을 것

목적모델의 대상과 관계를 랩 DB에 옮기는 적재 문장을 종류 · 관계마다 쓴다
입력입력/schema.json(종류 · 관계 · 방향), 결과/load.cypher 첫 줄, 2단계 개수 표
지킬 것이 랩 DB에만. 전체 삭제문 금지. 행은 $rows(노드는 속성 묶음, 관계는 a · b · props). 다시 실행해도 늘지 않게.
결과의 꼴결과/load.cypher의 문장들
확인 방법4단계 개수 견줌과 한 번 더 실행한 뒤의 개수
정답 보기

노드는 id로 MERGE하고 값은 처음 만들 때만 넣습니다(ON CREATE SET — 다시 적재해도 수정본이 고친 값을 되돌리지 않게). 관계는 양 끝 id로 찾은 뒤 같은 방식으로 MERGE합니다.

붙여 넣는 내용 · VS Code 편집기에서 — 결과/load.cypher

// 적재 — 노드는 id로 같은 대상을 알아보고(MERGE), 값은 처음 만들 때만 넣는다(ON CREATE SET — 다시 적재해도 수정본이 고친 값을 되돌리지 않음). 관계는 양 끝 id와 관계 이름으로 알아본다.
// 넣을 것: Asset
UNWIND $rows AS row MERGE (n:Asset {id: row.id}) ON CREATE SET n = row;

// 넣을 것: Component
UNWIND $rows AS row MERGE (n:Component {id: row.id}) ON CREATE SET n = row;

// 넣을 것: Part
UNWIND $rows AS row MERGE (n:Part {id: row.id}) ON CREATE SET n = row;

// 넣을 것: Quantity
UNWIND $rows AS row MERGE (n:Quantity {id: row.id}) ON CREATE SET n = row;

// 넣을 것: Sensor
UNWIND $rows AS row MERGE (n:Sensor {id: row.id}) ON CREATE SET n = row;

// 넣을 것: Supplier
UNWIND $rows AS row MERGE (n:Supplier {id: row.id}) ON CREATE SET n = row;

// 넣을 것: HAS_COMPONENT
UNWIND $rows AS row MATCH (a {id: row.a}), (b {id: row.b}) MERGE (a)-[r:HAS_COMPONENT]->(b) ON CREATE SET r = row.props;

// 넣을 것: MONITORED_BY
UNWIND $rows AS row MATCH (a {id: row.a}), (b {id: row.b}) MERGE (a)-[r:MONITORED_BY]->(b) ON CREATE SET r = row.props;

// 넣을 것: OBSERVES
UNWIND $rows AS row MATCH (a {id: row.a}), (b {id: row.b}) MERGE (a)-[r:OBSERVES]->(b) ON CREATE SET r = row.props;

// 넣을 것: SUPPLIES
UNWIND $rows AS row MATCH (a {id: row.a}), (b {id: row.b}) MERGE (a)-[r:SUPPLIES]->(b) ON CREATE SET r = row.props;

// 넣을 것: USES_PART
UNWIND $rows AS row MATCH (a {id: row.a}), (b {id: row.b}) MERGE (a)-[r:USES_PART]->(b) ON CREATE SET r = row.props;
