# 설비·부품·공급 정보를 연결하는 온톨로지 설계하기

## 목표

포털 지식 지도에서 한 부품을 쓰는 설비를 찾아보며, 연결이 있다는 것과 그 부품을 실제로 살 수 있는 조건이 확보됐다는 것은 다르다는 것을 확인했습니다. 이번에는 그 공급 조건을 직접 모델에 넣습니다. 제공된 설비 · 부품 모델에 구매팀의 견적 · 승인 · 품번 자료를 연결해, 부품마다 쓰는 설비와 공급사별 조건을 함께 답하는 모델로 확장합니다.

같은 부품이라도 어느 공급사에서 어떤 조건으로 살 수 있는지는 시점과 출처에 따라 달라집니다. 그래서 값마다 어느 자료의 언제 값인지 남겨야 고르는 사람이 믿고 쓸 수 있습니다. 이 모델은 공급사를 골라 주지 않습니다. 고르는 사람이 고를 때 필요한 정보를 찾아 주는 구조입니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 첫 단계인 온톨로지의 설계 — 질문으로 범위를 정하고, 종류(이론의 클래스 — 공통 특성을 가진 대상의 유형) · 속성 · 관계를 정의해 원자료로 모델을 만드는 일 — 를 맡습니다.

만들 것: 공급 정보를 더한 스키마(종류 · 속성 · 관계의 정의)와 인스턴스(실제 대상과 관계), 원자료에서 그것을 만드는 코드와 모델에 물어보는 확인 코드, `결과/요구사항.md` · `결과/자료_검토.md`.

## 출발점

- `입력/schema.json` · `입력/graph.json` — 제공된 설비 · 부품 모델. 설비 7대 · 구성 요소 · 센서 · 부품과 그 연결이 들어 있고, 공급 정보는 아직 없습니다.
- `자료/` — 원자료. CSV 8개(설비 대장 · 구성 요소 · 센서 · 예비품 · 품번 교차표 · 공급 조건 · 승인 공급사 · 입고 이력), 현장 메모, 구매 기준서 발췌. 기준일은 2026-10-15입니다.
- `결과/` — 이번에 만든 것을 두는 자리. 「제공 빈 틀」 `요구사항.md` · `자료_검토.md`가 있습니다.
- `AGENTS.md` · `.github/copilot-instructions.md` · `CLAUDE.md` — Codex와 GitHub Copilot이 지키는 작업 규칙(세 파일이 같은 내용). 학생도 함께 읽습니다.

## 해결할 질문

아래 질문의 답은 구매 담당이 다음 발주에서 공급사를 비교할 때 씁니다. 고르는 것은 구매 담당입니다.

1. 펌프 축 씰 키트를 쓰는 설비와 구성 요소는 어디인가?
2. 기준일(2026-10-15)에 펌프 축 씰 키트를 어느 공급사에서 어떤 조건(승인 여부 · 단가 · 불량률 · 납기)으로 살 수 있고, 각 값은 어느 파일 · 어느 날짜 자료에서 왔는가?
3. 이름이 비슷한 다른 품번, 예전 품번이나 다른 표기, 원자료에 없는 품번으로 물으면 결과가 서로 구별되는가?

## 학생이 정할 것

원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 `결과/요구사항.md` 「정한 것」 표에 적습니다.

- **조건이 붙은 승인** — 승인 목록에 조건을 달아 등록된 쌍을 승인 여부(참 · 거짓)에 어떻게 담고, 그 조건을 구매 담당에게 어떻게 보여 줄지
- **빈 값의 뜻** — 비어 있는 칸을 「없음」으로 읽을지 「적지 않음」으로 읽을지
- **쓰는 사람에 따라 갈리는 답** — 구매 담당이 공급사를 비교할 때 함께 봐야 할 것이 자료에 있으면, 그것을 모델에 어떻게 남길지

AI에게 이 지점을 대신 정하게 하지 않습니다. AI가 고를 것을 내놓거나 「권장」을 붙여도 그대로 따르지 말고, 원문 줄을 열어 내 선택과 근거를 말합니다. 못 정한 지점은 미결로 남깁니다.

## 이번 범위 밖

- 공급사를 고르거나 점수 · 순위를 매기는 일
- 입고 이력으로 실측 납기를 계산하는 일
- 그래프 DB에 적재하고 조회하는 일(다음 실습)
- 제공된 설비 · 부품 모델의 설비 · 구성 요소 · 센서 · 부품 부분을 고치는 일(이상한 곳은 `결과/자료_검토.md`에 적습니다)

자료에 있어도 이번 결과에 만들지 않습니다.

## 결과 형식

`check.py`와 다음 실습이 읽는 모양입니다. 무엇을 종류·속성·관계로 둘지는 직접 정합니다.

- `결과/schema.json`: `{"classes": {종류: {"meaning": 뜻, "required": {속성: 자료형}, "optional": {속성: 자료형}}}, "relations": {관계: {"from": 종류 또는 [종류…], "to": 종류, "cardinality": "1:N" 등, "properties": {속성: 자료형}}}}`
- 자료형은 `string`·`number`·`integer`·`boolean`·`list` 중 하나이거나, 허용 값 목록(예: `["upper", "lower"]`)입니다.
- `결과/graph.json`: `{"nodes": [{"labels": [종류], "props": {"id": 고유 ID, …}}], "rels": [{"type": 관계, "a": 시작 id, "b": 끝 id, "props": {…}}]}`
- 같은 두 대상 사이에 같은 관계를 여러 개 두려면 그 관계의 props에 `id`를 붙입니다.

### 공급 조건 형식(다음 실습의 조회가 읽는 모양)

- 공급사에서 부품으로 가는 관계 `SUPPLIES` 하나가 그 공급사 · 부품 쌍의 기준일 견적 조건 하나와 그 공급사의 승인 여부입니다. 같은 쌍에 `SUPPLIES`를 둘 이상 두지 않습니다. 기준일에 쓸 조건이 없는 쌍은 이 관계를 두지 않고, 그 사정을 `결과/자료_검토.md`에 남깁니다.
- `SUPPLIES`에 반드시 둘 속성: `approved`(boolean, 승인 공급사인지), `price_manwon`(number, 만원), `defect_rate`(number, 0~1 비율), `lead_days`(integer, 일), `quote_date`(string, 견적일). 그 밖의 속성(출처 · 조건 · 원래 표기 등)은 직접 정합니다.
- 견적 · 승인 이력을 함께 남기려면 다른 종류나 관계로 둡니다(선택).

## 진행 단계

한 번에 한 단계씩 갑니다. 단계마다 결과를 확인한 뒤 다음 단계로 갑니다. 단계마다 정하거나 물을 것, 요청에 담을 것, 판단할 증거는 `guide.html`의 같은 번호에 있습니다.

1. **폴더와 출발점 확인** — VS Code 탐색기에서 이 폴더의 `입력/` · `자료/` · `결과/` · START.md를 열어 각 자리의 역할과 이번 질문을 확인합니다.
2. **파일을 바꾸지 않고 자료 파악** — AI에게 파일을 바꾸지 말고, 펌프 축 씰 키트에 관한 줄을 자료마다 찾아 파일 · 줄로 짚어 달라고 합니다. 짚은 줄을 직접 엽니다.
3. **요구와 기대 답 정하기** — 질문 · 이 답을 쓰는 사람 · 기준일 · 지킬 조건과, 질문 1 · 2의 기대 답을 원자료에서 직접 찾아 `결과/요구사항.md`에 내 말로 적습니다. 「학생이 정할 것」의 지점마다 고른 것과 근거 줄을 적습니다.
4. **설계 계획 검토** — 공급 정보를 모델의 어느 종류 · 속성 · 관계로 둘지 AI의 계획을 받아 검토하고, 5 ~ 10단계의 구현 순서에 동의합니다. 아직 파일을 만들지 않습니다.
5. **구현 ① 공급사 대상 만들기** — 견적 자료와 승인 공급사 목록에 나오는 공급사를 하나씩 공급사 대상으로 만드는 코드를 `결과/`에 만들고 실행합니다. 이 단계에서 처리한 문제 행은 `결과/자료_검토.md`에 한 줄씩 적습니다.
6. **구현 ② 기준일에 쓸 견적 조건 잇기** — 공급사 · 부품 쌍마다 기준일에 쓸 견적 조건 하나를 공급 조건 관계(`SUPPLIES`)로 잇는 기능을 더하고 실행합니다. 이 단계에서 처리한 문제 행은 `결과/자료_검토.md`에 한 줄씩 적습니다.
7. **구현 ③ 승인 정보 붙이기** — 공급 조건 관계(`SUPPLIES`)마다 승인 여부(`approved`)와, 4단계에서 정한 승인 정보 속성을 「정한 것」 표의 결정대로 붙이고 실행합니다. 이 단계에서 처리한 문제 행은 `결과/자료_검토.md`에 한 줄씩 적습니다.
8. **구현 ④ 단위 맞추기** — 단가 · 불량률 · 납기를 「공급 조건 형식」의 단위로 맞추고, 바꾼 값은 원래 표기를 남기는 기능을 더하고 실행합니다. 이 단계에서 처리한 문제 행은 `결과/자료_검토.md`에 한 줄씩 적습니다.
9. **구현 ⑤ 값마다 출처 남기기** — 공급 조건 관계(`SUPPLIES`)의 값마다 어느 파일 · 어느 날짜 자료에서 왔는지 남기는 기능을 더하고 실행합니다.
10. **구현 ⑥ 품번으로 물어보기** — 품번이나 표기 하나를 받아 `결과/graph.json`에서 사용 설비 · 구성 요소와 공급 조건(출처 포함)을 보여 주는 확인 코드를 만들고 실행합니다.
11. **구조 검사와 고치기** — 터미널에서 구조 검사를 실행하고, 나온 문제를 고친 뒤 10단계 확인을 다시 합니다.
12. **저장하고 다시 열기** — 결과 파일을 모두 저장하고 VS Code에서 폴더를 닫았다 다시 연 뒤 10단계 명령을 다시 실행합니다. `요구사항.md` 끝에 기준일 · 저장 시점 · 확인하지 못한 점을 적습니다.

이 순서는 바이브 코딩 일곱 단계 — 파일을 바꾸지 않고 파악 → 요구와 기대 답을 내 말로 → 계획 검토 → 작게 구현 → 원자료와 대조 → 고침 → 저장하고 다시 열기 — 를 따릅니다.

요청에 파일 이름을 쓸 때는 `결과/schema.json`처럼 백틱(`)으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다.

## 확인

확인할 사례의 종류(어느 행이 해당하는지는 원자료에서 직접 찾습니다):

- 같은 공급사 · 부품의 견적이 여러 줄인 경우
- 기준일에 기한이 지난 기록(견적 · 승인 등록)
- 같은 공급사를 다르게 적은 이름
- 출처마다 다른 승인 정보
- 기준서에 나오는 기준값과 같거나 가까운 값
- 단위 · 표기가 줄마다 다른 값
- 품번 칸의 표기가 줄마다 다른 경우
- 이름이 비슷한 다른 품번 · 예전 품번 · 다른 표기 · 원자료에 없는 품번
- 같은 코드를 다시 실행한 결과

실행 명령:

```
python check.py
python 결과/<만든 코드 이름>.py
python 결과/<확인 코드 이름>.py <품번>
```

바뀐 파일 확인: AI가 단계를 마칠 때마다 바뀐 파일 목록을 봅니다. `입력/` · `자료/`가 바뀌지 않았는지, 요청하지 않은 파일이 생기지 않았는지 확인합니다. 편집 승인 창에서는 경로가 `결과/` 아래일 때만 허용합니다.

## 완료 판정

형식 검사나 실행 성공만으로 완료하지 않습니다. 질문마다 원자료에서 먼저 적은 기대 답과 실제 결과가 맞고, 「정한 것」마다 근거 줄과 그 선택으로 바뀌는 답을 설명할 수 있으면 완료입니다. 고친 점과 확인하지 못한 점은 `결과/요구사항.md`에 짧게 남깁니다.

## 저장과 다음 실습

`결과/schema.json` · `결과/graph.json`을 한 쌍으로, 만든 코드 · 확인 코드 · `요구사항.md` · `자료_검토.md`와 함께 보관합니다. 다음 실습 「부품의 사용 설비와 공급 정보를 조회하는 그래프 구현하기」에서는 이 판본을 쓰거나 제공된 설비 · 부품 · 공급 모델로 시작할 수 있습니다. 재부팅 전에 이 실습 폴더를 USB 또는 개인 클라우드에 복사합니다. 자동으로 되살려 주지 않습니다.
