01 폴더 열고 자료 확인하기

목표 받은 랩 폴더를 VS Code로 열고 첫 명령을 실행한다. 이 폴더 하나로 실습 전체가 돌아간다.

상황

  • ZIP 안에 랩 폴더와 이 가이드가 들어 있다
  • 할 일은 터미널에 명령을 넣는 것과 Codex에게 말하는 것, 두 가지뿐이다
  • 폴더 안에 있는 것
    • data/ — 원자료 표와 현장 메모, 바로 쓸 모델(model/), 기준일 뒤에 바뀐 줄을 모은 수정본(changes/)이 있고, 읽기만 한다
    • AGENTS.md — AI가 지킬 공통 규칙
    • app/features/ — Codex와 함께 채울 빈 파일들. 단계를 따라 하나씩 채운다
    • app/ui/ · app/utils/ — 미리 만들어 둔 화면 · 처리 코드
    • run.py — 실행 파일. 명령은 모두 python run.py …로 시작한다
    • output/ — 실행하면 생기는 결과. 결과 화면 result.html도 여기에 생긴다

뭐부터 해야 할까?

  1. ZIP을 풀고, VS Code에서 파일 → 폴더 열기로 안쪽 graph-lab 폴더(run.py가 있는 폴더)를 연다
  2. 폴더를 신뢰하겠느냐고 물으면 예, 작성자를 신뢰합니다를 누른다
  3. 터미널 → 새 터미널을 열고 아래 명령을 실행한다

터미널(PowerShell · 이 실습 폴더)

python run.py

확인 결과 화면이 열리고 맨 위에 사용할 모델의 노드 수와 관계 수가 나오면 됩니다. 결과 화면이 안 열리면 탐색기에서 output/result.html을 직접 엽니다. 다음 명령부터는 실행한 뒤 결과 화면에서 F5(새로 고침)를 누릅니다.

03 Codex에게 물어 제공 모델 파악하기

목표 그래프 DB에 넣기 전에, 받은 모델에 무엇이 몇 개 있는지 알아 둔다. 넣은 뒤 개수를 맞춰 봐야 제대로 들어갔는지 알 수 있다.

상황

  • 랩 DB를 띄웠고, 아직 비어 있다
  • data/model/에 바로 쓸 모델이 있다. schema.json은 스키마(클래스와 관계), graph.json은 인스턴스 데이터다
  • 모델에는 공급사와 견적도 들어 있다. 이 둘은 구매팀의 질문을 다루는 13단계부터 쓴다
  • 이 모델은 설계 실습과 같은 원자료를 같은 클래스와 관계로 끝까지 설계해 둔 것이다. 내가 만든 모델과는 식별자를 지은 꼴이나 고른 것이 다를 수 있어, 화면의 수를 이 안내와 맞춰 보기 쉽게 이 모델로 시작한다
  • 결과 화면에 「종류」라고 나오는 것이 클래스이고, 그래프 DB에서는 이것을 노드의 레이블이라고 부른다

뭐부터 해야 할까?

  1. Codex에게 종류마다 몇 개인지, 관계는 몇 개이고 어느 방향인지 물어보자
  2. 대상마다 무엇으로 구별했는지(식별자)도 물어보자
  3. 원자료의 줄 수와 모델의 개수가 다른 곳이 있으면, 왜 다른지 원자료 줄로 알려 달라고 하자
  4. Codex가 까닭으로 든 원자료 줄은 직접 열어 그 줄이 맞는지 보자

Codex에게 파일 이름을 말할 때는 백틱 기호(키보드 숫자 1 왼쪽)로 감쌉니다.

04 역량 질문과 기대 답 정하기

목표 쿼리를 쓰기 전에, 세 역량 질문에 어떤 답이 나와야 하는지 먼저 정한다. 쿼리 결과를 이 기대 답과 견줘 확인하는데, 결과를 본 뒤에 정하면 틀린 결과도 맞아 보인다.

상황

  • 모델에 무엇이 몇 개 있는지 알았다
  • expected.csv(미리 정해 두는 기대 답 표)는 아직 비어 있다
  • 역량 질문 세 가지
    • ① 설비의 구성 요소마다 어떤 센서가 붙는가?
    • ② 설비의 구성 요소마다 어떤 교체 부품이 들어가는가?
    • ③ 부품을 어느 설비가 쓰고 그 설비의 상태는 무엇인가? 다른 표기(예전 품번 · 제조사 품번 · 표기 변형)나 원자료에 없는 품번으로 물으면 어떻게 구별되는가?
  • data/changes/의 수정본(기준일 뒤에 바뀐 줄)은 11 · 12단계에서 다룬다

뭐부터 해야 할까?

  1. 질문마다 「무엇을 물으면 무엇이 나와야 하는지」를 근거 줄과 함께 표로 받아 보자
  2. 질문 ①은 값만 모아 두면 짝이 틀려도 맞아 보인다. 구성 요소와 센서, 센서와 물리량, 센서와 한계를 줄마다 짝지어 견주게 세 줄로 두자. 한계가 없는 센서는 「없음」으로 둔다
  3. 질문 ②의 부품은 원자료에 적힌 표기 그대로 적을까, 모델이 부품을 구별하는 값(사내 품번)으로 적을까? 쿼리가 돌려줄 값과 같은 꼴이어야 견줄 수 있다
  4. 질문 ③은 수정본에서 상태가 바뀌는 설비가 쓰는 부품으로 물어 두자. 그 부품의 다른 표기로 물은 줄도 두고, 지금은 반영하기 전의 답으로 정한다
  5. 원자료에 없는 품번으로 물으면 무엇이 나와야 할까? 빈 결과로 둘지, 없다고 알려 주는 한 줄로 둘지 지금 정해 두자
  6. 교체 부품이 없는 구성 요소는 질문 ② 답에서 뺄지, 「없음」으로 남길지도 지금 정해 두자
  7. 센서 표에는 붙은곳이 구성 요소가 아니라 「설비 전체」인 줄이 있다. 질문 ①은 구성 요소마다 붙은 센서를 묻는다. 이 줄을 답에 넣을지 뺄지도 지금 정해 두자
  8. 후보 가운데 한두 줄은 근거 줄을 직접 열어 맞는지 보고, 받아들인 줄만 적어 달라고 하자

승인 창이 뜨면 Codex가 app/features/ 안의 파일을 고치려는 것일 때만 Allow once, 그 밖이거나 python run.py 명령을 대신 실행하려는 것이면 Deny를 누릅니다.

세 역량 질문의 기대 답 후보를 원자료와 제공 모델에서 찾아 근거 줄(파일:줄)과 함께 표로 보여 줘. ① 설비의 구성 요소마다 어떤 센서가 붙는가? ② 설비의 구성 요소마다 어떤 교체 부품이 들어가는가? ③ 부품을 어느 설비가 쓰고 그 설비의 상태는 무엇인가? 다른 표기(예전 품번 · 제조사 품번 · 표기 변형)나 원자료에 없는 품번으로 물으면 어떻게 구별되는가? 꼴은 `expected.csv` 빈 틀의 첫 줄을 따르고, 볼_열은 component · tag · quantity · limit · part · asset · status · note 가운데 그 줄에 맞는 이름으로 붙여 줘. 질문 1은 같은 설비로 볼_열이 component+tag, tag+quantity, tag+limit인 줄을 하나씩 두고(기대 답은 결과 줄마다 「값=값」), 한계가 없는 센서는 「없음」으로 적어 줘. 질문 2의 부품은 사내 품번으로 적고, 교체 부품이 없는 구성 요소는 빠지지 않게 품번 칸을 「없음」으로 적어 줘. 원자료에 없는 품번으로 물은 줄은 볼_열을 note로, 기대 답을 「원자료에 없는 품번」으로 적어 줘. 질문 3은 수정본에서 상태가 바뀌는 설비가 쓰는 부품과 그 부품의 다른 표기로 묻고, 수정본을 반영하기 전의 답으로 해 줘. 파일은 바꾸지 마.

05 같은 식별자가 둘 생기지 않게 하기: 유일 제약

목표 모델을 넣기 전에, 식별자마다 유일 제약을 건다. 걸어 두면 누가 어떤 쿼리로 넣든 같은 식별자의 노드가 둘 생기는 것을 DB가 막는다.

상황

  • 랩 DB는 아직 비어 있다
  • 유일 제약은 값이 겹치는 것을 저장할 때 DB가 막는 DB 제약 조건이다. 회원 가입에서 이미 쓰는 아이디를 받아 주지 않는 것과 같다
  • constraints.cypher(유일 제약을 거는 Cypher 쿼리 파일)는 비어 있다

뭐부터 해야 할까?

  1. 어느 값이 겹치면 안 될까? 03단계에서 들은 식별자를 떠올려 보자
  2. 종류(레이블)마다 식별자에 유일 제약을 거는 쿼리를 constraints.cypher에만 써 달라고 하자
  3. 한 번 더 실행하면 어떻게 될까? 이미 걸려 있으면 그대로 두게 하자
  4. 쿼리 한 줄이 무엇을 하는지 풀어 달라고 하고, 내 말로 한 문장으로 말해 보자
  5. 아래 명령으로 걸고, 같은 식별자로 노드를 두 번 만들면 DB가 뭐라고 답하는지 결과 화면에서 보자

`data/model/schema.json`의 종류(레이블)마다 식별자 `id`에 유일 제약을 거는 쿼리를 `constraints.cypher`에 작성해 줘. 다시 실행해도 오류가 나지 않게 IF NOT EXISTS를 쓰고 쿼리 끝에 ;를 붙여 줘. 데이터를 넣는 쿼리와 다른 파일은 아직 작성하지 마. 작성한 뒤 쿼리 한 줄이 무엇을 하는지 쉬운 말로 풀어 줘.

06 넣기 전에 DB에 물어보기: 예측하고 실제 답 보기

목표 넣는 쿼리를 쓰기 전에, 쿼리를 이렇게 쓰면 DB가 뭐라고 하는지 먼저 알아본다. 내 예측과 DB의 실제 답을 견줘 두면, 넣는 쿼리에서 무엇을 지키고 넣은 뒤 무엇을 확인할지가 정해진다.

07 스키마를 그래프로 옮기기: 넣기와 다시 넣기

목표 모델을 랩 DB에 넣고, 다시 넣어도 개수와 값이 그대로이게 한다. 같은 데이터를 다시 넣는 일은 자주 생기는데, 그때마다 늘어나거나 고친 값이 되돌아가면 그래프를 믿을 수 없다.

12 바뀐 것만 고치기: 수정본 반영

목표 수정본을 반영한다. 전부 지우고 다시 넣지 않고 식별자로 찾아 바뀐 것만 고쳐야, 무엇이 달라졌는지 수정본 줄과 하나씩 견줄 수 있다.

상황

  • 불용 설비와 목록에서 빠진 센서를 어떻게 할지 골랐다
  • update.cypher(수정본을 반영하는 Cypher 쿼리 파일)는 비어 있다
  • 수정본의 줄은 표에 적힌 열 이름 그대로 쿼리로 넘어오고, 값은 모두 글자다
  • schema_additions.csv(스키마에 없던 속성을 더할 때 적는 표)도 비어 있다

뭐부터 해야 할까?

  1. 먼저 기대 답을 반영한 뒤의 답으로 고쳐 달라고 하자. 새로 등록된 표기로 물은 줄과, 목록에서 빠진 센서가 붙은 설비로 물은 질문 ① 줄도 두어 내 선택이 답에 보이게 하고, 반영한 뒤 종류마다 몇 개여야 하는지도 세어 달라고 하자
  2. 센서를 상태로 남기기로 했다면, 그 상태를 적을 속성을 schema_additions.csv에 먼저 정하고 질문 ①이 그 상태도 돌려주게 하자
  3. 수정본의 열 이름이 모델의 어느 속성인지 짝지어 달라고 하고, 식별자로 찾아 바뀐 값만 고치게 하자. 설비 코드 같은 값은 쿼리에 적지 말고 수정본 줄의 칸으로 받게 해야, 다음 수정본이 와도 같은 쿼리를 쓴다
  4. 추가 · 수정 · 삭제마다 쿼리를 나누고, 불용 설비와 삭제 줄은 앞 단계에서 고른 대로 하자
  5. 어디까지 지워야 할지 애매하면 먼저 물어봐 달라고 하자
  6. 반영한 뒤 개수를 다시 세고, 모델을 한 번 더 넣어도 고친 값이 그대로인지 보자

14 구매팀 질문을 쿼리로 묻기: 기준일의 공급 조건

목표 질문 ④를 쿼리로 묻는다. 앞의 질문들과 같은 차례로, 기대 답을 먼저 정하고 쿼리를 돌려 견준다. 맞으면 이 화면이 구매팀에 건네는 조회 결과가 된다.

상황

  • 공급사에서 견적을 지나 부품까지 이어졌다
  • 견적마다 유효기한이 있고, 기준일은 현장 메모에 적혀 있다
  • 같은 공급사가 같은 부품에 견적을 두 번 낸 곳이 있고, 이 모델은 그 둘을 따로 담았다

뭐부터 해야 할까?

  1. 물어볼 부품 하나는 내가 고르자. 공급사가 둘 이상인 부품이면 견줄 것이 생긴다
  2. 기대 답 후보를 원자료의 견적표와 승인 공급사 목록에서 근거 줄과 함께 받아 보자. 공급사와 승인 상태, 공급사와 단가처럼 줄마다 짝지어 견주게 둔다
  3. 기준일에 유효기한이 지난 견적은 답에 넣을까, 뺄까? 승인 상태는 두 표 가운데 어느 쪽 것을 따를까? 구매 기준서의 줄로 물어보고 정하자
  4. 그 부품의 다른 표기로 물은 줄과 원자료에 없는 품번으로 물은 줄도 하나씩 두자
  5. 근거 줄을 한두 곳 열어 보고, 받아들인 줄만 expected.csv에 질문 4로 적어 달라고 하자

  3. 폴더는 USB나 개인 클라우드에 따로 보관하자

터미널(PowerShell · 이 실습 폴더)

python run.py db

확인 결과 화면 「랩 DB」 막대가 0이 아니고 13단계 뒤의 개수 그대로면 됩니다.

새 랩 DB가 만들어졌다는 안내가 나왔을 때 — 먼저 실행

터미널(PowerShell · 이 실습 폴더)

python run.py constraints

종류마다 유일 제약이 다시 걸렸는지 봅니다.

터미널(PowerShell · 이 실습 폴더)

python run.py load

넣은 개수가 모델과 같은지 봅니다.

터미널(PowerShell · 이 실습 폴더)

python run.py update

수정본과 내 선택이 반영됐는지 봅니다.

터미널(PowerShell · 이 실습 폴더)

python run.py usage

결과가 그대로인지 봅니다.

터미널(PowerShell · 이 실습 폴더)

python run.py export

랩 DB의 그래프를 output/schema.json · graph.json으로 저장합니다.

터미널(PowerShell · 이 실습 폴더)

python run.py check

확인 「구조 검사 통과」가 보이면 됩니다.

내 말로 불용 설비와 목록에서 빠진 센서를 왜 그렇게 처리했는지, 그래서 질문 ① · ③이 어떻게 나왔는지, 유일 제약과 MERGE가 각각 무엇을 맡아 다시 넣어도 그대로였는지, DB가 막아 주지 않아 내가 확인한 것은 무엇이었는지 말해 봅니다. 구매팀 질문 때문에 그래프에 무엇을 더 이었고, 기준일을 쿼리의 어디에서 어떻게 걸렀는지도 말해 봅니다.
