HYD · 실습 가이드

부품의 사용 설비와 공급 정보를 조회하는 그래프 구현하기

설비·부품·공급 모델을 이 폴더 전용 그래프 DB(랩 DB)에 구현합니다. 부품별 사용 설비와 공급 조건을 돌려주는 조회 결과를 원자료와 대조합니다. 스키마의 식별자와 관계 방향이 그래프의 노드·관계로 옮겨지는 것을 다시 짚습니다. 줄기(온톨로지 → 에이전트 → 프로세스)에서 첫 단계 온톨로지의 구현과 검증을 맡습니다.

01 폴더 열고 자료 확인하기

클래스룸의 2회차 실습 자료에서 이 실습의 ZIP을 받아 압축을 풀고, VS Code의 파일 → 폴더 열기로 graph-lab 폴더를 엽니다. 그 위 폴더를 열면 AI가 정답이 든 이 가이드까지 읽습니다. 신뢰 여부를 물으면 예, 작성자를 신뢰합니다(Yes, I trust the authors)를 고릅니다. 제한 모드에서는 Codex를 쓸 수 없습니다.

README.md에서 폴더 역할을 봅니다. data/는 원자료, data/model/은 공급 조건까지 담은 설비·부품·공급 모델이라 자기 모델이 없어도 시작할 수 있고, app/features/는 AI와 구현할 Cypher 쿼리와 기록입니다. AGENTS.md는 Codex가 지킬 공통 작업 원칙입니다.

터미널 → 새 터미널을 열고, 오타를 줄이도록 명령 블록의 복사로 붙여 넣습니다.

터미널(PowerShell · 이 실습 폴더)

python run.py

원자료 파일과 사용할 모델의 개수가 보입니다. 결과는 output/result.html에 저장됩니다. 브라우저가 열리지 않으면 Windows 파일 탐색기로 이 실습 폴더의 output 폴더를 열고 result.html을 두 번 누릅니다(VS Code 탐색기에서 누르면 화면이 아니라 HTML 글이 열립니다). 이후에는 명령을 실행한 뒤 열린 화면에서 F5를 누릅니다.

02 랩 DB 준비하기

모델을 넣고 조회할 랩 DB를 준비합니다. 랩 DB는 이 실습 폴더에만 쓰는 그래프 DB로, Docker가 새로 띄웁니다. Docker Desktop을 켠 뒤 아래 명령을 실행합니다. 처음 한 번은 DB 이미지를 받느라 오래 걸립니다.

Docker와 랩 DB 명령은 내 터미널에서 실행합니다. Codex가 이런 명령을 실행하려 하면 실행 승인 창에서 Deny를 누르고 그 명령을 터미널에 붙여 넣습니다.

터미널(PowerShell · 이 실습 폴더)

python run.py db

모델 파일의 개수와 랩 DB 개수가 나란히 보입니다. 처음 만든 랩 DB는 0이며, 이어서 작업하는 랩 DB는 이전에 넣은 개수입니다. 「랩 DB 준비 확인 필요」가 나오면 Docker Desktop이 켜져 있는지 보고 다시 실행합니다. 뒤 단계에서 「랩 DB가 꺼져 있습니다」가 나오면 이 명령으로 다시 켭니다.

03 Codex와 모델 파악하기

적재가 맞았는지 세려면 모델에 무엇이 몇 개 있는지 먼저 알아야 합니다. 왼쪽 활동 표시줄의 Codex 아이콘을 눌러 채팅을 열고 로그인한 뒤, 파일을 바꾸지 말고 data/model/graph.json의 종류별 대상·관계 수와 펌프 축 씰 키트에 닿는 관계, 그 값의 원자료 줄을 짚어 달라고 요청합니다. 계정이 없거나 막히면 클래스룸에서 별도로 받는 graph-lab-completed.zip을 실행해 볼 수 있습니다.

제공 모델의 식별자와 공급 조건 관계에 붙은 속성(값과 출처)도 묻습니다. data/model/provenance.md에서 모델에 적용된 기준을 확인합니다.

설계 실습에서 만든 자기 온톨로지 모델을 쓰는 것은 선택입니다. 사용할 때만 기준일·종류·식별자·관계의 형식을 확인하고, 두 JSON 파일을 app/features/model/에 함께 복사합니다. 제공 모델은 보존합니다.

터미널(PowerShell · 이 실습 폴더)

python run.py

현재 사용하는 모델 경로와 개수를 확인합니다. 자기 모델을 골랐다면 이후 질문과 Cypher 쿼리도 그 모델에 맞춥니다. Codex가 파일을 바꾸려 하면 편집 승인 창이 뜹니다. 경로가 app/features/ 아래인 요청한 변경만 Allow once, 그 밖은 Deny를 누릅니다. Codex가 단계를 마칠 때마다 보고한 바뀐 파일이 요청한 파일뿐인지 봅니다.

04 질문과 기대 답 정하기

보전·구매 담당이 예비품을 쓰는 설비와 공급사별 조건을 함께 볼 때 쓸 답을 만듭니다. 고르는 것은 구매 담당입니다. app/features/review.md에 질문·사용할 자료·기준일·지킬 조건을 자기 말로 적습니다. 공급사를 고르거나 점수·순위를 매기는 일, 입고 이력으로 실측 납기를 세는 일, 모델 정의 변경은 이번 범위에서 제외합니다.

① 세 설비가 함께 쓰는 펌프 축 씰 키트를 어느 설비·구성 요소에서 쓰고, 기준일의 세 공급 조건(승인 여부·단가·불량률·납기)은 무엇이며 각 값은 어느 파일·어느 줄에서 왔는가? ② 이름이 비슷한 다른 품번, 예전 품번이나 다른 표기, 원자료에 없는 품번으로 물으면 결과가 서로 구별되는가? 비승인 공급사는 승인 상태와 함께 구별되는가? ③ 같은 적재를 다시 실행해도 대상과 관계가 늘지 않는가?

app/features/expected.csv에 펌프 축 씰 키트의 사용 설비와 세 공급 조건, 다른 표기·없는 품번의 기대 답과 근거를 먼저 적습니다. 한 물을 값에 견줄 것이 여럿이면(사용 설비와 공급사처럼) 줄을 나눠 씁니다. 볼_열은 조회를 만든 뒤(사용 설비와 공급 조건 조회, 다른 표기 조회) 그 조회가 돌려주는 열 이름으로 채우므로 지금은 비워 둡니다. 여러 값은 「 · 」로 잇습니다.

쓰는 사람에 따라 갈리는 답을 정합니다. 구매 담당이 공급사를 비교할 때 승인 여부·단가·불량률·납기 말고도 함께 봐야 할 것이 모델에 있으면, 그것을 조회 결과에 함께 돌려줄지와 어떻게 보일지입니다. 선택과 근거를 decisions.csv에 적고 AI의 추천은 원자료로 다시 확인합니다.

파일을 손으로 고친 뒤에는 Ctrl+S로 저장합니다(탭 이름 옆 ●가 사라지면 저장됨). 저장하지 않으면 명령이 고치기 전 내용을 읽어 0행으로 보입니다.

05 모델 적재하기

이론에서 본 대로 스키마의 종류(클래스) 이름은 그래프의 레이블이 되고, 대상 하나(인스턴스)는 노드, 관계 정의의 시작·끝은 관계의 방향이 됩니다. CREATE는 실행할 때마다 새로 만들고, MERGE는 같은 것이 있으면 찾고 없으면 만듭니다. 그래서 다시 적재해도 늘지 않으려면 같은 대상을 무엇으로 알아볼지(MERGE의 열쇠) 먼저 Codex와 정합니다.

계획을 확인한 뒤 적재 Cypher 쿼리를 app/features/load.cypher에만 작성하도록 요청합니다. 종류·관계마다 쿼리를 나누고, 바로 위에 // 넣을 것: <종류 또는 관계>를 적습니다. 제공 도구가 해당 행을 $rows로 넘겨 실행합니다.

요청에 파일 이름을 쓸 때는 키보드 숫자 1 왼쪽의 백틱 기호로 앞뒤를 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다. python run.py 명령은 내 터미널에서 실행하고, 터미널 출력과 결과 화면으로 확인합니다.

06 사용 설비와 공급 조건 조회하기

공급 조건은 공급사와 부품 사이 관계의 값이라, 부품에서 설비 쪽과 공급사 쪽 두 길을 따라가야 한 번에 나옵니다. 무엇을 함께 돌려줄지는 결과를 쓰는 사람이 공급사를 무엇으로 견주는지에 따라 정하고, 그 선택에 따라 결과의 열이 달라집니다.

app/features/query.cypher의 // 질문 1 아래에 품번 하나로 사용 설비·구성 요소와 공급사별 공급 조건(승인 상태·출처 포함)을 돌려주는 Cypher 쿼리를 작성합니다. 비승인 공급사를 어떻게 구별해 보일지와 decisions.csv의 선택대로 무엇을 함께 돌려줄지 Codex에게 말합니다. 쿼리를 만든 뒤 expected.csv 질문 1 줄의 볼_열을 돌려받은 열 이름으로 채웁니다.

07 다른 표기와 없는 품번 구별하기
