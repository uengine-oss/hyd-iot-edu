# 부품의 사용 설비와 공급 정보를 조회하는 그래프 구현하기

## 목표

「설비·부품·공급 정보를 연결하는 온톨로지 설계하기」에서는 부품마다 쓰는 설비와 공급사별 조건을 모델에 넣었습니다. 이번에는 제공된 설비 · 부품 · 공급 모델(또는 내가 만든 모델)을 이 폴더 전용 랩 DB(그래프 DB)에 적재하고, 질문마다 조회문을 만들어 원자료와 대조합니다. 스키마의 ID와 관계 방향이 그래프의 노드 · 관계로 어떻게 옮겨지는지 직접 봅니다.

조회가 돌려준 공급 조건을 구매 담당이 믿고 쓰려면 승인되지 않은 공급사가 승인된 것처럼 섞이지 않고 값마다 출처가 따라와야 합니다. 이 조회는 공급사를 골라 주지 않습니다. 고르는 사람이 볼 정보를 돌려줍니다. 그래프에 넣은 자료는 다시 넣을 일이 생깁니다. 같은 적재를 다시 실행해도 대상이 늘지 않아야 믿고 다시 돌릴 수 있습니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 첫 단계인 온톨로지의 구현과 검증 — 설계한 모델을 그래프 DB에 옮기고, 질문에 실제로 답하는지 원자료와 대조하는 일 — 를 맡습니다.

만들 것: 모델을 랩 DB에 넣는 적재문(또는 적재 코드), 질문별 조회문, `결과/검증_기록.md`.

## 출발점

- `입력/schema.json` · `입력/graph.json` — 제공된 설비 · 부품 · 공급 모델. 설비 7대 · 구성 요소 · 센서 · 부품 · 공급사와 그 연결이 들어 있고, 공급 조건마다 승인 여부 · 단가 · 불량률 · 납기와 값마다 출처(쓴 견적 · 승인 등록의 원자료 줄과 기준일)가 붙어 있습니다. 그 밖에 붙은 속성은 `입력/schema.json`에서 봅니다.
- `입력/자료/` — 그 모델의 원자료(기준일 2026-10-15).
- `입력/요구사항.md` · `입력/자료_검토.md` — 제공된 모델이 답하는 질문과 자료 처리 근거.
- `lab_db.py` — 이 폴더 전용 랩 DB를 켜는 도구. `결과/` — 이번에 만든 것을 두는 자리(「제공 빈 틀」 `검증_기록.md`).
- `AGENTS.md` · `.github/copilot-instructions.md` · `CLAUDE.md` — Codex와 GitHub Copilot이 지키는 작업 규칙(세 파일이 같은 내용). 학생도 함께 읽습니다.
- 내 모델을 쓸 때: 제공 입력은 그대로 두고 내 `schema.json` · `graph.json`을 `결과/내_모델/`에 복사해 씁니다. 만든 날짜 · 질문 · 파일 형식 · ID가 이번 입력과 맞는지 먼저 보고, 관계 이름이나 방향이 다르면 내 모델의 정의로 조회합니다. 내 모델이 없어도 제공된 모델로 끝까지 할 수 있습니다.

## 처음 쓰는 도구

- **랩 DB**: `python lab_db.py`가 이 폴더 전용 그래프 DB(이 실습에서는 Neo4j)를 Docker로 켜고 Browser를 엽니다. 포털 DB와 분리돼 있습니다. Browser 입력 칸에 Cypher를 넣어 실행하고 표(Table)로 원자료와 대조합니다. 수백 개 대상은 AI가 모델 파일에서 적재문을 만들게 합니다.
- **명령 실행 승인 창**: AI가 Docker · 랩 DB 명령을 실행하려 하면 폴더 밖 실행 승인 창이 뜹니다. 명령이 `python lab_db.py` · 이 폴더의 적재 · 조회이고 주소가 `127.0.0.1` 랩 DB일 때만 「Allow once」를 누릅니다.

## 해결할 질문

아래 질문의 답은 보전 · 구매 담당이 예비품을 쓰는 설비와 공급사별 조건을 함께 볼 때 씁니다. 고르는 것은 구매 담당입니다.

1. 세 설비가 함께 쓰는 펌프 축 씰 키트를 어느 설비 · 구성 요소에서 쓰고, 기준일의 세 공급 조건(승인 여부 · 단가 · 불량률 · 납기)은 무엇이며 각 값은 어느 파일 · 어느 줄에서 왔는가?
2. 이름이 비슷한 다른 품번, 예전 품번이나 다른 표기, 원자료에 없는 품번으로 물으면 결과가 서로 구별되는가? 비승인 공급사는 승인 상태와 함께 구별되는가?
3. 같은 적재를 다시 실행해도 대상과 관계가 늘지 않는가?

## 학생이 정할 것

원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 `결과/검증_기록.md` 「정한 것」 표에 적습니다.

- **쓰는 사람에 따라 갈리는 답** — 구매 담당이 공급사를 비교할 때 승인 여부 · 단가 · 불량률 · 납기 말고도 함께 봐야 할 것이 모델에 있으면, 그것을 조회 결과에 함께 돌려줄지와 어떻게 보일지

AI에게 이 지점을 대신 정하게 하지 않습니다. AI가 고를 것을 내놓거나 「권장」을 붙여도 그대로 따르지 말고, 원문 줄을 열어 내 선택과 근거를 말합니다. 못 정한 지점은 미결로 남깁니다.

## 이번 범위 밖

- 공급사를 고르거나 점수 · 순위를 매기는 일
- 입고 이력으로 실측 납기를 세는 일
- 모델의 종류 · 속성 · 관계 정의를 새로 바꾸는 일(이상한 곳은 `결과/검증_기록.md`에 적습니다)
- 포털 DB에 접속하거나 포털 자료를 랩 DB에 넣는 일

자료에 있어도 이번 결과에 만들지 않습니다.

## 결과 형식

`결과/`에 아래 파일을 둡니다. 파일 안에서 무엇을 어떤 문장으로 쓸지는 직접 정합니다.

- `결과/load.cypher`(또는 적재 코드): 모델 파일의 대상과 관계를 랩 DB에 넣습니다. 같은 파일을 다시 실행해도 됩니다.
- `결과/query.cypher`: 질문마다 조회문 하나. 조회문 위에 어느 질문의 조회인지 주석(`// 질문 1`)으로 적습니다.
- `결과/검증_기록.md`: 「제공 빈 틀」의 칸대로 채웁니다.

## 진행 단계

한 번에 한 단계씩 갑니다. 단계마다 결과를 확인한 뒤 다음 단계로 갑니다. 단계마다 정하거나 물을 것, 요청에 담을 것, 판단할 증거는 `guide.html`의 같은 번호에 있습니다.

1. **폴더와 출발점 확인** — VS Code 탐색기에서 `입력/`(제공된 모델 · 원자료) · `결과/` · `lab_db.py` · START.md를 열어 각 자리의 역할과 이번 질문을 확인합니다.
2. **랩 DB 켜기** — 터미널에서 `python lab_db.py`를 실행해 이 폴더 전용 랩 DB를 켜고, 열린 Neo4j Browser에 연결합니다.
3. **파일을 바꾸지 않고 자료 파악** — AI에게 파일을 바꾸지 말고, `입력/graph.json`에 어떤 종류의 대상과 관계가 몇 개 있는지와 펌프 축 씰 키트에 닿는 관계와 그 관계의 값이 어느 원자료 줄에서 왔는지 파일 · 줄로 짚어 달라고 합니다. 짚은 줄을 직접 엽니다.
4. **요구와 기대 답 정하기** — 질문 · 이 답을 쓰는 사람 · 지킬 조건과, 펌프 축 씰 키트의 사용 설비와 세 공급 조건, 값마다 원자료 파일 · 줄(견적일 `quote_date` · 기준일 `as_of`), 다른 품번 · 다른 표기 · 없는 품번으로 물었을 때의 답을 원자료에서 직접 찾아 기대 답으로 `결과/검증_기록.md`에 편집기에서 적습니다. 「학생이 정할 것」의 지점마다 고른 것과 근거 줄을 적습니다. 다 적으면 AI에게는 파일을 바꾸지 말고 내가 적은 것을 되짚게만 합니다.
5. **적재 계획 검토** — 대상과 관계를 어떤 문장으로 어떤 순서로 넣을지 AI의 계획을 받아 검토합니다. 스키마의 ID와 관계 방향이 그래프의 노드 · 관계로 어떻게 옮겨지는지 짚습니다. 아직 파일을 만들지 않습니다.
6. **구현 ① 적재하기** — 모델 파일의 대상과 관계를 랩 DB에 넣는 적재문(또는 적재 코드)을 `결과/`에 만들고 실행합니다.
7. **같은 적재 다시 실행** — 같은 적재를 한 번 더 실행하고 종류별 개수를 첫 실행과 비교합니다.
8. **구현 ② 사용 설비와 공급 조건 조회** — 품번 하나를 받아 그 부품을 쓰는 설비 · 구성 요소와 공급사별 공급 조건(승인 상태 · 출처 포함)을 돌려주는 조회문을 `결과/query.cypher`에 만들고 실행합니다.
9. **구현 ③ 다른 표기와 없는 품번 구별** — 예전 품번 · 다른 표기로 물어도 같은 부품을 찾고, 이름이 비슷한 다른 품번과 원자료에 없는 품번을 구별해 돌려주게 조회를 고치고 실행합니다.
10. **저장하고 다시 열기** — 적재 · 조회 파일과 검증 기록을 저장하고, VS Code에서 폴더를 닫았다 다시 연 뒤 랩 DB를 다시 켜고 9단계 조회를 다시 실행합니다. 기록 끝에 기준일 · 저장 시점 · 확인하지 못한 점을 적습니다.

이 순서는 바이브 코딩 일곱 단계 — 파일을 바꾸지 않고 파악 → 요구와 기대 답을 내 말로 → 계획 검토 → 작게 구현 → 원자료와 대조 → 고침 → 저장하고 다시 열기 — 를 따릅니다.

요청에 파일 이름을 쓸 때는 `결과/schema.json`처럼 백틱(`)으로 감쌉니다. 채팅 입력이 밑줄(_)을 서식으로 바꾸기 때문입니다.

## 확인

확인할 사례의 종류(어느 행이 해당하는지는 원자료에서 직접 찾습니다):

- 세 설비가 함께 쓰는 부품
- 비슷한 이름의 다른 품번
- 예전 품번 · 다른 표기
- 원자료에 없는 품번
- 비승인 · 조건이 붙은 공급사
- 공급사 이름 표기(견적표 · 승인 목록)
- 같은 적재 두 번

실행 명령:

```
python lab_db.py
(적재 · 조회문은 열린 Neo4j Browser에서 실행하거나, 만든 코드로 실행합니다)
```

바뀐 파일 확인: AI가 단계를 마칠 때마다 바뀐 파일 목록을 봅니다. `입력/`(원자료 포함)이 바뀌지 않았는지, 요청하지 않은 파일이 생기지 않았는지 확인합니다. 편집 승인 창에서는 경로가 `결과/` 아래일 때만 허용합니다.

## 완료 판정

형식 검사나 실행 성공만으로 완료하지 않습니다. 질문마다 원자료에서 먼저 적은 기대 답과 실제 조회 결과가 맞고, 같은 적재를 다시 해도 개수가 같으며, 「정한 것」마다 근거 줄과 그 선택으로 바뀌는 답을 설명할 수 있으면 완료입니다. 고친 점과 확인하지 못한 점은 `결과/검증_기록.md`에 짧게 남깁니다.

## 저장과 다음 실습

적재 · 조회 파일과 `검증_기록.md`를 함께 보관합니다. 기록에는 반영한 자료의 기준일을 적습니다. 다음 실습 「작업 기준의 복합 조건과 예외를 조치 조건표로 표현하기」는 제공된 자료로 시작하므로 이 결과는 참고로 보관합니다. 재부팅 전에 이 실습 폴더를 USB 또는 개인 클라우드에 복사합니다. 자동으로 되살려 주지 않습니다.
