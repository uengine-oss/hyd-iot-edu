부품의 사용 설비와 공급 정보를 조회하는 그래프 구현하기

설비 · 부품 · 공급 모델을 이 폴더 전용 그래프 DB에 적재하고, 부품의 사용 설비와 공급 조건을 돌려주는 조회문을 만들어 원자료와 대조합니다. 다시 적재해도 개수가 같은지 확인합니다. 진행은 파일을 바꾸지 않고 자료 파악 → 요구와 기대 답 정하기 → 계획 검토 → 기능 하나씩 구현하며 원자료와 대조 → 저장하고 다시 열기 순서입니다.

01 폴더와 출발점 확인

「설비·부품·공급 정보를 연결하는 온톨로지 설계하기」에서는 부품마다 쓰는 설비와 공급사별 조건을 모델에 넣었습니다. 이번에는 제공된 설비 · 부품 · 공급 모델(또는 내가 만든 모델)을 이 폴더 전용 랩 DB(그래프 DB)에 적재하고, 질문마다 조회문을 만들어 원자료와 대조합니다. 스키마의 ID와 관계 방향이 그래프의 노드 · 관계로 어떻게 옮겨지는지 직접 봅니다.

조회가 돌려준 공급 조건을 구매 담당이 믿고 쓰려면 승인되지 않은 공급사가 승인된 것처럼 섞이지 않고 값마다 출처가 따라와야 합니다. 이 조회는 공급사를 골라 주지 않습니다. 고르는 사람이 볼 정보를 돌려줍니다. 그래프에 넣은 자료는 한 번으로 끝나지 않습니다. 수정본이 들어오면 전체를 지우고 다시 넣지 않고 필요한 대상만 고쳐야 다른 곳에서 쓰던 ID와 연결이 그대로 남고, 같은 적재를 다시 실행해도 대상이 늘지 않아야 믿고 다시 돌릴 수 있습니다.

과정은 온톨로지 → 에이전트 → 프로세스 순서로 올라갑니다. 이 실습은 첫 단계인 온톨로지의 구현과 검증 — 설계한 모델을 그래프 DB에 옮기고, 질문에 실제로 답하는지 원자료와 대조하는 일 — 를 맡습니다.

이 답은 보전 · 구매 담당이 지금 가동하는 설비의 예비품 수요와 공급사별 조건을 볼 때 씁니다. 고르는 것은 구매 담당입니다.

받기 「실습 시작」 도구에서 과정 → 회차 → 실습을 고르고 새로 시작(이어서 할 때는 이전 작업 열기)을 누르면 이 폴더와 가이드가 열립니다. 받기에 실패하면 다시 시도하고, 안 되면 수동 ZIP을 풀어 VS Code의 파일 → 폴더 열기(File → Open Folder)로 엽니다.

필요한 것 VS Code와 Python, 로그인해 둔 Codex 또는 GitHub Copilot, 랩 DB를 켤 Docker Desktop.

받은 폴더 VS Code 왼쪽 탐색기에 이렇게 보입니다.

해결할 질문

  1. 세 설비가 함께 쓰는 펌프 축 씰 키트를 어느 설비 · 구성 요소에서 쓰고, 기준일의 세 공급 조건(승인 여부 · 단가 · 불량률 · 납기)은 무엇이며 각 값은 어느 파일 · 어느 날짜 자료에서 왔는가?
  2. 이름이 비슷한 다른 품번, 예전 품번이나 다른 표기, 원자료에 없는 품번으로 물으면 결과가 서로 구별되는가? 비승인 공급사는 승인 상태와 함께 구별되는가?
  3. 견적 납기와 지난 입고의 실측 납기는 공급사별로 얼마나 다른가?
  4. 수정본을 반영한 뒤에도 같은 ID가 유지되고, 같은 적재를 다시 실행해도 대상과 관계가 늘지 않는가?

말 풀이 적재는 모델 파일의 대상과 관계를 그래프 DB에 넣는 일이고, 수정본은 기준일 뒤 담당자들이 고친 줄만 모은 자료입니다.

내 모델을 쓸 때: 제공 입력은 그대로 두고 내 schema.json · graph.json을 결과/내_모델/에 복사해 씁니다. 만든 날짜 · 질문 · 파일 형식 · ID가 이번 입력과 맞는지 먼저 보고, 관계 이름이나 방향이 다르면 내 모델의 정의로 조회합니다. 내 모델이 없어도 제공된 모델로 끝까지 할 수 있습니다.

왜 하는가 만들기 전에 무엇이 주어졌고 무엇을 만들어야 하는지 알아야 AI에게도 같은 출발점을 말할 수 있습니다. 이 답을 누가 어디에 쓰는지에 따라 무엇을 하나로 보고 무엇을 따로 둘지가 달라지므로, 쓰는 사람도 여기서 확인합니다. 제공된 모델과 내가 만든 모델 가운데 무엇을 쓸지 여기서 정해야 뒤에서 개수를 견줄 기준이 하나로 정해집니다.

02 랩 DB 켜기

왜 하는가 이 실습의 적재 · 조회는 이 폴더에만 딸린 그래프 DB에서 합니다. 포털 DB와 떨어져 있어 여러 번 넣고 지워도 포털에 영향이 없고, 처음에 비어 있는 것을 확인해 두어야 뒤에서 센 개수가 모두 이번에 넣은 것임을 믿을 수 있습니다.

할 일 터미널에서 python lab_db.py를 실행해 이 폴더 전용 랩 DB를 켜고, 열린 Neo4j Browser에 연결합니다.

터미널 → 새 터미널(Terminal → New Terminal)로 이 실습 폴더에서 터미널을 엽니다. 명령은 직접 치지 말고 블록의 복사로 붙여 넣습니다(손으로 옮기면 오타가 납니다). 오류로 멈추면 명령과 출력 전문을 AI 채팅에 보내 까닭부터 묻습니다.

명령 전에 Docker Desktop을 켜 둡니다.

정하거나 물을 것 출력된 주소가 127.0.0.1의 이 폴더 전용 주소인지 확인합니다.

명령

터미널 명령 · PowerShell · 이 실습 폴더에서

python lab_db.py

「랩 DB 준비 완료」 뒤 열린 연결 창에서 Protocol bolt://, Connection URL은 출력의 127.0.0.1:포트, Database user neo4j, Password는 비운 채(이 PC 안에서만 열리는 DB라 비밀번호가 없습니다) Connect를 누릅니다. Browser 입력 칸에 Cypher를 붙여 넣어 실행하고 Table로 원자료와 견줍니다.

개수 조회 종류별 노드 수와 관계 수를 세는 두 질의입니다. 뒤에서 적재 · 수정 뒤 개수를 견줄 때도 이 둘을 씁니다.

Neo4j Browser 질의 · 위쪽 입력 칸에서

MATCH (n) RETURN labels(n)[0] AS 종류, count(*) AS 개수 ORDER BY 종류

Neo4j Browser 질의 · 위쪽 입력 칸에서

MATCH ()-[r]->() RETURN type(r) AS 관계, count(*) AS 개수 ORDER BY 관계

막히면 「랩 DB 준비 확인 필요:」 줄이 나오면 Docker Desktop이 켜져 있는지 보고 다시 실행합니다.

판단할 증거 「랩 DB 준비 완료」와 주소가 나왔고, 처음 켰을 때 Browser의 두 개수 조회가 빈 결과(이 폴더 전용 DB가 아직 비어 있음)를 보입니다.
다를 때 처음 켰는데 개수 조회에 대상이 보이면 연결한 주소가 터미널 출력의 주소와 같은지 봅니다. 이전 작업을 연 경우에는 전에 이 폴더에서 넣은 대상의 개수가 보이는 것이 맞습니다.
증거를 확인한 뒤 다음 단계로 갑니다.

03 파일을 바꾸지 않고 자료 파악

왜 하는가 적재가 맞았는지는 모델 파일에 무엇이 몇 개 있는지를 먼저 알아야 셀 수 있습니다. 수정본은 줄마다 그래프의 어느 대상에 닿는지 알아야 필요한 곳만 고칠 수 있습니다. 입고 이력도 미리 보아 두어야 실측 납기를 셀 때 무엇을 한 번으로 셀지 정할 수 있습니다.

할 일 AI에게 파일을 바꾸지 말고, 입력/graph.json에 어떤 종류의 대상과 관계가 몇 개 있는지와 수정본의 줄마다 그래프의 어느 대상을 가리키는지 파일 · 줄로 짚어 달라고 합니다. 짚은 줄을 직접 엽니다.

Codex는 왼쪽 활동 표시줄의 Codex 아이콘으로, GitHub Copilot은 같은 채팅 창의 Chat 탭으로 엽니다. 답에 나온 줄은 편집기에서 직접 열어 읽고, 「완료」라는 말 대신 실제 파일과 출력으로 확인합니다.

편집 승인 창(Allow ChatGPT to edit the following file?)에서는 경로가 결과/ 아래인 요청한 변경만 Allow once, 그 밖은 Deny를 누릅니다.

정하거나 물을 것 수정본에서 무엇이 바뀌는지(이름 · 상태 · 값 · 줄 삭제), 제공된 모델의 ID가 무엇으로 지어졌는지 묻습니다. 입고 이력에서 한 발주가 여러 줄인 곳이 있는지도 묻습니다.

요청에 담을 것 — AI에게 그대로 보내는 글이 아니라 내 요청을 짤 때 채울 다섯 가지

아래 다섯 가지를 내 말로 채워 요청을 짭니다. 값은 원자료에서 내가 찾습니다.

목적적재할 모델과 수정본을 파악한다. 아직 아무것도 만들지 않는다.
입력입력/schema.json · 입력/graph.json · 입력/자료_검토.md, 입력/자료_변경분/2026-10-20_수정본/, 입력/자료/입고_이력.csv
지킬 것파일을 바꾸지 않는다. 해석보다 파일 · 줄 번호와 개수를 먼저 받는다.
결과의 꼴종류별 대상 수 · 관계 수 표, 수정본 줄마다 「가리키는 대상 · 바뀌는 것」 목록
확인 방법개수 몇 개와 수정본 줄 몇 개를 내가 직접 파일에서 세어 본다

명령 없음 — 이 단계는 탐색기 · 편집기 · AI 채팅에서 합니다.

판단할 증거 AI가 짚은 줄을 열었을 때 그 내용이 실제로 있습니다. 편집 승인 창이 뜨지 않았고 AI의 답에 바꾼 파일이 없습니다. 종류별 대상 수와 수정본의 줄 수를 내 말로 말할 수 있습니다.
다를 때 AI가 센 개수와 내가 센 개수가 다르면 그 종류의 대상을 목록으로 보여 달라고 해 어디서 달라졌는지 찾습니다. 편집 승인 창이 떴다면 Deny를 누르고, 이 단계는 파일을 바꾸지 않는 단계라고 다시 알립니다.
증거를 확인한 뒤 다음 단계로 갑니다.

04 요구와 기대 답 정하기

왜 하는가 기대 답을 내가 원자료에서 먼저 찾아 적어 두어야, 뒤에서 AI가 만든 결과가 맞는지 견줄 기준이 생깁니다. AI가 낸 답을 기대 답으로 옮기면 틀린 결과도 맞아 보입니다. 원자료만으로 하나로 정해지지 않는 지점은 이 답을 쓰는 사람의 일을 보고 내가 정해야 같은 질문에 늘 같은 답이 나옵니다.

할 일 질문 · 이 답을 쓰는 사람 · 지킬 조건과, 펌프 축 씰 키트의 사용 설비와 세 공급 조건, 공급사 하나의 지난 발주별 납기, 수정본 반영 뒤 달라져야 할 것을 원자료에서 직접 찾아 기대 답으로 결과/검증_기록.md에 적습니다. 「학생이 정할 것」의 지점마다 고른 것과 근거 줄을 적습니다.

고친 파일은 Ctrl+S로 저장합니다(탭 이름 옆 ●가 사라지면 저장됨).

학생이 정할 것 — 지점의 종류 원자료만으로는 하나로 정해지지 않아, 근거를 찾아 내가 정해야 결과를 업무에 쓸 수 있는 지점이 있습니다. 이번 자료에는 아래 종류의 지점이 있습니다. 어느 행 · 어느 절이 해당하는지는 탐색에서 직접 찾고, 지점마다 고른 것 · 근거(파일 · 줄) · 그 선택으로 바뀌는 답을 결과/검증_기록.md 「정한 것」 표에 적습니다.

왜 하는가 견적의 납기는 공급사가 약속한 계획 값이고, 실측 납기는 발주일부터 실제로 들어온 날까지 센 관측 값입니다. 둘을 나란히 보아야 약속과 실제가 얼마나 다른지 압니다. 실측 납기는 지난 입고 기록에서 세는 값이라 그래프에 넣지 않고 코드로 셉니다.

할 일 입력/자료/입고_이력.csv에서 펌프 축 씰 키트의 공급사별 실측 납기를 세는 코드를 결과/에 만들고 실행해, 견적 납기와 나란히 놓습니다.

정하거나 물을 것 이 단계의 결과는 내 결정에 따라 달라집니다. 나눠 들어온 발주와 아직 다 들어오지 않은 발주에 「정한 것」 표의 결정이 그대로 적용됐는지 묻습니다.

11 구현 ⑤ 수정본 반영하기

왜 하는가 전체를 지우고 다시 넣으면 다른 곳에서 이 ID를 가리키던 연결이 끊깁니다. 있는 대상의 값은 ID로 찾아 SET으로 고치고, DETACH DELETE는 대상과 그 관계를 함께 지웁니다. 지우기 전에는 그 대상에 걸린 다른 대상을 먼저 조회해야, 실제로 있는 대상까지 함께 사라지지 않습니다.

할 일 수정본의 줄마다 필요한 대상 · 관계만 고치는 수정문(또는 수정 코드)을 결과/에 만들고 실행합니다.

정하거나 물을 것 이 단계의 결과는 내 결정에 따라 달라집니다. 상태가 바뀐 설비를 「정한 것」 표의 결정대로 반영했는지, 「삭제」 줄이 그래프에서 무엇을 바꿨는지 묻습니다. AI가 결정을 대신 정하려 하면 돌려보내고 내 선택과 근거를 다시 말합니다.
