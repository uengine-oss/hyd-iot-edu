# 촬영 — 여러 도구 공통

규칙은 [영상](../../지침/영상.md)에 있고, 도구마다 다른 길, 값, 함정은 그 도구의 `촬영준비.md`에 있다. 이 문서에는 둘 이상의 도구에 똑같이 해당하는 것만 둔다. 새로 뚫은 길, 새 함정, 바뀐 값은 그 자리의 문장을 고쳐 쓰고, 날짜나 경위는 적지 않는다.

## 길 — ego로 찍는 도구(ARROWS · Notion · Neo4j · 웹 VS Code · 포털 지식 지도)

1. 준비 — ego lite 설치와 로그인은 사용자가 한다. 설치된 `ego-browser skill`의 출력을 끝까지 읽는다(API는 설치된 버전의 설명을 따른다). 공간은 번호가 바뀌므로 이름으로 `taskSpace(<이름>)`처럼 부른다. 다른 세션과 같은 공간이나 같은 페이지를 함께 쓰지 않고, 다른 공간으로 옮겨 다니지 않는다. 앞에 있는 탭에서만 프레임이 오므로, ego 창을 최소화하지 않고 녹화 탭을 앞에 둔다.
2. 시작 화면 — 시작값은 프레임 1920×1080, UI 배율 150%다. 대표 화면을 실제 녹화 프레임으로 받아 글자가 읽히는지 본다. 이전 시연의 흔적을 화면에서 정리하고(DB 데이터를 지우는 것이 아니다) 첫 프레임을 본다. 리허설이 앱에 남긴 상태(최근 사용 색 · 서식, 이미 적용된 설정, 만든 노드 · 인스턴스, 업데이트 막대)가 처음 하는 학생의 화면과 다르면 녹화 전에 없애고, 없앨 수 없으면 대본이 그 차이를 짚는다(영상 V-2 — Notion 학습노트는 리허설의 파란 배경이 남아 새 콜아웃이 처음부터 파란색으로 찍혔다). 촬영 전용 문서나 페이지 하나에서 이어 쓰고, 다시 시도할 때마다 사본을 늘리거나 최종본을 덮어쓰지 않는다. 물리 마우스, 키보드, 전경 창은 쓰지 않는다.
3. 스크립트 부르기 — 스크립트는 UTF-8 `.mjs`로 쓰고, `node --check`로 문법을 본 뒤 `ego-browser nodejs -e "await import('file:///<절대경로>.mjs?<판>')" < /dev/null`로 부른다. 같은 주소는 다시 실행되지 않으므로 부를 때마다 `?<판>` 표시를 바꾼다. 도구의 `run.sh`가 이 부르기와 함께 바쁨 검사(`BUSY:`), 부하 검사(화상회의 여부, 여유 메모리 3 GB — 모자라면 Notion은 멈추고 VS Code는 경고만 한다), 시간 초과(`TMO`) 정리를 한다.
4. 녹화 — 스크립트마다 시작할 때 `Emulation.setDeviceMetricsOverride`로 도구의 화면 값을 건다(한 도구 안에서는 값을 바꾸지 않는다). `Page.startScreencast`의 프레임은 받는 즉시 저장하고 ACK한다. 조작 리듬은 도구가 맞춘다.
   - 모든 ego 호출은 직렬 큐 하나로 보낸다.
   - 표시 포인터(SVG를 `element.animate`로 움직임)와 실제 입력(같은 경로를 단계별 `mouse.move`)이 함께 움직이고, 실제 입력이 끝날 때까지 화살표를 목표에 고정한다.
   - 움직이는 대상은 150ms 간격으로 두 번 읽어 위치가 같을 때 출발한다.
   - 조작은 행동 문장이 끝나기 약 250ms 전에 한다. 다음 음성은 행동이 끝난 뒤 녹화 제어의 `gap`만큼 쉬고 시작하며, 그 값은 영상 V-14의 쉼이다(조작 직후 같은 문맥의 말만 `gap` 옵션으로 줄인다).
5. 대상 찾기 — 웹 페이지(Notion, 포털, Neo4j 입력칸)에서는 보이는 DOM 요소를 정확한 글로 찾고, 클릭 직전에 위치를 다시 읽는다. 화면 밖 요소를 고정 좌표로 누르지 않는다. 캔버스(ARROWS, Neo4j 그래프, bpmn.io)에서는 그리기 함수를 감싸 대상 위치를 기록하고, 배치 순서는 녹화 전에 계산해 큐에 고정한다.
6. 사용자와 주고받기 — 사용자가 배치나 입력을 해야 하면 녹화를 멈추고 `task.handOff()` → 사용자 조작 → `takeOverTaskSpace(<번호>)` 순서로 넘겼다가 되찾는다. 사용자가 만든 결과는 앱의 저장 데이터로 읽는다. 「Control of this task space is with the user」가 나오면 사용자에게 「계속」을 받은 뒤에 되찾는다.
7. 상태 맞추기 — 이전 구간의 끝 상태는 저장해 둔 `end-state.json`의 데이터를 가져와 맞춘다. 실행 취소는 마지막 수단이다. 포커스와 글자 단위 기록 때문에 다른 내용까지 잃을 수 있다.
8. 기록 — 구간마다 `end-state.json`과 `timing.json`을 남긴다. 녹화 원본은 그 도구 `config.json`의 `work` 폴더(`작업/촬영/<도구>/`, 이 PC 전용)에 둔다. take(녹화 한 번의 결과)는 매번 새 이름으로 만들고, 실패한 take는 남기되 합성에 쓰지 않는다. 합성 출력의 이름도 매번 새로 짓는다.

## 함정

- 명령이 출력 없이 멈출 때가 있다. 명령을 끊어도 스크립트는 ego `NodeService` 안에서 계속 돈다. 그 utility 프로세스만 끄고(창과 탭은 그대로 둔다), 스크립트가 실제로 실행됐는지는 앱 상태로 본다.
- 스크립트가 조용히 멈추거나, 고친 파일이 반영되지 않거나, 셸 안에서만 멈추는 원인은 셋 중 하나다. 문법 오류(`node --check`로 본다), 같은 `file:///` 주소의 재사용, 입력 대기(`< /dev/null`을 붙인다).
- 해상도와 배율이 다음 호출에서 풀린다. 그러니 모든 스크립트의 시작에서 metrics를 건다. 1080p인데 글자가 작으면 UI 배율, 대상 확대, 패널 폭을 고친다. 압축 품질 문제가 아니다.
- 커서가 움직이는 중에 프레임이 비거나 휘청이면 큐 점유, 녹화 중 무거운 작업, CPU 경쟁을 살핀다. fps나 복제 프레임으로 숨기지 않는다.
- 1~2초 정지나 시간 초과가 갑자기 되풀이되면 화상회의나 메모리 부족이 원인이다. 녹화를 멈추고, 부하가 사라진 뒤 멈춘 큐부터 다시 찍는다.
- 앞 구간이 실패했는데 다음 구간이 돌아 버린 적이 있다. 구간을 이어 찍을 때는 실패하면 멈추는 `chain.sh`만 쓴다.
- 합성 영상이 내레이션보다 짧아 끝인사가 잘린 적이 있다. concat의 끝 줄에도 같은 framerate를 주고, 합성 뒤 끝 시각을 잰다. 보정 이미지 뒤에서 프레임이 빠지는 것은 concat에 이미지 코덱을 섞었기 때문이니 섞지 않는다.
- EPERM으로 상태 파일이 충돌하면 같은 공간에서 두 번 실행한 것이다. 사용자 클릭이 먹지 않으면 에이전트가 공간을 쥐고 있는 것이니 `handOff`한다.
- 시간 초과로 끊긴 명령이 ego 안에서 계속 돌아 상태를 바꾼 적이 있다. 명령을 끊은 뒤에는 저장 데이터로 상태를 확인하고 찍는다.
- `join.py`는 인자를 `:`로 나눠 조각과 자막을 읽으므로, Windows 경로의 드라이브 문자(`D:`)가 들어가면 멈춘다. 드라이브 문자 없는 상대 경로로 넘긴다.
