# 2회차 VS Code 실습 영상 세 편(06-1 · 06-2 · 07) — 장 차례

이론 2회차가 확정되어 듣는 차례가 바뀌었습니다. 학생은 이 차례로 듣습니다.

이론(클래스와 인스턴스) → 포털에서 지식 지도 읽기 → 이론(스키마 설계) → **06-1 · 06-2** → 이론(그래프 DB와 Cypher) → Neo4j에서 쿼리 돌려 보기 → **07** → 복습과 퀴즈

그래서 06-1 · 06-2에서는 그래프 DB · 쿼리 · Cypher를 이미 아는 것처럼 말하지 않고, 07은 그것을 막 배우고 직접 돌려 본 학생에게 말합니다. 장 차례는 학생이 옆에 펴 두는 실습 안내 문서의 단계 차례와 같습니다.

## 06-1 VS Code 랩 시작하기

| 장 | 하는 것 | 이 장에서 학생이 알게 되는 것 |
|---|---|---|
| 1. 여는 말 | 목표 → 4회차까지 이어지는 차례 → 한 상황을 예로 잡기 → 그 상황 → 왜 이것부터 → 오늘의 세 걸음 (견본 장면 1) | 지금부터 만드는 것은 포털에서 읽던 그 지식 지도의 바탕이고, 문서를 넣는 일보다 설비와 스키마를 세우는 일이 먼저다 |
| 2. 폴더 받아 열기 | 자료 받기 → 압축 풀기 → VS Code로 폴더 열기 → 신뢰(직접 녹화하시는 장면) | 랩마다 똑같이 하는 시작 순서 |
| 3. VS Code 화면과 랩 폴더 | 쓰는 곳 네 군데, 폴더 안의 표 다섯 개와 메모, 미리 만들어 둔 코드와 비어 있는 곳 | 글자를 넣는 곳은 터미널과 Codex 두 곳뿐이고, 코드는 읽을 줄 몰라도 된다. 표의 가로 한 줄을 행이라고 부른다 |
| 4. 첫 실행 | 터미널에 `python run.py` → 결과 화면에서 표마다 행 수 확인 | 받은 자료를 원자료라고 부르고, 무엇을 만들든 맞는지는 이 원자료와 견줘서 본다 |
| 5. 바이브 코딩과 Codex | 말로 시키고 결과는 내가 판단한다, 우리는 이것을 Codex로 한다 (견본 장면 2 앞부분) | 바이브 코딩이 무엇이고 Codex가 무엇인지 |
| 6. 막연하게 부탁해 보기 | 「현장 메모 정리해 줘」를 보내고 답을 읽음 (견본 장면 2) | 뜻을 말하지 않으면 AI가 대신 고르고, 나에게는 그 답을 판단할 기준이 없다(블랙박스) |
| 7. AI를 어디에 두고 일하나 | 회사에 새로 들어온 사람이 물어 가며 일을 파악하는 모습에 견줌 | 처음에는 AI에게 물어 가며 배우고, 익숙해지면 내가 방향을 잡고 판단한다 |
| 8. 갖춰서 다시 부탁하기 | 무엇을 하려는지 · 볼 자료 · 지킬 것 · 답의 꼴(예로 든 행과 개수)을 갖춰 새 대화로 보냄 | 부탁에 무엇이 들어가야 답을 판단할 수 있게 되는지 |
| 9. 답을 원자료와 맞춰 보기 | 답의 행 수를 4장의 숫자와 견주고, 답이 가리킨 행을 직접 열어 봄. 표끼리 이어지는 칸(설비 코드), 설비 네 대에 똑같이 있는 TS1, 같은 장치의 다른 이름 | AI의 답은 대체로 맞지만 틀린 곳이 섞여 나오므로 몇 군데는 직접 열어 본다. 이론에서 본 공통 식별자 · 이름이 같은 인스턴스 · 다른 이름 · 의미 불일치가 실제 자료에 그대로 있다 |
| 10. 앞으로 랩은 이 차례로 | 방금 한 일을 되짚어 요령과 일하는 차례로 묶음 | 파악 → 기대 답 → 따져 보고 결정 → 작게 만들기 → 원자료와 대조 → 고치기 → 다시 열어 확인. 앞으로 모든 랩을 이 차례로 한다 |
| 11. 폴더가 이렇게 나뉜 까닭 | 미리 채워 둔 코드와 비워 둔 곳, AI가 지킬 규칙을 적은 파일(AGENTS.md) | 누가 해도 같은 일은 채워 두었고 사람이 판단할 곳만 비워 두었다. 6장의 답이 그럴듯했던 것도 이 규칙 파일 덕분이다 |
| 12. 맺음 | 찾아 둔 엇갈림(TS1, 펌프 두 행, 다르게 적힌 이름)을 다시 짚음 | 돌아갔다고 끝이 아니라 무엇을 왜 했는지 내 말로 말할 수 있어야 끝이다. 찾아 둔 엇갈림이 곧 스키마에서 정할 거리다 |

- 3 · 4장을 둘로 둔 까닭: 화면 익히기와 첫 실행은 처음 보는 것이 몰리는 자리라 한 번에 하나씩 갑니다.
- 8 · 9장을 둘로 둔 까닭: 「어떻게 부탁하나」와 「받은 답을 어떻게 믿나」가 이 편의 중심이라 따로 세웁니다.

## 06-2 온톨로지 설계

| 장 | 하는 것 (안내 문서 단계) | 이 장에서 학생이 알게 되는 것 |
|---|---|---|
| 1. 여는 말과 설계 흐름 그림 | 이론에서 배운 다섯 걸음을 펜으로 그림: 역량 질문 → 질문의 낱말을 클래스 · 속성 · 관계로 → 정의를 표에 적기 → 넣기 전 검증 → 넣어 물어보고 막히면 정의 고치기 | 오늘은 이 다섯 걸음을 진짜 자료로 밟는다. 장이 바뀔 때마다 이 그림에서 지금 자리를 짚는다 |
| 2. 역량 질문과 기대 답 (03) | 메모의 「알고 싶은 것」 세 가지를 역량 질문으로 → 나와야 할 답을 먼저 적음 | 결과를 본 뒤에 답을 정하면 틀린 결과도 맞아 보이므로 기대 답을 먼저 적는다(시험지와 답안지에 견주는 말은 여기서 한 번) |
| 3. 클래스 · 식별자 · 관계 방향 · 카디널리티 (04) | 질문의 낱말에서 클래스 다섯 → 설비 네 대에 똑같이 있는 TS1을 무엇으로 구별할지 → 관계를 어느 쪽에서 어느 쪽으로 이을지 → 몇 개까지 이어지는지 → 표 두 장에 적고 돌려 봄 | 무엇으로 구별할지(이름이 겹치면 설비 코드를 붙여 식별자를 짓는다)와 어느 쪽으로 이을지(문장으로 읽어 주어가 되는 쪽에서 나간다). 이 표 두 장이 이론에서 본 「표 한 장」이다 |
| 4. 고르기 ①: 바꾼 펌프를 따로 셀까 (05) | 식별자가 겹친 두 행을 열어 봄 → 두 길의 결과를 Codex에게 받음 → 내 이유로 고르고 적어 둠 (견본 장면 3) | 무엇을 하나로 셀지는 답할 질문이 정한다. 다른 쪽을 골라도 틀리지 않다 |
| 5. 고르기 ②: 온도를 하나로 묶을까 (06) | 모두 기름 온도인데 재는 곳이 다른 센서들 → 묶을 때와 나눌 때 질문의 답이 어떻게 달라지는지 받음 → 고르고, Codex가 채운 규칙을 열어 봄 | 이름이 같아도 다른 것일 수 있고 이름이 달라도 같은 것일 수 있다. 어디까지를 같은 것으로 볼지를 한 문장으로 정해 둬야 누가 넣어도 같아진다 |
| 6. 여러 가지로 적힌 품번을 하나로 (07) | 명령 하나로 품번을 이음 → 다르게 적힌 품번이 사내 품번 하나로 모였는지 봄 → 모델 파일 두 개가 생김 | 식별자는 하나로 두고 나머지 표기는 다른 이름으로 남긴다. 파일 두 개가 이론의 스키마와 인스턴스 데이터다 |
| 7. 기대 답과 맞춰 보기 (08 앞) | 처음에 고르지 않은 설비 · 예전 품번 · 원자료에 없는 품번도 기대 답에 먼저 더하고 맞춰 봄 | 처음 고른 예에서만 맞는 것일 수 있으므로 다른 값으로도 물어본다. 결과에 맞추려고 기대 답을 바꾸지 않는다 |
| 8. 넣기 전 검증 (08 뒤) | 구조 검사를 돌림 | 이론에서 배운 검증이 실제로 보는 것(빠진 필수 속성, 관계의 양 끝, 카디널리티를 넘은 곳). 검증을 통과해도 답이 맞는지는 7장처럼 따로 물어봐야 안다 |
| 9. 맺음 (09) | 폴더를 닫았다 다시 열어 같은 답인지 봄 → 무엇을 왜 골랐는지 내 말로 | 다시 열어도 같아야 제대로 남은 것이다. 이렇게 만든 것을 어디에 담고 어떻게 물어 꺼내는지는 이어지는 이론에서 배운다 |

- 7 · 8장을 둘로 둔 까닭: 이론이 「검증」을 넣기 전에 기록을 스키마와 맞춰 보는 일로 가르쳤으므로, 기대 답과 맞춰 보는 일(7장)과 검증(8장)을 한 이름으로 섞지 않습니다(아래 「정해 주실 것」 2).

## 07 그래프 구현과 검증

| 장 | 하는 것 (안내 문서 단계) | 이 장에서 학생이 알게 되는 것 |
|---|---|---|
| 1. 여는 말 | Neo4j에서 한 일을 한 마디로 받고 → 이번 일 세 가지 → 이번 편의 「검증」이 무엇인지 (견본 장면 4) | 설계한 것을 넣고, 묻고, 바뀐 것만 고친다. 쿼리는 AI가 쓰지만 무엇을 쓰게 할지 정하고 읽어서 확인하는 것은 나다 |
| 2. 폴더와 랩 DB (01 · 02) | 첫 실행 → Docker Desktop을 켜고 랩 DB를 띄움 | 랩 DB는 이 폴더에서만 쓰는 그래프 DB이고 아직 비어 있다 |
| 3. 넣을 모델 살피기 (03) | 종류마다 몇 개인지, 관계는 어느 쪽으로 가는지, 무엇으로 구별했는지를 Codex에게 물음 | 설계 때의 클래스가 레이블로, 인스턴스가 노드로, 관계가 화살표로 들어간다. 지금 받아 둔 개수가 넣은 뒤에 맞춰 볼 기준이다 |
| 4. 역량 질문과 기대 답 (04) | 이번 질문 세 가지의 기대 답을 먼저 적음. 원자료에 없는 품번으로 물으면 무엇이 나와야 하는지도 미리 정함 | 쿼리를 쓰기 전에 답부터 정한다. 「없다」를 어떻게 답할지도 정해 둘 일이다 |
| 5. 고르기: 쓰지 않기로 한 설비를 남길까 지울까 (05) | 두 길의 결과를 받고 내 이유로 고름 | 노드를 지우면 거기 붙은 관계와 그 길로 나오던 답도 함께 빠진다 |
| 6. 유일 제약 (06) **— 새로 들어온 장** | 식별자마다 유일 제약을 거는 쿼리를 받아 읽고 돌림 (견본 장면 5) | 스키마에 적은 약속은 DB가 저절로 지켜 주지 않으므로 넣기 전에 걸어 둔다. 걸고 나면 같은 식별자를 다시 만들 때 DB가 거절한다 |
| 7. 넣기와 다시 넣기 (07) | 넣는 쿼리를 읽고 돌림 → 한 번 더 넣어 개수가 그대로인지 봄 | 유일 제약이 걸려 있어서 MERGE로 넣는다. MERGE의 패턴에는 식별자만 적고 나머지 값은 처음 만들 때만 적는다. 수백 개를 쿼리 하나로 넣는 꼴은 여기서 처음 푼다 |
| 8. 질문 ①: 구성 요소마다 붙은 센서 (08) | 쿼리를 읽고 돌려 기대 답과 맞춤 | 설계 때 정한 화살표 방향 그대로 패턴을 적는다. 질문은 하나씩 물어야 틀린 곳을 바로 안다 |
| 9. 질문 ②: 구성 요소마다 교체 부품 (09) | 질문 ①과 달라진 줄만 읽고 돌림 | 같은 설비라도 묻는 것이 다르면 따라갈 관계가 달라진다. 부품이 없는 구성 요소도 답에서 빠지지 않게 찾는 꼴 |
| 10. 질문 ③: 다른 표기로 부품 찾기 (10) | 쿼리를 읽고 돌림. 없는 품번은 4장에서 정한 대로 나오는지 봄 | 어느 표기로 물어도 같은 부품이 나온다. 그냥 찾으면 「없는 것」과 「잘못 물은 것」이 똑같이 빈 결과가 된다 |
| 11. 바뀐 것만 고치기 (11) | 고친 뒤의 개수를 먼저 세고 → 식별자로 찾아 값만 고치는 쿼리를 읽고 돌림 | 전부 지우고 다시 넣지 않고 식별자로 찾아 바뀐 값만 고친다. 그래야 무엇이 달라졌는지 하나씩 견줄 수 있다 |
| 12. 포털의 지식 지도와 견주기 (12) | 내 그래프와 포털 지도를 나란히 봄 | 포털은 오일 쿨러를 하나로, 내 그래프는 설비마다 따로 셌다. 어느 쪽이 틀린 것이 아니라 답하려는 질문이 다르다 |
| 13. 맺음 (13) | 폴더를 다시 열어 같은 결과인지 보고, 그래프를 파일로 꺼냄 | 유일 제약과 MERGE가 저마다 무엇을 맡아서 다시 넣어도 늘지 않았는지 내 말로 말한다. AI가 쓴 쿼리를 읽을 줄 알아야 하는 까닭 |

- 6장을 넣은 자리: 이론이 「식별자에는 유일 제약을 걸고, 넣는 쿼리는 MERGE로 적는다」를 한 짝으로 가르쳤고 랩에도 그 걸음이 새로 생겼으므로, 넣기(7장) 바로 앞에 둡니다.
- 8 · 9 · 10장을 셋으로 둔 까닭: 안내 문서가 질문마다 한 단계이고, 질문마다 새로 배우는 쿼리 꼴이 하나씩 다릅니다.

## 지난번 차례에서 바뀐 곳
