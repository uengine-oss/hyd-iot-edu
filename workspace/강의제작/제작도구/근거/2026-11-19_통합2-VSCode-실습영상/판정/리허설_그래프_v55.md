## 05 → 06 → 07 (이번에 특히 본 곳)

- **06은 가이드와 힌트만으로 부탁할 말이 나왔다.** 「03단계에서 들은 식별자」 → 여섯 종류 모두 `id`(03 답에 있음), 「constraints.cypher에만」, 「이미 걸려 있으면 그대로」 → Codex가 `CREATE CONSTRAINT … IF NOT EXISTS FOR (n:종류) REQUIRE n.id IS UNIQUE;` 여섯 줄을 한 번에 냄. 「쿼리 한 줄을 내 말로」: 「그 종류의 노드는 id가 같은 것이 둘 있을 수 없다는 규칙을 DB에 걸고, 이미 있으면 새로 만들지 않는다.」
- **06 화면은 확인 글의 세 가지(자물쇠 · 제약 이름 · 모두 거절)를 그대로 보여 준다.** 「같은 식별자로 두 번 만들면 DB가 뭐라고 답하는지」는 카드의 영어 원문 칩이고, 바로 위 「→ DB가 거절」과 표의 「거절 — …」이 한국어로 받쳐 노베이스도 읽힌다. 힌트 「한 번 더 실행하면?」은 가이드에 두 번째 명령이 없지만, 다시 치면 표 「0(이미 걸려 있음)」으로 확인된다(가이드 밖 실행 1회).
- **05 → 06 연결**: 05는 명령 없이 결정 표만 채우고 끝나며, 06 「상황」의 「랩 DB는 아직 비어 있다」와 실제(노드 0)가 맞는다. 06에서 시험한 노드를 되돌려 남기지 않았다고 화면이 밝혀(「노드 0개 그대로」) 07 「랩 DB는 비어 있다」와도 맞는다.
- **06 → 07 연결**: 07 「상황」의 「CREATE로 넣는 쿼리는 두 번째 실행에서 DB가 거절해 오류로 멈춘다」가 06 화면의 「거절」과 이어져 MERGE를 고를 까닭이 된다. 07 힌트 세 줄(MERGE · 식별자 · 값은 처음 만들 때만)로 `MERGE (n:종류 {id: row.id}) ON CREATE SET n += row`가 나왔고, `load` · `repeat` 둘 다 한 번에 맞았다. 끝 질문 「유일 제약과 MERGE가 각각 무엇을 맡았나」에 내 말로 답할 수 있다: 유일 제약은 같은 id의 노드가 둘 생기는 것을 DB가 막고, MERGE는 id로 있는 노드를 찾아 없을 때만 만들어 다시 넣어도 늘지 않게 한다.

## 막힌 곳과 고칠 방향

1. **[결과 화면 · 08 그림] 「쿼리가 따라간 길」이 쿼리가 지나지 않은 길을 칠한다.** 질문 ①은 HAS_COMPONENT → MONITORED_BY만 따라가는데, 구성 요소 「이름」을 결과 열로 내자 그림이 USES_PART 선 17개와 HYD-02 · 03 · 04 · 07의 같은 이름 구성 요소 · 부품까지 「따라간 길」(주황)로 칠했다. 같은 쿼리의 구성 요소 열만 id로 바꿔 보니(학생 흐름 밖 시험 1회, 곧 되돌림) 이번엔 HAS_COMPONENT 7줄만 칠하고 MONITORED_BY(센서 쪽) 선은 하나도 칠하지 않았다. 즉 그림이 결과 값이 같은 노드를 골라 길을 잇는 듯하고, 이름이 여러 설비에 겹치거나 열 꼴이 바뀌면 틀린 길을 보인다. 가이드 08 확인 「설비 → 구성 요소 → 센서로 따라간 길이 보이면」은 첫 꼴에서 겉으로는 맞지만, 학생이 「쿼리가 부품까지 갔다」로 잘못 읽을 수 있다. 고칠 방향: 결과 화면의 길 그림이 결과 값 맞추기가 아니라 쿼리가 실제로 지난 관계(돌려받은 경로나 결과 행의 노드 식별자)로 칠하게 한다. 09 · 10 그림은 맞게 칠했다.
