## 2. 앞 포털 실습과 잇는 지점 (포털에서 본 것 → 랩에서 직접 만드는 것)

포털이 실제로 하는 일(main 코드로 확인):
- 조치 판단 규칙 화면 = `agentsvc/cards.py` `evaluate`. 후보 선택 규칙(SELECT) → 규정 판정(`dec:compliance`, Collect)에서 후보마다 EXCLUDE · PENALTY · WARN을 모은다. 규칙에 적용 대상(APPLIES_TO)이 없으면 모든 후보에 건다(`compliance_applies`). **값을 모르는 조건**은 맞았다고 치지 않고, WARN이면 「확인되지 않은 경고」, EXCLUDE · PENALTY면 제외 쪽으로 넣는다(`cards.py` 「pending」). 원천을 아예 못 읽으면 판단이 멈춘다(`decide.py` FactUnavailable).
- 지금 포털의 쿨러 규칙은 매뉴얼 적재가 만든 것이다(`course_extractions.json`): `rule:hm-8-8-remote-auto-only`(EXCLUDE, SOP-COOL-11~13), `rule:hm-8-8-fan-life-penalty`(PENALTY 20, SOP-COOL-11 · 12), `rule:cooler-forecast-temperature-warning`(WARN ≥ 55 ℃, SOP-COOL-11~13), 시드 `rule:ts1-hard`(EXCLUDE ≥ 65 ℃, 출처 `ks:sr-04`, 대상 없음 = 전부).
- 순위 = 정책 점수 `rule:rank-value`(`instances.cypher`). 조건별 손익 화면 = `whatif.py`(원 단위 손익 · 값 바꿔 보기 · 경계값 찾기, 시험값은 사본에만).

## 7. plantsim 문제 — 근본 원인과 고치는 법 (실측)

**확인한 사실.** main에 `plantsim.thermal.equilibrium_ts1`은 없다. 삭제가 아니라 **옮김 + 이름 바꿈**이다 — main 커밋 `04efb988`(2026-11-02 「시스템 건강검진 반영」)이 열 모델의 상수 · 식을 `common/hydcommon/plant_model.py` 한 곳으로 옮겼고(시뮬레이터와 예측이 같은 식을 쓰게), `equilibrium_ts1(load, fan, health, t_amb)`는 `plant_model.steady_ts1(load_pct, leak, fan_pct, cooler_health, running, t_amb)`가 됐다. `thermal.K_HEAT · K_LEAK · K_BASE · K_COOL`도 `plant_model`로 갔다(`git show 04efb988 -- ot/plant-sim/plantsim/thermal.py`).

같은 커밋에서 생성기가 기대던 것이 더 바뀌었다:
1. 예측 거부 문장이 영어 → 한국어(`forecast.py` 「예측할 수 없습니다: …」) — `data_conditions.py`의 `REFUSAL` 표 열쇠가 안 맞아 거부 사례에서 멈춘다.
2. 예측 모델 판 1.1 — 트립 · 정지 설비는 자연 냉각만(`MODEL_REVISION = '1.1'`). 트립 사례의 작업지시 후보 예측값이 바뀐다.
3. PLC 상태 보고 주기 10초 → 1초(`daq_contract.STATUS_INTERVAL_S`, 유예 `OBSERVATION_GRACE_S` 2초). 생성기가 이 값을 그대로 쓰면 PLC 수신이 10배로 늘고, 랩의 게이트웨이 기록(10초)과 어긋난다.
4. 시드 결정표에서 쿨러 규칙(`rule:auto-mode` · `ts1-warn` · `ps1-warn` · `fan-24h` · `trip-reset-only` 등)을 지웠다 — 이제 매뉴얼 적재(`course_extractions.json`)가 만든다. `rule_excerpt()`가 찾을 행 · 머리 줄이 없어 멈춘다. `rule:ts1-hard`(SR-04)는 남아 있다(`instances.cypher:325`).
5. 클라우드 workspace 체크아웃에는 `ot/` · `common/` · `it/`가 없다 — `ROOT/'ot/plant-sim'`를 찾을 수 없다(이 PC는 main 체크아웃 안에 workspace/가 있어 경로가 있다).

**재현과 고침 시험(저장소 밖, scratchpad에서).** `git archive main`으로 main 코드를 `…/scratchpad/s3fix/main/`에 풀고 생성기 사본의 ROOT만 그쪽으로 돌려 실행 → `AttributeError: … no attribute 'equilibrium_ts1'`(150줄) 재현. 사본에 네 가지만 고치자 `build()`가 4.7초에 끝났다: ① `plant_model.steady_ts1(load0, leak, fan0, 1.0, True, t_amb)` ② 「예측할 수 없습니다」로 시작하는 ValueError는 그 문장을 거부 사유로 그대로 ③ 게이트웨이 주기 10초를 생성기 상수로 ④ 옛 결정표를 `04efb988^` 판 `instances.cypher`에서. 결과를 지금 랩 `자료/`와 견주면 `예측_결과.csv`만 다르다(거부 사유 17행, 트립 사례 E09 · E27 · E37의 SOP-COOL-14 예측 43.30~43.61 → 56.44~57.20 ℃). 이 시험은 옛 생성기가 네 고침으로 돈다는 확인일 뿐이다 — 새 생성기는 사례 행을 궤적에서 다시 뽑으므로(3.3) 모든 원천 파일의 바이트가 바뀐다.

**고치는 법(유지보수 1순위 — 관리할 곳을 줄이는 쪽).**
- 물리는 main의 `hydcommon.plant_model` 한 곳을 그대로 쓴다(같은 사실 한 곳). 다시 만들 때 바이트가 바뀌면 3.3절 설계 조건 검사와 `--check`가 알린다.
- 랩 현장 값(게이트웨이 주기 · 유예 · 예측 유효 시간)은 시스템 계약에서 가져오지 않고 생성기가 갖는다 — 랩 PLC 자료는 현장 게이트웨이 기록이다(K요-7: 포털은 방향 기준, 입력값까지 맞추지 않음). 경보 패턴 값은 main과 같아야 하므로 상수 + 출처 줄 + `--check` 대조.
- 거부 사유는 예측 서비스 문장을 그대로 쓴다 — 번역 표(`REFUSAL`)를 지운다.
- 판단 시스템 결정표 내보내기는 `04efb988^:it/neo4j/v2/instances.cypher`의 규칙 18행 · 스킬 목록을 생성기 안 상수로 고정하고 출처 커밋을 주석에 적는다(main이 바뀌어도 랩의 「옛 판」은 그대로여야 하므로).
- main 코드 경로는 한 곳에서 푼다: `lab_package.py`(이미 모든 생성기가 import)에 `system_root()` — 환경 변수 `HYD_MAIN_ROOT`가 있으면 그것, 없으면 저장소 루트, `ot/plant-sim`이 없으면 「`git worktree add ../main main` 뒤 `HYD_MAIN_ROOT=../main`」을 알리고 멈춤. `data_documents.py`(`ROOT/'it/portal/www/samples'`) · `build_session3_documents.py`(`course_extractions.json`)도 같은 함수를 쓰게 한다. 클라우드 실행: `git fetch origin main:main` → `git worktree add ../main main` → `HYD_MAIN_ROOT=../main python3 …`(CLAUDE.md 7절).
- 미확인: 고친 `data_conditions.py`로 지금 판 `build_session3_judgement.py` · `build_conditions.py`가 끝까지 도는지(실행하지 않음 — 새 생성기로 바꿀 것이라).

## 11. 미결

**사용자에게 물을 것(되돌리기 비싼 것만).**
1. **HM-8 원문(main)의 「교육용」 문장** — 1줄 제목 「(교육용 예시)」와 22줄 「아래 값은 교육용 가상 설비의 축소 기준이다(일반 산업 설비의 경보는 보통 80 ℃ 안팎이다)」가 랩에 그대로 복사되면 K-18(꼬리표 · 면책 0) 불통과다. 랩 사본만 고치면 원문과 달라지고, main 원문을 고치면 포털 매뉴얼 적재의 인용 위치(`course_extractions.json`의 `start` · `end`)와 덱 인용까지 바뀌는 시스템 작업이다. 제안: 랩 사본은 원문 그대로 두고 K-18을 **미충족으로 보고**(K-5)하며, main 원문 정리는 별도 시스템 작업으로 돌린다. 이렇게 해도 될까요?
2. **실라버스 통합 온라인 R33의 「조건표」** — R32는 「결정표 자료를 완성한다」, R33은 「앞 실습의 조건표를 읽는」, 오프라인 R24 · R25는 둘 다 「결정표」라 같은 파일을 두 이름으로 부른다(K-142 — 한 랩 안에 두 이름이 생김). 제안: 통합 온라인 R33 「앞 실습의 조건표를 읽는」을 「앞 실습의 결정표를 읽는」으로 고치고(K요-5), 통합 03 덱 SLIDE 65~67의 「조건표」는 덱 쪽에 넘긴다. 이렇게 해도 될까요?
