## 4. 문제 없던 것

- PLC 명령 검사 순서(형식 → 출처 · 모드 → PLC 시계 만료 → 실행된 cmdId 32개 중복 → 범위 → 인터록)와 「거절은 본 것으로 기억하지 않음」(plc.py:95-159). 명령의 출처는 payload 가 아니라 토픽에서 정한다(edge.py:86-91).
- 승인 장부: 지문 필드가 cmdId · asset · incident · actions · approvedBy · expiresAt · approvalId 를 모두 덮는다(schemas.py:27). 키 기본값이 없다(schemas.py:30-35, gw/main.py:32). 재사용 창도 계산이 맞다: 속도 한도 2/s × 만료 120 s = 240 < seen 256 < 장부 512. 그래서 지문이 맞는 옛 명령을 다시 보내도 DUPLICATE 나 PLC 중복에 걸린다.
- ACL: cmd/auto 는 cmd-gateway 만, 학생 계정은 구독만 한다. 허락 없는 발행은 연결을 끊는다(acl.conf, emqx.conf:52-58). 안쪽 1883 은 호스트에 열지 않았다(compose.yaml:49). 9번(대시보드 발행)만 미확인으로 남았다.
- 토픽 해석은 모르는 설비 키를 거절하고(topics.py:53-65), 모든 소비자가 같은 계약 검사(schemas *_record)를 한다.
- connect-sink: 행과 소비 위치를 한 트랜잭션에 쓰고, CommitFailedError 를 처리하며, 깨진 묶음은 파티션별로 시험해 그 파티션만 건너뛴다. 토픽을 다시 만든 것도 알아챈다(replay_verdict).
- 05faa3a2f 자체는 맞다: 거절된 commit 의 offset 은 바로 앞 SQLite 체크포인트에 있고, 다시 배정되어 돌아온 기록은 replay_verdict 가 걸러 한 번만 처리한다. 남은 것은 1번(다른 예외 · 감독 부재)이다.
- 시간 규칙: TIME_SCALE · DAQ_PROFILE 에 코드 기본값이 없다(timeutil.py:36-46, daq_contract.py:31-36). 감지 지속 · 기울기는 설비 초(이벤트 시각 × 배속)로 잰다. lite 에서 1 Hz 가 아닌 태그를 쓰는 패턴은 적재할 때 거절한다(patterns.py:132-140). 배속이 다른 저장 상태는 시작하지 않는다(main.py:209-218). 결함 램프는 설비 초이고 상한 · 정의역을 검사한다(plant.py:108-136). 관문 · PLC 의 만료와 속도 한도는 벽시계다(IT 단계, 규칙에 맞음).
- 예측은 외란 램프 중이면 거절하고, 빠진 입력에 건강 상태로 폴백하지 않는다(forecast.py:41-55).
- topics.sh 는 「이미 있음」만 통과시키고 그 밖의 실패는 종료 코드 1 로 하류 기동을 막는다. fuxa-init 은 올린 뒤 되읽어 대조한다.
- 읽기 계정: 전용 무권한 역할이 아니면 거절한다(enterprise.py). SQL 가드는 AST 로 읽기만 허용한다(sql_read.py). neo4j 읽기는 EXPLAIN 으로 질의 종류를 확인한다(neo4j_mcp.py:62-76).
- 쓰기 요청은 다른 사이트에서 오면 거절한다(service.py:29-51), CORS 없음.
