## SLIDE 07 — 센서와 상태 변수
### 화면 내용
- 유형: 비교
- 메시지: 같은 유온을 재는 센서를 하나 더 달면 계측 채널은 둘이 되고, 두 채널이 쓸 한계는 유온 한 곳에 남는다.
- 요소:
  1. 센서(Sensor) | 값을 내놓는 계측 채널 / 유온 센서: sen:ts1 / 태그 TS1 · 단위 ℃ / 채널을 더하면 식별자 1개 → 2개 | 재는 쪽

- 노트: [짚을 곳] 왼쪽 유온 센서의 식별자와 태그 → 오른쪽 유온의 식별자와 이 설비의 두 기준 → 양쪽 마지막 줄 / · 어느 채널의 값을 읽을지 정하려면 유온 센서의 태그 TS1을 본다. 얼마와 비교할지는 이 설비에 정한 유온의 정상값 48 ℃와 한계 65 ℃에서 찾는다 / · 같은 유온을 재는 채널을 한 개 더 등록한다고 가정한다. 서로의 기록을 구별하려면 센서 식별자가 두 개 필요하다 / · 두 채널 모두 같은 유온을 재므로 오른쪽의 유온은 한 개다. 한계를 바꾸려면 유온 한 곳에서 고친다 / · 두 측정값이 다르면 원래 채널과 시간을 보존하고 설치·측정 조건을 확인한다. 기준을 공유해도 기록은 둘이다. / [다음] 센서의 태그와 유온의 한계를 찾는 길

## SLIDE 10 — 증상 · 고장 유형 · 원인

- 요소:
  1. 증상(Symptom) | 계측값에서 관측한 이상 양상이다. / 부하 90 %에서 유온이 56→58 ℃, 냉각 효율이 69→67 %로 변했다면 | 무엇이 보이는가

## SLIDE 45 — RETURN: 속성값과 노드 · 관계
### 화면 내용
- 유형: 코드
- 메시지: 같은 패턴을 찾더라도 속성값을 받으면 표로 읽고, 노드와 관계를 받으면 연결을 그릴 수 있다.

## SLIDE 56 — 기존 노드를 찾아 관계 생성
### 화면 내용
- 유형: 코드
- 메시지: 추가한 관계가 0개일 때는 기존 관계가 있었는지, 양 끝 노드를 모두 찾았는지 다시 조회한다.
- 코드: MATCH (c:Component {id: 'comp:cooler'}), /       (s:Sensor {id: 'sen:ts1'}), /       (v:StateVariable {id: 'sv:ts1'}) / MERGE (c)-[:MONITORED_BY]->(s) / MERGE (s)-[:OBSERVES]->(v) /  / ── 없는 id로 찾으면 ── / MATCH (c:Component {id: 'comp:cooler'}), /       (s:Sensor {id: 'sen:zz9'}) / MERGE (c)-[:MONITORED_BY]->(s) / 결과: 만들어진 관계 없음
- 요소:
  1. MATCH | 각 식별자로 노드 c, s, v를 찾는다.
  2. **MERGE** | 변수로 부른 두 노드 사이에 그 관계가 없을 때만 만든다.
  3. 방향 | 화살표는 스키마의 시작 클래스에서 끝 클래스로 향하게 적는다.
  4. 끝점 누락 | 찾는 노드가 하나라도 없으면 아무 관계도 만들어지지 않는다.
- 노트: [짚을 곳] 위 MATCH 세 노드 → MERGE 두 관계(방향) → 아래 없는 식별자 예와 결과 줄 / · 관계는 양 끝 노드를 식별자로 먼저 찾아 변수에 담은 뒤 만든다 / · MERGE: 쿨러 → 센서 계측 관계, 센서 → 유온 읽는 관계. 두 노드 사이에 이미 있으면 그대로 쓴다. 화살표는 스키마의 시작 → 끝 / · 없는 식별자로 찾으면 MATCH가 찾은 행이 없어 MERGE도 만들 일이 없다 → 「만들어진 관계 없음」인데 오류 없이 끝날 수 있다 / · 실행 완료 표시만 보고 관계가 생겼다고 판단하지 않는다. RETURN이 없어 결과 표가 안 보이는 것만으로는 성공 · 실패를 못 가린다 / · 저장 뒤 같은 두 노드 사이를 다시 조회해 확인 → 방향을 잘못 적은 경우도 이 대조에서 드러난다 / · 기존 연결이 있는 경우와 없는 끝점으로 MATCH한 경우를 재조회해 구별한다 / [다음] 넣고 확인하는 한 과정
