## SLIDE 06 — 센서 클래스의 속성과 속성값
### 화면 내용
- 유형: 표
- 메시지: 속성(Property)은 값을 담는 항목이고, 그 항목에 채운 내용은 속성값(Property Value)이다.
- 머리: 속성 | 유온 센서 | 냉각 효율 채널
- 요소:
  1. 식별자(id) | sen:ts1 | sen:ce
  2. 이름(name) | 유온 센서 | 냉각 효율
  3. 태그(tag) | TS1 | CE
  4. 단위(unit) | ℃ | %
  5. 계산 채널 여부(virtual) | false: 직접 계측 | true: 다른 계측값으로 계산
- 노트: [짚을 곳] 왼쪽 속성 열 → 가운데 유온 센서 → 오른쪽 냉각 효율 채널 / · 값을 담는 항목이 속성이고, 그 칸에 실제 채운 내용이 속성값입니다. / · 식별자 행에서 sen:ts1과 sen:ce를 짚는다. 유온 센서 열을 따라 읽으면 태그 TS1과 단위 ℃가 한 채널에 속한다. 냉각 효율 채널 열에서는 CE와 %가 짝을 이룬다. / · 냉각 효율은 다른 측정값으로 계산하지만 태그와 단위를 갖고 값을 내는 계측 채널입니다. / [다음] 센서의 값과 다른 대상을 가리키는 연결

## SLIDE 09 — 카디널리티의 네 가지 형태
### 화면 내용
- 유형: 삽화
- 라벨: 큰
- 메시지: **카디널리티**(Cardinality)는 관계 한쪽의 대상 하나에 이어질 수 있는 반대쪽 대상의 수이다.
- 그림: ../../../../온라인/decks/integrated/day02/figures/카디널리티.svg
- 요소:
  1. 1:1 · MANIPULATES | 팬 인버터 하나 → 팬 속도 하나 | 12.5,64,23
  2. 1:N · EVIDENCED_BY | 핀 오염의 증거 둘 / 냉각 효율 평균 낮음 / 팬 진동 정상 | 37.5,64,23
  3. N:1 · OBSERVES | 센서 여럿 → 상태 변수 하나 / 현재 유온 센서 1개 → 유온 | 62.5,64,23
  4. N:M · MONITORED_BY | 쿨러 하나에 계측 채널 여럿 / 한 채널에 구성 요소 여럿 | 87.5,64,23
- 노트: [짚을 곳] 왼쪽에서 오른쪽으로 1:1 → 1:N → N:1 → N:M / · 첫 칸은 팬 인버터 하나와 팬 속도 하나가 짝을 이룬다. N과 M은 여러 상대를 허용한다. 둘째 칸에서 원인 하나가 여러 증거로 갈라지는 선을 짚는다 / · 셋째 칸에서는 유온 센서 하나가 읽는 물리량은 몇 개인지, 그 유온을 읽을 센서를 하나 더 달 수 있는지 묻는다. 현재 센서는 하나지만 여러 센서가 유온을 읽을 수 있다고 답하면 바로 넷째 칸으로 간다. 답이 갈리면 흰 원 하나에서 파란 원을 찾고 그 파란 원으로 모이는 흰 원들을 짚은 뒤 넷째 칸으로 간다 / · 넷째 칸은 양쪽 모두 여러 상대를 허용한다. 앞에서 찾은 오일 쿨러와 유온 센서의 계측 관계를 양쪽에서 읽는다 / [다음] 여러 대상이 연결될 때 독립 클래스를 두는 기준

### 화면 구성
흰 원은 관계의 시작, 파란 원은 끝이다. 네 칸에서 원 하나를 잡고 맞은편의 상대 수를 양쪽에서 읽는다. 셋째 칸에는 유온 센서의 현재 연결을 적고, 마지막 칸에는 계측 관계를 양쪽에서 읽은 뜻을 나란히 쓴다.

## SLIDE 28 — MATCH · RETURN: 패턴과 결과의 행
### 화면 내용
- 유형: 코드
- 메시지: MATCH는 패턴에 맞는 연결을 찾고, RETURN은 그 결과에서 돌려받을 항목을 정한다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / c.name         s.tag / "오일 쿨러"    "TS1" / "오일 쿨러"    "CE"
- 요소:
  1. MATCH | 이름이 오일 쿨러인 구성 요소에서 계측 관계로 이어진 센서를 찾는다.
  2. RETURN | 구성 요소 이름과 센서 태그를 결과의 두 열로 받는다.
  3. **행의 수** | 쿨러 하나에 채널이 둘이라 결과는 두 행이다.
  4. 행과 노드 | 두 행의 오일 쿨러는 같은 노드이다. 이름의 반복이 노드의 중복을 뜻하지 않는다.
- 노트: [짚을 곳] 코드 위 MATCH 두 줄 → RETURN → 아래 결과 두 행 → 오른쪽 강조한 행의 수 / · 절 = 쿼리를 하는 일별로 나눈 한 부분. MATCH = 찾을 패턴(이름이 오일 쿨러인 구성 요소에서 계측 관계로 이어진 센서) / · RETURN = 돌려받을 항목(구성 요소 이름 · 센서 태그 → 결과 두 열) / · 결과: 쿨러-유온 센서, 쿨러-냉각 효율 채널 → 두 연결이 각각 패턴에 맞아 두 행 / · 쿨러 이름이 두 번 나와도 같은 노드. 이름 반복 ≠ 노드 중복 / · 개수를 적지 않았다: 조건에 맞는 연결이 실제로 둘이라 두 행 → 한 행이 무엇을 나타내는지 알면 여러 행을 중복 데이터로 오해하지 않는다 / [다음] 같은 대상이 여러 결과 행에 나타나는 경우

## SLIDE 29 — DISTINCT: 반환한 값의 중복 제거
### 화면 내용
- 유형: 표
- 메시지: DISTINCT는 반환하는 값의 조합이 같은 행을 하나로 남기며, 저장된 노드를 지우지 않는다.
- 머리: 같은 MATCH의 반환 절 | 결과 | 남는 행
- 요소:
  1. RETURN c.name | 오일 쿨러 / 오일 쿨러 | 2행
  2. **RETURN DISTINCT c.name** | 오일 쿨러 | 1행
  3. RETURN DISTINCT c.name, s.tag | 오일 쿨러 · TS1 / 오일 쿨러 · CE | 2행
  4. 중복 제거(DISTINCT) | 쿨러 → 계측 채널 둘의 같은 패턴에서 반환 절만 바꾼다 / 반환한 모든 열의 값이 같을 때 한 행으로 남긴다 | 결과 정리
- 노트: [짚을 곳] 표 첫 줄(이름만, 2행) → 강조한 둘째 줄(DISTINCT, 1행) → 셋째 줄(이름 + 태그, 2행) → 넷째 줄 설명 / · 이름 열만 남겨도 MATCH가 찾은 연결은 여전히 둘 → 같은 이름이 두 번 / · DISTINCT = 반환한 값의 조합이 같은 행을 하나로. 이름만이면 쿨러가 한 번 / · 이름 + 태그를 받으면 조합이 달라(쿨러 · 냉각 효율 채널/쿨러 · 유온 센서) 두 행 그대로 → 열 하나가 아니라 반환한 열 전체의 조합을 본다 / · DISTINCT는 저장된 센서 · 관계를 지우지 않는다. 결과만 정리 / · 이름이 같은 별개 장치는 이름 목록으로 구별 못 한다 → 대상을 구별할 땐 노드나 고유 식별자로. 결과를 짧게 만들기보다 질문에 필요한 구별을 남기는 게 먼저 / [다음] 중복을 가린 결과로 실제 대상 수를 세는 방법

### 화면 구성
표: 같은 MATCH에서 반환 절만 바꾼 세 줄과 결과 · 남는 행, 마지막 줄은 DISTINCT의 뜻. 둘째 줄(RETURN DISTINCT c.name)을 강조한다.

### 화면 내용

- 유형: 코드
- 메시지: WHERE로 한계가 있는 물리량만 남기면, 값이 없는 상태 변수를 결과에서 구별할 수 있다.
- 코드: MATCH (s:Sensor)-[:OBSERVES]->(v:StateVariable) / WHERE v.limit IS NOT NULL / RETURN s.tag, v.name, v.limit, v.unit / ORDER BY s.tag /  / ── 결과 ── / "PS1"  "토출 압력"  130   "bar" / "TS1"  "유온"       65    "℃" / "VS1"  "팬 진동"    2.0   "mm/s" /  / ── 빠진 행 ── / CE 냉각 효율 · FS1 유량: limit 값 없음
- 요소:
  1. WHERE | MATCH가 찾은 행 가운데 조건에 맞는 행만 남기는 조건 절이다.
  2. **IS NOT NULL** | 속성에 값이 있는지를 묻는다. 크기를 비교하는 조건이 아니다.
  3. 빠진 행 | 냉각 효율과 유량은 센서와 이어져 있지만 limit 값이 없어 빠진다.
  4. 크기 비교 | limit > 100처럼 비교할 수도 있으나, 단위가 다른 물리량을 한 기준으로 견주지 않는다.
