## SLIDE 36 — MATCH · RETURN: 결과 행과 돌려받는 항목
### 화면 내용
- 유형: 코드
- 메시지: MATCH가 찾은 연결 하나가 결과의 한 행이 되고, RETURN은 그 행에 속성값을 담을지 노드와 관계를 담을지 정한다.
- 코드: MATCH (c:Component {id: 'comp:cooler'}) /       -[r:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / c.name         s.tag / "오일 쿨러"    "TS1" / "오일 쿨러"    "CE" /  / ── 같은 MATCH, 다른 RETURN ── / RETURN c, r, s / → 쿨러 노드 하나와 센서 노드 둘을 그래프로
- 요소:
  1. MATCH | 식별자로 고른 오일 쿨러에서 계측 관계로 이어진 센서를 찾는다.
  2. **결과 행** | 패턴에 맞는 연결 하나가 한 행이다. 센서가 둘이라 두 행이다.
  3. 행과 노드 | 두 행의 오일 쿨러는 같은 노드다. 이름이 두 번 나와도 노드는 하나다.
  4. RETURN | 속성값(c.name, s.tag)을 받으면 표로, 노드와 관계(c, r, s)를 받으면 그래프로 읽는다.
- 노트: [짚을 곳] 코드의 MATCH → RETURN c.name, s.tag → 결과 두 행 → 다른 RETURN → 오른쪽 넷째 줄 / · “결과에 「오일 쿨러」가 두 번 나왔으니 오일 쿨러 노드도 둘일까요?” 오른쪽 셋째 줄 「두 행의 오일 쿨러는 같은 노드다」 / · 둘이라는 답이 나오면 오른쪽 둘째 줄로 돌아가, 결과 한 행은 패턴에 맞는 연결 하나이고 센서가 둘이라 두 행이라는 점을 짚는다 / [다음] 같은 노드가 여러 행에 나올 때

## SLIDE 37 — DISTINCT · COUNT: 같은 노드가 여러 행에 나올 때
### 화면 내용
- 유형: 코드
- 메시지: 같은 노드가 여러 행에 나오므로, DISTINCT로 반환 조합을 줄이고 COUNT로 셀 것이 행인지 노드인지 정한다.
- 코드: // 쿨러 → 센서의 같은 MATCH에 RETURN만 바꾸면 / RETURN c.name                  // "오일 쿨러" 2행 / RETURN DISTINCT c.name         // "오일 쿨러" 1행 / RETURN DISTINCT c.name, s.tag  // TS1 · CE 2행 /  / // 세 설비에서 유온 센서까지 / MATCH (a:Asset)-[:HAS_COMPONENT]->(c:Component) /       -[:MONITORED_BY]->(s:Sensor {id: 'sen:ts1'}) / RETURN count(*) AS rows, count(DISTINCT s) AS sensors / // rows 3 · sensors 1
- 요소:
  1. **DISTINCT** | 반환한 열 전체의 조합이 같은 행을 하나로 남긴다. 저장된 노드는 그대로다.
  2. COUNT · AS | count(*)는 결과 행을, count(DISTINCT s)는 서로 다른 노드를 센다. AS는 결과 열의 별명이다.
  3. 행 3 · 센서 1 | 세 설비가 같은 오일 쿨러 노드를 거쳐 같은 유온 센서 노드에 닿는다.
  4. 노드와 계기 | 센서 노드 하나가 계기 한 대는 아니다. 세 호기에 하나만 둔 노드다.
- 노트: [짚을 곳] 코드 위 세 RETURN → 아래 세 설비 쿼리 → rows 3 · sensors 1 → 오른쪽 넷째 줄 / · “세 설비에서 유온 센서까지 세었더니 3이 나왔다면 유온 센서는 세 개일까요?” 코드 마지막 줄 rows 3 · sensors 1 / · 세 개라는 답이 나오면 오른쪽 둘째 줄 count(*)와 count(DISTINCT s)로 돌아가, 셀 것이 행인지 노드인지 먼저 정한다는 메시지를 짚는다 / [다음] 구성 요소마다 센서 수 세기

### 화면 구성
코드 위는 같은 MATCH에 RETURN만 바꾼 세 줄과 행 수, 아래는 세 설비에서 유온 센서까지 센 쿼리와 결과. 오른쪽 첫 칸(강조)이 DISTINCT, 셋째 칸이 행 수와 노드 수가 갈린 까닭이다.

## SLIDE 38 — 구성 요소별 집계와 원래 행 대조
### 화면 내용
- 유형: 표
- 메시지: 집계하지 않고 함께 반환한 열이 묶는 기준이 되어, 구성 요소마다 센서 수를 따로 센다.

- 요소:

  2. **RETURN** | c.id AS componentId, c.name AS component, count(DISTINCT s) AS sensors / 집계하지 않은 c.id · c.name이 묶는 기준, 이름이 같아도 id로 구별 | 쿨러 2 · 주 펌프 (A) 2 · 쿨러 팬 1
  3. ORDER BY | sensors DESC, componentId / 큰 값부터, 같으면 componentId 오름차순. 개수는 바뀌지 않음 | 쿨러가 주 펌프 앞
  4. 원래 행과 대조 | 묶기 전 다섯 행의 센서 | 쿨러 CE · TS1 / 주 펌프 FS1 · PS1 / 팬 VS1
  5. 조회 범위 | 센서로 이어진 구성 요소만 나온다 | 모든 장치 목록이 아님
- 노트: [짚을 곳] 코드의 RETURN과 count → 결과 세 줄 → 오른쪽 첫 줄 묶는 기준 → 셋째 줄 원래 행 / · “RETURN에 c.name만 두면 이름이 같은 두 구성 요소의 센서는 따로 세어질까요?” 오른쪽 첫 줄 「c.id와 c.name이 같은 행끼리 센다 · 이름이 같아도 id로 구별한다」 / · 따로 세어진다는 답이 나오면 메시지 「집계하지 않고 함께 반환한 열이 묶는 기준」으로 돌아가 이름만 두면 한 묶음이 된다는 점을 짚고, 셋째 줄 원래 행과 견줘 2 · 2 · 1을 확인한다 / [다음] 여러 관계를 잇는 경로와 조건

## SLIDE 39 — 여러 관계를 잇는 경로와 WHERE · AND · OR
### 화면 내용
- 유형: 코드
- 메시지: 노드와 관계를 번갈아 이어 설비에서 한계까지 한 쿼리로 따라가고, WHERE로 결과 행을 거르되 OR는 괄호로 묶는다.
- 코드: MATCH (a:Asset {id: 'asset:hyd-01'}) /       -[:HAS_COMPONENT]->(c:Component) /       -[:MONITORED_BY]->(s:Sensor) /       -[:OBSERVES]->(v:StateVariable) / WHERE (c.id = 'comp:cooler' OR c.id = 'comp:fan') /   AND v.limit IS NOT NULL / RETURN c.name, s.tag, v.name, v.unit, v.limit / ORDER BY s.tag /  / ── 결과 ── / "오일 쿨러"  "TS1"  "유온"     "℃"     65 / "쿨러 팬"    "VS1"  "팬 진동"  "mm/s"  2.0 /  / ── 괄호를 빼면 ── / CE 냉각 효율(limit NULL) 행까지 남는다
- 요소:
  1. **경로(Path)** | 노드와 관계를 번갈아 이은 패턴. 설비에서 상태 변수까지 세 관계를 건넌다.
  2. WHERE · IS NOT NULL | 찾은 행 가운데 조건에 맞는 행만 남긴다. / NULL은 값 없음, 0이나 끊긴 연결과 다르다.
  3. AND · OR | AND가 OR보다 먼저 묶인다. 두 장치를 고르는 OR를 괄호로 묶어야 한계 조건이 둘 다에 걸린다.
  4. ORDER BY · 단위 | 결과 행을 적은 항목 순서로 놓는다. / 값의 크기는 단위가 같은 것끼리만 견준다.
- 노트: [짚을 곳] 코드의 세 관계 경로 → WHERE의 괄호 → 결과 두 행 → 괄호를 빼면 / · “괄호를 빼면 왜 냉각 효율 행이 남을까요?” 오른쪽 셋째 줄 「AND가 OR보다 먼저 묶인다」와 코드 맨 아래 「CE 냉각 효율(limit NULL) 행까지 남는다」 / · IS NOT NULL이 빈 값을 못 걸러서라는 답이 나오면 오른쪽 셋째 칸 「AND가 OR보다 먼저 묶인다」로 돌아가, 괄호가 없으면 한계 조건이 팬 쪽에만 걸려 쿨러의 냉각 효율 행은 한계 조건을 거치지 않고 남는다는 점을 짚는다 / [다음] 저장된 방향과 따라가는 방향

## SLIDE 41 — 적재 쿼리: CREATE · MERGE · SET과 관계 잇기
### 화면 내용
- 유형: 코드
- 메시지: 조회 쿼리는 그래프를 바꾸지 않고, 적재 쿼리는 식별자로 찾고 없을 때만 만드는 MERGE로 같은 대상을 하나로 남긴다.
- 코드: CREATE (s:Sensor {id: 'sen:ts1'})   // 늘 새로 만듦 /  / MERGE (s:Sensor {id: 'sen:ts1'})    // 없을 때만 만듦 / SET s.name = '유온 센서', s.tag = 'TS1' /  / MERGE (s:Sensor {id: 'sen:ts1', name: '온도 센서'}) / // 이름이 달라 못 찾음 → 만들려다 유일 제약이 거절 /  / MATCH (c:Component {id: 'comp:cooler'}), /       (s:Sensor {id: 'sen:ts1'}) / MERGE (c)-[:MONITORED_BY]->(s) / // 새 관계 0 → 다시 조회: 관계 1개면 이미 있음, 노드 0개면 이을 노드 없음
- 요소:
  1. CREATE · MERGE | CREATE는 늘 새로 만들어 실행마다 생기는 기록에 쓴다. MERGE는 패턴 전체가 맞는 것을 찾고 없을 때만 만든다.
  2. **유일 제약(Unique Constraint)** | 같은 레이블에서 id가 겹치면 저장을 거절하는 DB 제약(DB Constraint). 그래서 바뀔 이름은 SET으로 넣고 검색 조건에는 식별자만 둔다.
  3. 관계 잇기 | 양 끝 노드를 식별자로 먼저 찾고, 스키마의 시작 → 끝 방향으로 MERGE한다.
  4. 새 관계 0 | 양 끝 노드가 있는지 먼저, 둘 다 있으면 그 사이 관계를 다시 조회한다.
