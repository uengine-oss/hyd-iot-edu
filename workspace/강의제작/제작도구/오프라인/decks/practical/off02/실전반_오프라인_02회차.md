## SLIDE 06 — 속성과 속성값
### 화면 내용
- 유형: 표
- 메시지: 속성(Property)은 값을 담는 항목이고, 같은 항목을 같은 형식으로 채워야 프로그램이 값을 찾고 비교한다.
- 머리: 속성 | 유온 센서 · 냉각 효율 채널 | 현장에서 쓰는 때
- 요소:
  1. 식별자(id) | sen:ts1 · sen:ce | 같은 센서는 / 식별자 하나
  2. 이름(name) | 유온 센서 · 냉각 효율 | 사람이 읽는 이름 / 찾기는 식별자로
  3. 태그(tag) | TS1 · CE | 계측 데이터를 / 태그로 찾는다
  4. 단위(unit) | ℃ · % | 단위는 단위 칸에만 / 값과 섞지 않는다
  5. **계산 채널 여부(virtual)** | false: 직접 계측 · true: 다른 계측값으로 계산 | true면 계기가 없어 / 값이 이상할 때 / 계산에 쓰인 값부터
- 노트: [짚을 곳] 표 왼쪽 공통 항목 → 가운데 두 채널의 값 → 오른쪽 「현장에서 쓰는 때」 → 강조한 계산 채널 여부 줄 / · 속성 = 값을 담는 항목, 속성값 = 실제로 채운 내용 / · 식별자: 같은 센서는 이름을 어떻게 적든 하나. 이름은 사람이 읽는 말, 프로그램은 식별자로 찾는다 / · 태그: 계측 데이터를 찾는 항목. 어느 센서든 같은 태그 항목을 읽는다 / · 단위는 단위 칸에만: 숫자 칸에 붙여 적으면 글자가 돼 측정값과 비교 못 한다 / · 계산 채널 여부 참 = 달린 계기가 없다 → 값이 이상하면 센서 교체가 아니라 계산에 쓰인 값부터 본다 / · 같은 항목을 같은 형식으로 채워야 프로그램도 사람도 같은 자리에서 판단 / [다음] 센서의 값과 다른 대상을 가리키는 연결

## SLIDE 20 — 관계 정의와 유효한 연결
### 화면 내용
- 유형: 코드
- 메시지: 관계 정의가 이름 · 방향 · 양 끝 클래스를 정해 두어야, 정의를 따르는 **유효한 연결**인지 가를 수 있다.
- 코드: { /   "type": "USES_PART", /   "from": ["Component"], /   "to": ["Part"], /   "cardinality": "N:M", /   "description": "구성 요소에 들어가는 교체 부품" / } /  / (:Component)-[:USES_PART]->(:Part)        유효 / (:Component)-[:USES_PART]->(:Component)   끝 클래스가 다르다 / (:Part)-[:USES_PART]->(:Component)        방향이 반대이다 / (:Component)-[:HAS_PART]->(:Part)         정의에 없는 이름 /  / 오일 쿨러를 팬 베어링에 USES_PART로 이었다고 하자 / 양 끝 클래스는 맞지만 쿨러에 들어가는 부품은 쿨러 코어다
- 요소:
  1. type | 관계 유형의 이름이다. 뜻이 비슷한 다른 이름은 다른 관계가 된다.
  2. **from · to** | 시작과 끝 클래스다. 화살표는 from에서 to로, 장치에서 부품으로 향한다.
  3. cardinality | N:M으로 선언되어 장치와 부품 양쪽이 여럿을 받을 수 있다.
  4. 유효한 연결(Valid Connection) | 이름 · 방향 · 양 끝이 정의를 따르는 연결이다. 실제 대상이 맞는지는 따로 본다.

## SLIDE 24 — Cypher 패턴: 경보 태그 TS1에서 유온 한계까지
### 화면 내용
- 유형: 코드
- 메시지: **Cypher**는 찾을 연결을 괄호와 화살표로 적는 질의 언어로, 경보 규칙의 태그에서 그 물리량까지 한 패턴으로 잇는다.
- 코드: // 경보 규칙의 TS1: 이 센서가 읽는 물리량과 한계는? / (s:Sensor {tag: 'TS1'})-[:OBSERVES]->(v:StateVariable) /  / ── 조각마다 ── / ( )              노드 하나 / s, v             변수: 찾은 노드를 뒤에서 부르는 이름 / :Sensor          레이블: 노드의 종류 / {tag: 'TS1'}     속성 조건: 경보의 태그로 좁힌다 / -[:OBSERVES]->   관계 이름과 저장된 방향 /  / ── 포털 기준 그래프에서 이 패턴에 맞는 곳 ── / (sen:ts1 유온 센서)-[:OBSERVES]->(sv:ts1 유온) / v.limit 65 · v.unit '℃'
- 요소:
  1. **출발은 경보의 태그** | 쿨러 성능 저하 경보의 규칙에 적힌 TS1을 속성 조건에 넣어 센서를 고른다.
  2. 방향은 저장된 대로 | 센서가 물리량을 읽으므로 화살표를 센서에서 유온 쪽으로 적는다.
  3. 변수와 식별자 | s, v는 이 쿼리 안에서만 쓰는 이름이다. 'sen:ts1' 같은 id와 다르다.
  4. tag로 고를 때 | tag에는 유일 제약이 없다. 한 대상을 계속 가리켜야 하면 id로 찾는다.
- 노트: [짚을 곳] 코드 맨 위 주석(담당자의 물음) → 패턴 한 줄 → 조각별 설명 → 맨 아래 맞는 곳 → 오른쪽 넷째 칸 / · 질의(쿼리) = DB에 보내는 요청. Cypher = 그래프 DB 쿼리 언어. 쿨러 사건에서 에이전트가 원인 후보를 찾은 것도 Cypher / · 패턴 = 찾을 연결을 그림 모양 그대로 글자로 적은 것. DB는 맞는 곳을 모두 찾는다 / · 둥근 괄호 = 노드, 콜론 뒤 = 레이블, 콜론 앞 = 변수(뒤에서 다시 부르는 이름, 점 + 속성으로 값을 읽음. 식별자와 다름), 중괄호 = 속성 조건(태그 TS1로 좁힘), 대괄호 = 관계 이름, 화살표 = 저장된 방향(센서 → 유온) / · 결과: 유온 센서 → 유온, 한계 65 ℃ · 단위 → 경보 태그 하나에서 기준까지 패턴 한 줄 / · 태그에는 유일 제약이 없어 늘 하나라는 보장이 없다 → 대상을 계속 가리킬 땐 식별자로 / · 실행 화면(Neo4j Browser) = 조건을 직접 적어 묻는 곳. 포털 지식 지도는 항목을 골라 기준 지식을 따라가는 화면 / [다음] MATCH · RETURN: 찾은 연결과 돌려받는 항목

## SLIDE 25 — MATCH · RETURN: 찾은 연결과 돌려받는 항목
### 화면 내용
- 유형: 코드
- 메시지: MATCH가 찾은 연결 하나가 결과의 한 행이 되고, RETURN은 그 행에 값을 담을지 노드를 담을지 정한다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[r:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / c.name         s.tag / "오일 쿨러"    "TS1" / "오일 쿨러"    "CE" /  / ── 같은 MATCH에 RETURN c, r, s ── / (:Component)-[:MONITORED_BY]->(:Sensor {tag: 'TS1'}) / (:Component)-[:MONITORED_BY]->(:Sensor {tag: 'CE'})
- 요소:
  1. MATCH | 오일 쿨러에서 계측 관계로 이어진 센서를 모두 찾는다.
  2. **한 행 = 연결 하나** | 연결이 둘이라 두 행이다. 이름이 두 번 나와도 쿨러 노드는 하나이다.
  3. 값을 돌려받기 | c.name, s.tag는 속성값이라 표로 읽는다.
  4. 노드 · 관계를 돌려받기 | c, r, s를 받으면 쿨러 하나에 센서 둘이 이어진 그래프로 그린다.
- 노트: [짚을 곳] 코드 MATCH → RETURN → 결과 두 행 → 아래 노드 · 관계 반환 → 오른쪽 강조한 「한 행 = 연결 하나」 / · 절 = 쿼리를 하는 일별로 나눈 부분. MATCH = 찾을 패턴(이름이 오일 쿨러인 구성 요소에서 계측 관계로 이어진 센서), RETURN = 돌려받을 항목(쿨러 이름 · 센서 태그 → 두 열) / · 결과: 쿨러-유온 센서, 쿨러-냉각 효율 채널. 연결 하나가 한 행 → 두 행. 쿨러 노드가 둘이라서가 아니다 / · 같은 MATCH에 노드 · 관계 자체를 받으면 그림으로 쿨러 하나에서 센서 둘로 선 → 두 행의 쿨러가 같은 노드 / · 센서 목록 보고엔 값을, 연결이 맞게 이어졌는지 눈으로 확인할 땐 노드와 관계를 받는다 / [다음] 조회된 행 중 원하는 값만 남길 조건

### 화면 구성
코드의 글자·위치·글꼴과 오른쪽 설명 위치는 보존한다. 코드 배경은 x=0.600, y=2.059, 폭7.4, 높이3.742인치이고, 코드 글상자는 같은 윗자리에서 높이3.442인치로 맞춘다. 내용에 맞춰 배경과 글상자 높이만 줄인다.

## SLIDE 26 — WHERE: 찾은 행을 거르는 조건
### 화면 내용
- 유형: 코드
- 메시지: 보호 한계가 있는 채널만 경보 점검 목록에 남길 때 WHERE를 쓰며, IS NOT NULL은 값이 있는지만 본다.
- 코드: // 보호 한계가 정해진 채널만 점검 목록에 / MATCH (s:Sensor)-[:OBSERVES]->(v:StateVariable) / WHERE v.limit IS NOT NULL / RETURN s.tag, v.name, v.limit, v.unit / ORDER BY s.tag /  / ── 결과 ── / "PS1"  "토출 압력"  130   "bar" / "TS1"  "유온"       65    "℃" / "VS1"  "팬 진동"    2.0   "mm/s" /  / ── 걸러진 행 ── / CE 냉각 효율 · FS1 유량: limit 값 없음
- 요소:
  1. 거르는 자리 | MATCH가 찾은 다섯 행 가운데 조건에 맞는 행만 RETURN으로 넘긴다.
  2. **IS NOT NULL** | 한계가 적혀 있는지만 묻는다. 「0보다 크다」와 다른 조건이다.
  3. 빠진 두 채널 | CE · FS1도 MATCH는 찾았지만 한계 칸이 비어 목록에서 빠진다.
  4. 남은 세 한계 | 130 bar · 65 ℃ · 2.0 mm/s는 단위가 달라 크기끼리 견주지 않는다.

## SLIDE 28 — CREATE · MERGE · SET: 새로 만들기와 찾아서 쓰기
### 화면 내용
- 유형: 코드
- 메시지: 적재를 중간에 멈췄다가 다시 돌려도 센서가 하나로 남으려면, 식별자로 찾고 없을 때만 만드는 MERGE를 쓴다.
- 코드: CREATE (s:Sensor {id: 'sen:ts1', /                   name: '유온 센서', /                   tag: 'TS1'}) /  / MERGE (s:Sensor {id: 'sen:ts1'}) / SET s.name = '유온 센서', /     s.tag  = 'TS1', /     s.unit = '℃' /  / ── sen:ts1이 이미 있을 때 CREATE의 결과 ── / Node(…) already exists with label `Sensor` /   and property `id` = 'sen:ts1'
- 요소:
  1. **CREATE** | 있는지 보지 않고 새 노드를 만든다. 같은 id가 있으면 유일 제약이 거절한다.
  2. **MERGE** | 패턴에 맞는 노드를 찾아 쓰고, 없을 때만 만든다.
  3. SET | 찾았거나 만든 노드에 속성값을 넣는다.
  4. 쓰는 자리 | 시드는 CREATE 없이 MERGE · SET으로 적어 다시 돌려도 같다. 매번 새로 남길 기록은 CREATE로 만든다.
- 노트: [짚을 곳] 맨 위 CREATE → 맨 아래 오류 메시지 → 가운데 MERGE와 SET → 오른쪽 넷째 칸 / · CREATE = 있는지 안 보고 새 노드. 같은 식별자가 있으면 유일 제약이 거절(아래 메시지) / · MERGE = 식별자로 찾아 있으면 쓰고 없을 때만 만든다. SET = 찾았거나 만든 노드에 이름 · 태그 · 단위. 찾는 일과 값 넣는 일을 나눠 적었다 / · 적재를 중간에 멈추고 처음부터 다시 돌려도 MERGE면 같은 센서가 하나로 남는다 / · 이 시스템의 기준 그래프 파일도 CREATE 없이 MERGE와 SET으로 적어 다시 실행해도 결과가 같다 / · 매번 새 대상이 생겨야 하는 곳(문서 적재 때마다 「언제 무엇을 넣었다」 기록)엔 CREATE. 새 대상인가, 같은 대상을 다시 다루나로 고른다 / [다음] 다시 넣은 설비 모델을 같은 질문으로 확인하는 방법

## SLIDE 39 — 결정 · 결정표 · 규칙으로 쿨러 사건 판정하기
### 화면 내용
- 유형: 코드
- 메시지: 결정표는 한 물음에 답하는 규칙 행의 모음이라, 같은 입력을 대면 누가 판정해도 행마다 같은 결과가 나온다.
