# 점검 요청 기능 — 긴급 확인 표시 추가 명세

## 목표

- 점검 요청 결과마다 긴급 확인 표시(`urgent`)와 그 근거(`긴급_근거`)를 더해, 받는 사람이 요청 초안에서 표시의 이유와 확인할 항목을 함께 읽게 한다.
- 처리 시간 단축 · 처리 순서 변경 · 승인 생략은 이번 목표가 아니다.
- 지킬 것: 일반 요청의 기존 결과(상태 · 보류_사유 · 사례 · 사례_확인 · 질문 · 초안 · 확인_항목_변화 · 승인 · 후속_업무 · 상태_기록)의 이름 · 형식 · 뜻.

## 입력

- 요청: `source/입력/점검_요청.json`의 번호 · 설비 · 경보_패턴 · 사례 · 요청_글(요청_글은 칸의 값이 아님).
- 판정 값: 정해진 사례의 `센서_입력.json`에서 판단할 때 읽는다 — `freshness`(TS1 · ok), `readings`의 `TS1 · avg · 120`의 `value`와 `coverage.covered`.
- 사람: `source/사람/답변.json`(정보), `source/사람/승인.json`(결정). 온톨로지 · 매뉴얼은 기존과 같다.

## 출력 계약

- 기존 항목은 이름 · 형식 · 뜻을 바꾸지 않는다. 상태 값은 `접수` · `질문 대기` · `재개` · `보류` · `승인 대기` · `승인됨` · `거절` 그대로다.
- 더하는 항목(요청 결과의 맨 위 칸):
  - `urgent`: `true` · `false` · `null`. `null`은 「긴급 아님」이 아니다.
  - `긴급_근거`: `구분`(긴급 · 긴급 아님 · 미판정 · 적용 대상 아님), `기준`, `판정_값`, `신선도_ok`, `표본_covered`, `이유`.
- 초안이 있으면 `초안.긴급_확인_표시`에 같은 값을 넣어, 초안만 읽어도 표시 · 이유 · 확인 항목이 함께 보이게 한다. `점검_요청.md`의 요청마다 한 줄로 보인다.

## 금지 조건

- 승인 없이 `승인됨`으로 바꾸거나 후속 업무를 만들지 않는다. 긴급이라도 질문 · 승인 단계를 건너뛰지 않는다.
- 모르는 값을 짐작하지 않는다: 값 없음 · 신선도 실패 · 표본 부족을 `false` · 0 · 이전 값으로 채우지 않는다.
- 답변을 승인으로 받지 않는다(「급하니 승인한 걸로」도 정보일 뿐).
- 실제 설비 기준(60 ℃ 초과 경고 · 65 ℃ 인터록)과 승인 역할 · 등급을 바꾸지 않는다.

## 긴급 조건과 유효성

- 적용 대상: 정해진 사례(사례가 없으면 요청)의 경보 패턴이 `COOLER_DEGRADATION`일 때만. 다른 경보는 `urgent: null`, 구분 「적용 대상 아님」, 기존 처리 그대로. (결정: 다른 경보를 `false`로 두면 「조건을 적용해 긴급이 아니라고 판정했다」로 읽히므로 null + 구분으로 남긴다.)
- 판정 순서: 적용 대상 → 사례가 정해졌는가 → 신선도 `freshness.ok = true` → 값 있음 → 표본 `coverage.covered = true` → 비교.
- 유효하고 평균 ≥ 60 ℃ → `true`, 유효하고 < 60 ℃ → `false`. 60.0 ℃는 `true`(교육용 「이상」, 운전 화면의 「초과」와 다르다).
- 사례 미정 · 신선도 실패 · 값 없음 · 표본 부족 → `null`, 구분 「미판정」, 이유에 어느 것인지 적는다.
- 미판정이어도 요청의 상태는 바꾸지 않는다(결정: 긴급 표시는 표시일 뿐 관문이 아니다 — 상태를 바꾸면 기존 승인 조건이 바뀐다). 요청이 다른 까닭으로 보류이면 `보류_사유`는 그 까닭 그대로다.

## 수용 기준

1. 같은 원자료로 실행했을 때 요청 R01~R10의 기존 항목(상태 · 사례 · 질문 · 초안의 근거 상태 · 확인 항목 · 승인 · 후속 업무)이 변경 전 결과와 같다.
2. 모든 요청 결과에 `urgent`와 `긴급_근거`가 있다(빠진 요청이 없다).
3. 쿨러 경보 · 유효한 TS1 120초 평균 ≥ 60 ℃인 요청은 `urgent is True`, < 60 ℃는 `urgent is False`다.
4. 쿨러 경보에서 신선도 실패 · 값 없음 · 표본 부족 · 사례 미정이면 `urgent is None`, 구분 「미판정」, 이유가 비어 있지 않다.
5. 쿨러 경보가 아닌 요청은 `urgent is None`, 구분 「적용 대상 아님」이고 다른 항목은 변경 전과 같다.
6. `urgent`가 true여도 승인 기록 없이 `승인됨`이 되지 않고, 거절된 요청의 후속 업무는 0건이다.
7. 초안이 있는 요청은 `점검_요청.md`에서 긴급 표시 · 이유 · 확인 항목을 함께 읽을 수 있다.
8. 실행 번호 · 시각처럼 매번 달라질 수 있는 값은 없고, 같은 입력으로 다시 실행하면 결과 파일이 같다.
