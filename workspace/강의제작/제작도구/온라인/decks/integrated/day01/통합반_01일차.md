## SLIDE 22 — 공장 쪽 망 OT와 사무 쪽 망 IT

- 아이콘: engine, world
- 메시지: 설비 쪽 망과 사무 쪽 망은 지킬 것이 달라서, 두 망을 나누고 직접 잇지 않는다.
- 요소:
  1. OT | Operational Technology / 공장 안 설비 쪽 망 / 설비를 감시하고 움직인다 / 잘못된 명령 하나가 곧 사고다 | 멈추지 않음 · 안전

- 노트: [짚을 곳] 왼쪽 OT → 오른쪽 IT, 카드 끝 줄의 지킬 것 / · 지금까지 본 설비 · PLC · 엣지 · 브로커는 모두 공장 안에 있다. 값을 분석하고 AI가 원인을 따지는 서버는 사무실 쪽에 있다. 층으로 보면 Layer 1 · 2는 공장 안에, Layer 3부터 위는 사무실 쪽에 놓인다. 둘을 어떻게 이을까 / · OT(Operational Technology, 운영 기술) = 공장 안 설비 쪽 망. 설비를 감시하고 움직인다. 가장 먼저 지킬 것은 설비가 멈추지 않는 것과 사람 · 설비의 안전. 잘못된 명령 하나가 곧 사고가 된다 / · IT(Information Technology, 정보 기술) = 사무실 컴퓨터 쪽 망. 업무 데이터 · 분석 · AI를 다룬다. 메일 · 인터넷과 이어져 있어 뚫릴 가능성이 늘 있다. 그래서 허가된 사람만 보고 바꾸게 하는 것이 먼저다 / · 둘을 줄 하나로 바로 이으면: 사무실 PC 한 대가 뚫렸을 때 그 길로 PLC까지 닿는다 → 정보 사고가 설비 사고가 된다 / · 그래서 두 망을 나누고 직접 잇지 않는다(망 분리, Network Segmentation). 그래도 값은 건너가야 하므로 사이에 건너는 자리를 따로 둔다 / · 보호를 PLC에 둔 것과 같은 까닭: 위쪽이 멈추거나 뚫려도 공장은 홀로 돌아야 한다 / [다음] 두 망 사이에 두는 완충 구역
### 화면 구성

### 제작 기준

## SLIDE 23 — 세 보안 영역과 DMZ: 값은 공장 안에서 내보낸다
### 화면 내용
- 유형: 구조
- 메시지: OT와 IT 사이에 완충 구역 **DMZ**(Demilitarized Zone)를 두어, 망을 **세 보안 영역**으로 나눈다.
- 영역: OT | DMZ | IT
- 요소:
  1. 현장 · PLC · 운전 화면 | 제어와 조작 | OT
  2. 브로커 | 지금 값의 허브 | OT
  3. **DMZ 중계** | OT가 연 연결로 받은 값을 넘긴다 | DMZ
  4. 이벤트 로그 | 넘겨받은 값을 쌓는다 | IT
  5. 분석 · AI | 쌓인 값을 읽는다 | IT
- 연결: 브로커 > DMZ 중계 ; DMZ 중계 > 이벤트 로그
- 노트: [짚을 곳] 위 세 띠(OT · DMZ · IT) → 왼쪽 OT 두 상자 → 가운데 강조한 DMZ 중계 → 오른쪽 IT, 화살표 방향 / · DMZ(Demilitarized Zone, 비무장 지대) = OT와 IT 사이에 따로 둔 완충 구역. 아파트 택배 보관함을 떠올리면 된다: 택배 기사는 집 안까지 들어오지 않고 보관함에 넣고 간다. 공장도 값을 보관함(DMZ)까지만 내보내고, 바깥은 보관함에서만 꺼내 간다. 닮은 점 = 바깥이 안으로 들어오지 않는다. 다른 점 = 여기서는 공장 쪽이 먼저 보관함으로 연결을 열어 값을 밀어 넣는다 / · 세 보안 영역 = 망을 OT · DMZ · IT 셋으로 나눈 것. 영역마다 서로 닿을 수 있는 범위가 정해진다. IT와 OT는 DMZ에서만 만나고, IT에서 OT로 곧장 가는 길은 없다 / · 연결은 OT 쪽이 먼저 연다: OT의 브로커가 DMZ 중계 쪽으로 연결을 열고 값을 밀어 보낸다. 바깥이 OT 안으로 들어와 값을 끌어가지 않는다 / · 왜 방향이 중요한가: 「OT가 먼저 연 연결만 허용」으로 문 단속이 단순해지고, DMZ가 뚫려도 그쪽에서 OT로 새 연결을 열 수 없다 / · 값도 한 방향: OT → DMZ → IT. DMZ 중계는 받은 값을 IT의 이벤트 로그에 옮겨 쓰고, 분석 · AI는 그 쌓인 값을 읽을 뿐 OT로 접속하지 않는다 / · 현업에서는 이렇게 층을 나눈 망 그림을 Purdue 모델로, 구역과 그 사이 통로를 나누는 보안 방식을 IEC 62443으로 부른다 / [다음] 공장 안 오래된 통신 약속의 약점과, 겹겹이 지키는 방법
### 화면 구성
OT · DMZ · IT 세 띠. 데이터 화살표는 왼쪽에서 오른쪽으로만 간다. 오른쪽에서 왼쪽으로 가는 화살표를 그리지 않는다.
### 제작 기준
「All connections with the OT environment should be initiated as outbound connections from within the OT environment.」: OT 연결 원칙 p.11(현업조사 19 C2가 12 §1-B의 근거를 이 문서로 바로잡음). OT와 IT의 외부 연결은 DMZ를 거침: 같은 문서 p.19 · p.25(현업조사 19 C1). Purdue 모델(망 층)과 IEC 62443 영역 · 통로(보안 경계): 현업조사 12 §1-A. OT가 밀어내고(push) 바깥은 DMZ에서만 끌어감: CISA Defense in Depth 2016 §2.4.2(현업조사 16 §4-2 ①). AI는 OT 밖에서 밀려 나온 데이터를 씀: CISA 외 AI-OT 지침 p.15 · p.20(현업조사 12 §1-B 3).

## SLIDE 24 — 오래된 현장 규약과 심층 방어
### 화면 내용
- 유형: 풀이
- 메시지: 보호 기능이 없는 오래된 현장 규약은 OT 안에 가두고, 여러 겹의 방어로 보완한다.

약점(규약) → 가두기(격리) → 겹겹 방어의 순서로 세 줄을 둔다.

IT에서 시계열 저장소를 읽어 추세를 그리고, 경보와 조치 시점을 겹쳐 본다. 읽기만 하고 설비를 움직이지 않는다 / · 같은 층인데 영역이 다른 까닭: 조작하는 화면은 설비 곁(OT), 분석만 하는 화면은 사무 쪽(IT). 앞의 망 분리가 화면에도 그대로 적용된다 / · 인프라 감시: 서버 · 망 · 프로그램이 살아 있는지 보는 화면도 따로 둔다. 운전원이 아니라 시스템 담당이 받는다 / · 이 역할에는 HMI로 Ignition · WinCC, 대시보드로 Grafana 같은 것이 쓰인다 / [다음] 화면에 뜨는 알림의 종류

### 화면 내용

### 제작 기준

- 노트: [짚을 곳] 왼쪽 맡기는 것 → 오른쪽 강조한 맡기지 않는 것 / · 맡기는 것: 데이터와 지식을 읽고, 계산하고, 원인을 진단하고, 추천안을 쓰는 일. 사람보다 빠르고 지치지 않는다 / · 맡기지 않는 것 셋: 설비에 명령을 보내는 권한, 안전에 관한 결정, OT 안으로 늘 열려 있는 연결. 예: 새로 온 유능한 분석가에게 자료는 다 보여 주지만, 공장 기계 스위치 열쇠는 주지 않는 것 / · 왜: AI는 그럴듯하게 틀릴 수 있다. 틀린 추천은 사람이 걸러 내면 되지만, 틀린 명령은 곧 설비 사고다 / · 연결로 보면: 에이전트가 OT에 늘 붙어 있으면 그 자체가 공격자가 OT로 들어오는 길이 된다. 그래서 에이전트는 IT에 두고, OT에서 밀려 나온 데이터만 읽는다 / · 정리: 에이전트는 「무엇을 하면 좋을지」를 말하고, 「해도 된다」는 결정은 사람이, 「실제로 하는 일」은 OT가 한다 / [다음] 그 결정을 내리는 사람의 자리
### 화면 구성
두 비교 칸을 같은 물음(읽기, 판단, 실행)으로 맞세운다.
### 제작 기준
사람이 개입하지 않는 AI의 OT 능동 제어 제한, AI · LLM은 OT 안전 결정에 쓰지 않음: CISA 외 AI-OT 지침 p.8 · p.16(현업조사 12 §1-E C5). AI가 OT로 들어가는 상시 공격 경로가 되지 않게 push 방식: 같은 지침 p.15 · p.20(현업조사 12 §4-3 3-A). 확인한 사례 중 에이전트가 제어기에 직접 쓰는 것은 없음: 현업조사 12 §4-3 3-C.

## SLIDE 37 — Layer 9 · 프로세스 · 승인 · 앱
### 화면 내용
- 유형: 풀이
- 메시지: 추천안은 사람이 근거를 보고 승인해야 실행되며, 이 구조를 **HITL**이라 한다.
- 요소:
  1. **HITL** | 사람의 판단을 거쳐야 다음 단계로 넘어가는 구조이다. | Human-in-the-Loop
  2. 승인 · 거절 | 담당자가 추천안과 근거를 읽고 승인하거나 거절한다. / 거절하면 실행하지 않는다. | 사람의 결정
  3. 담당자 | 그 조치를 승인할 권한이 정해진 사람이다. / 운전 조치는 운전 책임자, 정비는 정비 책임자처럼 나뉜다. | 승인 권한
  4. 변경 관리 | 설비를 바꾸는 일은 정해진 절차로 허락받는다. / AI의 추천도 이 절차에 들어간다. | Change Management
  5. 제조 실행 시스템(MES) | 생산 지시 · 실적 · 납기를 관리하는 시스템이다. / 담당자는 조치가 생산에 주는 영향을 여기서 본다. | Manufacturing Execution System
- 노트: [짚을 곳] 강조한 HITL → 승인 · 거절 → 담당자 → 변경 관리 → 제조 실행 시스템 / · Layer 9 · 프로세스 · 승인 · 앱: 추천을 실제 업무로 바꾸는 층. 사람의 결정과 업무의 순서가 여기 있다 / · HITL(Human-in-the-Loop) = 사람이 고리 안에 있는 구조. 자동으로 흐르다가도 사람이 판단해야 다음으로 넘어간다. 예: 회사에서 직원이 기안을 올려도 팀장이 결재하기 전에는 돈이 나가지 않는다. AI가 기안을 쓰고, 결재는 사람이 한다 / · 승인 · 거절: 담당자는 추천안만 보지 않고 근거(어떤 값을 보고, 어떤 원인을 빼고 남겼는지)를 읽고 결정한다. 거절하면 아무것도 설비로 내려가지 않는다 / · 담당자: 아무나가 아니라 그 조치를 허락할 권한이 정해진 사람. 운전을 바꾸는 조치와 정비를 하는 조치는 승인하는 사람이 다르다 / · 변경 관리: 공장에서 설비 설정을 바꾸는 일은 원래 「누가 · 왜 · 무엇을 바꿨는지」 남기며 허락받는 절차가 있다. AI의 추천도 새 길을 만들지 않고 이 절차에 들어간다 / · 제조 실행 시스템(MES, Manufacturing Execution System) = 공장의 생산 지시 · 실적 · 납기를 관리하는 시스템. 「오늘 무엇을 몇 개, 언제까지」가 여기 있다. 설비를 세우는 조치는 생산을 멈추게 하므로, 담당자는 승인하기 전에 이 조치가 납기에 무슨 영향을 주는지 본다 / · 왜 사람인가: 설비와 생산 · 납기 사이에서 무엇을 감수할지는 책임을 지는 사람이 정한다. AI는 근거를 모아 주고, 결정과 책임은 사람에게 남는다 / [다음] 승인을 포함한 업무 한 건을 이끄는 장치
### 화면 구성
정의 → 결정 → 결정하는 사람 → 절차 → 결정에 보는 생산 정보의 순서로 다섯 줄.
### 제작 기준
AI 권고를 기존 변경 관리 절차에 넣어 사람이 결정: CISA 외 AI-OT 지침 p.18-19(현업조사 12 §1-F 명령 안전 장치 표 「사람 승인」). 변경을 허락하는 결정은 변경 관리 절차의 책임자가: OT 연결 원칙 p.5 · p.15(현업조사 16 §5). 이름 「승인 · 거절」: 기술사실표 「같은 말 · 같은 값」. MES는 L3에서 작업 지시 · 생산을 관리: 현업조사 12 §1-A(ISA-95 L3) · §1-D H11. 이름 「제조 실행 시스템(MES)」: 기술사실표 「같은 말 · 같은 값」.

## SLIDE 38 — 프로세스 엔진과 판단 기록
### 화면 내용
- 유형: 단계
- 메시지: **프로세스 엔진**(Process Engine)은 사건 한 건을 정한 순서대로 이끌고, 단계마다 기록을 남긴다.
- 요소:
  1. 사건을 연다 | 경보 한 건에 / 처리 한 건을 연다
  2. 판단 기록을 남긴다 | 원인 진단과 / 조치 추천을 남긴 / 기록 한 건
  3. **승인을 기다린다** | 담당자에게 넘기고 / 승인 · 거절을 받는다
  4. 요청을 보낸다 | 승인된 조치만 / 설비로 보낼 / 요청을 만든다
  5. 결과를 닫는다 | 결과를 확인하고 / 남은 정비는 / 작업지시로 잇는다
- 노트: [짚을 곳] 단계 다섯 칸 왼쪽부터 → 둘째 판단 기록 → 셋째 강조한 승인 / · 프로세스 엔진(Process Engine) = 업무 순서를 미리 그려 정해 두고, 사건 한 건마다 그 순서대로 다음 단계를 부르는 프로그램. 이 역할에는 Camunda 같은 것이 쓰인다 / · 사건을 연다: 경보 한 건이 들어오면 그 처리 한 건을 연다. 이 한 건 안에서 모든 단계가 이어진다 / · 판단 기록 = 원인 진단과 조치 추천을 남긴 기록 한 건. 에이전트의 추천안이 여기 담긴다 / · 승인을 기다린다: 담당자에게 넘기고 답을 기다린다. 사람이 답하지 않으면 다음으로 가지 않는다 / · 요청을 보낸다: 승인된 조치만 설비 쪽으로 보낼 요청으로 만든다. 거절이면 여기서 멈춘다 / · 결과를 닫는다: 설비가 실제로 좋아졌는지 확인하고, 사람이 손봐야 할 정비가 남으면 정비 관리 시스템의 작업지시로 잇는다 / · 왜 엔진이 필요한가: 단계가 많고 사람이 끼면 「지금 어디까지 왔나」를 잃기 쉽다. 엔진이 순서를 지키고 단계마다 기록을 남긴다. 예: 택배 조회 화면처럼 접수 → 집하 → 배송 중 → 완료가 한 건마다 차례로 찍히고, 앞 단계를 건너뛰지 않는다 / [다음] 승인된 요청이 설비까지 내려가는 길
### 화면 구성
다섯 단계를 왼쪽에서 오른쪽으로. 판단 기록 칸에 정의를 둔다. 식별자 형식은 싣지 않는다.
### 제작 기준
AI 제안 → 정비 요청(사건) → 사람 승인 → 명령 요청 → … → ACK 대조 → 재관측 → 기록: 현업조사 13 F2 · 결정표 23행. 정비 활동(요청 → 작업지시 배정 → 실행 → 추적): ISA-95 Part 3(현업조사 13 F2). 작업지시는 사람에게 간다: 현업조사 16 §4-1(CMMS 행). 정의 「판단 기록」: 기술사실표 「같은 말 · 같은 값」.

- 메시지: 무엇을 할지는 IT가 정해도, 지금 실제로 해도 되는지는 설비 곁 OT 안에서 정한다.

### 화면 구성
연속된 IT · DMZ · OT 영역 위에 다섯 자리를 놓고, 자리마다 그곳이 정하는 것 한 줄을 둔다. 검사 항목 목록과 토픽 이름은 싣지 않는다.
### 제작 기준

AI 권고를 기존 변경 관리 절차에 넣음: CISA 외 AI-OT 지침 p.18-19. 실라버스 온라인 8행 끝 문장(명령 게이트웨이와 설비 제어 영역이 필요한 이유).

## SLIDE 40 — 확인 응답 · 재관측 · 회복 판정
### 화면 내용
- 유형: 단계
- 메시지: PLC의 **확인 응답**은 명령을 처리했는지를, 재관측은 설비가 실제로 좋아졌는지를 알린다.
- 요소:
  1. 요청 | 승인된 조치를 / 설비 쪽에 보냈다
  2. **확인 응답(ACK)** | Acknowledgement / PLC가 알리는 / 명령 처리 결과
  3. 재관측 | 명령 뒤 / 다시 읽은 / 계측값
  4. **회복 판정** | 재관측 값이 / 회복 기준 안에 들고 / 경보가 해제됐는지 본다
- 노트: [짚을 곳] 단계 네 칸 왼쪽부터 → 둘째 강조한 확인 응답 → 셋째 재관측 → 넷째 강조한 회복 판정 / · 보낸 뒤 세 물음을 따로 묻는다: 처리됐나, 설비가 실제로 좋아졌나, 이제 끝내도 되나 / · 확인 응답(ACK, Acknowledgement) = PLC가 알리는 명령 처리 결과. 받아서 처리했는지, 거부했다면 왜인지(지금 받을 수 없는 때, 인터록 등)를 돌려준다 / · 재관측 = 명령 뒤 다시 읽은 계측값. 팬을 바꿨다면 그 뒤 온도가 실제로 내려가는지 본다 / · 예: 「배송 완료」 문자(확인 응답)가 와도, 문 앞에 가서 물건이 있는지 봐야(재관측) 정말 받은 것이다 / · 왜 둘을 따로 보나: 처리했다는 응답이 와도 온도가 계속 오르면 문제는 그대로다. 거꾸로 온도가 내려갔어도 명령이 처리된 덕인지는 응답을 봐야 안다 / · 회복 판정 = 조치 뒤 재관측 값이 정해 둔 회복 기준 안으로 돌아오고, 경보가 해제됐는지 확인하는 판단. 이것이 맞아야 사건을 닫는다 / · 결과 되돌림: 응답과 새 상태는 올라가는 길(데이터 경로)을 따라 다시 위로 올라온다 / [다음] 원천 값이 판단 결과가 되기까지의 흐름
### 화면 구성
