## SLIDE 19 — 카디널리티의 네 가지 표기
### 화면 내용
- 유형: 표
- 메시지: **카디널리티**(Cardinality)는 관계 한쪽 대상 하나에 이어질 수 있는 반대쪽 대상의 수다.
- 머리: 표기 | 뜻 | 쿨러 사건의 관계 유형
- 요소:
  1. 1:1 | 양쪽 모두 하나에 하나 | 팬 인버터 → 팬 속도 / (MANIPULATES)
  2. 1:N | 시작 하나에 끝 여럿 / 호기마다 둔 그림 | HYD-02 → 구성 요소 / (HAS_COMPONENT)
  3. N:1 | 시작 여럿이 끝 하나에 | 고장 유형 → 구성 요소 / (OCCURS_IN)
  4. N:M | 양쪽 모두 여럿 | 구성 요소 → 부품 / (USES_PART)
  5. **함께 쓰는 그림이면** | 같은 HAS_COMPONENT가 N:M | 기종 하나의 쿨러를 / 세 설비가 가리킨다
- 노트: [짚을 곳] 표 위 네 줄: 왼쪽 표기 → 가운데 뜻 → 오른쪽 쿨러 사건의 관계 → 하늘색 다섯째 줄 → 화면 위 문장 / · 카디널리티 = 관계 한쪽 대상 하나에 이어질 수 있는 반대쪽 대상의 수. 두 점 왼쪽이 시작 쪽, 오른쪽이 끝 쪽이고 N · M은 여럿. 읽을 때는 양쪽 끝에 한 번씩 서서, 이쪽 하나에서 저쪽이 몇 개인지를 차례로 묻는다 / · 1:1: 팬의 속도를 바꾸는 장치 하나가 팬 속도 하나를 맡고, 팬 속도 쪽에 서도 그 장치는 하나뿐 / · 1:N: 설비마다 쿨러를 둔 그림에서 설비 한 대에 오일 쿨러 · 쿨러 팬 · 주 펌프처럼 구성 요소가 여럿. 쿨러 쪽에 서면 설비 한 대에만 속한다 / · N:1: 시작 쪽 고장 유형 하나에 서면 일어나는 곳은 구성 요소 하나. 거꾸로 구성 요소 하나에서는 여러 고장 유형이 일어날 수 있다 / · N:M: 구성 요소 하나가 부품을 여럿 쓰고, 같은 부품이 여러 구성 요소에 쓰일 수도 있다고 정한 경우. 같은 규격의 베어링을 여러 팬에 쓰면 그 베어링이 어느 팬들에 들어가는지 거꾸로 찾아야 한다 / · 다섯째 줄: 쿨러 하나를 세 설비가 함께 쓰는 그림이면 설비와 구성 요소 사이가 N:M. 그리는 법을 고른 순간 그 관계의 카디널리티도 함께 정했다 / [다음] 수를 잘못 정하면 질문의 답까지 달라진다

### 화면 내용

- 메시지: **Cypher**는 노드와 관계의 모양으로 그래프 DB에 묻는 쿼리 언어이며, 찾는 문장은 세 절(Clause)로 된다.
- 요소:

  3. 찾는 문장의 절 | 찾을 모양 → 고를 조건 → 돌려받을 것 / 절마다 MATCH · WHERE · RETURN을 쓴다 | Clause

Neo4j 같은 그래프 DB가 알아듣는 그 말이 Cypher. 관계 그림을 내보냈을 때 나온 문장도 Cypher였다. 찾을 것을 노드와 관계의 모양으로, 그림 그리듯 적는다 / · 찾는 쿼리는 세 부분: 무엇을 찾을지 → 그 가운데 무엇만 고를지 → 무엇을 돌려받을지. 고를 게 없으면 가운데는 뺀다. 부분 하나하나 = 절. 맨 앞에 붙이는 낱말이 MATCH · WHERE · RETURN, 하나씩 차례로 써 본다 / [다음] 평소 말로 물으면 DB 앞에서 길이 하나로 정해지지 않는다

## SLIDE 49 — Cypher 패턴의 표기
### 화면 내용
- 유형: 표
- 메시지: 노드는 ( ), 관계는 -[ ]->, 레이블은 :, 속성은 { }로 적고, 찾은 대상은 **변수**(Variable)로 다시 부른다.
- 머리: 표기 | 적는 꼴 | 쿨러 사건에서
- 요소:
  1. 노드 | ( ) | (c:Component)
  2. 관계 | -[ ]-> | -[:MONITORED_BY]->
  3. 레이블 · 관계 유형 | : 뒤에 이름 | :Sensor · :OBSERVES
  4. 속성 | { 이름: 값 } | {id: 'HYD-02:TS1'}
  5. 변수 | 괄호 맨 앞 이름 / 찾은 대상을 다시 부른다 | c · s
  6. **거슬러 찾기** | 저장된 방향대로 적고 출발 노드만 바꾼다 / (s:Sensor)<-[:MONITORED_BY]-(c) | 센서에서 출발
- 노트: [짚을 곳] 표 여섯 줄을 위에서부터: 노드 → 관계 → 쌍점 → 속성 → 다섯째 줄 변수 → 하늘색 마지막 줄 거슬러 찾기 / · 위 네 줄은 앞 장 코드를 읽는 법, 새로 나온 건 다섯째 줄과 마지막 줄 / · 노드는 둥근 괄호로 감싼다. 관계 그림의 원 하나가 괄호 하나 / · 관계는 짧은 줄 끝에 화살표 머리를 단 모양, 가운데 대괄호 안에 관계 이름. 머리가 향하는 쪽이 관계의 방향 / · 쌍점: 괄호 안에서 낱말 앞에 찍으면 그 낱말이 이 노드의 레이블이라는 표시. 화살표 안에서는 관계 이름 앞에. 다른 글자와 헷갈리지 않게 표시한다 / · 속성은 중괄호로 묶어 속성 이름과 값을 쌍점으로 이어 적는다. 앞 장의 쿨러 식별자 · 센서 태그 / · 변수: 앞에서 찾은 쿨러를 뒤에서 다시 가리킬 때가 많다(「그 쿨러의 이름을 보여 줘」). 긴 패턴을 다시 적지 않고, 찾은 쿨러에 짧은 이름을 붙여 그 이름으로 다시 부른다. 변수 = 찾은 대상에 붙여 두고 다시 부르는 이름. 괄호 맨 앞, 레이블 앞의 짧은 글자. 다섯째 줄 오른쪽 칸의 짧은 글자 둘이 변수이고, 같은 글자가 첫 줄에서는 구성 요소 레이블 앞에, 마지막 줄에서는 센서 레이블 앞에 붙어 있다. 이름은 쿼리를 쓰는 사람이 정한다 / · 거슬러 찾기: 관계는 쿨러에서 센서 쪽으로 저장돼 있어도, 센서를 먼저 잡고 어느 쿨러를 재는지 물을 수 있다. 찾을 때는 저장된 방향과 반대로 따라가도 된다. 센서를 맨 앞에 적고 화살표는 여전히 쿨러에서 센서를 가리키게 둔다(가운데 칸에서 화살표 머리가 왼쪽 센서 쪽). 저장된 방향은 건드리지 않고 출발점만 옮긴다. 반대 뜻의 관계를 새로 만들지 않는다 / [다음] 적은 문장을 쳐서 돌려 봐야 무엇이 나오는지 보인다

## SLIDE 51 — MATCH와 RETURN
### 화면 내용
- 유형: 코드
- 메시지: **MATCH**는 적은 모양에 맞는 연결을 모두 찾고 **RETURN**은 그 가운데 돌려받을 것을 정하며, 결과는 행으로 나온다.
- 코드: MATCH (c:Component {id: 'HYD-02:cooler'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN s.tag, s.unit
- 요소:
  1. 패턴(Pattern) | MATCH 뒤에 적은 찾을 모양
  2. RETURN | 찾은 센서의 tag와 unit을 돌려받는다
  3. 결과 5행 | TS1 · TS2(℃), FS2(L/min), CE(%), CP(kW)
- 노트: [짚을 곳] 왼쪽 코드 세 줄: 앞 두 줄 MATCH → 셋째 줄 RETURN → 오른쪽 굵은 제목 셋 → 맨 아래 「결과 5행」 / · 처음 쳐 볼 쿼리: 두 번째 설비의 오일 쿨러를 재는 센서를 모두 꺼내는 문장 / · 앞 두 줄은 MATCH = 적어 준 모양에 맞는 연결을 DB에서 모두 찾는 절. MATCH 뒤에 적은 찾을 모양 = 패턴. 두 번째 설비의 쿨러에서 「센서로 계측된다」 관계를 따라가 닿는 센서를 찾아라 / · 관계 그림을 옮겨 적었던 패턴과 다른 곳: 센서 쪽 괄호에 레이블만 있고 어느 센서인지 고르는 속성이 없다 → 맞는 센서를 빠짐없이 다 찾는다 / · 셋째 줄 RETURN이 찾은 것 가운데 돌려받을 것을 정한다: 찾은 센서마다 태그와 단위. 찾은 센서는 붙여 둔 변수로 다시 부른다 / · 결과는 줄로. 찾은 연결 하나가 한 줄, 다섯 줄 = 그 쿨러를 재는 센서가 다섯. 괄호 안 단위로 보면 섭씨도가 둘, 나머지 셋은 흐르는 양 · 효율 · 동력 / [다음] 다섯 가운데 온도를 재는 것만 보고 싶을 때

## SLIDE 54 — MERGE: 있으면 찾고 없을 때만 만든다
### 화면 내용
- 유형: 코드
- 메시지: **MERGE**는 적은 패턴 전체로 찾고 없을 때만 만들므로, 찾는 자리에는 바뀌지 않는 식별자만 적고 이름은 **SET**으로 넣는다.
- 코드: MERGE (c:Component {id: 'HYD-02:cooler'}) / SET c.name = '오일 쿨러', c.group = '냉각'
- 요소:
  1. SET | 찾았든 만들었든 속성 값을 넣거나 바꾼다
  2. SET의 이름을 바꿔 다시 돌리면 | 노드는 하나, 이름만 새 값으로 바뀐다
  3. 이름까지 찾는 자리에 적으면 | 이름을 고친 뒤 다시 돌릴 때 찾지 못해 새로 만들려 한다
- 노트: [짚을 곳] 코드 두 줄: 첫 줄 MERGE의 괄호 안(레이블과 중괄호, 중괄호가 찾을 속성을 적는 자리) → 둘째 줄 SET → 오른쪽 굵은 제목 셋(맨 아래 「이름까지 찾는 자리에 적으면」이 피할 꼴) / · 같은 자료를 몇 번 다시 넣어도 쿨러가 하나로 남게 하는 문장 / · 첫 줄 MERGE = 적은 패턴 전체로 이미 있는 대상을 먼저 찾아보고 없을 때만 만든다. 여러 번 돌려도 노드는 하나 / · MERGE는 괄호 안의 레이블과 중괄호 속성이 모두 맞는 노드를 찾는다. 중괄호, 찾을 속성을 적는 자리에는 쿨러의 식별자 하나만. 식별자는 이름이 바뀌어도 변하지 않는 값이라 찾는 기준으로 맞다 / · 둘째 줄 SET = 노드의 속성 값을 넣거나 바꾸는 절. 찾아낸 쿨러든 새로 만든 쿨러든 이름과 계통처럼 바뀔 수 있는 값은 여기서 따로. 둘째 제목처럼 이름을 바꿔 다시 돌려도 노드는 하나, 이름만 새 값 / · 피할 꼴: 찾는 자리에 식별자와 함께 이름까지 적으면 처음에는 잘 돈다. 나중에 이름을 고쳐 다시 돌리면 새 이름까지 맞는 노드를 못 찾아 새로 만들려 한다. 유일 제약이 없으면 같은 식별자의 노드가 둘, 있으면 그 문장이 거절된다 / · 자료를 다시 넣어도 늘지 않게 하려면 MERGE의 찾는 자리에는 식별자만 둔다 / [다음] 처음 물음을 쿼리로 꺼낸다
