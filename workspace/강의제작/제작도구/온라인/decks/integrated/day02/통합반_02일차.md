- 노트: [짚을 곳] 오른쪽 설비 세 대 → 왼쪽 클래스 → 오른쪽 강조한 인스턴스 → 아래 센서 둘 → 맨 아래 문장 / · 경보가 어느 설비에서 났는지 알려면 세 대는 서로 구별돼야 하고, 동시에 모두 설비라는 공통점이 있다 / · 클래스 = 공통 특성을 가진 대상의 유형(설비 · 센서). 그 유형이 적을 정보와 연결할 대상을 공통으로 정한다 / · 인스턴스 = 그 유형에 속하는 개별 대상. 같은 정의를 쓰되 이름과 내용은 각자 / · 유온 센서와 냉각 효율 채널: 둘 다 센서 클래스지만 서로 다른 인스턴스. 읽는 법 「유온 센서는 센서의 하나이다」 / · 쓰임: 새 센서는 유형을 새로 만들지 않고 내용만 채운다. 「센서 전부」는 클래스로, 「유온 센서의 단위」는 인스턴스로 묻는다 → 찾는 범위가 다르다 / · 두 질문을 견준다. 자료의 종류를 물으면 클래스, 경보 설비를 물으면 코드를 대조해 고른 한 인스턴스다. / [다음] 센서에 채우는 값

## SLIDE 06 — 센서 클래스의 속성과 속성값
### 화면 내용
- 유형: 표
- 메시지: 같은 숫자 50도 채널의 단위에 따라 50 ℃ 또는 50 %다. 태그로 열을 찾고 단위를 확인한다.
- 머리: 속성 | 유온 센서 | 냉각 효율 채널
- 요소:
  1. 식별자(id) | sen:ts1 | sen:ce
  2. 이름(name) | 유온 센서 | 냉각 효율
  3. 태그(tag) | TS1 | CE
  4. 단위(unit) | ℃ | %
  5. 계산 채널 여부(virtual) | false: 직접 계측 | true: 다른 계측값으로 계산
- 노트: [짚을 곳] 왼쪽 속성 열 → 가운데 유온 센서 → 오른쪽 냉각 효율 채널 / · 값을 담는 항목이 속성이고, 그 칸에 실제 채운 내용이 속성값입니다. / · 식별자 행에서 sen:ts1과 sen:ce를 짚는다. 유온 센서 열을 따라 읽으면 태그 TS1과 단위 ℃가 한 채널에 속한다. 냉각 효율 채널 열에서는 CE와 %가 짝을 이룬다. / · 냉각 효율은 다른 측정값으로 계산하지만 태그와 단위를 갖고 값을 내는 계측 채널입니다. / · 50이라는 숫자의 뜻은 채널의 태그와 단위로 확인한다. 직접 계측값과 계산값은 검토할 원자료가 다르다. / [다음] 센서와 물리량의 기준
### 화면 구성
유온 센서와 냉각 효율 채널의 속성을 하나의 대응표로 보인다. 공통 항목과 두 인스턴스의 값을 같은 가로줄에서 비교하도록 하며 별도 그림은 만들지 않는다.

## SLIDE 07 — 센서와 상태 변수
### 화면 내용
- 유형: 비교
- 메시지: 같은 유온을 재는 센서를 하나 더 달면 계측 채널은 둘이 되고, 두 채널이 쓸 한계는 유온 한 곳에 남는다.
- 요소:
  1. 센서(Sensor) | 값을 내놓는 계측 채널 / 유온 센서: sen:ts1 / 태그 TS1 · 단위 ℃ / 채널을 더하면 식별자 1개 → 2개 | 재는 쪽
  2. **상태 변수(StateVariable)** | 설비의 상태를 나타내는 물리량 / 유온: sv:ts1 / 이 설비의 정상값(normal) 48 ℃ · 한계(limit) 65 ℃ / 두 채널이 재는 유온 1개 · 한계 1개 | 재어지는 쪽
- 노트: [짚을 곳] 왼쪽 유온 센서의 식별자와 태그 → 오른쪽 유온의 식별자와 이 설비의 두 기준 → 양쪽 마지막 줄 / · 어느 채널의 값을 읽을지 정하려면 유온 센서의 태그 TS1을 본다. 얼마와 비교할지는 이 설비에 정한 유온의 정상값 48 ℃와 한계 65 ℃에서 찾는다 / · 같은 유온을 재는 채널을 한 개 더 등록한다고 가정한다. 서로의 기록을 구별하려면 센서 식별자가 두 개 필요하다 / · 두 채널 모두 같은 유온을 재므로 오른쪽의 유온은 한 개다. 한계를 바꾸려면 유온 한 곳에서 고친다 / · 두 측정값이 다르면 원래 채널과 시간을 보존하고 설치·측정 조건을 확인한다. 기준을 공유해도 기록은 둘이다. / [다음] 센서의 태그와 유온의 한계를 찾는 길
### 화면 구성
두 칸 위에서 현재 센서와 물리량의 식별자를 짚고 아래에서 같은 유온을 재는 채널을 한 개 더 둔 가정을 비교한다. 왼쪽 마지막 줄은 식별자 수의 변화, 오른쪽 마지막 줄은 공유하는 물리량과 한계의 수다.
### 제작 기준

## SLIDE 50 — MATCH · RETURN: 패턴과 결과의 행
### 화면 내용
- 유형: 코드
- 메시지: MATCH는 패턴에 맞는 연결을 찾고, RETURN은 그 결과에서 돌려받을 항목을 정한다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / c.name         s.tag / "오일 쿨러"    "TS1" / "오일 쿨러"    "CE"
- 요소:
  1. MATCH | 이름이 오일 쿨러인 구성 요소에서 계측 관계로 이어진 센서를 찾는다.
  2. RETURN | 구성 요소 이름과 센서 태그를 결과의 두 열로 받는다.
  3. **행의 수** | 쿨러 하나에 채널이 둘이라 결과는 두 행이다.
  4. 행과 노드 | 두 행의 오일 쿨러는 같은 노드이다. 이름의 반복이 노드의 중복을 뜻하지 않는다.
- 노트: [짚을 곳] 코드 위 MATCH 두 줄 → RETURN → 아래 결과 두 행 → 오른쪽 강조한 행의 수 / · 절 = 쿼리를 하는 일별로 나눈 한 부분. MATCH = 찾을 패턴(이름이 오일 쿨러인 구성 요소에서 계측 관계로 이어진 센서) / · RETURN = 돌려받을 항목(구성 요소 이름 · 센서 태그 → 결과 두 열) / · 결과: 쿨러-유온 센서, 쿨러-냉각 효율 채널 → 두 연결이 각각 패턴에 맞아 두 행 / · 쿨러 이름이 두 번 나와도 같은 노드. 이름 반복 ≠ 노드 중복 / · 개수를 적지 않았다: 조건에 맞는 연결이 실제로 둘이라 두 행 → 한 행이 무엇을 나타내는지 알면 여러 행을 중복 데이터로 오해하지 않는다 / [다음] 무엇을 돌려받을지에 따라 달라지는 결과

## SLIDE 51 — RETURN: 속성값과 노드 · 관계
### 화면 내용
- 유형: 코드
- 메시지: 같은 패턴을 찾더라도 속성값을 받으면 표로 읽고, 노드와 관계를 받으면 연결을 그릴 수 있다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[r:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 같은 MATCH, 다른 RETURN ── / RETURN c, r, s /  / ── 반환하는 대상(속성 일부 생략) ── / (:Component)  [:MONITORED_BY]  (:Sensor {tag: 'TS1'}) / (:Component)  [:MONITORED_BY]  (:Sensor {tag: 'CE'})
- 요소:
  1. 찾는 패턴 | 두 쿼리 모두 같은 쿨러와 센서의 연결을 찾는다.
  2. 속성값 반환 | c.name, s.tag는 각 노드의 값이다. 이름과 태그 두 열을 받는다.
  3. **노드 · 관계 반환** | c, r, s는 구성 요소 노드, 계측 관계, 센서 노드 자체이다.

## SLIDE 52 — DISTINCT: 반환한 값의 중복 제거
### 화면 내용
- 유형: 표
- 메시지: DISTINCT는 반환하는 값의 조합이 같은 행을 하나로 남기며, 저장된 노드를 지우지 않는다.

## SLIDE 53 — COUNT: 결과 행과 서로 다른 대상의 수
### 화면 내용
