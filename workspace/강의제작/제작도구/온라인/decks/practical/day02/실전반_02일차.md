## SLIDE 06 — 한계를 둘 자리: 속성과 관계
### 화면 내용
- 유형: 비교
- 메시지: 한계 같은 값은 그 대상의 칸에 두고, 센서에서 그 값을 읽으려면 상태 변수로 건너가는 관계를 따라간다.
- 요소:
  1. 속성 — 데이터 속성(Data Property) | 값이 그 인스턴스의 칸 안에 있다 / 유온 센서의 tag 'TS1' · unit '℃' / 이 설비에서는 유온 normal 48 · limit 65 ℃ | 인스턴스와 값
  2. **관계 — 객체 간 관계(Object Property)** | 유온 센서 → OBSERVES → 유온 / 유온은 상태 변수(StateVariable): 설비의 상태를 나타내는 물리량 / 한계는 건너간 유온에서 읽는다 / 센서를 하나 더 두어도 유온 1개 · 한계 1개 | 인스턴스와 인스턴스
- 노트: [짚을 곳] 왼쪽 속성의 센서 값과 유온의 정상값 · 한계 → 오른쪽 강조한 읽는 관계 → 상태 변수 → 한계를 읽는 길 → 마지막 줄 / · 온톨로지 책의 데이터 속성 · 객체 간 관계 = 이 과정의 속성 · 관계 / · 태그와 단위는 센서 칸 안의 값, 정상값과 한계는 유온 칸 안의 값 → 모두 속성 / · 상태 변수 = 설비의 상태를 나타내는 물리량. 센서는 재는 쪽, 유온은 재어지는 쪽 / · 센서에서 한계를 알려면 읽는 관계로 유온에 한 번 건너간다. 센서를 바꾸거나 같은 유온을 재는 센서를 하나 더 두어도 관리할 유온은 하나 → 한계를 센서마다 적으면 두 군데, 한쪽만 고치면 한계가 둘 / · 헷갈리는 짝: 글자냐 숫자냐가 기준이 아니다. 값이 그 대상의 칸에 있나, 이어진 다른 대상에 있나 / [다음] 관계 그림의 이름들은 어느 클래스인가

## SLIDE 36 — MATCH · RETURN: 결과 행과 돌려받는 항목
### 화면 내용
- 유형: 코드
- 메시지: MATCH가 찾은 연결 하나가 결과의 한 행이 되고, RETURN은 그 행에 속성값을 담을지 노드와 관계를 담을지 정한다.
- 코드: MATCH (c:Component {id: 'comp:cooler'}) /       -[r:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / c.name         s.tag / "오일 쿨러"    "TS1" / "오일 쿨러"    "CE" /  / ── 같은 MATCH, 다른 RETURN ── / RETURN c, r, s / → 쿨러 노드 하나와 센서 노드 둘을 그래프로
- 요소:
  1. MATCH | 식별자로 고른 오일 쿨러에서 계측 관계로 이어진 센서를 찾는다.
  2. **결과 행** | 패턴에 맞는 연결 하나가 한 행이다. 센서가 둘이라 두 행이다.
  3. 행과 노드 | 두 행의 오일 쿨러는 같은 노드다. 이름이 두 번 나와도 노드는 하나다.
  4. RETURN | 속성값(c.name, s.tag)을 받으면 표로, 노드와 관계(c, r, s)를 받으면 그래프로 읽는다.
- 노트: [짚을 곳] MATCH 패턴 → 결과 두 행 → 아래 다른 RETURN → 오른쪽 칸 넷 / · MATCH = 적은 패턴에 맞는 연결을 찾는 절, RETURN = 그 결과에서 돌려받을 항목을 정하는 절 / · 오일 쿨러를 식별자로 고르고 계측 관계로 이어진 센서를 찾는다 → 센서가 둘이라 연결도 둘 → 결과 행 둘 / · 두 행에 「오일 쿨러」가 두 번 나오지만 같은 노드. 이름의 반복이 노드의 중복은 아니다 / · 같은 MATCH에서 RETURN만 바꿔 노드와 관계를 받으면 쿨러 하나 · 센서 둘 · 관계 둘이 그래프로 그려진다. 행 수는 그대로 둘 / · 표로 읽을지 그래프로 볼지는 RETURN이 정한다 / [다음] 같은 이름이 여러 행에 나올 때 줄이고 세기
### 화면 구성
코드 위는 MATCH와 속성값 RETURN과 결과 두 행, 아래는 같은 MATCH에 노드 · 관계를 돌려받는 RETURN 한 줄과 그 결과. 오른쪽 칸 넷은 MATCH · 결과 행 · 행과 노드 · RETURN 순.

## SLIDE 37 — 행의 수와 대상의 수: DISTINCT · COUNT · 묶는 기준
### 화면 내용
- 유형: 코드
- 메시지: 같은 노드가 여러 행에 나오므로, 목록은 DISTINCT로 줄이고 개수는 행을 셀지 서로 다른 대상을 셀지 골라 센다.
- 코드: // 세 설비에서 유온 센서까지 / MATCH (a:Asset)-[:HAS_COMPONENT]->(c:Component) /       -[:MONITORED_BY]->(s:Sensor {id: 'sen:ts1'}) / RETURN count(*) AS rows, count(DISTINCT s) AS sensors / // rows 3 · sensors 1 /  / // 첫 번째 설비의 구성 요소마다 / MATCH (a:Asset {id: 'asset:hyd-01'}) /       -[:HAS_COMPONENT]->(c:Component) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name AS component, count(DISTINCT s) AS sensors / ORDER BY sensors DESC, component / // 오일 쿨러 2 · 주 펌프 (A) 2 · 쿨러 팬 1
- 요소:
  1. **DISTINCT · COUNT** | DISTINCT는 반환한 값의 조합이 같은 행을 하나로 남긴다. count(*)는 결과 행을, count(DISTINCT s)는 서로 다른 노드를 센다.
  2. 행 3 · 센서 1 | 세 설비가 같은 오일 쿨러 노드를 거쳐 같은 유온 센서 노드에 닿는다.
  3. 묶는 기준 | 집계하지 않고 함께 반환한 c.name이 같은 행끼리 따로 센다.
  4. AS · DESC | AS는 결과 열의 별명, DESC는 큰 값부터.
- 노트: [짚을 곳] 위 쿼리의 두 count와 결과 → 아래 쿼리의 묶는 기준과 결과 → 오른쪽 칸 넷 / · DISTINCT = 중복 제거. 반환한 열 전체의 조합이 같은 행을 하나로 남긴다. 저장된 노드를 지우지 않는다 / · COUNT = 여러 행을 개수 하나로 요약하는 집계 함수 / · 위: 세 설비 모두에서 출발하면 세 경로가 같은 유온 센서 노드에 닿는다 → 결과 행 3, 서로 다른 센서 노드 1 → 무엇을 세는지 먼저 정한다. 센서 노드 하나가 계기 한 대는 아니다(세 호기에 하나만 둔 노드) / · 아래: 함께 반환한 구성 요소 이름이 묶는 기준 → 구성 요소마다 따로 센다. 이름이 같은 다른 장치가 있으면 식별자도 함께 반환해 묶는다 / · 결과를 원래 행과 대조: 쿨러 TS1 · CE, 주 펌프 FS1 · PS1, 팬 VS1 / [다음] 여러 관계를 건너 한계까지 찾고 거르기
### 화면 구성
코드 위는 세 설비에서 유온 센서까지 센 쿼리와 결과, 아래는 첫 번째 설비의 구성 요소별 집계와 결과. 오른쪽 첫 칸(강조)이 DISTINCT와 COUNT, 둘째 칸이 행 수와 노드 수가 갈린 까닭이다.

## SLIDE 38 — 여러 관계를 잇는 경로와 WHERE · AND · OR
### 화면 내용
- 유형: 코드
- 메시지: 노드와 관계를 번갈아 이어 설비에서 한계까지 한 쿼리로 따라가고, WHERE로 결과 행을 거르되 OR는 괄호로 묶는다.

## SLIDE 42 — 응용: 유온을 낮출 변수를 쿼리로 찾을 때
### 화면 내용
