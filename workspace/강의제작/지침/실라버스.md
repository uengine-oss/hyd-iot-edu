# 실라버스

## 반드시
1. **L-1. 고친 것은 A(구분), B(제목), C(상세) 칸의 글뿐이다 — 고정 항목은 사용자 승인 없이 바꾸지 않는다.** — 판정: 「전후 비교」 출력에서 글 칸 밖(D 칸, 수식, 병합, 너비, 틀 고정)의 변경과 바뀐 고정 항목은 작업 기록(`기록.md`)에 승인 문장이 있는 셀만 있어야 하고, 「합계 검사」가 오류 0을 내야 통과다.
   고정 항목은 시트 넷, 회 수, 회차 주제, 행 구분의 이론과 실습 갈래(「실습(어디서)」의 어디서는 L-7대로 고칠 수 있다), 행 순서, 시간, 날짜, 강사 배정, Wrap-up 행, ProcessGPT 시연 행이다.
   행을 넣거나 지우면 합계 수식이 어긋난다. 그래서 승인받아 행 수를 바꿀 때는 같은 커밋에서 회 합계 수식과 전체 합계 수식도 고친다.
   시간 칸은 교재 판정에서 배정 시간에서 10분을 뺀 것보다 짧은 행이 나와 사용자에게 물었고, 사용자가 같은 회 안에서 시간을 옮기기로 승인한 때만 바꾼다. 회 합계는 온라인 240분, 오프라인 200분 그대로 둔다.
2. **L-2. 줄기는 온톨로지 → 에이전트 → 프로세스 → 종합 순서이고, 회차 안의 한 주제는 이론 → 포털 실습 → 코딩 랩(VS Code) 순서다.** — 판정: 행마다 줄기 단계와 구분 순서를 적어 보고, 순서가 뒤집힌 곳이 없어야 한다. 그리고 포털에 대응 기능(`it/portal/www/index.html`의 메뉴, `workspace/개발/scripts/class_round.py`)이 있는 주제에는 포털 행이 있어야 통과다.
   줄기 단계는 통합반이 1~4회차 온톨로지, 5~8회차 에이전트, 9~10회차 프로세스, 11회차 종합이고, 실전반은 1~3, 4~5, 6~7, 8회차가 차례로 같은 단계다.
   포털 대응이 없는 코딩 랩(외부 MCP, 자기 노트 퀴즈)은 이론 → VS Code 순서다. BPMN은 이론 → bpmn.io와 포털 순서이고 코딩 랩이 없다.
3. **L-3. 상세 칸의 문장은 학생이 배우는 것, 직접 해 보는 것, 확인하는 것 중 하나다.** — 판정: 문장마다 셋 중 무엇인지 표시해 보고, 셋 밖의 문장이 없어야 한다. 빈 병합 행까지 읽어 운영 메모가 없어야 통과다.
   셋 밖의 문장이란 운영이나 진행의 말, 그리고 강의실 운영(학교 PC, USB, 내보내기, 작업 폴더에 받기)에 관한 말이다. 금지 사항은 「…하지 않는지 확인한다」 꼴로 쓴다.
4. **L-4. 이론 행은 배우는 것을 쓰고, 실습 행은 「어느 화면을 열어 → 무엇을 하고 → 무엇과 대조해 확인」하는지를 쓴다.** — 판정: 이론 행의 첫 문장이 실습 결과(「…를 만든다」)가 아니어야 하고, 이론 행 안의 포털 조작은 짧은 확인 하나까지만 있어야 한다. 실습 행마다 화면, 행동, 확인 셋이 다 있어야 통과다.
   실습 행이 쓰는 개념(DMN, 여러 규칙이 맞을 때 고르는 방식, 경고, 감점, 제외, 도구 호출 결과 반영)은 그보다 앞의 이론 행이 다룬다. 온라인 포털 행은 「강사를 따라」로 시작한다.
5. **L-5. 도구 실습 행(포털, ARROWS, Notion, Neo4j, bpmn.io)은 그 화면으로 무엇을 왜 판단하는지 쓰고, 코드 과제와 파일 저장 단계는 넣지 않는다.** — 판정: 셀 검색 `'저장|폴더|기록 파일|START'`로 후보를 모아 도구 실습 행에 걸린 곳을 읽는다. 도구 밖의 파일이나 폴더를 다루는 단계가 없어야 한다. 그리고 통독해서 코드 과제, 이론 재설명, 마무리 정리, 임의 문서, 외부 도구 서버 등록이 없어야 통과다.
   도구 안의 내보내기와 가져오기(ARROWS Export JSON)는 써도 된다. bpmn.io 행은 그린 흐름을 기준 흐름과 매핑에 견주고, 포털 행은 등록된 흐름을 실행해 이력과 대조한다.
   포털에 등록하는 것은 마지막 회에 제공하는 교대 BPMN(`it/process/definitions/shift_handover.bpmn`) 하나뿐이고, 학생이 그린 흐름은 포털에 등록하지 않는다.
6. **L-6. VS Code 행은 현실 문제 → 바이브 코딩 일곱 단계 → 다른 입력으로 검증하는 순서다.** — 판정: 행마다 문제, 검증 문장, 활동 순서를 적어 보고, 빠진 것과 뒤집힌 순서(예: 요구보다 구현이 먼저)가 없어야 한다. 결과물이 아래 세부의 실전반 결과물, 통합반 결과물과 같아야 통과다.
   일곱 단계: ① 파일을 바꾸지 않고 AI와 파악 ② 요구와 기대 답을 내 말로 ③ 계획 검토 ④ 작게 구현 ⑤ 원자료와 대조 ⑥ 고침 ⑦ 저장하고 다시 열기.
   문제는 여러 출처가 어긋나는 자료, 규모, 품번 변형, 판본 차이 중 그 랩에 해당하는 것이다. 랩이 지킬 대상은 행에 명시한다. 포털 시드 값이나 판정 결과에 맞추는 랩, 포털 에이전트에 자동으로 연결하는 랩이 없어야 한다.
   실전반 결과물은 같은 구축에 실제 역할이 쓰는 모양을 더한 것이다: 부품 활용 조회(공급 근거), 조치 검토 결과(후보별 이유와 출처), 작업 확인 카드, 점검 요청(대상, 관측 시각, 이유), 다음 협의 안건, 같은 점검 요청의 명세와 검증.
   외부 MCP를 연결하고 직접 만든 조회 도구를 더하는 랩 하나는 두 과정이 같다. 통합반만 다른 것은 활용(통합 5회차)과 자료 통합(통합 8회차)이다.
7. **L-7. 구분 칸은 「이론」 또는 「실습(어디서)」이고, 상세 칸에 나오는 화면이 상세 칸의 순서대로 구분 칸에 모두 있다.** — 판정: 네 시트의 A 칸 값에 아래에 적은 값 밖의 것이 없어야 한다. 상세 칸의 화면 목록과 구분 칸의 화면 목록이 같아야 하고, 구분 칸의 화면마다 상세 칸에 조작 문장이 있어야 통과다.
   「어디서」에 들어가는 값은 포털, VS Code, Notion, ARROWS, Neo4j, bpmn.io, ProcessGPT 시연이고, 둘이면 「 · 」로 잇는다.
   도구로 결과를 만들거나 실행을 확인하는 행은 강사 혼자 하더라도 실습이다. 결과 예상, 근거 비교, Wrap-up 행은 이론이다. 보기만 하는 행의 구분은 「실습(ProcessGPT 시연)」(오프라인은 「실습(ProcessGPT 시연 · Notion)」) 하나뿐이다.
   구분 칸의 화면이 상세 칸에 없으면 구분 칸을 고치는 대신 상세 칸에 그 화면의 조작을 넣는다.
8. **L-8. 한 대상은 네 시트에서 이름이 하나이고, 처음 나오는 말은 그 시트에서 그 말이 처음 나오는 행이 풀어 준다.** — 판정: 아래 셀 검색으로 후보를 모으고 걸린 셀을 읽어 가른다. 규칙에 어긋난 곳이 없어야 하고, 약어가 처음 나오는 행에 풀이가 있어야 하며, 한 대상에 두 이름, 한 이름에 두 뜻이 없어야 통과다.
   셀 검색 정규식은 `'[A-Z]+-[A-Z0-9]+|TS[0-9]'`, `'일차|첫날'`, 온라인 시트의 `'[0-9]+회([^차]|$)'`, 오프라인 시트 본문의 `'[0-9]+회차'`(머리 행 「NN회차  |  주제」는 그대로 둔다), 그리고 `'[A-Z]{2,}|→'`이다.
   SDD와 BDD는 「명세 주도 개발(SDD)」 「행동 주도 개발(BDD)」로만 쓰고, 배운 회차(온라인 통합 7 · 8회차와 실전 5회차, 오프라인 통합 7회와 실전 6회)부터 쓴다. 식별자는 뜻으로 풀어 쓴다.
   줄인 랩 이름, 한 행 안에서 같은 뜻을 두 번 쓰기, 두 뜻으로 읽히는 동사(「SOP를 쓴다」), 맞춤법 오류가 없어야 한다.
9. **L-9. 원리가 주어이고, 재료는 「이 설비에서는」으로만 얹는다.** — 판정: 행마다 근거(파일이나 영상 구간)를 붙여 보고, 근거 없는 화면, 기능, 이름, 장면이 없어야 한다. 개념이 이론 덱의 정의와 같아야 통과다.
   구현의 이름은 원리 이름(「사람 작업 · 시스템 작업 · 에이전트 작업」)으로 쓰고, 아홉 층은 이 시스템의 예로 든다.
   설비 사례는 하나(쿨러 사건 설비)로 깊게 다루고, Notion은 활용 사례 하나만 쓴다. Lane은 담당이나 역할별로 나눈다. 억지 실패, 가상 상황, 미리 정한 AI 응답이 없어야 한다.
10. **L-10. 아직 나오지 않은 것을 전제하지 않고, 각 회는 앞 회를 이름으로 받아 열고 다리 문장으로 닫는다.** — 판정: 위에서부터 읽으며 행마다 「쓰는 것이 앞 행에 그 이름으로 나왔는가」를 표시하고, 앞에 없던 것을 쓰는 곳이 없어야 한다. 다리 수가 통합 온라인 10, 실전 온라인 7, 통합 오프라인 9, 실전 오프라인 8이어야 한다. 셀 검색 `'다음 실습|이어지는|로컬 랩에서|[0-9]+회에는'`으로 후보를 모아 도구 실습 행에 걸린 곳을 읽고, 다리가 아닌 예고가 없어야 통과다.
   「앞서 만든 · 기존 · 제공된 …」 같은 말은 그 행만 읽어도 대상(회, 처리 건, DB, 작업)이 특정되게 쓴다(예: 「1회차에 승인했던 처리 건」).
   다리 문장은 회의 마지막 행 끝에 두는 「다음 회차에는 …」 문장이고, 다음 회의 머리 주제와 첫 행에 쓰인 말로 쓴다.
   앞 실습을 잇는 말은 뒤 행의 첫머리에 둔다. 다음 회의 주제를 당겨 온 행이 없어야 한다.
11. **L-11. 오프라인 한 회는 대응하는 온라인 회차의 활동을 같은 순서로 4행 × 50분에 담고, 학생이 가이드를 보며 직접 한다.** — 판정: 회마다 행 수, 구분, 분을 센다. 온라인 행의 학생 활동마다 짝이 되는 오프라인 행을 적어 보고, 빠진 활동, 다른 회차의 행, 순서 차이가 없어야 한다. 오프라인 시트에 「강사를 따라」가 없어야 통과다.
   대응: 통합 오프라인 1~6회 = 온라인 1~6회차, 7회 = 7 + 8회차, 8~10회 = 9~11회차 / 실전 오프라인 1~3회 = 온라인 1~3회차, 4회 = 온라인 4회차에서 스킬 앞까지, 5회 = 스킬부터 4회차 끝까지, 6~9회 = 5~8회차.
   이론 회(통합 1~8회, 실전 1~7회)의 첫 행은 이론 행이고, 실행 중심 회에는 이론 행이 없다. 이론 행은 대응하는 온라인 이론 행의 압축이며 새 개념을 넣지 않는다. 압축은 문장을 줄이는 것이지 활동을 빼는 것이 아니다. 「빨리 끝나면 해 볼 것」에는 그 회의 랩만 넣는다.
   첫 회는 HYD 전체 구조 → 실제 포털로 경보 → 판단 → 승인 → 조치 → 결과 → 관계 모델 순서다. 첫 그래프 실습 행은 Cypher 생성, 조회, 조건, 수정, 삭제, 재조회와 노드 속성 확인을 담는다.
   통합 오프라인에서 도구가 처음 나오는 행에는 그 도구의 첫 조작 문장을 쓴다. 1회에 만든 Notion 학습노트를 통합 6 · 10회와 실전 5 · 9회에 이어 쓴다.
12. **L-12. 두 과정의 시트는 같은 코어이고, 1회차는 글자까지 같다.** — 판정: 두 온라인 시트의 1회차 셀끼리, 두 오프라인 시트의 1회 셀끼리 글자 차이가 없어야 한다. 실전반만 바꾸는 일이면 「전후 비교」에 통합반 시트의 변경이 없어야 한다. 실전반 시트에 통합반 문장을 옮겨 온 흔적(「실전반은 …」, 실전반에 없는 실습의 언급)이 없어야 통과다.
   공통 도구 실습(1회차, Cypher)은 두 시트가 같은 기능과 절차를 쓰고, 촬영된 영상과 맞는다. 실전반의 차이는 L-6의 실전반 결과물로만 둔다.
13. **L-13. 마지막 회(통합 온라인 11회차, 실전 온라인 8회차, 통합 오프라인 10회, 실전 오프라인 9회)는 교대 인수인계다.** — 판정: 마지막 회의 행을 아래 단계와 대조한다. 빠진 단계와 목록 밖의 학생 작업이 없어야 하고, 실전반은 인수자가 받아들일 근거와 보완 질문까지 검토하는 단계가 있어야 통과다.
   단계: 보충 매뉴얼 추출, 원문 검토, 추가 적재 → 미완료, 주의, 기록 불일치를 정리하는 에이전트와 스킬 → bpmn.io 흐름(조회 → 인계안 → 인계자 검토 → 인수자 확인/보완 → 완료) → 제공 교대 BPMN의 표시 이름, 배치, 초안 단계의 에이전트 배정, 별도 판본 등록 → 실행.
   인계 확인을 정비 완료, 실제 조치, 발주로 쓴 문장이 없어야 한다.
14. **L-14. 바꾼 행은 묶인 넷, 소비자, 노션까지 같은 판으로 맞추고, 교재에 대응이 없는 문장은 처리 방법을 정해서 처리한다.** — 판정: 바꾼 셀마다 묶인 넷(같은 회의 앞뒤 행, 회 끝 다리, 오프라인 짝, 다른 과정 짝)을 다시 판정한 결과와 「소비자」 검색 결과(고친 파일, 또는 `기록.md`의 고칠 목록)가 기록에 있어야 한다. 노션은 다시 읽어 셀과 글자 차이가 없어야 통과다.
   교재 어디에도 대응이 없는 문장은 교재 보강과 행 수정 중 하나로 정한다. 교재가 맞으면 행을 고칠지 먼저 묻는다. 행 제목을 바꾸면 대본의 행 제목 줄은 승인 없이 맞춘다.
   노션 반영은 먼저 묻는다. 두 과정의 홈과 온라인 회차 페이지 19개에 바뀐 셀만 옮기고, 그 밖의 블록은 그대로 둔다. 바꾸기 전 페이지를 작업 폴더에 저장하고, 공개 엑셀 링크를 새 커밋 해시로 바꾼다. 강사 실명이 들어간 배정본은 사용자에게 전달하는 파일로만 만든다.

## 길
1. 맥락 — 공통 「행 뽑기」로 고칠 회차와 그 짝(오프라인 짝, 다른 과정 짝)만 뽑는다.
2. 다른 세션 확인 — `git hash-object <엑셀>`과 `git rev-parse workspace:<엑셀>`의 값이 다르면 다른 세션의 미커밋 수정이 있는 것이니, 그 수정이 커밋될 때까지 기다린다.
3. 고칠 표 — 셀마다 「시트 · 행 · 칸 · 전 · 후 · 근거 · 까닭」을 적는다. 고정 항목을 바꾸거나 교재를 근거로 행을 고칠 때는 이 표를 보여 주며 먼저 묻는다.
4. 적용 — openpyxl `load_workbook(<엑셀>)`로 열어 지금 값이 「전」과 같은 셀만 바꾸고, 다른 셀이 하나라도 있으면 멈춘다. 고친 셀을 다시 읽어 앞 문장의 찌꺼기가 남지 않았는지 본다.
5. 자동 검사 — 「합계 검사」 오류 0 → 「전후 비교」 결과가 고칠 표와 같은지 확인 → 셀 검색(L-5, L-8, L-10, 공통 C-3)에 걸린 칸을 읽어 판정한다.
6. 소비자 — 옛 제목과 옛 문장 조각으로 「소비자」 자리를 grep하고, 걸린 곳을 고치거나 `기록.md`의 고칠 목록에 넣는다.
7. 독립 검토를 1회 받는다(바뀐 행과 묶인 넷, 새로 쓴 시트는 모든 행). 그 뒤 지적 목록만 고친다.
8. 올리기 — `<py> workspace/동기화.py commit "…" --만 <엑셀>` → `push`. 노션 반영은 승인받은 뒤 커밋 다음에 한다.

## 함정
- openpyxl로 저장하면 수식의 계산값이 사라진다. 노션에 게시하기 전에 LibreOffice로 열어 합계를 확인한다.
- 행을 고친 뒤 덱과 대본만 따라 고치고 `구성.json`, 가이드 첫 화면, `START.md`, 노션이 옛 판으로 남은 적이 있다. 길 6을 건너뛰지 않는다.
- 노션의 공개 엑셀 링크는 커밋에 고정된 주소라서, 엑셀을 고쳐도 링크는 옛 판을 가리킨다.
- 통합 오프라인 8~10회와 실전 오프라인 5~9회는 회 번호가 대응하는 온라인 회차 번호와 다르다. 그래서 「앞 회차의 …」라고 쓴 문장이 틀린 회를 가리킨 적이 있다.
