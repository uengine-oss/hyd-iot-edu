# 가이드 — 만드는 법과 인수 조건

공통 기준은 `공통.md`, 작업 순서는 `hyd-task`. 이 문서는 실습 가이드(도구 실습 · 코딩 랩)의 나머지를 가진다 — 학생이 강사 없이 따라 하는 가이드의 생성 원본 · HTML · 사진 · 학생 안내 문장 · 정적 검사 · 받기 시험 · 학생 패키지(ZIP) · 회차 안내 · workspace 반영 · 노션 회차 페이지 게시까지. 실습 대본 · 촬영 · 영상, 코딩 랩의 과제 설계 자체, 덱은 각자의 문서가 소유하고, 이 문서는 그 산출물과 주고받는 것을 가이드의 말로 적는다.

## 반드시 — 어기면 불통과

1. 실라버스 그 행의 문장마다 가이드 단계 · 설명 · 화면 · 확인 방법이 대조표에 채워져 있다 — 대조표 빈칸 0, 행에 없는 단계 0(P-1, P-2).
2. 도구 실습과 코딩 랩은 별개다. 도구 실습은 그 도구 화면에서 시작해 그 화면에서 끝나고, VS Code 장면 · 받은 폴더 · `START.md` · `결과/` · 학생 코드 과제 · 다음 실습 예고 0(P-57, P-59, P-60, P-62).
3. 학생이 하는 조작마다 그 순간의 실제 화면 사진이 있고, 사진은 본 촬영 화면에서 뽑았으며 보충 화면은 같은 판본이다 — 사진 없는 조작 0(P-141, P-143).
4. 하지 않은 조작 · 보지 않은 화면 · 아직 나오지 않은 AI 응답 · 실행 결과를 쓰지 않는다 — 비슷한 화면으로 채운 곳 0, 꾸민 실패 · 가정 분기 0, 못 찍은 단계가 남은 가이드는 게시하지 않는다(P-53, P-54, P-147).
5. 클릭 · 입력 · 확인할 요소마다 같은 색 · 두께의 빨간 사각형이 있다. 가림은 민감정보(P-157)의 글자 자리뿐이고 이름 · PC 경로 · 대화 목록 · 즐겨찾기 · 프로필은 가리지 않는다(P-149, P-156).
6. 단계마다 목적 · 행동(위치를 첫 문장에 녹임) · 입력 · 실제 화면 · 결과 확인 다섯 칸이 있다(P-122).
7. 프롬프트 · 명세 · 쿼리 · 명령은 사진 속 글자로만 주지 않고 복사 블록이나 파일로 주며, 복사 단추는 본문만 복사한다(P-130, P-132).
8. 코딩 랩 가이드 · 학생 폴더에 정답 · 해결 로직 · 완성 프롬프트 · 강사 폴더나 강사 참조를 가리키는 말 · 풀어 쓴 답 · 해설 0(P-71, P-33).
9. AI 결과 화면은 「강사 화면의 예」로 표시하고 성공 판정은 원자료 대조 조건으로 쓴다. 포털 실습 가이드에 AI 응답 재생 · 저장된 응답 안내 0(P-39, P-140).
10. 받기 시험을 실제 학생 경로로 했다 — 코딩 랩은 다운로드 → 새 시험 폴더에 압축 해제 → 열기 → 실행 → 저장 → 다시 열기, 도구 실습은 그 도구 화면에서 결과까지, 가이드 밖 도움이 필요했던 단계 0(P-112, P-173).
11. ZIP의 경로 집합과 파일별 바이트가 배포 폴더와 같고, `verify_packages.py` 실패 0, 학생이 읽을 것 말고는 ZIP에 없다(P-171, P-178, P-183).
12. 게시는 노션 두 과정 회차 페이지 「가이드문서」 탭의 workspace 커밋 고정 링크이고, 페이지를 실제로 열어 눌러 200 · 원본과 같은 크기를 확인했다(P-194).

## 목적 · 가치 · 배경

**P목-1** 가이드는 강사 없이 따라 하는 학생 자료다. 온라인 학생은 강사 한 사람이 실제로 작업하며 하나의 수업처럼 보여 주는 원맨쇼 영상을 보고, 오프라인 학생은 온라인 선행 학습 뒤 강의실에서 가이드만 펼쳐 준비 → 작업 → 결과 확인까지 스스로 하며 막힌 곳만 강사의 도움을 받는다. 그래서 가이드는 「학생이 행동하고, 결과를 관찰하고, 다음 판단을 할 수 있게」 쓴 글이어야 하고, 영상을 보지 않은 학생도 이 문서만으로 같은 결과에 닿아야 한다. 영상은 원맨쇼라 가이드를 띄우거나 읽어 주지 않으므로, 가이드와 영상은 같은 실습을 서로 다른 학생 행동(보기 / 직접 하기)으로 받친다.

**P목-2** 과정의 줄기(C목-2)에서 가이드는 실습의 「직접 해 보기」가 실제로 일어나게 하는 유일한 학생 자료다.

**P목-3** 가이드는 이론 · 도구 실습 · 코딩 랩의 몫(C목-3 · C목-4)을 학생 손에 넘기는 글이므로, 도구 실습 가이드와 코딩 랩 가이드는 하는 일이 다르다.

**P목-5** 사진이 없는 조작은 따라 할 수 없는 조작이다. 학생은 가이드만 보고 따라 하므로 모든 과정을 사진으로 담는다(가장 중요). 사진은 본 촬영 화면에서 뽑는다 — 리허설 화면이나 비슷한 다른 화면은 랩이 안정되기 전의 상태라 단계 · 버튼 위치 · 결과 값이 실제와 어긋난다. 없는 화면을 지어내면 학생은 그 화면을 찾다 막히고, 막힌 까닭을 스스로 알아낼 수 없다.

**P목-6** 복사할 것을 텍스트로 주는 까닭: 노베이스 학생이 사진 속 명령 · 프롬프트를 손으로 옮기면 오타가 나고, 그 오타가 「과제가 어렵다」가 아니라 「가이드가 틀렸다」로 끝난다. 블록 종류를 색과 글자로 함께 표시하는 것도 학생이 AI에 보낼 글과 터미널에 칠 글을 섞지 않게 하려는 것이다.

**P목-7** 코딩 랩 학생 폴더의 경계가 왜 그런가:
- 학생 실습 폴더와 가이드에 정답 · 해결 로직 · 완성 프롬프트 · 강사 참조를 가리키는 말을 넣지 않는 까닭: 학생의 AI(Codex · GitHub Copilot)가 폴더 전체를 읽으므로 넣는 순간 아무 요청이나 해도 정답이 나오고 과제가 장난감이 된다.
- 학생용 완성본이 실습 폴더와 따로 받는 별도 묶음인 것도 같은 까닭이다 — 같은 폴더에 있으면 학생의 AI가 읽어 정답이 된다. 완성본은 무료 계정조차 못 쓰는 학생이 결과를 확인하는 용도다.
- 작업 규칙을 `AGENTS.md`와 `.github/copilot-instructions.md`에 같은 내용으로 두는 것은 두 도구가 읽는 위치가 달라서이고, `입력/`에 앞 단계 완성 상태를 주는 것은 앞 단계를 안 했거나 PC가 초기화돼도 독립 시작이 되게 하려는 것이다.

**P목-8** 학교 PC는 재부팅하면 초기화될 수 있다. 초기화 뒤 실습 폴더의 신뢰가 풀려 VS Code가 제한 모드로 열리면 AI 도구가 동작하지 않는다 — 그래서 가이드는 재다운로드로 다시 시작하는 길을 주고, 받기 시험은 초기화된 PC와 개인 환경을 구별해 확인한다. GitHub는 강사 쪽 원본 · 배포 관리에 쓰므로 학생에게 개인 Git 설정을 요구하지 않는다.

**P목-9** 두 과정의 도구 실습은 화면 · 조작이 같아 같은 안내 · 캡처로 충분하고, 코딩 랩은 과정마다 요구 · 입력 · 출력이 달라 가이드도 달라진다.

**P목-10** 이 규칙이 생긴 실제 사고와 사용자 지적(처음 보는 사람이 이해할 만큼):
- 가이드도 실라버스 행 문장에서 시작해 문장마다 가이드 단계가 있는지 대조하지 않으면 50분 수업을 7분으로 만든 일(C목-1)이 그대로 생긴다.
- 포털 실습(실전 2-2)에 VS Code 장면 · 기록 파일 · START · 결과 폴더를 넣고, 뺀 뒤에도 「다음 실습부터 VS Code…」로 엮었다. 코딩 랩 조항(제공물 · 저장 · 다시 열기 · 바이브 코딩)을 도구 실습에 넓혀 적용한 것이다 — 도구 실습과 코딩 랩은 완전히 별개다.
- 통합반 4회차 포털 실습 1(매뉴얼 등록과 검토)은 도구 실습인데 `START.md`가 있고, 그 첫 화면이 옛 실라버스 행 그대로 「매뉴얼 원문과 등록된 지식의 조건·출처 대조하기 … 코드를 작성하지 않는 관찰·대조 실습 … 포털에 문서를 새로 등록하거나 적재하지 않습니다」라고 말했다. 실라버스 39행은 이미 「올리기 → 추출 요청 → 대조 · 고침 → 적재」로 바뀌었고 덱의 실습 소개 장도 그렇게 말했다 — 실라버스를 고친 뒤 그 행을 가리키는 가이드 · `START.md` · `안내.html` 제목 · 실습 대본 · ZIP을 함께 고치지 않은 결함이다.
- 통합반 1회차 실습 2 · 3 가이드는 옛 판(「실행 환경과 서비스 연결 확인 … ZIP · compose」, 「쿨러 사건 관찰과 근거 연결표」)으로 남았고, 실라버스 9 · 10행과 덱의 실습 소개 장, 이미 만들어진 실습 영상 04(실행 환경 — README 소개 → 설치부터 실행 → 포털 메뉴 일곱 묶음 소개) · 06(전체 과정 관찰 — 매뉴얼 적재 → 쿨러 열화 주입 → AI 판단 → 운전원 승인 → 조치 · 재관측)과 다른 말을 했다. 반대로 실습 1(학습노트) 가이드는 사용자가 확정한 영상 02대로 「주제 갤러리」였는데 덱의 소개 장이 영상에 없는 「세 구획 · 작성일」을 써서 어긋났다 — 영상이 있으면 그 영상이 실제로 한 것이 기준이다.
- 폐기판 산출물(랩 폴더 · 구성)과 옛 구성안의 「사용자 확인 대기」 항목을 실라버스와 대조하지 않고 이어받았다. 요청문의 「재사용할 수 있다」를 「재사용한다」로 읽었다 — 「대조해 맞으면 쓴다」이다.
- 식별자 · 속성 키를 낭독하고 「랩 그래프」 같은 제작 용어를 썼으며, 조작만 읽는 얕은 설명 · 결과를 띡띡 읽고 넘어가는 설명을 했다. 가이드 문장도 같은 잣대로 본다.
- 학생 랩 폴더에 제작 기록(작업 폴더 경로를 적은 화면 목록, 예상 시간 표)이 섞이거나 회차 안내 README에 「실제 실습/촬영 미수행」 같은 진행 상태가 남았다 — 학생 산출물은 학생이 읽을 것만 둔다.
- 학생 문장에 「시작본」 「이미 있는 추출 결과」 같은 운영 사정이 새어 나왔다 — 학생은 수업 운영의 내부 사정을 알 필요가 없다.

**P목-11** 가이드에 「교육용이라 실제와 다르다」 같은 단서 · 면책을 넣지 않는 까닭: 학생은 그 문장에서 아무것도 할 수 없고, 원리가 재료에 묶이지 않았다면 면책이 필요 없다.

## 작업 컨텍스트

과정 · 대상 · 오프라인 편성 · 회 ↔ 회차 대응 · 코딩 랩 영역표 · 실습 이름은 `공통.md` C맥-1 · C맥-3 · C맥-5 · C목-3이다.

**P맥-2** 오프라인 실습 행의 구분 칸은 실습 장소를 붙이고, 한 행에서 두 화면을 오가면 하는 순서대로 둘 다 적는다(예: 실습(포털 · VS Code), 실습(Neo4j · 포털)).

**P맥-3** 마지막 종합 실습(교대 인수인계)은 통합 온라인 11회차 · 실전 온라인 8회차 · 통합 오프라인 10회 · 실전 오프라인 9회다.

**P맥-4** 두 과정의 같음 · 다름은 대본만이 아니라 랩 · 가이드 · 판정에 두고, 가이드에 걸리는 판정은 C-44~C-46, 「두 과정 · 온라인과 오프라인」 표, P-96 · P-100이 가진다.

**P맥-5** 코딩 랩 가이드의 결과 확인 · 완료 기준은 영역표 C맥-5의 그 과정 칸에서 나온다(C-46을 가이드 끝 절에서 대조한다).

**P맥-6** 실습 종류마다:

| 종류 | 시작 화면 | 하는 것 | 없는 것 | 가이드가 가져가는 것 |
|---|---|---|---|---|
| 도구 실습 | 그 도구 화면이 켜진 상태(포털 실습은 포털 화면) | 정해진 화면에서 무엇을 보고 어떻게 판단하는지 차근차근 설명하며 조작하고, 결과를 그 화면에서 읽는다(그 도구 안의 내보내기 · 가져오기 · 다시 열기 포함) | 학생이 만드는 코드, 받은 폴더 · 기록 파일 · 코딩 랩식 파일 · 폴더 저장 단계, 다른 도구로 넘어가는 장면 · 예고 | 조작마다 본 촬영 화면의 사진, 두 과정이 함께 쓰는 안내 · 캡처 |
| 코딩 랩 | VS Code에서 받은 실습 폴더를 연 상태 | 바이브 코딩 일곱 단계로 요구를 내 말로 정하고, 작게 구현하고, 결과를 원자료와 대조하고, 저장 · 다시 열기 | 학생에게 주는 정답 · 해결 로직 · 완성 프롬프트, 코드 해설, 포털 관찰 실습의 화면 설명 | 단계 · 단계마다 학생이 정하거나 물을 것 · 프롬프트 힌트(C-55) · 명령 · 확인 조건 · 저장 위치(랩이 실제로 돌려 본 결과에서) |

## 작업 요령

### 시작하기

**P요-1** 규칙 문서는 `공통.md`와 이 문서 둘이다. 다른 산출물의 문서를 일괄 적용하지 않는다(가이드 작업에 이론 덱의 규칙을 끌어오지 않는다). 촬영 원천의 값 · 함정은 그 도구 `촬영준비.md`를 자료로 연다.

**P요-4** 이어받기 전에 대조한다. 시작 전에 그 종류의 본보기(P맥-7)를 통독해 「실제 학생이 이 가이드로 이렇게 따라 한다」를 잡는다. 폐기판 산출물(랩 폴더 · 구성안 · 대본 · 가이드)과 옛 구성안의 「사용자 확인 대기」 항목은 실라버스 그 행과 대조하지 않고 이어받지 않는다 — 요청문의 「재사용할 수 있다」는 「대조해 맞으면 쓴다」이지 「쓴다」가 아니다.

**P요-5** 실습 종류부터 정한다 — 화면 · 조작이 정해진 도구 실습(포털 · ARROWS · Notion · Neo4j Browser · bpmn.io)인가, VS Code에서 만드는 코딩 랩인가. 둘은 별개의 실습이라 서로의 장면 · 예고 · 제공물을 섞지 않는다. P맥-6 표의 「없는 것」은 이 문서의 일반 조항보다 앞선다(예: 「결과 확인 · 저장」 일반 조항이 도구 실습에 받은 폴더 · 코딩 랩식 파일 · 폴더 저장 단계를 들이지 않는다 — 그 도구 안의 저장 · 내보내기 · 다시 열기는 도구 화면 안의 조작이라 해당 없음).

**P요-6** 어떤 가이드 작업이든 `공통.md`와 이 문서의 `## 반드시`부터 지키고, 시작 보고에 지금 일에 어떻게 적용할지 한 줄씩 적는다. 검토도 이것부터 본다.

### 실라버스에서 시작하기

**P요-7** 모든 가이드의 첫 단계는 실라버스 그 행이다(가장 중요). 그 행의 배정 시간을 먼저 적고, 상세 문장을 한 줄씩 떼어 대조표를 만든다 — 문장마다 가이드의 어느 단계에서, 어떤 설명과 사진으로 다루고, 무엇으로 확인하는지(영상과 함께 만들면 영상 구간과 분도). 표의 꼴:

| 실라버스 상세 문장(원문 그대로) | 가이드 단계 | 영상 구간 | 설명 · 화면 | 확인 방법 | 예상 분 |
|---|---|---|---|---|---|

**P요-8** 시간. 대조표의 「영상 구간 · 예상 분」은 그 실습의 온라인 영상이 실라버스 행 하나를 감당하는지 이 단계에서 보려는 칸이다 — 분의 판정(행 단위, 늘어남 · 줄어듦)은 그 영상의 몫이고, 가이드는 그 칸을 채워 영상 쪽에 넘긴다. 가이드 자체에는 시간 조건이 없고(완료 보고의 「배정 / 계획 / 실측」은 그 실습 영상의 숫자를 함께 적는 것이다, P-197), 오프라인은 강사가 직접 유연하게 진행하므로 오프라인 가이드도 내용으로만 준비한다.

**P요-9** 실라버스를 고칠 일이 생기면(결과 조건은 P-6 · P-7 · P-8):
- 실라버스와 교재는 양쪽 방향으로 맞춘다 — 실라버스가 맞으면 가이드를 고치고, 가이드 쪽이 맞으면(이미 만들어진 영상 · 포털 실제 기능 · 앞뒤 흐름이 근거) 실라버스 고치기를 사용자에게 묻는다.
- 행의 상세 항목과 행 이름 문구는 작업하며 바꿀 수 있다 — 무엇을 왜 바꾸는지 먼저 말하고 고친다. 고정 항목을 바꾸려면 사용자에게 따로 받는다.
- 정본 엑셀과 노션 실라버스를 함께 맞추고(노션 수정은 게시라 묻는다, P요-23), 고친 행에 묶인 앞뒤 다리 · 오프라인 짝 행 · 다른 과정 짝 행을 다시 판정한다.
- 가이드의 표현을 고치는 일과 실라버스를 고치는 일을 혼동하지 않는다. 최신 결정과 엑셀이 어긋나면 임의로 섞지 말고 어긋난 셀을 적어 맞춘다.

### 앞뒤 산출물과 잇기

**P요-10** 연결점 찾기. 바로 앞 이론 대본(덱의 실습 간지 · 설명 장)과, 코딩 랩이면 앞에서 본 포털 화면에서 연결점을 찾아 가이드의 여는 단락이 앞 단계를 이름으로 받아 시작하게 쓴다(포털에 대응 기능이 없으면 앞 이론에서). 여는 말의 예: 포털 실습은 「이론에서 이걸 따졌죠. 포털에는 이렇게 들어가 있습니다」, 코딩 랩은 「포털에서 이렇게 돌아가는 걸 봤죠. 이제 이걸 직접, 더 지저분한 현실 자료로 만들어 봅니다」.

**P요-11** 연결 산출물 맞추기(결과 조건은 P-8 · P-184 · P-186 · P-188, C-33 · C-56):
- 덱·대본의 소개가 가리키는 활동은 실라버스 실습 행과 맞춘다. 가이드 첫 화면과 코딩 랩의 `START.md`는 P-184로 대조한다. 확정된 덱 화면·발화 수정은 해당 산출물의 승인 범위를 따른다.
- 승인된 덱 화면 문구는 배포된 `workspace/강의제작/산출물/<과정>/이론/NN회차/*.pptx`에서 그 문구가 든 런만 python-pptx로 바꾼다.
- 실제 촬영 큐에서 바뀐 대사 · 입력 · 순서 · 결과만 맞추고, 사소한 발화 차이로 가이드를 바꾸거나 재촬영하지 않는다.

### 만드는 순서

**P요-13** 순서:
- 실습 하나를 시작 → 수행 → 검증 → 저장 → 영상 · 가이드 전달까지 끝낸 뒤 다음 실습으로 간다. 각 단계는 앞 단계가 끝나야 넘어간다.
- 실습 한 개의 순서: 시작(실라버스 대조표 · 앞과 잇기) → 랩 강화 → 구성안 사용자 확인(꼴은 P요-23) → 대본 → 대본 사용자 확인 → 분량 → 리허설 · 녹음 · 촬영 → 검사 → 가이드 · ZIP 만들기 · 정적 검사 · 패키지 검사 · 받기 시험 → 게시(가이드 · ZIP · 영상 모두 workspace 커밋, 노션 두 과정 회차 페이지) → 완료 보고.
- 가이드 쪽 순서는 **준비 → 리허설 1회 → 수정 → 본 촬영 → 사진 추출 → 동기화**다. 준비 때 실습 자료 · 시작 상태 · 완료 조건과 대본 초안 · 가이드 단계를 정적으로 맞추되, 미리 준비하는 것은 관찰할 항목과 판단 조건뿐이다(AI 응답 · 실행 결과는 본 촬영 화면에 나온 뒤 쓴다). 리허설 전에 사진 가이드를 완성하지 않는다 — 단계 · 자료 링크 · 판정 조건을 먼저 준비하고, 랩이 안정된 뒤 본 촬영 화면에서 추출한다. 도구 실습의 실습 자료는 그 도구 화면의 시작 상태와 경계(P-57~P-66, C-42 · C-48)다.
- 영상 쪽에서 찍은 뒤 시간 계산(`python workspace/강의제작/제작도구/촬영/시간계산.py check`)으로 예상과 비교하고 바뀐 대사 · 입력 · 순서를 받으면 P요-11대로 가이드에 맞춘다.

**P요-14** 브라우저 기반 제작:
- 실습 제작 · 촬영은 모두 브라우저 기반이다. 포털 · ARROWS · Notion · Neo4j는 브라우저 화면이고, VS Code도 데스크톱 앱이 아니라 공식 `code serve-web`으로 띄운 웹 VS Code를 ego 브라우저 탭에서 조작한다(값 · 함정은 [`workspace/강의제작/제작도구/촬영/vscode/촬영준비.md`](../제작도구/촬영/vscode/촬영준비.md) 1절 · 2절 함정표). 데스크톱 앱 조작 · computer use · CDP 원격 디버깅 경로는 쓰지 않는다 — 학생 가이드에 넣을 네이티브 장면만 따로 캡처한다.
- 웹판은 표시 언어를 영어로 두므로(한국어 팩이 웹판에서 글자를 엉뚱하게 바꾼다), 학생 가이드 사진은 같은 결과 파일을 네이티브 한국어 VS Code에서 따로 캡처한다. 웹판과 네이티브의 동선 차이(창 제목줄 · 메뉴줄 대신 ☰, 「Get Started with VS Code for the Web」 문구, 폴더 열기는 브라우저 주소로, 다운로드 · 압축 해제 · 폴더 열기 · 신뢰 창)는 따로 처리하고 `vscode/촬영준비.md` 1-6에 기록한다.

### 가이드 쓰기

**P요-15** 구성하는 법. 본보기 가이드(P맥-7)의 절 목록을 먼저 뽑아 놓고, 실라버스 대조표의 순서대로 그 절에 단계를 채운다(소재 · 길이 · 순서는 실라버스와 랩이 정한다). 단계마다 위치는 행동 문장 첫머리에 녹인다(예: 「왼쪽 세로 아이콘줄 맨 위」). 처음 쓰는 도구 · 화면의 풀이 분량은 그 과정의 학생 기준으로 정하고(통합반은 처음 쓰는 비전공자, 실전반도 모른다는 전제), 뒤 단계에서 같은 조작이 나오면 풀이를 줄이되 이번 위치 · 입력값 · 선행 조작은 남긴다.

**P요-16** 복사 블록 만들기. Cypher처럼 따라 하는 질의는 `graph_guide.py`가 촬영 큐에서 바로 블록을 만든다 — 손으로 옮겨 적지 않는다. 블록의 결과 조건은 P-130~P-135.

**P요-17** 사진 만들기:
- 뽑기 · 재사용: 사진은 본 촬영 영상에서 그 조작의 순간을 뽑는다(ARROWS는 `build_student_guide.py --video <확정 mp4>`가 지정 시각에서 뽑는 방식). 기존 사진이 최신 영상의 상태와 같으면 재사용한다. 모자라거나 읽히지 않는 장면만 같은 판본으로 보충하고, 보충 근거는 `workspace/강의제작/제작도구/실습시작/capture-provenance.json` · `학생가이드_사진근거.json`처럼 원본 · 좌표 · 해시로 남긴다.
- 표시 그리기: 표시 상자의 좌표는 실제로 재고, 표시는 원본에서 다시 그린다(원본 보존 — 표시된 사진 위에 다시 그리지 않는다).
- 글자 크기 · 남의 캡처: 사진 글자가 작으면 더 나은 원본이나 그 영역 캡처를 쓴다(원본 화면에서 그 영역을 잘라 쓴다). 남의 캡처의 옛 표시가 지금 설명과 맞는지 보고, 이미 받은 캡처를 다시 요청하지 않는다.
- 결과 조건은 P-141~P-160.

**P요-18** 문장 쓰기(결과 조건은 C-1~C-11 · P-21~P-29 · P-161~P-169):
- 말투 · 본보기: 가이드의 말투 · 쓰지 않는 말은 `공통.md`와 이 문서가 정하고, 본보기는 절 구조와 단계 꼴의 정본이다(문장은 인수 조건이 앞선다).
- 앞 단계를 받는 문장은 「이론 시간에는 …을 배웠습니다. 이번에는 …을 직접 확인해 보겠습니다」 꼴로 쓴다.
- 이어 읽기: 다 쓴 뒤 문장을 이어 읽어 앞 문장에서 다음 문장으로 자연스럽게 이어지는지 확인한다. 검토는 실제 문단을 읽어 판단하고, 금지어 검색 통과만으로 자연스러움 · 교육 효과를 판정하지 않는다.

### 검사 · 받기 시험

**P요-20** 검사하는 법(결과 조건은 P-170~P-178):

**P요-21** 받기 시험은 같은 판본으로 맞춘 뒤 실제 학생 경로로 한다(결과 조건은 P-173~P-177). 포털 · Docker를 쓴 작업(로컬 · 촬영 · 받기 시험)이 끝나면 Docker Desktop을 끄고 프로세스가 0인지 확인한다.

### 일하는 방식

**P요-23** 범위 · 확인 받기(C요-2~C요-5에 더해 가이드에서만).
- 범위: 정적 가이드 작업에는 실행 · AI 시연 · 캡처 · 음성 생성이 들어가지 않는다(요청한 도구 · 회차에서만). 처음부터 `공통.md`의 이 일 절 · 이 문서와 원 자료를 끝까지 읽고 완성판을 만들고, 여러 회차에 같은 틀을 적용할 때는 대표 하나로 먼저 확인한 뒤 넓힌다. 같은 판본 산출물의 재검토 · 재생성 · 재검사 · AI 호출을 되풀이하지 않는다.
- 묻는 것: 허용된 반복 작업은 다시 묻지 않는다(사전 승인 단계 없음 — 예외는 새 촬영 리듬 · 도구의 대표 구간, 실습 구성안 · 대본). 더 묻는 것은 실라버스 조정(교재 근거로 행을 고침) · 노션 실라버스 수정 · 데이터 볼륨 삭제다.
- 묻는 꼴: 들을 수 없는 음성도 상태를 특정해 요청한다. 사용자 지적은 같은 유형 전체에 적용하며, 앞의 판정을 뒤집으면 그렇다고 밝힌다. 비용 견적은 글자 수 · 크레딧 등으로 알린다.
- 사용자 확인을 받을 때는 전문을 읽게 하지 않고 판단용 요약을 준다(구성안 → 대본 두 번, 가이드도 같은 꼴): ① 배정 · 계획 시간과 구간별 분 ② 구성 흐름 ③ 실라버스 문장 ↔ 구간 · 가이드 단계 대조(빈칸 0) ④ 실제 문장 발췌(시작 · 중간 여러 곳 · 끝) ⑤ 판단할 지점만 준다.

**P요-24** 작업 단위와 작업자:
- 세션의 담당 범위 · 산출물 순서 · 검토(작업자 작업 → 검토자 1회 → 목록만 수정 → 끝)는 `hyd-task` 3절이 정한다. 검토자는 이 문서 · 실제 산출물 · 품질 본보기로 대조하고, 작업자 지시에 범위 · 금지 · 보고 양식을 적으며 작업자는 원문과 줄 번호를 가져온다.
- 파일이 겹치지 않는 갈래만 동시에 돌리고 같은 파일을 두 세션이 동시에 고치지 않는다. 다른 세션의 자원 · 탭을 확인 없이 끄거나 지우지 않는다.

**P요-25** 보고 꼴은 `hyd-task` 3절 「보고」이고 상태어는 C-60이다.

**P요-26** 가이드 · 랩 · 도구는 `workspace/` 안에서 고친다. 이 문서를 고치는 법은 C요-9이고, 상태 글자는 정본의 글자를 그대로 옮긴 것만 두며, 규칙 문장은 근거 없이 바꾸지 않는다. 표 안 순서는 번호 순서와 다를 수 있다.
