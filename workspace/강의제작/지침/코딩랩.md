# 코딩 랩

## 반드시
1. **K-1. 랩의 범위는 실라버스 그 행의 VS Code 구간 하나다.** — 판정: 대조표를 읽는다. 대조표는 행 문장 원문마다 다루는 곳(`START.md` 절, 자료, 확인 사례, 가이드 단계), 확인 방법, 예상 분을 적은 표다. 빈칸이 없고 행에 없는 과제가 없어야 통과다.
   코딩 랩은 실라버스 구분 칸에 VS Code가 있는 행에만 있다. 프로세스 · 종합 회차(온라인 통합 9~11 · 실전 6~8회차, 오프라인 통합 8~10회 · 실전 7~9회)에는 코딩 랩이 없고, bpmn.io와 포털 도구 실습을 한다.
   시간은 온라인 랩만 행 단위로 잰다. 계획 분과 실측 분이 모두 「배정 분 − 10분」 이상이어야 하고 상한은 없다. 그 시간은 행의 내용으로만 채우고 대기, 억지로 만든 실패, 가상 학생으로 채우지 않는다. 오프라인 랩은 분으로 판정하지 않는다.
2. **K-2. 공통 C-8의 회차 안 순서대로 앞을 이름으로 받아 열고, 포털 없이 돈다.** — 판정: `START.md` 첫머리와 가이드 첫 화면을 읽는다. 앞 포털 실습을 이름으로 받고(대응하는 포털 기능이 없으면 바로 앞 이론), 이 랩이 줄기 단계(온톨로지 → 에이전트 → 프로세스) 가운데 어디인지 말해야 한다. 그리고 `grep -rn -E '다음|포털에서|앞 실습의' <랩 폴더>`로 후보를 모아 걸린 곳을 읽어 가른다. 실라버스 순서상 바로 다음 랩이 아닌 것의 예고, 포털 화면 설명, 학생이 만든 적 없는 결과를 전제한 문장이 없어야 통과다.
3. **K-3. 문제는 현업 규모로 어렵고, 바이브 코딩 일곱 단계를 밟아야만 풀린다.** — 판정: 장난감 시험(학생 ZIP을 AI 도구에 주고 통째로 풀어 달라고 하는 유료 시험, 길 6)을 Codex와 Claude에서 각각 `two_turn`과 `one_turn`으로, 모두 네 번 돌린다. 어느 번에도 강사 참조 답과 같은 결과가 나오지 않아야 통과다.
   자료는 공장 단위의 여러 출처(자산 대장, 수백 줄의 태그, 정비 이력, 품번이 변형된 부품 마스터, 판본이 다른 점검표)라서 눈으로는 맞출 수 없다. 주 질문의 경로 위에 원자료만으로는 하나로 정해지지 않는 결정 지점이 1개 이상 있고, 고른 갈래에 따라 역할(정비 · 구매 · 운전 · 품질)의 다음 행동이 바뀐다. 억지 함정, 고의 오류, 파일 수로 꾸민 난도, 해피패스, 구세주 데이터가 없어야 한다.
   일곱 단계: ① 파일을 바꾸지 않고 AI와 파악 ② 요구와 기대 답을 내 말로 정리 ③ 계획 검토 ④ 작게 구현 ⑤ 실행 결과를 원자료와 대조 ⑥ 고침 ⑦ 저장하고 다시 열어 확인.
   랩마다 아래 셋 중 기법 하나를 전면에 둔다. 설계는 탐색으로 함정을 찾고 사람이 결정한다. 구현은 한 기능씩 실제 DB로 확인한다. 판정은 기대 결과를 원문에서 먼저 적고 대조하며, AI 출력을 기대값으로 쓰지 않는다.
4. **K-4. 학생 폴더에 답이 없다 — 학생의 AI는 폴더 전체를 읽는다.** — 판정: `grep -rn -E 'reference|제작용|강사|정답|해결 로직' <랩 폴더>`로 후보를 모아 걸린 곳을 읽어 가른다. 답이나 강사 자료의 위치를 알려 주는 문장이 없어야 한다(「막히면 강사에게」와 「정답이 하나로 정해져 있지 않다」는 해당 없음). 그리고 학생 폴더 전문을 강사 참조와 견줘 읽어, 답을 풀어 쓴 문장이 없어야 통과다.
   학생 폴더에 없어야 하는 것: 해결 로직, 정답 값, 기대 결과 표, 판정 절차, 정답 방향, 그대로 붙여 넣으면 끝나는 완성 프롬프트, 강사 대본, 결정 지점의 답을 적은 현장 메모. README는 출처, 시점, 맥락까지만 쓴다. 작업 규칙(K-6)은 답을 지키는 보안 장치가 아니다.
   강사 참조(갈래별 답과 기대 결과)는 `실습시작/reference/`에만 둔다. 학생용 완성본은 실습 ZIP 밖의 별도 묶음이고, 「계정이 없는 학생이 결과를 확인하는 묶음」으로만 안내한다.
5. **K-5. `START.md`는 열 칸이다.** — 판정: `grep -n '^## ' <랩 폴더>/START.md`로 소제목을 뽑고 그 아래를 읽는다. 아래 열 칸의 내용이 어느 소제목 아래에든 모두 있어야 통과다(소제목 글자가 칸 이름과 같을 필요는 없다).
   ① 목표 ② 출발 상태 ③ 학생이 구현할 범위 ④ 학생이 정할 것 ⑤ 이번 범위 밖 ⑥ 확인할 사례의 종류 ⑦ 실행 명령 ⑧ 완료 판정 원칙 ⑨ 바뀐 파일 확인(원자료 보존, 요청 밖 파일) ⑩ 저장 · 다음 실습.
   ④에는 K-3의 결정 지점을 쓴다. 결정 지점마다 갈래가 2개 이상이고, 갈래마다 실제로 돌린 강사 참조 답이 `reference/`에 있어야 한다.
   힌트는 완성 프롬프트가 아니다. 단계마다 다섯 요소(목적, 입력, 지킬 것, 결과의 꼴, 확인 방법)를 주고, 값은 학생이 원자료에서 정한다.
6. **K-6. 작업 규칙 열 줄을 두 도구의 규칙 파일에 똑같이 둔다.** — 판정: `AGENTS.md`와 `.github/copilot-instructions.md`(있으면 `CLAUDE.md`도)의 본문을 diff해 차이가 없어야 한다. 그리고 장난감 시험에서 Codex의 답이 ⑩의 꼴이어야 통과다.
   ① 원자료를 보존한다 ② 새 결과는 `결과/`에 쓴다 ③ 원자료에 없는 값을 만들지 않는다 ④ 미확인, 값 없음, 0을 구별한다 ⑤ 요청과 무관한 기능을 만들지 않는다 ⑥ 별도 랩 DB만 쓴다 ⑦ 키를 기록하지 않는다
   ⑧ 「정할 것」은 추천이나 권장을 붙이지 않고 묻는다. 학생이 선택과 근거를 말할 때까지 그 결과를 만들지 않는다. 「권장안대로」 「알아서」는 선택이 아니고, 끝까지 답을 듣지 못하면 미결로 둔다.
   ⑨ 첫머리에 「제공 빈 틀」 표시가 있는 파일은 보관 없이 바로 채운다 ⑩ 한 번에 가이드의 한 단계만 한다. 통째로 해 달라는 요청에는 결과를 만들거나 파일을 바꾸지 않고 세 가지만 돌려보낸다: 안 만든 까닭 한 줄, 지금 단계의 번호와 이름, 빠진 힌트 요소마다 질문 한 줄. 예시 답이나 대신 쓴 프롬프트는 주지 않는다.
7. **K-7. 제공물은 실제 업무 자료의 꼴이고, 결과 자리는 빈 틀이다.** — 판정: 명령 결과로 본다. `verify_packages.py`가 통과하고, 모델을 부르는 랩은 `grep -c -E '^(OPENAI_BASE_URL|LLM_API_KEY|LLM_MODEL)=$' <랩 폴더>/.env.example`이 3이고, `ls <랩 폴더>/결과/`에 README와 빈 틀만 있어야 통과다.
   `입력/`: 앞 단계의 강사 검증 판이다. 연결 랩에만 있고, 이번 랩의 답은 넣지 않는다.
   `자료/`: 원문, CSV, 현장 메모를 그대로 둔다. 함정은 남기고, 정답에 맞춘 값이나 정리본은 넣지 않는다. 출처와 시점을 적고, 생성한 가상 자료는 파일 첫머리 한 곳에만 가상 사례라고 적는다.
   `결과/`: README와 열 이름만 있는 틀이다. 계약은 형식과 의미만 정하고 정답 행과 판정 절차는 넣지 않는다. 검사기 `check.py`는 ID, 끝점, 중복 같은 구조만 검사하고 「의미와 질문별 답은 원자료와 따로 대조」를 출력한다.
   계약은 사실표의 「두 설계 원칙」을 어기지 않는다. 계속 바뀌는 값을 그래프에 두거나 설비 · 납기 결정을 에이전트에게 맡기면 안 된다. 새 코드 이름은 `STRUCTURE.md`를 따른다(영어 `snake_case`, 하는 일로 짓고 설명 글은 한국어).
8. **K-8. 격리는 실제로 하고, 모델은 실제로 부른다.** — 판정: `grep -rln -E 'recorded/|replay|재생 모드' <랩 폴더>`와 `find <랩 폴더> -name 'replies*.json'`의 결과가 0줄이어야 통과다. 학생 실행이 남긴 자기 호출 기록은 세지 않는다.
   그래프 DB는 `lab_db.py`가 만든다. 폴더마다 `neo4j:5.26-community` 컨테이너를 새로 띄우고 127.0.0.1의 포트를 자동으로 고르며, `랩_연결.json`의 ID와 컨테이너 라벨 `hyd.practice.id`가 같을 때만 재사용한다. 포털 DB의 주소와 계정은 쓰지 않는다.
   가드레일이 막는 것은 포털 DB, 전체 삭제, 키를 코드 · 결과 · 기록에 적는 것, 원자료 덮어쓰기뿐이다. 외부 MCP와 학생 자신의 Notion은 막지 않는다. 랩 결과가 포털 에이전트에 자동으로 연동된다고 쓰지 않는다.
9. **K-9. 랩 하나만 받아 앞 랩 없이 시작하고, 저장하고 다시 열어 다음 랩으로 잇는다.** — 판정: 새 시험 폴더에서 그 ZIP 하나만 받아 시작되고, `test_launcher.py`가 통과해야 한다. 그리고 학생 파일을 고친 뒤 「이전 작업 열기」가 그 파일을 덮지 않고 「새 시작」이 새 폴더를 써야 통과다.
   자기 앞 랩의 결과를 가져오는 것은 선택이다. 가져올 때는 판본과 계약을 확인하고 별도로 보관하며 덮어쓰지 않는다. 다음 랩의 `입력/`은 이 랩 `결과/`의 계약을 받는다.
   자동 복구를 약속하지 않고, 학생에게 Git 설정이나 commit을 요구하지 않는다. 수정본을 반영하는 랩에는 반영한 뒤 개수와 값을 원자료와 다시 세는 확인 사례가 `START.md` ⑥과 가이드에 있어야 한다.
10. **K-10. 두 과정은 같은 랩을 하고, 실전반은 아래 영역에서 실제 역할이 쓰는 결과물을 하나 더 만든다(공통 C-4).** — 판정: 두 과정 랩의 `결과/` 계약과 완료 조건을 아래 목록과 견줘 목록 밖 차이가 없어야 한다. 1회차는 두 과정 공통이므로 `diff -rq workspace/강의제작/산출물/통합반/실습/01회차/랩 workspace/강의제작/산출물/실전반/실습/01회차/랩`의 결과가 0줄이어야 통과다.
    읽는 법: 괄호 안은 온라인 회차(통합/실전)이고, 「/」 앞은 두 과정의 결과, 「/ +」 뒤는 실전반이 그 위에 더 만드는 결과다.
    모델 설계 · 적재 · 조회(2/2): 설비 · 센서 · 공용 부품 모델과 별도 랩 DB 조회 / + 공급 조건을 포함한 부품 활용 조회(사용 설비, 공급 근거). 절차 · 판단(3/2~3): 절차, 금지, 완료 조건과 결정표, 후보 비교 / + 후보별 이유, 출처, 추가 확인을 담은 조치 검토 결과. 문서 지식화(4/3): 추출 → 출처를 포함한 후보 → 사람 검토 → 별도 DB 적재 / + 준비, 금지, 완료 조건을 담은 작업 확인 카드.
    기본 에이전트(5/4): 원인 · 점검 계획 에이전트 / + 대상, 관측 시각, 이유, 확인 항목을 담은 점검 요청. 스킬 · 자기 자료(6/4): 회의 후속 작업, 자기 노트 퀴즈 / + 회의 · 점검 · 변경 근거를 담은 다음 협의 안건. 외부 · 직접 만든 도구(6/4): 두 과정 공통 한 랩(외부 MCP 연결, 그리고 서버 골격에 조회 함수 추가). 질문 · 재개 · 명세 · 검증(7~8/5): 부족한 정보만 묻고 재개, 작성 · 검토 역할, 긴급 표시의 명세와 구현, 회귀 검사 / + 같은 점검 요청으로 명세와 검증. 통합반에만 있는 것: 다른 활용(5회차 — 품질 접수, 센서 도표), 자료 통합(8회차 — 로컬 인수인계).
11. **K-11. 오프라인은 온라인 랩 묶음을 그대로 받는다.** — 판정: 오프라인 회의 가이드와 묶음 목록을 대응하는 온라인 회차 랩과 견줘, 새 과제와 오프라인 전용 묶음이 없어야 통과다. 예외는 1회의 `01일차_오프라인_모델과질문`, `오프라인_가이드.html`, `오프라인1_가이드.zip`이다.
    오프라인 회와 온라인 회차의 대응은 실라버스 L-11을 따른다. 한 회에 다 들어가지 않으면 뒤 랩부터 「빨리 끝나면 해 볼 것」으로 돌린다.
    Notion 학습노트는 학습노트 하나 아래에 주제 카드를 두고 자유롭게 쓰며, 분류나 별도 DB를 강제하지 않는다. 쓰는 순서는 1회 준비 → 통합 6회 퀴즈 · 10회 정리, 실전 5회 협의 안건 · 9회 기록이다. Notion 접속이나 MCP가 안 되면 같은 노트를 파일로 두고 파일 · Git · 시간 MCP로 같은 단계를 한다.
12. **K-12. 코드를 몰라도 개인 GPT 무료 계정으로 끝까지 간다.** — 판정: 가이드 단계와 리허설 기록을 읽어, 코드 해설이 있어야 넘어가는 단계와 유료 기능이 필요한 단계가 없어야 한다. 그리고 학생용 완성본을 새 폴더에서 실행한 결과가 영상 끝의 결과와 같아야 통과다.
    학생이 판단하는 곳은 요구를 내 말로 정하기, 결과를 원자료와 대조하기, 다른 입력으로 검증하기의 세 군데다. 만드는 데 필요한 이론은 그 단계에서 앞 이론의 같은 이름과 같은 정의 한 줄로 다시 건다(공통 C-9).
13. **K-13. 학생이 읽는 문장은 한 대상에 한 이름을 쓰고, 회는 그 과정의 말로 부른다.** — 판정: 온라인 랩은 `grep -rn -E '[0-9]+회([^차]|$)|[0-9]+일차|첫날' <랩 폴더>`, 오프라인 랩은 `grep -rn -E '[0-9]+회차|[0-9]+일차' <랩 폴더>`를 돌려 걸린 곳 가운데 폴더 이름이 아닌 것이 없어야 한다. 그리고 온라인 통합 7회차 · 실전 5회차, 오프라인 통합 7회 · 실전 6회보다 앞 회차 랩에서 `grep -rn -E 'SDD|BDD|명세 주도|행동 주도' <앞 회차 랩>`의 결과가 0줄이어야 통과다.
    이름은 공통 C-9대로 한 대상에 하나만 쓴다(랩에서 자주 갈리는 예: 「실습용 예제 DB」와 「별도 랩 DB」). 식별자와 속성 키는 문장에서 뜻으로 풀어 쓰고, 그대로 쓰는 것은 자료, 명령, 복사 블록에서만 한다. 줄인 랩 이름 대신 그 랩이 하는 일로 부른다.
14. **K-14. 랩 완성은 네 실행 기록이 모두 `확인됨`일 때다.** — 판정: 작업 폴더 `기록.md`에 넷 각각의 명령, 출력 위치, 판본 해시가 있어야 한다. 넷 중 하나라도 `미확인`이면 완료가 아니다.
    ① 학생 경로 리허설 1회: 학생과 같은 입력, 폴더, 명령으로 Codex와 강의 중계 `coding` 모델을 써서 돈다.
    ② 검사기가 일부러 망가뜨린 입력(ID 중복, 끝점 없음, 관계 방향)을 잡는지 본다. ③ 강사 참조를 갈래마다 실행한다.
    ④ 받기 시험: 시작 도구 → 다운로드 → 새 폴더에 풀기 → VS Code로 열고 신뢰 → 가이드대로 실행 → 저장 → 다시 열기. 학교 PC 초기화 뒤와 개인 환경을 구별해 적는다.
15. **K-15. 본 것만 쓰고, 영상과 가이드 작업에는 실제로 돌린 것을 넘긴다.** — 판정: `grep -rn '예상과 다르면' <랩 폴더>`의 결과가 0줄이어야 한다. 그리고 `START.md`와 결과 README의 결과 문장마다 그것을 본 리허설이나 실행 기록이 있어야 통과다.
    아직 나오지 않은 AI 응답과 실행 결과(추천안 이름, 점수, 순위)는 쓰지 않고 관찰할 항목과 판단 조건만 쓴다. AI가 처음에 맞혔으면 고의 오류를 넣거나 다시 시도하지 않는다. 막혀서 참조본으로 바꾼 곳은 그렇다고 짧게 밝힌다. 이미 만든 영상이 있으면 랩과 `START.md`가 그 영상의 실제 입력, 순서, 결과와 같아야 한다.
    영상 작업에 넘길 것: 돌려 본 시작본, 단계마다 AI에게 묻고 정하는 순서, 결과 화면, 결정 지점과 확인 사례, 그 자리에서 다시 걸 이론의 이름과 정의 한 줄, 학생용 완성본.
    가이드 작업에 넘길 것: 단계, 단계마다 정하거나 물을 것, 힌트, 명령, 확인 조건, 저장 위치(학생 폴더에 있는 것만, 키와 접속값은 빼고), 네이티브 VS Code 캡처 목록(다운로드, 압축 해제, 폴더 열기, 신뢰 창).

## 길
1. 행 뽑기 — 공통 「행 뽑기」 명령으로 그 회차 행과 앞뒤 행을 뽑고, 대조표(K-1)를 작업 폴더 `스펙.md`에 쓴다.
2. 앞과 잇기 — 앞 이론 덱의 실습 설명 장과 앞 포털 실습 가이드를 보고 연결점 한 줄을 정한다. 그 한 줄을 `START.md` 첫머리, 가이드 첫 화면, 영상 여는 말에 똑같이 쓴다.
3. 과제 설계 → 구성안 사용자 확인 1회 — 사용자에게 보여 줄 것은 배정 분과 계획 분, 흐름, 대조표, `START.md`의 첫머리 · 「학생이 정할 것」 · 끝 부분 발췌, 결정 지점과 갈래다.
4. 생성 — 생성기를 고치고 그 랩 하나만 만든다: `python workspace/강의제작/제작도구/실습시작/<생성기>`. 어느 랩이 어느 생성기인지는 `실습시작/README.md` 「생성」 표에 있다. 폴더만 고쳤으면 `python …/실습시작/lab_package.py <랩 폴더> --version <새 판>`을 돌린다. `START.md` 랩(`START.md`에서 가이드와 ZIP을 만드는 랩)은 `python workspace/강의제작/제작도구/온라인/labs/online/start_guides/build.py <랩 폴더>`를 돌린다. 산출물 HTML과 ZIP은 손으로 고치지 않는다.
5. 강사 참조 — 2회차 실습3 · 4는 `python …/실습시작/verify_reference.py`, 조치 판단 네 랩은 `HYD_MAIN_ROOT=<저장소 루트> python …/실습시작/reference/session3/run_reference.py`, 문서 지식 네 랩은 `python …/실습시작/reference/session3_docs/run_reference.py`를 돌린다. 「불일치」로 멈추면 결과를 맞추지 말고 원인을 고친다. 검사기 고의 손상(K-14 ②)도 이 실행이 기록한다(2회차는 `reference/session2_check_trials.py`).
6. 장난감 시험(유료) — `python …/실습시작/reference/ai_toy_test.py <학생 ZIP> --tool codex|claude --scenario two_turn|one_turn --out 작업/검사/<새 폴더>`를 네 번 돌린다. 모델을 부르는 랩은 `--lab-env <파일>`을 더한다. 뚫리면 결정 지점, 자료, 작업 규칙을 고친 새 판으로만 다시 돌린다.
7. 학생 경로 리허설 — 웹 VS Code(`code serve-web`)를 ego 탭에서 열고 Codex와 중계 `coding` 모델로 돈다(값과 길은 `촬영/vscode/촬영준비.md` 「길」 1~4). 준비, 설명, AI 대기, 구현, 확인, 막힘 시간을 나눠 기록한다.
8. 묶고 검사 — `python …/실습시작/build_launcher.py` → `python …/실습시작/verify_packages.py` → `python …/실습시작/test_launcher.py`.
9. 받기 시험(K-14 ④) — 기본 주소는 `http://127.0.0.1:8765`다. 공개 배포는 패키지 커밋을 먼저 올리고, 그 커밋의 raw 주소로 `build_launcher.py --base-url <주소>`를 돌려 커밋 해시와 ZIP 해시를 함께 고정한다.
10. 넘기기 — K-15 목록을 영상 작업과 가이드 작업에 넘긴다. 커밋은 `CLAUDE.md` 2절대로 한다.
11. 고칠 때 — 바뀐 랩의 생성기 하나만 고치고, 바뀐 곳과 그 연결에 대해서만 4~9를 다시 한다. 승인된 덱 화면 문구가 바뀌었으면 그 랩의 `참고_교재_발췌.md`와 ZIP도 다시 만든다. 같은 판본에서 통과한 리허설, 강사 참조, 장난감 시험은 다시 돌리지 않는다.

## 함정
- 작업 규칙이 「묻고 멈추기」만 하면, 「START.md대로 다 해 줘」에 이어 「권장안대로 다 해 줘」 두 마디로 강사 참조 답이 값까지 나왔다. 그래서 ⑧과 ⑩의 돌려보내기가 있어야 한다.
- 현장 메모나 자료 설명이 결정 지점의 답을 적어 두었거나 결정 지점이 주 질문 밖에 있으면, 장난감 시험이 뚫렸다.
- 수정본을 반영하던 학생 AI가 실제 센서 TS1을 지웠다(실전 2-4). 반영 뒤 다시 세는 확인 사례는 그래서 있다.
- 학생 AI는 실습 폴더 위 폴더의 `AGENTS.md`와 `CLAUDE.md`(저장소 제작 규칙)도 읽는다. 그래서 리허설과 장난감 시험 폴더는 저장소 밖에 둔다.
- AI가 「정할 것」에 권장을 붙여 낸다. 그래서 학생이 원문을 열어 자기 선택과 근거를 말하는 자리가 랩 흐름에 있어야 한다.
- 학교 PC가 초기화되면 폴더 신뢰가 풀려 VS Code가 제한 모드로 열리고 AI 채팅이 동작하지 않는다.
- `lab_db.py`가 내는 「새로 만든 랩 DB라 비어 있습니다」는 오류가 아니다. 컨테이너가 없어서 새로 만든 것이므로 적재부터 다시 실행한다.
- 생성기 가운데 일부는 돌리면 다른 랩까지 옛 판으로 되돌린다. 돌리기 전에 `실습시작/README.md` 「생성」 표의 「지금」 칸을 본다.
