# 5일차 — 에이전트: 질문하는 AI와 일하는 AI

## 5.1 이론 1 (48행) 「질문하는 AI와 일하는 AI의 차이 이해하기」(40분)

### 5.1.1 LLM · RAG · Agent의 구분

| 항목 | (가) 표준 개념 [일반] | (나) HYD의 대응물 | (다) 교재에 쓸 실제 예 |
|---|---|---|---|
| **LLM** (Large Language Model, 대규모 언어 모델) | 주어진 글을 이어 새 글을 만들어 내는 모델. 입력 한 번에 응답 한 번. 모델이 학습한 내용 밖의 최신 값을 스스로 알지 못한다 | 워커의 Claude Code CLI는 자기 키가 없고, process의 로컬 중계 관문(`it/process/procsvc/course_model.py` — 점유에 묶인 실행 토큰)을 거쳐 강의 중계(LiteLLM)의 수업 모델 하나(`course_ledger.POLICY['model'] = 'coding'`)를 부른다. 키 없는 PC는 녹화 재생(`AI_MODE=replay`)이다. [기록] 관문을 두기 전 호스트 워커 실행 로그의 모델 표기는 `claude-opus-5-5`였다(기록 ② 이벤트 줄의 `run_start`) | LLM만 있으면 「HYD-01 유온이 지금 몇 도인가」에 답할 수 없다. 값은 시계열 DB에 있고 모델 안에 없다 |
| **RAG** (Retrieval-Augmented Generation, 검색 증강 생성) | 질문과 가까운 문서 조각을 먼저 찾아 모델에게 읽혀 근거 있는 답을 만든다. 답이 문서에서 나오고, 도구를 골라 부르거나 일을 끝까지 수행하지는 않는다 | **HYD 에이전트는 RAG를 쓰지 않는다.** 임베딩 · 벡터 저장소 코드가 없다(`R/it`, `R/common`, `R/scripts`에서 `embedding · pgvector · faiss · chroma` 검색 → 없음). 지식은 그래프 질의(Cypher), 값은 SQL로 읽는다. 4일차 덱 32장이 「문서 검색과 구조화 등록」을 이미 비교했다(`R/workspace/강의제작/제작도구/온라인/decks/integrated/day04/통합반_04일차.md:531` SLIDE 32) | RAG와의 대비 예: 승인 카드의 「출처 HM-8.5 즉시 완화 조치」는 문서 조각을 검색한 것이 아니라, 인제스천으로 등록된 규칙에서 문서 절로 이어진 **관계를 따라간 결과**다 |
| **Agent** (에이전트) | 목표를 받고 도구를 골라 부르며, 결과를 보고 다음 행동을 정해 목표를 이룰 때까지 반복하는 시스템(LLM + 도구 + 실행 고리). 단순 답변이 아니라 산출물을 만든다 | 워커가 CLI에 **프롬프트 한 개와 작업 폴더**를 준다. 프롬프트는 업무 · 지시사항 · 입력 데이터 · 작업 공간 · 결과 제출 형식 순이다(`R/it/agent-worker/worker/prompt.py:13-55`). 도구는 MCP 서버로 붙는다(6일차) | 5.1.2의 실제 실행 기록 |

- 「LLM · RAG · Agent」를 가르는 기준(교재 표현 후보): **LLM = 말하기, RAG = 찾아서 말하기, Agent = 찾고 계산하고 제출하기.** HYD 에이전트가 한 마지막 행동은 말이 아니라 **조치 카드 묶음을 process에 제출**한 것이다(`submit_decision`, 판단 id `DEC-1010-056-0972`).
- 에이전트의 일은 「판단 · 제안」까지다. 설비 명령 · 작업지시 · 메일은 에이전트가 하지 않고 사람 승인 뒤 시스템 단계가 한다(1일차 사실표 4.4, 이 문서 7.1절).

### 5.1.3 「단순 답변」과 「업무 산출물」의 차이 — 쿨러 사례

### 5.2.2 「지식」과 「현재값」을 혼동하지 않는 방법

- 2~4일차 사실표 5절(「지식과 값」)의 구분을 따른다. 에이전트 쪽의 실제 장치:
  - 정적 지식(그래프)은 「어느 센서를 어떤 조건으로 보라」만 갖고, **값은 조회 시점에 시계열 DB · 업무 DB에서 가져온다**. `gather_facts` 도구가 이 일을 한다: 「규칙이 검사할 사실을 온톨로지가 정한 출처(시계열 · PLC 상태 · MES 등)에서 실제로 가져온다. 값마다 어디서 어떻게 얻었는지 provenance 를 함께 준다.」(`dmn_mcp/server.py:60-63`)
  - 고정 규칙(워커가 실행마다 CLI에 시스템 지시로 붙이고 — `--append-system-prompt`, 포털 에이전트 화면이 같은 글을 보인다): 「연결된 MCP 도구가 있으면 추측 대신 도구로 확인하세요. 지식은 온톨로지(Neo4j MCP), 현황·업무 값은 업무 DB(enterprise MCP), 규칙 판정은 DMN 도구(hyd-dmn MCP)의 결정론적 결과를 씁니다. 규칙을 임의로 해석해 바꾸지 않습니다.」(`it/process/procsvc/work_rules.py` 공통부 `_TOOLS` + 업무부 `HYD_PLANT.tool_sources`)
  - 값에는 신선도가 붙는다: `freshness: {"ok": true, "age_s": 0.9, "max_age_s": 60, …}` — 최신 TS1이 60초보다 묵었으면 `ok: false`가 되어 판단이 보류된다(5.2.3).
  - 학생이 보는 곳: 처리 기록의 도구 호출 줄(물음 → 받음). 값마다 「물음(입력)」과 「받은 원문」이 나란히 보인다(`R/it/portal/www/caseRecord.js:262-265`).

### 5.2.3 멈춤 조건 — 근거 부족 · 도구 호출 실패 · 권한 제한

| 상황 | 시스템이 하는 일 | 근거 · 실제 문구 |
|---|---|---|
| **근거가 부족하다**(데이터가 묵음 · 관측 공백 · 모든 원인 증거가 불일치) | 에이전트는 값을 꾸며 폼을 채우지 않고 **보류 객체 하나만** 제출한다: `{"__deferred__":{"status":"UNKNOWN 또는 UNSUPPORTED","reason":"현장 담당자가 읽을 보류 이유","evidence":{}}}`. status는 판단 엔진(진단 도구)이 낸 근거 판정(`evidence_status.status`)을 그대로 쓰고, 그런 판정이 없을 때만 조회 실패 · 결측은 `UNKNOWN`, 조회한 근거가 모두 조건에 맞지 않으면 `UNSUPPORTED`. reason은 처리 건 화면에서 현장 담당자가 읽는 한국어 한두 문장이고 도구 · 함수 · 필드 이름을 쓰지 않는다(실제 조회 결과는 evidence에). 서버가 모양을 검사한다(`status` · `reason` · `evidence` 세 키만, 증거 128 KiB 이내). 보류와 완료 폼을 섞으면 거절. 작업은 PENDING으로 멈추고 사람이 **재평가를 요청**하거나(`POST /api/todolist/{id}/reassess`) 닫는다 | `it/agent-worker/worker/prompt.py` `output_contract` · `DEFERRAL_RULE`, `R/it/process/procsvc/task_deferral.py`, `R/it/process/procsvc/instance_mode.py`의 `reassess_task` 경로. 도구 쪽도 같다: `diagnose`는 「withheld=true이면 근거 미확인 또는 지지 근거 없음이므로 원인을 임의로 골라 후속 조치 판단을 하지 않는다」(`dmn_mcp/server.py:41-44`) |
| **도구 호출이 실패한다** | 모든 hyd-dmn · enterprise 도구는 같은 봉투 `{"result": "ok", "document": …}` 또는 `{"result": "error", "error_kind": "INVALID" \| "UNKNOWN", "message": …}`로 답한다. 스택 추적을 에이전트에게 던지지 않는다. 지시: 「조회 실패와 값 없음을 구분합니다」 「끝내 실패하거나 결과가 0행이면 그대로 적습니다. 실패를 0이나 빈 값으로 바꿔 성공처럼 제출하지 않습니다.」 | `dmn_mcp/tools.py` `enveloped`, 고정 규칙 `work_rules.py` 공통부 `_NO_INVENTION` · 업무부 `HYD_PLANT.sections` |
| **권한이 없다** | 에이전트가 허용 목록에 없는 도구를 부르려 하면 CLI가 권한 요청을 내고, 헤드리스 실행은 답할 수 없어 **사람에게 묻는 질문**으로 올라간다(`permission_request`). 도구 접근 거절을 우회하는 용도로 질문을 쓰지 말라고 프롬프트가 못 박는다 | `settings.py:94-96`, `prompt.py:45-51` 「도구 접근 거절이나 설비 조치 승인 우회에는 쓰지 마세요. 답변은 실행 권한을 바꾸지 않습니다.」 |
| **필수 업무 정보가 없다** | `{"__human_input__":{"question":"…","options":[]}}` 하나만 내고 기다린다 → 7절 | `prompt.py:45-51`, `R/it/agent-worker/worker/hitl.py:18-38` |
| **너무 오래 걸린다 · 죽었다** | 1,800초 제한. 워커가 죽은 작업은 `draft_status = FAILED`, 사람이 닫는다 | `settings.py` `run_timeout_s`, `instances.py` `close_agent_task` |

### 5.2.4 구조화 출력과 실행 기록

- **구조화 출력**: 작업에는 **폼 필드(출력 계약)**가 붙는다. 에이전트는 JSON 객체 하나를 `output/result.json`에 쓴다(길면 반드시 파일로). 서버가 폼 필드와 맞는지 검사하고, 틀리면 같은 세션에 「방금 제출한 결과가 출력 형식 검사에서 거절됐습니다: …」로 고치게 한다(`prompt.py` `format_correction`, 결과 읽기 `it/agent-worker/worker/outcome.py` `Outcome.contract_met` · `missing_fields`, 서버 쪽 결과 계약 검사 `it/process/procsvc/instances.py` `check_result`). 모델 API의 스키마 강제 기능이 아니라 **약속한 모양의 JSON 파일**이다(2~4일차 사실표 4절과 같음).
- 실제 출력 한 건 [기록] 기록 ② 작업 폴더의 `output/result.json`(21,698바이트)의 최상위 키: `cause`(`cause:cooler-fin-fouling`) · `failure_mode`(`fm:cooler-performance-loss`) · `guide_card`(진단 가이드 카드 전체) · `decision{recommended, explanation, order}` · `decision_id`(`DEC-1010-056-0972`).
- **실행 기록**: 도구 호출의 시작 · 끝이 `events` 표에 행으로 남는다(`tool_usage_started` · `tool_usage_finished`, 말 · 파일 쓰기 · 스킬 사용도 `task_working`). 행마다 입력 · 출력(4,000자까지, 넘으면 원문을 따로 보관), 시각, 걸린 시간이 있다(`R/it/agent-worker/worker/events.py:20-26`, `PREVIEW_MAX = 4_000`). 포털은 서버 · 도구별로 모아 보여 준다: [기록] `curl -s "localhost:8080/api/mcp/calls?limit=5"` → 가장 최근 호출 `hyd-dmn` / `submit_decision`, 처리 건 `anomaly_response.80b346e3-…`, 작업 「우선순위 · 카드 작성」, 18:05:24, 367 ms, 입력 `{"asset": "HYD-01", "cause": "cause:pump-seal-wear", "pattern": "PUMP_LEAKAGE", "incident": "INC-1010-15-532f", "failure_mode": "fm:volumetric-loss", …}`, 출력 `{"result": "ok", "document": {"id": "DEC-1010-082-448a", "status": "SUBMITTED", "recommended": "skill:switch-standby-pump", …`. 이 호출의 식별자는 옛 전체판 시드의 것이다 — 지금 그래프(시드 한 벌 + 수업 문서 적재)에서는 `cause:pump-shaft-seal-wear` 펌프 축 씰 마모 · `fm:pump-volumetric-efficiency-loss` 주 펌프 체적 효율 저하이고, 예비 펌프 전환은 조치 방법(Skill)이 아니라 원자 조치 `action:select-pump`(운전 펌프 전환)뿐이다(적재분 덤프 `그래프_이름표.md`). 교재 예로는 쿨러 식별자를 쓴다.
- 처리 건 목록 머리말로 한눈에 보는 요약: 「단계 7 · AI 도구 호출 10 · 사람 1 · AI 일꾼 1 · 시스템 4」(기록 ①).
- **근거 제시**: (1) 카드마다 근거 노드 id · 문서 절을 인용한다(고정 규칙 `work_rules.py` `HYD_PLANT.citation` 「모든 판단에 온톨로지 노드 id(cause:…, fm:…, skill:…, rule:…, ms:…)를 인용합니다.」). (2) 「에이전트에게 질문」은 에이전트가 근거로 적은 질의가 **실제 도구 호출 기록에 있는지 서버가 대조**하고, 없으면 「답할 수 없음 + 이유」로 보인다(`it/process/procsvc/ask.py` `verdict`). 화면(`it/portal/www/ask.js` `resultHtml`)은 답 아래 「조회 기록 N개 확인」 · 「성공한 조회 N건」, 근거마다 「실행 기록에서 확인됨」 / 「실행 기록에 없음」을 보이고, 답의 수치 · ID 표기를 조회 결과 원문과 대조한 안내(`ask.py` `result_comparison` — 「수치·ID의 표기만 대조했습니다. 답의 의미와 계산이 맞다는 보증은 아닙니다」 또는 찾지 못한 값 목록)를 붙인다. 근거가 기록에 없으면 「에이전트가 낸 답 (근거 확인 안 됨)」을 접어 보인다.

**SKILL.md 원문 한 건** — 실제로 에이전트가 읽은 파일 [기록] 그 작업 폴더의 `.claude/skills/cooling-emergency-response/SKILL.md`:

```markdown
---
name: cooling-emergency-response
description: 쿨러 과열 경보 — 원인 진단 · 냉각 조치 카드 (시나리오 A)
---

# 냉각 긴급 대응 (시나리오 A)

쿨러 과열 경보(COOLER_DEGRADATION) 한 건에서 원인을 진단하고, 냉각 조치 후보를 비교해 추천 카드 한 장과 지는 대안을 올린다.
승인 전에는 조회 · 계산만 한다. 설비 명령은 사람 승인 뒤 시스템이 낸다.

## 절차
1. `context/task.json` 의 입력에서 asset · pattern · alert.alertId · incident 를 읽는다.
2. hyd-dmn `diagnose(asset, pattern, alert_id)` — 원인 1순위(top cause) · 고장 유형 · 가이드 카드(권장 조치)를 얻는다.
   withheld 이면 원인을 지어내지 말고 보류(__deferred__)로 낸다.
3. 필요하면 enterprise 로 납기 오더 · 출하 대기 로트를 확인한다(조회만).
4. hyd-dmn `evaluate_cards(asset, pattern, cause, failure_mode)` — 후보 · 규정(제외 · 감점 · 경고) · 예측 유온 · 성과 지표 득실 · 순위를 본다.
   추천 안이 왜 이기고 다른 안이 어디서 지는지(예측 유온 · 생산 손실 · 규정) 한 줄씩 정리한다.
5. hyd-dmn `submit_decision(asset, pattern, cause, failure_mode, incident, alert_id, process_scope)` — 돌려준 id 가 decision_id 다.

## 결과
cause · failure_mode · guide_card(diagnose 결과의 가이드 카드) · decision{recommended, explanation, order} · decision_id.
explanation 은 한국어 두세 문장: 원인, 추천 안, 지는 안의 이유.
```

- 같은 스킬을 쓰는 에이전트 정의: `agent:cooling`「냉각 긴급 대응 에이전트」, 목표 「쿨러 과열 경보의 원인을 진단하고, 냉각 조치 후보를 규정 · 회사 목표로 비교해 추천 카드 한 장과 지는 대안을 올린다」, 도구 `neo4j · enterprise · hyd-dmn`, 스킬 `cooling-emergency-response`. [기록] `curl -s localhost:8080/api/agents`. 같은 SKILL.md 형식이 B(`pm-schedule-planning`, 도구 `neo4j · hyd-dmn · enterprise-maint`)와 C(`spare-purchase-planning`, `neo4j · hyd-dmn · enterprise-purchase`)에도 쓰인다 — **도구 구성과 절차만 다르고 틀은 같다**는 재사용의 실제 예.
- 학생용 스킬 출발본 · 완성 예는 시스템 저장소에 없다(옛 `students/_template/agent/SKILL.md` · `example_meeting/agent/SKILL.md`(`qbr-prep`)는 git 이력 `9af500d9^:students/`에 있다). 포털에서 쓰는 형식의 기준은 위 기준 스킬 셋이다. 머리말의 `name`은 스킬 이름과 같아야 저장된다(오류 「문서 머리의 name(…)이 스킬 폴더 이름(…)과 다릅니다 — 같게 맞추세요」, `it/process/procsvc/agent_authoring.py`).
- 포털에서 스킬 만들기: `POST /api/skills`(`agent_authoring_api.py`), 본문 최대 60,000자(`agent_authoring.py` `LIMITS`). 스킬은 에이전트에 붙여야 실행에 들어간다 — 「붙이지 않은 스킬은 어떤 실행에도 들어가지 않습니다」(`it/portal/www/agents.js`). 시험 실행(`it/agent/agentsvc/trial.py`)은 스킬 본문에서 도구 이름을 등장 순서대로 읽어 보조 조회로 부르므로 스킬을 붙이기 전 · 후로 도구 호출이 달라진다(시험 `workspace/개발/tests/test_trial.py`의 `test_스킬_절차는_본문의_도구_언급_순서이고_코드_블록은_차례로_짝짓는다`).

### 6.2.3 Skill은 수행 방법, MCP는 연결된 실행 도구

- 실제 기록 5.1.2 ②에서 그대로 보인다: 스킬(`SKILL.md`)이 「`diagnose` → `evaluate_cards` → `submit_decision`을 이 순서로 부르라」고 **방법**을 말하고, 그 도구들은 hyd-dmn MCP 서버가 **실행**한다. 스킬만 있고 도구가 없으면 방법만 알고 못 한다. 도구만 있고 스킬이 없으면 무엇을 어떤 순서로 부를지 에이전트가 처음부터 정한다.
- 시험 실행 화면이 둘의 효과를 따로 보여 준다: **스킬 차이는 도구 호출 순서 · 인용의 차이**로, **도구(서버) 구성 차이는 사실을 받느냐(예: enterprise가 없으면 업무 DB 값이 「받지 못함」)의 차이**로 나타난다. 같은 입력 스냅숏 + 같은 설정이면 결과 지문이 같다([기록] git 이력 `39f447ce:문서/시스템/검증_기록/2026-10-08/u10-agent-compare.md` 1~3절, 시험 `workspace/개발/tests/test_trial.py` · `test_agent_trials.py`). 주의: 이 시험 실행은 워커(Claude Code)를 거치지 않고 agent 서비스의 읽기 전용 판단(`POST /api/agent/trial`, `agentsvc/trial.py` — 진단 → 스킬이 부르는 보조 도구 → 사실 수집 → `cards.evaluate`)으로 판단 단계만 돌리므로 실제 워커와 일부 다르다(`procsvc/agent_trials.py` 머리말).

### 6.3.1 읽기 / 쓰기 권한 — 경계가 세 겹이다

CLI에 켜는 내장 도구 자체가 `Read · Write · Edit`(+ 배정 스킬이 있으면 `Skill`)뿐이다. 학생이 등록한 서버는 `mcp__<서버>__*`가 아니라 **연결 검사에서 읽기로 찍힌 도구 이름만** 허용 목록에 더하고, 쓰기 · 미표시 도구는 `--disallowedTools`로 막는다 | `R/it/agent-worker/worker/settings.py:20-27,30-56`, `cli_sandbox.py:47-50`, `runner.py:258-261`. 효과: 에이전트는 막힌 도구를 **부를 수도 없다**(`settings.py:53-56` 주석 "so the agent cannot even ask for them") |

- hyd-dmn의 쓰기는 **`submit_decision` · `submit_purchase` 둘**이고 **설비를 건드리지 않는다.** 서버 설명: 「submit_decision·submit_purchase는 판단 카드를 쓰며(process /api/decisions), 설비 명령은 어디서도 나가지 않는다.」(`dmn_mcp/server.py` FastMCP `instructions`) 쓰기에도 층이 있다 — ① 카드 제출(`submit_decision` · 구매는 `submit_purchase`: 사람이 고를 안을 기록, 에이전트가 함) ② 설비 명령(process의 승인 전이만 만듦) ③ 업무 쓰기 · 메일(승인 뒤 시스템 단계가 부름; 메일 도구 `send_mail`은 에이전트 서버 목록에 없고 process의 `EFFECT_MCP_SERVERS`로만 부름 — `effects_mcp/server.py` 머리말).

### 6.3.2 파일 접근 범위

- 에이전트는 **실행마다 별도 작업 폴더** 하나에서 일한다(`<작업 공간>/<tenant>/<작업 id>/`). 규칙: 「작업 디렉터리 밖의 파일을 읽거나 수정하지 마세요. 홈 디렉터리(`~/.claude` 등)를 찾아보지 마세요.」(고정 규칙 `work_rules.py` 공통부 `_WORKSPACE`). 작업 지시에도 「이 디렉터리 밖에는 쓰지 마세요」(`prompt.py` `build` 「작업 공간」 절).
- **정직한 한계**: 폴더 분리는 「조직 경계이지 OS 접근 통제 경계가 아니다」(`R/it/agent-worker/worker/workspace.py:1-6` 머리말: "Different directories are an organization boundary, not an OS access-control boundary"). 허용 목록은 `Read · Write · Edit · Skill`과 MCP 도구뿐이고 셸 도구 `Bash` · `PowerShell`은 늘 막지만(6.3.1 — `settings.py` `DEFAULT_ALLOWED_TOOLS` · `BLOCKED_SHELL_TOOLS`), `Read`가 작업 폴더 밖 경로를 못 읽게 하는 OS 장치는 아니다. 「워커 `saved_path`가 `tool-results` 이름 폴더 아래면 어느 파일이든 읽는 잔여 위험」이라는 옛 현황 기록(git 이력 `d0eb7dc:docs/handoff/NOW.md:139` F8)과 달리, 지금 워커는 그 CLI 메시지가 가리킨 `tool-results` 안 경로만 읽는다(`R/it/agent-worker/worker/payloads.py:19-20`). 6일차에서 「파일 접근 범위를 좁히는 설정이 있다」까지는 맞고 「완전히 격리된다」고 쓰면 안 된다.
- 결과 파일 경로는 고정 상대 경로 `output/result.json`뿐이다(`workspace.py` `RESULT_FILE`).

| 장치 | 내용 | 근거 · 실제 값 |

CLI는 자기 로그인이 없고 실행마다 받은 수업 관문 토큰으로만 모델을 부르므로 개인 CLI 키(`ANTHROPIC_API_KEY` · `CLAUDE_CODE_OAUTH_TOKEN` …)도 같이 지운다 | `R/it/agent-worker/worker/env_guard.py` 머리말 · `DEFAULT_BLOCK` · `BLOCK_SUFFIXES` · `BLOCK_PREFIXES`, `main.py`의 `env_guard.scrub`. 이유(주석): CLI의 셸이 읽으면 MCP 경계를 우회하게 되므로 |
| **실행 뒤 정리** | 실행이 끝나면 작업 폴더 `.mcp.json`의 서버 `headers`(토큰) · `env`를 지운다. 읽을 수 없는 설정 파일은 통째로 지운다 | `bridge.py` `cleanup` |
| **로그 가림** | 도구 입력 · 결과의 비밀값은 가려서 돌려준다 | `mcp_check.mask_value`, `mcp_secrets.redact` |

### 6.3.4 외부 응답의 불완전성 · 실패 · 타임아웃 · 근거 표시

- **외부 응답은 불완전할 수 있다 — 실제 사례**: `evaluate_cards`의 결과가 128,466자라 CLI가 본문을 에이전트에게 주지 않고 임시 파일로 뺐다(5.1.2). 에이전트는 이를 알아차리고 「필요한 항목만 좁혀 다시 뽑겠습니다」라고 말했지만 기록 ①에서 그다음 호출은 판단 제출이라 다시 뽑기에 성공했는지는 기록으로 확인되지 않는다. 기록 ②는 최종 메시지에 「조치 후보 비교의 상세 출력은 작업 디렉터리 밖에 저장돼 열지 않았고」라고 **못 읽은 범위를 밝혔다**. 포털 처리 기록은 이를 「결과 잘림」 칩으로 보인다(처리 기록 화면 글 [기록] 「대안 평가 … 결과 잘림 807 ms」). 포털 「도구 써 보기」도 결과를 `MAX_RESULT_CHARS = 20,000`자로 자르고 `truncated: true`와 원래 크기를 알린다(`mcp_check.py:56, 307-`).
- **실패의 분류**: 연결 검사 · 호출 실패는 사람이 읽는 한국어 사유 + 분류 `error_kind`(`config · refused · unreachable · timeout · auth · not_mcp · protocol · server · closed · too_large · busy`, 비밀 값 문제는 `secret`)로 돌려준다. 명령형 설정은 형식 검사에서 `STDIO_REFUSED`로 거절한다(실행 분류 `exec`는 없다). 「폴백·빈 성공은 없다: 도구 목록을 받지 못하면 status 는 'failed' 다」(`mcp_check.py` 머리말 · `CheckError`).
- **타임아웃**: 포털 도구 목록 기본 4초(0.5~6), 호출 기본 15초(0.5~25), 동시 3연결(`mcp_api.py:25-27`). 시계열 · 업무 DB 쿼리 5초(`sql_read`). 에이전트 한 번 실행 1,800초.
- **근거 표시**: 호출마다 입력 · 출력 · 시각 · 걸린 시간이 남는다(5.2.4). 모든 hyd-dmn 판단 결과에 값의 출처가 붙는다(`provenance`: 원천 · 표 · 열 · 조건 · 실행 SQL · 관측 시각 — 2~4일차 사실표 5절).
- **학생 등록 도구의 제약(실라버스가 말한 「실제 제약」)**: **지금 수업 단계에서는 학생 서버 등록 자체가 막혀 있다.** 서버 등록 · 고치기 · 연결 검사 · 「읽기로 확인」 · 비밀값 쓰기 · 지우기(`POST /api/mcp/servers` · `PUT /api/mcp/servers/{이름}` · `POST /api/mcp/check` · `POST /api/mcp/servers/{이름}/read-confirm` · `PUT`/`DELETE /api/mcp/secrets/{키}`)는 거절되고 「외부 도구 서버 등록 · 비밀값 · 쓰기 도구를 읽기로 확인하기는 PBL 단계에서 엽니다. 수업에서는 준비된 도구 서버를 그대로 씁니다.」가 돌아온다(`R/it/process/procsvc/course_policy.py:301-312,448-454`). PBL 단계는 강사 서명 단계 선언(`course_phase.json`)으로만 열리고 선언이 없으면 수업 단계다(`course_policy.py:9-12,101-105` — 지금 저장소에 선언 파일이 없다). 아래는 PBL 단계에서 등록한 서버의 규칙이다. 학생이 등록한 서버는 ① 형식 검사 ② **실제 연결 검사** 통과 ③ 검사 때 찍힌 설정 지문이 지금 설정과 같을 때만 에이전트에 붙고 ④ 그 안에서도 **읽기로 표시된 도구만** 허용된다(`R/it/process/procsvc/mcp_registry.py:1-30`). 설정을 고치면 도장이 사라져 다시 검사해야 한다. 읽기 표시가 아예 없는 서버(공개 구글 MCP 서버 등)는 강사가 도구별로 「읽기로 확인」할 수 있되(`confirmable`), 서버가 쓰기로 표시했거나 이름이 쓰기면 확인할 수 없다(`mcp_check.py:296-303`). 기준 서버 다섯은 수정 · 삭제 거절(`mcp_registry.py` `BASE_SERVERS`).
- 포털은 명령형(stdio) 등록을 PBL 단계에서도 받지 않는다 — process 안에서 남의 명령을 띄우지 않는다. 명령으로 띄우는 서버는 HTTP로 띄워 그 주소를 등록한다(`mcp_check.py` `STDIO_REFUSED`, `mcp_registry.py` 머리말 「포털에 등록하는 서버는 HTTP 주소 하나다」).

### 7.1.2 사람이 개입하는 세 가지 지점

| 지점 | 언제 | 누가 · 어떻게 | 기록 · 상태 |
|---|---|---|---|
| ① **승인 단계** (사람 작업) | 에이전트가 카드를 낸 뒤, 조치 실행 전 | 지정 역할의 담당자가 포털에서 승인 또는 거절 | 흐름 분기 「승인?」(승인 / 거절). 끝 이벤트 이름(냉각 긴급 대응): `E_end` 「끝」 · `E_rejected` 「거절 종결」 · `E_notice` 「알림」 · `E_kind` 「실행하지 않음」(`course_flows.json:4`, 1일차 사실표 5.6) |
| ② **에이전트의 질문** (정보가 부족할 때) | 필수 업무 정보가 없고 연결된 조회 도구로도 확인할 수 없을 때 | 에이전트가 마지막 메시지에 `{"__human_input__":{"question":"…","options":[…]}}` 하나만 내고 멈춤 → 포털 **내 할일**에 「에이전트의 질문」 카드 → 사람이 답(`POST /api/todolist/{id}/human-response`) → **같은 세션으로 이어서** 재개 | 작업 상태 `draft_status = HUMAN_ASKED` → 답 뒤 `FB_REQUESTED` → 재실행. 이벤트 `human_asked` → `human_response`. 질문 1~4000자, 선택지 최대 8개(`hitl.py:18-38`). 답은 한 번만(「이미 답변한 질문입니다」), 같은 질문 중복 억제(`hitl.fingerprint`) |
| ③ **멈춘 단계 닫기** (`close_agent_task`) | 진행 중인 처리 건에서 에이전트 단계가 실행 실패·실행 취소·보류·한도 초과 등으로 멈췄거나 시스템 단계의 재시도가 한도를 넘겼을 때 | 담당자가 닫는 사유를 적는다. 사람 단계, 진행 중인 단계, 질문에 대한 답을 기다리는 단계는 닫을 수 없다. 열린 사건이 있어도 멈춘 단계를 닫을 수 있다 | 해당 단계는 `CANCELLED`, `task_cancelled` 이벤트에 닫은 사람과 사유가 남는다. 다른 열린 일이나 이미 도달해 예약 시각을 기다리는 일이 없으면 처리 건은 기술 종료 `closed-by-human`(「사람이 닫음」)이 되고, 그때까지 열려 있던 사건은 책임자 확인으로 닫힌다. 근거: `it/process/procsvc/instances.py`의 `InstanceRuntime.stuck`, `close_agent_task`, `_settle_incident` 및 `workspace/개발/tests/test_instances.py`의 `test_실패한_AI_단계의_처리_건은_멈춤으로_보이고_사람이_닫으면_사건도_책임자_확인으로_닫힌다`. |

- **질문의 실제 예**: [기록] 에이전트가 「조회할 대상 설비를 선택해 주세요. HYD-02와 HYD-03 중 …」 하고 멈췄고(9.6초), 사람이 답 「HYD-02」를 넣자 16.1초 뒤 **같은 세션**으로 재개해 `describe_schema` → `query`를 부르고 `selected_asset: HYD-02`를 냈다. (실행 환경: 호스트 Claude Code 워커 1개, `AGENT_BRIDGE=off`.) 출처는 git 이력 `d0eb7dc:docs/sessions/14-가드레일과-사람에게-묻기.md`이고, 증거 폴더(로컬 실행 기록)는 남아 있지 않다.
- **CLI마다 다르다**: 같은 질문 정의를 Codex로 돌리니 질문 없이 바로 완료한 관찰이 있다(같은 문서) — 질문 여부는 모델 · CLI의 재량이므로 「항상 묻는다」고 쓰면 안 된다.
- **질문은 권한 우회 수단이 아니다**: 프롬프트가 「도구 접근 거절이나 설비 조치 승인 우회에는 쓰지 마세요. 답변은 실행 권한을 바꾸지 않습니다」(`prompt.py` `build` 「담당자에게 업무 정보 질문」 절). 사람의 답이 근거 충족이나 설비 승인으로 간주되지도 않는다(고정 규칙 `work_rules.py` `HYD_PLANT.reassessment` 「다시 평가 요청에서는 원천을 새로 조회하며 사람의 요청을 근거 충족이나 설비 승인으로 간주하지 않습니다.」).

### 7.1.3 「AI의 자기 검토」와 「실제 사람 승인 절차」는 다르다

| | AI · 서버의 검토 | 사람의 승인 |
|---|---|---|
| 예 | **가드레일**: 후보 카드마다 후보 선택 규칙 인용(`Rule -OUTPUTS-> Skill`)이 있는가와 원문 참고 절차(실행 카드로 제출할 수 없음)가 아닌가, **권하는 카드**가 규정(EXCLUDE 규칙)에 걸리지 않고 승인 역할(`Skill -APPROVED_BY-> Role`) · SOP 단계(`Skill -HAS_STEP-> Step`)를 갖는가를 검사(승인 역할 · 단계는 권하는 카드만 본다). 어기면 상태 `REJECTED_BY_GUARDRAIL`로 **제출되지 않음** | 지정 역할의 사람이 포털에서 승인 |
| 근거 | `R/it/agent/agentsvc/guardrail.py` `check_cards`, `decide.py`의 `decide()`(위반이면 `REJECTED_BY_GUARDRAIL`) — 워커가 부르는 `submit_decision`도 같은 `decide()`를 거치므로 가드레일이 적용된다(`dmn_mcp/tools.py` `DmnTools.submit_decision` → `decidelib.decide`). 가이드 카드 가드레일(`guardrail.py` `check`, `FORBIDDEN_KEYS`)은 「에이전트에게 명령 권한이 없다」: 카드에 `writes · cmdId · expiresAt · mqtt · topic` 필드가 있으면 거부 | 서버가 `approved_by`를 기록하고 그 뒤에야 명령이 만들어짐 |
| 결과 | 검사 통과 = 사람에게 **올려도 된다** | 권한 있는 사람이 경로에서 결정하며, 실행 단계로 넘길 때에도 현재 조건이 맞아야 한다 |
| 학생용 문장 | 통과한 카드도 **승인된 것이 아니다.** 승인 전 상태는 `AWAITING_APPROVAL` | — |

- 같은 구분이 데이터에도 남는다: 승인 필드(`approval` · `approved_by` · `approved_role`)는 서버가 승인 경로에서만 넣고 에이전트의 출력에서는 낼 수 없다.
- 통합반 온라인 74행 「서로 다른 에이전트가 제안과 검토를 나눠 수행하기」에는 학생용 시작본이 있다. 통합반 실습3 「제안과검토」의 `코드/writer.md`는 작성 역할, `reviewer.md`는 원문·초안 대조와 누락·모순·수정 제안, `review.md`는 빈 확인 기록이다. `source/사람/승인.json`에는 사람이 결정한 별도의 입력이 있다. R07의 결정은 거절이며 사유도 기록돼 있다. 학생이 채운 검토 의견이나 자동 승인을 뜻하지 않는다. 포털의 사람 승인 부품은 `human:approve`이며 결정과 사유를 승인 경로에서 받는다.

### 7.3.2 「모호한 변경이 기존 출력이나 승인 규칙을 흔든다」의 실제 근거와 한계

- **실제로 있는 것**: 기존 기능을 지키는 장치가 구현되어 있다 — 흐름 등록 사전 검사는 승인 없이 효과 부품으로 가는 경로, 반려 경로가 효과 부품에 닿거나 결과 보고(반려) 없이 끝나는 경로를 찾아 등록을 거절한다(`it/process/procsvc/bpmn_import.py`의 `_reached_past_rejection`을 쓰는 검사, 문구 「…의 반려 경로가 결과 보고(반려) 없이 끝납니다 — 경로: …」). 승인 단계의 행동은 `workspace/개발/tests/test_instances.py`의 거절 · 승인 역할 · 승인 지연 시험이, 고정 규칙의 업무부 선택은 `test_work_rules.py`가 지킨다. 옛 승인 카드 고정본과 규칙 글 바이트 고정 시험은 저장소에 없다. 이 검사들은 **바뀐 흐름이 승인 규칙을 깨뜨리는 것을 막는다.** 반려 경로 두 경우만 따로 잰 시험은 지금 시험 폴더에서 찾지 못했다.
- **저장소에서 「모호한 변경이 실제로 출력 계약을 깨뜨린 사례」는 찾지 못했다.** 사전에 확인한 실패 재현 입력은 없다(7.2 표 행 73). 실라버스도 「실패가 항상 발생한다고 단정하지 않는다」고 쓴다. 교재에서는 **위험의 구조**(출력 계약 · 승인 조건 · 기존 일반 요청이 바뀔 수 있는 자리)만 설명하고 실제 실패 사례를 지어내지 않는다.
- **「긴급 정비 조건」**: 실라버스 7일차 실습이 다루는 소재다. HYD의 정기 점검(B)에는 「야간 정비 시간 · 허용 오차 · 한계까지(h)」 같은 **시간 조건**이 있고(`pm_status` 도구의 설명: 「기한까지(h) · 허용 한계까지(h) · 예정된 정비 시간(야간 · 주말 · 월간)까지(h)와 한계 안 여부」), 구매(C)에는 「300만 원 초과는 전결 기준 초과 ‘표시’일 뿐 추가 승인이 아니다」라는 **승인 규칙**이 SKILL.md에 적혀 있다(`spare-purchase-planning`). 둘 다 「조건이 바뀌면 승인 규칙이 흔들릴 수 있는 자리」의 실제 예로 쓸 수 있다. 「긴급 정비」라는 이름의 기존 기능은 없다.
- **실전반 5회차 · 통합반 7회차 랩의 긴급 표시 조건**: `COOLER_DEGRADATION`에서 판단 때 유효한 TS1 120초 평균이 60 ℃ 이상이면 긴급이다. `freshness.ok`와 `coverage.covered`를 함께 확인하고, 유효하지 않으면 `urgent=null`과 보류 사유를 남긴다. FUXA 운전 화면의 유온 경고는 TS1 현재값에 적용하고 하한은 55 ℃다(1일차 사실표 3.8). 현재값만으로는 120초 평균을 알 수 없으므로 운전 화면의 경고와 랩의 긴급 표시는 따로 판정한다(사실표 「같은 말 · 같은 값」의 대표 값 행).

### 8.1.3 모델 출력의 표현 차이와 필수 계약 위반을 구별하는 장치

| 장치 | 무엇을 보고 무엇을 무시하나 | 근거 |
|---|---|---|
| **출력 계약 검사** | 에이전트가 쓴 문장은 달라도 된다. 폼 필드가 모두 있는지 · 형식이 맞는지만 본다(`contract_met`, `missing_fields`, `mismatch_reason`). 어긋나면 같은 세션에서 최대 2회 교정 | `it/agent-worker/worker/outcome.py` `Outcome`, 서버 쪽 결과 계약 검사 `it/process/procsvc/instances.py` `check_result`, 교정 지시 `prompt.py` `format_correction` |
