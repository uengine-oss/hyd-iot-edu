# 5일차 — 에이전트: 질문하는 AI와 일하는 AI

## 5.1 이론 1 「질문하는 AI와 일하는 AI의 차이」(40분)

### 5.1.1 LLM · RAG · Agent의 구분

| 항목 | (가) 표준 개념 [일반] | (나) HYD의 대응물 | (다) 교재에 쓸 실제 예 |
|---|---|---|---|
| **LLM** (Large Language Model, 대규모 언어 모델) | 주어진 글을 이어 새 글을 만들어 내는 모델. 입력 한 번에 응답 한 번. 모델이 학습한 내용 밖의 최신 값을 스스로 알지 못한다 | 워커가 부르는 모델은 Claude Code CLI가 쓰는 모델이다. 기본 `CLI_MODEL=opus`(`R/scripts/run_worker_host.sh:18`). [기록] 실행 로그의 모델 표기 `claude-opus-5-5`(기록 ② 작업 폴더의 `…events.jsonl` 3번째 줄 `run_start`) | LLM만 있으면 「HYD-01 유온이 지금 몇 도인가」에 답할 수 없다. 값은 시계열 DB에 있고 모델 안에 없다 |
| **RAG** (Retrieval-Augmented Generation, 검색 증강 생성) | 질문과 가까운 문서 조각을 먼저 찾아 모델에게 읽혀 근거 있는 답을 만든다. 답이 문서에서 나오고, 도구를 골라 부르거나 일을 끝까지 수행하지는 않는다 | **HYD 에이전트는 RAG를 쓰지 않는다.** 임베딩 · 벡터 저장소 코드가 없다(`R/it`, `R/common`, `R/scripts`에서 `embedding · pgvector · faiss · chroma` 검색 → 없음). 지식은 그래프 질의(Cypher), 값은 SQL로 읽는다. 4일차 덱 25장이 「검색해 참고하는 방식(RAG)과 구조화해 등록하는 방식」을 이미 비교했다(`R/production/decks/integrated/day04/통합반_04일차.md` SLIDE 25) | RAG와의 대비 예: 승인 카드의 「출처 HM-8.5 즉시 완화 조치」는 문서 조각을 검색한 것이 아니라, 인제스천으로 등록된 규칙에서 문서 절로 이어진 **관계를 따라간 결과**다 |
| **Agent** (에이전트) | 목표를 받고 도구를 골라 부르며, 결과를 보고 다음 행동을 정해 목표를 이룰 때까지 반복하는 시스템(LLM + 도구 + 실행 고리). 단순 답변이 아니라 산출물을 만든다 | 워커가 CLI에 **프롬프트 한 개와 작업 폴더**를 준다. 프롬프트는 업무 · 지시사항 · 입력 데이터 · 작업 공간 · 결과 제출 형식 순이다(`R/it/agent-worker/worker/prompt.py:13-55`). 도구는 MCP 서버로 붙는다(6일차) | 5.1.2의 실제 실행 기록 |

- 「LLM · RAG · Agent」를 가르는 기준(교재 표현 후보): **LLM = 말하기, RAG = 찾아서 말하기, Agent = 찾고 계산하고 제출하기.** HYD 에이전트가 한 마지막 행동은 말이 아니라 **조치 카드 묶음을 process에 제출**한 것이다(`submit_decision`, 판단 id `DEC-1010-056-0972`).
- 에이전트의 일은 「판단 · 제안」까지다. 설비 명령 · 작업지시 · 메일은 에이전트가 하지 않고 사람 승인 뒤 시스템 단계가 한다(1일차 사실표 4.4, 이 문서 7.1절).

### 5.2.2 「지식」과 「현재값」을 혼동하지 않는 방법

- 2~4일차 사실표 5절(「지식과 값」)의 구분을 따른다. 에이전트 쪽의 실제 장치:
  - 정적 지식(그래프)은 「어느 센서를 어떤 조건으로 보라」만 갖고, **값은 조회 시점에 시계열 DB · 업무 DB에서 가져온다**. `gather_facts` 도구가 이 일을 한다: 「규칙이 검사할 사실을 온톨로지가 정한 출처(시계열 · PLC 상태 · MES 등)에서 실제로 가져온다. 값마다 어디서 어떻게 얻었는지 provenance 를 함께 준다.」(`dmn_mcp/server.py:60-63`)
  - 작업 폴더 규칙: 「연결된 MCP 도구가 있으면 추측 대신 도구로 확인하세요. 지식은 온톨로지(Neo4j MCP), 현황 · 업무 값은 업무 DB(enterprise MCP), 규칙 판정은 DMN 도구(hyd-dmn MCP)의 결정론적 결과를 씁니다.」(작업 폴더 `CLAUDE.md`, 원문은 `R/tests/fixtures/constitution_hyd_2fbefff.md`와 바이트 단위로 같음 — `R/it/process/procsvc/work_rules.py:15-17`)
  - 값에는 신선도가 붙는다: `freshness: {"ok": true, "age_s": 0.9, "max_age_s": 60, …}` — 최신 TS1이 60초보다 묵었으면 `ok: false`가 되어 판단이 보류된다(5.2.3).
  - 학생이 보는 곳: 처리 기록의 도구 호출 줄(물음 → 받음). 값마다 「물음(입력)」과 「받은 원문」이 나란히 보인다(`R/it/portal/www/caseRecord.js:262-265`).

### 5.2.4 구조화 출력과 실행 기록

- **구조화 출력**: 작업에는 **폼 필드(출력 계약)**가 붙는다. 에이전트는 JSON 객체 하나를 `output/result.json`에 쓴다(길면 반드시 파일로). 서버가 폼 필드와 맞는지 검사하고, 틀리면 같은 세션에 「방금 제출한 결과가 출력 형식 검사에서 거절됐습니다: …」로 고치게 한다(`prompt.py:71-78`, `R/it/agent-worker/worker/outcome.py:41-62`). 모델 API의 스키마 강제 기능이 아니라 **약속한 모양의 JSON 파일**이다(2~4일차 사실표 4절과 같음).
- 실제 출력 한 건 [기록] 그 작업 폴더의 `output/result.json`(21,698바이트)의 최상위 키: `cause`(`cause:cooler-fin-fouling`) · `failure_mode`(`fm:cooler-performance-loss`) · `guide_card`(진단 가이드 카드 전체) · `decision{recommended, explanation, order}` · `decision_id`(`DEC-1010-056-0972`).
- **실행 기록**: 도구 호출의 시작 · 끝이 `events` 표에 행으로 남는다(`tool_usage_started` · `tool_usage_finished`, 말 · 파일 쓰기 · 스킬 사용도 `task_working`). 행마다 입력 · 출력(4,000자까지, 넘으면 원문을 따로 보관), 시각, 걸린 시간이 있다(`R/it/agent-worker/worker/events.py:20-26`, `PREVIEW_MAX = 4_000`). 포털은 서버 · 도구별로 모아 보여 준다: [실측] `curl -s "localhost:8080/api/mcp/calls?limit=5"` → 가장 최근 호출 `hyd-dmn` / `submit_decision`, 처리 건 `anomaly_response.80b346e3-…`, 작업 「우선순위 · 카드 작성」, 2026-10-10 18:05:24, 367 ms, 입력 `{"asset": "HYD-01", "cause": "cause:pump-seal-wear", "pattern": "PUMP_LEAKAGE", "incident": "INC-1010-15-532f", "failure_mode": "fm:volumetric-loss", …}`, 출력 `{"result": "ok", "document": {"id": "DEC-1010-082-448a", "status": "SUBMITTED", "recommended": "skill:switch-standby-pump", …`.
- 처리 건 목록 머리말로 한눈에 보는 요약: 「단계 7 · AI 도구 호출 10 · 사람 1 · AI 일꾼 1 · 시스템 4」(기록 ①).
- **근거 제시**: (1) 카드마다 근거 노드 id · 문서 절을 인용한다(작업 폴더 규칙 「모든 판단에 온톨로지 노드 id(cause:…, fm:…, skill:…, rule:…, ms:…)를 인용합니다」). (2) 「에이전트에게 질문」은 에이전트가 근거로 적은 질의가 **실제 도구 호출 기록에 있는지 서버가 대조**하고, 없으면 「답할 수 없음 + 이유」로 보인다(`ask.py:21-24`, 화면 `ask.js:101-107` 「근거 N개 확인」 · 「에이전트가 낸 답 (근거 확인 안 됨)」).

**SKILL.md 원문 한 건** — 실제로 에이전트가 읽은 파일 [기록] 그 작업 폴더의 `.claude/skills/cooling-emergency-response/SKILL.md`:

```markdown
---
name: cooling-emergency-response
description: 쿨러 과열 경보 — 원인 진단 · 냉각 조치 카드 (시나리오 A)
---

# 냉각 긴급 대응 (시나리오 A)

쿨러 과열 경보(COOLER_DEGRADATION) 한 건에서 원인을 진단하고, 냉각 조치 후보를 비교해 추천 카드 한 장과 지는 대안을 올린다.
승인 전에는 조회 · 계산만 한다. 설비 명령은 사람 승인 뒤 시스템이 낸다.

## 절차
1. `context/task.json` 의 입력에서 asset · pattern · alert.alertId · incident 를 읽는다.
2. hyd-dmn `diagnose(asset, pattern, alert_id)` — 원인 1순위(top cause) · 고장 유형 · 가이드 카드(권장 조치)를 얻는다.
   withheld 이면 원인을 지어내지 말고 보류(__deferred__)로 낸다.
3. 필요하면 enterprise 로 납기 오더 · 출하 대기 로트를 확인한다(조회만).
4. hyd-dmn `evaluate_cards(asset, pattern, cause, failure_mode)` — 후보 · 규정(제외 · 감점 · 경고) · 예측 유온 · 성과 지표 득실 · 순위를 본다.
   추천 안이 왜 이기고 다른 안이 어디서 지는지(예측 유온 · 생산 손실 · 규정) 한 줄씩 정리한다.
5. hyd-dmn `submit_decision(asset, pattern, cause, failure_mode, incident, alert_id, process_scope)` — 돌려준 id 가 decision_id 다.

## 결과
cause · failure_mode · guide_card(diagnose 결과의 가이드 카드) · decision{recommended, explanation, order} · decision_id.
explanation 은 한국어 두세 문장: 원인, 추천 안, 지는 안의 이유.
```

- 같은 스킬을 쓰는 에이전트 정의: `agent:cooling`「냉각 긴급 대응 에이전트」, 목표 「쿨러 과열 경보의 원인을 진단하고, 냉각 조치 후보를 규정 · 회사 목표로 비교해 추천 카드 한 장과 지는 대안을 올린다」, 도구 `neo4j · enterprise · hyd-dmn`, 스킬 `cooling-emergency-response`. [실측] `curl -s localhost:8080/api/agents`. 같은 SKILL.md 형식이 B(`pm-schedule-planning`, 도구 `neo4j · hyd-dmn · enterprise-maint`)와 C(`spare-purchase-planning`, `neo4j · hyd-dmn · enterprise-purchase`)에도 쓰인다 — **도구 구성과 절차만 다르고 틀은 같다**는 재사용의 실제 예.
- 학생용 출발본 [저장소] `R/students/_template/agent/SKILL.md`(「T6 출발본」: 머리말 `name` · `description`, 절차 5단계, 규칙 표, `## 결과` JSON)와 완성 예 `R/students/_template/example_meeting/agent/SKILL.md`(`qbr-prep`, 분기 리뷰 회의 준비). 머리말의 `name`은 스킬 이름과 같아야 저장된다(오류 「문서 머리의 name … 이 스킬 폴더 이름과 다릅니다」, `R/students/_template/agent/goal.md` 「막혔을 때」).
- 포털에서 스킬 만들기: `POST /api/skills`(`agent_authoring_api.py:136`), 본문 최대 60,000자. 스킬은 에이전트에 붙여야 실행에 들어간다 — 「에이전트에 붙이지 않은 스킬은 어떤 실행에도 들어가지 않습니다」(`agents.js`). 시험 실행 화면에서 스킬을 붙이기 전 · 후로 **첫 도구 호출이 달라진다**(붙인 뒤에는 절차 1단계 도구부터)는 확인이 있다(`goal.md`, 시험 `R/tests/test_agent_trial.py`).

### 6.1.2 SOP와 에이전트 실행 지침의 차이 — 「Skill」 낱말 정리

| | **SOP** (현장 작업 절차) | **에이전트의 Agent Skill** (실행 지침) | **온톨로지의 `Skill` 노드** |
|---|---|---|---|
| 읽는 이 | 현장 작업자(사람) | 에이전트(LLM) | 판단 엔진 · 포털 지식 지도 |
| 무엇을 적나 | 설비를 어떻게 만지는가: 안전 전제 · 단계 · 금지 | **에이전트가 어떤 도구를 어떤 순서로 부르고 무엇을 내는가** | 조치 방법 한 건의 식별자 · 승인 역할 · 단계 · 규칙과의 관계 |
| 형식 | 매뉴얼 문서(`HM-8` 등) → 인제스천 | `SKILL.md` 파일(머리말 + 본문) | 그래프 노드 `(:Skill {id:'skill:sop-cool-11', sopId:'SOP-COOL-11', …})` |
| 저장 위치 | 문서 원문 보관 + 그래프(`Skill` · `Step`) | `tenant_skills` 표 → 작업 폴더 `.claude/skills/` | Neo4j |
| 예 | 「SOP-COOL-11 팬 최대 운전: 1. 팬을 100 %로」 | `cooling-emergency-response` (`diagnose` → `evaluate_cards` → `submit_decision`) | `skill:sop-cool-11` |
| 서로의 관계 | SOP가 지식이 된 것이 온톨로지 `Skill` | **저장소에서 서로 가리키지 않는다**: Agent Skill 본문은 `evaluate_cards`가 돌려주는 조치 후보를 쓸 뿐, 어떤 `Skill` 노드도 직접 가리키지 않는다 | — |

- 한 문장: **SOP는 사람이 설비에 하는 일의 절차, Agent Skill은 에이전트가 정보 · 도구로 하는 일의 절차**다. 이름이 같아 보이는 온톨로지 `Skill`은 앞의 SOP를 지식 그래프에 넣은 노드다. 교재에서는 「스킬」 단독으로 쓰지 말고 **「에이전트 스킬(SKILL.md)」 / 「조치 방법(SOP)」**으로 구분해 쓴다(포털 메뉴 이름도 조치 방법: `index.html:45` `data-tab="skills"`는 「조치 방법」, 에이전트 스킬은 에이전트 화면 안에서 관리).
- 「재사용 지침과 한 번의 프롬프트」: 한 번의 프롬프트는 그 실행에만 쓰인다. 스킬은 이름이 있어 에이전트 여럿 · 실행 여러 번에 붙고 한곳에서 고치면 모두에 반영된다. [실측] `GET /api/skills` 항목의 `agents` 칸(어느 에이전트에 붙었는지)과 `steps` 칸(어느 흐름 단계에 배정됐는지)이 이를 보인다.

### 6.2.3 Skill은 수행 방법, MCP는 연결된 실행 도구

- 실제 기록 5.1.2 ②에서 그대로 보인다: 스킬(`SKILL.md`)이 「`diagnose` → `evaluate_cards` → `submit_decision`을 이 순서로 부르라」고 **방법**을 말하고, 그 도구들은 hyd-dmn MCP 서버가 **실행**한다. 스킬만 있고 도구가 없으면 방법만 알고 못 한다. 도구만 있고 스킬이 없으면 무엇을 어떤 순서로 부를지 에이전트가 처음부터 정한다.
- 시험 실행 화면(A10)이 둘의 효과를 따로 보여 준다: **스킬 차이는 도구 호출 순서 · 인용의 차이**로, **도구(서버) 구성 차이는 사실을 받느냐(예: enterprise가 없으면 업무 DB 값이 「받지 못함」)의 차이**로 나타난다. 같은 입력 스냅숏 + 같은 설정이면 결과 지문이 같다(git 이력 `39f447ce:문서/시스템/검증_기록/2026-10-08/u10-agent-compare.md` 1~3절, 시험 `R/tests/test_agent_trial.py`). 주의: 이 시험 실행은 서버 안 결정론 경로로 판단 단계만 흉내 내므로 실제 워커와 일부 다르다(같은 문서 3절 표).

### 6.3.4 외부 응답의 불완전성 · 실패 · 타임아웃 · 근거 표시

- **외부 응답은 불완전할 수 있다 — 실제 사례**: `evaluate_cards`의 결과가 128,466자라 CLI가 본문을 에이전트에게 주지 않고 임시 파일로 뺐다(5.1.2). 에이전트는 이를 알아차리고 필요한 항목만 다시 뽑았으며, 최종 메시지에 「조치 후보 비교의 상세 출력은 작업 디렉터리 밖에 저장돼 열지 않았고」라고 **못 읽은 범위를 밝혔다**. 포털 처리 기록은 이를 「결과 잘림」 칩으로 보인다(`A-7-record-text.txt:272` 「대안 평가 … 결과 잘림 807 ms」). 포털 「도구 써 보기」도 결과를 `MAX_RESULT_CHARS = 20,000`자로 자르고 `truncated: true`와 원래 크기를 알린다(`mcp_check.py:56, 307-`).
- **실패의 분류**: 연결 검사 · 호출 실패는 사람이 읽는 한국어 사유 + 분류 `error_kind`(`config · exec · refused · unreachable · timeout · auth · not_mcp · protocol · server · closed · too_large`, 비밀 값 문제는 `secret`)로 돌려준다. 「폴백 · 빈 성공은 없다: 도구 목록을 받지 못하면 status는 `failed`」(`mcp_check.py:1-25`).
- **타임아웃**: 포털 도구 목록 기본 4초(0.5~6), 호출 기본 15초(0.5~25), 동시 3연결(`mcp_api.py:25-27`). 시계열 · 업무 DB 쿼리 5초(`sql_read`). 에이전트 한 번 실행 1,800초.
- **근거 표시**: 호출마다 입력 · 출력 · 시각 · 걸린 시간이 남는다(5.2.4). 모든 hyd-dmn 판단 결과에 값의 출처가 붙는다(`provenance`: 원천 · 표 · 열 · 조건 · 실행 SQL · 관측 시각 — 2~4일차 사실표 5절).
- **학생 등록 도구의 제약(실라버스가 말한 「실제 제약」)**: 학생이 등록한 서버는 ① 형식 검사 ② **실제 연결 검사** 통과 ③ 검사 때 찍힌 설정 지문이 지금 설정과 같을 때만 에이전트에 붙고 ④ 그 안에서도 **읽기로 표시된 도구만** 허용된다(`R/it/process/procsvc/mcp_registry.py:1-30`). 설정을 고치면 도장이 사라져 다시 검사해야 한다. 읽기 표시가 아예 없는 서버(공개 구글 MCP 서버 등)는 강사가 도구별로 「읽기로 확인」할 수 있되(`confirmable`), 서버가 쓰기로 표시했거나 이름이 쓰기면 확인할 수 없다(`mcp_check.py:296-303`). 기준 서버 다섯은 수정 · 삭제 거절(`mcp_registry.py` `BASE_SERVERS`).
- 학생 서버 stdio 등록은 연결 검사가 process 컨테이너 안에서 명령을 띄우므로 실행기(`npx · uvx · node · python …`)만 받고 셸(`sh · bash · cmd · powershell`)은 거절한다(`mcp_registry.py` 머리말).

### 7.1.2 사람이 개입하는 세 가지 지점

| 지점 | 언제 | 누가 · 어떻게 | 기록 · 상태 |
|---|---|---|---|
| ① **승인 단계** (사람 작업) | 에이전트가 카드를 낸 뒤, 조치 실행 전 | 지정 역할의 담당자가 포털에서 승인 또는 거절 | 흐름 분기 `approval == '승인'` / 그 밖(거절). 끝 이벤트 이름: 승인 처리 완료 `E_ok` · 미달 `E_fail` · 거절 `E_rejected`(`F-syllabus.md`, 1일차 사실표 5.6) |
| ② **에이전트의 질문** (정보가 부족할 때) | 필수 업무 정보가 없고 연결된 조회 도구로도 확인할 수 없을 때 | 에이전트가 마지막 메시지에 `{"__human_input__":{"question":"…","options":[…]}}` 하나만 내고 멈춤 → 포털 **내 할일**에 「에이전트의 질문」 카드 → 사람이 답(`POST /api/todolist/{id}/human-response`) → **같은 세션으로 이어서** 재개 | 작업 상태 `draft_status = HUMAN_ASKED` → 답 뒤 `FB_REQUESTED` → 재실행. 이벤트 `human_asked` → `human_response`. 질문 1~4000자, 선택지 최대 8개(`hitl.py:18-38`). 답은 한 번만(「이미 답변한 질문입니다」), 같은 질문 중복 억제(`hitl.fingerprint`) |
| ③ **멈춘 에이전트 작업 닫기** (`close_agent_task`) | 에이전트 작업이 한도를 넘겨 PENDING이 되었거나 워커가 죽어 `FAILED` | 사람이 사유를 적고 닫음: 포털 「단계 닫기」 = `POST /api/todolist/{id}/close` (`instance_mode.py:1080`). 사람 작업 · 진행 중 작업 · 사건이 아직 열린 처리 건은 거절 | 행은 `CANCELLED`, 로그에 `[Closed by …]`, 이벤트 `task_cancelled`(`job_id = TASK_CLOSED`). 다른 열린 일이 없으면 처리 건은 기술 종료 이벤트 `closed-by-human`으로 끝남(업무 종료 이벤트가 아님). 구현 `instances.py:893-`. 시험 `R/tests/test_close_agent_task.py`. 라이브 확인: 단계 닫기는 실제 스택에서 통과(NOW 1절), PENDING 쪽은 단위 시험만(NOW K4) |

- **질문의 실제 예**: [기록] `docs/sessions/14`의 증거 — 에이전트가 「조회할 대상 설비를 선택해 주세요. HYD-02와 HYD-03 중 …」 하고 멈췄고(9.6초), 사람이 답 「HYD-02」를 넣자 16.1초 뒤 **같은 세션**으로 재개해 `describe_schema` → `query`를 부르고 `selected_asset: HYD-02`를 냈다. (실행 환경: 호스트 Claude Code 워커 1개, `AGENT_BRIDGE=off`.) 이 증거 폴더(로컬 실행 기록)는 남아 있지 않아 문서(`R/docs/sessions/14-가드레일과-사람에게-묻기.md`)의 기록만 확인했다.
- **CLI마다 다르다**: 같은 질문 정의를 Codex로 돌리니 질문 없이 바로 완료한 관찰이 있다(같은 문서) — 질문 여부는 모델 · CLI의 재량이므로 「항상 묻는다」고 쓰면 안 된다.

### 7.1.3 「AI의 자기 검토」와 「실제 사람 승인 절차」는 다르다

| | AI · 서버의 검토 | 사람의 승인 |
|---|---|---|
| 예 | **가드레일**: 카드마다 후보 선택 규칙 인용이 있는가 · 권고 카드가 규정(EXCLUDE 규칙)에 걸리지 않는가 · 승인 역할이 있는가 · SOP 단계가 있는가를 검사. 어기면 상태 `REJECTED_BY_GUARDRAIL`로 **제출되지 않음** | 지정 역할의 사람이 포털에서 승인 |
| 근거 | `R/it/agent/agentsvc/guardrail.py:56-71` `check_cards`, `decide.py:284-295` — 워커가 부르는 `submit_decision`도 같은 `decide()`를 거치므로 가드레일이 적용된다(`dmn_mcp/tools.py:171-188`). 옛 카드 가드레일(`guardrail.py:1-25`)은 「에이전트에게 명령 권한이 없다」: 카드에 `writes · cmdId · expiresAt · mqtt · topic` 필드가 있으면 거부 | 서버가 `approved_by`를 기록하고 그 뒤에야 명령이 만들어짐 |

- 입력 · 기대 결과가 **실행 가능한 검증으로 연결**되는 이유(실라버스 문구): 자연어 시나리오만으로는 「거절하면 아무 일도 안 일어난다」를 반복해서 확인할 수 없다. 위 표의 오른쪽 열은 시험 코드의 단언(assert)이 되어 매번 같은 입력으로 돌고, 어긋나면 어느 시나리오가 깨졌는지 이름으로 드러난다.
- 승인 카드 **고정본**(`a_cards_before.json`)도 같은 원리다: 고정된 입력(경보 · 사실값) → 기대하는 카드 화면(추천 `SOP-COOL-11` 3.38점 외)을 저장해 두고 바뀌면 근거와 함께 갱신. 주의: 이 고정본의 점수 성분 합과 총점이 맞지 않는다(NOW F14, 원인 미확인) — **고정본을 점수 계산의 교재 예로 쓰지 말 것.**

### 8.1.3 모델 출력의 표현 차이와 필수 계약 위반을 구별하는 장치

실라버스 실습 81의 핵심 질문(「표현 차이」 vs 「필수 계약 위반」)에 대응하는 실제 코드:

| 장치 | 무엇을 보고 무엇을 무시하나 | 근거 |
|---|---|---|
| **출력 계약 검사** | 에이전트가 쓴 문장은 달라도 된다. 폼 필드가 모두 있는지 · 형식이 맞는지만 본다(`contract_met`, `missing_fields`, `mismatch_reason`). 어긋나면 같은 세션에서 최대 2회 교정 | `outcome.py:41-62`, `prompt.py:71-78` |

# 12. 확인 못 한 것

1. **새 에이전트 실행**: 조사 시점에 워커가 꺼져 있어 실제 실행을 새로 보지 못했다. 5.1.2 · 6.1 · 7.1의 실행 장면은 모두 저장소의 [기록]이다. 로컬 실행 기록은 남아 있지 않으므로 교재의 근거 표기는 「실행 기록」으로 하고 파일 경로는 쓰지 않는다.
2. **학생 동선 전체**(실라버스 49 · 60 · 69행): 포털에서 학생 계정으로 에이전트 만들기 → 질문 → 도구 등록 → 승인까지의 실제 화면 검증은 NOW U17~U19 대기다. API · 시험 수준 근거만 있다.
3. **쓰기 권한이 없는 학생 계정**의 실제 제한: 포털에 로그인이 없고 역할을 고르는 구조다. 학생별 권한 계정이 있는지 확인 못 함.
4. **외부 MCP 3종(파일시스템 · Git · 시간)**: 설치 · 권한 · 접속 방식과 도구 이름이 저장소에 없다. 실라버스 운영 유의 행(124)도 「미실측」이라고 적는다.
5. **SDD 실패 재현 케이스 · 5일차 업무 요청 에이전트 · 불량 접수 자료 · 사전 배포 CSV · 예제 회의록 · 학습 코치 자료 · 인수인계서 기준 예제**: 제공 자료이거나 학생 산출물이며 저장소에서 찾지 못했다.
6. **ReAct · Agent Skills · MCP · BDD · SDD의 정식 출처 문구**: 표준 정의는 [일반] 지식으로 적었다. 교재에서 정식 명칭이나 인용을 쓰려면 공식 문서(MCP 명세, Anthropic Agent Skills 문서, Cucumber/Gherkin 문서, GitHub Spec Kit 등)에서 한 번 확인할 것.
7. **`docs/sessions/14`의 증거 폴더**(로컬 실행 기록): 남아 있지 않다. 질문 → 답 → 재개의 시간(9.6초 · 16.1초)은 문서 기록이다.
8. **`evaluate_cards` 128 KB 결과가 CLI에서 잘린 것**이 모든 실행에서 일어나는지: 두 기록(11:13 실행, 15:19 실행)에서 모두 발생했다. 상시인지 환경 의존인지 확인 못 함(CLI의 최대 토큰 설정 영향 추정, 확인 못 함).
9. **옛 `agent_authoring.py` 편집 규칙 중 포털 입력 칸 전체 목록**: 이름 · 역할 · 목표 · 성격 · 도구 · 스킬 · 모델 7칸이라는 주석(원본 `AgentField.vue` 대응)과 `LIMITS`를 읽었으나, 현재 포털 화면의 실제 입력 칸을 눈으로 보지는 않았다.
