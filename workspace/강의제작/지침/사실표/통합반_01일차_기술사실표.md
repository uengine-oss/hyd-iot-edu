# 통합반 01일차 기술 사실표 — HYD 시스템 (교재 재구성 재료)

## 같은 말 · 같은 값 — 모든 교재 공통

여섯 지침이 이 표로 판정하고, 이 표가 회차를 넘는 이름의 장부다. 값이 코드 · 그래프와 달라지면 이 표를 고친다. 「처음 푼 자리」는 그 이름의 정의와 까닭을 처음 푼 통합반 회차와 장을 「통합 N회차 M장」 꼴로 적고(실전반 대응은 공통.md 「자료」의 표), 뒤 회차는 그 이름을 다시 풀지 않고 받는다. 「쓰지 않을 말」 칸에는 그 대상에 붙었던 다른 이름 가운데 원고에서 찾아도 다른 뜻으로 걸리지 않는 말만 「」 안에 적고, `앞회차.py --검사`가 그 말을 원고에서 후보로 찾는다. 여러 회차가 다르게 부른 이름은 가장 먼저 정의한 회차의 이름을 쓰는 말로 두고, 뒤 회차의 다른 이름은 쓰지 않을 말로 둔다. 회차의 덱을 닫는 작업자가 그 회차에서 새로 푼 이름을 이 표에 더하고, 덱이 닫히기 전의 이름에는 「진행 중」을 붙인다(hyd-task 3-1).

## 1. HYD의 9개 기능 계층 (L1~L9)

### 1.1 이 계층 구분의 출처 — 외부 표준이 아니라 이 프로젝트의 설계서

- [설계서] 9계층은 **프로젝트 설계서 v3 4쪽 구조도(L1~L9, OT · DMZ · IT)**에서 온 구분이다. [저장소] compose 머리말도 「v3 아키텍처 L1~L9」라고 적는다(`R/compose.yaml:1`).
- [설계서] 정본은 [설계서 v3](../설계서_v3_유압설비_IoT-SCADA_아키텍처.pdf)다. 1쪽의 L1~L9 이름, 3쪽의 기능 계층·배치 영역 구분, 4쪽 구조도가 계층과 경로의 근거다. 실제 서비스와 설정값은 현재 코드가 우선한다.
- [저장소] 저장소 어디에도 이 9계층을 **ISA-95나 Purdue 모델의 계층이라고 부르는 문구는 없다**. `Purdue`·`ISA-95`·`IEC 62443` 검색 결과는 아래 넷뿐이며 모두 9계층이 아니라 망 분리·자재 개념을 말한다.
  - git 이력 `03c23fdd:문서/시스템/5_결정_기록.md:554` — (보류된 제품 교체 방향) "**구역 라우터 3망 채택**(ceco `shared/network-router`, IEC 62443 구역·통로/Purdue/CISA: OT→DMZ·IT→DMZ만 연결을 열고 DMZ는 열지 않음)" — **실행하지 않은 방향**이다.
  - [저장소] `compose.yaml`의 망 정의(`R/compose.yaml:24-27`)에는 방화벽 장치나 전용 DMZ 망이 없다. 두 망에 함께 붙은 서비스 둘(connect-ingest · cmd-gateway)이 그 역할을 하고, 방향은 서비스 코드가 지킨다(2.2 · 2.3절).
  - git 이력 `39f447ce:문서/시스템/검증_기록/2026-10-09/scenario-research.md:603` — "준용: ISO 14224 예비품 · ISA-95 Material"(온톨로지 확장 검토 메모).
- **교재 결론**: "**HYD 설계서가 정의한 9개 기능 계층(L1~L9)**"이라고 쓴다. "산업 표준 9계층 모델"이라고 쓰면 틀린다. [일반] 참고로 Purdue 모델(ISA-95가 채택한 참조 모델)은 Level 0(물리 공정)·1(기본 제어: PLC)·2(감시 제어: SCADA/HMI)·3(제조 운영: MES)·3.5(산업 DMZ)·4~5(기업 IT)로 나누는 **다른** 구분이다. HYD의 L1~L9와 숫자가 1:1로 대응하지 않는다(대응표는 저장소에 없음 — 교재에서 대응을 주장하려면 "저자 해석"임을 밝힐 것).
- [저장소] 9계층(기능)과 OT/DMZ/IT(보안 영역)는 **서로 다른 분류 축**이다. 한 계층이 두 영역에 걸친다. 포털 정의에서 L3(이벤트 백본: DMZ의 connect-ingest · cmd-gateway와 IT의 Redpanda)와 L6(관제: OT의 FUXA와 IT의 Grafana · Prometheus)는 `zone: 'mixed'`다(`R/it/portal/www/layers.js:30,43`).

## 2. 보안 영역 OT / DMZ / IT

### 2.1 [일반] 배경 지식 (교재 서술용)

- **OT(Operational Technology, 운영 기술)**: 물리 설비를 직접 감시·제어하는 시스템(센서, 구동기, PLC, SCADA/HMI). 우선순위가 가용성·안전·실시간성이다. **IT(Information Technology)**: 업무 데이터를 다루는 시스템(DB, 분석, ERP). 우선순위가 기밀성·무결성 쪽이다.
- 왜 나누나: IT 망은 인터넷·사무 PC와 닿아 침해 가능성이 높고, OT 망이 뚫리면 물리 피해(설비 정지·사고)로 이어진다. 그래서 두 망을 직접 잇지 않고 **DMZ(Demilitarized Zone, 완충 구역)**에 중계 시스템을 두어 "OT→DMZ, IT→DMZ" 연결만 허용하는 것이 산업 보안의 통상 구조다(IEC 62443의 zone/conduit 개념, Purdue 모델의 Level 3.5).
- 실제 현장의 DMZ는 방화벽 두 대(또는 3-leg 방화벽), 데이터 다이오드, 프록시/복제 서버 등 **장치와 규칙**으로 만든다.

### 2.2 [저장소] compose의 네트워크 정의

```yaml
networks:
  ot-net: {}
  it-net: {}
  sim-net: {}                              # 실습 시뮬레이터 API(:8000) 전용: process(정비 수행 모사) · portal(같은 출처 /svc/plant-sim/) ↔ plant-sim 만. OT 망(emqx · PLC)은 DMZ 만 넘는다
```
(`R/compose.yaml:24-27`) — 셋 다 옵션 없는 기본 Docker 브리지 네트워크다(`internal`, 서브넷, 방화벽 규칙 지정 없음).

| 영역 | 서비스 | 붙은 네트워크 | 근거(`compose.yaml`) |
|---|---|---|---|
| **OT** | emqx | ot-net | :46 |
| | plant-sim | ot-net, **sim-net** | :65 |

### 2.3 [저장소] 영역을 넘는 연결을 실제로 제한하는 것

| 장치 | 무엇을 보장하나 | 근거 |
|---|---|---|
| **네트워크 분리(Docker 브리지 2개)** | it-net에만 붙은 컨테이너는 `emqx`·`plant-sim` 이름을 풀 수도, 닿을 수도 없다 | `compose.yaml` networks |
| **배포 계약 시험** | 「ot-net과 it-net에 함께 붙은 서비스는 connect-ingest · cmd-gateway뿐」을 검사하던 시험은 지금 저장소에 없다(`workspace/개발/tests/`에 망 배치 검사가 없다). 이 배치는 `compose.yaml`의 `networks` 줄이 정한다 | 확인 못 함(옛 근거 경로 없음) |
| **코드 규칙(방향)** | connect-ingest는 MQTT를 구독만 하고 **발행 코드가 없다**("Nothing flows back: this container never publishes to MQTT"). cmd-gateway는 Kafka→MQTT 방향으로 명령 · 경보만 낸다 | `R/dmz/connect-ingest/app/main.py:1-8,61`, `R/dmz/cmd-gateway/gw/main.py:1-11` |
| **호스트 포트 바인딩** | 모든 포트가 `127.0.0.1:`에만 열린다(같은 노트북의 브라우저만 접근). 이를 검사하는 시험은 없다 | `compose.yaml`의 `ports` 줄 전부 |

- **망 분리와 토픽 권한은 다른 장치다.** `compose.yaml`의 네트워크 배치와 수집·명령 서비스의 코드가 연결 경로를 나누고, EMQX의 인증·토픽 ACL은 그 경로에서 사용할 주체와 발행·구독 범위를 제한한다.
- **EMQX 인증·ACL**: `ot/emqx/emqx.conf`는 안쪽 입구의 비밀번호 인증을 끄고 username을 ACL 주체로 쓰며, 바깥 MQTT·WebSocket 입구에는 비밀번호 인증을 적용한다. `ot/emqx/acl.conf`는 자동 명령 발행을 명령 관문, 수동 명령·모드 변경을 운전 화면, 계측·상태 발행을 설비 서비스로 제한한다. 수집 서비스와 바깥 수강생 접속은 구독만 허용하고 나머지는 거절한다. 안쪽 username 기반 권한은 서비스의 암호학적 신원 검증과 같지 않다.

### 2.4 "DMZ가 유일한 통로"는 구현상 정확한가 — 정확한 범위와 예외

정확한 문장: "**컨테이너 네트워크에서 IT 서비스가 OT의 MQTT 브로커(EMQX) · PLC 명령 경로에 닿는 길은 DMZ의 두 서비스뿐이고, IT→OT로 내려가는 설비 명령의 길은 cmd-gateway 하나다.**" (`compose.yaml:351` "ot-net 에는 붙이지 않는다 — IT 서비스가 OT(emqx)에 직접 닿으면 DMZ(cmd-gateway)가 유일한 하향 통로가 아니게 된다")

예외와 한계(모두 저장소 근거):

1. **`sim-net`** — process(IT) · portal과 plant-sim(OT)이 함께 붙은 세 번째 망이다. portal은 같은 출처 길 `/svc/plant-sim/`으로 시뮬레이터 API를 중계한다. process의 "정비 수행 모사"(현장 정비원이 부품을 고치는 일을 시뮬레이터 API로 흉내)가 plant-sim API를 직접 부른다. "OT MQTT 에는 닿지 않음"(`compose.yaml:27,65`, `R/it/process/procsvc/instance_mode.py:47`). 실제 공장의 네트워크 경로가 아니라 **시뮬레이터 조작 통로**다.
2. **강의용 입구(브라우저 → plant-sim HTTP)** — 포털의 「결함 시뮬레이션」 화면은 운전 모드 · 수동 쓰기 · 보호 정지 해제 · 전체 초기화를 브라우저에서 포털의 같은 출처 길(`/svc/plant-sim/`, `compose.yaml:27`)을 거쳐 plant-sim API(`POST /api/mode` · `/api/manual` · `/api/reset`)로 부른다(`R/it/portal/www/app.js:355-367`, `R/ot/plant-sim/plantsim/main.py:93-115`). 이 길은 cmd-gateway의 검증을 거치지 않고, 현장 패널 조작의 대역이다. 결함 주입([쿨러 열화 주입])은 process `POST /api/scenario/A/degrade`를 거친다(`app.js:341`).
3. **호스트는 분리 대상이 아니다** — 호스트(노트북)에서는 EMQX 1883과 IT 서비스 포트에 모두 닿는다. 분리는 컨테이너 사이에만 성립한다.
4. **하행에는 명령 말고 경보도 있다** — cmd-gateway는 Kafka `alerts`를 `plant/{a}/alert`(표시 전용, retain)로도 내려보낸다(`R/dmz/cmd-gateway/gw/validate.py:149`).
5. **방향 보장은 프로그램 규칙** — connect-ingest가 MQTT로 발행하지 않는 것은 코드가 그렇게 짜여 있기 때문이지 망이 막아서가 아니다.

**교재 결론**: "DMZ는 물리적으로 유일한 통로"라고 쓰지 않는다. "이 구성에서는 **네트워크 분리(브리지 2개) + 두 망에 함께 붙는 서비스를 둘로 제한한 배치 + 서비스 코드의 방향 규칙**으로 DMZ를 흉내 낸다. 방화벽 장치는 없고, EMQX는 토픽 ACL로 발행 · 구독 범위를 제한한다(2.3절). 실제 현장은 IEC 62443의 구역/통로를 방화벽으로 구현한다"가 정확하다.

### 3.1 가상 설비 plant-sim이 모사하는 것 (L1)

- [저장소] 유압 파워팩 3기 **HYD-01 · HYD-02 · HYD-03**(`R/common/hydcommon/topics.py:4`). 한 대 = 주 펌프 A(+ 예비 펌프 B) + 모터 + 오일 쿨러 + 쿨러 팬 + 작동유 탱크(`R/ot/plant-sim/plantsim/thermal.py:3`, `R/it/neo4j/v2/instances.cypher:113-114`). 세 대는 같은 구조이고 노이즈 난수 시드만 1 · 2 · 3으로 다르다(`plant.py:65-66`).

```

PS1   = 155 + 0.3*load - LEAK_PS1_DROP * leak
FS1   = 10 * load/100 * (1 - leak)
VS1   = 0.55 + 0.004*(TS1-48)+ + K_VIB * bearing_wear * (fan/60)^2
```
  상수: `K_HEAT=1.0, K_COOL=0.05036, K_BASE=0.005, C=20.0, T_AMB=25.0` (`thermal.py:28-32`). 가상 센서: `CE = 100 × cooler_health × (0.6 + 0.4 × fan/100)` (`thermal.py:117`).

- [저장소] **외란(숨은 값) 3개 = 결함 3종**(`plant.py:16-18`): `cooler_degradation` → `cooler_health`(쿨러 핀 오염), `pump_leakage` → `leak`(펌프 A 내부 누설, 기본 0.15), `fan_vibration` → `bearing_wear`(팬 베어링 마모, 기본 0.8). 결함은 계단이 아니라 **램프**로 들어간다: 기본 300설비초(팬은 900설비초)에 걸쳐 목표값까지(`plant.py:33,96-124`).

### 3.2 PLC 모사(soft-PLC)의 역할 (L1)

[일반] 배경: **PLC(Programmable Logic Controller)**는 현장에 설치되는 산업용 제어기다. "입력 읽기 → 프로그램 실행 → 출력 쓰기"를 수~수십 ms 주기로 반복(스캔 주기)한다. **인터록(interlock)**은 위험 조건에서 다른 어떤 명령보다 우선해 설비를 안전 상태로 보내는 보호 로직이다. 대형 공정에서는 인터록을 일반 제어와 독립된 안전 계장 시스템(SIS, IEC 61511)에 둔다. [저장소] 이 설비는 소프트웨어 PLC 하나(`plc.py`)가 제어와 인터록을 함께 맡는다.

[저장소] 이 시스템의 soft-PLC(`R/ot/plant-sim/plantsim/plc.py`):

| 항목 | 값 | 근거 |
|---|---|---|
| 스캔 | 1설비초마다 `check_interlock` 호출(20배속이면 실제 1초에 20회). ms 단위 스캔은 모사하지 않는다 | `plant.py:75-79` |
| 운전 모드 | `LOCAL`(현장 제어) · `REMOTE_MANUAL`(원격 수동) · `REMOTE_AUTO`(원격 자동). 기본 `REMOTE_AUTO` | `schemas.py:49`, `plc.py:31`, 한글 표시 `edge.py:100` |
| 운전 상태 | `RUN` · `TRIP`(보호 정지) · `STOP`(명령에 의한 계획 정지) | `plc.py:32` |
| **하드 인터록 3종** | `TS1 > 65` → `OVERTEMP` / `PS1 < 130` → `LOW_PRESSURE` / `VS1 >= 2.0` → `HIGH_VIBRATION`. 먼저 걸린 하나로 `TRIP`. **자동 리셋 없음** | `plc.py:49-59` |

### 3.3 MQTT로 내보내기 (L2) — 토픽 · QoS · 페이로드

[일반] 배경: **MQTT(Message Queuing Telemetry Transport)**는 OASIS/ISO(ISO/IEC 20922) 표준의 경량 발행–구독(publish/subscribe) 메시징 프로토콜이다(TCP 위, 기본 포트 1883). 1999년 원격지 송유관 계측용으로 만들어져 대역폭이 좁고 불안정한 링크와 작은 장치를 전제로 한다.
- **브로커(broker)**: 발행자와 구독자 사이의 중계 서버. 발행자는 구독자가 누구인지 모른다(결합도 낮음). 브로커가 없으면 센서 쪽이 받을 상대(화면, 수집기…)를 모두 알고 각각 연결해야 한다.
- **토픽(topic)**: `/`로 구분한 계층형 문자열 주소. 구독은 와일드카드를 쓴다: `+` 한 단계, `#` 이하 전부.
- **QoS(Quality of Service)**: 0 = 최대 한 번(확인 없음, 유실 가능), 1 = 최소 한 번(PUBACK까지 재전송, 중복 가능), 2 = 정확히 한 번(4단계 핸드셰이크).
- **retain**: 토픽마다 마지막 메시지 한 건을 브로커가 보관했다가 새 구독자에게 즉시 준다("지금 상태"용). **clean session**: 끊긴 동안의 메시지를 브로커가 쌓아 두지 않는다.
- MQTT 브로커는 기본적으로 **메시지를 보관하는 저장소가 아니다**(retain 한 건 제외). 과거를 다시 읽을 수 없다 → 이것이 뒤에 Kafka 계열 로그를 두는 이유다.

{"asset":"HYD-01","t":"2026-10-10T13:02:38.654Z","mode":"REMOTE_AUTO","state":"RUN","forecast_model":"hydraulic-lumped-simulator-v1","ts1":48.00090867787168,"t_amb":25.0,"trip":null,"fan_pct":60.0,"load_pct":90.0,"cooler_health":1.0,"leak":0.0,"bearing_wear":0.0,"pump":"A","cmdId":null,"result":null,"reason":null,"source":null,"interlock":"PASS","sim_t":22560.0,"time_scale":20.0}
```

- [저장소] **왜 계측은 QoS 0, 상태는 QoS 1 + retain인가**: 계측값과 파형은 곧 새 값이 또 오니 한 장쯤 빠져도 되는 QoS 0으로 보낸다(`edge.py:112`). 설비 상태는 QoS 1 + retain으로 보내(`edge.py:105`) 나중에 연결한 쪽도 지금 상태를 바로 안다. 명령 토픽은 retain하지 않는다 — 재접속한 PLC가 옛 명령을 다시 받아 실행하면 안 되기 때문이다(`R/workspace/개발/scripts/build_fuxa_project.py:58` "retain must be false for command topics (v3: cmd retained 금지)").
- **EMQX의 역할 정리**: OT 망 안의 단일 MQTT 브로커. 발행자(plant-sim, FUXA, cmd-gateway)와 구독자(FUXA, connect-ingest, cmd-gateway, plant-sim)를 토픽으로 잇는다. 저장 · 변환 · 판정은 하지 않는다. 없으면 FUXA 화면도, IT로의 복제도, 하행 명령도 모두 끊긴다(OT 내부 단일 장애점).

### 3.5 Redpanda — Kafka API 호환 이벤트 로그 (L3)

[일반] 배경: **Apache Kafka**는 분산 이벤트 스트리밍 플랫폼이다(LinkedIn에서 시작, 2011년 공개). 핵심은 "**추가만 하는 로그(append-only log)**"다.
- **토픽(topic)**: 레코드의 논리적 묶음. **파티션(partition)**: 토픽을 나눈 물리 로그. 순서는 **파티션 안에서만** 보장된다. 같은 키의 레코드는 같은 파티션으로 간다.
- **오프셋(offset)**: 파티션 안에서 레코드의 일련번호. 읽어도 지워지지 않고 **보존 기간(retention)**이 지나야 지워진다 → 여러 소비자가 같은 데이터를 각자 속도로, 과거부터 다시 읽을 수 있다.
- **컨슈머 그룹(consumer group)**: 그룹마다 "어디까지 읽었나(커밋한 오프셋)"를 따로 가진다. 서로 다른 그룹은 서로 독립이다.
- **프로듀서/컨슈머**, **브로커**, **복제 계수(replication factor)**.
- MQTT와의 차이: MQTT는 **프로토콜**(브로커는 받은 즉시 밀어 주고 보관하지 않음, 장치 연결용). Kafka는 **플랫폼**(디스크에 보관하는 로그, 소비자가 끌어 읽음, 재처리 가능, 서버 간 데이터 파이프라인용).
- **Redpanda**는 Kafka의 클라이언트 프로토콜(Kafka API)과 호환되는 별도 제품이다(C++ 구현, JVM · ZooKeeper 없음). Kafka 클라이언트 라이브러리가 그대로 붙는다. **Apache Kafka 그 자체는 아니다.**

### 3.6 detector — 스트림 처리 · CEP (L4)

[일반] 배경: **스트림 처리**는 저장된 데이터에 질의하는 대신 흘러오는 이벤트를 도착하는 대로 계산하는 방식이다. **CEP(Complex Event Processing, 복합 이벤트 처리)**는 여러 이벤트의 조합 · 순서 · 지속 시간으로 패턴을 찾는다(예: Apache Flink CEP의 `MATCH_RECOGNIZE`). 단순 임계치 알람과의 차이는 "여러 신호의 AND + 추세 + 유지 시간"이다. **히스테리시스(hysteresis)**는 켜는 기준과 끄는 기준을 다르게 두어 경계에서 깜빡이지 않게 하는 기법이다.

[저장소] detector(`R/it/detector/det/`) — 설계서의 "Apache Flink CEP + ONNX" 자리(설계서 PDF, `compose.yaml:249` 「Flink 역할」)

**(1) 특징 계산** (`features.py`, `main.py:59-60,158-190`)
- TS1이 들어올 때마다 **기울기**: 최근 **60설비초** 구간의 선형회귀 기울기(단위: 값/설비초)(`features.py:21-46`).
- **이상 점수(score)**: 고정 기준 `NORMAL = {"TS1": (48.0, 1.0), "CE": (84.0, 3.0), "VS1": (0.6, 0.05)}`에 대한 z 점수 세 개의 RMS ÷ 4를 0~1로 자른 값(`main.py:60`, `features.py:77-80`). **학습 모델이 아니다**("the anomaly-score stand-in for the ONNX autoencoder", `features.py:1`; Grafana 패널 설명 "학습된 오토인코더의 출력은 아닙니다", `R/workspace/개발/scripts/build_grafana_dashboard.py:110`). 이 점수는 **경보 판정에 쓰이지 않고** 표시 · 근거용이다(판정은 아래 패턴).
- 결과를 Kafka `feat.1s`에 발행.

**(2) 패턴 정의는 코드가 아니라 지식 그래프에서 읽는다**
- Neo4j의 `AnomalyPattern`(detectionMode='held') 노드의 `TESTS` 관계(AND 조건) · `clearRule` · `holdSeconds` · `clearHoldSeconds` · `slopeWindowSeconds`를 기동 때와 **15초마다** 다시 읽는다(`main.py:263-266`, `patterns.py:155-199`, 정의 행 `R/it/neo4j/v2/instances.cypher:244-277`).
- 정의는 실행 코드로 평가하지 않고 "비교 · and/or/not · slope(TAG)"만 허용하는 닫힌 문법으로 파싱한다(`patterns.py:25-102`).
- 판정 입력 태그는 **매초 보고되는 태그**여야 한다(아니면 정의 거부, `patterns.py:133-141`).

**(3) 세 패턴의 조건식 (원문)** (`cep.py:15-18`, `R/it/neo4j/v2/instances.cypher:254-262`)

| 패턴 코드 | 발생(RAISE) 조건 | 해제(CLEAR) 조건 | 유지 |
|---|---|---|---|
| `COOLER_DEGRADATION` (쿨러 성능 저하) | `TS1 > 55 and CE < 70 and slope(TS1) > 0` | `TS1 < 52 and slope(TS1) <= 0` | 60설비초 / 60설비초 |
| `PUMP_LEAKAGE` (펌프 내부 누설) | `PLC.state == 'RUN' and PS1 < 165 and FS1 < 8.0 and LoadSP >= 80` | `PLC.state == 'RUN' and ((PS1 >= 168 and FS1 >= 8) or LoadSP < 80)` | 60 / 60 |
| `FAN_VIBRATION` (팬 진동 상승) | `VS1 > 1.2 and slope(VS1) > 0` | `VS1 < 1.1` | 60 / 60 |
| `OVERHEAT_TRIP` · `LOW_PRESSURE_TRIP` · `HIGH_VIBRATION_TRIP` | PLC `state == TRIP`(`plant.status` 직접 감시, 유지 시간 없음) | PLC 리셋 | 즉시 |

**(4) 상태 기계** (`cep.py:38,68-98`)

```
IDLE ──조건 참──▶ CANDIDATE ──조건이 hold_s 동안 유지──▶ RAISED (RAISE 발행)
RAISED ──해제식 참──▶ CLEARING ──해제식이 hold_s 동안 유지──▶ IDLE (같은 alertId로 CLEAR 발행)
CANDIDATE에서 조건이 거짓이 되면 IDLE로, CLEARING에서 해제식이 거짓이 되면 RAISED로 되돌아간다
```
- 단계 이름은 코드상 4개(`IDLE | CANDIDATE | RAISED | CLEARING`). 포털 표시말: IDLE "감시 중", CANDIDATE "이상 징후"(`it/portal/www/ui.js:240`).
- **데이터 품질 처리**: 값이 무효(시각 이상 · 품질 bad · 숫자 아님)이거나 보고 주기 + 2초(`OBSERVATION_GRACE_S=2`, `compose.yaml:256`)보다 오래 끊기면 **채우던 유지 시간을 처음으로 돌린다**. "Unknown data cancels a pending hold; it cannot clear a raised alert."(`cep.py:59-65`) — 모르는 동안을 "계속 참이었다"로 치지 않는다.
- **전달 보장**: 상태 · 오프셋 · 보낼 경보를 SQLite 한 트랜잭션에 저장하고 경보는 전송 확인 뒤 지운다(outbox, **최소 1회 전달** — 같은 경보가 한 번 더 갈 수 있음)(`R/it/detector/det/store.py:1`, `main.py:298`).

### 3.7 TimescaleDB와 connect-sink — 시계열 저장 (L5)

[일반] 배경: **시계열 데이터**는 "시각 + 식별자 + 값"이 계속 추가되는 데이터다. 쓰기는 거의 추가뿐, 조회는 대부분 시간 범위 · 최근값 · 집계다. **TSDB(Time Series Database)**는 이 패턴에 맞춰 시간 기준 분할 · 압축 · 보존 정책 · 다운샘플링을 제공한다. **TimescaleDB**는 PostgreSQL 확장이다 — 표를 **하이퍼테이블(hypertable)**로 만들면 시간 구간별 **청크(chunk)**로 자동 분할되고, SQL은 일반 PostgreSQL 그대로 쓴다. **연속 집계(continuous aggregate)**는 자동 갱신되는 구체화 뷰다. **Historian**은 산업 현장에서 공정 값을 장기 보관하는 시스템을 가리키는 통칭이다(이 저장소는 온톨로지에서 TimescaleDB를 "Historian (TimescaleDB)"라고 부른다, `instances.cypher:104`).

```

                          └▶ Kafka action.cmd
cmd-gateway: 검사 7종 ─통과─▶ MQTT plant/{a}/cmd/auto ─▶ plant-sim 엣지 ─▶ soft-PLC 검사 5단계 ─▶ 설정값 적용
PLC 결과 ─▶ MQTT plant/{a}/status (cmdId · result) ─▶ connect-ingest ─▶ Kafka plant.status ─▶ process(ACK 대조, 30초 안)

### 4.1 [저장소] `action.cmd` 메시지

- 토픽: Kafka `action.cmd`, 생산자 process(`machine.py:171-178`).
- 페이로드(코드 원문 구조): `{"cmdId", "asset", "incident", "source": "HITL", "actions": [...], "approvedBy", "approvalId", "issuedAt", "expiresAt"}`.
- 식별자 형식(코드): `cmdId = CMD-{MMDD}-{순번 4자리}-{16진 4자}` 예 [기록] `CMD-1010-0001-b94a`; `approvalId = APR-{MMDD}-{16진 8자}`; `expiresAt = 승인 시각 + 120초`(벽시계, `definition.py:29` `CMD_EXPIRY_S = 120`).
- 조치 코드 허용 목록: `FAN_SET` · `LOAD_SET` · `RESET` · `PUMP_SELECT` · `STOP`(`common/hydcommon/schemas.py:56-63`) → PLC 자원으로 변환 `FAN_SET → FanSpeedSP(fan_pct)`, `LOAD_SET → LoadSP(load_pct)`, `RESET → Reset`, `PUMP_SELECT → PumpSelect`, `STOP → Stop`.
- [기록] 승인 원문의 설비 조치 부분: `{"sop": "SOP-COOL-11", "code": "FAN_SET", "name": "팬 속도 설정", "param": "fan_pct", "skill": "skill:sop-cool-11", "value": 100, "system": "actr:fan-drive"}`.

### 4.2 [저장소] cmd-gateway의 검증 — 거절 사유 7종

`CHECKS = ("SCHEMA", "WHITELIST", "EXPIRED", "DUPLICATE", "APPROVAL", "MODE", "RATE_LIMIT")` (`R/dmz/cmd-gateway/gw/validate.py:30`)

| 순서 | check | 무엇을 보나 | 거절 사유 예(코드 문자열) |
|---|---|---|---|
| ① | `SCHEMA` | 필수 필드(`cmdId, asset, incident, source, actions, approvedBy, expiresAt`), `source`가 `HITL`인지 | `missing field: …`, `source must be HITL` |
| ② | `WHITELIST` | 조치 코드가 허용 목록에 있는지 | `action not allowed: [...]` (예: PLC에 없는 `PRESSURE_SET`) |
| ③ | `EXPIRED` | `expiresAt`이 지났는지 | `expired at …` |
| ④ | `DUPLICATE` | 최근 256개 cmdId와 겹치는지 | `cmdId … already forwarded` |
| ⑤ | `APPROVAL` | **승인 장부**: process가 `audit` 토픽에 먼저 쓴 `CMD_APPROVAL_RECORDED` 기록이 이 cmdId로 있는지, `approvalId`가 같은지, 명령에서 다시 계산한 **HMAC-SHA256 지문**이 기록과 같은지 | `no process approval record for cmdId …`, `command fingerprint differs from the approval record (actions/asset/expiry/approver changed)` |
| ⑥ | `MODE` | 구독해 둔 최신 `plant/{a}/status`의 `mode`가 `REMOTE_AUTO`인지 | `PLC mode is REMOTE_MANUAL (REMOTE_AUTO required)`, `no status seen for …` |
| ⑦ | `RATE_LIMIT` | 같은 초에 2건 넘게 통과했는지 | `more than 2 commands in one second` |

- 통과하면 `plant/{a}/cmd/auto`에 `{"cmdId", "source": "HITL", "expiresAt", "writes": [{"res": "FanSpeedSP", "v": 100}]}`를 QoS 1 · retain=false로 발행하고 `audit`에 `CMD_FORWARDED`(통과한 검사 목록 포함)를 남긴다. 거절하면 **버리고** `audit`에 `CMD_REJECTED`(`check`, `reason`)를 남긴다(`gw/main.py:136-149`).
- `validate.py` 머리말도 "the seven checks every downward command must pass"라고 적는다(`validate.py:1`). 관문이 MQTT 발행을 확인하지 못하면 `gw/main`이 `PUBLISH_CHECK`를 덧붙인다(`validate.py:28`). → 교재는 "**7가지 거절 사유**(SCHEMA · WHITELIST · EXPIRED · DUPLICATE · APPROVAL · MODE · RATE_LIMIT)"로 쓴다.
- 한계: 게이트웨이의 기억(최근 cmdId 256개 · 승인 기록 512개 · 설비 상태)은 메모리라 재시작하면 비워지고, 재시작 직후 상태를 다시 받기 전의 명령은 `MODE`로 거절된다(`validate.py:27,47`).

### 4.3 [저장소] PLC 모사에 닿는 방법과 ACK

1. plant-sim의 엣지가 `plant/{a}/cmd/auto`를 QoS 1로 구독(`edge.py:57`).
2. **출처는 페이로드가 아니라 토픽으로 정한다**: `cmd/auto`로 오면 `HITL`, `cmd/manual`로 오면 `FUXA`. "A payload claiming another source is ignored."(`edge.py:23-26`)
3. soft-PLC가 3.2절의 5단계 검사(모드/출처 → 만료 → 중복 → 범위 → 인터록)를 다시 한다 — **검사가 두 겹**(DMZ 게이트웨이 + PLC).
4. 결과를 즉시 `plant/{a}/status`(QoS 1, retain)에 실어 보낸다: `cmdId`, `result`(`DONE`/`REJECTED`), `reason`, `interlock`(`PASS`/`TRIP`)(`edge.py:90`, `plc.py:168-172`).
5. connect-ingest → Kafka `plant.status` → process가 **자기 cmdId와 같은** 상태만 ACK로 받는다(`machine.py:245-263`). `DONE`이면 재관측 시작, `REJECTED`면 `ESCALATED`. **30초**(벽시계) 안에 ACK가 없으면 `ACK_TIMEOUT` → `ESCALATED`(`definition.py:25`, `machine.py:296-299`).
6. connect-sink가 같은 상태에서 ACK 네 칸을 `actions` 표의 `ack_result · ack_reason · ack_at`에 적는다 → Grafana 「조치」 표.

- [기록] 명령 전송 11:14:57 → 설비 응답 11:14:58, 단계 소요 865 ms, "안전 연동 통과".
- 게이트웨이가 거절하면 사유는 `audit`에만 남고, 처리 쪽은 30초 안에 ACK를 받지 못해 `ACK_TIMEOUT`으로 사람에게 넘어간다(`R/it/process/procsvc/definition.py:28,77-78`).

### 6.2 "같은 유온 상승이 서로 다른 원인에서 올 수 있다"의 실제 근거

**(a) 지식 그래프 — 한 고장 유형에 원인 후보가 여럿이고, 원인마다 가르는 증거가 다르다**

수업 문서 적재 결과(`it/process/procsvc/course_extractions.json`, 그래프 조회로 확인. `it/neo4j/v2/instances.cypher:5`는 이 지식을 시드에 넣지 않는다):

| 고장 유형 | 원인 후보 (prior) | 증거 규칙 (rule 원문) | 읽는 센서 | 뜻 |
|---|---|---|---|---|
| 쿨러 냉각 성능 상실 `fm:cooler-cooling-loss` | 쿨러 핀 오염 (먼지 · 유막) `cause:cooler-fin-fouling` (0.6) | `avg(CE) over 30s < 70` | CE | 냉각 효율이 실제로 낮다 |
| | | `avg(VS1) over 120s < 0.9` — "팬 진동 정상 (팬 고장 아님)" | VS1 | **다른 원인을 배제**하는 증거 |
| | 주변 온도 상승 `cause:ambient-temperature-rise` (0.2) | `avg(TS4) over 120s >= 35` — "캐비닛 온도 35 ℃ 이상" | TS4 | 쿨러가 아니라 환경 |

| | 작동유 오염 `cause:hydraulic-oil-contamination` (0.3) | `avg(FS1) over 60s < 8` | FS1 | 유량이 낮다 |

수업 매뉴얼 `HM-8.4`(`R/it/portal/www/samples/HM-8_cooler-fan-manual.md:31-38`, 구조판에 적재되는 문서) 원문:

> 쿨러 냉각 성능 상실은 오일 쿨러에서 생기는 고장이며 유온 상승과 냉각 효율 저하로 나타난다. 원인은 아래 세 가지를 순서대로 확인한다.
> - 쿨러 핀 오염(먼지 · 유막으로 핀이 막힘)이 가장 흔하다(사전 확률 0.6). 최근 30초 냉각 효율 평균이 70 % 미만이고, 최근 2분 팬 진동 VS1 평균이 0.9 mm/s 미만(팬은 정상)이면 핀 오염으로 판정한다. 관련 부품은 쿨러 코어다.
> - 주변 온도 상승(외기 고온 · 캐비닛 환기 불량)은 사전 확률 0.2로 본다. 최근 2분 캐비닛 온도 TS4 평균이 35 ℃ 이상이면 외기 고온으로 판정한다.
> - 팬 구동 불량(벨트 슬립 · 베어링 마모)은 사전 확률 0.2로 본다. 최근 2분 팬 진동 VS1 평균이 0.9 mm/s 이상이면 HM-8.1 점검으로 넘어간다.

→ **같은 증상(유온 상승 + 냉각 효율 저하) · 같은 경보(COOLER_DEGRADATION)에 원인 후보가 셋**이고, 가르는 데 **유온이 아닌 다른 센서(VS1, TS4, CE)의 다른 구간 평균**이 필요하다. 원인에 따라 근본 조치도 다르다: 핀 오염 → `SOP-COOL-14 쿨러 핀 세척`, 주변 온도 → `SOP-COOL-15 캐비닛 환기 보강`, 팬 구동 불량 → `HM-8.1 쿨러 팬 벨트 점검`(`SOP-FAN-11`)(`HM-8…md:3-10,69-80`). "온도가 오르면 쿨러 고장"이라는 단일 규칙이 틀린 이유의 실물이다.

**(b) 물리 모델 — 유온을 올리는 경로가 여러 개다** (`instances.cypher:146-166`의 `INFLUENCES`, "설비 모델의 식과 같은 방향이다")

→ 유온(TS1)을 올리는 요인이 저장소 기준 넷: **쿨러 핀 오염(→ CE↓)**, **부하 증가**, **펌프 내부 누설(약하게)**, **팬 속도 저하**. 여기에 외부 변수 "외기 온도 → 유온"(식의 `T_AMB`, `thermal.py`)이 있다. TS1 하나만 보면 이들을 구분할 수 없고, CE · LoadSP · PS1/FS1 · FanSpeedSP · TS4를 함께 봐야 갈린다.

**(c) 고장의 전파(LEADS_TO)** (`instances.cypher:232`): 쿨러 냉각 성능 상실 → 과열 정지 · 작동유 열화 / 펌프 체적 효율 저하 → 작동유 열화 / **팬 베어링 열화 → 쿨러 냉각 성능 상실**. → "팬 베어링이 닳아 팬을 늦추면 냉각이 줄어 유온이 오른다" — 유온 상승이 **다른 고장의 결과**일 수도 있다.

**(d) 조치가 원인에 따라 역효과가 되는 경로**: 유온이 오른다는 이유만으로 팬 최대 운전을 고르면 다른 위험을 키울 수 있다. [저장소·계산] `common/hydcommon/plant_model.py`의 `vibration`은 `0.55 + 0.004 × max(0, TS1−48) + bearing_wear × (fan/60)²`이다. `ot/plant-sim/plantsim/thermal.py`의 마모 기본 목표 0.8에서 팬 100 %를 대입하면 유온48~65 ℃ 구간의 잡음 제외 진동은 약2.77~2.84 mm/s다. 교재의 약2.8 mm/s는 이 계산 규모에 해당하며, 특정 시각의 관측값으로 취급하지 않는다. `ot/plant-sim/plantsim/plc.py`의 `check_interlock`은 운전 중 VS1 ≥ 2.0 mm/s이면 고진동 보호 정지로 전환한다. 펌프 누설에 압력 설정 상향은 씰 손상을 키워 규정상 제외한다(`instances.cypher` HM-5.4).

**(e) 경보가 꺼진 것과 고장이 나은 것은 다르다**: 펌프 누설 경보는 `LoadSP >= 80`이 조건에 들어 있어 부하를 낮추면 경보가 꺼지지만 누설은 그대로다("the leak is masked, not gone — the re-observation of the process still checks PS1 >= 165", `cep.py:20-22`). 쿨러도 팬 최대로 유온은 내려가지만 `cooler_health`는 그대로라 CE는 여전히 낮다(근본 원인 잔존 → 작업지시 등록의 이유).

**한계(단정 금지)**: 위 수치 · 관계는 **이 시뮬레이터의 모델**이다. 저장소 스스로 "아래 값은 교육용 가상 설비의 축소 기준이다(일반 산업 설비의 경보는 보통 80 ℃ 안팎이다)"라고 밝힌다(`HM-8…md:22`). 실제 유압 설비의 일반 법칙처럼 쓰지 말고 "이 설비 모델에서는"으로 한정한다. TS4는 모델상 `T_AMB + 3`에 고정이라 "주변 온도 상승" 원인은 이 시뮬레이터에서 실제로 발생시키는 주입 수단이 없다(`thermal.py:63`).

## 7. 온톨로지 (1일차 범위: 필요성과 기초 표현)

### 7.1 [일반] 기초 개념 (교재 서술용)

- **온톨로지(ontology)**: 한 분야의 개념(클래스), 개념의 속성, 개념 사이 관계와 제약을 명시적으로 정의한 것. "무엇이 있고 서로 어떻게 연결되는가"의 **틀(스키마)**과 그 틀을 따르는 **실제 개체(인스턴스)**를 구분한다.
- **지식 그래프(knowledge graph)**: 개체를 노드, 관계를 간선으로 저장한 것. **속성 그래프(property graph)** 모델(Neo4j)은 노드에 레이블과 속성, 관계에 **이름(type) · 방향 · 속성**을 둔다. 질의 언어는 **Cypher**: `(a:Label)-[:REL_TYPE]->(b:Label)`.
- 관계의 **방향**은 관계 이름의 뜻이 정해진 뒤에 옳고 그름이 결정된다(`causes`와 `causedBy`는 방향이 반대인 같은 사실).
- 그림을 그렸다고 온톨로지가 끝난 것이 아니다: 클래스 정의 · 관계의 끝점(어느 클래스에서 어느 클래스로) · 다중도 · 필수 속성 · 검증이 있어야 한다. arrows.app으로 그리는 것은 "노드 · 관계 · 방향"의 **표현**을 익히는 수준이다.

**방향에 대한 정확한 사실**(관계 방향 퀴즈 · 설명에 쓸 것):

- 이 스키마에는 "증상 → 원인"을 직접 잇는 관계가 **없다**. 증상과 원인은 **고장 유형을 사이에 두고** 이어진다: `(Symptom)-[:INDICATES]->(FailureMode)<-[:CAUSES]-(Cause)`. 화살표가 양쪽에서 고장 유형으로 **모인다**. 에이전트가 실제로 쓰는 질의(`R/it/neo4j/templates/t1_causes.cypher:3`):
```cypher
MATCH (p:AnomalyPattern {code: $pattern})-[:DETECTS]->(s:Symptom)-[:INDICATES]->(fm:FailureMode)<-[:CAUSES]-(c:Cause)
OPTIONAL MATCH (c)-[:EVIDENCED_BY]->(e:Evidence)
```
- 조치는 **원인이 아니라 고장 유형에** 붙는다: `(FailureMode)-[:MITIGATED_BY|REMEDIED_BY]->(Skill)`. 특정 원인에만 맞는 조치일 때만 `(Skill)-[:ADDRESSES]->(Cause)`를 덧붙인다(`t2_skills.cypher:3-4`). 예: 같은 "쿨러 냉각 성능 상실"이라도 핀 오염이면 세척, 외기 고온이면 환기 개선(`schema-v2.md:206`).
- 설비 쪽 실제 인스턴스 경로(`instances.cypher:109-143`): `(asset:hyd-01)-[:HAS_COMPONENT]->(comp:cooler 오일 쿨러)-[:MONITORED_BY]->(sen:ts1 유온 센서, tag TS1)-[:OBSERVES]->(sv:ts1 유온, 단위 ℃, kind controlled, normal 48, limit 65)`.
- 1일차 실습(arrows.app)의 "설비–증상–원인–조치" 단순 그림은 이 스키마의 축약이다. 학생이 `증상 -causedBy-> 원인` 또는 `원인 -causes-> 증상`으로 그려도 관계 이름과 방향이 일치하면 틀리지 않다. 다만 "HYD의 실제 스키마는 증상과 원인 사이에 고장 유형을 둔다"는 것을 2일차로 넘기는 연결 문장으로 쓸 수 있다.

### 7.4 [저장소] 정적 지식과 조회 시점에 가져오는 값의 구분

| | 어디에 | 무엇이 | 언제 바뀌나 |
|---|---|---|---|
| **정적 지식** | Neo4j | 설비 구조, 센서–상태 변수 대응, 패턴 정의(조건식 · 유지 시간), 증상 · 고장 유형 · 원인(사전 확률), **증거 규칙(무엇을 어떤 SQL로 어떤 기준과 비교할지)**, SOP · 단계 · 매뉴얼 절, 상태 변수의 정상값 · 한계(`normal 48`, `limit 65`) | 시드 적재, 사람이 검토한 매뉴얼 적재 때 |

| **둘을 잇는 고리** | Neo4j의 `Evidence.sql` · `tag` · `windowSeconds`, `InputData -[:SOURCED_FROM]-> Sensor|System`, `InputData -[:REPRESENTS]-> StateVariable|Measure` | "어느 값을 어디서 어떻게 읽을지"의 **정의** | — |
| **운영 기록** | Neo4j(`Incident`, `DecisionCase`) | 종결된 사건 · 사람의 판단 사례 | 처리 건이 진행 · 종결될 때 |

- Neo4j에는 실시간 값이 없다(이 절의 표). 그래프에는 "TS4를 `tag_1s`에서 최근 2분 평균으로 읽어 35와 비교하라"는 **방법**이 있고, 값은 판단 시점에 TimescaleDB에서 읽는다. [기록] 처리 기록의 "가져온 데이터" 표가 값마다 출처와 읽은 방법을 남긴다: "유온 59.9 ℃ · 유온 센서 · TimescaleDB tag_1s TS1 최신값 (0 s 전)", "PLC 운전 모드 원격 자동 · SCADA · PLC (cmd-gateway 경유) · plant.status 최신 메시지 (process 서비스가 구독)", "긴급 오더 남은 시간 5.98 h · MES · MES 생산오더 납기까지 남은 시간".
- 증거 SQL은 에이전트가 지어내지 않는다. 증거 노드에 든 질의문(`e["sql"]`)을 그대로 실행한다(`R/it/agent/agentsvc/tools/mcp_tsdb.py:87,94`). 데이터가 묵었거나(최신 TS1 60초 초과) 공백이 있으면 판정을 **보류**한다(`withheld`, git 이력 `03c23fdd:문서/시스템/참조/sensor-queries.md:13`).
- 구조와 문서 지식: `instances.cypher`는 구조(설비 · 센서 · 패턴 · 증상 · 스키마)만 넣고, 고장 유형 · 원인 · 증거 · 조치 · 매뉴얼 규칙은 수업 문서(HM-8 · PM-02 · PR-07) 적재가 만든다(`it/neo4j/v2/instances.cypher:5`).

## 10. 기존 교재가 틀리게 단순화했을 수 있는 곳 — 정리본 7.6의 검수 지점 여덟 가지

**① SCADA — "보여 주고 경보만 울린다"가 아니다.**
이 구현의 SCADA인 FUXA는 감시(실시간 값 표시), 자체 알람(TS1 55 ℃ 초과 높음 · 65 ℃ 보호 정지 구간), IT 경보 표시, 그리고 **운전 제어**(팬 속도 · 펌프 부하 입력, 정지 해제, 운전 모드 전환)를 모두 한다(`ot/fuxa/project.json`의 devices · alarms). 포털 구성 화면도 FUXA를 "설비 감시·수동 조작·운전 모드 전환"이라고 적는다(`layers.js:32`). FUXA 수동 조작이 들어오면 PLC가 원격 수동으로 바뀌어 **승인된 자동 조치가 거절된다**(수동 우선). FUXA가 하지 않는 것은 다변량 패턴 판정(detector) · 원인 진단(지식 그래프 + 판단 엔진) · 장기 이력(TimescaleDB/Grafana) · 보호 정지(PLC)다. 판단의 귀속은 3.8절 끝 줄을 쓴다.

**② OT/DMZ/IT — "DMZ가 물리적으로 유일한 통로", "문이 두 개라서 한쪽은 올라가기만 한다"는 근거가 다르다.**
실체는 Docker 브리지 네트워크 2개(`ot-net`, `it-net`)와 그 둘에 함께 붙은 서비스 2개다. 방화벽 · 전용 DMZ 망이 없고, "올라가기만 한다"는 것은 connect-ingest 코드에 MQTT 발행이 없다는 **프로그램 규칙**이다. "두 망에 함께 붙는 서비스는 둘뿐"은 `compose.yaml`의 배치이고, 이를 검사하는 시험은 지금 없다. 예외로 `sim-net`(process · portal ↔ plant-sim 시뮬레이터 API)과 브라우저의 강의용 입구가 있다. 하행 통로(cmd-gateway)로는 명령뿐 아니라 표시용 경보도 내려간다. 2.4절의 "정확한 문장"을 쓴다.

**③ MQTT와 Kafka — 종류가 다르고, 이 시스템은 Apache Kafka가 아니라 Redpanda다.**
MQTT는 **프로토콜**(OT 구간, EMQX 브로커가 받은 즉시 밀어 주고 보관하지 않음), Kafka는 **플랫폼**(디스크 로그, 오프셋으로 끌어 읽기, 재처리). 이 시스템에서 둘은 대체 관계가 아니라 **직렬**이다("MQTT 다음에 Kafka"): 설비 → MQTT(EMQX) → connect-ingest → Kafka API(Redpanda). 제품명은 Redpanda v24.2.7이며 "Kafka API 호환"이라고 쓴다. Kafka Connect · Flink · EdgeX도 쓰지 않는다(파이썬 대역). 설정값: MQTT 태그 QoS 0 / 상태 QoS 1 retain, Kafka 토픽 7개 · 파티션 1 · 복제 1 · 키 = 자산. 유실 가능 지점(QoS 0, clean session, 메모리 큐 2만 건)과 중복 가능 지점(detector 경보 최소 1회)도 사실대로 쓴다.

**④ 임계치 경보와 원인 추론 — 경보는 원인을 말하지 않는다.**
경보 `COOLER_DEGRADATION`은 "TS1 > 55 **그리고** CE < 70 **그리고** 유온 상승 중이 60설비초 유지"라는 **다변량 + 추세 + 지속** 조건의 성립일 뿐이다. 원인은 그 뒤에 지식 그래프의 후보 3개(핀 오염 0.6 · 주변 온도 0.2 · 팬 구동 불량 0.2)를 VS1 · TS4 · CE의 구간 평균으로 가려 정한다(5.3 · 6.2절). 증거를 읽을 수 없으면 원인을 고르지 않고 보류한다. 단일 임계치 알람은 FUXA(55/65 ℃)와 PLC 인터록(65 ℃)에 따로 있다 — "알람 · 패턴 경보 · 인터록"의 세 층을 구분해 쓴다. 이상 점수(score)는 고정 기준 z 계산이라 "AI 모델이 이상을 탐지한다"고 쓰면 틀린다.

**⑤ 온톨로지와 관계 그래프 — 그림을 그린 것과 온톨로지 모델링은 다르다.**
저장소의 온톨로지는 `schema.json`(클래스 48 · 관계 64, 관계마다 끝점 클래스 · 다중도 · 속성)이 단일 원본이고(`schema-v2.md:23`), 인스턴스는 그 틀을 따라야 하며 `validate`로 기계 검사한다. 스키마 그림과 인스턴스 그림도 따로다(`schema-v2.md:205-224`). 1일차 arrows.app 실습이 다루는 수준은 "노드 · 관계 이름 · 방향"의 표현까지이고, 클래스 · 속성 · 제약 · 인스턴스 구분은 2일차 범위(실라버스 02일차 "클래스·인스턴스·속성·관계·스키마의 차이")다. 교재에 이 범위를 명시한다.

**⑥ 관계 방향 — 이름의 뜻이 방향을 정한다.**
이 스키마의 실제 방향: `Cause -[:CAUSES]-> FailureMode`(원인이 고장을 **일으킨다**), `Symptom -[:INDICATES]-> FailureMode`(증상이 고장을 **가리킨다**), `FailureMode -[:MITIGATED_BY]-> Skill`(고장이 조치에 의해 **완화된다** — 수동태라 고장에서 조치로 향한다), `Cause -[:EVIDENCED_BY]-> Evidence`. "증상 → 원인" 직접 관계는 없고 고장 유형에서 만난다. 퀴즈를 낼 때 "화살표 방향 맞히기"가 아니라 "관계 이름 · 주어 · 목적어가 일치하는가"로 묻는다(예: `MITIGATED_BY`를 Skill → FailureMode로 그리면 이름과 방향이 어긋난다).

**⑦ AI · 프로세스와 권한 — 승인 전 자동 실행을 막는 근거가 실제로 있다. 다만 완비는 아니다.**
막는 장치: 에이전트 계열 서비스는 OT 망에 없음 / 도구는 읽기 전용(쓰기는 판단 제출뿐) / 가드레일이 명령 모양 필드를 거부 / 명령은 process의 승인 전이에서만 생성 / 게이트웨이가 승인 장부(HMAC 지문)가 없는 명령을 `APPROVAL`로 거절 / PLC가 토픽으로 출처를 판정하고 REMOTE_AUTO에서만 수락 / 흐름 등록 때 "설비 명령 앞에 사람 승인이 없으면" 거절(4.4절). 저장소 원칙 문장: "승인 전 에이전트는 조회 · 계산 · 보고서만 한다. 사람 승인 1회 뒤 process가 실행한다."(`R/CLAUDE.md` §5) 한계도 사실이다: 2.3절의 EMQX 안쪽 입구 인증 한계, 포털 무로그인, 기본 HMAC 키, 강의용 입구. "모든 안전 장치가 완비"라고 쓰지 않는다. 승인 **거절** 경로(설비 명령 없이 거절 종결)는 수업 흐름에 있다(5.6절).

**⑧ 데이터 계보 — "길 설명"이 아니라 출처 · 변환 · 사용 · 추적 가능성이다.**
TS1 한 값의 계보: ① 시뮬레이터 메모리에서 생성 → ② 태그 이름 대문자화 · 소수 자리 정리(`round(s.ts1, 2)`) → ③ DAQ 필터가 이번 초에 보낼지 선택 → ④ MQTT `plant/hyd01/tag/TS1` `{t, v, q}`(t는 보낸 실제 시각, `edge.py:110`) → ⑤ connect-ingest가 설비 · 이름을 본문에 넣어 Kafka `plant.tag`(키 `hyd01`) → ⑥ detector가 기울기 · 점수 계산(`feat.1s`)과 패턴 판정 → ⑦ connect-sink가 `tag_1s`에 적재(**품질 q는 버림**) → ⑧ 1분 집계 `tag_1m` → ⑨ Grafana 추세(1초 표를 직접 읽음) → ⑩ 판단 엔진이 증거 SQL로 다시 읽음 → ⑪ process가 재관측에서 다시 읽음. 추적 가능성의 실물: 경보가 자기 근거 값 · 적용한 정의 · 값의 나이를 싣고(3.6절), 처리 기록이 값마다 "어느 시스템 · 어떻게 읽었나"와 도구 호출의 입력/출력 원문을 남기며, `audit` 토픽(5년 보존)에 누가 무엇을 했는지 남는다. **변환에서 사라지는 것**(q, status 원본, 파형)도 계보의 일부로 쓴다.
