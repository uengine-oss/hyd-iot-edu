# 구조 개편 설계 — 다음 개편의 출발점 (2026-10-30 기준)

결함을 고치는 범위를 넘는 구조 문제 셋과 그 설계다. 지금 시스템은 이 개편 없이도 수업에 쓴다. PBL(현업 수준)로 넘어가기 전에 한다.
원칙: 개편은 저장 구조 · 이미지 경계 · 파일 경계를 바꾸므로 수업 중인 강사 스택에 바로 넣지 않고, `workspace/개발/tests` 전체가 통과하는 상태에서 별도 작업으로 한다.

## 1. 사건 · 판단의 원천이 두 곳이다
- **지금**: 처리 건 · 작업 · 승인은 Supabase(PostgreSQL, `procdb.py`), 설비 사건(Incident)과 조치 판단 장부(book) · 감사 기록은 process 메모리의 전역 dict + SQLite 스냅숏 한 덩어리(`main.py`의 `incidents` · `book` · `audit_log`, `store.py` — 사건 · 판단이 바뀔 때마다 수 MB JSON 전체를 다시 쓴다).
- **왜 문제인가**: 두 저장소 사이에 원자성이 없다. 승인 전달은 판단 장부를 먼저 바꾸고 PG를 나중에 커밋한다 — PG가 실패하면 장부만 바뀐 채 남는다. 재시작 때 진행 중 사건을 「재시작 검토」로 바꾸는 규칙(`store.restore`)도 원천이 메모리라 생긴 장치다. 감사 한 줄마다 스냅숏 전체를 쓰는 것이 process 메모리 증가(OOM)의 뿌리였다. 학생이 Supabase Studio로 「처리 건 → 사건 → 판단」을 따라가며 배울 수 없다(사건 · 판단은 DB에 없다).
- **설계**: 사건 · 판단 · 감사를 Supabase 표로 옮긴다 — `process_incident`(사건 상태 기계의 현재 상태 + 이력 jsonb), `process_decision`(판단 장부 한 건 = 한 행, 옵션 · 선택 · 승인 이력), `process_audit`(줄 단위 추가). 상태 전이는 처리 건 잠금(`instance_transaction`) 안에서 같은 트랜잭션으로 쓴다(`rt._transition`이 이미 처리 건 단위 잠금을 잡는다). `machine.py`의 순수 전이 함수는 그대로 두고 저장만 바꾼다. 재관측 마감은 이미 작업 행에 저장하고 폴링이 판정하므로(`service_parts._reobserve`) 메모리 상태가 필요 없다. 옮긴 뒤 `store.py`(SQLite 스냅숏) · 전역 dict · `persist()` 호출 · 재시작 검토 규칙 · SQLite 그래프 반영 대기열(`case_projection_store.py`)을 지운다.
- **옮기는 순서**: ① 표 만들기(마이그레이션, 기존 스냅숏을 읽어 한 번 옮기는 SQL 함수 포함) ② 읽기를 표로(포털 `/api/incidents` · `/api/decisions`) ③ 쓰기를 표로 + 같은 트랜잭션 ④ 스냅숏 삭제. 단계마다 테스트(처리 건 + 사건 + 판단을 한 트랜잭션에서 바꾸다 중간에 실패시키면 셋 다 그대로인가).
- **참고**: ProcessGPT(process-gpt-vue3)는 처리 건 · 작업 · 이벤트를 모두 Supabase 표에 둔다(`bpm_proc_inst` · `todolist` · `events`) — 이 저장소의 처리 건 쪽은 이미 그 모양이고, 사건 · 판단만 남아 있다.

## 2. 워커 이미지가 process 코드를 통째로 복사한다
- **지금**: `it/agent-worker/Dockerfile`이 `it/process/procsvc`(파이썬 107개 파일, 약 3만 줄)를 통째로 복사한다. 워커 모듈 12개가 그중 일부만 가져온다 — `procdb`(작업 점유 · 결과 저장) · `agents_store` · `mcp_secrets` · `mcp_check` · `result_correction` · `task_deferral` · `work_rules` · `engine` · `ask` · `course_ledger`(관문 장부 상수) · `course_policy`(녹화 목록 점검이 읽는 AI 자리 목록). 두 이미지가 같은 코드를 다른 라이브러리 판(fastapi · neo4j)으로 돌린다.
- **왜 문제인가**: process를 고칠 때마다 워커 이미지도 다시 빌드된다. 워커가 쓰지 않는 서버 코드(라우트 · 관문)까지 워커 컨테이너에 들어가 「무엇이 워커의 계약인가」가 코드에서 안 보인다. import 범위가 넓어 한 파일 이동이 다른 서비스의 기동 실패로 이어진다(2026-10-30 실측: agent 서비스의 LLM 도우미 모듈을 지운 뒤 dmn-mcp가 그것을 가져오다 기동 실패 — 지금은 `workspace/개발/tests/test_service_images.py`가 서비스마다 이미지에 넣는 폴더만으로 진입 모듈을 가져와 이런 경우를 잡는다).
- **설계**: 워커와 process의 계약을 패키지 하나로 뺀다 — `common/hydwork/`(작업 점유 · 결과 저장 · 이벤트 기록 SQL, 폼 계약, 에이전트 설정 읽기, MCP 비밀값 풀기, 결과 교정 규칙, 관문 장부 상수). process와 워커가 둘 다 이 패키지를 쓰고, 워커 이미지는 `hydcommon` + `hydwork` + `worker`만 복사한다. 수업 경계 판정은 이미 서버 API(`POST /internal/worker/course-decision`)로 읽는다. 워커의 서버 쪽 일(관문 토큰 · 수업 판정 · 도구 실행 자격)은 지금처럼 process 내부 API.
- **옮기는 순서**: ① 워커의 `from procsvc …`를 모두 모아 `hydwork`로 옮길 함수 목록 확정 ② 옮기고 procsvc는 그 패키지를 가져다 씀 ③ 워커 Dockerfile에서 procsvc 복사 삭제 ④ `test_service_images.py`가 워커 이미지를 procsvc 없이 가져오는지 본다.

## 3. 거대 파일
- **지금(2026-10-30 줄 수)**: `instances.py` 1,860줄(처리 건 런타임 전부), `main.py` 1,339줄(라우트 수십 개 + 사건 처리 + Kafka 소비 + 지식 그래프 질의), `instance_mode.py` 1,250줄(조립 + 라우트), `bpmn_import.py` 1,155줄. 포털 `caseRecord.js` 981줄 · `instances.js` 885줄 · `hitl.js` 859줄.
- **설계(파일을 기능 단위로, 동작은 그대로)**: `main.py` → `app.py`(조립만) · `incidents_api.py` · `kg_api.py` · `kafka_source.py`. `instances.py` → `runtime.py`(시작 · 진행 · 잠금) · `human_steps.py`(제출 · 승인 · 거절) · `service_steps.py`(명령 · 재관측 · 작업지시). `instance_mode.py`는 조립과 라우트를 나눈다. 포털은 처리 건 화면이 이미 나뉜 선(`instances.js` 목록 · 차례, `caseRecord.js` 기록, `trace.js` 처리 과정)을 따른다.
- **원칙**: 쪼개기 전에 그 기능의 테스트가 있어야 한다(`workspace/개발/tests`의 모듈별 테스트가 바탕). 쪼갠 뒤 옛 파일 이름 검색 0.
