## 2.1 비즈니스 프로세스 · Task · End-to-End

**(가) 표준 개념** [일반]
- 비즈니스 프로세스(Business Process): 조직이 어떤 결과(고객 · 내부에 가치 있는 산출물)를 내기 위해 수행하는 관련 활동의 순서 있는 묶음. 시작 사건이 있고 완료 조건이 있다.
- Task(작업): 프로세스 안의 일의 단위 하나. End-to-End(종단 간) 프로세스: 시작 사건에서 최종 결과까지 전체. Task 하나를 잘해도 전체 완료가 보장되지 않는다.
- BPM(Business Process Management, 업무 프로세스 관리)의 생애주기: 분석(Analysis) → 설계(Design) → 실행(Execution) → 모니터링(Monitoring) → 개선(Optimization). AS-IS는 지금의 방식, TO-BE는 바꾸려는 방식.
- BPMN은 OMG(Object Management Group)가 만든 표기법이고 BPMN 2.0은 ISO/IEC 19510으로도 표준화됐다. [일반] (`process-gpt` README도 「ISO/IEC 19510 process model」이라고 적는다 — [외부 README])

## 3.2 요소별: 표준 정의 · HYD 대응 · 실제 예

**Start Event / End Event** (시작 · 끝 이벤트)
- (가) 시작 이벤트는 프로세스를 여는 사건, 끝 이벤트는 한 갈래를 닫는 사건. 메시지 시작 이벤트(Message Start Event)는 메시지를 받으면 시작한다. [일반]
- (나) HYD: 세 흐름 모두 **메시지 시작 이벤트**(`<bpmn:messageEventDefinition>`), 이름은 「쿨러 과열 경보」 · 「정기 점검 요청」 · 「재고 보충 요청」(`c3_flows.py:90,121,145`). 메시지의 실체는 **경보**다. 정의 JSON에서 시작 이벤트는 `eventDefinition: "message"` + `alertPolicy.patterns`(어떤 경보 패턴이 열고 어떤 회복 기준으로 닫는가). 지식 쪽은 `Event.eventDefinition`(`none · message · timer · escalation`)과 `CORRELATES`(이벤트 → 경보 패턴)(`schema.json:250`).
  - 끝 이벤트는 흐름마다 3개: A `E_end`(정상 · 미달) · `E_rejected`(반려) · `E_notice`(지연 알림 가지의 끝). 지식 쪽 기준 흐름의 끝은 `ev:closed`(종결) · `ev:escalated`(에스컬레이션 종료, `eventDefinition: escalation`).
- (다) 실제 예: 정의 `Event.position`은 `start · boundary · end`뿐이다(`schema.json:250`). 중간 이벤트(Intermediate Event)는 `position`에 없고 가져오기에서도 거절된다(아래 「Timer」).

**Activity / Task** (작업) — 사람 · 에이전트 · 시스템의 구분이 핵심이다
- (가) Activity는 프로세스 안에서 수행되는 일. Task는 더 쪼개지지 않는 Activity. 종류: User Task(사람) · Service Task(시스템 호출) · Script Task · Business Rule Task(판단 규칙 호출) · Manual/Send/Receive Task. [일반]
- (나) HYD가 엔진에서 가르는 방법 (`R/it/process/procsvc/engine.py:33-54`):
  - 사람 작업 = `userTask`/`manualTask` 이면서 `agentMode`가 없는 것(`is_human`).
  - **에이전트 작업 = `userTask` + `agentMode`(`DRAFT`|`COMPLETE`) + `orchestration: cliagents`**(`is_agent`). 제품 ProcessGPT 와 같은 모양이다. 옛 정의의 `businessRuleTask`+`agentMode`도 계속 돈다(`engine.py:36-39`, `R/문서/시스템/참조/REPO_GAP.md` 6절 B5).
  - 시스템 작업 = `serviceTask`/`scriptTask`/`sendTask`. `orchestration: hyd-process`(process 서비스가 직접 실행)(`engine.py:57`).
- (다) **같은 처리 건의 단계 표** [기록] `c3_cooling.32aca7de-…` 의 todolist(작업함 행):

| `T_cmd` | 냉각 명령 | 시스템 | `sys:scada` | `incident:command` | `hyd-process` | DONE | 1.1초 |
| `T_reobs` | 재관측 | 시스템 | `sys:process` | `incident:reobserve` | `hyd-process` | DONE | 60.2초 |

**Gateway** (게이트웨이)
- (가) 흐름이 갈라지거나 합쳐지는 지점. 배타(Exclusive, XOR): 조건이 참인 하나로 간다. 병렬(Parallel, AND): 모두 간다. [일반]
- (나) HYD: 배타 · 병렬 둘을 읽는다(`bpmn_import.py:37`, `Gateway.gatewayType` = `exclusive · parallel`). 조건은 **작은 식**이고 화이트리스트 AST 로 평가한다. 자연어 조건을 LLM 이 판정하는 방식은 일부러 지원하지 않는다(「결정은 결정론」, `engine.py` 머리말, `R/문서/시스템/5_결정_기록.md` 3 · 12). 조건 선이 모두 거짓이면 **기본 흐름**(default)으로 간다. 판정은 `gateway_decisions`로 단계 행에 기록된다(`engine.py:733-748`).
- (다) 실제 예 — A 흐름 분기 둘 (`R/students/flows/cooling-emergency.mapping.json`의 `flows`):

| 분기 | 선 | 조건 |
|---|---|---|
| 승인? (`G_approved`) | `F_approved` (이름 「승인」) | `approval == '승인'` |
| | `F_rejected` (이름 「거절」) | 그 밖의 경우(`default: true`) |
| 유온 정상? (`G_ok`) | `F_yes` (「예」) | `recovered == True` |
| | `F_no` (「아니오」) | 그 밖의 경우(기본) |

  - 조건에 쓰는 변수 `approval` · `recovered`는 앞 단계가 내놓은 값이다(`approval` ← `T_approve`, `recovered` ← `T_reobs`, 2.3절 변수 표). 안내문 표기가 `recovered == True`(대문자 T)인 것은 시스템 표기이고, 사전 검사 시험이 지킨다(`final-verify.md` 2절).

**Sequence Flow** (시퀀스 흐름) — 요소를 잇는 화살표. A 15개. 분기 뒤의 선만 조건(`conditionExpression` 대신 포털 「분기 조건」 칸)과 이름(승인 · 거절 · 예 · 아니오)을 갖는다. 끊긴 선(출발 · 도착이 없는 선)은 가져오기 때 「끊긴 선」 문제로 잡힌다(`bpmn_import.py:236-244`). 되돌아가는 선(루프)은 빠져나갈 배타 분기가 있어야 하고, 되돌아가는 선 안의 병렬 분기는 실행하지 않는다(`bpmn_import.py:878-889`).

**Pool · Lane** (풀 · 레인 — 책임자 구분)
- (가) 풀(Pool)은 참여자 하나의 영역, 레인(Lane)은 풀 안의 책임 구분(역할 · 부서 · 시스템). [일반]
- (나) HYD: **풀은 하나만** 읽는다. 풀이 둘 이상이면 「풀(참가자)이 N개입니다 — 한 풀 안에 칸(레인)으로 나눠 그리세요」로 거절(`bpmn_import.py:131-140`). 레인은 가장 안쪽 칸이 담당이다(`bpmn_import.py:258-266`). 칸 이름이 역할 이름과 같으면 그 역할로 자동 연결, 사람이 바꿀 수 있다(`:409-411`). 레인과 단계 부품의 담당이 다르면 사전 검사가 알린다(`:641`).
- (다) 실제 예: 참조 흐름의 칸은 고정 셋 **담당자(`L_person`) · 에이전트(`L_agent`) · 시스템(`L_system`)**. A에서 담당자 칸에 `T_approve` · `G_approved`, 에이전트 칸에 `Start` · `T_agent`, 시스템 칸에 나머지 전부(`cooling-emergency.bpmn:7-30`). 처리 건에 붙는 역할 바인딩 [기록]: `AI 에이전트(sys:agent)` · `SCADA(sys:scada)` · `프로세스(sys:process)` · `CMMS(sys:cmms)` · `운전원(role:operator)`. 지식 쪽: `Task -PERFORMED_BY-> Role|System`(「BPMN 레인」)(`schema.json` 관계 `PERFORMED_BY`).
- 참고: bpmn.io 가 만든 `.bpmn`의 프로세스는 `isExecutable="false"`다(`cooling-emergency.bpmn`). 포털 가져오기는 이 속성으로 거절하지 않는다(가져와 등록 · 배포 · 완주가 검증됨, `final-verify.md` 4.4). 지식 클래스 `Process.isExecutable`은 별개의 속성이다.

**Message Flow** (메시지 흐름)
- (가) 서로 다른 풀 사이의 메시지 전달선(점선 화살표). [일반]
- (나) HYD: **메시지 흐름을 그림에서 읽지 않는다**. 가져오기 코드에 `messageFlow` 처리가 없다(`bpmn_import.py` 전체 검색). 풀이 하나만 허용되므로 풀 사이의 메시지 흐름을 그릴 일이 없다. 「메시지」는 두 곳에만 나온다: (1) 메시지 시작 이벤트(경보가 메시지 역할), (2) 서비스 단계가 부르는 메일 등 외부 호출(`svc:mcp-call` · 승인 뒤 MCP 호출).
- 교재: Message Flow는 [일반] 개념으로 설명하고, 「HYD는 풀을 하나만 쓰므로 그리지 않는다」를 명시한다. 실습에서 그리게 하지 말 것.

**Timer · Boundary Event** (타이머 · 경계 이벤트)
- (가) 경계 이벤트(Boundary Event)는 작업 테두리에 붙어 그 작업이 진행 중일 때 발생하는 사건에 반응한다. 중단형(interrupting, 실선)은 작업을 끊고 자기 가지로 간다. 비중단형(non-interrupting, 점선)은 작업을 계속 두고 **별도 가지**를 연다. 타이머 이벤트는 기간(duration) · 날짜(date) · 반복(cycle)으로 정한다. [일반]
- (나) HYD: 경계 **타이머**만 지원. 기간(`timeDuration`, ISO 8601 `PT10M`)만 쓰고 날짜 · 반복 타이머는 「실행하지 않습니다」로 거절(`bpmn_import.py:206-211`). 비중단형(`cancelActivity="false"`)을 지원한다 — 「멈추지 않는(점선) 경계 타이머 = 알림 가지」(`bpmn_import.py:195-205,748-751`). 비중단형은 엔진에서 「두 번째 토큰」으로 다룬다(`engine.py:537-540,551`). 기다림은 **작업의 경계 타이머로만** 그린다(중간 타이머 이벤트는 거절).
- (다) 실제 예: 승인 지연(`B_overdue`)은 `T_approve`에 붙은 점선 타이머, 기한 `PT10M`. 시간 배율 20에서 10분은 **30초**다(`c3_flows.py:54` 「사람 응답 타이머라 배속만 적용」). [기록] 무응답 경우: 승인 단계가 열린 뒤 30.8초에 타이머가 발사돼 `T_notice`(결과 보고, 결과 「승인 지연」)가 `DONE`, 승인 단계는 계속 `IN_PROGRESS`. 이때 처리 건에는 열린 단계가 **둘**이다(`T_approve` 진행 + 알림 가지) — 「토큰이 둘」의 실물.
  - 반대 예(끊는 타이머, 기준 흐름): `ev:select-timeout`(선택 시간 초과, `PT10M`)이 `task:select`에 붙어 `task:escalate`(상급자 호출)로 간다(`anomaly_response_v22.json`).

**병렬 · 하위 프로세스** — 개념만 소개, 실습 구현을 주장하지 않는다 (실라버스 문구 그대로)
- 병렬 게이트웨이: 엔진 · 가져오기가 지원한다(`engine.py:659-676,745`; 분기 뒤 합류는 모든 경로가 올 때까지 기다림). 단 **세 시나리오 흐름에는 쓰이지 않는다**. 게이트웨이 없이 갈라지는 선은 등록 거부(「uncontrolled split」, `REPO_GAP.md` 6절 A6).
- 하위 프로세스(`subProcess`) · 호출 활동(`callActivity`) · 포괄(`inclusiveGateway`) · 이벤트 기반 분기 · 복합 분기 · 중간 던지기/받기 이벤트 · 트랜잭션: **실행하지 않음**, 가져오기에서 사유와 함께 거절(`bpmn_import.py:38-48`). 예: 「하위 프로세스는 아직 실행하지 않습니다 — 펼쳐서 한 흐름으로 그리세요」.
- 제품 ProcessGPT 는 하위 프로세스 · 다중 인스턴스 등을 지원하고 HYD는 없다(`REPO_GAP.md` 5절). → 11일차 경계 설명에 쓴다.

## 4.1 프로세스 정의와 인스턴스 (Process Definition / Process Instance)

**(가)** 정의(Definition): 흐름의 설계도(요소 · 선 · 조건 · 역할). 인스턴스(Instance): 그 설계도에 따라 실제로 도는 한 건. 한 정의에서 인스턴스가 여러 개 나온다. 프로세스 엔진(Process Engine)이 인스턴스를 진행시킨다. 오케스트레이션(Orchestration): 중앙의 조정자(여기서는 엔진)가 단계 순서와 호출을 이끄는 방식. [일반]

**(나) HYD 대응**

| 개념 | HYD 이름 | 근거 |
|---|---|---|
| 정의 | 정의 JSON(`activities` · `events` · `gateways` · `sequences` · `roles` · `data`). 표(DB) `proc_def` · `proc_def_version`(판본은 바꿀 수 없음) | `R/it/supabase/migrations/20261003000001_process_engine.sql:74,93`, `engine.py` 머리말 |
| 인스턴스 | 포털 말 「**처리 건**」. 표 `bpm_proc_inst`. 상태 `NEW · RUNNING · COMPLETED · CANCELLED` | `…process_engine.sql:124`, `schema.json:1803` |
| 작업(Task)의 실행 단위 | 포털 말 「**단계**」. 표 `todolist`의 행 하나 = **작업함 행(work item)**. 지식 쪽 클래스 `WorkItem` | `…process_engine.sql:154`, `schema.json:1883` |
| 단계 상태 | `NEW · TODO · IN_PROGRESS · SUBMITTED · PENDING · DONE · CANCELLED` | `schema.json`(`WorkItem.status`) |
| 이벤트 기록 | 표 `events`(에이전트가 한 일의 실시간 기록) | `…process_engine.sql:219` |
| 판본 고정 | 처리 건이 열릴 때 판본이 고정된다. 이미 열린 처리 건은 자기 판본으로 끝까지 간다 | `flow_deploy.py:1-22` |

용어 정리(교재용): 표준 BPMN의 「Task」는 정의의 요소, HYD의 「단계」(work item)는 그 요소가 한 처리 건에서 실제로 실행되는 **행**이다. 하나의 정의 요소 `T_agent`가 처리 건마다 행 하나(`todolist`)가 된다. 반려 후 재작업이면 같은 요소의 행이 세대(`generation`)별로 더 생긴다(`WorkItem.generation`, `supersedes_id`).

**(다) 실제 예 [실측]** — 정의와 판본: 
```
curl -s localhost:8080/api/process/definitions
→ c3_cooling 판본 9개(1…9, 최신 9 "냉각 긴급 대응"), c3_pm 9개, c3_spare 9개 — 모두 deployed:false
→ anomaly_response 2.2 "설비 이상 조치" deployed:true
```
**[기록]** 인스턴스가 정의 판본을 쓴 모습: `proc_def_id: "c3_cooling"`, `proc_def_version: "9"`, `proc_inst_name: "냉각 긴급 대응 HYD-01"`, `start_event_id: "ALT-hyd01-0026-767a"`(처리 건이 어느 경보로 열렸는지), `status: "COMPLETED"`, `end_event: "E_end"`.

중복 방지: 같은 경보로 처리 건이 두 번 열리지 않는다. `start_definition`이 `(테넌트, 정의, event_id)`로 이미 있는 처리 건을 찾는다(`R/it/process/procsvc/instances.py:229-256`).

## 4.2 Token 의 진행 개념

**(가)** [일반] BPMN 의 실행 의미는 토큰(Token)으로 설명한다. 시작 이벤트에서 토큰이 생겨 선을 따라 움직이고, 작업이 끝나면 다음으로 넘어가며, 병렬 게이트웨이에서 나뉘고 합쳐지며, 끝 이벤트에서 소멸한다. 토큰이 어디 있는지가 「프로세스가 지금 어디인가」다.

**(나) HYD 대응 — 이름이 다르다**
- **`token`이라는 필드 · 객체는 없다.** 코드에 낱말은 주석 한 곳뿐이다(「its path is a second token」, `engine.py:539`).
- 토큰의 위치에 해당하는 것: ① `bpm_proc_inst.current_activity_ids`(지금 열려 있는 단계 id 목록), ② 단계 행의 상태(`IN_PROGRESS`가 토큰이 있는 곳), ③ `flow_state.activity_arrivals`(각 단계에 흐름이 닿은 시각)와 `end_arrivals`(끝 이벤트에 닿은 기록). 병렬 합류는 모든 들어오는 경로가 올 때까지 기다린다(`engine.py:638-676`).
- 엔진 순서(제품 `handle_workitem`과 같은 모양, `engine.py:502-548`): 단계 결과를 변수에 합침 → 나가는 조건 판정(`gateway_decisions`) → 조건이 안 맞으면 `PENDING` + 사유 / 맞으면 `DONE` → 안 간 가지와 붙은 경계 이벤트를 `CANCELLED` → 다음 단계에 도달시킴.

**(다) 실제 예** [기록] 토큰이 둘인 순간(무응답 경우의 스냅샷): `current_activity_ids: ["T_approve"]`인 채로 점선 타이머 가지가 `T_notice`를 `DONE`으로 만들었다. 정상 승인 경로의 토큰 이동은 단계 시각으로 읽힌다:

| 단계 | 닿은 시각(`activity_arrivals`) | 끝난 시각 |
|---|---|---|
| `T_agent` | 15:22:46.236 | 15:24:08.508 |
| `T_approve` | 15:24:08.508 | 15:24:09.795 |
| `T_cmd` | 15:24:09.795 | 15:24:10.879 |
| `T_reobs` | 15:24:10.880 | 15:25:11.093 |
| `T_wo` | 15:25:11.093 | 15:25:12.060 |
| `R_ok` | 15:25:12.060 | 15:25:12.348 (→ `E_end`) |

교재의 「토큰이 선을 따라 움직인다」 그림에 이 시각들을 그대로 얹을 수 있다. 단, 「토큰」이라는 이름은 HYD 화면 · API 어디에도 나오지 않는다고 명시할 것.

## 4.3 변수와 결과 전달

**(가)** [일반] 프로세스 변수(Process Variable)는 인스턴스가 들고 다니는 데이터. 앞 작업의 출력이 변수가 되어 뒤 작업의 입력이나 분기 조건이 된다.

**(나) HYD**: `bpm_proc_inst.variables_data`가 제품 모양의 목록 `[{key, name, value}]`이고, 같은 인스턴스에 `variable_sources`가 **각 변수를 어느 단계가 만들었는지**를 기록한다(`engine.py` 머리말, `set_variables` 호출 `engine.py:515-518`). 단계가 선언한 `outputData`에 있는 키만 합쳐진다.

**(다) 실제 예** [기록] 처리 건 `c3_cooling.32aca7de-…` 의 변수와 출처:

| 변수 | 값(요약) | 만든 곳(`variable_sources`) |

## 4.4 User Task · Service Task · HYD 에이전트 단계가 실제로 실행되는 방식

**에이전트 단계가 실행되는 길** [저장소]
1. 흐름이 에이전트 단계에 닿으면 행이 `IN_PROGRESS`(`agent_mode: COMPLETE`, `agent_orch: cliagents`)가 된다.
2. **워커**(`it/agent-worker`)가 `fetch_pending_task`(DB 함수)로 그 행을 집는다(`draft_status` → `STARTED`). 호스트 PC 또는 컨테이너에서 도는 Claude Code 를 headless 로 부른다 — 제품 `process-gpt-cli-agent`와 같은 구조(`agent_orch = cliagents`). 근거: `R/it/supabase/migrations/20261004000004_process_lock_order.sql:43`, `R/문서/시스템/참조/REPO_GAP.md` 1절 「7 · 8」, [외부 README] `process-gpt/services/cli-agent/README.md`(「delegates a work item to a CLI coding agent — Claude Code or Codex」).
3. 워커는 작업 폴더에 지시문 · 스킬 · 도구 설정을 놓고 에이전트를 실행하며, 도구 호출 하나하나를 `events`에 쓴다(`task_started` · `tool_usage_started/finished` · `task_working` · `task_completed`).
4. 결과를 `save_task_result`로 내면 행이 `SUBMITTED`. **엔진 폴링**(2초마다)이 `SUBMITTED`를 집어 변수에 합치고 다음 단계를 연다 — 워커는 흐름을 진행시키지 않는다(`R/it/process/procsvc/instance_mode.py:45`, `REPO_GAP.md` 1절 「11」).

# 11. 확인 못 한 것

1. **ProcessGPT 제품 화면 · 동작**: 이 컴퓨터에 제품 저장소(`process-gpt`, `process-gpt-all`, `process-gpt-vue3-hli` 등)는 있으나 띄우지 않았고 README 수준만 읽었다. 제품의 인스턴스 화면 · 작업함 · 정의 편집기의 실제 모습, 제품의 권한 · 로그인 · 멀티테넌시 세부는 확인하지 못했다. `processgpt-flows.md` · `processgpt-gaps.md`(HYD 쪽 제품 조사, 각 15만 자 안팎)는 전문을 읽지 않았다.
2. **수업 흐름의 새 [실측]**: 지금 스택은 기준 흐름이 열린 상태(학생 흐름 미배포)이고, 수업 흐름 값은 2026-10-10 밤 [기록]이다. 새로 돌리려면 `scripts/c3_flows.py deploy`와 워커가 필요하고(쓰기 · 잠금), 이번 범위가 아니었다. 이 [기록]의 상당수는 `.evidence`(gitignore)에 있어 저장소에는 요약(`final-verify.md`)만 올라간다.
3. **Neo4j 직접 질의**: 이번에는 Neo4j를 질의하지 않았다. 프로세스 계층 클래스는 `schema.json` · `instances.cypher`로만 확인했다. 현재 그래프(전체판) 안의 `ProcessInstance` · `WorkItem` 수는 읽지 않았다(2~4일차 사실표 2.7절은 노드 1,540 · `ProcessInstance` 66 등을 적었다).
4. **`GET /api/instances` 대량 조회**: 시도했으나 응답이 오래 걸려 중단했다. 실행 중 처리 건 목록의 [실측]은 없다. `GET /api/scenario/status`로 B · C 의 시작 값(재고 · 운전시간)과 마지막 처리 건만 읽었다.
5. **9일차 92행(간단 승인 절차) 정답 파일**: 저장소에 없다.
6. **AS-IS/TO-BE · BPM 사이클 자료**: 저장소에 없다(검색).
7. **프로세스 지표 · 병목 화면**: 확인하지 못했다. 설비 · 구매 KPI 서비스(`kpi.py`)만 있다.
