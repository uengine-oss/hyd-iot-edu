# 03. 덱 만드는 법

이 문서는 새 일차 · 회차의 덱을 만들거나, 전체를 다시 점검하거나, 실라버스가 바뀌어 덱을 크게 손봐야 할 때 읽는다.

무엇을 어떻게 써야 하는가는 `문서/교재/덱_제작기준.md`(특히 12절 「만들기와 점검」, 13-1 · 13-2절)에 있다. 이 문서는 **작업을 어떤 단계로 나누어 누구에게 맡겼는가**와 그때 배운 것을 적는다. 단계마다 쓴 지시문은 `지시문/`에 있고 쓰임은 `지시문/README.md`에 있다. 이미 있는 덱을 고치는 순서와 명령은 `4_만드는_법_덱_고치기.md`다.

## 1. 통합반 원 덱(새 일차)을 만드는 흐름

```
사실 조사 → 쓰기 → 검토 → 반영 → (여러 일차를 같이 만들었으면) 일차 사이 맞춤
```

| 단계 | 하는 일 | 산출물 | 지시문 |
|---|---|---|---|
| ① 사실 조사 | 실라버스 이론 행의 항목마다 표준 정의, HYD의 대응물과 근거, 교재에 쓸 실제 예를 저장소에서 찾는다. 확인하지 못한 것과 실라버스가 구현과 다른 곳을 따로 모은다. 읽기 전용이다 | `문서/교재/통합반_…_기술사실표.md` | `사실조사_지시.md` |
| ② 쓰기 | 장 목록(제목과 메시지)을 먼저 짜고, 본문 · 노트 · 제작 기준 칸 · 삽화를 쓴 뒤 빌드하고 전 장을 렌더로 본다 | 덱 MD, PPTX, `figures/` | `새일차쓰기_지시.md` |
| ③ 검토 | 쓴 작업자가 검토자 하나를 불러 덱 MD 전체와 렌더 전 장을 보게 한다. 검토자는 고치지 않고 상 · 중 · 하 목록을 낸다 | 검토서(작업 폴더) | `새일차검토_지시.md` |
| ④ 반영 | 쓴 작업자가 상 · 중은 모두, 하는 판단해 반영하고 다시 빌드한다. 기준이나 사실과 어긋나는 제안은 따르지 않고 이유를 적는다 | 고친 덱 | `새일차쓰기_지시.md`의 「검토와 반영」 |
| ⑤ 일차 사이 맞춤 | 용어, 약어 풀네임의 자리, 같은 예의 값을 앞뒤 일차 덱과 대조한다(제작 기준 10 · 12.2절) | 고친 덱 | 따로 없다(`점검반영_지시.md`의 「덱 사이의 결정」이 그 결과다) |

새 덱을 다 만든 뒤 할 일: 제작 기준 13절 현황표, `production/decks/README.md`, `NOW.md`, `3_현황.md`의 숫자를 맞추고(`4_만드는_법_덱_고치기.md` (나) 6), 배포 묶음을 다시 만든다.

## 2. 조립 덱(실전반 일차, 오프라인 회차)을 만드는 흐름

```
계획표 → 조립 → 검토 → 반영 → 과정 전체 맞춤
```

| 단계 | 하는 일 | 산출물 | 지시문 |
|---|---|---|---|
| ① 계획표 | 실라버스 항목마다 통합반 덱의 어느 장을 가져올지 고른다. 덱 전체를 통독하지 않고 스크립트로 `장 번호 \| 유형 \| 제목 \| 메시지` 목록을 뽑아 고른다. 손질할 문구(원문 → 바뀔 문구)와 새로 쓸 장의 명세를 적는다. 읽기 단계라 아무것도 고치지 않는다 | 계획표(작업 폴더) | `실전반계획_지시.md`, `오프라인계획_지시.md` |
| ② 조립 | 계획표를 `조립.py`의 순서표와 손질 목록으로 옮기고, 새 장을 `새장_*.md`에 쓰고, 조립 → 빌드한다. 조립본을 전 장 통독해 정의 없는 용어와 틀린 지시어를 찾는다 | `조립.py`, `새장_*.md`, 덱 MD, PPTX | `실전반쓰기_지시.md`, `오프라인쓰기_지시.md` |
| ③ 검토 | 검토자 하나가 맡은 덱 전부를 본다. 장 하나하나의 문장이 아니라 **조립해서 생긴 문제**를 본다 | 검토서(작업 폴더) | `실전반검토_지시.md` |
| ④ 반영 | 상 · 중을 `조립.py`와 `새장_*.md`에 반영하고 다시 조립 · 빌드한다. 통합반 원문의 결함이면 고치지 않고 보고한다 | 고친 덱 | `오프라인쓰기_지시.md`의 「검토」 |
| ⑤ 과정 전체 맞춤 | 회차 묶음을 나눠 만들었으면 과정 전체를 순서대로 보고 풀네임의 자리, 뒤 회차가 전제하는 것, 겹친 장과 퀴즈, 틀을 맞춘다 | 고친 덱 | `오프라인맞춤_지시.md` |

- 한 작업자가 ①~④를 이어서 할 때는 `오프라인일괄_지시.md`를 앞의 두 문서와 함께 준다.
- 새 `조립.py`의 본보기는 `production/decks/practical/day07/조립.py`(원천이 한 일차)와 `production/decks/integrated-offline/session10/조립.py`(원천이 두 일차)다. 새 장 원고의 본보기는 `production/decks/practical/day07/새장_07일차.md`다.
- 조립 작업자가 통합반 원문의 결함을 보고하면 모아서 원 덱에서 한 번에 고친다(`원덱결함_지시.md`). 그 뒤 조립 스크립트를 모두 다시 돌린다.

## 3. 전체 점검 → 반영 → 재조립의 흐름

```
점검(고치지 않음) → 원 덱 반영 → 조립 덱 재작업 → 배포 묶음과 현황표
```

| 단계 | 하는 일 | 지시문 |
|---|---|---|
| ① 점검 | 덱을 범위로 나눠 점검자에게 준다(지난번은 여섯: 통합반 1~4 · 5~8 · 9~11일차, 실전반 온라인, 통합반 오프라인, 실전반 오프라인). 모든 점검자가 같은 **기준선**(통합반 1일차 온톨로지 단원과 3일차 첫 단원)을 먼저 정독한다. 산출물은 덱별 점수표, 고칠 것 목록, 「뒤로 갈수록 품질이 떨어졌는가」의 답, 확인하지 못한 것이다 | `전체점검_지시.md` |
| ② 조율 | 여섯 결과를 모아 **덱 사이의 결정**을 먼저 정한다(같은 대상의 이름, 값의 벌, 일차 표기 등). 사용자 결정이 필요한 것은 묻는다 | `점검반영_지시.md`의 「덱 사이의 결정」이 지난번의 결과다 |
| ③ 원 덱 반영 | 통합반 원 덱을 일차 묶음으로 나눠 고친다. 조립 덱 점검이 「원문」이라고 표시한 항목도 여기서 고친다. 제목을 바꾸거나 장을 지우면 「조립에 영향」 표로 보고받는다 | `점검반영_지시.md` |
| ④ 조립 덱 재작업 | 원 덱이 다 고쳐진 뒤에, 과정별로 조립을 다시 돌려 멈추는 곳을 고치고 조립 덱의 점검 결과를 반영한다 | `조립재작업_지시.md` |
| ⑤ 마무리 | 배포 묶음, 현황표의 숫자, `NOW.md` 4.7절 | `4_만드는_법_덱_고치기.md` (나) 5 · 6 |

화면만 따로 보려면 `화면확인_지시.md`를 쓴다(내용은 보지 않고 넘침 · 겹침 · 깨진 그림만 본다).

지난 점검의 결과 요지는 `3_현황.md` 5절에 있다. 다음 점검은 그 표와 견주면 된다.

## 4. 실라버스가 바뀌었을 때

실라버스는 사용자가 직접 쓴다. 바뀐 xlsx를 받으면 고치기 전에 **무엇이 달라지는지 먼저 사용자에게 말한다**(`5_결정_기록.md` 1절).

| 바뀐 것 | 할 일 |
|---|---|
| 이론 행의 제목 · 상세 내용 | 그 행에 해당하는 단원과 대조한다(항목 → 장 번호). 빠진 항목이 생겼으면 사실표에 근거가 있는지 보고 장을 더한다. 근거가 없으면 사실 조사부터 한다 |
| 이론 행의 시간 | 단원 본문 장수의 기준(분 ÷ 1.5, ±15 %, 모자라면 안 됨)을 다시 맞춘다 |
| 실습 행의 추가 · 삭제 · 제목 | 실습 간지와 설명 장(2장)을 더하거나 빼거나 고친다. 실습 가이드의 목록(`실습_목록.md`)도 다시 뽑는다 |
| 이론 ↔ 실습 구분 | 덱의 틀과 목차의 구분을 바꾼다(지난 예: ProcessGPT 이론 단원 → 시연 실습) |
| 통합반 시트가 바뀌었다 | 원 덱을 고친 뒤 조립 덱까지 다시 만든다(`4_만드는_법_덱_고치기.md` (나)) |
| 실전반 · 오프라인 시트만 바뀌었다 | 그 덱의 `조립.py` 순서표와 `새장_*.md`만 고친다 |

저장소의 xlsx를 새 파일로 바꾸고, 제작 기준 0절과 `NOW.md` 1절의 「실라버스」 줄이 가리키는 파일 이름이 맞는지 본다.

## 5. 일을 나누는 방식

| 무엇 | 어떻게 했는가 |
|---|---|
| 지시는 파일로 | 공통 지시를 문서 하나로 쓰고, 작업자마다 다른 것(맡은 범위, 산출물 이름)만 프롬프트에 적었다. 같은 일을 여럿에게 줄 때 기준이 어긋나지 않는다 |
| 읽기와 쓰기를 가른다 | 계획 · 검토 · 점검은 「아무것도 고치지 않는다」로 맡기고 산출물을 작업 폴더에만 쓰게 했다 |
| 모델 | 읽기 · 계획 · 검토 · 문서는 가벼운 모델, 쓰기는 Opus. fable 모델은 쓰지 않는다(`5_결정_기록.md` 3절) |
| 조율자의 몫 | 커밋과 push, 덱 사이의 결정, 현황표와 인계 문서, 사용자에게 묻는 일. 작업자는 커밋하지 않는다 |
| 보고는 짧게, 형식을 정해 | 장수(실라버스 분과 나란히), 따르지 않은 제안과 이유, 눈으로 본 범위와 못 본 장을 반드시 받는다 |
| 렌더는 차례로 | 렌더는 한 번에 하나만 돈다. 작업자 여럿이 같이 렌더하면 서로 기다린다. 작업자에게 「기다리는 것이 정상, soffice를 죽이지 않는다」고 적어 준다 |
| 끊김에 대비 | 긴 작업은 단위(회차) 하나가 끝날 때마다 진행 파일에 한 줄씩 적게 했다 |

## 6. 이 작업에서 배운 것

| 배운 것 | 다음에는 |
|---|---|
| 일차를 동시에 따로 쓰면 덱 사이의 용어와 값이 어긋난다. 5~11일차를 따로 쓴 결과 같은 산출물이 「추천안 / 조치 카드 / 추천 카드 / 제안」으로, 같은 경보가 두 이름으로 불렸고, 같은 장면을 두 일차가 다시 설명했다 | 쓰기 전에 **용어 기준을 먼저 준다**(제작 기준 8절 「덱 사이의 용어」가 그 결과다). 끝에 일차 사이 맞춤을 반드시 한 번 한다 |
| 같은 사건의 값이 실행 회차에 따라 두 벌이었다(1~8일차와 9~11일차). 말없이 바뀌어 조립 덱에서는 한 회차 안에서도 섞였다 | 사실 조사 때 「어느 실행 기록의 값인가」를 사실표에 적는다. 벌이 바뀌는 자리에서 한 번 밝힌다 |
| 정리(Wrap-up) 단원이 약해지기 쉽다. 표 · 비교 · 카드가 이어지고, 앞 장을 그대로 되풀이하고, 노트가 한두 문장이 된다 | 정리 단원에도 그림을 두고, 「되풀이」가 아니라 「잇는」 관점의 장으로 쓴다. 검토 때 정리 단원을 따로 지목한다 |
| 검토 뒤 고친 장만 다시 보면 최종본 전 장을 본 사람이 없게 된다 | 마지막에 전 장 화면 확인을 따로 한다(`화면확인_지시.md`). 보고에는 「못 본 장」을 번호로 받는다 |
| 조립 덱은 장을 골라 온 탓에 정의 없는 용어가 생긴다. 정의하던 장이 빠지면 뒤 장의 용어 · 값 · 번호가 설명 없이 나오고, 퀴즈의 근거가 화면에서 사라지고, 실습을 받치는 이론이 없어진다 | 새로 쓰지 말고 통합반의 정의 장을 더 가져와 메운다(단원이 한두 장 넘어도 된다). 조립본은 전 장을 통독한다 |
| 가져온 장의 「지난 시간」 「N일차에」 「앞에서 본」은 다른 과정에서 틀린 말이 된다 | 손질 목록으로 그 과정의 구성에 맞춘다. 원 덱은 되도록 일차 번호를 쓰지 않는다 |
| 약어의 풀네임은 「그 과정에서 처음 나오는 자리」가 과정마다 다르다 | 회차 묶음을 나눠 만들 때는 새로 붙이지 않게 하고, 과정 전체 맞춤에서 한 번에 붙인다 |
| 원 덱의 제목을 바꾸면 조립 스크립트가 멈추고, 문구를 바꾸면 손질 원문이 어긋난다 | 원 덱을 고칠 때 「조립에 영향」 표를 받는다. 고치기 전에 `조립.py`들을 문자열로 검색한다 |
| 실습 설명 장의 메시지가 「이 실습을 마치면 …」 한 틀로 몰린다 | 일차마다 한두 장은 산출물을 주어로 쓴다 |
| 실습 설명에서 실라버스의 한 구절(「기준 흐름으로 되돌린다」, 「기준 그래프와 랩 그래프는 다르다」)이 빠지기 쉽다. 반대로 근거 없는 구절(「복구 상태 확인」)은 넣으면 안 된다 | 학생이 실제로 하거나 알아야 하는 것은 한 칸 · 한 줄로 싣고, 근거가 없으면 싣지 않고 보고한다 |
| 점검자의 근거 확인은 표본이다 | 「제작 기준 칸의 근거가 헛것인가」를 표본으로 대조하게 한다. 지난번에는 헛근거가 없었다 |
| 검토 · 점검의 지적이 제작 기준과 부딪칠 때가 있다(실라버스의 「시뮬레이션임을 명시」가 덱에 없다는 지적과 제작 기준 3절의 가상 강조 금지) | 작업자는 기준과 어긋나는 제안을 따르지 않고 이유를 보고에 적는다. 실라버스 문구와 기준이 부딪치면 조율자가 사용자에게 묻는다 |
