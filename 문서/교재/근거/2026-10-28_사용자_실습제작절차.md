# 사용자 지시 — 실습 한 개 제작 절차 (2026-10-28, 원문)

A 기준정리 세션에 사용자가 준 원문이다. 기준 정리 장부의 출처(`사용`)로 쓴다. 사용자 덧붙임: 「대충 이런데 니가 보고 직접 판단하고 상호충돌 생기는 건 나한테 물어보고 내가 판단해줄게. 우선순위를 일단 실습 관련도」 「그 A만 하지 말고 모든 문서 다 정리 대상입니다」.

0. 시작 전: 내가 할 일을 스스로 정한다

* 전독: `기준_실습대본.md` 전문, 그 문서가 가리키는 `기준_이론대본.md`의 발화 조항, `기준_실습랩.md`, `2_기준.md`, 촬영 안내, 인계 기준 9항을 처음부터 끝까지 읽습니다. 「확인 일시 / 연 화면」 같은 기록 틀도 확인합니다. 특히 1회차 확정 실습 대본을 읽고 「실제 강사가 이렇게 말한다」는 감을 잡습니다. 윤문 기준을 사용자에게 다시 묻지 않습니다.
* 인계의 옛 완료 표시는 믿지 않습니다. 「음성 생성」이라고 적혀 있어도 실제 파일을 열어 확인합니다.

1. 실라버스로 뼈대를 잡는다

* 실라버스 행의 상세 문장을 한 줄씩 떼어 대조표를 만듭니다. 실전 2-2라면 다음 항목들입니다.
   * 설비·구성 요소·부품·문서의 연결 펼치기
   * 노드의 식별자·속성·관계 방향 확인
   * 한 부품을 쓰는 설비 찾기
   * 「연결이 있다」와 「재고·공급 조건이 확보됐다」의 구분
   * 다음 랩에서 공급 자료로 답할 질문 정하기
항목마다 영상의 어느 구간에서, 어떤 설명과 화면으로 다룰지 적습니다. 빈칸이 있으면 다음 단계로 가지 않습니다.
* 실라버스보다 더 좋은 흐름이나 내용이 보이면, 무엇을 왜 바꾸는지 먼저 말씀드리고 고칩니다.

2. 앞 이론과 잇는다

* 바로 앞 이론 대본을 열어 연결점을 찾습니다. 실전 2-2는 이론 18장(공통 노드로 둘지, 설비마다 나눌지)과 19~21장(공급 관계에 딸린 값, 비승인 공급사)이 연결점입니다.
* 실습에서 「이론에서 이걸 따졌죠. 실제 지도에는 이렇게 들어가 있습니다」를 화면으로 보여 주게 짭니다.

3. 랩을 강화한다 (장난감 금지)

* 코딩 랩(실전 2-3 등): 리서치(공식 모범 사례, 현업 사례)로 근거를 잡습니다. 재료는 현업 규모로 만듭니다. 다출처 불일치, 품번 변형, 판본 차이처럼 눈으로는 못 맞추고 AI와 코드로 대조해야 풀리는 수준입니다. 포털이 너무 단순하면 포털에 묶이지 않고 재료를 키웁니다. 정답·해결 로직·완성 프롬프트는 주지 않고, 가드레일은 위험한 것만 둡니다.
* 포털 관찰 랩(실전 2-2 등): 코드 과제는 붙이지 않습니다. 대신 「무엇을 보고 어떻게 판단하는가」의 깊이를 채웁니다.

4. 대본: 실제 강사가 차분히 설명하는 말

* 바로 실습에 들어가지 않습니다. 먼저 이렇게 엽니다.
   * 지난 이론에서 무엇을 배웠는지
   * 오늘 무엇을 왜 하는지(현장에서 왜 필요한지)
   * 무엇을 만드는지
   * 무엇으로 맞았다고 판정하는지
* 처음 쓰는 도구는 설명합니다. VS Code, 포털 화면, Codex, 터미널이 처음 나올 때입니다. 통합반은 차근차근, 실전반은 핵심만 짧게 합니다.
* 진행하면서 매번 이어서 말합니다. 어디를 왜 보는지 → 결과가 무슨 뜻이고 왜 그렇게 나왔는지 → 어떻게 확인하는지 → 어디에 쓰는지. 결과를 띡띡 읽기만 하지 않습니다.
* 코딩 랩은 바이브 코딩을 실제로 보여 줍니다.
   1. 파일을 바꾸지 않고 AI와 프로젝트를 파악합니다.
   2. 요구와 기대 답을 내 말로 정합니다.
   3. 계획을 검토합니다.
   4. 작게 구현합니다.
   5. 실행 결과를 원자료와 대조합니다.
   6. 고칩니다.
   7. 저장합니다.
코드는 읽어 검사하지 않고, 결과가 요구에 맞는지로 판단합니다.
* 표기: 식별자·속성 키·관계 영문명은 읽지 않고 뜻으로 말합니다(예: 「P-PMP-SEAL」이 아니라 「펌프 축 씰 키트의 부품 번호」). 「랩 그래프」 같은 제작 용어는 쓰지 않습니다. 「~입니다」만 반복하지 않는 자연스러운 구어체로 씁니다.
* 다 쓰면 처음부터 끝까지 이어 읽으며 스스로 윤문하고 검수합니다.

5. 분량 (C71)

* 내용이 먼저입니다. 실라버스 항목과 설명, 바이브 코딩을 시간과 상관없이 최대한 넣습니다.
* 배정 시간 +10분까지는 괜찮습니다. 그보다 길면 조정합니다.
* 모자라면 문제입니다. 빠진 항목이나 얕은 설명이 없는지 다시 보고 보강합니다. 정말 더 넣을 것이 없을 때만 멈추고, 그 사유를 기록합니다.
* 대기, 느린 타이핑, 같은 말 반복으로 채우지 않습니다.
* 50분 실습이 7분이면 그것은 실습이 아닙니다.

6. 녹음·촬영

* 음성은 비용을 먼저 알리고 만듭니다.
* 촬영은 이미 뚫은 길을 재사용합니다. 코딩 랩 전에는 안 뚫린 길(Codex 채팅, 터미널, 시작 도구 장면, 별도 랩 DB)을 먼저 뚫습니다.

7. 검사: 기술 검사만으로 「완료」라 하지 않는다

* verify·scenes(길이, 싱크, 무음, 오류 화면)는 기술 검사일 뿐입니다.
* 그것과 별도로 수업으로 성립하는지 판정합니다. 대조표 항목이 다 들어갔는지, 설명이 충분한지, 바이브 코딩이 실제로 보이는지, 분량이 C71을 지키는지 봅니다.

8. 마무리

* 가이드에 실제 화면을 넣고, guide.html과 ZIP을 만들고, 학생 경로로 받기 시험(다운로드 → 압축 해제 → 열기 → 실행 → 저장 → 다시 열기)을 합니다.
* 영상은 other-pc에, 문서는 main에 올리고, 완료 표에 커밋·해시·검증 결과를 기록합니다.
