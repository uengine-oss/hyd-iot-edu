### 1.1 Anthropic — Claude Code

**[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)** (확인 2026-10-28)

- 지시는 두 종류다. 프롬프트·`CLAUDE.md`·스킬은 모델이 읽고 판단하는 **비결정적** 지시라 준수가 보장되지 않는다. 반드시 지켜야 하는 것은 hook·deny 규칙·설정 같은 **결정적** 장치로 옮기라고 한다.
- 「Claude가 볼 수 없는 것을 알려라」: 저장소를 읽어 알 수 있는 것은 적지 말고, 회의 결정·머릿속 절차처럼 저장소에 없는 것만 적는다.
- 구체적 프롬프트: 파일·증상·「고쳐진 상태」를 처음에 말한다. 예시로 「재현하는 실패 테스트를 먼저 쓰고 고쳐라」를 든다. 가진 자료(파일·스크린샷·명령 출력)는 설명 대신 그대로 건넨다.
- 요구가 아직 흐리면 Claude에게 **인터뷰를 시켜** 명세(`SPEC.md`)를 쓰게 하고, 새 세션에서 그 명세로 구현한다.
- `CLAUDE.md`는 짧게: 확인 명령, 코드가 오해를 부르는 곳, 저장소에 없는 결정, 두 번 고친 것만.
- **「Claude에게 돌릴 검사를 줘라」**: 통과/실패가 나오는 검사(테스트, 빌드 종료 코드, 출력과 기준 파일 비교 스크립트, 화면 대조)가 없으면 Claude는 「끝나 보이는」 데서 멈추고 사람이 테스트 역할을 하게 된다. 완료 주장에는 **증거(실행한 명령과 출력)**를 요구하라고 한다. 「All tests pass」만으로는 알 수 있는 게 거의 없다는 취지다.
- 명세 대비 검토: 일반 버그 찾기 대신 명세의 요구별 구현 여부를 검토하게 하고 「스타일은 건너뛰라」고 덧붙인다. 문제를 찾으라고 하면 리뷰어는 항상 무언가를 찾아내기 때문이다.
- 세션 조종: 첫 1분을 지켜보고 어긋나면 바로 멈춘다. **두 번 고쳐도 틀리면 세 번째 수정 대신 `/clear` 후 배운 것을 담은 새 프롬프트**를 쓴다. 체크포인트(`/rewind`)는 Claude 파일 도구로 고친 파일만 되돌리며 git을 대체하지 않는다.
- 낡은 조언 목록: 대문자·IMPORTANT 강조, 「think hard」, 「계속해, 게으르지 마」, 구조 설명을 `CLAUDE.md`에 쓰기 등은 이제 불필요하다고 정리한다.

**[Common workflows](https://code.claude.com/docs/en/common-workflows)** (확인 2026-10-28)

- 낯선 코드는 넓은 질문(개요)부터 좁은 질문(특정 흐름 추적)으로 탐색한다. 프로젝트 고유 용어집을 요청하라고 한다.
- 버그 수정: 재현 명령·재현 단계·간헐/항상 여부를 알려 준다.
- 리팩터링은 「작고 시험 가능한 단위로」, 테스트 요청은 「검증하려는 동작을 구체적으로」.
- **Plan before editing**: plan mode에서는 파일을 읽고 계획만 제안하며 승인 전까지 편집하지 않는다.

**[Output styles](https://code.claude.com/docs/en/output-styles)** (확인 2026-10-28)

- 내장 **Learning** 스타일은 설계 판단이 있는 몇 줄을 `TODO(human)`으로 남겨 사용자가 직접 쓰게 하고 기다린다. Explanatory는 선택 이유를 `Insight` 블록으로 설명한다. 둘 다 지시일 뿐 강제가 아니라고 명시한다.

### 1.2 OpenAI — Codex

**[Best practices](https://learn.chatgpt.com/guides/best-practices)** (구 `developers.openai.com/codex/learn/best-practices`에서 308 이동, 확인 2026-10-28)

- 프롬프트를 **목표·맥락·제약·「끝났다」의 모습** 네 부분으로 쓰고 「Done when:」을 명시한다. 관련 파일은 `@`로 붙인다.
- 어렵거나 모호한 일은 코딩 전에 계획(`/plan`). 생각이 흐리면 Codex에게 인터뷰를 시켜 구체화한다.
- AGENTS.md는 짧고 정확하게, **같은 실수가 반복된 뒤에만 규칙을 추가**한다.
- 승인 모드·샌드박스는 기본값에서 시작해 좁게 유지하고, 신뢰된 저장소·특정 작업에서만 푼다.
- 테스트를 쓰거나 고치게 하고, 관련 검사를 돌리고, 최종 동작이 요청과 맞는지 확인하게 한다. 수락 전 diff를 검토한다(`/review` 또는 diff 패널). 흔한 실수로 복잡한 다단계 작업에서 계획을 건너뛰는 것을 든다.

**[Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)** (구 `developers.openai.com/codex/guides/agents-md`에서 이동, 확인 2026-10-28)

- 전역(`~/.codex`)→저장소 루트→현재 폴더까지 내려가며 파일을 이어 붙이고, 가까운 파일이 뒤에 와서 앞 지침을 덮는다. 기본 합산 한도는 32 KiB다.
- 권장 내용: 변경 전 돌릴 테스트·린트 명령, 선호 도구, 승인 규칙(예: 운영 의존성 추가 전 확인), 동작 변경 시 문서 기대.

**[Codex IDE extension](https://learn.chatgpt.com/docs/codex/ide)** (확인 2026-10-28)

- VS Code와 호환 편집기에서 열린 파일·선택 코드·최근 대화를 참조하고 `@`로 파일을 언급한다. 변경 요약과 바뀐 줄을 코드 옆에 보여 주어 원하는 편집만 남길 수 있다.
- 「작업 전후에 Git 체크포인트를 만들어 되돌릴 수 있게」 하라고 권한다.

### 1.3 GitHub Copilot

**[Best practices for using GitHub Copilot](https://docs.github.com/en/copilot/get-started/best-practices)** (확인 2026-10-28)

- 복잡한 일은 작은 단계로 나누고, 요구를 구체적으로 쓰며, **예시 입력·기대 출력**을 포함한다.
- 출력 확인: 쓰기 전에 코드를 이해하고(모르면 Chat에 설명 요청), 보안·가독성·유지보수를 검토하며, 린트·코드 스캔 같은 자동 검사로 뒷받침한다. Copilot이 판단을 대신하지 않는다고 한다.
- 관련 파일만 열고 무관한 파일은 닫는다. 맥락이 어지러우면 새 대화를 시작한다. 빗나가면 다시 쓰거나 요청을 쪼갠다.

**[Get the best results (cloud agent)](https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results)** (확인 2026-10-28)

- 「명확하고 범위가 잡힌 작업」: 문제 설명·수용 기준·변경할 파일을 적는다. 다만 의미 검색이 되므로 정확한 경로가 항상 필요하지는 않다.
- 맡기기 좋은 일(버그 수정·테스트 보강·문서)과 사람이 맡을 일(넓은 리팩터링, 깊은 업무 지식, 보안·개인정보, 모호한 문제, **「직접 배우고 싶은 작업」**)을 구분한다.
- 저장소 조사→계획 제안→브랜치 변경 후 diff를 검토·다듬는 흐름, 동료 PR처럼 검토하고 반복을 예상하라고 한다.
- 빌드·테스트·검증 단계를 지침에 넣으면 스스로 확인한 변경이 나올 가능성이 높아진다.

**[About custom instructions](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions)** (확인 2026-10-28)

- 종류: 저장소 전체(`.github/copilot-instructions.md`), 경로별(`.github/instructions/*.instructions.md`), 에이전트 지침(`AGENTS.md`·`CLAUDE.md`·`GEMINI.md`, 모든 기능이 지원하지는 않음).
- Copilot이 지침을 「매번 같은 방식으로 따르지 않을 수 있다」, 지침이 정책 준수를 **보장하지 않는다**, 충돌하는 지침은 결과를 나쁘게 한다.

### 1.4 VS Code

**[Best practices (agents)](https://code.visualstudio.com/docs/agents/best-practices)** (확인 2026-10-28)

- 추측시키지 말고 관련 정보(`#파일`·`#폴더`, 터미널 출력, 테스트 실패, 스크린샷)를 가리킨다. 맥락은 가볍게 유지한다.
- 지침 파일은 짧게(매 대화에 로드됨), 필요한 도구만 켠다.
- 복잡한 다파일 변경은 **계획과 구현을 분리**: 먼저 탐색, Plan 에이전트로 계획, 다듬은 뒤 구현.
- 한 번에 하나의 제한된 작업, **관찰 가능한 결과를 정의**, 요구가 모호하면 AI가 질문하게 한다.
- AI 출력은 출발점: 통합 전 검토(경계 사례·오류 처리·하드코딩 비밀), 바뀐 파일을 모두 보고 의도한 변경만 남긴다.
- 체크포인트로 파일·대화를 되돌릴 수 있으나 **이미 실행된 명령·외부 서비스 변경은 되돌리지 않는다**.
- 프롬프트에 **테스트 사례와 기대 출력**을 넣어 에이전트가 스스로 확인하게 하고, AI 변경 뒤 테스트를 돌린다(에이전트가 안 돌리면 직접).

**[Planning](https://code.visualstudio.com/docs/agents/run/planning)** (확인 2026-10-28)

- 접근이 불명확하거나 여러 부분에 걸치면 먼저 계획, 작고 명확한 수정은 바로 구현.
- `/plan`에 목표·제약·성공 기준을 주면 조사·명확화 질문 후 단계·관련 파일·**검증 단계**를 담은 계획을 낸다. 승인 전에 범위·프로젝트 적합성·미결 결정·검증 단계를 확인한다.
- 기본 Plan 에이전트는 프로젝트 파일을 편집하지 않고 조사한다(Local 세션).

**[Custom instructions](https://code.visualstudio.com/docs/copilot/customization/custom-instructions)** (확인 2026-10-28)

- 루트 `AGENTS.md`는 `chat.useAgentsMdFile`(기본 켜짐), 하위 폴더 `AGENTS.md`는 실험 설정(기본 꺼짐), `CLAUDE.md`는 `chat.useClaudeMdFile`, `.github/copilot-instructions.md`는 Local 세션에서 `github.copilot.chat.codeGeneration.useInstructionFiles`로 제어된다.
- **지침은 입력 중 인라인 제안에는 적용되지 않는다.**

### 1.5 스펙 주도 개발

**[GitHub Blog — Spec-driven development with AI](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)** (Den Delimarsky, 2025-09-02, 확인 2026-10-28)

- 4단계: Specify(무엇·왜, 사용자 여정·성공 기준, 기술 스택 제외) → Plan(스택·제약) → Tasks(따로 구현·시험 가능한 작은 작업) → Implement(작은 변경 단위로 검토).
- 사람의 역할은 「조종」과 「검증」이고 단계마다 명세가 원하는 것을 담았는지, 계획이 실제 제약을 반영하는지, 빠진 경계 사례가 없는지 본다.
- 이유: 모델은 패턴 완성은 잘하지만 마음을 읽지 못하므로, 모호한 프롬프트는 말하지 않은 요구를 추측하게 하고 틀린 추측은 늦게 드러난다.
- 스스로 밝힌 한계: 긴 글 읽기가 지루하고 마크다운 파일 관리가 버거울 수 있다. 실험 단계다.

**[github/spec-kit README](https://github.com/github/spec-kit)** (확인 2026-10-28)

- 현재 README는 `constitution → specify → plan → tasks → implement → converge` 순서를 보이며 converge가 「Converged」를 낼 때까지 구현·수렴을 반복하라고 한다. 블로그 시점과 명령 구성이 달라졌다.
- 명령을 하나씩 실행하고 **각 결과를 검토한 뒤 다음으로** 가라고 한다. 프로세스는 필수 단계가 아니라 독립된 진입점이다.

**[spec-kit/spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)** (확인 2026-10-28)

- 명세가 1차 산출물이고 코드는 그 표현이라는 입장.
- 모호한 곳은 추측하지 않고 `[NEEDS CLARIFICATION: 질문]`으로 표시한다. 체크리스트를 「명세의 단위 테스트」로 쓴다.
- 헌법 제3조(test-first)는 테스트를 쓰고 승인받고 **실패를 확인하기 전에는** 구현 코드를 쓰지 않는다.
- 명세에는 「무엇을·왜」만, 기술 스택·API·코드 구조는 별도 파일에.

**[Kiro — Specs](https://kiro.dev/docs/specs/)·[Feature specs](https://kiro.dev/docs/specs/feature-specs/)** (확인 2026-10-28)

- `requirements.md`(사용자 이야기·요구) → `design.md`(구조·흐름·오류 처리·시험 전략) → `tasks.md`(추적 가능한 작업).
- 요구는 EARS 형식 「WHEN [조건/사건] THE SYSTEM SHALL [기대 동작]」으로 써서 시험 가능·추적 가능하게 한다. 설계 전에 요구의 모순·빈틈을 분석하는 기능이 있다.
- Quick Spec은 단계 사이 승인 관문 없이 한 번에 만들며 「잘 이해된 기능」에 맞다고 한다(=일반 Feature Spec은 단계별 확인이 기본).

### 1.6 「vibe coding」의 정의와 한계

- **원래 정의(Karpathy)**: X 원문은 열지 못했다(HTTP 402). [Simon Willison 글](https://simonwillison.net/2025/Mar/19/vibe-coding/)(2025-03-19)과 [Wikipedia](https://en.wikipedia.org/wiki/Vibe_coding)가 전하는 표현은 「fully give in to the vibes」「forget that the code even exists」, 버리는 주말 프로젝트용이라는 것이다. 날짜는 Willison 본문이 2월 6일, Wikipedia가 2월 2일로 적어 서로 다르다. Willison이 링크한 게시물 ID(1886192184808149383)의 Snowflake 시각을 풀면 2025-02-02 23:17 UTC다. 원문 확인 전까지 「2025년 2월 초」로 쓴다.
- **Willison의 구분**: vibe coding은 「LLM이 쓴 코드를 검토하지 않고 만드는 것」으로 좁게 정의하고, 검토·시험·이해한 LLM 코드는 그냥 소프트웨어 개발이라고 한다. 자기 규칙은 남에게 정확히 설명할 수 없는 코드는 커밋하지 않는 것. vibe coding이 괜찮은 조건은 피해가 작은 일, 비밀·개인정보 주의, 외부 서비스 부하·과금 주의다. 초보자가 소프트웨어를 만들어 보는 데 유익하다고도 한다.
- **비판(2차 집계)**: Wikipedia는 보안 결함 보고(Lovable 생성 앱의 개인정보 노출 등), 유지보수·중복 증가 분석, 이해 없이 커밋하는 문제, 책임성 부족 비판, Andrew Ng의 용어 비판을 정리한다. 개별 원문은 열지 않았다(미확인).

### 1.7 교육·학습 근거

**[Anthropic — How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills)** (2026-01-29, 확인 2026-10-28)

- 무작위 대조 실험(52명, 새 라이브러리 Trio 학습). AI 사용군 퀴즈 평균 50%, 직접 코딩군 67%로 유의한 차이, 가장 큰 차이는 **디버깅**. 속도 차이(약 2분)는 유의하지 않았다.
- 낮은 학습(40% 미만): AI에 위임, 점진적 의존, AI에 반복 디버깅 맡기기. 높은 학습(65% 이상): 생성 후 이해, 코드와 설명 함께 요청, 개념 질문.
- 권고: 학습자는 인지적으로 계속 관여하고, 교육자는 의도적으로 배치해 사람이 AI 코드를 감독할 능력을 유지하게 한다. 「막히는 고통」도 숙달에 중요할 수 있다고 쓴다.
- 한계: 새 라이브러리 학습 과제 하나이며 일반 프로그래밍 능력 전체가 아니다.

**[Prather 외, The Widening Gap (ICER 2024, arXiv 2405.17739)](https://arxiv.org/abs/2405.17739v1)** (초록, 확인 2026-10-28)

- 21명 관찰·인터뷰·시선 추적. 이미 계획한 코드를 빨리 쓰는 데 AI를 쓴 학생은 가속됐고, 메타인지 어려움이 있던 학생은 AI로 어려움이 커지거나 새로 생겼다. 실제보다 잘했다고 믿는 「능력의 착각」이 나타났다.
- 초록은 초보자 AI 사용에 비계를 줄 방법을 제안한다고만 하며 구체 방법은 본문 확인이 필요하다(미확인).

**[Liu 외, Teaching CS50 with AI (SIGCSE 2024)](https://cs.harvard.edu/malan/publications/V1fp0567-liu.pdf)** (PDF 텍스트 추출로 확인 2026-10-28)

- 강좌 전용 AI(코드 설명 확장, 스타일 검사, CS50 Duck)에 「교육적 가드레일」을 두어 답을 바로 주지 않고 해답으로 **안내**하게 했다. 시스템 프롬프트로 강좌 규칙을 정한다. 정답 검사 도구(check50)와 의미 설명 도구를 나눠 둔다.
- 상용 AI 사용은 제한했다. 결론은 금지보다 가드레일을 둔 허용이 낫다는 것.

## 2. 모범 바이브 코딩 순환과 근거

여러 출처가 공통으로 말하는 순서다. 모든 작업에 같은 길이로 강제하라는 출처는 없다. VS Code·Codex 모두 작고 명확한 일은 계획 없이 바로 하라고 한다.

| 단계 | 하는 일 | 근거 |
|---|---|---|
| 1. 탐색 | 편집 없이 AI에게 프로젝트·자료를 읽고 현재 상태를 설명하게 한다. 넓은 질문에서 좁은 질문으로 | Claude Common workflows(개요→흐름 추적, Plan mode는 승인 전 편집 없음), VS Code Planning(Plan 에이전트는 파일 편집 없이 조사), VS Code Best practices(먼저 탐색) |
| 2. 요구·명세 | 목표·맥락·제약·끝난 모습을 적는다. 모호하면 AI에게 질문(인터뷰)을 시키고, 모르는 것은 추측 대신 표시한다 | Codex(네 부분, Done when, 인터뷰), Claude(구체적 프롬프트, 인터뷰→SPEC.md), Copilot(수용 기준), VS Code(관찰 가능한 결과, 질문 요청), Spec Kit(`[NEEDS CLARIFICATION]`, 무엇·왜), Kiro(EARS) |
| 3. 계획 검토 | 복잡하거나 불명확할 때만 계획을 받고, 범위·미결 결정·**검증 단계**가 있는지 본 뒤 승인 | VS Code Planning, Codex(`/plan`), Spec Kit(단계별 검토 후 다음) |
| 4. 작은 구현 | 한 번에 하나의 제한된 작업, 따로 시험 가능한 단위 | VS Code(하나의 제한된 작업), Copilot(작은 단계), Spec Kit 블로그(작고 검토 가능한 작업), Claude(작고 시험 가능한 단위) |
| 5. 검증 | 기대 결과·확인 사례를 **실행 전에** 정해 두고, AI가 돌린 명령과 출력이라는 증거로 판정. 바뀐 파일·diff를 확인하고 코드를 설명할 수 있는지 본다 | Claude(돌릴 검사, 증거 요구, 실패 테스트 먼저), VS Code(테스트 사례·기대 출력을 프롬프트에, 변경 파일 모두 검토), Copilot(예시 입력·기대 출력, 이해 후 사용), Codex(테스트·diff 검토), Spec Kit(test-first), Willison(설명 가능해야 커밋) |
| 6. 수정 요청 | 증상·재현 방법·기대와 실제를 함께 준다. 두 번 고쳐도 안 되면 대화를 비우고 배운 것을 담아 다시 요청 | Claude(재현 명령·단계, 두 번 실패 후 `/clear`), Copilot(다시 쓰기·쪼개기, 어지러우면 새 대화), VS Code(테스트 실패·터미널 출력 첨부) |
| 7. 저장·기록 | 되돌릴 지점을 남기고, 반복된 실수만 지침 파일에 짧게 추가, 명세는 변경 기준으로 유지 | Codex IDE(작업 전후 Git 체크포인트), VS Code·Claude(체크포인트는 실행 명령·외부 변경을 되돌리지 않음), Codex(반복 실수 후에만 규칙 추가), Claude(두 번 고친 것을 CLAUDE.md에), Spec Kit(명세는 살아 있는 문서) |

관통 원칙 셋:

1. **AI가 볼 수 없는 것을 사람이 준다** — 목표·완료 기준·업무 판단·자료. 저장소에 이미 있는 것은 다시 적지 않는다(Claude, Codex, VS Code).
2. **검증 수단이 없으면 완료가 아니다** — 통과/실패가 나오는 확인과 실행 증거(Claude, VS Code, Codex, Copilot).
3. **지침은 안내이지 보장이 아니다** — 반드시 지킬 것은 별도 장치로(Claude 결정적/비결정적, Copilot custom instructions, Claude output styles).

교육 근거가 더하는 원칙: **결과보다 이해에 관여할 것**. AI에 위임만 한 학습자는 디버깅 이해가 가장 크게 떨어지고(Anthropic RCT), 약한 학생은 능력의 착각에 빠지기 쉽다(Prather). 생성 뒤 설명을 듣고 이해하는 사용, 개념 질문이 학습을 지켰다.

## 3. 학생 랩에 쓸 수 있는 구체 기법

| 기법 | 근거 | 초보자에게 맞게 쓸 때 주의점 |
|---|---|---|
| **파일 변경 금지 탐색 요청** — 「아직 고치지 말고, 이 폴더가 무엇을 하고 무엇이 비어 있는지 설명해 줘」 | Claude Plan mode·Common workflows, VS Code Plan 에이전트(편집 없음) | 도구마다 읽기 전용 모드 이름·위치가 다르다(Copilot Ask/Plan, Codex Chat·`/plan`, Claude plan mode). 문장으로만 금지하면 지침과 같아서 보장되지 않으므로, 첫 회차에 모드 전환 화면을 한 번 보여 준다 |
| **지침 파일로 범위·제약 제한**(AGENTS.md·CLAUDE.md·copilot-instructions) | Codex AGENTS.md, Copilot custom instructions, VS Code custom instructions, Claude(짧게) | 준수 보장이 아니다. 도구별 읽기 설정이 다르고(CLAUDE.md는 VS Code에서 설정 필요), **인라인 자동완성에는 적용되지 않는다**. 「AI에게 지금 읽은 작업 규칙을 요약해 달라」로 읽혔는지 확인하는 단계를 둔다. 해결 방법은 넣지 않는다 |
| **확인 사례·기대 결과를 실행 전에 적기** — 원자료에서 손으로 2~3건의 기대값을 먼저 적고 실행 결과와 대조 | VS Code·Copilot(테스트 사례·기대 출력), Claude(돌릴 검사), Spec Kit(test-first) | 노베이스 학생에게 테스트 코드를 먼저 쓰게 하지 않는다. 「원자료의 이 줄이면 결과에 이 값이 나와야 한다」 수준의 표로 충분하다. 기대값을 AI에게 대신 만들게 하면 같은 오해가 양쪽에 들어가므로 학생이 원자료에서 직접 뽑는다 |
| **목표·맥락·제약·완료 기준 네 칸으로 요청 쓰기** | Codex(Done when), Copilot(수용 기준), VS Code(관찰 가능한 결과) | 빈칸 양식이 「정답 프롬프트」가 되지 않도록 칸 이름만 주고 내용은 START를 자기 말로 옮겨 쓰게 한다 |
| **AI에게 질문(인터뷰) 시키기** — 「요구에서 애매한 점을 먼저 물어봐 줘」 | Claude(인터뷰→SPEC), Codex(인터뷰), VS Code(모호하면 질문 요청) | AI의 질문에 답하려면 원자료를 다시 봐야 한다는 점을 습관으로 묶는다. 답을 모르면 「모름」으로 남기고 지어내지 않게 한다 |
| **계획 모드는 필요할 때만** | VS Code Planning, Codex | 모든 랩에 계획 문서를 강제하면 문서량만 는다. 여러 파일·불명확한 요구일 때만. 계획 검토는 「검증 단계가 들어 있나」 하나만 봐도 된다 |
| **작은 diff 검토** — 바뀐 파일 목록과 바뀐 줄을 보고 의도한 변경만 남기기 | VS Code(바뀐 파일 모두 검토), Codex IDE(바뀐 줄 표시·원하는 편집만 유지), Codex(diff 검토) | 코드 전체를 이해하라고 요구하지 않는다. 「원자료·결과 폴더 밖 파일이 바뀌었나」「요청하지 않은 기능이 생겼나」 두 질문으로 시작한다 |
| **완료 주장에 증거 요구** — 「돌린 명령과 출력 그대로 보여 줘」 | Claude(증거 요구), VS Code(테스트 직접 실행) | AI 요약 문장을 결과로 받아 적지 않게 한다. 학생이 직접 한 번 실행해 같은 출력이 나오는지 본다 |
| **실패 시 입력·기대·실제를 함께 주기** | Claude(재현 명령·증상·고쳐진 모습), VS Code(테스트 실패·터미널 출력 첨부) | 「안 돼요」 대신 어떤 입력에서 무엇을 기대했고 무엇이 나왔는지. 오류 메시지는 일부가 아니라 그대로 붙인다 |
| **두 번 실패하면 대화를 새로** | Claude(`/clear` 후 새 프롬프트), Copilot(새 대화) | 실패한 대화를 계속 이어 붙이면 혼란이 커진다는 것을 알려 준다. 새 요청에는 배운 것(무엇이 틀렸는지)을 담는다 |
| **다른 입력으로 재검증** | Claude(검사로 반복 확인), Spec Kit·Kiro(경계 사례), 우리 기준(다른 입력·PBL 재사용) | 원자료 안의 다른 사례(중복·별칭·단위 누락 등 이미 있는 함정)로 확인한다. 정상 자료를 망가뜨려 실패를 연출하지 않는다 |
| **설명할 수 있을 때 저장** — 「이 변경이 무엇을 하는지 한 문장으로 말할 수 있나」 | Willison 규칙, Copilot(이해 후 사용), Anthropic RCT(생성 후 이해·개념 질문이 학습 유지) | 코드 줄 설명이 아니라 기능·조건·영향 수준. 모르면 AI에게 설명을 요청하고 그 설명을 원자료로 확인한다 |
| **명세 문서로 변경 관리** | Spec Kit, Kiro, Claude(SPEC.md 대비 검토) | SDD를 배우는 회차·변경 기준을 계속 관리할 때만. 초기 회차에 constitution·EARS 같은 용어를 앞질러 강제하지 않는다. 쓴다면 `[NEEDS CLARIFICATION]` 같은 「모름 표시」 한 가지 습관부터 |
| **되돌릴 지점 남기기** | Codex IDE(Git 체크포인트), VS Code·Claude 체크포인트 | 학생 GitHub를 요구하지 않으므로 VS Code 체크포인트·결과 폴더 사본으로 대신할 수 있다. 체크포인트는 실행한 명령(DB 적재 등)을 되돌리지 않는다는 점을 함께 알린다 |
| **학습 모드 활용(선택)** | Claude Learning 스타일, Anthropic RCT 권고 | Claude Code 전용이고 Copilot·Codex에는 같은 이름의 기능을 확인하지 못했다. 공통 절차로 넣지 않고 선택 안내로만 |

## 4. 우리 현재 기준과의 대조

### 4.1 이미 반영된 것

- **탐색 먼저, 파일 변경 금지**: 「랩 제공 틀」의 습관 순서 첫 단계. 근거 Claude plan mode, VS Code Plan 에이전트와 일치.
- **목표·입력·제약·확인 사례를 자기 말로**: 「바이브 코딩의 제공 경계」. Codex 네 부분, Copilot 수용 기준과 같은 구조.
- **계획 검토 → 작은 단위 구현**: 습관 순서에 있다. 실습 대본 기준이 「작고 명확한 변경은 직접 구현」을 이미 VS Code 근거로 채택했다.
- **결과를 원자료와 대조, 입력·기대·실제를 주고 수정 요청, 저장·재열기**: 습관 순서에 있다.
- **지침 파일은 안내이지 보안 장치가 아니다**: 세 출처(Claude, Copilot, Claude output styles)가 같은 말을 한다. 실제 격리를 별도 DB·컨테이너로 둔 것도 Claude의 「결정적 장치로 옮겨라」와 같은 방향이다.
- **지침 파일은 짧은 맥락·제약만**: Claude·Codex·VS Code의 「짧게」와 일치. 해결 방법을 넣지 않는 것은 우리 교육 목적에 따른 추가 제약이다.
- **정답 미제공·자동 완성 금지**: CS50 「답을 바로 주지 않고 안내」, Copilot 「직접 배우고 싶은 작업은 맡기지 말라」, Anthropic RCT(위임하면 학습 저하)가 뒷받침한다.
- **검사기는 구조만, 의미는 원자료와 대조, 검사기는 일부러 망가뜨린 입력으로 확인**: CS50의 정답 검사·의미 설명 분리, Claude 「돌릴 검사」와 맞다.
- **매 랩에 같은 길이의 절차를 강제하지 않음, SDD는 필요 시점에**: VS Code·Codex(작은 일은 바로), Spec Kit README(필수 단계 아님)와 일치.
- **고의 오류 연출 금지**: 출처에 반대 권고가 없다.

### 4.2 빠진 것 — 반영 제안

1. **기대 결과를 실행 *전에* 적는 단계가 명시돼 있지 않다.** 습관 순서는 「확인 사례 정리」와 「실행 결과를 원자료와 대조」만 있어, 결과를 본 뒤 맞춰 보는 사후 판정이 될 수 있다. VS Code·Copilot·Claude·Spec Kit 모두 기대값을 먼저 두라고 한다. 「START에 기대 결과 표를 넣지 않는다」는 경계와 충돌하지 않게, **학생이 원자료에서 직접** 2~3건의 기대값을 실행 전에 적는 단계로 넣는 것을 제안한다. Prather의 「능력의 착각」을 막는 가장 직접적인 장치다.
2. **완료 주장에 증거(실행 명령·출력)를 요구하는 습관이 없다.** Claude가 가장 강하게 말하는 항목이다. 「AI가 됐다고 하면 돌린 명령과 출력을 보여 달라고 하고, 직접 한 번 실행한다」를 검증 단계에 붙인다.
3. **바뀐 파일·diff 확인 단계가 없다.** 습관 순서에 「작은 단위 구현」은 있지만 「무엇이 바뀌었는지 보기」가 없다. VS Code·Codex 공통 권고. 초보자용으로 「원자료가 바뀌지 않았나, 요청하지 않은 기능이 생기지 않았나」 두 질문으로 둔다.
4. **설명 가능성 확인이 없다.** Anthropic RCT의 핵심 결과(위임 시 디버깅 이해 하락, 생성 후 이해는 유지)와 Willison 규칙. 저장 전 「이 변경이 무엇을 하는지 한 문장으로」를 넣는 것을 제안한다. 코드 해설을 늘리라는 뜻은 아니다(실습 대본 기준의 「소스 해설 금지」와 양립).
5. **AI에게 모호한 점을 묻게 하는 요청이 없다.** 우리 기준은 학생이 요구를 정리하게 하지만, AI가 질문하게 하는 기법(Claude·Codex·VS Code 공통)은 없다. 요구 정리를 돕는 비계로 첫 회차에 한 번 보여 줄 만하다.
6. **두 번 실패 시 새 대화 규칙이 없다.** 초보자가 같은 대화에 수정을 계속 쌓는 실패를 막는다(Claude, Copilot).
7. **지침 파일이 실제로 읽혔는지 확인하는 방법이 구체적이지 않다.** 근거 문서는 「실제 읽기 여부는 별도 확인」만 적었다. VS Code 설정 이름(`chat.useAgentsMdFile` 기본 켜짐, `chat.useClaudeMdFile`, `github.copilot.chat.codeGeneration.useInstructionFiles`)과 **인라인 자동완성은 지침을 쓰지 않는다**는 사실을 가이드·대본 확인 항목에 넣는다. 학교 PC 기본 설정에서 실제로 읽히는지는 미확인(5절).
8. **되돌리기 수단 안내가 없다.** Git을 요구하지 않으므로 VS Code 체크포인트 또는 결과 폴더 사본을 쓰되, DB 적재처럼 이미 실행한 명령은 되돌아가지 않는다는 점(VS Code·Claude 명시)을 함께 알린다.
9. **반복된 실수만 지침에 추가한다는 원칙**: 학생이 지침 파일을 고칠 일이 생기는 회차(에이전트·스킬 회차 등)에 Codex 권고를 근거로 쓸 수 있다. 현재 기준에는 없다.
