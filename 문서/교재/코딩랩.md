# 코딩 랩 — 만드는 법과 인수 조건

## 목적 · 가치 · 배경

**K목-1 코딩 랩이 무엇인가.** 이 과정의 실습은 두 가지다. **도구 실습**은 포털 · ARROWS · Notion · Neo4j · bpmn.io처럼 화면과 조작이 정해진 실습이고, **코딩 랩**은 학생이 VS Code에서 AI(GitHub Copilot · Codex)와 함께 직접 만드는 실습이다. 폴더 이름 `랩/`은 실습 묶음 폴더라 도구 실습 묶음도 그 안에 있다.
이 문서가 다루는 산출물은 코딩 랩 하나의 과제 설계, 학생에게 주는 제공물(`START.md` · 작업 규칙 · `입력/` · `자료/` · `결과/` · 검사기 · `guide.html`), 시작본 · 연결 · 저장, 완성 판정, 실습 폴더와 따로 받는 학생용 완성본 묶음, 실습 시작 도구, 학교 PC 조건, 오프라인 Notion 운영이다.
같은 랩을 찍는 대본 · 촬영 · 음성은 영상 산출물이, 학생이 따라 하는 가이드의 문장 · 사진은 가이드 산출물이 만든다. 이 문서는 그 둘에게 랩이 무엇을 넘기는지만 랩의 말로 적는다(K-132).

**K목-2 과정의 줄기 안의 자리.** 노베이스 학생이 **온톨로지 마스터 → 에이전트 마스터 → 프로세스**로 올라가게 과정이 짜여 있다. 이론은 각 단계의 원리와 까닭을, 실습은 같은 단계를 학생이 직접 만들어 보는 경험을 맡는다. 그래서 회차 · 장 · 실습마다 지금 줄기의 어느 단계를 채우는지 말할 수 있어야 하고, 코딩 랩도 마찬가지다(K-13).

| 단계 | 배우는 것 | 마친 학생이 할 수 있는 것 |
|---|---|---|
| **1. 온톨로지 마스터** | 온톨로지가 무엇이고 왜 필요한가(수치만으로는 조치를 정할 수 없다) → 무엇으로 구성되나(클래스 · 인스턴스 · 속성 · 관계 · 식별자 · 제약) → 어떻게 만드나(골든 퀘스천으로 범위를 정하고 설계 → 그래프 구현 · 질의 → 절차 · 판단 조건 연결) → 문서 인제스천(원문에서 뽑고 사람이 검토해 적재, 출처 확인) → 골든 퀘스천에 지식이 실제로 답하는지 검증 | 새 현장 문제를 받아도 **스스로 온톨로지를 설계하고 구축 · 검증할 수 있다**. 결과물은 질문 · 모델 · 문서 · 추출/검토 · 적재 코드 · 조회 검증을 갖춘 구축 결과다 |
| **2. 에이전트 마스터** | 그 지식을 쓰는 에이전트 — 하나가 아니라 무궁무진한 활용: 설비 원인 점검, 품질 접수, 분석 · 시각화, 회의 후속 업무, 자기 자료 학습 · 퀴즈, 작성 · 검토 협업처럼 목적 · 입력 · 도구 · 결과가 다른 활용과 그 구현 · 검증(도구 · MCP · 스킬, 명세, 근거와 승인 경계) | 어떤 일을 맡길 수 있는지와 필요한 자료 · 도구 · 권한 · 검증을 판단하고, **목적이 다른 에이전트를 스스로 설계 · 구현 · 검증할 수 있다** |
| **3. 프로세스** | 지식과 에이전트를 업무 흐름(BPMN)에 넣어 사람의 승인 · 실행 · 결과 확인까지 잇는다. 마지막 종합 실습(교대 인수인계, K-95 · K-96)이 1~2단계를 종합한다 | 사건 한 건을 지식 → 에이전트 판단 → 사람 승인 → 실행 · 기록으로 잇는 흐름을 만들고 돌릴 수 있다 |

실습은 이 줄기의 각 단계를 학생이 직접 만들어 보는 곳이고, 두 과정(통합반 · 실전반)은 이 줄기를 함께 걷는다.

**K목-3 이론 → 포털 실습 → 코딩 랩.** 한 주제는 이 순서로 배운다. 이론에서 원리와 까닭을 배우고, 포털 실습에서 그 개념이 완성된 시스템에서 실제로 어떻게 돌아가는지를 보고, 코딩 랩에서 포털에서 본 그 기능을 포털보다 어렵게, 현업에 가까운 현실 문제로 직접 만들어 본다(결과 조건은 K-14 · K-15).
수업 전체는 이어지는 하나의 이야기이고, 코딩 랩은 그 이야기에서 「본 것을 내 손으로 만든다」를 맡는다 — 그래서 랩의 물음은 앞에서 이해한 것에서 나와야 학생이 왜 이 일을 하는지 안다(K-16).

**K목-4 PBL을 위한 준비.** PBL은 이 과정 밖의 별도 수업이다. 이 과정의 목표는 학생이 그 PBL에서 스스로 문제를 정의하고 온톨로지 · 에이전트 · 프로세스를 설계 · 구현 · 검증할 수 있을 만큼 끌어올리는 것이다.
이론은 원리와 설계 판단을, 도구 실습은 배운 것을 정해진 화면에서 하나씩 짚으며 따라 가는 체험을, **코딩 랩은 손으로 만들며 그때 필요한 이론까지 다시 풀어 익히는 몫을 가장 많이 맡는다.** 그래서 랩의 수준은 PBL 목표로 잰다(K-32).

**K목-5 원리와 가치가 주인공이고 HYD는 재료다(가장 중요).** 우리는 강의를 하는 것이지 우리가 만든 시스템을 보고 · 자랑하는 것이 아니다. 온톨로지 → 에이전트 → 프로세스를 마스터하게 하려고 무엇을 왜 하는지(원리 · 까닭 · 판단 기준 · 현장의 가치)를 가르치고, 포털 · HYD는 그 원리를 보여 주는 도구다.
원리를 먼저 말하는 예: 「정상 범위는 멈춰야 할 한계보다 아래여야 손쓸 여유가 생긴다」 — 그다음에 「이 설비에서는 한계를 65 ℃로 둔다」처럼 그 상황의 설정을 얹는다(K-17).
제품도 재료라 「Neo4j」가 아니라 「그래프 DB」를 가르친다. 코딩 랩이 가르치는 것은 도구 사용법이 아니라 도구가 바뀌어도 통하는 습관과 설계 판단이다(K-19 · K-20). 피지컬 AI의 맥락은 설비 · 지식 · 판단 · 사람 · 실행의 연결이고, 무게는 온톨로지와 에이전트에 있다(K-21).

**K목-6 랩의 목적 — 모범적으로 바이브 코딩해 결과를 뽑는 습관.** 코딩 랩은 과정의 핵심이고 현업 난이도가 최우선이다(K-23).
현업 규모의 다출처 자료라서 눈으로는 못 맞추고 AI와 코드로 대조해야만 풀리는 문제여야, 학생이 「AI에게 맡기면 된다」가 아니라 「요구를 내 말로 정하고, 작게 만들고, 원자료와 대조해야 쓸 만한 결과가 나온다」를 몸으로 익힌다.
문제는 어렵게, 해결은 좋은 습관으로 수월하게 — 이것이 랩 설계의 한 문장이다. 그 습관이 바이브 코딩 일곱 단계(K-36)다.

**K목-7 정답을 주지 않는 까닭.** 학생의 AI는 받은 폴더 전체를 읽는다. 그래서 `START.md`에 해결 로직 · 기대 결과 표 · 그대로 붙이면 끝나는 완성 프롬프트를 넣는 순간, 학생이 무엇을 요청해도 AI가 그것을 답으로 써서 학생 판단 없이 끝나는 장난감이 된다. 판정 절차나 정답 방향을 계약에 적어도 같고, 학생용 완성본이 실습 폴더 안에 있어도 AI가 읽어 정답이 된다.
작업 규칙(`AGENTS.md` 등)은 AI에게 주는 학습 맥락이라 막는 힘이 없다 — 그래서 격리를 따로 둔다(K-53). 판정 기준이 「포털과 같은 답」이 아니라 「근거 있는 판단으로 쓸 만한 결과」인 것도 같은 까닭이다 — 현업에는 정답표가 없다(K-34).

**K목-8 무료 계정과 학생용 완성본.** 코딩 랩은 개인 GPT 무료 계정으로 끝까지 할 수 있어야 한다(사용자 결정) — 학생이 수업이 끝난 뒤에도 같은 습관으로 자기 일을 할 수 있어야 하기 때문이다. 계정 · 도구 설정은 환경 세팅 가이드 · 영상이 맡는다.
무료 계정조차 못 쓰는 학생도 결과를 확인할 수 있도록 학생용 완성본을 하나 준비하고, 온라인 영상 끝에서 그 완성본을 실행해 같은 결과가 나오는 것을 보인다. 이 학생에게는 「계정이 없으면 완성본으로 결과를 확인하고, 바이브 코딩 과정은 영상으로 보며 습관을 익힌다」가 길이 된다(K-58).

**K목-9 학생과 과정.** 대상은 코딩을 모르는 노베이스 대학생 · 취업 준비생이다. 학생은 노션 학습 포털의 회차 페이지에서 영상 · 교재 · 가이드 · 랩 묶음을 연다.
온라인은 강사 한 사람이 영상으로 설명하고 조작해 보인다. 오프라인은 학생이 그 회차 온라인을 듣고 왔다는 전제로, 가이드로 직접 하고 강사는 막힌 곳만 도우며 진행 빠르기를 유연하게 조절한다.
두 반 모두 처음 배우는 학생이다. 코딩 랩에서 두 과정의 차이는 덧붙인 숙제가 아니라 결과물의 모양(K맥-6)으로 나타난다(K-69).

**K목-10 규칙이 생긴 배경 — 실제로 있었던 잘못.** 아래는 사용자가 실제로 짚었거나 검수에서 걸린 일이고, 이 문서의 인수 조건은 이것이 다시 생기면 잡히도록 걸려 있다.
- 실라버스 행의 배정 시간 · 상세를 보지 않고 만들어 **50분 수업을 7분으로 만들고 그 상태로 완료라고 보고했다.** 실라버스를 안 보면 50분 수업이 7분이 된다 — 50분 실습이 7분이면 실습이 아니다.
- 포털 실습(실전 2-2, 10분)에 VS Code 장면 · 기록 파일 · START · 결과 폴더를 넣고, 뺀 뒤에도 「다음 실습부터 VS Code…」로 엮었다. 코딩 랩 조항(제공물 · 저장 · 다시 열기 · 바이브 코딩)을 도구 실습에 넓혀 적용한 것이다. **도구 실습과 코딩 랩은 완전히 별개다.**
- 폐기판 산출물(랩 폴더 · 구성)과 「사용자 확인 대기」 항목을 실라버스와 대조하지 않고 이어받았다. 「재사용할 수 있다」는 「대조해 맞으면 쓴다」이지 「쓴다」가 아니다.
- 식별자 · 속성 키를 낭독하고, 「랩 그래프」 같은 제작 용어를 쓰고, 조작만 읽는 얕은 설명으로 결과를 읽고 넘어갔다. 행에 없는 장면 · 타이핑으로 시간을 늘렸다.
- 사용자에게 대본 전문을 읽으라고 넘겼다. 요청문의 읽는 순서(리서치 노트)를 다 읽지 않고 시작했다.
- 4회차에서 덱과 대본은 개편된 실라버스 행을 따랐는데 실습 1의 `START.md` · 가이드 · 실습 대본은 옛 행 그대로였고, 실습 2 · 3에는 `START.md`가 아예 없었다. 회차 README · 구성 파일에 실측 없이 「확인 완료」가 적혀 있었다.
- 실라버스에 실전반 학생이 만든 적 없는 「앞 실습의 모델」, 아직 만들지 않은 「별도 랩 DB에서 만든 모델」을 전제하는 문장이 있었다. 같은 DB를 「실습용 예제 DB」 · 「별도 랩 DB」 두 이름으로 부르면서 처음 나올 때 풀지 않았고, 「Skill」이 조치 방법과 에이전트 스킬 두 대상을 가리켰다.
- 「자기 자료 퀴즈」 「작성 · 검토 협업」처럼 랩 이름을 줄인 말은 노베이스 학생이 무슨 일인지 모른다. 「다음 실습에서는 …」이 실제 다음 실습과 달랐고, VS Code 실습 안에 다른 도구 · 세 회차 뒤 예고가 있었다. 온라인 행을 고쳤는데 오프라인 짝 행에 같은 문제가 남았다.
- 리허설에서 수정본을 반영하다 실제 센서 TS1이 지워진 일(실전 2-4)이 있었다 — 그래서 변경 반영 뒤에는 개수 · 값을 원자료와 다시 센다(K-143).

## 작업 컨텍스트

**K맥-1 이 문서 하나만 끝까지 읽는다.** 코딩 랩을 만들거나 고칠 때 필요한 규칙은 이 문서에 다 있다 — 다른 산출물 문서를 함께 읽지 않아도 된다.
이 문서의 스킬은 `hyd-coding-lab`이고, 스킬은 「이 문서를 끝까지 열어라」와 도구 요령만 갖는다. 내용의 주인은 이 문서다(Codex는 스킬을 못 읽고 `AGENTS.md`가 이 문서를 가리킨다).
해석 순서는 지금 사용자 지시(가장 뒤의 결정, 번복은 마지막 결정) → 이 문서와 실라버스 최종본 → 스킬 기본값 → 과거 인계 · 요청문 · 샘플이다. 스킬과 이 문서가 부딪치면 이 문서가 맞다. 확정된 최신 결정은 옛 것을 덮고 옛 요청문 · 샘플로 되돌리지 않지만, 관련 없는 규칙까지 지우지는 않는다. 리서치의 제안을 임의로 필수 요구로 올리지 않는다.
이 순서는 권한을 넓히지 않는다 — 랩 작업에서 포털 로직 · DB · 서비스를 바꾸지 않는다.

**K맥-2 코딩 랩의 시작 화면 · 하는 것 · 없는 것.** 아래 표의 「없는 것」은 이 문서의 다른 어느 조항보다 앞선다. 판정은 K-36 · K-39 · K-40 · K-41 · K-84.

| 시작 화면 | 하는 것 | 없는 것 |
|---|---|---|
| VS Code에서 받은 실습 폴더를 연 상태 | 바이브 코딩 일곱 단계로 요구를 내 말로 정하고, 작게 구현하고, 결과를 원자료와 대조하고, 저장 · 다시 열기 | 학생에게 주는 정답 · 해결 로직 · 완성 프롬프트, 코드 해설, 포털 관찰 실습의 화면 설명 |

코딩 랩 영상이 이미 있으면(「사용자 확정」이든 「사용자 재생 확인 전」이든) 랩 · `START.md` · 대조표를 그 영상의 실제 진행에 맞춘다(K-150). 영상과 다르게 바꿀 일이면 다시 찍지 않고 결함을 「대상 · 어긋남 · 근거 · 고칠 문장」으로 기록해 사용자 승인을 받는다.
지금 상태는 로컬 인계(`.evidence/인계/`), [`제작용/촬영/vscode/촬영준비.md`](../../제작용/촬영/vscode/촬영준비.md), 회차 README, `package-index.json` · `catalog.json`에서 확인하되 옛 완료 표시는 실물로 다시 본다. `.evidence`와 촬영 원본은 git clone에 없다.

## 작업 요령

**K요-1 시작할 때.**
- 먼저 이 실습이 코딩 랩인지 정한다. 화면 · 조작이 정해진 도구 실습(포털 · ARROWS · Notion · Neo4j Browser · bpmn.io)이면 이 문서가 아니다(경계의 결과 조건은 K-84 · K-145).
- 시작 보고에 아래 원칙마다 지금 랩에 어떻게 적용할지 한 줄씩 적고, 검토도 이것부터 본다: ① 실라버스가 메인 — 그 행의 문장과 배정 시간에서 시작 ② 원리와 가치가 주인공, HYD · 포털 · 제품은 재료 ③ 노베이스 학생에게 사람의 말로 ④ 본 것만 쓰고 연출하지 않음 ⑤ 완료는 숫자로, 확인은 판단용 요약으로 ⑥ 이 문서와 산출물은 고쳐 쓰고 한 곳에, 충돌은 바로 정리.
- 읽을 것: 이 문서, 그 실습 행, 앞 이론 덱의 실습 설명 장, 앞 포털 실습, K맥-8의 리서치 근거. 본보기 랩이 생기면 그것도 통독해 「실제로 이렇게 주고 이렇게 판정한다」를 잡는다. 읽은 목록은 완료 보고에 남긴다(K-138).
- 다시 시작할 때(새 세션 · 대화 요약 뒤 · 실패 직후)는 기억이 없다고 보고 이 문서를 다시 끝까지 읽고, git · 실행 상태와 인계(로컬 `.evidence/인계/`)의 차이만 확인해 최신 판본 · 다음 행동 · 미확인을 복원한다. 오래된 진행 기록은 현재 작업 목록이 아니다.
- 옛 완료 표시 · 경로는 실물로, 게시 여부는 게시 판본으로 다시 확인하고, 과거 샘플의 지시 · 포트를 현재 값으로 쓰지 않는다. 같은 판본을 읽은 기록(문서 · 해시 · 범위)이 있으면 바뀐 부분만, 없으면 원문 전체를 반드시 읽는다. 요약 · 키워드 검사는 원문을 대체하지 않고, 미확인을 임의 결정으로 메우지 않는다.
- 인계의 옛 완료 표시는 믿지 않고 실제 파일을 연다. 폐기판 산출물(랩 폴더 · 구성안 · 대본)과 옛 구성안의 「사용자 확인 대기」 항목은 실라버스 그 행과 대조하기 전에는 이어받지 않는다 — 「재사용할 수 있다」는 「대조해 맞으면 쓴다」다.

**K요-2 만드는 순서.** 랩 하나를 시작 → 설계 · 제공물 → 강사 참조 실행 → 학생 경로 리허설 → 패키지 · 받기 시험 → 영상 · 가이드 전달까지 끝낸 뒤 다음 랩으로 간다. 각 단계는 앞 단계가 끝나야 넘어간다.
1. 배정 시간과 실라버스 대조표(K요-3, 가장 먼저).
2. 앞 이론 · 앞 포털 실습과 잇는 지점(K요-6).
3. 과제 설계 — 현업 난이도 재료(K요-7), 판단이 갈리는 지점과 전면 기법(K요-8).
4. 제공물(K요-9), 이름(K요-10), 시작본 · 연결 · 저장(K요-12).
5. 구성안 사용자 확인(K요-18의 꼴).
6. 강사 참조를 갈래별로 실제 실행하고 학생용 완성본을 따로 묶는다(K요-11).
7. 리허설 · 검사 · 받기 시험(K요-14) — 바뀐 곳은 연결 산출물에 함께 반영(K요-16).
8. 패키지 빌드 · 게시 준비(K요-13), 완료 보고(K요-20).

**K요-3 실라버스 대조표.** 모든 랩의 첫 단계는 실라버스 그 행이다. 그 행의 배정 시간을 먼저 적고, 상세 문장을 한 줄씩 떼어 아래 꼴로 표를 만든다(결과 조건은 K-1 ~ K-4).

| 실라버스 상세 문장(원문 그대로) | 영상 구간 | 설명 · 화면 | 확인 방법 | 예상 분 |
|---|---|---|---|---|

빈칸이 있으면 다음 단계로 가지 않는다. 어디서 다루는지는 START 절 · 제공 자료 · 확인 사례 · 가이드 단계 · 영상 구간 중 하나로 적는다. 추측 · 자기 판단으로 넣고 빼지 않는다. 다 만든 뒤에는 대조표끼리가 아니라 실라버스 원문과 다시 맞춰 본다 — 랩 · 대본 · 가이드가 함께 빠뜨린 항목은 목록끼리 비교해서는 보이지 않기 때문이다.

**K요-4 시간.** 시간은 배정에서 시작하는 목표이고 내용이 먼저다 — 실라버스 항목 · 정식 용어 · 정의 · 필요성 · 예시 · 판단 근거와 바이브 코딩 과정까지 깊이 있게 채운다. 시간 판정은 온라인 랩에만, 실라버스 행 하나 단위로 한다(결과 조건은 K-7 · K-8).
- 계획 시간이 배정보다 짧으면 먼저 그 행 범위 안에서 어색하지 않고 자연스럽고 겹치지 않는 선으로 새 자료 · 설명 · 확인 사례를 찾아 최대한 보강한다(다음 회차를 당겨 오지 않음). 더 설명할 거리 · 자료가 없으면 그 까닭을 적는다(예: 30분 행이 20분, 40분 행이 30분).
- 보강해도 배정 −10분보다 짧으면 랩의 활동 자체가 그 시간을 감당하지 못한다는 뜻이다(50분 수업이 7분이 된 사고). 과제 규모 · 확인 사례를 다시 보강하거나, 실라버스 쪽 조정을 「상황 → 제안」으로 사용자에게 묻는다.
- 재는 법: 실제 강사 복제 음성으로 맞춘 계수 하나([`제작용/촬영/시간계수.json`](../../제작용/촬영/시간계수.json))로, 랩의 영상 큐는 `제작용/촬영/시간계산.py estimate <cues.json> [--target 분]`(말과 조작의 합집합, 말하며 한 조작을 다시 더하지 않음)으로 계획 시간을 낸다.
- 낭독 추정은 실제 진행 시간이 아니다 — 조작 · AI 응답 대기는 따로 잰다. 그래서 학생 수행 시간은 리허설에서 준비 · 설명 · AI 대기 · 구현 · 확인 · 막힘 · 완성본 전환을 구별해 기록한 실측으로 본다. 고친 뒤에는 같은 계수로 전후를 다시 잰다.
- 오프라인 랩은 강사가 직접 유연하게 진행하며 중요도에 따라 빠르기를 조절하므로 분으로 재지 않는다.

**K요-5 실라버스를 고칠 일이면.** 고정 항목은 K-11, 고친 뒤 맞출 자리는 K-12 · K-140이 정한다.
- 행의 상세 항목과 행 이름 문구는 작업하며 바꿀 수 있다 — **무엇을 왜 바꾸는지 먼저 말하고** 고친다. 이미 만들어진 영상(「사용자 재생 확인 전」 포함)의 실제 진행 · 포털 실제 기능 · 앞뒤 흐름이 근거면 실라버스를(상황 → 제안 → 이렇게 해도 될까요로 묻고), 실라버스가 맞으면 랩을 고친다. 노션 실라버스 수정은 게시라 먼저 묻는다.
- 랩의 표현을 고치는 일과 실라버스를 고치는 일을 혼동하지 않는다. 최신 결정과 엑셀이 어긋나면 임의로 섞지 말고 어긋난 셀을 적어 맞춘다. 시간 행이 바뀌었다고 내용을 바로 지우거나 늘리지 않고, 재편을 이유로 시간을 더하지 않는다.
- 엑셀은 병합이 안 되므로 고치기 직전 `git status`로 다른 세션의 미커밋 엑셀 수정이 없는지 본다.

**K요-6 앞과 잇기.** 바로 앞 이론 대본(덱의 실습 간지 · 설명 장)과 앞에서 본 포털 화면에서 연결점을 찾는다. 잇는 말은 「포털에서 이렇게 돌아가는 걸 봤죠. 이제 이걸 직접, 더 지저분한 현실 자료로 만들어 봅니다」 꼴이다. `START.md` 첫머리 · 가이드 첫 화면 · 영상 여는 말이 같은 연결점을 쓰도록 랩이 정해 넘긴다. 실전반처럼 앞에 그 랩이 없으면 「제공된 설비 · 부품 모델」로 주고 그렇게 부른다(결과 조건은 K-15 · K-16).

**K요-7 과제 설계 — 현업 난이도 재료.** 결과 조건은 K-23 ~ K-26 · K-34.
- 재료는 리서치(공식 모범 사례 · 현업 사례, 로컬 근거 노트는 K맥-8)로 근거를 잡고, 부족하면 조사한 현업 문제 유형 · 시뮬레이터 로직을 따라 생성한다. 포털 설비가 단순하면 포털에 묶이지 말고 재료를 키운다. 포털은 방향 기준일 뿐이라 시드 자료 · 입력값 · 판정 결과까지 맞추지 않는다.
- 생성한 자료는 그 파일 첫머리에 가상 사례임을 한 번 밝히고(K-18), 원문 · 판본 · 실행에서 가져온 값은 출처 · 시점을 자료 머리에 적는다(K-54).
- 규모는 함정이 대조로만 드러나도록 잡는다 — 중복 · 별칭 · 단위 누락 · 경계 · 판본 차이 · 품번 변형이 실제 업무 자료에서 생기는 모양으로 섞여 있어야 한다.

**K요-8 정답 없는 과제로 만들기.** 결과 조건은 K-37 · K-40 ~ K-46.
- 판단이 갈리는 지점 고르는 예: 같은 쌍의 견적이 여러 줄일 때 기준일에 유효한 조건을 무엇으로 볼지, 출처마다 다른 승인 표시를 어떻게 정할지. 학생이 정한 내용 · 근거 줄 · 바뀌는 답은 `결과/`의 결정 표에 적게 한다.
- 전면 기법은 그 랩의 일(설계 · 구현 · 판정)에 맞춰 하나 고른다.
- 강사 참조로 실제로 풀리는 것을 먼저 확인한 뒤 판단이 갈리는 지점, 그다음 확인할 사례를 정한다(대본 전에 끝낼 것 — K맥-10). 만드는 데 필요한 이론(예: 관계의 방향 · 식별자 · 출처)은 단계마다 짚어 영상에 넘긴다.

**K요-13 시작 도구와 배포.** 결과 조건은 K-99 ~ K-104.
- 학생 진입 파일: `index.html` → `실습시작.zip` → 압축 해제 → `실습시작.cmd`(`python launcher.py`). 새 시작은 UUID를 붙인 별도 폴더, 이전 작업 열기는 기록된 기존 폴더를 쓴다.
- 생성은 `python 제작용/실습시작/build.py`다. 이 파일이 생성기 여덟(`build_labs.py` → `build_offline.py` → `build_conditions.py` → `build_common.py` → `pack_arrows.py` → `build_session3_whatif.py` → `build_session3_judgement.py` → `build_session3_documents.py`)을 차례로 돌린 뒤 `build_launcher.py`(인수를 그대로 넘김) → `build_guide_bundle.py`를 돌린다. 생성기 하나만 돌리면 뒤 단계 목록을 다시 생성해야 한다.
- 그다음 `python 제작용/실습시작/verify_packages.py` → `python 제작용/실습시작/test_launcher.py`. 실제 캡처는 각 랩 폴더의 `images/`에 보존하고 다시 만들지 않는다.
- 기본 주소는 로컬 검증 서버 `http://127.0.0.1:8765`다. 공개 배포는 패키지를 먼저 게시하고 그 커밋의 raw URL을 `build.py --base-url <주소>`(→ `build_launcher.py`)에 넣어 시작 도구를 묶는다. `catalog.json`은 SHA-256으로 ZIP 판본을 확인한다.
- ZIP을 다시 만들면 내용이 같아도 메타데이터 해시가 바뀔 수 있으므로 게시 커밋과 해시를 항상 함께 고정한다. 주소만 바꾸고 검증 없이 게시 완료로 표시하지 않는다. 배포 ZIP은 전체를 자동 재생성하지 말고 요청된 묶음의 대상 목록과 ZIP 안 목록 · 바이트를 확인한다. 외부 게시는 요청이 있을 때 한다.

**K요-14 검사 · 리허설 · 완성 판정.** 검사는 판정하려는 것을 재야 한다 — 실행 없는 검사(정적 · 패키지)를 먼저, 실제 실행(강사 참조 · 리허설 · 받기 시험)을 뒤에 한다. 결과 조건은 K-105 ~ K-110 · K-133.
- 정적 검사는 실행 없이 한다 — Python은 AST, JSON/XML/BPMN은 파싱만, HTML은 내용 · 순서 · 로컬 링크, 복사 자료는 해시. 구문 통과는 구현 성공이 아니다.
- 패키지 검사 `python 제작용/실습시작/verify_packages.py`: `package-index.json`의 ZIP마다 SHA-256, `START.md` · `guide.html` · `결과/README.md` 존재, `.env` · `__pycache__` 없음, 2회차 ZIP의 학생이 만들 결과 · 강사 기대 답 없음, 가이드 내부 링크를 본다.
- 패키지 검사 결과는 `.evidence/practice-20261026/package-verification.json`에 남는다. 이 검사는 학생 AI 수행 검증이 아니다.
- 검사기 고의 손상: 학생 검사기(`check.py` 등)에 일부러 망가뜨린 입력(ID 중복 · 끝점 없음 · 관계 방향 등)을 넣어 잡는지 본다(기록 `reference/session2_검사기_고의손상.json` · `session3/검사기_확인.json`, 시험 `reference/session2_check_trials.py`). 안 잡으면 없는 검사다.
- 학생 경로 리허설: 준비 때 랩 코드 · 입력 · 시작본 · 참조본 · 완료 조건을 정적으로 맞추고, 학생과 같은 입력 · 폴더 · 명령으로 Codex를 써서 한 번 한다(준비 · 설명 · AI 대기 · 구현 · 확인 · 막힘 · 완성본 전환을 구별해 기록). 고친 뒤에는 바뀐 곳과 연결만 다시 본다.
- 리허설 · 받기 시험 화면은 브라우저 기반이다 — 공식 `code serve-web`으로 띄운 웹 VS Code를 ego 브라우저 탭에서 쓰고(값 · 함정은 [`제작용/촬영/vscode/촬영준비.md`](../../제작용/촬영/vscode/촬영준비.md) 「통과한 길」), 데스크톱 앱 조작 · computer use · CDP 원격 디버깅 경로는 쓰지 않는다. 웹판과 다른 네이티브 장면만 따로 캡처한다(K-110).
- 장난감 시험: 「한 줄 요청」(예: 「START.md대로 다 해 줘」)을 한 번 보내 같은 결과가 나오는지 본다(K-28).
- 같은 판본으로 맞춘 뒤(K요-16) 실제 수행을 확인한다. 코드 단계가 이미 리허설 · 강사 참조 실행을 통과한 판본이면 같은 판본으로 다시 돌리지 않는다.

**K요-15 오프라인 랩 고르기.** 결과 조건은 K-88 ~ K-94.

**K요-18 사용자에게 묻기 · 확인 받기 · 비용.**

- 물을 때는 상황 → 양쪽 내용 → 제안을 쉬운 말로 쓰고 「이렇게 해도 될까요」로 묻는다. 삭제는 실제 동작 이름으로 쓴다.
- 결과 확인을 사용자에게 넘기지 않고(열 수 없는 화면만 상태를 특정해 요청), 지적은 같은 유형 전체에 적용하며, 앞의 판정을 뒤집으면 그렇다고 밝힌다.
- 확인을 받을 때는 전문을 읽게 하지 않는다. ① 배정 · 계획 시간과 구간별 분 ② 구성 흐름 ③ 실라버스 문장 ↔ 구간 대조(빈칸 0) ④ 실제 문장 발췌(`START.md`의 시작 · 「학생이 정할 것」 · 끝, 가이드 첫 화면) ⑤ 판단할 지점만 준다.
- 비용이 드는 일은 먼저 알린다(모델을 많이 부르는 리허설, 작업자 여럿) — 규모와 견적을 알리고 진행한다. 유료 실험은 상한을 정하고, 실패하면 같은 조건을 재실행하지 않고 기존 결과부터 분석한다. 원격 push와 노션 게시는 사용자에게 묻고 한다.

**K요-19 작업 단위 · 범위 · 반복 금지.**
- 범위는 요청대로, 그 안은 끝까지 — 승인된 범위의 수정 · 동기화 · 검증을 끝까지 하고 제안만 하고 멈추지 않는다. 검토만 · 정리만이면 고치지 않고, 윤문만이면 뜻을 지켜 표현만 다듬으며, 요청하지 않은 ZIP · 보고서 · 업로드를 덧붙이지 않는다. 정적 작업에는 실행 · AI 시연 · 캡처가 들어가지 않는다(요청한 회차에서만).
- 처음부터 이 문서와 원 자료를 끝까지 읽고 완성판을 만들고, 여러 랩에 같은 틀을 적용할 때는 대표 하나로 먼저 확인한 뒤 넓힌다. 끝낸 작업, 같은 판본의 재독 · 재생성 · 재검사 · AI 호출을 되풀이하지 않고 새 수정 · 새 실패 · 미확인과 영향받는 파생물만 본다. 그렇다고 필요한 최종 검증을 빼거나 표본 · 키워드 검사로 내용 검토를 대신하지 않는다(K-139).
- 확정된 산출물(K맥-13)은 결함을 「대상 · 어긋남 · 근거 · 고칠 문장」으로 기록하고 사용자 승인을 받은 뒤 그 범위만 고친다.
- 한 세션은 한 단위(랩 하나)만 하고, 끝나면 인계를 고쳐 쓴 뒤 감독에게 보고하고 멈춘다(긴 세션이 요약되며 규칙을 잃지 않게, 품질이 뒤로 갈수록 줄지 않게). 새 세션은 사용자나 사용자가 맡긴 감독 세션이 연다. 파일이 겹치지 않는 갈래만 동시에 돌리고 같은 파일을 두 세션이 동시에 고치지 않으며, 커밋은 그 단위 세션이 경로를 지정해 한다.
- 단위를 끝내기 전에 이 문서 · 산출물 · 품질 본보기만 받은 새 검토자(고치지 않고 목록만)가 인수 조건 대조와 품질 비교를 한 번 한다. 서브에이전트는 `opus`(fable 금지)이고, 지시에 범위 · 금지 · 보고 양식을 적으며 작업자는 원문과 줄 번호를 가져온다. 남의 완료를 대신 확정하지 않는다.

**K요-20 기록 · 보고 · 우회 금지.** 결과 조건은 K-133 ~ K-138 · K-146 ~ K-148.
- 이 문서를 랩에 맞춰 고친 것은 랩을 고친 것이 아니고, 문서 · 가이드를 고친 것은 실제 랩 수행 · 리허설을 한 것이 아니다. 구조 검사 · 파일 존재 · mock · 문법 통과는 완주가 아니다. 한 도구 · 샘플 · 옛 판본의 상태를 다른 범위로 넓히지 않는다.
- 완료 보고는 항목별로 요구 → 결과 → 근거를 대조해 적는다.
- 우회하지 않는다 — 도구의 한계는 원인을 고치고, 검사기 경고를 무시해 통과로 바꾸지 않으며, 보안 설정 · 권한 제한을 끄거나 돌아가지 않는다. 다른 세션의 자원 · 탭 · 컨테이너를 확인 없이 끄거나 지우지 않는다.

**K요-21 저장소 · 키 · 이 문서 고치기.**
- 브랜치는 main 하나, 예외는 `other-pc` 하나다(영상 · 음성 · 자막 · 시간표는 other-pc). 랩 · 문서 · 도구는 main에서 고치고 other-pc는 main을 병합해 따라간다(other-pc에서 바뀐 문서는 그 변경만 main으로 가져온 뒤 다시 병합). 다른 작업 브랜치를 만들지 않고 옛 분기는 archive/ 태그로만 둔다.
- 커밋: 시작과 커밋 직전에 실제 HEAD · 원격 · 미커밋을 확인하고, 허용된 경로만 지정해 커밋하며(`git add .` 금지, `git commit -m … -- <경로>`, 커밋 전 `git diff --cached --name-only`로 남이 스테이징한 것이 없는지, 뒤에 `git show --stat`) 다른 세션의 미커밋은 보존한다. 원격 변경은 받아 병합하고 rebase · 강제 push · reset · stash는 하지 않는다. 원격 push는 묻는다.
- 공개 저장소다. `.env`는 열지 않고 키 값은 어디에도 다시 찍지 않는다. [`course/labs/offline/05-2-cause-agent/.env`](../../course/labs/offline/05-2-cause-agent/.env)처럼 실행 때 키가 써지는 추적 파일은 스테이징하지 않고 끝나면 `git checkout --`로 되돌린다. 학생 폴더의 빈 `.env`는 `git add -f`로 올리고, 값을 적은 `.env`는 커밋하지 않는다.
- 인계에는 현재 커밋 · 판본, 재실행 금지 목록, 남은 실패와 다음 행동 · 증거 위치를 적되 규칙은 이 문서의 번호로만 가리킨다. 이 문서에는 규칙만 두고 날짜 · 인용 · 경위는 결정 기록에 둔다(main 밖). 결정 번호 꼬리표를 달지 않고, 문장은 근거 없이 바꾸지 않는다.
- 본보기가 보여 주는 것은 「본보기대로」로 줄이고, 본보기로 알 수 없는 것(판단 기준, 되돌리기 비싼 금지, 실제 사고에서 나온 규칙, 숫자 · 경로 · 도구)만 문장으로 둔다.
- 이 문서를 고칠 때는 덧붙이지 않고 그 주제 자리를 다시 써서 겹치는 문장과 합친다(문장 사이 끼워 넣기 · 괄호나 「단」 꼬리도 덧붙이기다). 한 주제는 이 문서 한 자리에 두고, 서로 부딪치는 문장이 생기면 그 자리에서 최신 결정 하나로 정리하고 옛 문장을 남기지 않는다. 다른 산출물 문서와는 겹쳐도 되지만 이 문서 안에서 같은 뜻을 두 번 쓰지 않는다.
- 고친 뒤 전후 글자 수를 재고 늘었으면 까닭을 커밋 메시지에 적으며, 커밋 전에 `PYTHONUTF8=1 .venv314/Scripts/python.exe .evidence/기준정리/도구/재편검사.py`로 절 순서 · 인수 조건 빈 칸 · 같은 줄 · 대응 끊김 0을 확인한다(로컬 도구, 없으면 같은 확인을 손으로). 이 문서의 파일 이름 · 번호를 바꾸면 그것을 가리키는 스킬 · 촬영준비 · CLAUDE.md · AGENTS.md를 같은 커밋에서 고치고 옛 이름 검색 0을 확인한다.
- 포털 · Docker를 쓴 작업(리허설 · 강사 참조 실행 · 받기 시험)이 끝나면 Docker Desktop을 끄고 프로세스가 0인지 확인한다.

| K-16 | 랩이 이어지는 하나의 이야기 안에 있다 — 과제의 물음이 앞에서 이해한 것에서 나오고, 학생이 알아볼 장면 · 사건 하나의 물음에서 출발해 답하며 닫고(억지 드라마 아님), 끝에 다음 랩에 넘길 것이 있다. 앞에서 정의하지 않은 말 · 학생이 만들지 않은 결과를 전제하는 문장 0 | 과제의 물음이 앞 이론 · 포털 실습의 어느 장 · 화면에서 나왔는지 적어 봄: 적을 수 없거나, 앞에 없던 모델 · DB · 기능을 「앞 실습의 …」로 전제하는 문장이 1개 이상이면 불통과 |
| K-17 | 원리 · 까닭이 먼저 오고, HYD의 이름 · 값 · 코드 · 문서 절 번호는 「이 설비에서는 …」처럼 그 상황의 설정으로만 얹혀 정답처럼 박혀 있지 않다. 「규칙으로 만들지 않았다」 「HYD에서는 코드가 ~한다」 같은 구현 보고 문장과 「~했다 · 하지 않았다 · 이게 정답이다」 말투 0 | `START.md` · 작업 규칙 · README · 가이드 문장을 훑음: 원리 없이 HYD 값을 답으로 제시하거나 구현이 한 일 · 하지 않은 일을 알리는 문장 1개 이상이면 불통과 |
| K-18 | 꼬리표 · 면책 0 — 「교육용 · 강의용 · 수업용 · 예시 · 줄인 값」 꼬리표, 「실제와 다르다」 「표준과는 다르지만」 같은 면책 · 단서, 가상 · 시뮬레이터 강조, 값에 붙인 「(가정)」 「(예시)」(화면 이름 「결함 시뮬레이션」 인용은 예외). 가상 사례임을 밝히는 꼬리표의 자리는 가상 자료 파일 첫머리 하나이고, 생성한 가상 자료 파일에는 그 표시가 있다 | 랩 폴더 전체에서 이 낱말들을 찾음: 가상 자료 파일 첫머리 밖에서 1개 이상, 또는 생성한 가상 자료 파일 첫머리에 표시가 없으면 불통과 |
| K-19 | 제품도 재료다 — 「그래프 DB」를 가르치고 Neo4j는 한 예로 얹으며, 학생이 직접 쓰는 언어 · 도구는 정확한 이름(Cypher · VS Code · Codex · GitHub Copilot)이다 | 개념 설명 자리에서 제품 이름이 개념 이름을 대신하거나, 학생이 쓰는 도구 이름이 부정확하면 불통과 |
| K-20 | 재료(설비 · 제품 · 도구)가 바뀌어도 랩의 설명이 그대로 성립한다 — 랩은 도구 사용법이 아니라 도구가 바뀌어도 통하는 습관과 설계 판단을 가르친다 | 판단 설명 문장마다 HYD · 포털 · 특정 제품을 다른 것으로 바꿔 읽어 봄: 무너지는 판단 설명 1개 이상, 또는 랩의 목표가 특정 도구 조작 익히기면 불통과 |
| K-21 | 설비 사례 하나로 원리와 구축 과정을 깊이 다루고 소재를 나열하지 않는다(Notion은 활용 사례 하나). 무게는 온톨로지와 에이전트에 있고 설비 · SCADA는 판단 이해에 필요한 범위까지만이다 | 랩의 사건 · 판단 물음을 셈(한 사건 · 한 판단 물음 안에서 대조에 쓰이는 공장 단위 자료는 여러 사례로 세지 않음): 서로 다른 사건 · 물음이 여럿 나열되거나, 판단과 무관한 설비 · SCADA 설명이 과제의 중심이면 불통과 |
| K-22 | 한 재료의 구현 선택을 모든 시스템의 원리로, 골든 퀘스천을 특정 제품 기능으로 일반화하지 않고, 이 설비의 값을 현장 일반의 값이라 하지 않는다 | 「모든 시스템은 …」 「현장에서는 보통 …」 류 문장을 찾아 근거와 견줌: 이 설비 · 이 제품의 선택을 일반 원리 · 일반 값으로 쓴 곳 1개 이상이면 불통과 |

### 현업 난이도 · 장난감 금지 · 정답 없는 과제

| 번호 | 통과 기준 | 확인 방법 |
|---|---|---|
| K-23 | 현업 수준의 어려운 문제가 먼저 주어진다 — 「약간 어렵게」가 아니라 규모 · 성격 자체가 현업 수준인 공장 단위 다출처 자료(자산 대장 · 태그 수백 줄 · 정비 이력 · 품번 변형 부품 마스터 · 판본 다른 점검표 같은 것)라 눈으로는 못 맞추고 AI와 코드로 대조해야만 풀린다 | `자료/`를 열어 출처 · 판본 차이 · 품번 변형을 찾고 리허설 · 강사 참조 기록과 견줌: 출처가 하나, 판본 차이 · 품번 변형 · 중복 같은 대조 대상이 없음, 리허설 · 참조에서 코드 대조 없이 눈으로 맞춰 풀림 중 하나면 불통과 |

| K-31 | 랩마다 결정할 업무 · 입력과 출처 · 조건과 예외 · 학생이 구현할 기능 · 결과 확인 방법 · 다음 단계로 가져갈 산출물이 이어져 있고, 결과는 실제 역할이 쓰는 모양으로 남는다 | `START.md`에서 여섯 요소를 찾음: 하나라도 없거나, `결과/` 틀이 실제 역할(정비 · 구매 · 운전 등)이 쓸 모양이 아니면 불통과 |

| K-33 | 과정 전체로 기록 추적 → 지식 구조 · 판단 → 근거 추출 → 에이전트 · 도구 → 명세 · 검증 → 승인 · 실행 → 종합 조율이 명세 · 지식 · 출력 계약 · BPMN · 검증 기록으로 남는다 | 과정의 랩 목록과 각 `결과/` 계약을 차례로 봄: 이 사슬의 한 고리가 어떤 랩의 결과로도 남지 않으면 불통과 |
