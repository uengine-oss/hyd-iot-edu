PDF는 생성된 전체 낭독본으로 다시 만들고 본문 일치와 렌더를 확인한다. 다른 회차는 아직 분할 전이며 원격 최신판을 확인한 뒤 적용한다.

도구와 순서다. 지켜야 할 기준은 `2_기준.md`에 있다. 명령은 실제로 돌려 본 것만 적었다. 2026-10-14에 폴더를 옮긴 뒤 덱 빌드, 배포 묶음 검사, 장수 세기, 실습 목록, 대본 길이, 촬영 대본, 랩 가이드 도구를 한 번씩 돌려 확인했다.

덱 한 장을 빌드하는 명령(저장소 루트에서):

```bash

```

렌더에는 LibreOffice(`soffice`), `pdftoppm`, 맑은 고딕 글꼴이 필요하다. 렌더 폴더는 매번 새 이름으로 쓰고 저장소에 올리지 않는다.

## 1부. 덱 고치기

이 문서는 이미 있는 덱의 장을 고치거나, 통합반 원 덱을 고친 뒤 조립 덱과 배포 묶음까지 다시 만들 때 읽는다.

명령은 모두 저장소 루트에서 실행한다. 필요한 것은 `uv`, `python3`, 렌더할 때의 LibreOffice(`soffice`) · `pdftoppm` · 맑은 고딕 글꼴이다. 이 문서의 요약이 스킬 `.claude/skills/hyd-course-deck/SKILL.md`이고, (나)의 도구 셋(`재조립.py` · `장수.py` · `배포묶음.py`)은 그 스킬의 `scripts/`에 있다. 규칙(무엇을 어떻게 써야 하는가)은 `문서/교재/2_기준.md`에 있고, 이 문서는 순서와 명령만 적는다.

### (가) 한 장 고치기

#### 1. 어느 파일을 고치는가

| 고치려는 장 | 고칠 파일 | 그 뒤 |
|---|---|---|
| 통합반 온라인 덱의 장 | `만들기/decks/integrated/dayNN/통합반_NN일차.md` | 빌드. 그 장을 가져가는 조립 덱이 있으면 (나)로 간다 |
| 조립 덱의 장 가운데 통합반에서 **가져온** 장 — 모든 과정에서 고쳐져야 한다 | 통합반 원 덱 | (나) |
| 조립 덱의 장 가운데 가져온 장 — 그 덱에서만 달라야 한다(회차 표기, 빠진 장을 가리키는 말 등) | 그 덱 폴더의 `조립.py`: 그 장의 `G(...)`에 `(찾을 말, 바꿀 말)`을 더한다 | `조립.py` 실행 → 빌드 |
| 조립 덱의 **새로 쓴** 장(표지, 학습목표, 용어 정리, 정답, 그 과정에만 있는 실습 설명 등) | 그 덱 폴더의 `새장_*.md` | `조립.py` 실행 → 빌드 |
| 조립 덱에서 장을 더 가져오거나 빼기, 순서 바꾸기 | `조립.py`의 `ORDER` | `조립.py` 실행 → 빌드 |
| 실전반 1일차 | 통합반 1일차 원 덱(실전반 1일차는 과정 이름만 바꾼 사본이다) | `python3 만들기/decks/practical/만들기_01일차.py` → 빌드 |

**조립 결과 MD(`실전반_0N일차.md`, `<과정>_오프라인_NN회차.md`)는 손으로 고치지 않는다.** 다음 조립에서 덮여 사라진다. 어떤 장이 가져온 것인지 새 장인지는 `조립.py`의 `ORDER`에서 본다: `G("10", "제목", …)`은 통합반 10일차에서 가져온 장, `N("[N3]")`은 `새장_*.md`의 장이다.

`조립.py`의 손질은 찾을 말이 그 장 안에 **정확히 한 번** 있어야 한다. 없거나 두 번 있으면 스크립트가 장 번호와 문구를 찍고 멈춘다.

#### 2. 빌드

```bash
uv run --no-project --with python-pptx --with pymupdf python .claude/skills/lecture-deck/scripts/deck2pptx.py \
  만들기/decks/integrated/day03/통합반_03일차.md 만들기/decks/integrated/day03/통합반_03일차.pptx
```

- 규칙 위반과 넘침 추정이 있으면 파일을 쓰기 전에 장 번호와 칸 이름을 모아 찍고 실패한다. 문구를 다듬거나 장을 나누거나 유형을 바꿔 고친다.
- 삽화 라벨은 줄마다 글자 자리와 그 둘레 0.1인치 안에 그림의 선 · 아이콘 가장자리가 들어오거나, 다른 라벨과 0.1인치 안으로 붙으면 실패한다(같은 색으로 칠한 칸 위, 위아래를 테두리가 가로지르는 칸 안의 글자는 통과). 라벨 좌표나 폭, 그림의 배치를 옮겨 고친다.
- 카드 · 비교 · 흐름 · 단계는 내용이 적으면 빌더가 글자를 키워 본문 영역의 80 %까지 채운다(`deck2pptx.py`의 `grow`, 2026-10-14). 글자를 키운 뒤에도 같은 넘침 검사를 거친다.
- 덱 MD를 고치지 않았으면 저장소의 PPTX를 다시 만들어 덮어쓰지 않는다(`만들기/decks/README.md` 「원본과 산출물」).
- PowerPoint에서 그 PPTX를 열어 둔 채(`~$…pptx` 잠금 파일이 있을 때) 빌드하면 덮어쓰기가 실패할 수 있다.

#### 4. 삽화와 그래프 고치기

삽화는 직접 그린 SVG이고 그리는 스크립트가 같은 폴더에 있다. 그림 안에는 글자가 없다. 라벨은 덱 MD의 요소(`라벨 | 설명 | x,y[,폭]`)다.

| 고칠 것 | 방법 |
|---|---|
| 라벨의 글이나 위치 | 덱 MD의 그 장 요소만 고친다. 그림은 그대로다 |
| 그림 자체 | 그 일차의 `figures/만들기_삽화.py`에서 그 그림의 함수를 고치고 다시 돌린다 |
| 실제 데이터 그래프(PNG) | `figures/만들기_그래프.py`를 고치고 다시 돌린다 |

```bash
cd 만들기/decks/integrated/day10/figures && python3 만들기_삽화.py                               # SVG (표준 라이브러리만 쓴다)
cd 만들기/decks/integrated/day03/figures && uv run --no-project --with matplotlib python 만들기_그래프.py   # 그래프 PNG
```

- 스크립트는 그 폴더의 SVG를 모두 다시 쓴다. 돌린 뒤 `git diff --stat`으로 의도한 그림만 바뀌었는지 본다. 1일차의 `만들기_삽화.py`는 이미 있는 승인된 그림을 다시 쓰지 않게 되어 있다.
- 화풍(선 굵기, 색, 그림 조각)은 `삽화_기본.py`(1일차의 것을 복사한 것)에서 가져온다. 그림체는 바꾸지 않는다(`5_결정_기록.md` 1절).
- 그림을 고친 뒤에는 그 그림을 쓰는 장을 원본 크기 PNG로 본다. 라벨 좌표가 그림과 어긋날 수 있다.
- 통합반의 그림은 조립 덱도 함께 쓴다. 그림을 고쳤으면 그 그림이 든 장을 가져가는 조립 덱의 PPTX도 다시 빌드한다(덱 MD는 바뀌지 않으므로 `git diff`로는 드러나지 않는다 — 그림 파일 이름으로 `만들기/decks`의 덱 MD를 검색한다).

### (나) 통합반 원 덱을 고친 뒤 따라오는 일

#### 1. 고치기 전에 — 제목과 손질 원문

- **장 제목·구조 변경은 조립 참조에 영향을 준다.** 기존 제목을 지키려고 교육적으로 필요한 재구성을 포기하지 않는다. 변경 대응과 영향받는 `조립.py`를 먼저 확인하고, 실행·보류는 `6_남은_일.md` 0절을 따른다.
- 장 안의 문구를 고쳤는데 그 문구가 어느 `조립.py`의 손질 원문이면 그 스크립트도 멈춘다(「바꿀 말이 0번 있음」). 고치기 전에 찾아본다.

```bash
grep -rn --include='조립.py' '고치려는 문구' 만들기/decks
```

- 멈춘 손질은 지우지 말고 **뜻**을 본다. 그 손질이 하던 일(회차 표기 바꾸기, 빠진 장을 가리키는 말 고치기, 풀네임 붙이기)을 원 덱이 이미 해 놓았으면 손질을 지우고, 아니면 새 원문에 맞춰 다시 건다.

#### 3. 조립 스크립트 27개를 다시 돌린다

- 원 덱에 새 장을 넣었으면 조립 덱에는 저절로 들어가지 않는다. 그 회차의 실라버스 항목과 분량을 보고 `ORDER`에 넣을지 정한다(실전반 8일차는 통합반 11일차를 전부 가져오는 덱이라 새 장도 넣는다).

- 렌더 없이 빌드만 하므로 빠르다. 그 뒤 화면이 바뀐 장 몇 곳을 골라 (가) 3의 방법으로 렌더해 본다.

이 문서는 새 일차 · 회차의 덱을 만들거나, 전체를 다시 점검하거나, 실라버스가 바뀌어 덱을 크게 손봐야 할 때 읽는다.

무엇을 어떻게 써야 하는가는 `문서/교재/2_기준.md`(특히 6절 29-1~29-5번 압축과 용어, 14절 덱의 화면, 16절 점검)에 있고, 덱별 현황과 조립 규칙은 `3_현황.md` 7절에 있다. 이 문서는 **현재 제작과 검증의 순서**를 적는다. 과거 분업과 결정 경위는 `5_결정_기록.md`에서 확인한다. 단계마다 쓴 지시문은 `작업자_지시문/`에 있고 쓰임은 `작업자_지시문/README.md`에 있다. 이미 있는 덱을 고치는 순서와 명령은 `4_만드는_법.md` 1부다.

### 0. 덱과 대본을 함께 설계하고 확인하는 흐름

교육적 판정은 `2_기준.md`가 맡는다. 아래는 그 판정을 제작 중 언제 하는지 정한 절차다. 현재 원고를 모범으로 고정하지 말고, 해당 작업의 기준과 실제 학생의 이해 흐름을 대조한다.

| 단계 | 할 일 | 남길 근거 |

| 7. 검토·동기화 | 사용자 검토 뒤 허용된 파생물과 현황을 맞춘다. 조립 전환 등 보류 상태는 분리한다 | 수정 원본·갱신된 파생물·보류 목록 |

시간 조율에서 내용이 바뀌면 2~6의 영향받은 단계로 돌아간다. 시간을 먼저 정해 장 뒤에 문단을 덧붙이는 별도 공정으로 만들지 않는다. 변경 장의 우선 검토가 끝나도 최종 확인은 `2_기준.md` 104~107번의 범위를 따른다. 기존 지시문을 재사용할 때도 이 흐름과 최신 기준을 우선하며, 과거 작업자의 분업·모델·반영 방식이 적힌 지시를 그대로 다시 실행하지 않는다.

### 1. 원 덱과 대본 작성

0절로 제작한다. 덱 형식과 유형은 `.claude/skills/lecture-deck/references/덱MD-PPTX형식.md`, 사실은 `사실표/`와 코드·원문, 대본 형식은 `2_기준.md` 15절을 참조한다. 대본만 읽어 화면의 모든 글을 옮겨 적지 않았는지, 화면만 보아도 핵심이 남는지 각각 확인한다. 대본 머리의 구성표와 낭독본 생성은 3부 도구를 쓴다.

### 2. 조립 덱

공통 단원 조립 원칙은 `2_기준.md` 29-2번, 현재 전환 상태는 `6_남은_일.md` 0절에 있다. 가져올 장의 제목 목록은 탐색에만 쓰고, 실제 본문·노트·선수 개념을 읽어 조립 단위를 정한다. 1부의 기존 조립 명령은 현행 방식의 유지보수용이며, 과정별 새 본문이나 문자열 손질을 확대하는 설계안이 아니다. 승인된 도구 전환 뒤 원 덱의 내용과 생성된 고정 장을 구분해 확인한다.

### 3. 종합 점검과 적용 명령

점검 기준은 `2_기준.md` 16절, 점검자와 적용 방식은 45-2번이다. 동작과 사실은 근거 원문으로, 이해 가능성은 단원 전개와 낭독으로, 화면은 렌더로 검증한다. 어느 하나의 통과로 나머지를 대신하지 않는다.

```bash
bash 만들기/tools/deck/아스트라세션.sh <세션 ID | new> <요청문> <답>
python3 만들기/tools/deck/고칠것넣기.py <고칠것.json> <사본 대본> <사본 덱> --dry

```

사본 덱의 그림 상대 경로도 보존한다. 구조·번호를 바꾸면 대본·목차·실습 묶음·조립 참조까지 대조한다. 시간 도구가 아직 반영하지 않은 계산은 `6_남은_일.md` 0절에서 확인하고 별도 집계임을 표시한다. 반영 후 낭독본을 다시 뽑아 해당 단원을 연속으로 읽는다. 실제 청취·렌더를 하지 못한 범위는 명시한다.

### 4. 실라버스가 바뀌었을 때

실라버스는 사용자가 직접 쓴다. 바뀐 xlsx를 받으면 고치기 전에 **무엇이 달라지는지 먼저 사용자에게 말한다**(`5_결정_기록.md` 1절).

| 바뀐 것 | 할 일 |
|---|---|
| 이론 행의 제목 · 상세 내용 | 그 행에 해당하는 단원과 대조한다(항목 → 장 번호). 빠진 항목이 생겼으면 사실표에 근거가 있는지 보고 장을 더한다. 근거가 없으면 사실 조사부터 한다 |
| 이론 행의 시간 | 장수부터 바꾸지 않고 설명의 깊이와 회차 배분을 다시 검토한다. 필요한 화면 근거가 빠졌으면 덱도 고친다(`2_기준.md` 39~41번) |
| 실습 행의 추가 · 삭제 · 제목 | 실습 간지와 설명 장(2장)을 더하거나 빼거나 고친다. 실습 가이드의 목록(`실습_목록.md`)도 다시 뽑는다 |
| 이론 ↔ 실습 구분 | 덱의 틀과 목차의 구분을 바꾼다(지난 예: ProcessGPT 이론 단원 → 시연 실습) |
| 통합반 시트가 바뀌었다 | 원 덱을 고친 뒤 조립 덱까지 다시 만든다(`4_만드는_법.md` 1부 (나)) |
| 실전반 · 오프라인 시트만 바뀌었다 | 공통 단원의 대응과 시간표를 바꾼다. 새 조립 전환 전에는 2절과 `6_남은_일.md`의 보류 범위를 먼저 확인한다 |

저장소의 xlsx를 새 파일로 바꾸고, `2_기준.md` 1절과 11절, `3_현황.md`가 가리키는 실라버스 파일 이름이 맞는지 본다.

- 쉼의 자리는 `쉼_저장/`에서 읽는다(장마다 파일 하나, `"쉼"`에 문장 사이마다 0~3). 적히지 않은 장이 있으면 `"쉼": null`인 파일을 만들고 멈춘다. 그 파일을 채운 뒤 다시 돌린다.
- 쉼의 길이만 바꿔 다시 만드는 것은 크레딧이 들지 않는다.
- `덱문구.py`의 요청문 · 검사 · 넣기 · 자르기는 2026-10-14에 돌려 확인했다(검사가 바꾼 숫자를 잡고, 키가 어긋나면 넣기가 멈춘다). `아스트라.py`는 2026-10-14에 클라우드에서 1회차 덱 1~17장(문구 135개)으로 두 번, 18~44장(문구 244개)으로 한 번 실제로 불렀다(1~17장은 입력 · 출력 각 4,500 토큰 안팎에 1분 남짓, 18~44장은 각 8,500 토큰 안팎에 1분 40초). `자르기`는 첫 장이 1이 아니면 표지를 앞에 붙인다(덱의 첫 장은 표지여야 빌드된다). 요청문은 장마다 「── N장: 한 화면 ──」으로 묶는다(줄마다 따로 다듬으면 한 장 안에서 같은 말이 겹쳤다). 검사는 숫자와 영문 이름만 대조하므로 「수십 번」 같은 한글 수량의 변화는 사람이 읽어 본다. 하루치 음성에는 5,000 크레딧 안팎이 든다. 2026-10-14부터 `아스트라.py`의 기본은 사용자 계정 Codex다. 클라우드에서 `codex login --device-auth`로 로그인한 뒤 20장(문구 8개)을 한 번 불러 12초에 받았고 검사를 통과했다(빈 임시 폴더 · 읽기 전용으로 돌린다).

### 5. HYD 시스템을 띄울 때

절차는 `../시스템/4_켜고_돌리는_법.md`에 있다. 1일차 실습 2의 촬영 대본도 그 절차를 따른다.

같은 PC에서 다른 프로젝트가 5432 · 7474 · 7687 · 8080 · 8088 · 5432x 포트를 쓰고 있으면 그 포트를 차지하지 않는다. 저장소 파일은 고치지 않고 이렇게 한다.

- 업무 DB: `it/supabase`를 임시 폴더에 복사해 포트를 바꾸고 `npx supabase@2.119.0 start`로 띄운다.

- 포털은 브라우저에서 8080을 직접 부른다. 자동 조작 브라우저에서는 그 요청을 옮긴 포트로 돌린다.
