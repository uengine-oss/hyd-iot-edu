# 교재 4. 만드는 법

도구와 순서다. 지켜야 할 기준은 `2_기준.md`에 있다. 명령은 실제로 돌려 본 것만 적었다. 2026-10-14에 폴더를 옮긴 뒤 덱 빌드, 배포 묶음 검사, 장수 세기, 실습 목록, 대본 길이, 촬영 대본, 랩 가이드 도구를 한 번씩 돌려 확인했다.

덱 한 장을 빌드하는 명령(저장소 루트에서):

```bash
uv run --no-project --with python-pptx --with pymupdf python .claude/skills/lecture-deck/scripts/deck2pptx.py production/decks/integrated/dayNN/통합반_NN일차.md <출력.pptx> --render <새 렌더 폴더>
uv run --no-project --with pillow python production/tools/deck/시트.py <렌더 폴더> <출력 접두어> --cols 4 --per 24
```

렌더에는 LibreOffice(`soffice`), `pdftoppm`, 맑은 고딕 글꼴이 필요하다. 렌더 폴더는 매번 새 이름으로 쓰고 저장소에 올리지 않는다.

## 1부. 덱 고치기

이 문서는 이미 있는 덱의 장을 고치거나, 통합반 원 덱을 고친 뒤 조립 덱과 배포 묶음까지 다시 만들 때 읽는다.

명령은 모두 저장소 루트에서 실행한다. 필요한 것은 `uv`, `python3`, 렌더할 때의 LibreOffice(`soffice`) · `pdftoppm` · 맑은 고딕 글꼴이다. 이 문서의 요약이 스킬 `.claude/skills/hyd-course-deck/SKILL.md`이고, (나)의 도구 셋(`재조립.py` · `장수.py` · `배포묶음.py`)은 그 스킬의 `scripts/`에 있다. 규칙(무엇을 어떻게 써야 하는가)은 `문서/교재/2_기준.md`에 있고, 이 문서는 순서와 명령만 적는다.

### (가) 한 장 고치기

#### 1. 어느 파일을 고치는가

| 고치려는 장 | 고칠 파일 | 그 뒤 |
|---|---|---|
| 통합반 온라인 덱의 장 | `production/decks/integrated/dayNN/통합반_NN일차.md` | 빌드. 그 장을 가져가는 조립 덱이 있으면 (나)로 간다 |
| 조립 덱의 장 가운데 통합반에서 **가져온** 장 — 모든 과정에서 고쳐져야 한다 | 통합반 원 덱 | (나) |
| 조립 덱의 장 가운데 가져온 장 — 그 덱에서만 달라야 한다(회차 표기, 빠진 장을 가리키는 말 등) | 그 덱 폴더의 `조립.py`: 그 장의 `G(...)`에 `(찾을 말, 바꿀 말)`을 더한다 | `조립.py` 실행 → 빌드 |
| 조립 덱의 **새로 쓴** 장(표지, 학습목표, 용어 정리, 정답, 그 과정에만 있는 실습 설명 등) | 그 덱 폴더의 `새장_*.md` | `조립.py` 실행 → 빌드 |
| 조립 덱에서 장을 더 가져오거나 빼기, 순서 바꾸기 | `조립.py`의 `ORDER` | `조립.py` 실행 → 빌드 |
| 실전반 1일차 | 통합반 1일차 원 덱(실전반 1일차는 과정 이름만 바꾼 사본이다) | `python3 production/decks/practical/만들기_01일차.py` → 빌드 |

**조립 결과 MD(`실전반_0N일차.md`, `<과정>_오프라인_NN회차.md`)는 손으로 고치지 않는다.** 다음 조립에서 덮여 사라진다. 어떤 장이 가져온 것인지 새 장인지는 `조립.py`의 `ORDER`에서 본다: `G("10", "제목", …)`은 통합반 10일차에서 가져온 장, `N("[N3]")`은 `새장_*.md`의 장이다.

`조립.py`의 손질은 찾을 말이 그 장 안에 **정확히 한 번** 있어야 한다. 없거나 두 번 있으면 스크립트가 장 번호와 문구를 찍고 멈춘다.

#### 2. 빌드

```bash
uv run --no-project --with python-pptx --with pymupdf python .claude/skills/lecture-deck/scripts/deck2pptx.py \
  production/decks/integrated/day03/통합반_03일차.md production/decks/integrated/day03/통합반_03일차.pptx
```

- 규칙 위반과 넘침 추정이 있으면 파일을 쓰기 전에 장 번호와 칸 이름을 모아 찍고 실패한다. 문구를 다듬거나 장을 나누거나 유형을 바꿔 고친다.
- 삽화 라벨은 줄마다 글자 자리와 그 둘레 0.1인치 안에 그림의 선 · 아이콘 가장자리가 들어오거나, 다른 라벨과 0.1인치 안으로 붙으면 실패한다(같은 색으로 칠한 칸 위, 위아래를 테두리가 가로지르는 칸 안의 글자는 통과). 라벨 좌표나 폭, 그림의 배치를 옮겨 고친다.
- 카드 · 비교 · 흐름 · 단계는 내용이 적으면 빌더가 글자를 키워 본문 영역의 80 %까지 채운다(`deck2pptx.py`의 `grow`, 2026-10-14). 글자를 키운 뒤에도 같은 넘침 검사를 거친다.
- 덱 MD를 고치지 않았으면 저장소의 PPTX를 다시 만들어 덮어쓰지 않는다(`production/decks/README.md` 「원본과 산출물」).
- PowerPoint에서 그 PPTX를 열어 둔 채(`~$…pptx` 잠금 파일이 있을 때) 빌드하면 덮어쓰기가 실패할 수 있다.

#### 3. 렌더와 묶음 그림으로 확인

```bash
# 렌더: 출력 PPTX와 렌더 폴더를 저장소 밖(작업 폴더)에 둔다. 렌더 폴더는 매번 새 이름
uv run --no-project --with python-pptx --with pymupdf python .claude/skills/lecture-deck/scripts/deck2pptx.py \
  production/decks/integrated/day03/통합반_03일차.md <작업 폴더>/d03.pptx --render <작업 폴더>/d03_r1

# 묶음 그림: 검토용은 한 묶음 9장 이하
uv run --no-project --with pillow python production/tools/deck/시트.py <작업 폴더>/d03_r1 <작업 폴더>/d03_sheet --cols 3 --per 9
```

- 묶음 그림(`…_1.png`, `…_2.png`)을 열어 고친 장과 그 앞뒤를 본다. 의심스러운 장은 렌더 폴더의 원본 PNG(`*-NN.png`)를 따로 연다.
- 볼 것: 넘침, 겹침, 잘린 글자, 낱말 하나만 떨어진 줄, 작은 글자, 큰 빈 칸, 비스듬한 화살표(그래프 꼴 그림은 예외, `2_기준.md` 89-2번), 코드 상자 아래가 잘림, 그림이 비어 있음.
- 저장소의 PPTX를 갱신하려면 2의 명령으로 저장소 경로에 한 번 더 빌드한다(또는 렌더할 때 출력을 저장소 경로로 준다).
- 렌더 폴더, 묶음 그림, 중간 PDF, `__pycache__`는 저장소에 두지 않는다.

#### 4. 삽화와 그래프 고치기

삽화는 직접 그린 SVG이고 그리는 스크립트가 같은 폴더에 있다. 그림 안에는 글자가 없다. 라벨은 덱 MD의 요소(`라벨 | 설명 | x,y[,폭]`)다.

| 고칠 것 | 방법 |
|---|---|
| 라벨의 글이나 위치 | 덱 MD의 그 장 요소만 고친다. 그림은 그대로다 |
| 그림 자체 | 그 일차의 `figures/만들기_삽화.py`에서 그 그림의 함수를 고치고 다시 돌린다 |
| 실제 데이터 그래프(PNG) | `figures/만들기_그래프.py`를 고치고 다시 돌린다 |

```bash
cd production/decks/integrated/day10/그림 && python3 만들기_삽화.py                               # SVG (표준 라이브러리만 쓴다)
cd production/decks/integrated/day03/그림 && uv run --no-project --with matplotlib python 만들기_그래프.py   # 그래프 PNG
```

- 스크립트는 그 폴더의 SVG를 모두 다시 쓴다. 돌린 뒤 `git diff --stat`으로 의도한 그림만 바뀌었는지 본다. 1일차의 `만들기_삽화.py`는 이미 있는 승인된 그림을 다시 쓰지 않게 되어 있다.
- 화풍(선 굵기, 색, 그림 조각)은 `삽화_기본.py`(1일차의 것을 복사한 것)에서 가져온다. 그림체는 바꾸지 않는다(`5_결정_기록.md` 1절).
- 그림을 고친 뒤에는 그 그림을 쓰는 장을 원본 크기 PNG로 본다. 라벨 좌표가 그림과 어긋날 수 있다.
- 통합반의 그림은 조립 덱도 함께 쓴다. 그림을 고쳤으면 그 그림이 든 장을 가져가는 조립 덱의 PPTX도 다시 빌드한다(덱 MD는 바뀌지 않으므로 `git diff`로는 드러나지 않는다 — 그림 파일 이름으로 `production/decks`의 덱 MD를 검색한다).

### (나) 통합반 원 덱을 고친 뒤 따라오는 일

#### 1. 고치기 전에 — 제목과 손질 원문

- **장 제목을 바꾸거나, 장을 지우거나 합치면 그 장을 가져가는 `조립.py`가 멈춘다**(「통합반 N일차에서 장을 찾지 못함」). 꼭 필요할 때만 하고, 바꾼 것을 적어 둔다.
- 장 안의 문구를 고쳤는데 그 문구가 어느 `조립.py`의 손질 원문이면 그 스크립트도 멈춘다(「바꿀 말이 0번 있음」). 고치기 전에 찾아본다.

```bash
grep -rn --include='조립.py' '고치려는 문구' production/decks
```

- 멈춘 손질은 지우지 말고 **뜻**을 본다. 그 손질이 하던 일(회차 표기 바꾸기, 빠진 장을 가리키는 말 고치기, 풀네임 붙이기)을 원 덱이 이미 해 놓았으면 손질을 지우고, 아니면 새 원문에 맞춰 다시 건다.

#### 2. 원 덱 빌드

(가) 2 · 3과 같다.

#### 3. 조립 스크립트 27개를 다시 돌린다

```bash
python3 .claude/skills/hyd-course-deck/scripts/재조립.py --dry-run     # 돌릴 스크립트와 읽는 통합반 일차만 본다(아무것도 바꾸지 않는다)
python3 .claude/skills/hyd-course-deck/scripts/재조립.py --day 3       # 통합반 3일차를 읽는 스크립트만 돌린다
python3 .claude/skills/hyd-course-deck/scripts/재조립.py               # 27개를 모두 돌린다
```

- 이 도구는 `practical/만들기_01일차.py`와 `조립.py` 26개를 차례로 돌리고, 멈춘 스크립트와 그 까닭을 모아 보인다. 스크립트 하나만 돌리려면 `python3 production/decks/<과정>/<dayNN|sessionNN>/조립.py`다.
- 고친 일차를 쓰는 덱만 돌려도 된다(대응표는 `production/decks/README.md`). 전부 돌려도 바뀌지 않은 덱은 같은 결과가 나온다.
- 멈추면 그 `조립.py`의 순서표나 손질 원문을 원 덱의 지금 모습에 맞춰 고치고 다시 돌린다.
- 멈추지 않고 지나가는 변화도 있다. 원 덱에 새로 넣은 「N일차에」 같은 일차 언급, 그 과정에 싣지 않은 장을 가리키는 말은 조립 덱에서 틀린 말이 된다. 조립 뒤 `git diff`로 조립 덱 MD의 바뀐 줄을 읽는다.
- 원 덱에 새 장을 넣었으면 조립 덱에는 저절로 들어가지 않는다. 그 회차의 실라버스 항목과 분량을 보고 `ORDER`에 넣을지 정한다(실전반 8일차는 통합반 11일차를 전부 가져오는 덱이라 새 장도 넣는다).

#### 4. 바뀐 덱만 빌드

```bash
python3 .claude/skills/hyd-course-deck/scripts/재조립.py --build-only   # 조립은 건너뛰고, 덱 MD가 커밋과 다른 덱만 빌드한다
```

- 3과 4를 한 번에 하려면 `재조립.py --build`(또는 `--day 3 --build`)다. 멈춘 스크립트가 있으면 빌드하지 말고 먼저 고친다.
- 「바뀐 덱」은 `git status`에서 덱 MD가 커밋과 다른 덱이다. 이미 커밋한 뒤라면 이 도구는 바뀐 덱을 찾지 못하므로, `git -c core.quotepath=false diff --name-only <고치기 전 커밋> HEAD -- production/decks`로 덱 MD를 가려 (가) 2의 명령으로 하나씩 빌드한다.
- 렌더 없이 빌드만 하므로 빠르다. 그 뒤 화면이 바뀐 장 몇 곳을 골라 (가) 3의 방법으로 렌더해 본다.

#### 5. 배포 묶음 다시 만들기

```bash
python3 .claude/skills/hyd-course-deck/scripts/배포묶음.py           # production/dist/교재_전체.zip을 다시 만든다(PPTX 38개)
python3 .claude/skills/hyd-course-deck/scripts/배포묶음.py --check   # zip이 과정 폴더의 PPTX와 같은지만 본다
```

묶음의 구성은 `production/dist/README.md`에 있다. `--check`가 「검사 통과」를 내면 끝이다. PowerPoint에서 PPTX를 열어 둔 채면 잠금 파일(`~$…pptx`)이 있다고 알린다. 닫고 다시 한다.

#### 6. 현황표의 숫자 맞추기

장수가 바뀌었으면 아래 네 곳을 같은 값으로 고친다.

| 어디 | 무엇 |
|---|---|
| `문서/교재/2_기준.md` 13 · 13-1 · 13-2절 | 전체 장수, 단원별 본문 장수, 실습 건수, 가져옴 / 새로 |
| `production/decks/README.md` 머리 문단 | 과정별 장수 |
| `문서/시스템/3_현황.md` 1절 「교재(슬라이드)」 줄 | 과정별 장수 |
| `문서/교재/3_현황.md` 1절 | 장수와 합계 |

세는 법:

```bash
python3 .claude/skills/hyd-course-deck/scripts/장수.py --units   # 38개 덱의 전체 · 본문 · 실습 간지 수와 단원별 본문 장수
```

본문 장수는 간지와 다음 간지 사이의 이론 본문 장 수다(실습 설명, 용어 정리, 퀴즈 제외 — 제작 기준 13절 머리). 가져옴 / 새로의 「새로」는 그 덱 폴더 `새장_*.md`의 장 수(`grep -c '^## SLIDE ' <파일>`)이고 「가져옴」은 전체에서 그것을 뺀 수다. 실습 간지의 번호가 바뀌어도 `실습_목록.md`는 고칠 것이 없다(제목만 싣는다). 간지의 제목을 바꿨을 때만 고친다.

### (다) 도구의 알려진 제약

형식의 전체는 `.claude/skills/lecture-deck/references/덱MD-PPTX형식.md`에 있다. 아래는 작업하며 자주 걸린 것이다.

| 제약 | 내용 | 걸렸을 때 |
|---|---|---|
| 메시지는 한 줄 · 한 문장 | 두 문장을 이으면 실패하고, 한 줄(16pt)을 넘으면 넘침으로 멈춘다. 한글로 대략 46~60자 | 문장을 줄인다. 조립 덱의 손질로 메시지를 늘릴 때도 같다 |
| 제목은 한 줄 | 28pt 한 줄. 표지와 간지만 ` / `로 줄을 끊는다 | 제목을 줄인다(조립에 영향 — (나) 1) |
| 요소 수 한도 | 유형마다 범위가 있다: 카드 2~4, 비교 정확히 2, 흐름 2~6, 단계 3~5, 풀이 2~6, 표 2~9, 구조 2~12, 파이프라인 3~7, 관계도 2~8, 코드의 짚을 점 0~4, 그림의 짚을 점 0~4, 문답 보기 2~5, 목차 2~9 | 장을 나누거나 유형을 바꾼다 |
| 요소 한 줄은 세 칸까지 | `칸1 \| 칸2 \| 칸3`. 표도 3열이다. 구분자 `\|`는 앞을 띄운다 | 넷째 열이 필요하면 칸2 안에 ` / `로 줄을 나누거나 장을 나눈다 |
| 표의 셋째 칸은 세 줄까지 | ` / `로 줄을 바꾼다 | 문구를 줄인다 |
| 꼬리표가 칸보다 넓으면 실패 | 카드 · 비교의 셋째 칸 | 문구를 줄인다 |
| 삽화 라벨 | 16개까지, 가운데 정렬뿐, 크기는 두 단계(기본 13.5 / 11pt, `라벨: 큰`이면 16 / 13pt). 셋째 칸은 `x,y[,폭]`이고 폭의 기본은 그림 폭의 16 %. 이름 칸을 비우면(`| 설명 | x,y`) 설명 줄만 작은 일반 글씨로 쓴다(그래프의 관계 이름처럼) | 라벨이 끊기면 폭 값을 넓히거나 풀네임을 설명 줄로 내린다 |
| 코드 장 | `코드:` 안의 ` / `(앞뒤 공백)는 줄바꿈, 글자 그대로의 빗금은 `\/`. 코드 상자의 높이는 본문 영역을 넘지 못한다 | 줄이 많으면 상자 아래가 잘릴 수 있으니 렌더로 본다. 길면 장을 나눈다(몇 줄부터 잘리는지는 이 문서에서 재지 않았다 — 확인 필요) |
| `**` | 메시지와 요소 안의 `**굵게**`는 강조색으로 그려진다. 요소의 칸1 전체를 `**`로 감싸면 강조 칸이 된다. 짝이 맞지 않으면 그 뒤가 모두 강조로 그려진다 | 짝을 맞춘다 |
| 유니코드 빼기표(−, U+2212) 금지 | 화면 문구에 있으면 실패한다(덱 글꼴에 없어 다른 글꼴로 바뀐다). 노트는 검사하지 않는다 | 하이픈(-)을 쓴다 |
| 허용되지 않는 칸 | `핵심` `설명` `다음` `현재`는 없앤 칸이며 쓰면 실패한다 | 형식 문서의 허용 칸을 쓴다 |
| 아이콘 수 | 유형마다 정해져 있다(요소 수와 같게 또는 0개. 파이프라인은 필수) | `scripts/find_icon.py <낱말>`로 찾는다 |
| 그림 경로 | 덱 MD 위치 기준 상대 경로이고 파일이 없으면 실패한다 | 조립 덱은 통합반 일차 폴더의 `figures/`를 가리킨다(스크립트가 바꾼다) |
| 관계도의 좌표 | 두 원이 너무 가까우면 실패한다 | 좌표를 벌린다 |
| 렌더 잠금 | 렌더는 파일 잠금으로 한 번에 하나씩 돈다. 다른 렌더가 돌고 있으면 기다린다. 20분을 넘기면 도구가 끊고 알린다. `soffice` 프로세스를 죽이지 않는다 | 기다린다. 여러 덱을 동시에 렌더하지 않는다 |
| 렌더 폴더 | 매번 새 이름으로 쓴다. 경로가 약 235자를 넘으면 멈춘다 | 짧은 경로를 쓴다 |
| 글꼴 | 맑은 고딕이 아닌 글꼴로 그려지면 렌더가 멈춘다 | 맑은 고딕을 설치한다 |

도구의 한계를 만나면 우회하지 않고 도구를 고치는 것이 원칙이다(제작 기준 12.1절). 다만 도구를 고치면 38개 덱 전부의 화면이 달라질 수 있으니, 고친 뒤에는 덱 여럿을 렌더해 본다.

스킬(도구와 형식 문서)은 저장소의 `.claude/skills/`가 **유일한 원본**이다. 고칠 때는 여기서 고친다(목록은 `.claude/skills/README.md`).

| 규칙 | 내용 |

## 2부. 덱 새로 만들기와 전체 점검

이 문서는 새 일차 · 회차의 덱을 만들거나, 전체를 다시 점검하거나, 실라버스가 바뀌어 덱을 크게 손봐야 할 때 읽는다.

무엇을 어떻게 써야 하는가는 `문서/교재/2_기준.md`(특히 12절 「만들기와 점검」, 13-1 · 13-2절)에 있다. 이 문서는 **작업을 어떤 단계로 나누어 누구에게 맡겼는가**와 그때 배운 것을 적는다. 단계마다 쓴 지시문은 `지시문/`에 있고 쓰임은 `지시문/README.md`에 있다. 이미 있는 덱을 고치는 순서와 명령은 `4_만드는_법.md` 1부다.

### 1. 통합반 원 덱(새 일차)을 만드는 흐름

```
사실 조사 → 쓰기 → 검토 → 반영 → (여러 일차를 같이 만들었으면) 일차 사이 맞춤
```

| 단계 | 하는 일 | 산출물 | 지시문 |
|---|---|---|---|
| ① 사실 조사 | 실라버스 이론 행의 항목마다 표준 정의, HYD의 대응물과 근거, 교재에 쓸 실제 예를 저장소에서 찾는다. 확인하지 못한 것과 실라버스가 구현과 다른 곳을 따로 모은다. 읽기 전용이다 | `문서/교재/통합반_…_기술사실표.md` | `사실조사_지시.md` |
| ② 쓰기 | 장 목록(제목과 메시지)을 먼저 짜고, 본문 · 노트 · 제작 기준 칸 · 삽화를 쓴 뒤 빌드하고 전 장을 렌더로 본다 | 덱 MD, PPTX, `figures/` | `새일차쓰기_지시.md` |
| ③ 검토 | 쓴 작업자가 검토자 하나를 불러 덱 MD 전체와 렌더 전 장을 보게 한다. 검토자는 고치지 않고 상 · 중 · 하 목록을 낸다 | 검토서(작업 폴더) | `새일차검토_지시.md` |
| ④ 반영 | 쓴 작업자가 상 · 중은 모두, 하는 판단해 반영하고 다시 빌드한다. 기준이나 사실과 어긋나는 제안은 따르지 않고 이유를 적는다 | 고친 덱 | `새일차쓰기_지시.md`의 「검토와 반영」 |
| ⑤ 일차 사이 맞춤 | 용어, 약어 풀네임의 자리, 같은 예의 값을 앞뒤 일차 덱과 대조한다(제작 기준 10 · 12.2절) | 고친 덱 | 따로 없다(`점검반영_지시.md`의 「덱 사이의 결정」이 그 결과다) |

새 덱을 다 만든 뒤 할 일: 제작 기준 13절 현황표, `production/decks/README.md`, `3_현황.md`의 숫자를 맞추고(`4_만드는_법.md` 1부 (나) 6), 배포 묶음을 다시 만든다.

### 2. 조립 덱(실전반 일차, 오프라인 회차)을 만드는 흐름

```
계획표 → 조립 → 검토 → 반영 → 과정 전체 맞춤
```

| 단계 | 하는 일 | 산출물 | 지시문 |
|---|---|---|---|
| ① 계획표 | 실라버스 항목마다 통합반 덱의 어느 장을 가져올지 고른다. 덱 전체를 통독하지 않고 스크립트로 `장 번호 \| 유형 \| 제목 \| 메시지` 목록을 뽑아 고른다. 손질할 문구(원문 → 바뀔 문구)와 새로 쓸 장의 명세를 적는다. 읽기 단계라 아무것도 고치지 않는다 | 계획표(작업 폴더) | `실전반계획_지시.md`, `오프라인계획_지시.md` |
| ② 조립 | 계획표를 `조립.py`의 순서표와 손질 목록으로 옮기고, 새 장을 `새장_*.md`에 쓰고, 조립 → 빌드한다. 조립본을 전 장 통독해 정의 없는 용어와 틀린 지시어를 찾는다 | `조립.py`, `새장_*.md`, 덱 MD, PPTX | `실전반쓰기_지시.md`, `오프라인쓰기_지시.md` |
| ③ 검토 | 검토자 하나가 맡은 덱 전부를 본다. 장 하나하나의 문장이 아니라 **조립해서 생긴 문제**를 본다 | 검토서(작업 폴더) | `실전반검토_지시.md` |
| ④ 반영 | 상 · 중을 `조립.py`와 `새장_*.md`에 반영하고 다시 조립 · 빌드한다. 통합반 원문의 결함이면 고치지 않고 보고한다 | 고친 덱 | `오프라인쓰기_지시.md`의 「검토」 |
| ⑤ 과정 전체 맞춤 | 회차 묶음을 나눠 만들었으면 과정 전체를 순서대로 보고 풀네임의 자리, 뒤 회차가 전제하는 것, 겹친 장과 퀴즈, 틀을 맞춘다 | 고친 덱 | `오프라인맞춤_지시.md` |

- 한 작업자가 ①~④를 이어서 할 때는 `오프라인일괄_지시.md`를 앞의 두 문서와 함께 준다.
- 새 `조립.py`의 본보기는 `production/decks/practical/day07/조립.py`(원천이 한 일차)와 `production/decks/integrated-offline/session10/조립.py`(원천이 두 일차)다. 새 장 원고의 본보기는 `production/decks/practical/day07/새장_07일차.md`다.
- 조립 작업자가 통합반 원문의 결함을 보고하면 모아서 원 덱에서 한 번에 고친다(`원덱결함_지시.md`). 그 뒤 조립 스크립트를 모두 다시 돌린다.

### 3. 전체 점검 → 반영 → 재조립의 흐름

```
점검(고치지 않음) → 원 덱 반영 → 조립 덱 재작업 → 배포 묶음과 현황표
```

| 단계 | 하는 일 | 지시문 |
|---|---|---|
| ① 점검 | 덱을 범위로 나눠 점검자에게 준다(지난번은 여섯: 통합반 1~4 · 5~8 · 9~11일차, 실전반 온라인, 통합반 오프라인, 실전반 오프라인). 모든 점검자가 같은 **기준선**(통합반 1일차 온톨로지 단원과 3일차 첫 단원)을 먼저 정독한다. 산출물은 덱별 점수표, 고칠 것 목록, 「뒤로 갈수록 품질이 떨어졌는가」의 답, 확인하지 못한 것이다 | `전체점검_지시.md` |
| ② 조율 | 여섯 결과를 모아 **덱 사이의 결정**을 먼저 정한다(같은 대상의 이름, 값의 벌, 일차 표기 등). 사용자 결정이 필요한 것은 묻는다 | `점검반영_지시.md`의 「덱 사이의 결정」이 지난번의 결과다 |
| ③ 원 덱 반영 | 통합반 원 덱을 일차 묶음으로 나눠 고친다. 조립 덱 점검이 「원문」이라고 표시한 항목도 여기서 고친다. 제목을 바꾸거나 장을 지우면 「조립에 영향」 표로 보고받는다 | `점검반영_지시.md` |
| ④ 조립 덱 재작업 | 원 덱이 다 고쳐진 뒤에, 과정별로 조립을 다시 돌려 멈추는 곳을 고치고 조립 덱의 점검 결과를 반영한다 | `조립재작업_지시.md` |
| ⑤ 마무리 | 배포 묶음, 현황표의 숫자 | `4_만드는_법.md` 1부 (나) 5 · 6 |

화면만 따로 보려면 `화면확인_지시.md`를 쓴다(내용은 보지 않고 넘침 · 겹침 · 깨진 그림만 본다).

지난 점검의 결과 요지는 `3_현황.md` 5절에 있다. 다음 점검은 그 표와 견주면 된다.

### 4. 실라버스가 바뀌었을 때

실라버스는 사용자가 직접 쓴다. 바뀐 xlsx를 받으면 고치기 전에 **무엇이 달라지는지 먼저 사용자에게 말한다**(`5_결정_기록.md` 1절).

| 바뀐 것 | 할 일 |
|---|---|
| 이론 행의 제목 · 상세 내용 | 그 행에 해당하는 단원과 대조한다(항목 → 장 번호). 빠진 항목이 생겼으면 사실표에 근거가 있는지 보고 장을 더한다. 근거가 없으면 사실 조사부터 한다 |
| 이론 행의 시간 | 장수는 내용이 정하므로 그대로 둔다. 대본의 길이만 다시 재서 적는다 |
| 실습 행의 추가 · 삭제 · 제목 | 실습 간지와 설명 장(2장)을 더하거나 빼거나 고친다. 실습 가이드의 목록(`실습_목록.md`)도 다시 뽑는다 |
| 이론 ↔ 실습 구분 | 덱의 틀과 목차의 구분을 바꾼다(지난 예: ProcessGPT 이론 단원 → 시연 실습) |
| 통합반 시트가 바뀌었다 | 원 덱을 고친 뒤 조립 덱까지 다시 만든다(`4_만드는_법.md` 1부 (나)) |
| 실전반 · 오프라인 시트만 바뀌었다 | 그 덱의 `조립.py` 순서표와 `새장_*.md`만 고친다 |

저장소의 xlsx를 새 파일로 바꾸고, `2_기준.md` 1절과 11절, `3_현황.md`가 가리키는 실라버스 파일 이름이 맞는지 본다.

### 5. 일을 나누는 방식

| 무엇 | 어떻게 했는가 |
|---|---|
| 지시는 파일로 | 공통 지시를 문서 하나로 쓰고, 작업자마다 다른 것(맡은 범위, 산출물 이름)만 프롬프트에 적었다. 같은 일을 여럿에게 줄 때 기준이 어긋나지 않는다 |
| 읽기와 쓰기를 가른다 | 계획 · 검토 · 점검은 「아무것도 고치지 않는다」로 맡기고 산출물을 작업 폴더에만 쓰게 했다 |
| 모델 | 읽기 · 계획 · 검토 · 문서는 가벼운 모델, 쓰기는 Opus. fable 모델은 쓰지 않는다(`5_결정_기록.md` 3절) |
| 조율자의 몫 | 커밋과 push, 덱 사이의 결정, 현황표와 인계 문서, 사용자에게 묻는 일. 작업자는 커밋하지 않는다 |
| 보고는 짧게, 형식을 정해 | 장수(실라버스 분과 나란히), 따르지 않은 제안과 이유, 눈으로 본 범위와 못 본 장을 반드시 받는다 |
| 렌더는 차례로 | 렌더는 한 번에 하나만 돈다. 작업자 여럿이 같이 렌더하면 서로 기다린다. 작업자에게 「기다리는 것이 정상, soffice를 죽이지 않는다」고 적어 준다 |
| 끊김에 대비 | 긴 작업은 단위(회차) 하나가 끝날 때마다 진행 파일에 한 줄씩 적게 했다 |

### 6. 이 작업에서 배운 것

| 배운 것 | 다음에는 |
|---|---|
| 일차를 동시에 따로 쓰면 덱 사이의 용어와 값이 어긋난다. 5~11일차를 따로 쓴 결과 같은 산출물이 「추천안 / 조치 카드 / 추천 카드 / 제안」으로, 같은 경보가 두 이름으로 불렸고, 같은 장면을 두 일차가 다시 설명했다 | 쓰기 전에 **용어 기준을 먼저 준다**(제작 기준 8절 「덱 사이의 용어」가 그 결과다). 끝에 일차 사이 맞춤을 반드시 한 번 한다 |
| 같은 사건의 값이 실행 회차에 따라 두 벌이었다(1~8일차와 9~11일차). 말없이 바뀌어 조립 덱에서는 한 회차 안에서도 섞였다 | 사실 조사 때 「어느 실행 기록의 값인가」를 사실표에 적는다. 벌이 바뀌는 자리에서 한 번 밝힌다 |
| 정리(Wrap-up) 단원이 약해지기 쉽다. 표 · 비교 · 카드가 이어지고, 앞 장을 그대로 되풀이하고, 노트가 한두 문장이 된다 | 정리 단원에도 그림을 두고, 「되풀이」가 아니라 「잇는」 관점의 장으로 쓴다. 검토 때 정리 단원을 따로 지목한다 |
| 검토 뒤 고친 장만 다시 보면 최종본 전 장을 본 사람이 없게 된다 | 마지막에 전 장 화면 확인을 따로 한다(`화면확인_지시.md`). 보고에는 「못 본 장」을 번호로 받는다 |
| 조립 덱은 장을 골라 온 탓에 정의 없는 용어가 생긴다. 정의하던 장이 빠지면 뒤 장의 용어 · 값 · 번호가 설명 없이 나오고, 퀴즈의 근거가 화면에서 사라지고, 실습을 받치는 이론이 없어진다 | 새로 쓰지 말고 통합반의 정의 장을 더 가져와 메운다(단원이 한두 장 넘어도 된다). 조립본은 전 장을 통독한다 |
| 가져온 장의 「지난 시간」 「N일차에」 「앞에서 본」은 다른 과정에서 틀린 말이 된다 | 덱과 노트에 그런 말을 쓰지 않는다(`2_기준.md` 29-2 · 8번). 과정별 손질 목록은 새 조립(단원 · 과정별 시간표)으로 바꿀 때 없앤다 |
| 약어의 풀네임은 「그 과정에서 처음 나오는 자리」가 과정마다 다르다 | 회차 묶음을 나눠 만들 때는 새로 붙이지 않게 하고, 과정 전체 맞춤에서 한 번에 붙인다 |
| 원 덱의 제목을 바꾸면 조립 스크립트가 멈추고, 문구를 바꾸면 손질 원문이 어긋난다 | 원 덱을 고칠 때 「조립에 영향」 표를 받는다. 고치기 전에 `조립.py`들을 문자열로 검색한다 |
| 실습 설명 장의 메시지가 「이 실습을 마치면 …」 한 틀로 몰린다 | 일차마다 한두 장은 산출물을 주어로 쓴다 |
| 실습 설명에서 실라버스의 한 구절(「기준 흐름으로 되돌린다」, 「기준 그래프와 랩 그래프는 다르다」)이 빠지기 쉽다. 반대로 근거 없는 구절(「복구 상태 확인」)은 넣으면 안 된다 | 학생이 실제로 하거나 알아야 하는 것은 한 칸 · 한 줄로 싣고, 근거가 없으면 싣지 않고 보고한다 |
| 점검자의 근거 확인은 표본이다 | 「제작 기준 칸의 근거가 헛것인가」를 표본으로 대조하게 한다. 지난번에는 헛근거가 없었다 |
| 검토 · 점검의 지적이 제작 기준과 부딪칠 때가 있다(실라버스의 「시뮬레이션임을 명시」가 덱에 없다는 지적과 제작 기준 3절의 가상 강조 금지) | 작업자는 기준과 어긋나는 제안을 따르지 않고 이유를 보고에 적는다. 실라버스 문구와 기준이 부딪치면 조율자가 사용자에게 묻는다 |

19묶음 모두의 한계:

- 학생의 도구(Copilot)로는 한 번도 돌리지 않았다. 완성본과 기록은 Claude Code로 대신 돌린 것이다.
- 가이드의 사진 자리가 비어 있다.
- 에이전트가 든 묶음(5회차 실습 3 · 4, 7회차 실습 2 · 3 · 4)은 모델을 부르지 않는 파이썬 프로그램이다. 새 기준에 맞지 않는다.
- 시간은 추정이다. Windows에서 돌려 보지 않았다.

없는 것: 포털에서 하는 오프라인 실습의 가이드, 실전반 오프라인 랩.

배운 것: 이어지는 실습을 한꺼번에 나눠 만들면 출발 폴더의 구조가 서로 달라진다. 이어지는 묶음은 앞 묶음이 끝난 뒤에 그 완성본에서 출발시킨다.

### 4. 확인하지 못한 것

- 대본 본문은 작업자에게 나눠 썼다. 전 장을 한 사람이 읽은 적이 없고, 자동 검사(숫자, 이름, 길이)와 일부 장의 확인만 했다. 덱 안의 어긋남은 각 대본 끝의 「제작 확인용」 절에 있다.
- 윤문본도 자동 검사만 거쳤다. 지어낸 설명이 끼어든 곳은 자동으로 잡지 못한다.
- 2~11일차 대본은 퀴즈의 보기를 읽지 않는다.
- 영상은 만든 세션이 들어 보지 못한다. 쉼의 분포를 `ffmpeg`의 `silencedetect`로 재어 견줬을 뿐이다.
- 1일차 실습 3은 포털의 화면과 버튼, 이전 처리 기록의 단계와 걸린 시간을 보고 썼다.

### 5. HYD 시스템을 띄울 때

절차는 `../시스템/4_켜고_돌리는_법.md`에 있다. 1일차 실습 2의 촬영 대본도 그 절차를 따른다.

같은 PC에서 다른 프로젝트가 5432 · 7474 · 7687 · 8080 · 8088 · 5432x 포트를 쓰고 있으면 그 포트를 차지하지 않는다. 저장소 파일은 고치지 않고 이렇게 한다.

- 업무 DB: `it/supabase`를 임시 폴더에 복사해 포트를 바꾸고 `npx supabase@2.119.0 start`로 띄운다.
- compose: `SUPABASE_DSN` · `ENTERPRISE_READ_DSN` · `EFFECTS_SMTP_PORT`를 셸 환경변수로 주고, 겹치는 포트를 옮기는 덧씌움 파일을 `-f`로 더한다.
- 포털은 브라우저에서 8080을 직접 부른다. 자동 조작 브라우저에서는 그 요청을 옮긴 포트로 돌린다.
