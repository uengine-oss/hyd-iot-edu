# 기준 — 실습 랩

실습 하나(코딩 랩 · 도구 실습의 랩 · 대본 · 촬영 · 가이드)를 만들거나 고칠 때 이 문서와 [기준_공통](기준_공통.md)을 끝까지 읽는다. 대본 · 촬영 · 가이드는 L1 순서가 그 단계에 이르면 그 갈래 기준([기준_대본](기준_대본.md) · [기준_촬영](기준_촬영.md) · [기준_실습가이드](기준_실습가이드.md))을 그 단계에서 끝까지 읽는다 — 미리 다 읽지 않는다. 이 갈래의 스킬: hyd-lab-guide.

- **이 갈래의 성향:** 현업 난이도의 문제를 주고 정답은 주지 않는다(L2-3 · L4-1).
- **앞에서 받는 것:** 그 회차 덱의 실습 설명 장(목표 · 산출물 · 성공 기준)과 앞 이론 · 포털 실습에서 세운 개념 이름(L1-2).
- **뒤가 가져가는 것:** 대본 · 촬영은 실제로 돌려 본 시작본 · 화면에 보일 결과 · 확인 조건을, 가이드는 단계 · 명령 · 확인 조건 · 저장 위치를 가져간다. 그러니 대본 전에 강사 참조로 실제로 풀리는 것과 판단이 갈리는 지점 · 확인할 사례를 정해 둔다.

## L1 실습 한 개를 만드는 순서

실습 하나를 시작 → 수행 → 검증 → 저장 → 영상 · 가이드 전달까지 끝낸 뒤 다음 실습으로 간다.

0. **시작 전:** 본보기 실습(L0)의 랩 · 대본을 통독해 「실제 강사가 이렇게 말하고 보인다」를 잡는다. 인계의 옛 완료 표시는 믿지 않고 실제 파일을 연다.
1. **실라버스 행에서 시작한다(가장 중요).** 실라버스를 안 보면 50분 수업이 7분이 된다. 대조표는 기준_공통 G0 「범위와 시간」대로 만들되 실습은 항목마다 영상 구간과 분을 적어, 합이 배정 시간을 채우는지 이 단계에서 본다.
2. **앞 이론 · 앞 포털 실습과 잇기:** 바로 앞 이론 대본(덱의 실습 간지 · 설명 장)과, 코딩 랩이면 앞에서 본 포털 화면에서 연결점을 찾아 기준_공통 G0의 잇는 말이 화면으로 보이게 짠다(포털에 대응 기능이 없으면 앞 이론에서).
3. **랩 강화:** L2 · L4. 대본 전에 강사 참조로 실제로 풀리는지 확인한다(L4-4).
4. **대본:** 기준_대본을 이 단계에서 끝까지 읽고 쓴다.
5. **분량:** 대본으로 계획 시간을 재서 대조표의 합과 맞춘다(L1-1).
6. **리허설 · 녹음 · 촬영:** 기준_촬영을 이 단계에서 끝까지 읽는다. 리허설 1회는 L7-1 ①의 학생 경로 리허설을 겸한다.
7. **검사:** 기술 검사와 따로 수업으로 성립하는지 판정한다(L7).
8. **마무리:** 기준_실습가이드를 이 단계에서 끝까지 읽고 가이드에 실제 화면을 넣어 가이드 · ZIP을 만들고 학생 경로로 받기 시험을 한다. 영상은 other-pc, 문서는 main, 노션 두 과정 회차 페이지에 영상 · 가이드 · ZIP을 연결해 열리는지 확인한다(게시 절차는 기준_촬영 C8, push · 노션 게시는 기준_공통 G4-3대로 묻는다). 완료 표에 커밋 · 해시 · 검증 결과를 적는다.

## L2 실습의 종류와 목적

1. 실습은 과정의 줄기(기준_공통 G0)의 각 단계를 학생이 직접 만들어 보는 곳이다. 구분은 이론과 실습 둘뿐이다 — 도구를 조작해 결과물을 만들거나 실행을 확인하면 강사 혼자 보여 줘도 실습, 결과 예상 · 근거 비교 · Wrap-up은 이론.
2. **포털 도구 실습**은 화면 · 조작이 정해져 있으니 코드 과제를 붙이지 않고 「무엇을 보고 어떻게 판단하는가」의 설명 깊이를 채운다. 이론 안의 짧은 포털 확인을 늘리지 않고, 설치 · 환경 준비 · Notion · arrows.app에도 코드 과제를 기계적으로 붙이지 않는다.
3. **코딩 랩이 과정의 핵심이고 현업 난이도가 최우선이다.** 「약간 어렵게」로는 부족하다 — 규모 · 성격 자체가 현업 수준이어야 한다 — 공장 단위 다출처(자산 대장 · 태그 수백 줄 · 정비 이력 · 품번 변형 부품 마스터 · 판본 다른 점검표)라 눈으로는 못 맞추고 AI와 코드로 대조해야만 풀린다. 문제는 어렵게, 해결은 좋은 습관으로 수월하게. 억지 함정 · 고의 오류가 아니라 현실의 복잡함이고, 기능 수 · 파일 수 · 문서량 · 시간 · 어려운 용어로 난도를 꾸미지 않는다(규모는 대조가 필요해서 커지는 것이다).
4. 재료는 리서치(공식 모범 사례 · 현업 사례)로 근거를 잡고, 부족하면 조사한 현업 문제 유형 · 시뮬레이터 로직을 따라 생성한다(교육용 가상 자료는 기준_공통 G3-3대로 자료 첫머리에 한 번 밝힘). 포털 설비가 단순하면 포털에 묶이지 말고 재료를 키운다. 해피패스 · 구세주 데이터 금지 — 손익으로 지는 대안과 실제로 밟는 비해피 가지를 둔다.
5. **장난감 금지:** 통합반도 단순 예제 실행 · 정답 복사 · 한 번의 AI 요청 · 짧은 요약으로 끝나지 않는다. 자료 대조 · 조건 해석 · 구현 결과 판단이 있고, 결과는 다른 입력 · 경계 · 재실행으로도 확인한다. 이름 · 자료만 바꾼 같은 에이전트를 반복하지 않고, 에이전트 응용은 서로 다른 일을 하게 한다.
6. 활용 맥락은 피지컬 AI와 포털의 지식 · 판단 · 업무 흐름이 중심이고, 자기 Notion 출제 · 채점, 회의 후속 업무처럼 같은 기술을 다른 곳에 쓰는 경험도 넣는다. 회의는 어떤 부서가 어떤 근거 · 제약으로 무엇을 결정하는지, 학습이면 출제 근거 · 채점 기준 · 재도전 결과를 분명히 한다.
7. 랩마다 결정할 업무 · 입력과 출처 · 조건과 예외 · 학생이 구현할 기능 · 결과 확인 방법 · 다음 단계로 가져갈 산출물을 잇고, 결과는 실제 역할이 쓰는 모양으로 남긴다. **랩의 수준은 PBL 목표(기준_공통 G0-4)로 잰다.** 과정 전체로는 기록 추적 → 지식 구조 · 판단 → 근거 추출 → 에이전트 · 도구 → 명세 · 검증 → 승인 · 실행 → 종합 조율이 명세 · 지식 · 출력 계약 · BPMN · 검증 기록으로 남는다.
8. **랩의 목적은 주어진 자료로 모범적으로 바이브 코딩해 결과를 뽑는 습관이다.** 습관(기준_공통 G0-2)은 일관되게, 다양한 경험은 랩 주제로 준다. 실습마다 전면 기법 하나를 둔다(설계 = 탐색으로 함정을 찾고 사람이 결정 / 구현 = 한 기능씩 실제 DB로 확인 / 판정 = 기대 결과를 원문에서 먼저 적고 대조, AI 출력을 기대값으로 복사하지 않음). 흐름은 어려움 먼저 → 습관 순환으로 풀기 → 업무 가치와 다음 활용.
9. **코딩 랩은 개인 GPT 무료 계정으로 끝까지 할 수 있게 설계한다**(계정 · 도구 설정은 환경 세팅 가이드 · 영상). 무료 계정조차 못 쓰는 학생을 위해 학생용 완성본을 하나 준비한다(L4-4).

## L3 지킬 것과 판정 기준

1. 랩이 지킬 것은 실라버스 행이 명시한 대상(예: 실전 2-4의 펌프 축 씰 키트와 HYD-01~03 공급 3행)과 이론의 개념 · 용어뿐이다. 포털은 방향 기준일 뿐이라 시드 자료 · 입력값 · 판정 결과까지 맞추지 않는다.
2. 판정 기준은 「포털과 같은 답」이 아니라 「근거 있는 판단으로 쓸 만한 결과」다.

## L4 제공 경계

1. **설정 · 입력 · 원자료 · 가드레일은 완벽히 주고, 정답 · 해결 로직 · 완성 프롬프트는 주지 않는다. 핵심 로직은 학생이 구현한다**(그 회차 목표라면 DB · MCP 연결도). 아무 요청이나 해도 정답이 자동 완성되는 구조로 만들지 않고, 발판(시작점 · 확인 방법)은 주되 정답은 주지 않는다.
2. 학생의 코딩 도구는 VS Code의 GitHub Copilot과 Codex 둘 다다. 영상 · 리허설은 Codex로 하고 가이드는 두 도구의 채팅 위치를 함께 보인다. **가드레일은 위험한 것만** — 포털 DB · 전체 삭제 · 키 · 원자료 덮어쓰기. 작업 규칙(`AGENTS.md` 등)은 학습 맥락이지 보안 장치가 아니고, 실제 격리는 별도 폴더 · 컨테이너 · 주소 · 랩 DB로 한다. 기존 포털 DB에 랩 데이터를 넣지 않는다.

| 제공물 | 왜 있는가 | 담는 것 | 담지 않는 것 |
|---|---|---|---|
| `START.md` | 학생과 AI가 같은 출발점을 읽는 과제 정의서. 학생은 이것을 자기 말로 다시 정리해 AI에 요구를 전달한다 | 목표, 출발 상태, 학생이 구현할 범위, 「학생이 정할 것」 절(정답 없음), 「이번 범위 밖」, 확인할 사례의 종류, 실행 명령, 완료 판정 원칙, 「바뀐 파일 확인」(원자료 보존 · 요청 밖 파일), 저장 · 다음 실습 | 해결 로직, 정답 값 · 기대 결과 표, 그대로 붙이면 끝나는 완성 프롬프트(AI가 폴더 전체를 읽으므로 넣는 순간 장난감이 된다) |
| 작업 규칙 — `AGENTS.md` · `.github/copilot-instructions.md`(필요하면 `CLAUDE.md`) | 두 도구가 지킬 짧은 맥락과 제약(읽는 위치가 달라 같은 내용을 둔다) | 원자료 보존, 새 결과는 `결과/`, 원자료에 없는 값 만들지 않기, 미확인 · 값 없음 · 0 구별, 무관한 기능 추가 금지, 별도 랩 DB만 사용, 키 미기록, 「정할 것」은 묻고 미결 표시, 「제공 빈 틀」 표시 | 과제 해결 방법 |
| `입력/` | 연결 실습의 독립 시작(앞 단계를 안 했거나 PC가 초기화돼도) | 앞 단계 **완성** 상태(강사가 검증한 판본) | 이번 단계의 답 |
| `자료/`(원자료) | 결과를 판정하는 근거. 함정(중복 · 별칭 · 단위 누락 · 경계)은 실제 업무 자료처럼 남긴다 | 원문 · CSV · 현장 메모 | 정답에 맞추려고 고친 값 |
| `결과/` | 학생 산출물 자리, 저장 · 다시 열기 · 다음 실습 연결의 기준 | README와 열 이름 수준의 빈 틀 | 정답 행 |
| 검사기(`check.py` 등) | 구조 오류를 빨리 찾게 함 | ID · 끝점 · 중복 같은 구조 검사, 「의미와 질문별 답은 원자료와 따로 대조」 출력 | 의미 정답 판정 |
| `guide.html` | 가이드만으로 시작 → 판정 → 저장까지 가게 함 | 단계, 명령, 성공을 판단할 증거(판단 원칙 · 대표 사례), 실제 화면 | 정답 전체 목록, 제작 지시 문구 |

3. **계약 · START에는 형식과 의미만 둔다** — 판정 절차 · 정답 방향을 적으면 AI가 그대로 답으로 쓰고 학생 판단 없이 끝난다. 랩마다 **판단에 따라 결과가 갈리는 지점을 최소 하나** 두고, 강사 참조는 갈래별로 실행해 둔다.
4. **학생용 완성본과 강사 참조를 구별한다.** 학생용 완성본(보기 · 실행용)은 실습 폴더와 **따로 받는 별도 묶음**이다 — 같은 폴더에 있으면 학생의 AI가 읽어 정답이 된다. 강사 참조(판정용 기대 결과 · 갈래별 참조 답안)는 학생에게 주지 않고 학생 폴더 밖(`제작용/실습시작/reference/…`)에만 두며, **실제로 실행해 풀 수 있는 과제임을 증명**한다. 학생 실습 폴더 · 가이드에 강사 폴더 · 강사 참조 · 제작 기록을 가리키는 말을 넣지 않고(패키지 검사는 L8-4), 접속 정보는 `.env`로 받아 학생 폴더에는 값이 빈 `.env`만 둔다.
5. 빈칸을 두면 그 판단을 주석으로 미리 풀지 않고(연출 금지는 기준_공통 G3-8), 이전 기능을 바꾸는 과제까지 모두 빈칸 채우기로 만들지 않는다.
6. 원문 · 교육용 가상 자료 · 제공 실행 발췌의 성격과 시점을 표시하고, 같은 이름이라고 다른 설비 · 요청 · 판본을 합치지 않는다. 제공 사례 · 템플릿 · 완성본과 수업에서 만든 결과를 구별한다. 새 코드 이름은 `제작용/기존제작/labs/STRUCTURE.md`의 영어 이름 규칙을 따르되 기존 한국어 자료를 일괄 개명하지 않는다.

## L5 시작본 · 연결 · 저장

1. 각 실습은 필요한 자료만 받아 독립 시작하고, 연결 실습은 앞 단계 완성 상태를 시작본으로 주고 이번 요구를 구현 · 변경하게 한다. 자기 이전 결과를 가져오는 것은 선택이며 진행 조건이 아니다 — 가져오면 판본 · 입출력 계약을 확인하고 별도 보관한 뒤 쓰며 기존 결과를 덮어쓰지 않는다.
2. 학생 개인 Git · commit/push · 이름/이메일 설정을 필수로 요구하지 않는다(GitHub는 강사 측 원본 · 배포 관리).
3. 학교 PC는 재부팅하면 초기화될 수 있다. 저장 · 내보내기 방법을 안내하고 자동 복구를 약속하지 않으며, 결석 복귀는 회차별 선행 결과 시작본으로 한다.
4. 실행이 필요한 새 쿼리는 전용 랩 DB에서만 확인한다.
5. 결과 생성 · 수정 · 재확인 · 저장 · 다시 열기를 흐름에 넣고, 앞 요청 · 명세 · 지식 구조 · 스킬 · 검증 결과를 다음 실습에서 이어 쓴다.

## L6 과정 차이와 범위

1. 두 과정의 같음 · 다름은 기준_공통 G2 「두 과정의 차이」 표가 정한다(차이는 대본만이 아니라 랩 · 가이드 · 판정에 둔다). 1회차는 독립 코딩 과제 · 차이 설계로 시작하지 않고, 촬영된 Cypher 영상은 두 과정 공통이다.
2. **포털 경계:** 포털 실습은 현재 지원 기능과 승인 자료 안에서 하고 포털 시스템 로직은 절대 바꾸지 않는다. 준비된 도구의 목록 · 읽기는 허용하지만 관리 · 쓰기 설정은 별개다. 학생 등록 · 배포 · 되돌리기 · 학생 서버 등록 · 매뉴얼 등록, 일반 BPMN 등록 · 배포, 임의 도구 서버 추가, 임의 문서 추출을 학생에게 요구하지 않는다. bpmn.io에서 그린 흐름은 기준 흐름 · 매핑과 비교하고, 포털에서는 등록된 흐름을 실행해 이력과 대조한다. 포털 제한은 독립 코딩 랩의 외부 MCP · 직접 만든 MCP · 자기 Notion · 다른 문서 사용을 막지 않는다. 랩 결과가 포털 에이전트에 자동 연동된다고 말하지 않는다.
3. **마지막 적용 실습은 교대 인수인계 한 시나리오다**(통합 온라인 11 · 실전 온라인 8 · 통합 오프라인 9~10 · 실전 오프라인 8~9). 강사 제공 보충 매뉴얼을 기존 제조 스키마로 추출 · 원문 검토 · 추가 적재하고, 설비 · 정비 · ERP 조회로 미완료 · 주의 · 기록 불일치를 정리하는 에이전트 · 스킬을 만들고, bpmn.io의 조회 → 인계안 → 인계자 검토 → 인수자 확인/보완 → 완료 흐름을 포털의 별도 정의 · 시작 폼 · 역할 · 작업에 연결해 실행한다(시작 입력 · 검토 · 보완 분기는 유지). 강사 코드로 허용되는 행동은 제공 문서 검토 · 추가 적재, 에이전트 · 스킬 편집, 제공 교대 BPMN의 표시 이름 · 배치 · 초안 단계 에이전트 배정 · 별도 판본 등록이다. 강사 승인 문서 · 판본 · 수업 행동만 허용하고 임의 문서 · 도구 · 무제한 AI 실행을 열지 않으며, 임의 학생 코드를 자동 연결하지 않는다. 같은 조건의 추출 재사용은 표시하고 사람의 검토 · 적재는 유지한다(제공 문서의 추출 후보 재사용과 에이전트의 현재 자료 조회는 다르다). 인계 확인은 정비 완료 · 실제 조치 · 발주가 아니다.
4. **오프라인 Notion:** 기본은 Notion 없이 한다. 현장에서 설치 · 접속 · MCP 연결과 자기 자료 준비가 되면 강사가 그 교시 안에서 선택 실습으로 하고(과정별 내용은 기준_공통 G2 표), 안 되면 기본 파일 · Git · 시간 MCP 실습을 한다. 온라인 Notion 실습은 유지한다.
5. Notion 학습노트는 학습노트 하나 → 여러 주제 카드 → 자유로운 내용 · 하위 페이지이고 본인 주제로 템플릿을 적용한다. 이론/실습/실수노트 분류나 별도 자료 DB를 강제하지 않는다.
6. 첫 오프라인 그래프 실습에는 Cypher 생성 · 조회 · 조건 · 수정 · 삭제 · 재조회와 노드 속성 확인을 넣는다.

## L7 완성 판정

1. **랩 완성 = 네 가지 모두:** ① 실제 학생 경로 리허설 통과(학생과 같은 입력 · 폴더 · 명령, Codex) ② 검사기가 일부러 망가뜨린 입력을 잡음 ③ 강사 참조 실행(학생 수행을 대신하지 않음) ④ 가이드만으로 다운로드 → 저장 · 다시 열기(받기 시험).
2. **장난감 판정:** 「한 줄 요청」으로도 같은 결과가 나오면 장난감이다. 원문 문장이 그대로 답을 주는 설계 지점은 판별력이 없다. 판정 = 충분히 어려운가 + 습관으로 풀리는가(리허설).
3. **수업 성립 판정은 기술 검사와 별개다:** 대조표 항목이 다 들어갔는지, 설명이 충분한지, 바이브 코딩이 실제로 보이는지, 범위와 시간(기준_공통 G0)을 지키는지.
4. 실행 성공과 학습목표 달성, 배포 환경 검증과 학생 완주 · 이해를 따로 확인하고, 돌리지 못한 것은 `미확인`으로 적는다. AI가 도구 순서를 고르는 실습은 특정 순서만 정답으로 강제하지 않는다. 같은 판본으로 맞춘 뒤(기준_공통 G4-9) 실제 수행을 확인하고, 강사 참조는 리허설에서 실제로 만든 적재 · 조회문으로 확정한다.

## L8 배포와 시작 도구

1. 기본 동선은 PC 로컬 「실습 시작」 도구 → 과정 · 회차 · 실습 선택 → 그 판본만 다운로드 · 압축 해제 → VS Code 폴더와 가이드 열기다. 학생의 명령 입력 · 경로 지정 · Git 설정을 기본 동선에서 없애고, 실패하면 재시도와 수동 ZIP 대안을 준다(ZIP 경로는 대안으로 유지).
2. 같은 실습을 다시 열 때 학생 수정 파일을 덮어쓰지 않고, 새로 시작은 별도 폴더로 한다. 초기화된 PC에서 재다운로드로 시작할 수 있어야 하고, 학교 기본 이미지에 도구가 남는지 · 복구 경로가 있는지, 초기화 뒤 실습 폴더(`D:/HYD-Practice`)의 신뢰 · 쓰기 권한이 살아 있는지 확인한다 — 신뢰가 풀려 VS Code가 제한 모드로 열리면 AI 도구가 동작하지 않는다. 학생은 `.env`에 강의 키 한 줄만 넣는다. 코드 다운로드와 Docker/DB · AI 로그인 · 키 준비를 구별한다.
3. Notion 일반 링크만으로 PC 명령이 실행된다고 쓰지 않는다 — 시작 도구가 다운로드와 VS Code 실행을 맡고 Notion · HTML 가이드는 안내와 링크를 준다. `code -n` 같은 명령은 내부 구현이지 학생 절차가 아니고, 브라우저 버튼 직접 연동은 약속하지 않는다.
4. 학생 패키지에 키 · 개인정보 · 강사 정답이 없어야 한다 — `제작용/실습시작/verify_packages.py`로 검사한다. 실행 의존성은 `_` 접두사 · lock 파일이라는 이유만으로 빼지 않고, 필수 파일이 빠지면 목록을 결과에 맞춰 줄이지 않는다. 개인 절대경로 · 정답 하드코딩 · 로컬 검증용 localhost 목록은 배포하지 않는다.
5. 포털 전체 설치 · 촬영용 clone과 개별 랩 다운로드를 구별한다. 학생은 전체 저장소나 여러 회차를 한꺼번에 받지 않는다.
