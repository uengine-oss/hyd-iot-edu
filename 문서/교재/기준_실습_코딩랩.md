# 기준 — 코딩 랩 (VS Code)

학생이 VS Code에서 AI(GitHub Copilot · Codex)와 직접 만드는 코딩 랩의 랩 · 대본 · 촬영 · 가이드를 만들거나 고칠 때 [기준_공통](기준_공통.md) · [기준_실습](기준_실습.md) 다음에 이 문서를 끝까지 읽는다(촬영 검증 상태는 `제작용/촬영/vscode/촬영준비.md`). 이 갈래의 스킬: hyd-lab-guide.

- **이 갈래의 성향:** 현업 난이도의 문제를 주고 정답은 주지 않는다(K1 · K2). VS Code에서 시작하고, 학생이 좋은 습관으로 직접 풀어야 결과가 나온다.
- **뒤가 가져가는 것:** 대본 · 촬영은 실제로 돌려 본 시작본 · 화면에 보일 결과 · 확인 조건을, 가이드는 단계 · 명령 · 확인 조건 · 저장 위치를 가져간다. 그러니 대본 전에 강사 참조로 실제로 풀리는 것과 판단이 갈리는 지점 · 확인할 사례를 정해 둔다. 가이드에는 학생 실습 폴더에 있는 것(`START.md` · 입력 · 원자료 · 확인 사례 · 저장 위치)만 쓰고, 정답 · 해결 로직 · 완성 프롬프트 · 강사 폴더나 강사 참조를 가리키는 말 · 키 · 접속값은 넣지 않으며, 학생용 완성본은 실습 폴더와 따로 받는 묶음이라고만 안내한다(계정이 없는 학생이 결과를 확인하는 용도).

| 시작 화면 | 하는 것 | 없는 것 |
|---|---|---|
| VS Code에서 받은 실습 폴더를 연 상태 | 바이브 코딩 일곱 단계(기준_공통 G0-2)로 요구를 내 말로 정하고, 작게 구현하고, 결과를 원자료와 대조하고, 저장 · 다시 열기 | 학생에게 주는 정답 · 해결 로직 · 완성 프롬프트, 코드 해설, 포털 관찰 실습의 화면 설명 |

## K1 설계 — 현업 난이도, 정답 없는 과제

1. **코딩 랩이 과정의 핵심이고 현업 난이도가 최우선이다.** 「약간 어렵게」로는 부족하다 — 규모 · 성격 자체가 현업 수준이어야 한다 — 공장 단위 다출처(자산 대장 · 태그 수백 줄 · 정비 이력 · 품번 변형 부품 마스터 · 판본 다른 점검표)라 눈으로는 못 맞추고 AI와 코드로 대조해야만 풀린다. 문제는 어렵게, 해결은 좋은 습관으로 수월하게. 억지 함정 · 고의 오류가 아니라 현실의 복잡함이고, 기능 수 · 파일 수 · 문서량 · 시간 · 어려운 용어로 난도를 꾸미지 않는다(규모는 대조가 필요해서 커지는 것이다).
2. 재료는 리서치(공식 모범 사례 · 현업 사례)로 근거를 잡고, 부족하면 조사한 현업 문제 유형 · 시뮬레이터 로직을 따라 생성한다(교육용 가상 자료는 기준_공통 G3-3대로 자료 첫머리에 한 번 밝힘). 포털 설비가 단순하면 포털에 묶이지 말고 재료를 키운다. 해피패스 · 구세주 데이터 금지 — 손익으로 지는 대안과 실제로 밟는 비해피 가지를 둔다.
3. **장난감 금지:** 통합반도 단순 예제 실행 · 정답 복사 · 한 번의 AI 요청 · 짧은 요약으로 끝나지 않는다. 자료 대조 · 조건 해석 · 구현 결과 판단이 있고, 결과는 다른 입력 · 경계 · 재실행으로도 확인한다. 이름 · 자료만 바꾼 같은 에이전트를 반복하지 않고, 에이전트 응용은 서로 다른 일을 하게 한다.
4. 활용 맥락은 피지컬 AI와 포털의 지식 · 판단 · 업무 흐름이 중심이고, 자기 Notion 출제 · 채점, 회의 후속 업무처럼 같은 기술을 다른 곳에 쓰는 경험도 넣는다. 회의는 어떤 부서가 어떤 근거 · 제약으로 무엇을 결정하는지, 학습이면 출제 근거 · 채점 기준 · 재도전 결과를 분명히 한다.
5. 랩마다 결정할 업무 · 입력과 출처 · 조건과 예외 · 학생이 구현할 기능 · 결과 확인 방법 · 다음 단계로 가져갈 산출물을 잇고, 결과는 실제 역할이 쓰는 모양으로 남긴다. **랩의 수준은 PBL 목표(기준_공통 G0-4)로 잰다.** 과정 전체로는 기록 추적 → 지식 구조 · 판단 → 근거 추출 → 에이전트 · 도구 → 명세 · 검증 → 승인 · 실행 → 종합 조율이 명세 · 지식 · 출력 계약 · BPMN · 검증 기록으로 남는다.
6. **랩의 목적은 주어진 자료로 모범적으로 바이브 코딩해 결과를 뽑는 습관이다.** 습관(기준_공통 G0-2)은 일관되게, 다양한 경험은 랩 주제로 준다. 실습마다 전면 기법 하나를 둔다(설계 = 탐색으로 함정을 찾고 사람이 결정 / 구현 = 한 기능씩 실제 DB로 확인 / 판정 = 기대 결과를 원문에서 먼저 적고 대조, AI 출력을 기대값으로 복사하지 않음). 흐름은 어려움 먼저 → 습관 순환으로 풀기 → 업무 가치와 다음 활용.
7. **코딩 랩은 개인 GPT 무료 계정으로 끝까지 할 수 있게 설계한다**(계정 · 도구 설정은 환경 세팅 가이드 · 영상). 무료 계정조차 못 쓰는 학생을 위해 학생용 완성본을 하나 준비한다(K2-4).
8. 랩이 지킬 것은 실라버스 행이 명시한 대상(예: 실전 2-4의 펌프 축 씰 키트와 HYD-01~03 공급 3행)과 이론의 개념 · 용어뿐이다. 포털은 방향 기준일 뿐이라 시드 자료 · 입력값 · 판정 결과까지 맞추지 않는다.
9. 판정 기준은 「포털과 같은 답」이 아니라 「근거 있는 판단으로 쓸 만한 결과」다.

## K2 제공 경계

1. **설정 · 입력 · 원자료 · 가드레일은 완벽히 주고, 정답 · 해결 로직 · 완성 프롬프트는 주지 않는다. 핵심 로직은 학생이 구현한다**(그 회차 목표라면 DB · MCP 연결도). 아무 요청이나 해도 정답이 자동 완성되는 구조로 만들지 않고, 발판(시작점 · 확인 방법)은 주되 정답은 주지 않는다.
2. 학생의 코딩 도구는 VS Code의 GitHub Copilot과 Codex 둘 다다. 영상 · 리허설은 Codex로 하고 가이드는 두 도구의 채팅 위치를 함께 보인다. **가드레일은 위험한 것만** — 포털 DB · 전체 삭제 · 키 · 원자료 덮어쓰기. 작업 규칙(`AGENTS.md` 등)은 학습 맥락이지 보안 장치가 아니고, 실제 격리는 별도 폴더 · 컨테이너 · 주소 · 랩 DB로 한다. 기존 포털 DB에 랩 데이터를 넣지 않는다.

| 제공물 | 왜 있는가 | 담는 것 | 담지 않는 것 |
|---|---|---|---|
| `START.md` | 학생과 AI가 같은 출발점을 읽는 과제 정의서. 학생은 이것을 자기 말로 다시 정리해 AI에 요구를 전달한다 | 목표, 출발 상태, 학생이 구현할 범위, 「학생이 정할 것」 절(정답 없음), 「이번 범위 밖」, 확인할 사례의 종류, 실행 명령, 완료 판정 원칙, 「바뀐 파일 확인」(원자료 보존 · 요청 밖 파일), 저장 · 다음 실습 | 해결 로직, 정답 값 · 기대 결과 표, 그대로 붙이면 끝나는 완성 프롬프트(AI가 폴더 전체를 읽으므로 넣는 순간 장난감이 된다) |
| 작업 규칙 — `AGENTS.md` · `.github/copilot-instructions.md`(필요하면 `CLAUDE.md`) | 두 도구가 지킬 짧은 맥락과 제약(읽는 위치가 달라 같은 내용을 둔다) | 원자료 보존, 새 결과는 `결과/`, 원자료에 없는 값 만들지 않기, 미확인 · 값 없음 · 0 구별, 무관한 기능 추가 금지, 별도 랩 DB만 사용, 키 미기록, 「정할 것」은 묻고 미결 표시, 「제공 빈 틀」 표시 | 과제 해결 방법 |
| `입력/` | 연결 실습의 독립 시작(앞 단계를 안 했거나 PC가 초기화돼도) | 앞 단계 **완성** 상태(강사가 검증한 판본) | 이번 단계의 답 |
| `자료/`(원자료) | 결과를 판정하는 근거. 함정(중복 · 별칭 · 단위 누락 · 경계)은 실제 업무 자료처럼 남긴다 | 원문 · CSV · 현장 메모 | 정답에 맞추려고 고친 값 |
| `결과/` | 학생 산출물 자리, 저장 · 다시 열기 · 다음 실습 연결의 기준 | README와 열 이름 수준의 빈 틀 | 정답 행 |
| 검사기(`check.py` 등) | 구조 오류를 빨리 찾게 함 | ID · 끝점 · 중복 같은 구조 검사, 「의미와 질문별 답은 원자료와 따로 대조」 출력 | 의미 정답 판정 |
| `guide.html` | 가이드만으로 시작 → 판정 → 저장까지 가게 함 | 단계, 명령, 성공을 판단할 증거(판단 원칙 · 대표 사례), 실제 화면 | 정답 전체 목록, 제작 지시 문구 |

3. **계약 · START에는 형식과 의미만 둔다** — 판정 절차 · 정답 방향을 적으면 AI가 그대로 답으로 쓰고 학생 판단 없이 끝난다. 랩마다 **판단에 따라 결과가 갈리는 지점을 최소 하나** 두고, 강사 참조는 갈래별로 실행해 둔다.
4. **학생용 완성본과 강사 참조를 구별한다.** 학생용 완성본(보기 · 실행용)은 실습 폴더와 **따로 받는 별도 묶음**이다 — 같은 폴더에 있으면 학생의 AI가 읽어 정답이 된다. 강사 참조(판정용 기대 결과 · 갈래별 참조 답안)는 학생에게 주지 않고 학생 폴더 밖(`제작용/실습시작/reference/…`)에만 두며, **실제로 실행해 풀 수 있는 과제임을 증명**한다. 학생 실습 폴더 · 가이드에 강사 폴더 · 강사 참조 · 제작 기록을 가리키는 말을 넣지 않고(패키지 검사는 기준_실습 P12-5), 접속 정보는 `.env`로 받아 학생 폴더에는 값이 빈 `.env`만 둔다.
5. 빈칸을 두면 그 판단을 주석으로 미리 풀지 않고(연출 금지는 기준_공통 G3-8), 이전 기능을 바꾸는 과제까지 모두 빈칸 채우기로 만들지 않는다.
6. 원문 · 교육용 가상 자료 · 제공 실행 발췌의 성격과 시점을 표시하고, 같은 이름이라고 다른 설비 · 요청 · 판본을 합치지 않는다. 제공 사례 · 템플릿 · 완성본과 수업에서 만든 결과를 구별한다. 새 코드 이름은 `제작용/기존제작/labs/STRUCTURE.md`의 영어 이름 규칙을 따르되 기존 한국어 자료를 일괄 개명하지 않는다.

## K3 시작본 · 연결 · 저장

1. 각 실습은 필요한 자료만 받아 독립 시작하고, 연결 실습은 앞 단계 완성 상태를 시작본으로 주고 이번 요구를 구현 · 변경하게 한다. 자기 이전 결과를 가져오는 것은 선택이며 진행 조건이 아니다 — 가져오면 판본 · 입출력 계약을 확인하고 별도 보관한 뒤 쓰며 기존 결과를 덮어쓰지 않는다.
2. 학생 개인 Git · commit/push · 이름/이메일 설정을 필수로 요구하지 않는다(GitHub는 강사 측 원본 · 배포 관리).
3. 학교 PC는 재부팅하면 초기화될 수 있다. 저장 · 내보내기 방법을 안내하고 자동 복구를 약속하지 않으며, 결석 복귀는 회차별 선행 결과 시작본으로 한다.
4. 실행이 필요한 새 쿼리는 전용 랩 DB에서만 확인한다.
5. 결과 생성 · 수정 · 재확인 · 저장 · 다시 열기를 흐름에 넣고, 앞 요청 · 명세 · 지식 구조 · 스킬 · 검증 결과를 다음 실습에서 이어 쓴다.

## K4 대본 — VS Code에서 시작해 바이브 코딩을 보인다

1. **VS Code에서 시작한다.** 시작 도구 또는 ZIP으로 받은 실습 폴더를 VS Code에서 연다(첫 사용은 조작을 보여 주고 이후에는 짧게, 다운로드 서비스 · ZIP 목록 설명은 본론 밖). 마무리는 결과의 실행 · 판정 · 저장 · 다시 열기다.
2. VS Code를 처음 쓰는 학생에게 필요한 조작 — 폴더 열기 · 탐색기 · 편집 · 저장 · 터미널 · AI 채팅(Codex) — 은 처음 필요할 때 보이고 뒤로 갈수록 줄인다.
3. **코딩 랩은 바이브 코딩을 매번 실제로 보여 준다.** 랩마다 프롬프트 · 자료 · 판단이 다르므로 일곱 단계(기준_공통 G0-2)를 매 랩 처음부터 끝까지 화면에서 한다. 「바이브 코딩이란」 소개만 첫 코딩 랩에서 한 번.
4. **코드는 설명하지 않는다.** 「코드는 몰라도 된다」고 분명히 말해 안심시키고, 그 실습의 판단 지점(요구를 내 말로 정하기, 결과를 원자료와 대조하기)을 분명히 짚는다. 「AI가 이렇게 만들었습니다」까지만 보이고 판단은 요구 반영 · 원자료 대조 · 다른 입력 · 업무 쓸모로 한다. 화면에 보여 줄 것은 프롬프트 · 스킬 · 명세 · 조건 · 결과이고, 소스 해설 · 파일 목록 · ZIP 구성은 본론이 아니다.
5. **완성본 리뷰(코딩 랩):** 영상 끝에 학생용 완성본(따로 받는 묶음)을 실행해 방금과 같은 결과가 나오는 것을 보여 주고, 「계정이 없으면 완성본으로 결과를 확인하고, 바이브 코딩 과정은 영상으로 보며 습관을 익히세요」라고 안내한다.

## K5 촬영

1. 준비 때 랩 코드 · 입력 · 시작본 · 참조본 · 완료 조건을 맞추고, 리허설은 학생과 같은 입력 · 폴더 · 명령으로 Codex를 써서 한다(K6-1 ①의 학생 경로 리허설을 겸한다).
2. 코딩 랩 전에는 안 뚫린 길(Codex 채팅 · 터미널 · 시작 도구 장면 · 별도 랩 DB)을 먼저 뚫는다.
3. **Codex 요청이 있는 코딩 랩**은 구간을 나눈다(검증 상태는 `제작용/촬영/vscode/촬영준비.md`): ① 요청 구간(요청 이유와 요청 문장은 미리 쓰고, 전송 뒤 응답이 흐르기 시작하는 몇 초까지) ② 녹화 밖 대기(편집 승인 창은 `결과/` 아래일 때만 허용, 승인 장면은 첫 등장 랩에서 한 번 녹화) ③ 끝난 응답 · 바뀐 파일 · 실행 출력을 읽어 본 것만으로 「결과 확인」 큐를 쓰고 이때 음성을 만듦 ④ 결과 확인 구간(이미 있는 응답을 짚고 결과 파일 · 원자료를 열어 대조, Codex를 다시 부르지 않음).
4. **VS Code 촬영은 웹 VS Code로 한다**(기준_실습 P1-8). 웹판과 네이티브의 동선 차이는 숨기지 않고 따로 처리하고 기록한다(학생 가이드의 네이티브 캡처는 기준_실습 P9-2). 설치 화면 · 파일 탐색기 같은 데스크톱 앱 장면의 검증 상태는 `제작용/촬영/vscode/촬영준비.md`.

## K6 완성 판정

1. **랩 완성 = 네 가지 모두:** ① 실제 학생 경로 리허설 통과(학생과 같은 입력 · 폴더 · 명령, Codex) ② 검사기가 일부러 망가뜨린 입력을 잡음 ③ 강사 참조 실행(학생 수행을 대신하지 않음) ④ 가이드만으로 다운로드 → 저장 · 다시 열기(받기 시험).
2. **장난감 판정:** 「한 줄 요청」으로도 같은 결과가 나오면 장난감이다. 원문 문장이 그대로 답을 주는 설계 지점은 판별력이 없다. 판정 = 충분히 어려운가 + 습관으로 풀리는가(리허설).
3. AI가 도구 순서를 고르는 실습은 특정 순서만 정답으로 강제하지 않는다. 강사 참조는 리허설에서 실제로 만든 적재 · 조회문으로 확정한다.

## K7 배포 · 시작 도구와 범위

1. 기본 동선은 PC 로컬 「실습 시작」 도구 → 과정 · 회차 · 실습 선택 → 그 판본만 다운로드 · 압축 해제 → VS Code 폴더와 가이드 열기다. 학생의 명령 입력 · 경로 지정 · Git 설정을 기본 동선에서 없애고, 실패하면 재시도와 수동 ZIP 대안을 준다(ZIP 경로는 대안으로 유지).
2. 같은 실습을 다시 열 때 학생 수정 파일을 덮어쓰지 않고, 새로 시작은 별도 폴더로 한다. 초기화된 PC에서 재다운로드로 시작할 수 있어야 하고, 학교 기본 이미지에 도구가 남는지 · 복구 경로가 있는지, 초기화 뒤 실습 폴더(`D:/HYD-Practice`)의 신뢰 · 쓰기 권한이 살아 있는지 확인한다 — 신뢰가 풀려 VS Code가 제한 모드로 열리면 AI 도구가 동작하지 않는다. 학생은 `.env`에 강의 키 한 줄만 넣는다. 코드 다운로드와 Docker/DB · AI 로그인 · 키 준비를 구별한다.
3. Notion 일반 링크만으로 PC 명령이 실행된다고 쓰지 않는다 — 시작 도구가 다운로드와 VS Code 실행을 맡고 Notion · HTML 가이드는 안내와 링크를 준다. `code -n` 같은 명령은 내부 구현이지 학생 절차가 아니고, 브라우저 버튼 직접 연동은 약속하지 않는다.
4. **오프라인 Notion:** 기본은 Notion 없이 한다. 현장에서 설치 · 접속 · MCP 연결과 자기 자료 준비가 되면 강사가 그 교시 안에서 선택 실습으로 하고(과정별 내용은 기준_공통 G2 표), 안 되면 기본 파일 · Git · 시간 MCP 실습을 한다. 온라인 Notion 실습은 유지한다.
5. 1회차는 독립 코딩 과제 · 차이 설계로 시작하지 않는다. 과정별 결과물 · 완료 기준은 기준_공통 G2 영역표가 정한다. 포털 제한은 독립 코딩 랩의 외부 MCP · 직접 만든 MCP · 자기 Notion · 다른 문서 사용을 막지 않고, 랩 결과가 포털 에이전트에 자동 연동된다고 말하지 않는다.
