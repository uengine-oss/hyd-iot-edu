## 강사 본인의 자연스러운 원맨쇼 — 2026-10-20 사용자 확정

가장 중요한 기준은 강사 본인이 실제로 작업하며 설명하는 사람처럼 자연스럽게 진행하는 것이다. 앞 이론과 실제로 마친 포털 경험을 짧게 받아 오늘 할 일·목적·만들 결과·확인 기준으로 이어 간다. 처음 받은 프로젝트에서는 목적과 요구만 알고 출발하며, 이미 탐색한 것처럼 내부 구조나 정답을 미리 말하지 않는다. 실제 관찰과 판단을 따라 요청·구현·결과 확인을 이어 간다. 자연스러움을 이유로 설명·필수 검증을 생략하거나 실수·실패를 연출하지 않는다.

통합반은 VS Code를 처음 쓰는 비전공자를 기준으로 폴더 열기, 탐색기·파일 편집·저장·터미널을 처음 필요할 때 실제 화면에서 설명한다. AI 코딩 도구(GitHub Copilot · Codex)의 채팅도 처음 사용하는 시점에 위치·요청·응답 확인을 안내한다. 이후에는 익힌 설명을 점진적으로 줄인다. 실전반은 VS Code 기본 UI 사용법 설명을 생략한다(2026-10-26 사용자 결정). 실전반에서도 이번 폴더·자료·요구·실행 위치·결과 판정과 처음 쓰는 다른 도구의 안내는 유지한다. 이 차이를 이유로 공통 1회차를 재촬영하지 않는다.

바이브 코딩과 SDD는 실제 학습 시점과 필요에 맞춰 처음 적용할 때 설명하고, 이후 익숙한 조작·방법은 수행하되 길게 재설명하지 않는다. 새 요구·조건·판단·검증에 설명을 쓴다. 이론 대본 온라인 상세05·15절의 본인 발화, 제3자·제작 문구 분리, 영어·식별자·수치 선별 규칙을 그대로 적용한다.

시작 멘트는 승인 Excel에서 바로 앞의 이론·실습과 이번 과제를 대조해 쓴다. 앞에서 배운 내용 또는 실제 수행한 결과를 짧게 받고, 이번에 할 일·만들 결과·확인할 것을 연결한다. 도구 설명으로 바로 시작하거나 아직 하지 않은 작업을 마친 것으로 말하지 않는다. Neo4j 첫 사용은 접속·연결 상태·주요 영역·입력·실행·결과 읽기를 안내한다. 도입 시간을 고정하지 않고 내용과 실제 조작에 맞춰 자연스럽게 조정한다(사용자의 약3분 제안 뒤 고정 시간 제외 지시 반영). 기본 화면에서 패널을 접거나 전환하는 과정도 말하며 보여 준다. VS Code 기본 UI 생략을 다른 도구의 첫 안내 생략으로 확대하지 않는다.

각 기능 구간은 필요한 실제 조작을 빠뜨리지 않고 이어 촬영한다. 결함 부분만 연결 상태를 맞춰 교체할 수 있으며 배속·줌인으로 조작을 대체하지 않는다. 촬영 전에 읽을 수 있는 글자 크기와 패널 배치를 준비한다. 설명할 항목으로 커서를 옮겨 지금 보는 위치를 짚고, 글자·값을 가리지 않는 곳에 둔다. 화면이 바뀌면 필요한 위치를 짧게 알려 준다. 스크롤은 필요한 문맥을 보존하는 범위로 움직인 뒤 읽고 설명하며, 빠르게 지나가거나 이유 없이 왕복하지 않는다. 클릭·입력·붙여넣기·전환은 실제 작업 목적과 설명·확인에 맞춰 진행한다. 커서 이동·드래그·스크롤·타이핑을 포함한 모든 상호작용은 사람이 목표를 보고 연속해서 조작하는 속도와 호흡으로 보여 준다. 작은 이동 호출과 대기를 반복해 찔끔찔끔 움직이는 방식은 피한다. 녹화 fps만 높여 입력의 끊김이 해결됐다고 판정하지 않는다. 모든 조작에 고정 초 단위 지연을 붙이거나 사람처럼 보이려고 무의미한 커서 이동·느린 타이핑·실수를 추가하지 않는다. 기술·판본·예외 메모만 비낭독 영역에 둔다. 학생에게 필요한 위치·조작 안내는 실제 발화에 포함하며 메모로 대신하지 않는다.

VS Code 랩은 완성한 결과의 실행·판정·저장으로 마무리하도록 준비한다. 진행이 막혀 참조 완성본이 필요하면 전환 사실을 짧게 밝히고 해당 판본에서 실행·결과를 확인한다. 참조본을 방금 직접 만든 결과로 말하지 않는다. 실행 · 촬영은 사용자가 해당 실습의 촬영을 요청한 범위에서 [실습 영상 제작 안내](방법_ego_실습영상_촬영.md)대로 한다. 준비·리허설·가이드·본 촬영의 순서와 재확인 경계는 [검증과 마감](검증과마감.md#실습-준비와-후속-촬영의-순서--2026-10-20)을 따른다.

## 1회차 환경 준비·포털 안내 — 2026-10-22 사용자 확정

1회차는 두 과정 공통이다. VS Code는 파일을 열고 수정·실행할 작업 공간, Git은 프로젝트를 내려받고 변경 이력을 관리하는 도구로 쉽게 설명한다. IDE 같은 처음 보는 용어를 설명 없이 쓰지 않는다. GitHub Copilot · Codex는 요구를 전달하고 코드 작성·수정·결과 확인을 함께 진행할 AI 코딩 도구이며, 실습 재료나 확장 프로그램이라는 분류 중심으로 소개하지 않는다.

Docker는 다른 도구보다 필요성을 충분히 설명한다. 필요한 서비스를 각각 직접 설치·설정하는 부담을 줄이고 준비된 환경을 실행한다는 이유에서 출발한다. 이미지·컨테이너·접속 포트·데이터 보관은 실제 화면과 설정에서 필요한 만큼 쉽게 연결한다. 개념을 먼저 길게 강의하거나 모든 옵션을 깊이 풀이하지 않는다. 대부분의 서비스는 Docker로 준비하되 실제 설치 목록을 확인하며 전부 Docker 안에 있다고 단정하지 않는다. 현재 README에는 Node.js도 설치 대상으로 있으므로 촬영용 main 판본에서 다시 확인한다. 근거 없는 ‘나머지 실행 도구’ 항목을 만들지 않는다.

공식 다운로드 위치를 보여주고 설치 완료 상태에서 진행한다. 설치 대기·계정 로그인은 본론으로 늘리지 않는다. HYD 촬영용 main clone → VS Code 폴더 열기 → 실제 배포 절차의 시작 명령 → 출력·상태 확인 → 실제 주소로 포털 접속 순서다. 작업 중인 미커밋 수정은 보존하며 원격 main 게시 완료로 단정하지 않는다. 사용하는 명령은 작업 위치·목적·기대 결과를 조작하면서 한두 마디씩 설명한다. 명령의 모든 토큰·옵션·철자를 낭독하거나 깊이 강의하지 않는다. 짧은 명령·바이브 요청은 직접 타이핑하고 긴 명령은 붙여넣어도 된다.

포털 메뉴는 실제로 열며 언제 쓰고 무엇을 확인하는지 안내한다. 중요한 화면은 쉬운 예시를 짚고, 보조 메뉴는 용도·위치만 소개한다. 아직 배우지 않은 전문용어·설정은 지금 화면을 이해하는 만큼만 풀고 ‘뒤에서 직접 다룰 테니 지금은 이런 화면이 있다는 정도로 보시면 됩니다’처럼 부담을 낮춘다. 이 안내도 메뉴마다 반복하지 않는다. 시스템 구성은 앞 이론과 짧게 연결하고 사건 전체 실행은 해당 실습에서 수행한다. 종전 ‘아키텍처 위치만 안내’는 이 전체 메뉴 안내로 확대한다.

분량은 실제 설명·조작의 결과다. 50분을 맞추려고 느리게 타이핑하거나 대기하지 않는다. 처음 보는 기능과 중요한 결과에는 여유를 주고 익숙한 조작은 자연스럽게 진행한다. 환경 준비+메뉴 안내 34~45분은 대화에서 나온 계획 추정일 뿐 실측·고정 배정이 아니다.

## 자연스러운 진행과 유연한 조정

대본은 처음부터 끝까지 진행할 수 있게 준비하되 화면과 무관하게 정해진 길이를 낭독하는 규칙으로 쓰지 않는다. 표현·호흡·반복 설명량은 실제 화면에 맞춰 조정한다. 처음 보거나 헷갈리기 쉬운 부분은 위치와 이유를 보충하고, 이미 익힌 기능은 정의를 줄인다. 필요한 선행 조작·입력값·판단 조건·결과 확인은 생략하지 않는다. 조절 뒤에도 대상·행동 안내 시작→설명하며 조작→실제 결과 확인 순서는 유지한다.

학생이 대상을 찾을 수 있게 위치·이름·할 일을 먼저 짚기 시작하고, 대상과 행동을 알아들을 수 있는 시점부터 설명을 이어가며 조작한다. 설명 문단이나 음성 파일이 끝날 때까지 매번 멈추지 않는다. 커서를 해당 위치로 옮기는 동안 위치를 안내할 수 있다. 클릭·입력은 무슨 작업인지 알 수 있게 안내한 다음 수행하고, 결과 설명은 결과가 실제로 나타난 뒤 한다. 안내 없이 조작부터 끝내고 뒤늦게 해설하거나 아직 나타나지 않은 다음 메뉴를 연속 클릭하지 않는다. 필요한 클릭·엔터·선행 선택은 말하되 같은 위치·색상·정의를 매번 길게 반복하지 않는다.

화면에 표시된 이름·분류·속성과 코드에서 사용하는 변수를 섞어 부르지 않는다. 예를 들어 `(s:Sensor)`의 `s`는 노드를 가리키는 변수, `Sensor`는 노드의 레이블이다. 처음에는 실제 식의 해당 부분과 결과의 레이블·속성을 짚어 구분하고, 이후에는 익힌 용어로 자연스럽게 이어간다.

윤문 검수에서는 낭독할 문장 전체를 순서대로 읽는다. “앞 이론”, “펌프 사십, 팬 칠십” 같은 제작 메모식 축약은 구체적인 주어·대상·뜻을 갖춘 구어체로 풀고, 조회를 생성·연결로 표현하거나 지도를 실행한다고 말하지 않는다. 이론과의 연결은 “이론 시간에는 …을 배웠습니다. 이번에는 …을 직접 확인해 보겠습니다”처럼 실제 배운 내용과 이번 행동을 명시하되 같은 도입을 일괄 복제하지 않는다. 자동 받아쓰기 일치는 문장 자연스러움의 검수 근거로 대신할 수 없다.

어미를 바꾸는 것만으로 윤문을 끝냈다고 하지 않는다. 앞 문장에서 다음 동작으로 자연스럽게 이어지는지, 입력할 값이 명확한지, 과장·추임새·가상 학생 반응·기계적인 질문이 없는지 본다. 실제 화면으로 확인하지 않은 버튼 색은 추측해 대사에 넣지 않고 위치·이름으로 안내한다. 색이 확인되면 대상을 찾는 데 도움이 되는 곳에만 사용한다.

UI를 안내할 때 화면에서 확인한 위치·색상·모양과 정확한 이름을 함께 짚는다. 예를 들어 ‘오른쪽에 파란색 Add Node 버튼이 보이죠. 이걸 눌러 새 원을 하나 만들어 볼게요’처럼 학생이 대상을 바로 찾게 한다. 색상만으로 대상을 지칭하지 않고, 모든 버튼의 색·모양을 기계적으로 나열하지 않는다. 테마나 선택 상태에 따라 달라지는 특징은 실제 촬영 화면과 맞춘다.

대본은 실제 강사가 학생에게 안내하는 자연스러운 구어체로 윤문한다. ‘~습니다’만 반복하지 않고 문맥에 맞춰 ‘~볼게요’, ‘~네요’, ‘~하면 돼요’ 등을 섞되 특정 어미로 일괄 치환하거나 매 문장에 ‘보이죠’를 붙이지 않는다. 입력할 정확한 내용·UI 이름·판단 조건은 윤문 중에도 보존한다. 대상을 먼저 알려 주고 설명을 이어가며 자연스럽게 조작한다. 문장마다 멈추는 낭독 리듬으로 만들지 않는다.

선택 해제, 빈 여백 클릭, 입력칸 선택, 다음 줄 이동처럼 다음 UI를 나타내거나 입력을 가능하게 하는 선행 조작도 빠짐없이 안내한다. 예를 들어 ARROWS에서 원이 선택된 상태라면 ‘지금은 Add Node가 보이지 않습니다. 그림 영역의 빈 여백을 클릭해 선택을 풀겠습니다’라고 말한 뒤 클릭한다. 버튼이 나타난 결과를 확인하고 다음 버튼을 안내하며 누른다. Caption·Property 등의 위치·용도를 처음에 설명하고, 입력할 이름·값과 필요한 키도 말한 뒤 실제로 입력한다. 항목 칸 클릭과 내용 입력이 별도 행동이면 음성 큐도 필요한 만큼 나눈다.

반복 조작에서는 이미 설명한 기능의 정의를 줄이되, 이번에 누를 위치·입력할 내용·선행 조작을 생략하지 않는다. 결과를 눈으로 확인할 여유를 주고 다음 단계로 간다. 모든 조작에 같은 긴 대기를 강제하거나 학생 실습 대기 시간을 영상에 넣지 않는다. 자연스러운 강사 본인 발화, 영어·수치 선별, 이론 중복 금지 기준은 유지한다.

## 상세 적용 — 이론의 반복 점검과 실습 시작 장면

온라인은 강사 한 사람이 목적·요구사항만 알고 처음 받은 랩 프로젝트에서 제작을 진행하는 영상이다. 학생용 가이드를 읽는 시간·학생 작업 시간은 영상 분량에 넣지 않는다. 기존 가이드는 제작 참고 자료로 보존한다. 소스코드 해설·파일 목록·ZIP 구성 설명을 본론으로 삼지 않는다. 필요한 코드의 역할만 짧게 짚고, 학습 대상인 프롬프트·스킬·명세·조건과 결과를 화면에서 보여 준다.

도입은 앞 이론과 실제 앞서 본 포털의 장면을 오늘 만들 결과에 짧게 연결한다. 아직 보지 않은 것을 보았다고 말하지 않는다. 해당 실습 코드를 내려받고 VS Code로 여는 조작은 간결하게 진행한다. 다운로드 서비스의 사용법이나 파일 구조를 길게 낭독하지 않는다.

첫 바이브 코딩 실습은 모르는 프로젝트에서 목적·요구사항을 제시하고, AI가 관련 부분을 조사하게 하며, 현재 기능과 필요한 결정을 확인하고, 요구사항·완료 기준을 구체화해 계획·구현·결과 검증으로 이어가는 방법을 설명한다. 강사가 미리 알고 있는 파일·함수·정답 프롬프트를 탐색 없이 지정하지 않는다. AI 답변·실행 결과를 선기입하지 않고, 관찰한 근거에 따라 다음 요청을 발전시킨다. 소스 내부 탐색은 AI가 수행하되 강사는 기능·제약·변경 영향과 결과로 이해하고 판단한다.

이후에는 익힌 절차를 매번 처음부터 가르치지 않는다. 같은 프로젝트의 이전 명세·계획·결과를 이어 쓰고 이번에 달라진 요구·판단·검증 지점에 시간을 쓴다. 첫 적용은 이유와 판단 과정을 충분히 보여 주고, 재적용은 새 차이만 설명하며, 익숙한 작은 작업은 짧은 요청과 결과 확인으로 진행한다. 새로운 프로젝트나 불명확한 요구·큰 변경이면 필요한 탐색·계획을 다시 수행하되 방법론 소개를 반복하지 않는다. 설명을 줄이는 것이 필요한 실제 검증을 생략한다는 뜻은 아니다.

매 랩에 탐색→명세→계획→구현→검증을 같은 길이의 형식으로 강제하지 않는다. 명세 문서는 SDD가 학습 목표이거나 변경 기준을 지속해서 관리할 때 사용한다. 초기 회차에 아직 배우지 않은 SDD·BDD 전문 용어나 문서 작업을 앞질러 강제하지 않는다. 익숙한 기본 동작은 자연스럽게 수행하고, 이번 랩만의 학습상의 새 판단이 있어야 한다. 흥미를 위해 억지 실패·가상 학생·불필요한 기능·드라마를 만들지 않는다.

분량은 강사의 설명·실제 제작·결과 해석 흐름의 결과로 추정한다. 코드 해설·타이핑·같은 절차의 재설명·대기·학생 활동으로 배정 시간을 채우지 않는다. 실행 리허설 없이 안정적인 정확한 영상 길이를 확정하지 않는다. 일반 정적 교재 조사와 기록에서는 실제 실습·학생 코드/테스트·AI 시연·HYD/DB·브라우저 실습·캡처를 수행하지 않는다. 실습 영상 촬영은 사용자가 요청한 도구 · 회차에서 [실습 영상 제작 안내](방법_ego_실습영상_촬영.md)를 따른다.

첫 코딩은 목적과 요구에서 AI 탐색 → 현재 준비·미구현 확인 → 요구와 완료 기준 → 필요한 계획·구현 → 원문과 결과 대조로 간다. 이후에는 익힌 방법을 재강의하지 않고 새 조건·요구·검증을 설명한다. SDD·BDD는 해당 학습 시점과 업무에 필요한 범위에 둔다. 실제 명령은 촬영용 절차로 표시하며 이번 문서 작업에서 실행하지 않는다.

### 온라인

강사 혼자 검증된 시작 도구 또는 수동 ZIP 경로로 자료를 받아 VS Code에서 작업한다. 학생이 가이드를 읽거나 답할 시간을 넣지 않는다. HTML은 제작 참고 자료다. 파일 목록·소스 해설을 본론으로 늘리지 않고 입력할 프롬프트·스킬·명세·판단 근거·실제 결과를 보여 준다. 실습 대본의 내용과 순서는 랩·가이드에 맞춘 상태로 확정하며, 발화·전환·진행 속도는 촬영 때 튜닝할 수 있다.
