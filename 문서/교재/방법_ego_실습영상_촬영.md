# ego로 사용자 작업을 방해하지 않고 웹 실습 영상 촬영하기

2026-10-22. 대상은 로컬 명령과 파일 작업이 가능한 AI 에이전트를 사용하는 제작자다. 전용 Computer Use 기능 없이 ego-browser로 웹사이트를 조작하고, 페이지 화면과 조작 좌표를 녹화하는 방법이다. 일반 웹 채팅만으로는 실행할 수 없다. 수업 발화·분량은 [실습 대본 기준](기준_실습대본.md)을 따른다.

## 확인된 범위

### 최신 Notion 촬영 기준

Notion 2:48 튜토리얼 샘플은 원본 프레임 1920×1080, UI 약150%, 안치윤 음성으로 확인했고 사용자가 상세한 따라 하기 호흡을 승인했다. 근거는 `.evidence/notion-tutorial-3min-20261022/verification.json`이다. 아래 arrows 17초 수치는 과거 기술 시험이며 수업 촬영 해상도 기준이 아니다. `제작용/촬영/ego/`의 1280×800 예제도 과거 최소 재현용이다. 본 수업에서는 1920×1080 원본·UI150%를 적용하며, 원본 크기 확인 없이 출력만 늘리지 않는다. 현재 준비판은 [Notion 촬영 준비](../../제작용/촬영/notion/촬영준비.md)를 따른다.

150% 확대에서는 표 오른쪽 도구가 화면 밖으로 밀리는지 확인한다. 필요한 표는 전체 페이지로 열거나 해당 보기에 보일 열을 줄이고, 보이지 않는 버튼을 고정 좌표로 클릭하지 않는다. 본 촬영 중 확대 변경으로 해결하지 않는다. 이번 기존 완성본 보강 중 홈 캡처는 성공했으나 후속 `Page.captureScreenshot` 한 번은 시간 초과했다. 이를 최소화 때문이라고 단정하지 않으며 장시간 녹화 안정성 확인과 구별한다.

Windows의 ego lite 0.6.0.16, ego-browser 가이드 2.1.0에서 arrows 입력·노드 수정·캡처를 확인했다. ego를 최소화하지 않고 다른 작업 창을 앞에 둔 약 14초 시험에서 사용자가 “앞의 작업 유지, 간섭 없음”을 확인했다. 약 17초 후속 샘플은 포인터 표시와 이동 중 캡처를 개선했다. 이후 샘플에서 Windows 창 활성화·물리 마우스·Claude 조작은 하지 않았다.

| 항목 | 확인 상태 |
|---|---|
| 다른 작업 창 뒤의 arrows 조작과 녹화 | 짧은 시험 확인, 사용자 동시 작업 확인 |
| 최소화된 ego 캡처 | 이 설치 버전에서는 오류 발생 |
| 클릭과 표시 포인터 좌표 | 마지막 샘플의 3회 모두 CSS 좌표 오차 0 |
| 이동 중 프레임 | 이동당 10–19장, 이동 시간 296–514ms, 이동 안의 최대 프레임 간격 59ms |
| 한글 | 완성형 글자 단위 입력. 한글 IME의 초성·중성 조합 시연은 아님 |
| 다른 PC·OS·에이전트 | 재현 절차 제공. 실제 이식 검증 전 |
| 5분·50분 연속, 드래그·스크롤·새 탭·iframe | 이번 짧은 포인터 시험의 검증 범위 밖 |
| 음성 | 이번 ego 샘플은 무음. 음성 동기화 확인 전 |

ego의 별도 작업 공간은 클라우드 VM이나 헤드리스 실행을 뜻하지 않는다. 브라우저 창을 켜 둔 채 다른 창으로 가려 작업한 조건을 기준으로 삼는다. 화면 잠금·절전·원격 연결 해제에서도 유지된다고 확대하지 않는다.

## 도구 선택

| 작업 | 사용할 경로 |
|---|---|
| arrows, bpmn.io, 웹 Notion, Neo4j Browser | ego 후보. 사이트별 로그인·편집·저장·캡처부터 확인 |
| Windows 설치 화면, 파일 탐색기, 로컬 VS Code 앱 | ego 페이지 녹화 범위 밖. 별도 데스크톱/가상 화면 촬영 필요 |
| 웹 VS Code | 별도 환경 구성. 로컬 VS Code·Codex 시연과 동일하다고 간주하지 않음 |
| 창 상태까지 완전히 분리한 촬영 | Docker 가상 화면 등과 비교. 이 PC에서 Docker 무간섭 시험도 성공했음 |

Codex·Claude Code 등은 로컬 명령 실행 권한과 ego 스킬이 있으면 같은 접근을 사용할 수 있다. 제품명보다 `ego-browser nodejs` 실행과 생성 파일 반환 가능 여부를 확인한다. ego용 별도 Computer Use 모델 키를 설정하는 절차는 없다. 에이전트 자체의 인증·요금과 음성 API는 별개다. 이 문서를 따른다고 다른 에이전트의 권한·도구 정책이 사라지지는 않는다.

## 설치와 첫 연결

1. [ego 공식 사이트](https://lite.ego.app/ko)에서 해당 OS 설치 파일을 받는다. 설치·권한 승인·초기 설정·로그인은 사용자가 처리한다. 자동 실행이나 기본 브라우저 변경은 촬영에 필수가 아니다.
2. 사용할 에이전트만 연결한다. 기존 브라우저 데이터 가져오기는 선택 사항이다. 다른 사용자의 로그인 쿠키를 추출해서 옮기지 않는다. 이 프로젝트에서는 Claude를 변경하지 않는다.
3. 터미널/에이전트를 새로 열고 `ego-browser skill`을 실행한다. 가이드 마지막의 `[ego-browser:skill] end of guide`까지 읽는다. API는 설치 버전의 출력이 우선이다. 업데이트 후 다시 확인한다.
4. 명령을 찾지 못하면 설치 경로와 새 PATH를 확인한다. 이 PC의 `C:/Users/...` 경로를 다른 PC에 복사하지 않는다.
5. FFmpeg 실행 파일을 준비해 경로 또는 PATH를 확인한다. 아래 인코딩 예제는 Node.js도 사용한다. 녹화는 ego가 제공하는 Node 런타임에서 실행한다.

Windows PowerShell에서는 한글·긴 JavaScript를 `-e` 인수나 `Get-Content` 파이프로 전달하지 않는다. UTF-8 `.mjs`에 저장하고 ASCII 한 줄로 불러온다.

```powershell
ego-browser nodejs -e "await import('file:///C:/ego-recording/inspect.mjs')"
```

첫 파일은 다음처럼 실제 작업 공간과 페이지를 만들고 상태만 확인한다. 반환된 번호를 기록한다. 공간 이름/번호는 작업마다 확인하며 예제의 `1`을 임의로 재사용하지 않는다.

```js
const task = await taskSpace('arrows recording preparation');
const page = task.page('p1');
await page.goto('https://arrows.app');
console.log({spaceId: task.spaceId, pageLabel: page.label});
console.log(await page.snapshot());
```

동일 작업은 같은 공간을 재사용한다. `finish()` 후 남겨 둔 탭은 이전 페이지 라벨을 잃을 수 있다. 사용자가 재개를 요청한 경우 `claimTaskSpace(id)` → `task.tabs()` → 해당 탭의 `task.adopt(tab.page)` 순으로 새 라벨을 확인한다. 중단·사용자 제어·권한 오류를 새 공간으로 우회하지 않는다.

## 성공한 설정과 조정 우선순위

아래는 마지막 샘플의 시작값이다. 모든 PC에서 고정해야 하는 수업 기준이나 최대 성능 수치가 아니다.

| 설정 | 시작값 | 이유와 조정 방법 |
|---|---|---|
| 과거 최소 재현 예제의 페이지 크기 | 1280×800 CSS px, deviceScaleFactor 1 | 기술 시험값. 현재 수업 촬영은 위의 1920×1080 원본·UI150% 기준 사용 |
| 가독성 | 촬영 전 UI 확대·패널 배치 확정 | 125–150%는 후보. viewport 크기 설정은 브라우저 줌 설정과 다름. 실제 글자 크기를 직접 확인 |
| 화면 전송 | `Page.startScreencast`, JPEG quality 90, everyNthFrame 1 | 변화 프레임을 수신. API에 고정 30fps 보장 옵션이 있는 것으로 설명하지 않음 |
| 이벤트 확인 | 약 20ms 간격 | 빈 이벤트일 때 짧게 쉼. 지나친 폴링은 CPU·명령 수만 늘림 |
| 호출 방식 | 한 프로세스·한 명령 큐 | 상태 파일 동시 갱신 충돌을 피함. 다른 녹화 프로세스가 같은 공간을 쓰지 않음 |
| 포인터 이동 | 거리/14, 12–24단계, 각 `steps:1`, 단계 사이 약 5ms | 각 호출이 끝날 때 캡처·ACK가 큐를 사용할 기회를 줌. 실제 마지막 이동은 0.296–0.514초였음 |
| 이동 경로 | 직선에 완만한 가속·감속 | 무의미한 우회·흔들림·실수 연출을 추가하지 않음 |
| 클릭 전 | 샘플은 약 350ms | 목적을 확인하는 짧은 여유. 모든 수업 조작을 같은 속도로 늘리지 않음 |
| 입력 간격 | 약 110–210ms/글자 | 완성형 한글 글자·영숫자 입력. RPC 시간도 더해짐. 긴 입력은 허용된 붙여넣기와 구분 |
| 포인터 표시 | 흰 화살표 25×34, 검은 테두리, 후광 없음 | `mousemove`의 실제 clientX/Y를 따라감. `pointer-events:none`으로 클릭을 가로채지 않음 |
| MP4 | H.264, CRF 18, yuv420p, 30fps, 원래 시간 유지 | 출력 30fps는 부족한 원본 프레임을 복구하지 않음. 배속·시간 압축 금지 |

우선 적용할 최적화는 경로·페이지 번호를 설정으로 분리하고, 촬영 시작 전에 viewport와 선택 상태를 고정하며, 실제 이동 구간의 프레임 간격을 측정하는 것이다. 그다음 장시간 저장·복구를 확인한다. 해상도·fps·JPEG 품질을 먼저 올리지 않는다. 부하가 큰 PC는 JPEG 85를 후보로 비교하되 작은 글자의 가독성 확인 없이 채택하지 않는다.

## 끊김 원인과 수정 원리

처음에는 `mouse.move(..., {steps:28})` 하나가 약 0.45초 동안 명령 큐를 점유했다. 그동안 녹화 프레임 수신 확인(ACK)도 기다려 이동 중 화면이 1–4장만 남았다. 출력 파일의 30fps와 실제 이동 프레임 수는 다르다.

수정본은 `steps:1`의 짧은 이동 명령으로 나누고 그 사이에 이벤트 수신·ACK를 처리한다. 캡처와 조작의 동시 프로세스를 늘린 것이 아니다. 실제 움직임과 화면 전송을 한 큐에서 번갈아 진행한다. 특정 단계 수보다 관측된 이동 시간·프레임 간격이 판정 기준이다.

이 패턴을 지킨다.

```js
let queue = Promise.resolve();
function serial(fn) {
  const result = queue.then(fn);
  queue = result.catch(() => {});
  return result; // 호출자는 실패를 받아 중단해야 함
}
// 녹화 루프: serial(page.events) → 프레임 저장 → serial(screencastFrameAck)
// 이동 루프: serial(mouse.move(..., {steps:1})) → 짧은 양보 → 다음 단계
// 긴 이동 명령이나 전체 문자열 type(delay)를 하나의 큐 항목으로 넣지 않음
```

포인터는 영상 편집 때 경로를 합성하지 않는다. 녹화되는 페이지에 SVG를 표시하고 실제 입력 이벤트를 따라 위치를 갱신한다. `mousedown` 좌표와 SVG의 좌측 상단 좌표를 같은 CSS 좌표계에서 기록한다. 화살표 끝은 도형 테두리 때문에 약 1px 시각 차이가 있을 수 있다. 페이지 내부 표시이므로 브라우저 주소창·OS 대화상자는 포함하지 않는다. 새 페이지/iframe으로 이동하면 별도 설치·좌표 확인이 필요하다.

## 재현용 예제 사용

제작 원본은 [제작용/촬영/ego](../../제작용/촬영/ego/)에 있다. 성공한 샘플의 알고리즘을 경로·장면 설정으로 분리한 **arrows 전용 시작 예제**다. 문법·오프라인 인코딩 검사는 했지만, 이식한 예제의 실제 브라우저 재촬영과 다른 PC 실행은 아직 하지 않았다.

1. 폴더를 작업용 위치에 둔다. `recording.config.example.json`을 `recording.config.json`으로 복사한다.
2. 실제 spaceId/pageLabel, 새 절대 outputDir, 표시 이름·반지름·상태 문구를 채운다. outputDir은 기존 결과가 없는 새 경로를 사용한다.
3. arrows에서 테스트용 노드를 선택한다. snapshot과 화면으로 Caption 및 radius 입력을 확인한다. 예제의 input 순서 `0`, `4`는 이 UI에서 관찰한 값이며 다른 페이지의 정답이 아니다. 잘못된 대상이면 설정을 바꾸거나 실행을 중단한다.
4. ego는 최소화하지 않고 다른 작업 창 뒤에 둔다. 녹화 중 사용자도 다른 창에서 입력해 간섭 여부를 확인한다. 준비가 끝나면 운영체제 포커스 변경 명령을 쓰지 않는다.
5. 아래 명령을 실제 파일 위치에 맞춰 실행한다.

```powershell
ego-browser nodejs -e "await import('file:///C:/ego-recording/record-arrows.mjs')"
node C:/ego-recording/encode.cjs C:/recordings/ego-run-001 C:/tools/ffmpeg.exe
```

6. MP4를 열고 이동·타이핑·메뉴·결과를 본다. `report.json`에서 클릭 좌표 오차·이동 구간 프레임 간격과 디코드 결과를 확인한다. 테스트 완료 후 해당 작업 공간의 `finish({keep:[page.label]})`로 결과 탭만 남길 수 있다. 실패·사용자 제어 시에는 자동으로 finish/재시도하지 않는다.

## 촬영 합격 확인과 오류 대응

| 확인 | 통과 판단 / 대응 |
|---|---|
| 내 작업과 분리 | 앞의 작업 창 유지, 호스트 입력 간섭 없음. 사용자 확인을 남김 |
| 화면 | 글자 읽힘, viewport·배율 고정, 화면 변경에 따른 좌표 재관찰 |
| 클릭 | 클릭 당시 표시 포인터와 실제 입력 좌표가 일치. 어긋나면 CSS px·줌·iframe 기준 확인 |
| 이동 | 실제 이동 구간의 프레임 간격과 영상을 함께 확인. 검토용 경고값은 100ms 이상 공백. 성공 샘플은 최대59ms였지만 새 PC의 보장은 아님 |
| 타이핑 | 글자가 순차적으로 보이며 포인터가 내용을 가리지 않음. 완성형 입력과 IME 조합을 구분 |
| 결과 | 편집 내용과 최종 상태 일치. 전체 그래프 저장·재열기는 별도 과제 검증 |
| 최소화 오류 | 사용자가 ego를 복원한 뒤 새 시험. 사용자 작업 중 자동으로 앞에 띄우지 않음 |
| EPERM state 파일 충돌 | 동일 공간의 중복 실행 종료 여부 확인, 한 프로세스·직렬 큐로 통일. 권한/보안 기능을 무작정 끄지 않음 |
| 높은 출력 fps인데 끊김 | 원본 프레임·ACK 간격·긴 큐 점유 확인. 복제 프레임/배속으로 숨기지 않음 |
| 캡처에 커서 없음 | 페이지 내부 포인터 설치와 mousemove 수신 확인. 운영체제 포인터 녹화라고 표현하지 않음 |
| 녹화 오류·제어 중단 | 새 작업 공간으로 우회하지 않음. 부분 파일·오류·마지막 동작을 보존하고 후속 입력 중단 |

## 5분과 50분으로 늘리기 전

짧은 성공 시험은 50분 수업의 완성 판정이 아니다. 다음은 아직 확인할 항목이다.

- 5분 동안 여러 필드·스크롤·드래그·저장까지 확인한다. 잘 된 설치·포인터 시험을 매번 반복하지 않고 새 기능만 확인한다.
- 50분은 실제 연속 입력·서비스 응답·창 상태·음성 동기화·파일 보존을 별도로 확인한다. 시간을 채우려고 타이핑을 느리게 하지 않는다.
- 성공 샘플의 JPEG 168장은 약11.08MB/16.87초였다. 같은 변화량을 가정하면 50분 원본은 약1.97GB지만 **단순 외삽**이며 드래그·스크롤 빈도가 높으면 늘어난다. 작업 전 여유 공간을 측정한다.
- 장시간에는 프레임 목록을 끝에 한 번만 저장하지 말고 점진적으로 보존한다. 배포 예제는 프레임별 JSONL을 추가로 남긴다. 강제 종료 후 복구·버퍼 상한·저장 장치 포화 대응은 장시간 검증 전이다.
- 파일 분할 저장은 녹화 연속 시간축을 보존할 때만 사용한다. 영상 컷 편집과 구분한다. 배속하거나 중간 실패를 잘라 연속 성공처럼 만들지 않는다.
- 실제 동작 시간표에 짧은 설명·안치윤v5 음성을 맞춘다. 오디오를 생성했다고 동기화 완료로 판정하지 않는다. API 키는 설정 예제·로그·화면에 넣지 않는다.
