# 가이드 — 만드는 법과 인수 조건

이 문서 하나가 실습 가이드(도구 실습 · 코딩 랩)를 만드는 데 필요한 것을 다 가진다 — 학생이 강사 없이 따라 하는 가이드의 생성 원본 · HTML · 사진 · 학생 안내 문장 · 정적 검사 · 받기 시험 · 학생 패키지(ZIP) · 회차 안내 · main 반영 · 노션 회차 페이지 게시까지. 다른 문서를 함께 읽지 않아도 같은 결과물을 낼 수 있게 썼다. 실습 대본 · 촬영 · 영상, 코딩 랩의 과제 설계 자체, 덱은 각자의 문서가 소유하고, 이 문서는 그 산출물과 주고받는 것을 가이드의 말로 적는다.

## 목적 · 가치 · 배경

**P목-1** 가이드는 강사 없이 따라 하는 학생 자료다. 온라인 학생은 강사 한 사람이 실제로 작업하며 하나의 수업처럼 보여 주는 원맨쇼 영상을 보고, 오프라인 학생은 온라인 선행 학습 뒤 강의실에서 가이드만 펼쳐 준비 → 작업 → 결과 확인까지 스스로 하며 막힌 곳만 강사의 도움을 받는다. 그래서 가이드는 「학생이 행동하고, 결과를 관찰하고, 다음 판단을 할 수 있게」 쓴 글이어야 하고, 영상을 보지 않은 학생도 이 문서만으로 같은 결과에 닿아야 한다. 영상은 원맨쇼라 가이드를 띄우거나 읽어 주지 않으므로, 가이드와 영상은 같은 실습을 서로 다른 학생 행동(보기 / 직접 하기)으로 받친다.

**P목-2** 과정 전체는 노베이스 학생이 **온톨로지 마스터 → 에이전트 마스터 → 프로세스**로 올라가게 짜여 있다. 이론은 각 단계의 원리와 까닭을, 실습은 같은 단계를 학생이 직접 만들어 보는 경험을 맡는다. 실습은 과정의 줄기의 각 단계를 학생이 직접 만들어 보는 곳이고, 가이드는 그 「직접 해 보기」가 실제로 일어나게 하는 유일한 학생 자료다. 세 단계가 학생에게 남기는 것은 다음과 같다.

| 단계 | 배우는 것 | 마친 학생이 할 수 있는 것 |
|---|---|---|
| 1. 온톨로지 마스터 | 온톨로지가 무엇이고 왜 필요한가(수치만으로는 조치를 정할 수 없다) → 무엇으로 구성되나(클래스 · 인스턴스 · 속성 · 관계 · 식별자 · 제약) → 어떻게 만드나(골든 퀘스천으로 범위를 정하고 설계 → 그래프 구현 · 질의 → 절차 · 판단 조건 연결) → 문서 인제스천(원문에서 뽑고 사람이 검토해 적재, 출처 확인) → 골든 퀘스천에 지식이 실제로 답하는지 검증 | 새 현장 문제를 받아도 스스로 온톨로지를 설계하고 구축 · 검증할 수 있다. 결과물은 질문 · 모델 · 문서 · 추출/검토 · 적재 코드 · 조회 검증을 갖춘 구축 결과다 |
| 2. 에이전트 마스터 | 그 지식을 쓰는 에이전트 — 하나가 아니라 무궁무진한 활용: 설비 원인 점검, 품질 접수, 분석 · 시각화, 회의 후속 업무, 자기 자료 학습 · 퀴즈, 작성 · 검토 협업처럼 목적 · 입력 · 도구 · 결과가 다른 활용과 그 구현 · 검증(도구 · MCP · 스킬, 명세, 근거와 승인 경계) | 어떤 일을 맡길 수 있는지와 필요한 자료 · 도구 · 권한 · 검증을 판단하고, 목적이 다른 에이전트를 스스로 설계 · 구현 · 검증할 수 있다 |
| 3. 프로세스 | 지식과 에이전트를 업무 흐름(BPMN)에 넣어 사람의 승인 · 실행 · 결과 확인까지 잇는다. 마지막 종합 실습(교대 인수인계)이 1~2단계를 종합한다 | 사건 한 건을 지식 → 에이전트 판단 → 사람 승인 → 실행 · 기록으로 잇는 흐름을 만들고 돌릴 수 있다 |

**P목-3** 한 주제를 배우는 순서와 각 단계의 몫:
- 이론에서 원리와 까닭을, 포털 실습에서 그 개념이 완성된 시스템에서 실제로 어떻게 돌아가는지를 보고, 코딩 랩에서 포털에서 본 그 기능을 직접 만들어 본다 — 단 포털보다 더 어렵게, 현업에 가까운 현실 문제로.
- PBL은 이 과정 밖의 별도 수업이고, 목표는 학생이 그 PBL에서 스스로 문제를 정의하고 온톨로지 · 에이전트 · 프로세스를 설계 · 구현 · 검증할 수 있을 만큼 끌어올리는 것이다. 이론은 원리와 설계 판단을, 도구 실습은 배운 것을 정해진 화면에서 하나씩 짚으며 따라 가는 체험을, 코딩 랩은 손으로 만들며 그때 필요한 이론까지 다시 풀어 익히는 몫을 가장 많이 맡는다.
- 가이드는 이 몫을 학생 손에 넘기는 글이므로, 도구 실습 가이드와 코딩 랩 가이드는 하는 일이 다르다.

**P목-4** 원리와 가치가 주인공이고 HYD · 포털 · 제품은 재료다. 우리는 강의를 하는 것이지 우리가 만든 시스템을 보고 · 자랑하는 것이 아니다 — 온톨로지 → 에이전트 → 프로세스를 마스터하게 하려고 무엇을 왜 하는지를 가르치고, 포털 · HYD는 그 원리를 보여 주는 도구다. 가이드도 같다: 학생이 버튼 순서만 외우면 도구가 바뀌는 순간 쓸모가 없다. 피지컬 AI의 맥락은 설비 · 지식 · 판단 · 사람 · 실행의 연결이고, 무게는 온톨로지와 에이전트에 있다.

**P목-5** 사진이 없는 조작은 따라 할 수 없는 조작이다. 학생은 가이드만 보고 따라 하므로 모든 과정을 사진으로 담는다(가장 중요). 사진은 본 촬영 화면에서 뽑는다 — 리허설 화면이나 비슷한 다른 화면은 랩이 안정되기 전의 상태라 단계 · 버튼 위치 · 결과 값이 실제와 어긋난다. 없는 화면을 지어내면 학생은 그 화면을 찾다 막히고, 막힌 까닭을 스스로 알아낼 수 없다.

**P목-6** 복사할 것을 텍스트로 주는 까닭: 노베이스 학생이 사진 속 명령 · 프롬프트를 손으로 옮기면 오타가 나고, 그 오타가 「과제가 어렵다」가 아니라 「가이드가 틀렸다」로 끝난다. 블록 종류를 색과 글자로 함께 표시하는 것도 학생이 AI에 보낼 글과 터미널에 칠 글을 섞지 않게 하려는 것이다.

**P목-7** 코딩 랩 학생 폴더의 경계가 왜 그런가:
- 학생 실습 폴더와 가이드에 정답 · 해결 로직 · 완성 프롬프트 · 강사 참조를 가리키는 말을 넣지 않는 까닭: 학생의 AI(Codex · GitHub Copilot)가 폴더 전체를 읽으므로 넣는 순간 아무 요청이나 해도 정답이 나오고 과제가 장난감이 된다.
- 학생용 완성본이 실습 폴더와 따로 받는 별도 묶음인 것도 같은 까닭이다 — 같은 폴더에 있으면 학생의 AI가 읽어 정답이 된다. 완성본은 무료 계정조차 못 쓰는 학생이 결과를 확인하는 용도다.
- 작업 규칙을 `AGENTS.md`와 `.github/copilot-instructions.md`에 같은 내용으로 두는 것은 두 도구가 읽는 위치가 달라서이고, `입력/`에 앞 단계 완성 상태를 주는 것은 앞 단계를 안 했거나 PC가 초기화돼도 독립 시작이 되게 하려는 것이다.

**P목-8** 학교 PC는 재부팅하면 초기화될 수 있다. 초기화 뒤 실습 폴더의 신뢰가 풀려 VS Code가 제한 모드로 열리면 AI 도구가 동작하지 않는다 — 그래서 가이드는 재다운로드로 다시 시작하는 길을 주고, 받기 시험은 초기화된 PC와 개인 환경을 구별해 확인한다. GitHub는 강사 쪽 원본 · 배포 관리에 쓰므로 학생에게 개인 Git 설정을 요구하지 않는다.

**P목-9** 두 과정(통합반 · 실전반)은 이 줄기를 함께 걷는다. 도구 실습은 화면 · 조작이 같아 두 과정이 같은 안내 · 캡처로 충분하고, 코딩 랩은 과정마다 요구 · 입력 · 출력이 달라 가이드도 달라진다. 실전반 가이드를 쓸 때 조사한 현업 사례는 가이드 문장에 「현업에서는 이렇게 한다」는 단정으로 쓰지 않고, 자료와 문제를 탄탄하게 준비하는 근거로 쓴다.

**P목-10** 이 규칙이 생긴 실제 사고와 사용자 지적(처음 보는 사람이 이해할 만큼):
- 실라버스 행의 배정 시간 · 상세를 보지 않고 만들어 50분 수업을 7분으로 만들고, 그 상태로 완료라고 보고했다. 실라버스를 안 보면 50분 수업이 7분이 된다. 가이드도 실라버스 행 문장에서 시작해 문장마다 가이드 단계가 있는지 대조하지 않으면 같은 일이 생긴다.
- 포털 실습(실전 2-2)에 VS Code 장면 · 기록 파일 · START · 결과 폴더를 넣고, 뺀 뒤에도 「다음 실습부터 VS Code…」로 엮었다. 코딩 랩 조항(제공물 · 저장 · 다시 열기 · 바이브 코딩)을 도구 실습에 넓혀 적용한 것이다 — 도구 실습과 코딩 랩은 완전히 별개다.
- 통합반 4회차 포털 실습 1(매뉴얼 등록과 검토)은 도구 실습인데 `START.md`가 있고, 그 첫 화면이 옛 실라버스 행 그대로 「매뉴얼 원문과 등록된 지식의 조건·출처 대조하기 … 코드를 작성하지 않는 관찰·대조 실습 … 포털에 문서를 새로 등록하거나 적재하지 않습니다」라고 말했다. 실라버스 39행은 이미 「올리기 → 추출 요청 → 대조 · 고침 → 적재」로 바뀌었고 덱 40장도 그렇게 말했다 — 실라버스를 고친 뒤 그 행을 가리키는 가이드 · `START.md` · `안내.html` 제목 · 실습 대본 · ZIP을 함께 고치지 않은 결함이다.
- 통합반 1회차 실습 2 · 3 가이드는 옛 판(「실행 환경과 서비스 연결 확인 … ZIP · compose」, 「쿨러 사건 관찰과 근거 연결표」)으로 남았고, 실라버스 9 · 10행과 덱 43 · 45장, 이미 만들어진 실습 영상 04(실행 환경 27:00 — README 소개 → 설치부터 실행 → 포털 메뉴 일곱 묶음 소개) · 06(전체 과정 관찰 7:50 — 매뉴얼 적재 → 쿨러 열화 주입 → AI 판단 → 운전원 승인 → 조치 · 재관측)과 다른 말을 했다. 반대로 실습 1(학습노트) 가이드는 사용자가 확정한 영상 02대로 「주제 갤러리」였는데 덱 11장이 영상에 없는 「세 구획 · 작성일」을 써서 어긋났다 — 영상이 있으면 그 영상이 실제로 한 것이 기준이다.
- 폐기판 산출물(랩 폴더 · 구성)과 옛 구성안의 「사용자 확인 대기」 항목을 실라버스와 대조하지 않고 이어받았다. 요청문의 「재사용할 수 있다」를 「재사용한다」로 읽었다 — 「대조해 맞으면 쓴다」이다.
- 식별자 · 속성 키를 낭독하고 「랩 그래프」 같은 제작 용어를 썼으며, 조작만 읽는 얕은 설명 · 결과를 띡띡 읽고 넘어가는 설명을 했다. 가이드 문장도 같은 잣대로 본다.
- 학생 랩 폴더에 제작 기록(`.evidence` 경로를 적은 화면 목록, 예상 시간 표)이 섞이거나 회차 안내 README에 「실제 실습/촬영 미수행」 같은 진행 상태가 남았다 — main 산출물은 학생이 읽을 것만 둔다.
- 학생 문장에 「시작본」 「이미 있는 추출 결과」 같은 운영 사정이 새어 나왔다 — 학생은 수업 운영의 내부 사정을 알 필요가 없다.
- 포털 실습 5편의 이전 판은 배정 시간 · 상세를 안 보고 만들어 수업이 짧고 얕았는데 완료라고 보고했다. 그래서 완료는 「했다 · 검사 통과」가 아니라 이 문서의 인수 조건을 통과한 것이다.

**P목-11** 가이드에 「교육용이라 실제와 다르다」 같은 단서 · 면책을 넣지 않는 까닭: 학생은 그 문장에서 아무것도 할 수 없고, 원리가 재료에 묶이지 않았다면 면책이 필요 없다. 값은 「이 설비에서는 …」으로 그 상황의 설정으로만 말한다.

## 작업 컨텍스트

**P맥-1** 대상과 과정. 대상은 코딩을 모르는 노베이스 대학생 · 취업 준비생이다(두 반 모두 처음 배우는 학생). 과정은 넷이다: 통합반 온라인(44시간, 11회차) · 실전반 온라인(32시간, 8회차) · 통합반 오프라인(10회) · 실전반 오프라인(9회). 온라인은 강사 한 사람이 영상으로 설명하고 조작해 보이고, 오프라인은 학생이 직접 한다. 학생은 노션 학습 포털의 회차 페이지에서 영상 · 교재 · 가이드를 연다. 오프라인은 온라인 선행 학습 뒤 학생이 가이드로 직접 하고 강사는 막힌 곳만 돕는다(대본 · 영상은 온라인만).

**P맥-2** 오프라인 편성: 매회 50분 수업 · 10분 휴식 × 4교시이고 실제 진행은 강사가 조절한다. 오프라인 실습 행의 구분 칸은 실습 장소를 붙인다(실습(포털) · 실습(VS Code) · 실습(Notion) · 실습(ARROWS) · 실습(Neo4j) · 실습(bpmn.io)). 오프라인의 회는 「N회」로, 온라인은 「N회차」로 부른다.

## 작업 요령

### 시작하기

**P요-1** 이 문서 하나만 끝까지 읽는다 — 가이드를 만드는 데 필요한 규칙은 여기 다 있다. 다른 산출물의 문서를 일괄 적용하지 않는다(가이드 작업에 이론 덱의 규칙을 끌어오지 않는다). 촬영 원천의 값 · 함정은 그 도구 `촬영준비.md`를 자료로 연다.

**P요-2** 해석 순서: 지금 사용자 지시(가장 뒤의 결정, 번복은 마지막 결정) → 이 문서와 실라버스 최종본 → 스킬 기본값 → 과거 인계 · 요청문 · 샘플. 스킬과 이 문서가 부딪치면 이 문서가 맞다. 확정된 최신 결정은 옛 것을 덮고 옛 요청문 · 샘플로 되돌리지 않지만, 관련 없는 규칙까지 지우지는 않는다. 리서치의 제안을 임의로 필수 요구로 올리지 않는다. 이 순서는 권한을 넓히지 않는다 — 가이드 작업에서 포털 로직 · DB · 서비스를 바꾸지 않는다.

**P요-3** 다시 시작할 때(새 세션 · 대화 요약 뒤 · 실패 직후):
- 기억은 없다고 보고 이 문서를 다시 끝까지 읽고, git · 실행 상태와 인계(로컬 `.evidence/인계/`)의 차이만 확인해 최신 판본 · 다음 행동 · 미확인을 복원한다. 오래된 진행 기록은 현재 작업 목록이 아니다.
- 인계의 옛 완료 표시 · 경로는 믿지 않고 실물을 열어, 게시 여부는 게시 판본으로 다시 확인한다. 과거 샘플의 지시 · 포트를 현재 값으로 쓰지 않는다.
- 같은 판본을 읽은 기록(문서 · 해시 · 범위)이 있으면 바뀐 부분만, 없으면 원문 전체를 반드시 읽는다. 요약 · 키워드 검사는 원문을 대체하지 않고, 미확인을 임의 결정으로 메우지 않는다.
- 지난 세션의 도구 부재 · 오류와 다른 PC의 성공은 지금 여기서 다시 확인한다. `.evidence`와 촬영 원본은 git clone에 없으니, 없으면 그 의존성을 적고 가능한 준비를 계속한다.

**P요-4** 이어받기 전에 대조한다. 시작 전에 그 종류의 본보기(P맥-7)를 통독해 「실제 학생이 이 가이드로 이렇게 따라 한다」를 잡는다. 폐기판 산출물(랩 폴더 · 구성안 · 대본 · 가이드)과 옛 구성안의 「사용자 확인 대기」 항목은 실라버스 그 행과 대조하지 않고 이어받지 않는다 — 요청문의 「재사용할 수 있다」는 「대조해 맞으면 쓴다」이지 「쓴다」가 아니다.

**P요-5** 실습 종류부터 정한다 — 화면 · 조작이 정해진 도구 실습(포털 · ARROWS · Notion · Neo4j Browser · bpmn.io)인가, VS Code에서 만드는 코딩 랩인가. 둘은 별개의 실습이라 서로의 장면 · 예고 · 제공물을 섞지 않는다. 빈칸이 있으면 다음 단계로 가지 않는다. 다 만든 뒤에는 대조표끼리가 아니라 실라버스 원문과 다시 맞춰 본다(함께 빠진 항목은 목록끼리 비교해서는 안 보인다).

**P요-8** 시간. 대조표의 「영상 구간 · 예상 분」은 그 실습의 온라인 영상이 실라버스 행 하나를 감당하는지 이 단계에서 보려는 칸이다 — 분의 판정(행 단위, 늘어남 · 줄어듦)은 그 영상의 몫이고, 가이드는 그 칸을 채워 영상 쪽에 넘긴다. 가이드 자체에는 시간 조건이 없고, 오프라인은 강사가 직접 유연하게 진행하므로 오프라인 가이드도 내용으로만 준비한다.

**P요-9** 실라버스를 고칠 일이 생기면(결과 조건은 P-6 · P-7 · P-8):
- 실라버스와 교재는 양쪽 방향으로 맞춘다 — 실라버스가 맞으면 가이드를 고치고, 가이드 쪽이 맞으면(이미 만들어진 영상 · 포털 실제 기능 · 앞뒤 흐름이 근거) 실라버스 고치기를 사용자에게 묻는다.
- 행의 상세 항목과 행 이름 문구는 작업하며 바꿀 수 있다 — 무엇을 왜 바꾸는지 먼저 말하고 고친다. 고정 항목을 바꾸려면 사용자에게 따로 받는다.
- 정본 엑셀과 노션 실라버스를 함께 맞추고(노션 수정은 게시라 묻는다, P요-23), 고친 행에 묶인 앞뒤 다리 · 오프라인 짝 행 · 다른 과정 짝 행을 다시 판정한다.
- 가이드의 표현을 고치는 일과 실라버스를 고치는 일을 혼동하지 않는다. 최신 결정과 엑셀이 어긋나면 임의로 섞지 말고 어긋난 셀을 적어 맞춘다.

### 앞뒤 산출물과 잇기

**P요-10** 연결점 찾기. 바로 앞 이론 대본(덱의 실습 간지 · 설명 장)과, 코딩 랩이면 앞에서 본 포털 화면에서 연결점을 찾아 가이드의 여는 단락이 앞 단계를 이름으로 받아 시작하게 쓴다(포털에 대응 기능이 없으면 앞 이론에서). 여는 말의 예: 포털 실습은 「이론에서 이걸 따졌죠. 포털에는 이렇게 들어가 있습니다」, 코딩 랩은 「포털에서 이렇게 돌아가는 걸 봤죠. 이제 이걸 직접, 더 지저분한 현실 자료로 만들어 봅니다」.

**P요-11** 연결 산출물 맞추기(결과 조건은 P-8 · P-184~P-188):
- 덱의 실습 설명 장(목표 · 입력 · 할 일의 범위 · 산출물 · 성공 기준) · 가이드 첫 화면 · `START.md` · 그 장의 이론 대본 실습 소개가 어긋나면 실라버스 실습 행에 맞춰 모두 고친다. 덱 · 대본은 그 산출물의 절차로(확정 회차면 화면 · 발화는 승인 뒤).
- 승인된 덱 화면 문구는 배포된 `산출물/<과정>/이론/NN회차/*.pptx`에서 그 문구가 든 런만 python-pptx로 바꾼다.

- 근거와 어긋나는 수정 요청은 그대로 반영하지 않는다.

**P요-12** 확정된 산출물(P맥-13)의 화면 · 발화 · 영상은 결함을 「대상 · 어긋남 · 근거 · 고칠 문장」으로 기록하고 사용자 승인을 받은 뒤 그 범위만 고친다. 승인 없이 고칠 수 있는 것은 발표자 노트, 덱 MD의 화면에 나가지 않는 칸(제작 기준 · 화면 구성), 대본의 비낭독 부분(파일 머리 · 「이 회차의 구성」 표 · 행 제목 줄 · 끝 표시)뿐이다.

### 만드는 순서

**P요-13** 순서:
- 실습 하나를 시작 → 수행 → 검증 → 저장 → 영상 · 가이드 전달까지 끝낸 뒤 다음 실습으로 간다. 각 단계는 앞 단계가 끝나야 넘어간다.
- 실습 한 개의 순서: 시작(실라버스 대조표 · 앞과 잇기) → 랩 강화 → 구성안 사용자 확인(꼴은 P요-23) → 대본 → 대본 사용자 확인 → 분량 → 리허설 · 녹음 · 촬영 → 검사 → 가이드 · ZIP 만들기 · 정적 검사 · 패키지 검사 · 받기 시험 → 게시(영상은 other-pc, 문서는 main, 노션 두 과정 회차 페이지) → 완료 보고.
- 가이드 쪽 순서는 **준비 → 리허설 1회 → 수정 → 본 촬영 → 사진 추출 → 동기화**다. 준비 때 실습 자료 · 시작 상태 · 완료 조건과 대본 초안 · 가이드 단계를 정적으로 맞추되, 미리 준비하는 것은 관찰할 항목과 판단 조건뿐이다(AI 응답 · 실행 결과는 본 촬영 화면에 나온 뒤 쓴다). 리허설 전에 사진 가이드를 완성하지 않는다 — 단계 · 자료 링크 · 판정 조건을 먼저 준비하고, 랩이 안정된 뒤 본 촬영 화면에서 추출한다. 도구 실습의 실습 자료는 그 도구 화면의 시작 상태와 경계(P-57~P-66)다.
- 영상 쪽에서 찍은 뒤 시간 계산(`python 제작용/촬영/시간계산.py check`)으로 예상과 비교하고 바뀐 대사 · 입력 · 순서를 받으면 P요-11대로 가이드에 맞춘다.

**P요-14** 브라우저 기반 제작:
- 실습 제작 · 촬영은 모두 브라우저 기반이다. 포털 · ARROWS · Notion · Neo4j는 브라우저 화면이고, VS Code도 데스크톱 앱이 아니라 공식 `code serve-web`으로 띄운 웹 VS Code를 ego 브라우저 탭에서 조작한다(값 · 함정은 [`제작용/촬영/vscode/촬영준비.md`](../../제작용/촬영/vscode/촬영준비.md) 1절 「바로 가는 길」 · 2절 함정표). 데스크톱 앱 조작 · computer use · CDP 원격 디버깅 경로는 쓰지 않는다 — 학생 가이드에 넣을 네이티브 장면만 따로 캡처한다.
- 웹판은 표시 언어를 영어로 두므로(한국어 팩이 웹판에서 글자를 엉뚱하게 바꾼다), 학생 가이드 사진은 같은 결과 파일을 네이티브 한국어 VS Code에서 따로 캡처한다. 웹판과 네이티브의 동선 차이(창 제목줄 · 메뉴줄 대신 ☰, 「Get Started with VS Code for the Web」 문구, 폴더 열기는 브라우저 주소로, 다운로드 · 압축 해제 · 폴더 열기 · 신뢰 창)는 따로 처리하고 `vscode/촬영준비.md` 3절(웹판 화면 차이) · 4절에 기록한다.

**P요-18** 문장 쓰기(결과 조건은 P-17~P-29 · P-161~P-169):
- 말투 · 본보기: 가이드의 말투 · 쓰지 않는 말은 이 문서가 정한다. 강의별 승인된 예시 · 템플릿 · 청중 수준(본보기)을 먼저 따른다.

**P요-27** 사실 근거 찾기(결과 조건은 P-32 · P-34~P-42). 일반 사실(제품 동작 · 금액 · 모델명)은 검색으로 1차 자료 · 공식 문서에서 확인하고, 참고 자료가 그럴듯하다는 것은 근거가 아니다. 계층 이름 · 역할 · 설계 원칙은 설계서 v3, 실제 동작 · 값은 코드 · 사실표가 우선이다. 열어 보았는데도 없을 때만 `미확인`이다. 호출이 있다는 것과 실제로 쓰였다는 것, 조회 성공과 답이 맞다는 것은 다른 주장이다.

### 일하는 방식

**P요-23** 범위 · 반복 · 확인 받기.
- 범위는 요청대로, 그 안은 끝까지: 승인된 범위의 수정 · 동기화 · 검증을 끝까지 하고 제안만 하고 멈추지 않는다. 검토만 · 정리만이면 고치지 않고, 윤문만이면 뜻을 지켜 표현만 다듬으며, 요청하지 않은 ZIP · 보고서 · 업로드를 덧붙이지 않는다. 정적 가이드 작업에는 실행 · AI 시연 · 캡처 · 음성 생성이 들어가지 않는다(요청한 도구 · 회차에서만). 처음부터 이 문서와 원 자료를 끝까지 읽고 완성판을 만들고, 여러 회차에 같은 틀을 적용할 때는 대표 하나로 먼저 확인한 뒤 넓힌다.
- 같은 일을 반복하지 않는다: 끝낸 작업, 같은 판본의 재독 · 재생성 · 재검사 · AI 호출을 되풀이하지 않고 새 수정 · 새 실패 · 미확인과 영향받는 파생물만 본다. 그렇다고 필요한 최종 검증을 빼거나 표본 · 키워드 검사로 내용 검토를 대신하지 않는다.
- 묻는 것은 되돌리기 비싼 것만: 답이 문서 · 실라버스에 있거나 이미 정한 것, 허용된 반복 작업은 다시 묻지 않는다(사전 승인 단계 없음 — 예외는 새 촬영 리듬 · 도구의 대표 구간, 실습 구성안 · 대본). 묻는 것: 풀리지 않는 충돌, 새 범위 · 실행 권한, 실라버스 조정(교재 근거로 행을 고침), 원격 push · 노션 게시 · 노션 실라버스 수정 · 결제, 데이터 볼륨 · 원자료 · 강사 손질본 삭제.
- 묻는 꼴: 양쪽 내용과 제안을 쉬운 말로(「상황 → 제안 → 이렇게 해도 될까요」), 삭제는 실제 동작 이름으로. 결과 확인을 사용자에게 넘기지 않고(열 수 없는 화면 · 들을 수 없는 음성만 상태를 특정해 요청), 지적은 같은 유형 전체에 적용하며, 앞의 판정을 뒤집으면 그렇다고 밝힌다.
- 사용자 확인을 받을 때는 전문을 읽게 하지 않고 판단용 요약을 준다(구성안 → 대본 두 번, 가이드도 같은 꼴): ① 배정 · 계획 시간과 구간별 분 ② 구성 흐름 ③ 실라버스 문장 ↔ 구간 · 가이드 단계 대조(빈칸 0) ④ 실제 문장 발췌(시작 · 중간 여러 곳 · 끝) ⑤ 판단할 지점만 준다.
- 비용이 드는 일은 먼저 알린다(음성 · 영상 생성, 모델을 많이 부르는 일, 작업자 여럿) — 규모와 견적(글자 수 · 크레딧 등)을 알리고 진행한다. 유료 실험은 상한을 정하고, 실패하면 같은 조건을 재실행하지 않고 기존 결과부터 분석한다.

**P요-24** 작업 단위와 작업자:
- 한 세션은 한 단위(회차 하나 · 실습 하나)만 하고, 끝나면 인계를 고쳐 쓴 뒤 감독에게 보고하고 멈춘다(긴 세션이 요약되며 규칙을 잃지 않게, 품질이 뒤로 갈수록 줄지 않게). 새 세션은 사용자나 사용자가 맡긴 감독 세션이 연다.
- 파일이 겹치지 않는 갈래만 동시에 돌리고 같은 파일을 두 세션이 동시에 고치지 않으며, 커밋은 그 단위 세션이 경로를 지정해 한다.
- 단위를 끝내기 전에 새 검토자를 세운다(이 문서 · 산출물 · 품질 본보기만 주고, 고치지 않고 목록만 받음). 서브에이전트는 `opus`(fable 금지)이고, 지시에 범위 · 금지 · 보고 양식을 적으며 작업자는 원문과 줄 번호를 가져온다. 남의 완료를 대신 확정하지 않는다.
- 우회하지 않는다 — 도구의 한계는 원인을 고치고, 검사기 경고를 무시해 통과로 바꾸지 않으며, 보안 설정 · 권한 제한을 끄거나 돌아가지 않는다. 다른 세션의 자원 · 탭을 확인 없이 끄거나 지우지 않는다.

**P요-25** 판정 범위를 넓히지 않는다: 한 도구 · 샘플 · 옛 판본의 상태를 다른 범위로 넓히지 않는다. 보고는 항목별로 요구 → 결과 → 근거를 대조해 적고 상태어(P-200)로 쓴다.

**P요-26** 저장소와 이 문서 고치기.
- 브랜치: 작업 브랜치는 main 하나, 예외는 `other-pc` 하나다. 문서 · 도구는 main에서 고치고 other-pc는 main을 병합해 따라간다(other-pc에서 바뀐 문서는 그 변경만 main으로 가져온 뒤 다시 병합). 다른 작업 브랜치를 만들지 않고 옛 분기는 archive/ 태그로만 둔다.
- 커밋: 시작과 커밋 직전에 실제 HEAD · 원격 · 미커밋을 확인하고, 허용된 경로만 지정해 커밋하며(`git add .` 금지) 다른 세션의 미커밋은 보존한다. 원격 변경은 받아 병합하고 rebase · 강제 push · reset · stash는 하지 않는다. 원격 push는 묻는다(P요-23).
- 비밀: `.env`는 열지 않고, 키 값은 어디에도 다시 찍지 않는다.
- 기록 자리: 이 문서에는 규칙만, 날짜 · 인용 · 경위는 결정 기록에, 진행 상태는 인계에 둔다(둘 다 main 밖 로컬 `.evidence/`). 인계에는 현재 커밋 · 판본, 재실행 금지 목록, 남은 실패와 다음 행동 · 증거 위치를 적고 규칙은 이 문서의 번호로 가리킨다. 진행 기록 · 인계 · 요청문 · 찌꺼기는 main에 두지 않는다.
- 이 문서를 고칠 때(다시 더러워지면 안 된다): 덧붙이지 않고 그 주제 자리를 다시 써서 겹치는 문장과 합친다(문장 사이 끼워 넣기 · 괄호나 「단」 꼬리도 덧붙이기다). 한 문서 안에 같은 뜻을 두 번 두지 않는다. 서로 부딪치는 문장이 생기면 그 자리에서 최신 결정 하나로 정리하고 옛 문장을 남기지 않는다.
- 본보기가 보여 주는 것은 「본보기대로」로 줄이고, 본보기로 알 수 없는 것(판단 기준, 되돌리기 비싼 금지, 실제 사고에서 나온 규칙, 숫자 · 경로 · 도구)만 문장으로 둔다. 결정 번호 꼬리표를 달지 않고, 규칙 문장은 근거 없이 바꾸지 않는다.
- 고친 뒤 전후 글자 수를 재고, 늘었으면 까닭을 커밋 메시지에 적는다. 커밋 전에 `.evidence/기준정리/도구/재편검사.py`(로컬, 없으면 같은 확인을 손으로)로 빠짐 · 같은 뜻 두 번 · 덧붙이기 0을 확인한다. 이 문서의 이름 · 번호를 바꾸면 그것을 가리키는 촬영준비 · 스킬 · CLAUDE.md · AGENTS.md를 같은 커밋에서 고치고 옛 이름 검색 0을 확인한다.

## 인수 조건

판정 대상: 실습 하나의 가이드(`guide.html` · 기존 `가이드.html` · `안내.html`)와 그 생성 원본 · 사진 · 학생 패키지(랩 폴더 · ZIP) · 코딩 랩의 `START.md` · 회차 안내 README · 노션 회차 페이지의 그 실습 항목, 그리고 그 가이드의 완료 보고.
