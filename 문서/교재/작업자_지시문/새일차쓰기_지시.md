## 틀과 분량
- 표지(`기관: 경남대학교 피지컬AI 사관학교`, `과정: 통합반 N일차`) → 학습목표 → 목차 → [간지 → 본문]… → 용어 정리 → 퀴즈 간지 → 퀴즈 3문항 → 정답과 판단 기준. 고정 문구는 제작 기준 4절과 3일차 덱의 것을 그대로 쓴다.
- 단원 = 실라버스의 이론 행. 단원 제목은 「~하기」를 옮기지 않고 기술적 제목으로 쓴다.
- **단원의 이론 본문 장수 = 실라버스 분 수 ÷ 1.5 (±15 %).** 내용이 많으면 조금 넘고 가벼우면 조금 모자라도 된다.
- 실습은 실습마다 2장: 간지(`실습: 제목`) + 설명 1장(무엇을 하는지, 끝나면 무엇이 만들어지는지). 절차 · 메뉴 이름 · 화면 캡처 · 길 안내 금지. 실습 간지는 실라버스의 순서대로 해당 이론 단원 뒤에 둔다.

## 쓰는 법 (1~4일차를 만들며 얻은 것 — 반드시 지킨다)
- **장 목록부터 짠다.** 단원마다 제목과 메시지만 먼저 쓰고, 메시지만 이어 읽어 이야기가 되는지 본다(필요 → 개념 → 적용). 그다음 본문 · 노트 · 그림을 쓴다.
- **필요가 먼저, 용어가 뒤.** 단원은 문제 상황에서 시작한다. 1~4일차와 같은 사건(HYD-01의 유온 상승 → 쿨러 성능 저하 경보 → 원인 후보 → 조치 후보 → 승인)을 그 일차의 주제로 이어 쓴다.
- **메시지는 정의 낭독이 아니라 쓸모를 말한다**(왜 필요한가, 없으면 무슨 일이 생기는가, 무엇을 할 수 있는가 — 기술적 이유로). 단, 「~를 정해 두어야 ~할 수 있다」「~므로 ~한다」 같은 **한 가지 틀을 되풀이하지 않는다**(한 단원에 같은 틀 서너 번까지). 원인과 결과, 없을 때 생기는 일, 대비, 실제 사례를 주어로, 정의와 쓰임, 조건의 서술을 고르게 쓴다. 단원의 핵심 용어를 처음 세우는 장은 정의형이어도 된다. 다 쓴 뒤 단원마다 메시지를 뽑아 문장 끝과 이음말의 반복을 세고 고친다.
- **전문성**: 정식 용어, 영어 풀네임(처음 한 번), 정확한 정의, 실제 값 · 식별자 · 예를 화면에 싣는다. 쉽게 풀되 뜻을 바꾸지 않는다. 깊이의 상한은 「무엇이고, 왜 있고, 우리 시스템에서 무슨 일을 하는가」. 내부 옵션 · 구현 방식으로 파고들지 않는다.
- **대등한 항목 여럿은 묶어서 견준다**(왜 구분하는가 → 같은 예로 견주는 한 장 → 우리 사건에 쓰인 것). 항목마다 한 장씩 정의를 읽지 않는다. 한 그림을 여러 장에 걸쳐 한 부분씩 밝히는 것은 꼭 필요한 곳에만 두세 장까지.
- **한 장 한 주제.** 그림만 두고 비우지 않고, 글로 메우지도 않는다. 새 용어는 한 장에 하나에서 셋.
- **표현 수단을 섞는다**: 삽화(직접 그린 SVG — 대상이 무엇인지 알아볼 수 있게, 그림 안에 글자를 넣지 않고 라벨은 덱 MD의 요소로), 실제 데이터 · 메시지 · 로그를 보이는 코드, 아이콘 파이프라인, 관계도, 카드 · 흐름 · 비교 · 단계 · 풀이. 표는 꼭 표여야 하는 것만. 같은 형태가 세 장 넘게 이어지지 않게. 삽화는 3일차 스크립트의 그림 조각과 화풍을 가져와 그린다(단원마다 핵심 그림 두세 개면 된다. 삽화를 그리느라 시간을 다 쓰지 않는다. 덱의 3분의 1쯤이 삽화 · 그림이면 충분하다).
- **구현 설명과 몰라도 되는 것**: 「우리 시스템은 이렇게 구현했다」「표준과 다르다」, 단서 · 변명 · 면책, 내부 사정(없는 기능, 강제되지 않는 것, 버전 차이), 가상 · 시뮬레이터 강조를 화면에도 노트에도 쓰지 않는다. 없는 것을 있다고 쓰지 않되 없다는 사실을 굳이 알리지도 않는다. 예는 실제로 있는 것 가운데서 고른다.
- **범위를 넓히는 말**(「모두」「항상」「유일하게」「어느 쪽에서 보아도」)은 화면의 예가 전부 그 말에 맞을 때만.
- **노트**: 강사가 그대로 읽을 수 있는 말, 서너 문장(여러 항목을 담은 장은 다섯 문장까지, 짚는 순서를 적는다). 강사에게 하는 지시문이 아니다. 화면에 없는 새 내용을 노트에만 두지 않는다. 길 안내(「다음 장에서」) · 질문형 연결 금지. 비유는 어려운 개념 한두 곳에만 화면의 「비유」 칸(닮은 점 한 줄 + 다른 점 한 줄)으로, 그 밖에는 넣지 않는다.
- **앞 일차에서 가르친 것은 다시 설명하지 않는다**(이어받는 장은 한두 장). 뒤 일차의 주제를 앞질러 깊게 다루지 않는다. 약어 풀네임은 앞 일차가 붙인 것(OT · DMZ · IT · PLC · SCADA · MQTT · HMI · HITL · MES · SOP · DMN · BSC · KPI · LLM · RAG · JSON · SQL · LOTO)을 다시 붙이지 않는다. 「부품」과 「구성 요소」를 섞지 않는다(쿨러는 구성 요소).
- 각 장에 `### 제작 기준` 칸을 두고 그 장의 사실이 사실표의 어느 절에 근거하는지 적는다(화면에 나가지 않는다. 절대 경로 · 사람 이름을 쓰지 않는다).
- 퀴즈 3문항은 시나리오 해석 · 근거 구분 · 책임 경계 판단을 묻고 본문으로 풀려야 한다. 정답 번호가 몰리지 않게 한다.

## 빌드와 확인

## 검토와 반영 (네가 끝까지 한다)
덱이 빌드되고 네가 한 번 확인한 뒤, **검토자를 부른다**: Agent 도구로 `subagent_type: "general-purpose"`, `model: "sonnet"`인 서브에이전트를 하나 띄우고, 다음을 프롬프트로 준다 — 「교재 덱의 검토다(고치지 않는다). 지시 문서 `<작업 폴더>/새일차검토_지시.md`를 읽고 그대로 따른다. 덱: (경로), 렌더 PNG 폴더: (경로), 사실표: (경로), 실라버스의 일차: 통합반 N일차, 산출물: scratchpad `새일차검토_0N일차.md`.」 검토서가 오면 읽고, 「상」과 「중」은 모두 반영하고 「하」는 판단해 반영한다(검토자의 제안이 제작 기준이나 사실과 어긋나면 따르지 않고 이유를 보고에 적는다). 반영 뒤 다시 빌드 · 렌더하고 고친 장을 본다. 검토는 한 번이면 된다.
