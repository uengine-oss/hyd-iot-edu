# 시스템 2. 기준

## 2026-10-27 최신 확정 — PC 이미지 배포와 강사 해제 코드

- 각 PC에는 이미 같은 환경이 설치돼 있고 메인 PC의 이미지를 배포한다. 별도 공개 강사 서버·HTTPS 구축은 이 수업 배포의 필수 조건이 아니다. 처음 잠금 업데이트를 기존 이미지에 반영한 뒤, 마지막 날에는 각 PC에서 강사 코드를 한 번 입력해 교대 실습을 연다. 다시 clone·OS/도구 재설치·마지막 날 git pull을 요구하지 않는다.
- 기본 상태는 준비된 A/B/C 에이전트 실행과 기존 수업 자료 조회다. 교대 실습의 에이전트·스킬 편집/교대 단계 배정/제공 문서 추출·검토·적재는 코드로 연다. 제공된 교대 BPMN의 시작 입력·작업·검토·보완 분기는 유지하면서 표시 이름·그림 배치·세 초안 단계의 에이전트 배정만 바꾸어 별도 `ShiftHandover` 판본을 등록할 수 있다. API는 XML 구조와 매핑을 검사하고 등록 시 저장된 XML도 다시 대조한다. 자유 질문·임의 모델·도구 서버·일반 흐름/구성 관리와 임의 문서 AI 추출은 해제 후에도 열지 않는다. 기본 지식의 최초 적재는 배포된 정확한 검토본만 예외로 허용한다.
- 화면 표시만 잠그지 않고 프로세스 API와 워커의 AI 실행 직전에도 검사한다. `unlocked=true` 같은 설정은 권한 근거가 아니다. 강사 코드의 서명을 검증하고 재시작 시에도 저장된 코드를 재검증한다. 이미지에는 검증 공개키만 넣고 강사용 비밀키·코드 파일은 학생 배포물에 포함하지 않는다.
- 이 잠금은 일반 화면·설정·직접 API 요청의 우회를 막는 범위다. 학생이 관리자 권한으로 코드/이미지 자체를 변조하거나 원본 중계 키로 외부 AI를 직접 호출하는 것까지 차단했다고 주장하지 않는다. 기존 중계의 계정 비용·호출 상한은 별도 확인 대상이며, 이전 승인 자료·캐시·비용 통제 요구를 완료로 축소하지 않는다.

## 2026-10-27 확정 — 허용된 수업 실행과 AI 비용 통제

이 절은 수업 범위·모델·캐시에 관한 이전의 자유 주제/임의 문서 허용 설명보다 우선한다. **요구사항 확정이며 구현 완료 선언이 아니다.**

- 마지막 적용 실습은 두 과정 모두 **교대 인수인계 한 시나리오**다. 개인 자유 주제가 아니다. 기존 설비·정비·ERP와 제조 스키마를 재사용한다. 제공할 설비 점검·이상 확인 보충 매뉴얼에서 제조 지식을 추가하고, 인계 업무 자체를 고장 유형으로 억지 변환하지 않는다.
- 강사가 제공·승인한 문서 내용·판본과 수업 행동만 서버에서 허용한다. 파일명 변경, 다른 문서 ID, 직접 API 호출, 동시 요청, 새 요청 ID로 우회할 수 없어야 한다. 임의 개인 대용량 문서는 AI 호출 전에 차단한다. 강사 측에서만 허용 범위를 바꾸며 학생의 UI/로컬 설정은 권한 근거가 아니다.
- 인제스션은 승인된 동일 문서와 추출 조건의 결과를 재사용한다. 권한 범위·내용 해시·스키마·추출 지시/설정 판본을 식별하고 진행 중 요청은 합친다. 실패·검증 전 결과를 성공 캐시로 취급하지 않는다. 사람의 검토·수정·적재는 생략하지 않고 재사용 여부를 표시한다. 재추출은 강사 허용과 예산 범위 안에서만 한다.
- AI 경로는 **문서 추출**과 **에이전트의 스킬·도구 사용/판단 실행**을 구분한다. 입력·출력량, 호출 수, 동시 실행, 시간, 재시도, 학생/수업별 누적 비용을 통제한다. 최신 설비·ERP 상태에 의존하는 판단에 오래된 결과 캐시를 무조건 적용하지 않는다.
- 중계 키가 학생에게 배포되는 구조에서 포털만 제한하면 우회 호출을 막지 못한다. 강사 관리 서버/중계의 허용 작업·예산 강제를 포함해 설계·검증한다. 비밀키는 실행 때만 읽고 출력·로그·커밋하지 않는다.
- 모델은 Luna를 기본으로 검증한다. 교정 기준과 처리 로직 결함을 모델 변경으로 덮지 않는다. 고성능 모델은 강사 측 최초 추출에 한정해 비교할 수 있지만 실제 개선·비용·접근 가능성을 확인한 뒤 선택한다. Astra 금지. Claude Code 실행 도구와 실제 호출 모델은 구별한다.
- ProcessGPT 실제 처리 원리를 우선 대조·적용한다. 함수명·한도 숫자의 동일성이 아니라 필요한 정보의 보존, 제한된 조회, 구조화 입출력, 충돌 없는 지시, 검증·교정·복구를 비교한다. 별도 방식은 환경·수업 계약 때문에 필요한 근거를 남긴다. 코드 그래프/RTK는 탐색·출력 절약 보조이며 필수 도입 과제가 아니다.

시스템을 고칠 때 지키는 것이다. 결정 111건 가운데 지금도 유효한 것만 모았다. 뒤집힌 것은 싣지 않았다.

## 1. 바탕

1. **실패와 미확인을 성공으로 꾸미지 않는다.** 도구가 실패하면 오류로 남기고 성공으로 제출하지 않는다. 조회 오류와 관측 없음은 0이나 빈 값으로 바꾸지 않고 「미확인」으로 둔다. 모든 후보가 맞지 않아도 첫 후보를 추천하지 않는다.
2. **근본을 고친다.** 땜질, 폴백, 잘되는 길만 확인하기를 하지 않는다. 실패는 드러나게 한다. 우회한 곳은 먼저 밝힌다.
3. **새 시험은 일부러 깨뜨려 잡히는지 확인한다.** 작업자의 보고에서 핵심 주장은 실물로 다시 확인한다.
4. **기능은 끝까지 돌려 확인한 것까지가 완료다.** 재생한 것, 가정한 것, 예측한 것을 실제로 잰 것처럼 쓰지 않는다.
5. **코드와 시드에 정답을 넣지 않는다.** 그래프와 데이터를 손으로 고쳐 증상을 지우지 않는다. 화면에서 가리는 것도 같다.
6. **시간 배율은 20이 기본이다**(`TIME_SCALE=20`). 가상 설비이므로 수업, 실습, 검사를 모두 20배속으로 한다. 1~2배속을 권하는 문구는 쓰지 않는다.
7. **ProcessGPT 참고는 서비스의 실제 처리 흐름을 대조하는 것이다.** 화면이 부르는 서비스와 그 하위 저장소·패키지·호출 관계를 최신 커밋으로 목록화하고, 우리 기능과 연결되는 경로를 깊게 확인한다. 15만 자 문제만 찾거나 기능 이름만 비교하지 않는다. 온톨로지와 문서 적재부터 판단·승인·실행·실패 복구까지 포함한다. 우선 목표는 문제로 인식조차 하지 못했던 숨은 구현 결함까지 찾아 고쳐, 학생에게 실제로 작동하는 교육용 ProcessGPT 라이트를 제공하는 것이다. 적합한 원본 구현은 직접 활용하거나 환경에 맞게 보완하되 제품 전체를 그대로 복제하지 않는다. 기존 수업 목표와 실제 업무 처리 기준은 유지한다.
8. **피지컬 AI 수업의 실제 동작이 먼저다.** 설비 관측 → 지식 기반 판단 → 사람 승인 → 조치 → 결과 재관측을 중심에 둔다. 후보 목록 밖의 문제도 재현·수정한다. 범용화·재사용·유지보수는 후순위이며, 이를 이유로 구현 결함 조사와 수업 동작 확인을 미루지 않는다(사용자 2026-10-26 재확인). 코드 활용·보완·유지는 실제 동작과 교육 목표를 기준으로 정하고, 추상화 자체를 목적으로 범위를 늘리지 않는다.

## 2. 시나리오와 흐름

- 시나리오는 셋이다: A 긴급 대응, B 정기 점검, C 재고 보충. 옛 이름(「정비 계획 · 펌프 효율 저하」, 「예비품 구매」)은 쓰지 않는다.
- 에이전트의 추천은 하나다. 지는 안은 실제 손익의 이유로 진다.
- 승인하지 않으면 그 단계에서 기다린다. 자동 취소와 자동 거절은 없고, 기한이 지나면 지연 알림만 나간다. 거절하면 처리 없이 반려로 닫힌다.
- 더하지 않는 것: 예약 대기, 시운전, 입고 대기, 미달, 납기 초과, 수업용 원인 입력. 가지는 하나로 간다.
- B와 C는 설비까지 가지 않는다. 정비 시스템과 ERP의 화면은 만들지 않고 업무 시스템 대역(`enterprise-sim`)을 쓴다.
- 결함 실험 버튼: [쿨러 열화 주입][쿨러 복구] | [정기 점검][초기화] | [재고 보충][초기화]. A의 열화 세기는 보통(`moderate`)이다. 세게 하면 보호 정지가 먼저 온다.
- 카드의 [초기화]는 자기 시나리오가 실제로 잡은 것만 되돌린다: B는 정기 정비 오더를 취소로 닫고 그 오더가 예약 · 출고한 수량을, C는 열린 구매 요청 · 발주를 취소로 닫고 그 수량을 되돌린다. 두 시나리오가 같이 쓰는 부품(씰 키트) 행을 통째로 시작값으로 덮지 않는다 — 덮으면 다른 시나리오의 진행 중 건이 깨진다. 모든 업무 값을 시작값으로 되돌리는 것은 업무 전체 초기화(`/api/reset`)뿐이다.
- 승인 전에 경보가 풀리면(예: 승인 전 [쿨러 복구]) 처리 건은 「조치 전 해소」로 닫힌다. 흐름에 그 끝 이벤트가 없어도 갇히지 않는다.
- 업무 감시(`BUSINESS_MONITOR`)는 기본으로 꺼 둔다. 켜면 버튼을 누르기 전에 처리 건이 열린다.

## 3. 승인과 실행

- 사람의 선택, 승인 당시의 기록, 할 일 제출, 응답 타이머 취소는 한 트랜잭션에 저장한다. 그 전에 바깥 업무를 바꾸지 않는다.
- **선택할 때 유효했다는 것이 나중의 실행 허가는 아니다.** 선택 접수, 승인 전달, 명령 발행 직전에 지금의 그래프와 원천을 다시 읽는다. 읽지 못했거나 오래된 값은 통과로 치지 않는다.
- 사람은 미리 저장된 검토본을 지정해 승인한다. 검토한 것과 다른 명령은 거부한다. 미리보기는 승인이 아니다.
- 승인 허용치를 느슨하게 하지 않는다.
- 설비 명령은 사건(Incident) 경로로만 나간다. 카드 선택은 역할을 검사한다.
- PLC의 응답을 받은 뒤 서버가 죽어도 명령을 다시 보내지 않는다.

## 4. 다시 하기와 되돌리기

- **설비에는 어떤 경우에도 자동으로 역명령을 보내지 않는다.**
- 업무 시스템이 정확한 역거래를 주는 네 가지(작업지시, 구매 요청, 오더 이관, 로트 격리)만 보상 요청으로 되돌린다. 나머지는 사람의 확인으로만 해결한다.
- 다시 하기는 모든 효과가 해결된 뒤에만 허용한다. 끝난 행은 그대로 두고 새 세대를 만든다. 이전 판단의 결과를 다시 쓰지 않는다.
- 영향 범위는 화면이 보낸 목록이 아니라 서버가 고정된 정의에서 계산한다.
- 통신 오류로 접수됐는지 모르면 입력을 잠그고 똑같은 요청으로 확인한다.

## 5. 정의와 판본

- ProcessGPT의 실제 데이터 모양(정의 JSON, 할 일 목록, 이벤트, 폴링 워커)을 따른다.
- 판본은 바꾸지 않는다. 고치려면 새 판본을 등록한다. 진행 중인 처리 건은 자기가 시작한 판본으로 간다.
- 같은 사건으로 두 번 시작하지 못하게 막는다. 일부러 다시 돌리려면 새 이벤트 ID를 쓴다.
- 기준 흐름(`anomaly_response`)은 고정이다. 학생의 흐름은 별도 판본이다.
- 흐름은 포털에서 그리지 않는다. bpmn.io에서 그려 내보낸 파일을 포털이 가져온다.
- 합류는 들어오는 길이 모두 끝나야 다음으로 간다. 포괄 게이트웨이는 등록을 거부한다. 서브프로세스와 다중 인스턴스는 범위 밖이다.

## 6. 워커와 MCP

- 판단 엔진(결정론)은 버리지 않고 MCP 도구로 연다.
- 워커는 하나만 돌린다. 실행마다 고유한 점유를 발급하고, 점유가 살아 있을 때만 결과를 저장한다. 취소를 성공이나 실패로 덮지 않는다.
- 에이전트의 결과가 계약에 맞지 않으면 무엇이 틀렸는지 알려 같은 세션에서 고치게 한다(최대 2회). 그래도 틀리면 실패로 남긴다. 계약을 느슨하게 하거나 워커가 결과를 대신 고치지 않는다.
- 에이전트가 사람에게 물으면 작업은 「질문 중」으로 남는다. 결과를 가짜로 채우지 않는다.
- 업무 DB를 읽는 MCP는 읽기 전용 계정만 받는다. 쓰기와 잠금을 거절한다.
- MCP의 비밀값은 `${SECRET:KEY}` 자리표시자로 둔다. 비밀값을 화면, 기록, 저장소에 내지 않는다.
- 포털에서 에이전트, 스킬, 역할, MCP를 만들고 고칠 수 있다. 기본 구성은 보호한다(복제해서 고친다). 「기준으로 되돌리기」가 있다.
- LLM은 LiteLLM 중계 하나다(OpenAI 호환, 모델 이름 `coding`). GPU 모델 서버는 쓰지 않는다(2026-10-19). 중계 **주소**는 비밀이 아니라 `.env.example`에 적는다(OpenAI 방식 `OPENAI_BASE_URL` = 끝이 `/v1`, Anthropic 방식 `LLM_RELAY_URL` = 끝의 `/v1` 없이 — 사용자 2026-10-25). **키**는 저장소 · 로그 · 증거 · 화면에 넣지 않는다. 학생이 채우는 것은 `.env`의 `LLM_API_KEY` 한 줄뿐이다.
- 포털의 AI 단계(A · B · C 「판단 · 제안」, 에이전트에게 질문, 매뉴얼 추출, 학생 에이전트)는 AI 워커가 한다: 워커(일거리 가져오기 · 돌려주기) → 실행기 Claude Code CLI(도구를 여러 번 쓰는 작업 루프) → 모델 호출은 전부 중계. 실행기는 저장소의 워커 이미지(`it/agent-worker/Dockerfile`) 컨테이너 `agent-worker`(프로필 `cliagents`, 강의 배포본 `COMPOSE_PROFILES`에 포함)이고 compose가 `LLM_API_KEY` · `LLM_RELAY_URL` · `LLM_MODEL`을 실행기의 `ANTHROPIC_*` 값으로 넣는다(Anthropic 계정 · 모델을 쓰지 않는다, 사용자 2026-10-25). 강의실 PC에는 더 깔 것이 없다.
- 강의 배포본은 `AGENT_BRIDGE=off`다(에이전트 단계는 워커가 한다). `legacy`(서버 안 결정론 에이전트가 기준 흐름 네 단계만 채움)는 core 회귀용이며 수업 흐름 A · B · C의 「판단 · 제안」은 채우지 못한다. 그 밖에 모델을 직접 부르는 것은 5회차 실습 2 폴더의 `llm_client.py`, legacy 경로의 요약문(`it/agent/agentsvc/llm.py`)이다.
- 개발용 호스트 워커(`scripts/run_worker_host.sh`, Claude Code 구독 로그인)와 Codex를 중계에 붙이는 갈래(`CODEX_MODEL_PROVIDER_BASE_URL`, 키는 `CODEX_MODEL_PROVIDER_API_KEY`)는 넣을 때만 켜진다.

## 7. 감지와 근거

- 임계값과 예측값은 온톨로지에 있는 그대로 쓴다.
- 감지 규칙의 설명문은 설명이고, 실행 조건은 따로 선언한다.
- 관측이 비었거나 품질이 나쁘면 진행 중인 유지 시간을 처음부터 다시 센다. 이미 난 경보는 유지한다.
- 근거의 태그와 구간은 지식에 선언한다. 질의문을 뜯어 추측하지 않는다.
- 센서와 PLC의 값만 신선도(최근 15초)를 본다. 업무 기록은 「바뀌었는가」로 본다.

## 8. 지식

- **온톨로지 스키마는 v2로 고정한다**(`it/neo4j/v2/schema.json`). 필요하면 있는 클래스 안에서 더하기만 한다. 코드가 쓰는 것과 스키마가 말하는 것이 다르면 안 된다.
- 학생의 지식은 이름 공간을 따로 둔다.
- 지식 그래프가 중심이고 RAG는 보조다.
- **지식을 적재하려면 검토 기록이 있어야 한다.** 기본은 사람 검토다. 원문은 판본, 쪽, 글자 위치, 정확한 문자열로 검증한다.
- 문서의 실행 절차는 판단이 후보로 낼 길이 있어야 한다: 그 문서의 조치 후보 규칙(`dt:action-candidates` SELECT), 또는 고장 조치(즉시 완화 · 근본 조치)가 자동 합류할 그 고장 유형의 후보 규칙. 예방 정비 · 구매 절차는 자동 합류하지 않으므로 문서가 후보 규칙을 진술해야 한다. 없으면 적재 전 검사가 알린다(`CANDIDATE_RULE_MISSING`).
- 추출 제안의 link에서 비운 칸(빈 글 · null · 키 없음)은 모두 값 없음이다.
- PDF에서 글자가 없는 쪽(그림 · 스캔 · 빈 쪽)은 그 쪽만 표시하고(`text_missing_pages` · 경고 · 쪽 검토 메모) 나머지 쪽으로 추출 · 적재한다. 그 쪽 내용은 적재되지 않으니 검토자가 원문 PDF로 확인한다. 모든 쪽에 글자가 없을 때만 `OCR_REQUIRED`(글자 인식한 PDF로 다시 올림)다.
- 문서를 개정해도 판단 이력은 지우지 않는다. 이력이 걸린 노드가 빠지게 되면 거절하고 무엇이 걸렸는지 알린다.
- 모르는 지식은 지어내지 않고 전문가가 정할 항목으로 남긴다.
- 선례는 미리 넣은 예시만 순위에 든다. 승인으로 쌓인 사례는 그래프에 남지만 순위에 들지 않는다(단발성 교육이라 쌓이지 않게 한 것이다).
- 계속 바뀌는 값은 그래프에 두지 않는다. 시각을 저장하고 남은 시간은 읽을 때 계산한다.

## 9. 원천과 투영

- 업무 DB의 고정된 정의와 기록이 원본이다. 그래프의 실행 기록은 다시 만들 수 있는 투영이다.
- 투영이 실패해도 실행 기록을 버리지 않는다. 가짜 노드를 만들지 않는다.
- 센서 저장소의 값과 플랫폼 지표를 섞지 않는다. 없는 지표를 만들지 않는다.

## 10. 화면

- 화면에 내부 id와 영문을 내지 않는다. 일반인의 말로 쓴다.
- 화면의 말: 처리 건, 사건, 정비 요청, 책임자 확인, 효과 확인, 조치 방법. 코드와 API의 이름은 그대로 둔다.
- 흐름 그림의 레인은 셋이다: 에이전트, 담당자, 시스템.
- 카드 하나에 행동 하나. 「학생이 10초 안에 할 일을 찾는가」로 본다.
- 참고 화면(process-gpt-vue3, Dify)을 따른다. 「비슷하게」로 끝내지 않고 참고 화면과 나란히 놓고 본다.
- A 화면은 고정본(`tests/fixtures/a_cards_before.json`)과 같아야 한다. 일부러 바꿀 때는 고정본을 근거와 함께 고친다.
- 포털에 로그인과 회원가입을 넣지 않는다.

## 11. 망과 저장소

- OT와 IT를 잇는 것은 완충 구역의 서비스뿐이다. 프로세스 엔진과 설비 시뮬레이터의 직접 연결은 시험용 망(`sim-net`)에만 둔다. `tests/test_compose_contract.py`가 지킨다.
- `.env`는 키의 이름만 본다. 값을 열거나 출력하지 않는다.
- 커밋은 경로를 지정한다(`git add .`와 `-A`를 쓰지 않는다).
- 공개 저장소다. 키, 사람 이름, 메일, 절대 경로, 내부 주소를 올리지 않는다. 강의 영상·음성은 main에 올리지 않고 `other-pc` 브랜치에만 둔다(문서/교재/2_기준.md 76번).

## 12. AI 응답 재생(API 키 없는 온라인 실습)

동작 · 저장 형식 · 대응표는 `참조/재생모드.md`, 경위는 `5_결정_기록.md` 1절 2026-10-22 행이다.

- 재생하는 것은 AI가 응답하는 단계뿐이다. 포털 · 가상 설비 · 처리 흐름 · 결과 검사 · 저장은 학생 PC에서 실제로 실행한다. 워커의 CLI 실행 자리(`exec_fn`) 하나만 바꾸고 나머지는 실제 실행과 같은 코드다.
- 키가 없으면 재생, 있으면 실제 AI다(`AI_MODE=auto`, 학생은 설정하지 않는다). 키에는 CLI 로그인도 포함한다. 키 · 로그인이 확인되지 않으면 재생이다.
- 규칙은 하나다: 같은 업무면 저장된 응답을 쓴다. 업무는 무엇에 대한 처리 건인가(경보 종류 = 처리 건 값 pattern, 문서 추출이면 문서 내용 해시 · 구간, 없으면 비움)와 업무 이름으로 가린다. 흐름 정의 id는 쓰지 않는다(학생이 그린 흐름은 id가 다르다). 입력 · 지시문이 달라도 쓴다. 업무 하나에 저장 파일 하나다.
- 저장된 응답에 든 처리 건 값(처리 건 · 작업 id, 사건 번호, process_scope)은 지금 처리 건의 값으로 바꿔 넣는다. 저장된 AI가 부른 쓰기 도구(서버가 읽기 전용으로 표시하지 않은 것 — 판단 등록)는 저장된 결과를 쓰지 않고 학생 PC의 서버를 다시 부른다. 처리 흐름이 믿는 id(판단 id)는 그 처리 건이 직접 만든 것만 쓴다.
- 저장분이 없는 업무는 지어내지 않고 그 단계를 실패시킨다. 저장된 응답이 결과 형식에 맞지 않으면 실제 실행과 같은 검사가 실패시킨다.
- 재생한 단계는 처리 과정에 「미리 저장한 응답, 새로 추론한 것이 아님」을 한 줄로 남긴다. 저장된 응답 사이에는 아무것도 끼워 넣지 않는다.
- 키는 워커 환경 변수에만 둔다. 코드 · 포털 화면 · 저장 파일 · 로그 · 배포 파일에 넣지 않는다. 저장 내용의 키 · 토큰 값은 가리고 저장한다. 설비 명령 권한은 AI 키와 상관없다.
