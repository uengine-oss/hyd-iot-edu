### B. 사용자가 이번 대화에서 바로잡은 것(규칙으로 지킨다)
1. **AI에게 큰 결과를 통째로 넘기지 않는다 — 상식이다.** 목록 · 상세를 나누고, 필요한 정보만 넘기고, 자를 때는 잘림 표시를 남긴다. 요약하면 정보가 깎인다(열화). ProcessGPT가 이를 어떻게 처리하는지 보고 정한다.
2. **같은 흐름을 이미 처리하는 ProcessGPT를 실제 처리 로직 그대로 참고한다.** process-gpt-vue3가 쓰는 모든 서브레포, ontology-studio 등 관련 레포 전부를 **최신 커밋 기준으로** 본다. 안 쓰이는 기능을 대조하는 것이 아니다. 우리와 같은 흐름(작업 가져오기 → 에이전트 실행 → 도구 결과 → 사람 승인 → 실행, 문서 → 지식)에서 그들이 어떻게 처리했는지 보고 우리 문제를 고친다. 2026-10-08 대조는 기능 대조뿐이라 이런 문제를 못 잡았다.
3. **사용자가 다 찾아볼 수 없다.** 이런 기본적인 문제는 작업자가 먼저 찾아 고친다. 「대체로 정상」으로 넘기지 않는다. AI 답이 정답인지(근거를 제대로 써서 맞는 답을 내는지)를 본다.
4. **설명은 쉬운 말로 한다.** 작업자만 아는 표현은 쓰지 않는다. 예: 「카드 평가가 15만 자」가 아니라 「AI 판단 도구가 결과를 15만 자 통째로 AI에게 돌려줌」.
5. **첫 AI 요청이 느린 것은 원래 그렇다.** 결함으로 보지 않는다.
6. **질문을 받으면 도구를 실행하기 전에 답부터 한다.**
7. **실라버스는 함부로 고치지 않는다.** 세부 내용만 바뀌는 수준이면 그대로 두고, 차질이 생기면 문서에 기록한다(`문서/교재/5_결정_기록.md` 4회차 인제스천 결정).
8. **효율 · 속도 · 정확 · 비용을 모두 챙긴다.** 건너뛰거나 스크립트로 때우지 않고 체계적으로 한다.
9. **일 단위로 커밋 · push한다.**
10. **Node.js 보안 릴리스(2026-10-21)를 반영한다.** 수정판은 22.23.4 · 24.22.1 · 26.12.1이다(Brotli 원격 코드 실행 CVE-2026-111497 등 10건). 같은 계열 안에서 올리는 것이라 영향은 작다고 판단했다.

### 0. 목표(사용자 원문 요지)
1. 강의실에서 **`git pull` → `.env`에 `LLM_API_KEY` 한 줄 → 시작.bat → 점검.bat** 이면 수업 준비가 끝나게 한다. `.env.example`은 키 말고 다 채운다. 빈 포트 자동 배정(`scripts/prepare_ports.py`)은 유지.
2. **포털 실습**(아래 3절, 실라버스 기준 13개)이 학생이 하는 그대로 잘 도는지, 결함 · 오류 · 품질 문제가 없는지 확인하고 고친다. 랩(VS Code 안에서 끝나는 실습) · Notion · arrows.app · ProcessGPT 시연은 범위 밖.
3. main에 push.

### 1. 확정된 결정
- 작업 브랜치는 **main**. `replay-mode`(키 없는 온라인 학생용 AI 응답 재생)는 **필요 — 유지**, main을 병합해 따라간다. main에 재생 코드를 넣지 않는다.
- 강의실 학생 PC는 이미 clone · 설치가 끝났다. VS Code의 Copilot · Codex 확장은 **바이브 코딩 랩용**이며 이 시스템과 무관하다. 학생에게 주는 것은 **LiteLLM(강의 중계) 키 하나**다.
- 포털의 AI 단계(A · B · C 「판단 · 제안」, 에이전트에게 질문, 매뉴얼 추출, 학생 에이전트)는 **AI 워커**가 처리한다: 워커(일거리 가져오기 · 돌려주기) → 실행기 CLI(도구를 여러 번 쓰는 작업 루프) → **모델 호출은 전부 LiteLLM**. 실행기는 **유지보수 우선으로 저장소의 Docker 워커 이미지(`it/agent-worker/Dockerfile`, Claude Code CLI)** 를 그대로 쓰고 compose 설정으로 LiteLLM에 붙인다(Anthropic 계정 · 모델을 쓰지 않음). 강의실 PC에는 아무것도 더 깔지 않는다.
- 모델: LiteLLM 모델 이름 `coding`(사용자: 강의실은 gpt-6-luna 계열). 구조(결정론 판단 엔진 + 서버 검사 + 정해진 출력 형식)가 잘 짜여 있으면 결과가 잘 나온다는 전제로, 막히면 **프롬프트 · 스킬 · 지시문을 튜닝**한다.

### 2. 사실(2026-10-25 이 세션에서 확인)

### 6. 작업 규칙(사용자 지시 — 반드시)
- **해피패스 금지**: 실습마다 3절의 예외 · 실패 경로를 실제로 돌린다. 정상 한 번 통과로 끝내지 않는다. 시험 데이터를 정답에 맞추거나(구세주 데이터) 정답을 하드코딩하지 않는다.
- **누구는 되고 누구는 안 되면 안 된다**(사용자 2026-10-25: 학생들은 강사를 따라 같은 순서로 같은 것을 한다 — 각자 다른 행동을 하지 않는다). 판정은 「같은 단계를 한 학생 모두가 같은 결과를 받아 다음 단계로 가는가」.
  - **AI 결과의 흔들림**: AI 단계마다 같은 입력으로 **3번** 돌려 추천 카드 · 승인 역할 · 근거 · 추출 결과 · 소요 시간이 갈리는지 본다(2026-10-25 A 추천이 생산관리자 승인 카드로 나와 운전원 안내와 어긋난 사례). 갈리면 프롬프트 · 스킬 · 순위 입력을 안정되게 고치고, 그래도 갈리면 보고한다(가이드에 「카드의 승인 역할을 보고 「나」를 고른다」 같은 공통 안내가 필요한지 포함).
  - **속도 차이**: 20배속 시간 창(승인 요청 30초 · 예측 유효시간 · 승인 지연 알림)이 AI 응답이 느린 PC에서도 같은 결과인가 — 3번 중 가장 느린 소요 시간 기준으로 본다.
  - **PC 상태 차이**: 수업 시작 상태 그대로(구조판, 문서 적재 전, 처리 건 0)에서 실라버스 순서대로 누적해 간다. 포트가 옮겨진 PC, 시작 스크립트를 두 번 돌린 PC, 앞 회차 처리 건이 남은 PC에서도 같은 결과인가.
  - **뒤처진 학생이 따라붙는 길**: 멈춘 상태마다 화면에서 되돌릴 방법([초기화] · [닫기] · [다시 평가] · 되돌리기)이 있고 실제로 되는가. 오류 · 거절은 한국어 사람 글로 무엇을 하라는지 말한다(영문 예외 · 500 · 빈 화면 · 무한 대기 금지).
- **잘게 나누지 않는다**: 3절 전체를 실라버스 순서의 「수업 한 바퀴」 스크립트 하나로 묶어(학생 한 명처럼, 포털 화면 조작) 한 번에 돌리고, 결함을 모아 영역별로 한꺼번에 고친 뒤 한 번 다시 돌린다. 결함 하나마다 재빌드 · 회귀 · 커밋 · 보고하지 않는다. 독립 영역(예: 포털 화면 순회 · 문서 적재 품질 · 흐름 BPMN)은 서브에이전트(opus)로 동시에 — 라이브 스택을 쓰는 실행은 한 번에 하나.
