# 실제 공개 스트림의 증거 경계

현재 제품의 공개 설명→도구 요청/응답→실행 종료 구독 배선은 존재한다. 기존 실제 B/C 감시는 완료 전에 한국어 공개 설명이 화면에 표시됨을 증명한다. 다만 승인부터 업무 종료까지 모든 구간을 실시간으로 관찰했다고 주장할 증거는 없다. 이 감사는 기존 원본과 현재 소스를 읽었으며 HTTP·시험·캡처·LLM·업무 실행을 추가하지 않았다. 사용자 최종 이미지 승인도 대신하지 않는다.

현재 소스 연결은 `runner.py:289–368`의 공개 누적 문장과 도구 이벤트 저장, `events.py:25,77`의 저장 가능한 이벤트 매핑, `instance_mode.py:103–151,921`의 0.5초 이벤트 조회 SSE, `liveStream.js:88–93,177–185`의 history/fresh 구분 및 버스, `trace.js:157,397–402,478`의 메시지별 최신 공개 문장·인스턴스/작업 필터, `caseRecord.js:880–887,973–974`의 동일 사건 구독, `taskDetail.js:710–717`의 열린 작업 구독으로 이어진다. 계획 업데이트/사적 THINKING은 행 타입이 없어 공개 저장 이벤트가 되지 않는다. 이는 해당 종류가 MCP 결과나 사업 추천 카드라는 뜻도 아니다. 실제 공개 프레임에 private 이벤트가 들어오지 않았다는 감시 결과를 보존한다.

최초 B 감시의 23개는 모두 fresh이고 보류까지 성공했다. C 파일은 52행 중 history26/fresh26이다. 교육 보완 B는 history23/fresh8이며 공개 PNG1 뒤 도구행 스크롤 중 DOM이 교체돼 수집기가 중단됐다. history를 신규 실행 수로 세거나, 수집기 실패를 제품 구독 누락이라고 분류하지 않는다. 이후 저장 완료 PNG를 라이브 종료 직전 PNG라고 부르지 않는다. 현재 구독의 실제 누락으로 확정할 근거는 발견하지 못했다.

다음 검증이 필요하다면 새 LLM/업무 재완주 없이 이미 생긴 프레임·식별자를 기준으로 해당 구간의 저장 화면을 설명할 수 있다. 전체 실시간 승인/거절/시스템 완료의 증명 공백을 닫으려면 앞으로 정당하게 발생하는 사용자 업무 때 사건·작업·실행·도구 호출 키를 고정해 관찰해야 한다. 이번 감사가 이를 이유로 실행을 다시 요청하거나 시작하지 않는다. 특히 도구행은 tool_use_id만으로 고르면 이전 실행과 충돌할 수 있으므로 case+todo+job+tool_use_id와 실제 표시 시각을 함께 확인해야 한다.

참고는 ProcessGPT 모노레포 보존 architecture.md의 엔진/에이전트/MCP 분리, 최신 보존 Vue PgToolStep.vue의 도구 이름·진행 spinner, Dify 보존 공식 실행 기록 이미지의 요약/상세 구분, ontology-studio FilePanel.vue의 원본 이름·파일별 접기다. 모두 실제 경로·SHA를 JSON에 기록했다. 다른 제품의 참조를 현재 HYD의 실시간 동작·픽셀 동등성·외부 인증 증거로 사용하지 않는다.

현재 `ui.js:5–6`의 도구 키는 이미 case+todo+job+tool_use_id 조합이고 Trace/Record가 이 함수를 사용한다. 따라서 과거 watcher의 단순 행 선택 문제를 현재 제품의 도구 짝짓기 결함으로 옮기지 않는다. 기존 공개 스트림 집중 시험 원문은 87 PASS이며 이것은 저장된 시험 결과다. 이번 감사에서 다시 실행하지 않았고 실제 승인/거절 라이브 증거를 대신하지 않는다. C의 과거 purchase-part 렌더 오류 역시 이후 F27에서 해결된 과거 상태이며 현재 누락 목록에 올리지 않는다.
