## SLIDE 09 — 클래스와 인스턴스를 가르는 기준

- 문장: 「A는 B의 하나이다」가 성립하면 A는 인스턴스이고 B는 클래스이다
- 요소:

  3. 유온은 상태 변수의 하나이다 | 유온 = 인스턴스 / 상태 변수 = 클래스
- 노트: 헷갈릴 때는 문장에 넣어 봅니다. 오일 쿨러는 구성 요소의 하나이다는 말이 됩니다. 구성 요소는 오일 쿨러의 하나이다는 말이 되지 않습니다.

  2. **필수 속성이 빠진 센서** | id: sen:ts1 / name: 유온 센서 / tag: (없음) / 어느 값이 이 센서의 값인지 알 수 없다 | 스키마에 어긋난다

## SLIDE 43 — MATCH와 RETURN: 찾을 모양과 돌려받을 것
### 화면 내용
- 유형: 코드
- 메시지: MATCH에는 찾을 모양을, RETURN에는 돌려받을 것을 적으며, 모양에 맞는 것마다 한 행이 나온다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / "오일 쿨러"   "TS1" / "오일 쿨러"   "CE"
- 요소:
  1. **MATCH** | 찾을 모양을 적는 자리이다. 이름이 오일 쿨러인 구성 요소에서 MONITORED_BY로 이어진 센서를 찾는다.
  2. {name: '오일 쿨러'} | 중괄호는 속성 조건이다. Component 가운데 name 속성이 오일 쿨러인 노드만 가리킨다.
  3. **RETURN** | 돌려받을 것을 적는 자리이다. c.name, s.tag는 찾은 구성 요소의 이름과 센서의 태그이다.
  4. 결과 | 모양에 맞는 것이 둘이므로 두 행이 나온다.
- 노트: 조회의 첫 낱말은 MATCH입니다. 괄호 안의 중괄호는 속성 조건이며 글자 값은 작은따옴표로 감쌉니다. 이 질의는 오일 쿨러를 재는 센서는 무엇인가라는 질문이고, 센서가 몇 개인지는 적지 않았습니다. 모양에 맞는 것을 모두 찾는 것이 MATCH의 동작입니다. MATCH만으로는 아무것도 보이지 않으므로 RETURN에 구성 요소의 이름과 센서의 태그를 달라고 적었습니다. 오일 쿨러는 TS1과 CE 두 채널로 계측되므로 두 행이 나옵니다.
### 제작 기준
확정 실라버스의 「MATCH · WHERE · RETURN을 통한 조회」. 질의는 사실표 2.3의 [실측] 질의에서 구성 요소 → 센서 구간만 남기고 출발점을 오일 쿨러로 바꾼 **줄인 것**이다. [실측] 2026-10-11 읽기 전용(`cypher-shell --access-mode read`)으로 `MATCH (c:Component {name:'오일 쿨러'})-[:MONITORED_BY]->(s:Sensor) RETURN c.name, s.tag`를 실행한 결과 두 행.

## SLIDE 48 — CREATE와 MERGE: 새로 만들기와 찾아서 만들기
### 화면 내용
- 유형: 코드
- 메시지: MERGE는 식별자로 먼저 찾아 없을 때만 만들므로 CREATE와 달리 같은 노드를 중복해 만들지 않는다.
- 코드: CREATE (s:Sensor {id: 'sen:ts1', /                   name: '유온 센서', /                   tag: 'TS1'}) /  / MERGE (s:Sensor {id: 'sen:ts1'}) / SET s.name = '유온 센서', /     s.tag  = 'TS1'
- 요소:
  1. **CREATE** | 적은 대로 새로 만든다. 이미 있는지는 보지 않는다. Sensor 레이블이 붙고 속성 셋을 가진 노드 하나가 만들어진다.
  2. **MERGE** | id가 sen:ts1인 센서가 있으면 그 노드를 쓰고, 없으면 만든다.
  3. SET | 찾았거나 만든 노드의 속성에 값을 넣는다.
  4. 식별자로 찾는다 | MERGE의 괄호 안에는 식별자만 적고 나머지 속성은 SET에 적는다.
- 노트: 조회 다음은 만들기이고 표기는 조회와 같습니다. 먼저 위의 CREATE는 괄호 안에 적은 레이블과 속성대로 노드를 만듭니다. 다음으로 아래의 MERGE는 먼저 찾아봅니다. 무엇을 같다고 볼지는 괄호 안에 적은 것으로 정해지므로 그 자리에는 식별자를 적습니다. 이름까지 넣으면 이름을 고쳐 다시 실행했을 때 같은 노드를 찾지 못합니다.
### 제작 기준
확정 실라버스의 「CREATE를 통한 생성」. [일반] CREATE의 동작. [저장소] 속성값은 `sen:ts1`의 실제 값. 저장소에서 CREATE를 쓰는 곳(`manual_graph.py:346`, `skill_graph.py:101`)의 꼴에 실제 값을 넣은 **줄인 것**이며 이 문장은 실행하지 않았다. 확정 실라버스의 「MERGE를 통한 기존 대상 조회 또는 생성」. [저장소] `MERGE (n:Sensor {id: r[0]}) SET n.name = r[1], n.tag = r[2], …`(`instances.cypher:135`)에 실제 값을 넣고 unit · virtual을 뺀 **줄인 것**(「℃」를 코드 칸에 쓸 수 없다). 새 용어: SET.


## SLIDE 49 — MERGE로 관계를 만든다
### 화면 내용
- 유형: 코드
- 메시지: 관계는 양 끝의 노드를 MATCH로 먼저 찾은 다음 그 사이에 MERGE로 만든다.
- 코드: MATCH (c:Component {id: 'comp:cooler'}), /       (s:Sensor {id: 'sen:ts1'}), /       (v:StateVariable {id: 'sv:ts1'}) / MERGE (c)-[:MONITORED_BY]->(s) / MERGE (s)-[:OBSERVES]->(v)
- 요소:
  1. MATCH | 이을 노드 셋을 식별자로 찾아 c, s, v라는 변수를 붙인다.
  2. **MERGE** | 변수로 부른 노드 사이에 관계를 만든다. 이미 있으면 다시 만들지 않는다.
  3. 방향 | 화살표는 스키마가 정한 시작 클래스에서 끝 클래스로 향하게 적는다.
- 노트: 관계는 양 끝의 노드가 있어야 이을 수 있으므로 먼저 찾습니다. 오일 쿨러에서 유온 센서로, 유온 센서에서 유온으로 관계를 만듭니다. 스키마로 정의하고, 인스턴스를 정하고, 이런 질의로 넣는 것이 지식 그래프를 만드는 과정입니다.
### 제작 기준
[저장소] `… MATCH (c:Component {id: r[5]}), (v:StateVariable {id: r[6]}) MERGE (c)-[:MONITORED_BY]->(n) MERGE (n)-[:OBSERVES]->(v)`(`instances.cypher:136`)에 실제 값을 넣어 따로 떼어 낸 **줄인 것**. 이 문장은 실행하지 않았다(읽기 전용 조사).
