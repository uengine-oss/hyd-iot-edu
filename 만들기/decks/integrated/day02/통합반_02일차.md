- 메시지: 속성(Property)은 값을 담는 항목이고, 그 항목에 채운 내용은 속성값(Property Value)이다.
- 머리: 속성 | 유온 센서 | 냉각 효율 채널
- 요소:

## SLIDE 34 — 설비 모델의 속성과 관계 정의
### 화면 내용
- 유형: 코드
- 메시지: 질문에 쓰이는 값은 속성으로, 질문이 건너가는 길은 관계로 적은 것이 설비 모델의 핵심 정의이다.
- 코드: Asset         { id!  name!  code! } / Component     { id!  name!  aliases } / Sensor        { id!  name!  tag!  unit } / StateVariable { id!  name!  unit!  kind!  limit } / Part          { id!  name!  partNo } /  / HAS_COMPONENT   Asset     -> Component      1:N / MONITORED_BY    Component -> Sensor         N:M / OBSERVES        Sensor    -> StateVariable  N:1 / USES_PART       Component -> Part           N:M
- 요소:
  1. 느낌표 | 필수 속성이다. 이 다섯 클래스에서 id와 name은 필수이다.
  2. 필수로 둔 값 | 설비의 code, 센서의 tag, 상태 변수의 unit · kind는 없으면 쓸 수 없다.
  3. **핵심 정의 발췌** | 질문에 쓰이는 속성만 골랐다. 전체 정의에는 normal · virtual 등이 더 있다.
  4. HAS_COMPONENT | 1:N으로 선언되어 있지만 구성 요소 노드는 세 설비가 함께 가리킨다.
- 노트: 다섯 클래스의 속성을 중괄호 안에 나열했고, 느낌표가 붙은 것이 필수 속성입니다. 모든 클래스에 식별자와 이름을 두고, 설비에는 설비 코드, 센서에는 태그와 단위, 상태 변수에는 단위와 종류와 한계, 부품에는 부품 번호를 더했습니다. 아래 네 줄은 질문이 건너가는 길이며, 첫 질문은 HAS_COMPONENT와 MONITORED_BY를, 둘째 질문은 OBSERVES를, 셋째 질문은 USES_PART를 지납니다. 오일 쿨러는 유온 센서와 냉각 효율로 계측되고 한 센서가 여러 구성 요소를 잴 수도 있으므로 MONITORED_BY는 다대다입니다.

## SLIDE 41 — 온톨로지 스키마와 DB 제약
### 화면 내용
- 유형: 비교
- 아이콘: schema, lock
- 메시지: 스키마는 옳은 데이터의 조건을 정하고, **DB 제약**은 그중 저장할 때 데이터베이스가 직접 막는 조건이다.
- 요소:
  1. 온톨로지 스키마 | 클래스 → 레이블, 관계 유형 → 관계 유형, 속성 → 속성으로 옮겨진다 / 필수 속성 · 자료형 · 허용값 · 끝 클래스 · 카디널리티를 정한다 / 별도 검사기가 필수값 · 허용값 · 끝 클래스를 확인한다 / 자료형 전체와 카디널리티는 자동 검사되지 않는다 | 의미 모델의 정의
  2. **DB 제약(DB Constraint)** | 데이터베이스에 걸어 두어 저장하는 순간 검사하는 조건이다 / 유일 제약(Unique Constraint): 같은 레이블의 노드끼리 id가 겹치지 않는다 / 예: id가 sen:ts1인 Sensor 노드를 또 만들면 저장을 거절한다 | 저장할 때 강제

## SLIDE 42 — Cypher 쿼리와 실행 화면의 역할
### 화면 내용
- 유형: 풀이
- 메시지: 저장된 그래프는 **Cypher 쿼리**로 꺼내고 만들며, 쿼리는 찾을 노드와 관계의 모양을 글자로 적는다.
- 요소:
  1. 질의(Query) | 데이터베이스에 보내는 요청 한 건이다. 무엇을 찾거나 만들지를 적는다. / 쿨러 사건에서 경보로부터 원인 후보를 찾은 것도 그래프에 보낸 질의였다. |
  2. **Cypher 쿼리(Cypher Query)** | Cypher로 적은 질의이다. Cypher는 요청을 노드와 관계의 패턴(Pattern)으로 적는 그래프 DB 질의 언어이다. / 예: (c:Component)-[:MONITORED_BY]->(s:Sensor) |

- 노트: 그래프 DB에 들어 있는 것을 꺼내 보려면 질의를 보냅니다. 이 과정은 그래프 DB 전용 질의 언어인 Cypher로 쿼리를 적으며, Cypher 쿼리는 찾고 싶은 노드와 관계의 모양을 그림 그리듯 글자로 적습니다. 쿨러 사건에서 에이전트가 관계를 따라 원인 후보를 찾은 것도 이런 질의였고, 사람이 실행 화면에 적는 질의와 같은 언어입니다. 실행 화면은 데이터베이스에 딸린 창구이고, 포털의 지식 지도는 기준 지식의 속성과 연결을 살피는 화면입니다.

풀이 셋(질의 → Cypher 쿼리(강조) → 실행 화면). Cypher는 이 단원이 가르치는 질의 언어이므로 제목 · 메시지에 이름을 쓴다(기준 16번 단서).

## SLIDE 44 — MATCH · RETURN: 패턴과 결과의 행
### 화면 내용
- 유형: 코드
- 메시지: MATCH는 패턴에 맞는 연결을 찾고, RETURN은 그 결과에서 돌려받을 항목을 정한다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / c.name         s.tag / "오일 쿨러"    "TS1" / "오일 쿨러"    "CE"
- 요소:
  1. MATCH | 이름이 오일 쿨러인 구성 요소에서 계측 관계로 이어진 센서를 찾는다.
  2. RETURN | 구성 요소 이름과 센서 태그를 결과의 두 열로 받는다.
  3. **행의 수** | 쿨러 하나에 계측 채널 둘이 연결되어 결과는 두 행이다.
  4. 행과 노드 | 두 행의 오일 쿨러는 같은 노드이다. 이름의 반복이 노드의 중복을 뜻하지 않는다.
- 노트: 쿨러 하나를 찾았는데 결과가 왜 두 행인지 살펴봅니다. 쿨러에서 유온 센서로 가는 연결과 냉각 효율 채널로 가는 연결이 각각 패턴에 맞습니다. MATCH가 두 연결을 찾고 RETURN이 각 연결에서 필요한 값 두 개를 꺼내므로 두 열 두 행이 나옵니다. 이름이 반복되는 것은 같은 쿨러가 서로 다른 연결에 참여하기 때문입니다.
### 화면 구성

## SLIDE 46 — DISTINCT: 반환한 값의 중복 제거
### 화면 내용
- 유형: 표
- 메시지: DISTINCT는 반환하는 값의 조합이 같은 행을 하나로 남기며, 저장된 노드를 지우지 않는다.
- 머리: 같은 MATCH의 반환 절 | 결과 | 남는 행
- 요소:
  1. RETURN c.name | 오일 쿨러 / 오일 쿨러 | 2행
  2. **RETURN DISTINCT c.name** | 오일 쿨러 | 1행
  3. RETURN DISTINCT c.name, s.tag | 오일 쿨러 · CE / 오일 쿨러 · TS1 | 2행

- 노트: 같은 쿨러 이름이 두 행에 나옵니다. 쿨러의 이름 목록만 필요하면 DISTINCT로 하나를 남깁니다. 센서 태그도 함께 받으면 두 행의 태그가 다르므로 둘 다 남아요. DISTINCT는 반환하는 전체 열의 조합을 비교하며 이름이 같다는 이유로 노드를 합치거나 지우지 않습니다. 같은 이름의 다른 노드까지 구별하려면 노드나 고유 식별자를 기준으로 삼습니다.

표: 같은 MATCH에서 반환 절만 바꾼 세 줄과 결과 · 남는 행, 마지막 줄은 DISTINCT의 뜻. 둘째 줄(RETURN DISTINCT c.name)을 강조한다.

## SLIDE 49 — WHERE: 조건과 값의 존재 여부
### 화면 내용

  1. WHERE | MATCH가 찾은 행 가운데 조건에 맞는 행만 남기는 조건 절이다.

## SLIDE 50 — AND · OR: 조건을 괄호로 묶기
### 화면 내용
- 유형: 코드
- 메시지: 쿨러 또는 팬이라는 선택을 먼저 묶어야 두 장치 모두에 한계 값 조건을 적용한다.
- 코드: MATCH (c:Component)-[:MONITORED_BY]->(s:Sensor) /       -[:OBSERVES]->(v:StateVariable) / WHERE (c.name = '오일 쿨러' OR c.name = '쿨러 팬') /       AND v.limit IS NOT NULL / RETURN s.tag, v.name / ORDER BY s.tag / ── 결과 ── / TS1  유온 / VS1  팬 진동 / ── 괄호를 빼면 ── / CE   냉각 효율 / TS1  유온 / VS1  팬 진동
- 요소:
  1. OR: 어느 하나 | 오일 쿨러이거나 쿨러 팬인 구성 요소를 고른다.
  2. AND: 모두 | 고른 장치의 채널 중 한계가 있는 물리량만 남긴다.
  3. **괄호: 조건의 묶음** | 괄호가 없으면 AND가 OR보다 먼저 묶인다. 쿨러 쪽은 한계 값 조건을 거치지 않는다.
- 노트: 찾을 것은 쿨러 또는 팬의 채널 중 한계가 있는 물리량입니다. OR로 장치를 고르는 두 조건을 괄호에 묶고 그 묶음 전체에 AND로 한계 존재 조건을 붙입니다. 괄호를 빼면 쿨러이거나, 팬이면서 한계가 있는 것으로 뜻이 달라집니다. 따라서 한계가 없는 냉각 효율도 통과합니다. 문법 오류가 없어도 질문과 다른 조건일 수 있음을 두 결과로 확인합니다.

## SLIDE 51 — 구성 요소별 집계와 ORDER BY 정렬
### 화면 내용
- 유형: 코드
- 메시지: 구성 요소를 구별해 채널 수를 집계하면 원래의 다섯 행을 장치별 세 행으로 비교할 수 있다.
- 코드: MATCH (a:Asset {code: 'HYD-01'}) /       -[:HAS_COMPONENT]->(c:Component) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.id AS componentId, c.name AS component, /        count(DISTINCT s) AS channels / ORDER BY channels DESC, componentId /  / ── 결과(componentId 열은 생략) ── / component      channels / 오일 쿨러      2 / 주 펌프 (A)    2 / 쿨러 팬        1
- 요소:
  1. **묶는 기준** | 집계하지 않은 c.id와 c.name의 조합별로 센서를 센다. 같은 이름의 다른 장치도 id로 구별한다.

## SLIDE 54 — CREATE · MERGE · SET의 역할
### 화면 내용
- 유형: 코드
- 메시지: 다시 실행해도 같은 대상이 하나로 남게 하려면, 바뀌지 않는 식별자로 찾고 없을 때만 만든다.
- 코드: CREATE (s:Sensor {id: 'sen:ts1', /                   name: '유온 센서', /                   tag: 'TS1'}) /  / MERGE (s:Sensor {id: 'sen:ts1'}) / SET s.name = '유온 센서', /     s.tag  = 'TS1', /     s.unit = '℃' /  / ── sen:ts1이 이미 있을 때 CREATE의 결과 ── / Node already exists with label `Sensor` /   and property `id` = 'sen:ts1'
- 요소:
  1. **CREATE** | 적은 대로 새 노드를 만든다. 이미 있는지는 보지 않는다. sen:ts1이 이미 있으면 유일 제약에 걸려 거절된다.
  2. **MERGE** | 패턴에 맞는 노드를 찾고 없으면 만든다. 이 예는 id 유일 제약 아래 같은 id로 반복 실행한다.
  3. SET | 찾았거나 만든 노드의 속성에 값을 넣는다.
  4. 식별자로 찾는다 | 같은 id를 조건으로 기존 센서를 찾는다. 이름과 태그 같은 값은 SET으로 넣는다.
- 노트: 조회 다음은 만들기이며 표기는 조회와 같습니다. 위의 CREATE는 이미 있는지 보지 않고 새로 만들므로, 같은 id가 이미 있으면 유일 제약 때문에 저장이 거절됩니다. 아래의 MERGE는 괄호 안의 패턴으로 먼저 찾고 없을 때만 만들므로, 설비나 센서처럼 한 번만 있어야 하는 지식을 넣다가 멈추어 처음부터 다시 실행해도 중복이 생기지 않습니다. 무엇을 같다고 볼지는 괄호 안에 적은 것으로 정해지므로, 바뀔 수 있는 이름은 SET으로 넣고 괄호에는 식별자만 적습니다. CREATE는 문서를 적재할 때마다 기록이 한 건씩 새로 생겨야 하는 곳처럼 실행마다 새 대상이 필요한 데이터에 씁니다.
### 화면 구성
위 CREATE, 아래 MERGE와 SET. 오른쪽 짚을 점 넷.
### 제작 기준

## SLIDE 56 — 기존 노드를 찾아 관계 생성
### 화면 내용

  3. 방향 | 화살표는 스키마의 시작 클래스에서 끝 클래스로 향하게 적는다.
