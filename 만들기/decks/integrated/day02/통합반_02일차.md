  2. 필수로 둔 것 | 설비의 code, 센서의 tag, 상태 변수의 unit은 없으면 쓸 수 없는 값이다.

- 노트: 클래스 이름 옆 중괄호 안에 속성을 나열했습니다. 모든 클래스에 식별자 id와 이름 name을 두고, 질문에 필요한 값을 더합니다. 설비에는 설비 코드, 센서에는 태그와 단위, 상태 변수에는 단위와 한계, 부품에는 부품 번호입니다. 느낌표가 붙은 것이 필수 속성입니다. 한계는 잰 값과 비교해야 하므로 수로 정하고, 한계가 없는 상태 변수도 있으므로 필수로 두지는 않습니다.
### 제작 기준
[저장소] 다섯 클래스의 속성: `schema.json`(Asset id · name · code, Component id · name · aliases, Sensor id · name · tag · unit · virtual, StateVariable id · name · aliases · unit · kind · normal · limit, Part id · name · partNo). 칸에 맞춰 질문에 쓰이는 속성만 골라 적은 **줄인 것**이다. [저장소] `클래스 {속성! …}` 표기(`!`가 필수): 스키마 설명문의 표기(사실표 2.4). 필수 여부와 자료형: `schema.json`. 질문에 쓰이는 속성만 남긴 **줄인 것**이다.

## SLIDE 60 — 단계 4: 관계의 이름과 방향, 양 끝 클래스, 카디널리티
### 화면 내용
- 유형: 코드
- 메시지: 관계 넷은 질문 셋이 건너가는 길을 따라 놓였고, 이 네 줄이 연결의 유효성을 가리는 기준이다.
- 코드: HAS_COMPONENT   Asset     -> Component      1:N / MONITORED_BY    Component -> Sensor         N:M / OBSERVES        Sensor    -> StateVariable  N:1 / USES_PART       Component -> Part           N:M
- 요소:
  1. 질문의 길 | 첫 질문은 설비에서 구성 요소를 거쳐 센서로, 둘째는 센서에서 상태 변수로, 셋째는 구성 요소에서 부품으로 건너간다.
  2. 양 끝 | 화살표 왼쪽이 시작 클래스이고 오른쪽이 끝 클래스이다.
  3. **카디널리티** | 구성 요소 하나를 여러 센서가 재고, 센서 하나가 여러 구성 요소를 잴 수 있으므로 MONITORED_BY는 다대다이다.
- 노트: 질문 셋이 건너가는 길을 따라 관계를 놓았습니다. 첫 질문은 설비에서 구성 요소를 거쳐 센서로 가므로 HAS_COMPONENT와 MONITORED_BY를, 둘째 질문을 위해 OBSERVES를, 셋째 질문을 위해 USES_PART를 놓습니다. 오일 쿨러는 유온 센서와 냉각 효율 두 채널로 계측되므로 구성 요소 쪽에서 보아 센서가 여럿입니다. 이 네 줄이 앞에서 본 유효한 연결의 기준이 됩니다.
### 제작 기준
[저장소] 네 관계의 이름과 방향: `schema.json`(HAS_COMPONENT Asset → Component, MONITORED_BY Component → Sensor, OBSERVES Sensor → StateVariable, USES_PART Component → Part). [저장소] 네 관계의 from · to · cardinality: `schema.json`(사실표 2.5). 한 줄 표기는 원문의 관계 정의를 **줄인 것**이다. 오일 쿨러 → TS1 · CE: 실측 조회.

## SLIDE 77 — MATCH와 RETURN: 찾을 모양과 돌려받을 것
### 화면 내용
- 유형: 코드
- 메시지: MATCH에는 찾을 모양을, RETURN에는 돌려받을 것을 적으며, 모양에 맞는 것마다 한 행이 나온다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과 ── / "오일 쿨러"   "TS1" / "오일 쿨러"   "CE"
- 요소:
  1. **MATCH** | 찾을 모양을 적는 자리이다. 이름이 오일 쿨러인 구성 요소에서 MONITORED_BY로 이어진 센서를 찾는다.
  2. **RETURN** | 돌려받을 것을 적는 자리이다. c.name, s.tag는 찾은 구성 요소의 이름과 센서의 태그이다.
  3. 결과 | 모양에 맞는 것이 둘이므로 두 행이 나온다.
- 노트: 조회의 첫 낱말은 MATCH입니다. 이 질의는 오일 쿨러를 재는 센서는 무엇인가라는 질문이고, 센서가 몇 개인지는 적지 않았습니다. 모양에 맞는 것을 모두 찾는 것이 MATCH의 동작입니다. MATCH만으로는 아무것도 보이지 않으므로 RETURN에 구성 요소의 이름과 센서의 태그를 달라고 적었습니다. 오일 쿨러는 TS1과 CE 두 채널로 계측되므로 두 행이 나옵니다.
### 제작 기준
확정 실라버스의 「MATCH · WHERE · RETURN을 통한 조회」. 질의는 사실표 2.3의 [실측] 질의에서 구성 요소 → 센서 구간만 남기고 출발점을 오일 쿨러로 바꾼 **줄인 것**이다. [실측] 2026-10-11 읽기 전용(`cypher-shell --access-mode read`)으로 `MATCH (c:Component {name:'오일 쿨러'})-[:MONITORED_BY]->(s:Sensor) RETURN c.name, s.tag`를 실행한 결과 두 행.

## SLIDE 83 — CREATE와 MERGE: 새로 만들기와 찾아서 만들기
### 화면 내용
- 유형: 코드
- 메시지: MERGE는 식별자로 먼저 찾아 없을 때만 만들므로 CREATE와 달리 같은 노드를 중복해 만들지 않는다.
- 코드: CREATE (s:Sensor {id: 'sen:ts1', /                   name: '유온 센서', /                   tag: 'TS1'}) /  / MERGE (s:Sensor {id: 'sen:ts1'}) / SET s.name = '유온 센서', /     s.tag  = 'TS1'
- 요소:
  1. **CREATE** | 적은 대로 새로 만든다. 이미 있는지는 보지 않는다. Sensor 레이블이 붙고 속성 셋을 가진 노드 하나가 만들어진다.
  2. **MERGE** | id가 sen:ts1인 센서가 있으면 그 노드를 쓰고, 없으면 만든다.
  3. SET | 찾았거나 만든 노드의 속성에 값을 넣는다.
  4. 식별자로 찾는다 | MERGE의 괄호 안에는 식별자만 적고 나머지 속성은 SET에 적는다.
- 노트: 조회 다음은 만들기이고 표기는 조회와 같습니다. 먼저 위의 CREATE는 괄호 안에 적은 레이블과 속성대로 노드를 만듭니다. 다음으로 아래의 MERGE는 먼저 찾아봅니다. 무엇을 같다고 볼지는 괄호 안에 적은 것으로 정해지므로 그 자리에는 식별자를 적습니다. 이름까지 넣으면 이름을 고쳐 다시 실행했을 때 같은 노드를 찾지 못합니다.
### 제작 기준
확정 실라버스의 「CREATE를 통한 생성」. [일반] CREATE의 동작. [저장소] 속성값은 `sen:ts1`의 실제 값. 저장소에서 CREATE를 쓰는 곳(`manual_graph.py:346`, `skill_graph.py:101`)의 꼴에 실제 값을 넣은 **줄인 것**이며 이 문장은 실행하지 않았다. 확정 실라버스의 「MERGE를 통한 기존 대상 조회 또는 생성」. [저장소] `MERGE (n:Sensor {id: r[0]}) SET n.name = r[1], n.tag = r[2], …`(`instances.cypher:135`)에 실제 값을 넣고 unit · virtual을 뺀 **줄인 것**(「℃」를 코드 칸에 쓸 수 없다). 새 용어: SET.

## SLIDE 84 — 같은 문장을 두 번 실행했을 때
### 화면 내용
- 유형: 비교
- 아이콘: copy, circle-check
- 메시지: 같은 문장을 다시 실행하면 CREATE는 같은 노드를 또 만들려 하고, MERGE는 결과가 달라지지 않는다.
- 요소:
  1. CREATE를 두 번 | 같은 센서를 한 번 더 만들려고 한다 / 유일 제약이 있으면 Neo4j가 거절한다 / 없으면 같은 센서가 둘이 된다 | 실행할 때마다 새 기록이 필요한 데이터에

- 노트: 설비나 센서처럼 한 번만 있어야 하는 지식은 MERGE로 넣습니다. 넣다가 멈추어 처음부터 다시 실행해도 중복이 생기지 않습니다. CREATE는 작업 기록처럼 실행할 때마다 한 건이 새로 생겨야 하는 데이터에 씁니다.
