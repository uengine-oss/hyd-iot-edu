## SLIDE 16 — 두 대상의 짝에 붙는 속성
### 화면 내용
- 유형: 코드
- 메시지: 부품과 공급사의 짝마다 달라지는 단가와 납기는 둘을 잇는 **관계의 속성**으로 둔다.
- 코드: "type": "SUPPLIED_BY", / "from": ["Part"],  "to": ["Supplier"], / "cardinality": "N:M", / "properties": [ /   {"name": "price",    "type": "number", "required": true}, /   {"name": "failRate", "type": "number", "required": true}, /   {"name": "leadDays", "type": "number"} ] /  / 펌프 축 씰 키트의 공급 조건 / A정밀:     price 35, failRate 0.12, leadDays 2 / B-OEM:     price 55, failRate 0.02, leadDays 5 / C트레이딩: price 20, failRate 0.30, leadDays 1

## SLIDE 40 — 온톨로지 스키마와 DB 제약
### 화면 내용
- 유형: 비교
- 아이콘: schema, lock
- 메시지: 스키마는 옳은 데이터의 조건을 정하고, **DB 제약**은 그중 저장할 때 데이터베이스가 직접 막는 조건이다.
- 요소:
  1. 온톨로지 스키마 | 클래스 → 레이블, 관계 유형 → 관계 유형, 속성 → 속성으로 옮겨진다 / 필수 속성 · 자료형 · 허용값 · 끝 클래스 · 카디널리티를 정한다 / 별도 검사기가 필수값 · 허용값 · 끝 클래스를 확인한다 / 자료형 전체와 카디널리티는 자동 검사되지 않는다 | 의미 모델의 정의
  2. **DB 제약(DB Constraint)** | 데이터베이스에 걸어 두어 저장하는 순간 검사하는 조건이다 / 유일 제약(Unique Constraint): 같은 레이블의 노드끼리 id가 겹치지 않는다 / 예: id가 sen:ts1인 Sensor 노드를 또 만들면 저장을 거절한다 | 저장할 때 강제
- 노트: 스키마는 지식이 어떤 모양이어야 하는지를 정한 의미 모델이고, 그 정의는 그래프 DB에서 레이블, 관계 유형, 속성으로 옮겨집니다. 그러나 스키마의 제약이 모두 데이터베이스의 제약이 되는 것은 아니며, 여기서 예로 든 Sensor 노드에는 id 유일 제약이 걸려 있습니다. 필수 속성, 허용값, 끝 클래스는 저장된 데이터를 읽어 스키마와 대조하는 검사가 확인하고, 자료형 전체와 카디널리티는 이 검사기가 자동으로 확인하지 않으므로 별도로 대조해야 합니다. 그래서 같은 id의 센서를 또 만들면 저장할 때 거절되지만, tag가 빠진 센서는 저장된 뒤 검사에서 드러납니다.

## SLIDE 41 — Cypher 쿼리와 실행 화면의 역할
### 화면 내용
- 유형: 풀이
- 메시지: 저장된 그래프는 **Cypher 쿼리**로 꺼내고 만들며, 쿼리는 찾을 노드와 관계의 모양을 글자로 적는다.
- 요소:
  1. 질의(Query) | 데이터베이스에 보내는 요청 한 건이다. 무엇을 찾거나 만들지를 적는다. / 쿨러 사건에서 경보로부터 원인 후보를 찾은 것도 그래프에 보낸 질의였다. |
  2. **Cypher 쿼리(Cypher Query)** | 그래프 DB에 보낼 요청을 노드와 관계의 패턴(Pattern)으로 적는 질의 언어이다. / Neo4j에서 시작해 공개 사양 openCypher로 여러 그래프 DB가 쓰며, 국제 표준 GQL의 바탕이다. |
  3. 질의 실행 화면 | 사람이 질의를 입력해 실행하고 결과를 표와 그래프로 보는 화면이다. / Neo4j Browser 같은 것이 있으며, 포털의 지식 지도와는 별개이다. | 사람이 쓰는 창구
- 노트: 그래프 DB에 들어 있는 것을 꺼내 보려면 질의를 보냅니다. 이 과정은 그래프 DB 전용 질의 언어인 Cypher로 쿼리를 적으며, Cypher 쿼리는 찾고 싶은 노드와 관계의 모양을 그림 그리듯 글자로 적습니다. 쿨러 사건에서 에이전트가 관계를 따라 원인 후보를 찾은 것도 이런 질의였고, 사람이 실행 화면에 적는 질의와 같은 언어입니다. 실행 화면은 데이터베이스에 딸린 창구이고, 포털의 지식 지도는 기준 지식의 속성과 연결을 살피는 화면입니다.
### 화면 구성
풀이 셋(질의 → Cypher 쿼리(강조) → 실행 화면). Cypher는 이 단원이 가르치는 질의 언어이므로 제목 · 메시지에 이름을 쓴다(기준 16번 단서).
### 제작 기준
실라버스:21의 「Neo4j Browser의 역할을 소개」. [일반] 질의 · 질의 언어 · 패턴의 정의. [저장소] Browser는 Neo4j에 딸린 웹 화면이며 포털과 별개(사실표:240, 352), 에이전트의 원인 후보 조회가 그래프 질의(`it/neo4j/templates/t1_causes.cypher:3`, 사실표:256-261). 접속 주소 · 계정과 화면의 모양은 싣지 않는다. Cypher는 실라버스:21이 이름을 들어 가르치는 질의 언어라 전문 용어로 제목 · 메시지 · 용어 칸에 둔다(기준 16번 단서, 사용자 지시 2026-10-15). openCypher · Amazon Neptune · GQL: opencypher.org/projects, docs.aws.amazon.com/neptune(openCypher), neo4j.com 블로그(GQL ISO 2024-04). ## SLIDE 43 — 패턴 조회와 반환 결과의 형태
### 화면 내용
- 유형: 코드
- 메시지: 질의는 찾을 패턴과 돌려받을 항목을 적으며, 패턴에 맞는 것 하나가 결과의 한 행이 된다.
- 코드: MATCH (c:Component {name: '오일 쿨러'}) /       -[:MONITORED_BY]->(s:Sensor) / RETURN c.name, s.tag /  / ── 결과: 속성값 두 행 ── / "오일 쿨러"   "TS1" / "오일 쿨러"   "CE" /  / MATCH (c:Component {name: '오일 쿨러'}) /       -[r:MONITORED_BY]->(s:Sensor) / RETURN c, r, s /  / ── 결과: 노드 · 관계 · 노드 두 행 ── / (:Component)  [:MONITORED_BY]  (:Sensor {tag: "TS1"}) / (:Component)  [:MONITORED_BY]  (:Sensor {tag: "CE"})
- 요소:
  1. **MATCH** | 찾을 패턴을 적는 절이다. 이름이 오일 쿨러인 구성 요소에서 MONITORED_BY로 이어진 센서를 모두 찾는다.
  2. **RETURN** | 돌려받을 항목을 적는 절이다. 적은 항목 하나가 결과의 열 하나이다.
  3. 결과의 행 | 같은 쿨러가 TS1·CE에 이어져 두 행이다. 행마다 이름이 반복돼도 쿨러 노드는 하나이다.
  4. 반환의 형태 | 위처럼 속성값을 받으면 표가 된다. 아래처럼 노드 · 관계를 받아야 그래프로 그릴 수 있다.
- 노트: 이 질의는 오일 쿨러를 재는 센서가 무엇인지를 묻고, 센서가 몇 개인지는 적지 않았습니다. 찾을 패턴에 맞는 것을 모두 찾는 것이 MATCH의 동작이고, RETURN에 구성 요소의 이름과 센서의 태그를 달라고 적었으므로 결과는 두 열입니다. 한 행이 패턴에 맞는 연결 하나여서, 첫 행은 오일 쿨러에서 TS1로 가는 연결입니다. 여기처럼 속성값만 돌려받으면 결과는 표로 읽고, 결과를 그래프로 보려면 노드나 관계, 경로 자체를 돌려받아야 합니다.
### 화면 구성
왼쪽 질의와 실제 결과 두 행, 오른쪽 짚을 점 넷.
### 제작 기준

[일반] 속성값을 반환하면 결과는 표이고, 그래프 표시는 노드 · 관계 · 경로를 반환할 때 된다(설계:200). [시간 보강] 두 결과 행에 반복되는 이름과 실제 노드 수를 구별하도록 화면 풀이를 구체화한다. 근거: it/neo4j/v2/instances.cypher:132-136; .evidence/2회차_덱/질의_실측.md:7.

## SLIDE 45 — 조건 절과 값의 존재 여부
### 화면 내용
- 유형: 코드
- 메시지: 조건 절로 한계가 있는 물리량만 남기면 인터록 기준 셋이 나온다.
- 코드: MATCH (s:Sensor)-[:OBSERVES]->(v:StateVariable) / WHERE v.limit IS NOT NULL / RETURN s.tag, v.name, v.limit, v.unit / ORDER BY s.tag /  / ── 결과 ── / "PS1"  "토출 압력"  130  "bar" / "TS1"  "유온"       65   "℃" / "VS1"  "팬 진동"    2.0  "mm/s" /  / WHERE v.limit > 100 으로 바꾸면 / "PS1"  "토출 압력"  130  "bar"
- 요소:
  1. **WHERE** | MATCH가 찾은 것 가운데 조건에 맞는 것만 남기는 절이다.
  2. IS NOT NULL | 값이 있는 것만 남긴다. 한계가 정해진 상태 변수 셋이 남는다.
  3. 수의 비교 | limit이 number라서 v.limit > 100처럼 크기를 비교할 수 있다.
  4. 한계의 방향 | 유온 > 65 ℃, 팬 진동 ≥ 2.0 mm/s, 토출 압력 < 130 bar이면 인터록이 걸린다.

### 제작 기준
[실측] `MATCH (s:Sensor)-[:OBSERVES]->(v:StateVariable) WHERE v.limit IS NOT NULL RETURN s.tag, v.name, v.limit, v.unit ORDER BY s.tag` → 세 행, `WHERE v.limit > 100` → PS1 한 행(2026-10-15, 구조판 · 전체판 같음). `limit`의 설명 「인터록 한계」(`schema.json:639-`). 한계의 방향: 「PS1 < 130 bar 저압 인터록」 「VS1 ≥ 2.0 mm/s 진동 인터록」 「인터록 65 ℃까지의 여유」(`instances.cypher:158-163`). 인터록 세 가지는 1회차 덱 16장. 원 80을 옮기고 단위 열과 한계의 방향을 보탰다(설계:113, 205). 제목에서 절 이름을 뺐다. 새 용어: WHERE, IS NOT NULL.

## SLIDE 48 — 노드 생성과 병합의 식별자
### 화면 내용
- 유형: 코드
- 메시지: 다시 실행해도 같은 대상이 하나로 남게 하려면, 바뀌지 않는 식별자로 찾고 없을 때만 만든다.
- 코드: CREATE (s:Sensor {id: 'sen:ts1', /                   name: '유온 센서', /                   tag: 'TS1'}) /  / MERGE (s:Sensor {id: 'sen:ts1'}) / SET s.name = '유온 센서', /     s.tag  = 'TS1', /     s.unit = '℃' /  / ── sen:ts1이 이미 있을 때 CREATE의 결과 ── / Node already exists with label `Sensor` /   and property `id` = 'sen:ts1'
- 요소:
  1. **CREATE** | 적은 대로 새 노드를 만든다. 이미 있는지는 보지 않는다. sen:ts1이 이미 있으면 유일 제약에 걸려 거절된다.
  2. **MERGE** | 패턴에 맞는 노드를 찾고 없으면 만든다. 이 예는 id 유일 제약 아래 같은 id로 반복 실행한다.
  3. SET | 찾았거나 만든 노드의 속성에 값을 넣는다.
  4. 식별자로 찾는다 | 괄호 안에는 바뀌지 않는 id만 적는다. 이름까지 넣으면 이름을 고친 뒤 같은 노드를 찾지 못한다.
- 노트: 조회 다음은 만들기이며 표기는 조회와 같습니다. 위의 CREATE는 이미 있는지 보지 않고 새로 만들므로, 같은 id가 이미 있으면 유일 제약 때문에 저장이 거절됩니다. 아래의 MERGE는 괄호 안의 패턴으로 먼저 찾고 없을 때만 만들므로, 설비나 센서처럼 한 번만 있어야 하는 지식을 넣다가 멈추어 처음부터 다시 실행해도 중복이 생기지 않습니다. 무엇을 같다고 볼지는 괄호 안에 적은 것으로 정해지므로, 바뀔 수 있는 이름은 SET으로 넣고 괄호에는 식별자만 적습니다. CREATE는 문서를 적재할 때마다 기록이 한 건씩 새로 생겨야 하는 곳처럼 실행마다 새 대상이 필요한 데이터에 씁니다.
### 화면 구성
위 CREATE, 아래 MERGE와 SET. 오른쪽 짚을 점 넷.
### 제작 기준
실라버스:21의 「CREATE를 통한 생성, MERGE를 통한 기존 대상 조회 또는 생성」. [저장소] 시드의 `MERGE (n:Sensor {id: r[0]}) SET n.name = r[1], n.tag = r[2], n.unit = r[3], …`(`instances.cypher:132-135`, 「MERGE만 쓰므로 여러 번 실행해도 같다」 `:2`), CREATE를 쓰는 곳(`it/process/procsvc/manual_graph.py:346` 적재 배치 기록, 사실표:294-298). [실측] 같은 id로 CREATE → 「Node(76) already exists with label `Sensor` and property `id` = 'sen:ts1'」 거절(화면에는 내부 노드 번호를 빼고 적었다), 같은 MERGE를 두 번 실행해도 sen:ts1 노드는 하나, 괄호에 `name: '온도 센서'`를 넣은 MERGE는 같은 노드를 찾지 못하고 새로 만들려다 유일 제약에 걸림(임시 그래프에서 시험). MERGE는 패턴의 일치로 동작하며 고유성은 제약과 함께 다룬다(설계:202). 원 83(CREATE와 MERGE) · 84(두 번 실행)를 합쳤다. 제목과 메시지에서 절 이름을 뺐다. 새 용어: CREATE, MERGE, SET.
