## 관계 제안 (11종, 46개)

방향은 모두 관계도의 화살표와 같게 잡았습니다.

| type | from → to | 읽는 문장 | 개수 |
|---|---|---|---|
| `HAS_COMPONENT` | Asset → Component | 설비는 구성 요소를 가진다 | 18 |
| `MOUNTED_ON` | Sensor, Actuator → Component | 센서와 구동기는 구성 요소에 붙어 있다 | 9 |
| `MEASURES` | Sensor → StateVariable | 센서는 상태 변수를 잰다 | 5 |
| `CONTROLS` | Actuator → StateVariable | 구동기는 상태 변수를 바꾼다 | 3 |
| `USES_PART` | Component → Part | 구성 요소는 부품을 쓴다 | 3 |
| `SHOWS` | Sensor → Symptom | 센서는 증상을 보여 준다 | 2 |
| `INDICATES` | Symptom → FailureMode | 증상은 고장 유형을 가리킨다 | 2 |
| `CAUSES` | Cause → FailureMode | 원인은 고장 유형을 일으킨다 | 1 |
| `MITIGATED_BY` | FailureMode → Skill | 고장 유형은 조치로 완화된다 | 1 |
| `OCCURS_IN` | FailureMode → Component | 고장 유형은 구성 요소에서 일어난다 | 1 |
| `RELATED_TO` | Cause → Part | 원인은 부품과 관련된다 | 1 |

- **`HAS_COMPONENT` 18개**: 세 설비가 구성 요소 6개를 각각 가리킵니다.
- **`MOUNTED_ON` 9개**: 센서 5개에 구동기 4개입니다. 펌프 전환 밸브는 주 펌프와 예비 펌프 두 곳에 붙습니다.
- **잇지 않는 것**: 설비와 센서 · 구동기 · 부품은 직접 잇지 않고 구성 요소를 거칩니다. `팬 최대 운전`과 `팬 인버터`는 자료에 이어져 있지 않아 잇지 않습니다.

## 정해 주셔야 하는 것

1. **새 클래스 넷의 접두사**: `sym:`, `fm:`, `cause:`, `skill:`로 해도 될까요?
2. **식별자의 붙임표와 숫자**: 「영문 소문자」에 붙임표와 숫자를 허용해도 될까요(`comp:oil-cooler`, `asset:hyd-01`)? 숫자는 `sen:ts1`에 이미 들어갑니다.
3. **펌프 전환 밸브의 `A|B`**: 목록의 「단위」 칸에 있지만 단위가 아니라 고를 수 있는 값입니다. 구동기에 `options: ["A", "B"]`(string[], 선택) 속성을 더하고 `sv:pump-select`에는 `unit`을 적지 않는 쪽을 권합니다. 이 경우 `unit`은 선택 속성이 됩니다. 다른 길은 `unit: "A|B"`로 목록 그대로 두는 것입니다.
4. **한계의 방향**: `limit` 숫자만으로는 65가 상한이고 130이 하한이라는 것이 사라집니다. 목록 비고의 문장을 그대로 담는 `limit_note`(string, 선택) 속성을 권합니다(예: 「130 bar 미만에서 저압 인터록」). TS1의 비고는 「65 ℃에서 인터록」뿐이라 상한 · 하한으로 나눠 적으면 제가 짐작하게 됩니다. 속성을 더하지 않으면 방향은 파일에 남지 않습니다.
5. **상태 변수의 `aliases`**: HYD-02의 이름(오일 온도, 펌프 압력 등)은 목록에 「다른 이름」이라고 적혀 있지 않고, 태그가 같아서 제가 같은 것으로 본 것입니다. `aliases`에 넣어도 될까요?
6. **「보여 준다」의 시작**: 관계도대로 `Sensor → Symptom`으로 두는 쪽을 권합니다(판정 `같음`). `StateVariable → Symptom`으로 바꾸면 8, 9번은 `다르게 표현`이 됩니다.
7. **`tag` 속성 이름**: 센서의 태그와 구동기의 신호 이름을 둘 다 `tag`로 적어도 될까요, 아니면 구동기는 `signal`로 나눌까요?
