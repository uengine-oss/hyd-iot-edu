## 대본에서 설명하는 법 (1회차 환경 준비, 두 과정 공통)

- VS Code는 파일을 열고 고치고 실행하는 작업 공간, Git은 프로젝트를 내려받고 변경 이력을 관리하는 도구로 쉽게 말한다. IDE처럼 처음 보는 용어를 설명 없이 쓰지 않는다. GitHub Copilot · Codex는 요구를 전달하고 코드 작성 · 수정 · 결과 확인을 함께 하는 AI 코딩 도구로 소개한다(「확장 프로그램」 같은 분류 중심 소개 X).
- Docker는 다른 도구보다 필요성을 충분히 설명한다: 필요한 서비스를 하나하나 설치 · 설정하는 부담을 줄이고 준비된 환경을 실행한다는 이유에서 출발한다. 이미지 · 컨테이너 · 접속 포트 · 데이터 보관은 실제 화면과 설정에서 필요한 만큼만 잇고, 개념을 먼저 길게 강의하거나 옵션을 다 풀지 않는다. 실제 설치 목록을 확인해 「전부 Docker 안에 있다」고 단정하지 않고, 근거 없는 「나머지 실행 도구」 항목을 만들지 않는다.
- 공식 다운로드 위치를 보여 주고 설치 완료 상태에서 진행한다. 설치 대기 · 계정 로그인은 늘리지 않는다. 설치 중에는 중요한 옵션의 이유만 짧게 짚는다.

## 먼저 볼 촬영 순서

**Python → Node.js → VS Code(한국어·Codex·첫 채팅 포함) → Git → WSL → Docker.** GitHub HTTPS 주소 복사·git clone·Git Bash 실행 뒤 포털 설명으로 이어간다. 기존 원본은 보존하고 편집 순서 변경만으로 재촬영하지 않는다. Git 이름·이메일·로그인·커밋은 제외한다.

Git·WSL은 공식 최신 안정판. 나머지는 VS Code 1.143.0 / Node.js 24.16.0 / Python 3.14.7 / Docker Desktop 4.87.0 이상. WSL 2의 실행 방식은 유지하되 버전 번호를 고정하지 않는다.

## 설치 구간의 말과 행동 — 최신 사용자 확정

설치 구간에서는 해당 행동의 설명이 먼저 시작됐다면 바로 조작해도 된다. 문장 전체가 끝날 때까지 기다리지 않으며 말은 다음 동작 안내까지 자연스럽게 이어질 수 있다. “창을 닫고”처럼 익숙한 동작은 짧게 말하며 진행한다. 중요한 옵션·개념만 필요한 순간에 이유를 설명하고 실제 원본 영상에 맞춰 유연하게 음성을 편집한다. 다른 실습 전체로 이 예외를 확대하지 않는다.

아래 과거 표의 행동 전·후 초는 원본 확보 참고값이며 강제 대기가 아니다. 설치·다운로드·재부팅·응답은 실제 완료 신호로 확인한다. Python·Node.js는 버전과 실행 경로를 확인하고, 다른 프로그램의 버전 명령 화면은 설치 영상에 의무적으로 넣지 않는다. 중요한 선택과 실제 완료는 보존한다. 인증 정보는 녹화하지 않는다.

## WSL 도입·조작 대본 — 실제 영상에 맞춰 적용

“여기서는 우분투를 별도로 설치하지 않겠습니다. 프로젝트 명령은 윈도우의 깃 배시에서 실행하고, 도커가 필요한 리눅스 실행 환경은 직접 관리하기 때문입니다. 지금 준비할 더블유에스엘 투는 도커가 사용할 실행 기반입니다.”

“먼저 버전 확인 명령을 입력해 보겠습니다.” → `wsl --version`. 이번 PC에서는 이 호출 후 Ubuntu 없이 WSL 설치가 진행됐다고 사용자가 확인했다. 실제 영상이 이 흐름이면 설치 안내와 결과에 맞춰 설명한다. 다른 PC에서도 무조건 자동 설치된다고 말하지 않는다.

미설치 오류만 나오는 경우의 안내는 “이 환경에서는 설치 명령으로 기반만 준비하겠습니다.” → `wsl --install --no-distribution`. 기존 설치 업데이트는 `wsl --update`. 기본 `wsl --install`만 입력하거나 Ubuntu 사용자 이름·암호를 만드는 장면은 제외한다. Docker가 만드는 `docker-desktop`은 정상 구성이다.

## 시작 구간 — Codex 별도 담당

프로젝트 루트의 VS Code Git Bash 터미널에서 `bash scripts/start_all.sh`를 입력한다. 시작 BAT 없이 같은 스크립트를 실행하는 경로다. Docker·설정·포트·Supabase·이미지 다운로드/빌드·Compose·MCP·응답 확인을 포함한다. `docker compose up` 단독은 앞뒤 준비를 모두 대신하지 않는다. VS Code 터미널에 무해한 echo 명령을 실제 입력·실행하는 Computer Use 시험은 성공했으며 서비스 시작은 아직 수행하지 않았다.

**다음 문단은 삭제 전 조사 이력이다. 이후 사용자가 Docker 제거를 알리고 WSL·Ubuntu 전체 삭제를 요청했다. 현재 상태는 새로 확인해야 한다.** 당시에는 Docker 삭제를 보류했다. 약 23.1GiB의 docker_data.vhdx가 존재한다. 보존할 데이터와 복구 가능한 백업을 확인하지 않았으므로 Docker 파트는 조건부다. WSL·Ubuntu 등록 해제, 데이터 디스크 삭제는 이 촬영 준비에 포함하지 않는다. [Docker 백업 안내](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/).

VS Code·Git·Node·Python은 한 번에 지우지 않고 한 프로그램씩 재설치와 확인을 마친 뒤 다음으로 넘어간다. Python 제거가 기존 가상환경에 미치는 영향은 제거 직전 확인한다. Node 전역 도구에는 Claude Code·Gemini CLI·agent-browser·bun·Supabase·codegraph가 확인됐다. Node를 제거하는 동안 이 도구들의 실행이 중단될 수 있으므로 사용 중 세션을 임의로 끊지 않고 해당 파트 직전에 종료·복구를 준비한다. 현재 작업은 읽기 확인·문서 준비이며 제거·설치·업데이트·서비스 실행은 수행하지 않았다.

## 사용자 촬영 이후 — Codex 담당

README 도구 역할 설명과 공식 링크 안내를 EGO로 연결하고, 받은 원본을 위 순서로 편집한다. 안치윤 음성은 중요한 선택의 이유를 짧게 연결하고, 해당 행동의 안내를 시작한 뒤 실제 행동과 자연스럽게 겹칠 수 있게 배치한다. 이 유연성은 설치 구간에만 적용한다. 프로그램별 분할 촬영과 다운로드·재부팅 대기 축약은 이번 사용자 허용 범위다.

시스템 시작 촬영은 Codex가 실행·수집을 준비하고 EGO로 README·포털 설명을 맡는다. EGO가 Windows 터미널을 직접 조작한다고 표현하지 않는다. 필요 시 실제 실행 입력만 사용자에게 요청할 수 있으나 이번 사용자 촬영 종료점은 첫 채팅이다. 시작 경로·권한·포트·데이터 영향 검증 전에는 시스템을 실행하지 않는다.

현재 scripts/start_all.sh 전체를 읽어 Docker → 설정·포트 → Supabase → Compose → MCP → 서비스·포털 응답의 연결을 확인했다. 준비 중 이미지·명령 설명은 실제 진행 단계에 맞춘다. Python 보조 코드는 프로젝트 코드다. 현재 공개 ZIP과 로컬 미커밋 시작 코드가 달라 BAT 없는 실행은 준비 완료로 표시하지 않는다. 시작 BAT 차단도 해결된 것으로 보지 않는다. 이 미확인은 프로그램 설치·첫 채팅 촬영과 분리한다.

원본 수령 후: 실제 설치 화면에 맞춰 원고 수정 → 음성 생성·길이 측정 → 설명 종료 뒤 조작되도록 편집 → 실제 움직임·가독성·전체 음성 재생 확인. 파일 생성·디코드만으로 완성 판정하지 않는다. 점검.bat은 영상에 넣지 않는다.

## README 반영·게시 상태

로컬 README는 프로젝트 목적·구성·필수 프로그램·공식 링크·프로젝트 main ZIP·시작/종료·기존 BAT 접기 구조로 수정했다. README에는 수업·강사·촬영 진행을 쓰지 않는다. 역할 설명·화면 전환·말의 순서는 이 대본과 큐표에서만 다룬다. BAT 코드는 변경하지 않았고 Git·WSL을 과거 최소 기준으로 유지할 수 있다는 차이를 명시했다. 즉 최신 확인은 공식 경로에서 한다. GitHub 게시 전에는 온라인 README가 이 준비판과 같다고 안내하지 않는다. 조사 시 원격 main/develop은 8ecc6ae8, 로컬 develop은 2fbc50d8이며 다른 작업의 미커밋이 많다. 이번에는 전체 커밋·체크아웃·리셋·stash·강제 동기화를 하지 않는다.
